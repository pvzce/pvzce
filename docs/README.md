# 文档台账

> 这一页回答两个问题：**docs/ 里每一份是什么**，以及**一次任务收尾时该动哪几份**。
> 分工（避免三份文档互相抄）：
> - **本页 = 数据**：每份文档一行 —— 它是什么、属于哪一档、什么时候才改；
> - `验证约定.md` §8 = **规则**：为什么这么分档、三条老规矩（as-built 只写现状 / 一个事实只写一处 / 没传遍所有文档的义务）；
> - `AGENTS.md`（仓库根）= **动作**：收尾时按什么顺序做哪几件事。
>
> 新增或删除文档时改这一页；`DocLedgerTest` 会检查 `docs/` 下的每一份 `.md` 都在表里，
> 所以新文档不会悄悄逃过归属认定。

---

## 1. 三档归属

| 档 | 含义 | 收尾时 |
|---|---|---|
| **活·每轮过一遍** | 描述现状或待办，几乎每轮都可能有变化 | 打开看一眼，"这轮动到它了吗" |
| **活·按条件写** | 只在它描述的那件事真的变了时才改 | 按表的"什么时候改"逐条对 |
| **冻结** | 某个时间点或某一轮的快照，**永不回写** | 不动；要改先问用户 |

一条硬规矩：**冻结文档里的数字与结论过时了也不改**——它们是历史，改了就不是记录了。
发现冻结文档与现状冲突时，改的是活文档，最多在活文档里写一句"（`01` 的规划写法已被 X 取代）"。

### 2.3 历史、教训与规范

| 文档 | 定位 | 档 | 什么时候改 |

### 2.4 冻结（不随任务更新）

| 文档 | 定位 | 档 |
|---|---|---|
| `01-第一阶段-核心底层.md` | 第一阶段规划 | 冻结 |
| `02-第二阶段-广度开发.md` | 第二阶段规划 | 冻结 |
| `03-第三阶段-精修完善.md` | 第三阶段规划与第四阶段提纲 | 冻结 |
| `关卡机制与拼装式编辑器-设计方案.md` | 机制数据层与编辑器的设计方案（已实施） | 冻结 |
| `报告/*`（任务收官报告与调研，每份都是某一轮的快照） | 某一轮任务的收官报告或调研 | 冻结 |
| `mod-guide/*`（README / json-reference / rendering / animation） | 给**第三方 mod 作者**的对外文档 | 冻结·仅用户点名时改 |

`mod-guide` 为什么不跟：它描述的是**对外承诺的接口**，内部实现与关卡内容的改动不欠它一笔。
改了对外契约（内容 JSON 字段、`fabric.mod.json`、注册入口）才需要动它，且由用户点名。

## 3. 一轮任务的收尾顺序

1. **先确认行为/画面通过**（`验证约定.md` §1、§10），再写文档 —— 回退时那份记录要重写第二遍。
2. 按上面第 2 节的三张活文档表逐条对："这轮动到它了吗"。
3. 具体动作清单与命令模板见 `AGENTS.md` 的「收尾」一节与 `验证约定.md` §12。
4. 跑 `python3 tools/doc_check.py`：改了源码却没改文档时它会点名候选文档（提醒，不是门）。
5. **`docs/**` 与 `AGENTS.md` 是 `:pvzce-game:test` 的输入**，所以改完文档再跑一次测试，
   三条守门会重新执行（数秒）：`DocumentedSymbolsTest`（文档里的类/方法真的存在）、
   `DocStatsTest`（规模统计块与实际一致）、`DocLedgerTest`（每份文档都在台账里、每份归档卷都被索引链到）。

> 统计块（`当前项目架构.md` 开头那几行规模数字）不要手改：跑
> `./gradlew :pvzce-game:test --tests '*DocStatsTest*' -Ppvzce.smoke=pvzce.updateDocStats=true`
> 由测试写回，之后不带开关再跑一次确认同步。
