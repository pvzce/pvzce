## 架构文档指着 9 个不存在的符号
> 现象由 `DocumentedSymbolsTest` 报出（现状见 `当前项目架构.md`）

- **现象**：`当前项目架构.md` 与 `UI切换与导航架构.md` 是"现状"文档，写错的方式不是含糊，而是**指着一个被删掉的类或改过名的方法**——读者顺着指针走进空处。一次重构后一次性查出 7 处：`PvzceConstants.SAVE_DATA_VERSION`（本轮删除，文档还在说"写进每份存档"）、`PvzcePlayer.createPlantPlayer`（变成 `DeckCardSource` + `PvzcePlayer.deckSlots`）、`EntityVisuals.CHARMED_TINT`（拆成 `_R/_G/_B` 三个分量）、`InGameScreen.renderSlots`（抽成 `SeedCardBar`/`BeltCardBar` 两个 `CardBar` 实现）、`LevelValidator.validateSeedSelection`（从未叫过这个名字，真实归属是 `SeedSelection.sanitize` + `SlotResolver.reportUnknown` + `LevelValidator.describeFixedDeck`）、`LevelMove.saveKeyAfterMove`（客户端抄本已删，规则只剩 `LevelKey`）、`EditorScreen.renderCanvasBlock`（编辑器画布早已是 `CanvasPage.renderBoard`）。另有一处**反过来的错误**：文档说"编辑器里的水与游戏内不一致"（因为"编辑器自己画、未走 `LiquidTextures`"），实际 `CanvasPage.renderBoard` → `SceneTileRenderer` → `LiquidTextures` 走的就是同一趟液体渲染。
- **定论**：按实际符号改正这 8 处，并加 `DocumentedSymbolsTest` 钉住两类断言：文档里的全限定类名必须对应真实源文件；`` `Type.member` `` 必须在那个类型的源码里声明。文件名（`ConveyorBelt.png`）、数据/存档键（`LevelDef.playable_teams`、`PlayerProfile.UnlockedLevels`）与占位写法（`Screen.mouseXxx`）按形状排除，不进断言——否则校验会逼着文档把数据键写成 Java 字段。**这类错误以前没有任何测试能发现**：文档里关于"测试"的说法由测试自己保护，关于代码的说法谁都不保护。

## 一个音效文件有两个事件名，其中一个从没被播放过
> 清理轮发现（现状见 `架构-框架层.md` §3.5 与 `资源整理与内容扩充报告.md` §8）

- **现象**：`sounds.json` 里 15 个事件共用同一个 ogg，成对的写法是"原版音乐名"与"本项目 `music/` 名"：`sfx/misc/grasswalk` 与 `music/grasswalk`、`sfx/ui/win` 与 `music/win`、`sfx/ambient/choose_your_seeds` 与 `music/choose_your_seeds` 等。每一对里只有一个被代码/关卡引用（`PvzceMusicController` 用的是 `music/win`/`music/lose`），另一个带着自己的 `sound_events/<id>.json` 与 `sounds.json` 条目一起躺着 —— 11 个事件、11 个注册文件、11 行资产声明，描述的是已经存在的东西的第二个名字。

## "未知 JSON 键"这条通用检查做不成，原因是编解码器不对称
> 与上一条同一轮，结论保留给下一个想这么做的人

- **现象**：设想把 `validateLegacyKeys` 从"两个搬走的键"推广成"任何编解码器不读的键"—— 数据格式的未知键被静默忽略（`"max_seed_slot": 6` 拼错一个字母就完全没有效果，且没有任何提示），这是个真实的坑。最省事的实现是：把刚解码出的值**再编码一次**，用它出现的键当"已知键集合"，与文件里的键对比 —— 不需要手写字段清单，字段改了它自己跟上。
- **定论**：**这条路不通**，实测 `LevelDef.CODEC` 对 `{"id","width","height","slots","teams"}` 编码回来只有 `{"id","slots","teams"}`：DFU 的 `optionalFieldOf(name, default)` 在**值等于默认值时根本不写这个字段**（9 格宽、空名字都被省掉），所以编码结果不是 schema，拿它当已知键集合会把半个文件报成未知。通用检查需要另一条可靠来源（真做的话得从编解码器的定义里取字段名，或维护一张会漂移的表），代价不划算。保留按名字列举的 `MOVED_LEVEL_KEYS`，并把这段理由写在它旁边。

## 通关结算的规则没有测试，而它有个"只能靠打穿一关才能到达"的入口
> 清理轮发现（现状见 `架构-服务端.md` §4.5）

- **现象**：`PvzceServer` 里那一整套"这一局该发多少钱"的规则（首通/重复、解锁卡、资源折币、没用上的小推车、败局只结算捡到的钱）只能通过**真的打穿一关**到达 —— 这套规则历史上错过两次（重构漏掉"奖励只给胜局"，于是每次失败都发满额通关奖；解锁奖励被 `owns` 门住，于是"给一张你没有的卡"什么都不发），而两次都不是靠测试发现的。唯一能绕过整局流程的钩子 `awardProfileForTest` **没有任何调用者** —— 它是给测试写的，但没人用，于是"可测"只是看起来可测。
- **定论**：规则搬进新的 `RewardSettlement`（`settle` 负责编排与入账，`applyLevelRewards` 只做"关卡奖励 → 档案变化"这一步纯计算），`PvzceServer.awardProfile` 缩成"取档案 → 结算 → 存盘 → 发三个包"。同时**删掉死钩子** `awardProfileForTest`，换成真正直接调用规则的 `RewardSettlementTest`（7 例）：首通 500 / 重复 100、缺卡时**重复也照发**解锁、已拥有（含"每个档案都有的初始卡"）不发也不报、资源按 `default_value × amount` 折币并作为 `rewardItem` 上报、小推车按金币定义定价（断言具体数字 50，而不是把查找抄一遍自证）、非卡 id 与无人认识的 id 都不发。顺带一提，这条提取**当场**被文档守卫抓到：`架构-服务端.md` 里的 `PvzceServer.applyRewards` 在改名后几秒内就报红。

## 测试临时目录只增不减
> 清理轮发现（现状见 `代码规范.md` §8）

- **现象**：45 处 `Files.createTempDirectory` 从不删除任何东西：每次全量测试都在系统临时目录里留下一整套写了一半的存档、配置与数据包，且没人会再读它们。`TestContent` 更糟 —— 它每次被调用都建一个新目录，而每个需要内容的测试类都会调它一次，于是一次跑测试泄漏四十几份重复内容目录。
- **定论**：逐用例的 33 处改成 `@TempDir`（每个用例一个新目录、跑完即删、失败时还会在报告里打印路径；静态字段上的 `@TempDir` 在 `@BeforeAll` 之前建、类结束后删，`LevelRestartFlowTest` 的静态 setup 用它）；harness 里"给调用方建目录"的两处走新的 `testutil/TestDirs.create`（JVM 退出时递归删除）；`TestContent` 改成整个 JVM 共用一份。`Preconditions` 一类循环里的多目录用例改成在 `@TempDir` 下开子目录。**全仓库 `Files.createTempDirectory` 只剩 `TestDirs` 自己一处**。

## 等一个"已经发生但还没被处理"的状态：测试线程读到的是旧值
> 与上一条同一轮

- **现象**：测试里"等服务端状态"的写法有三种，其中两种不可靠：轮询 `LevelServer` 的 `plantCount()`/`aliveZombieCount()`（`entities` 是无同步的 `ArrayList`，服务端线程每 tick 才处理一次死亡，测试线程可能一直读到旧值 —— 这正是"濒死僵尸掉币"那条 flake 的根因），以及读 `entities()` 深处的实体对象。第三种（测试线程自己 tick 的单线程 harness 上做断言）是安全的。
- **定论**：`waitForCondition(() -> level()...)` **清零**，全部改成等包：放置植物等 `EntitySpawnS2C`（kind=plant），僵尸出现等同理，僵尸死亡等**死亡 clip 的 `EntityUpdateS2C`**（而不是 `aliveZombieCount() == 0`：尸体要在场上待几秒，两个事件不是一回事），恢复存档的僵尸直接读 spawn 包上的 `armor()` 与 `cellY()`。顺带合并了两份**逐字重复**的 `winLevel` 助手（`BackpackAndCoinsTest` 与 `SleepDeprivationTest`）为 `ServerHarness.winByClearingTheField()`，胜利用 `GameStateS2C` 判定，超时信息区分"没等到胜利"与"这波根本没出僵尸"（后者的症状是"掉落位置是 NaN"，指向不了原因）。**保留**的一处重叠：清场用的 `damageArea` 仍从测试线程调用 —— 服务端没有清场命令，加一条调试命令属于功能改动。

## "同一关但没有波次"在五个测试类里不是同一关
> 清理轮发现（现状见 `代码规范.md` §8）

- **现象**：`LevelDef` 是 25 个分量的 record，而"拿现成的关卡、去掉波次/换一条规则"这种需求，五个测试类各自手抄了一遍完整构造列表（`SunShroomGrowthTest`、`PoleVaultTest`、`CharmTest`、`GraveRiseTest`、`NightAreaTwoLevelsTest`）。抄本已经**分叉**：`CharmTest` 那份记得传 `playableTeams`，其余几份靠 23 参便捷构造器把它默认为空 —— 空的意思是"全部阵营可玩"，于是"2-1 去掉波次"与"1-4 去掉波次"在这一点上不是同一关。真正的代价在下一次改 `LevelDef`：加一个分量要动 21 处构造。
- **定论**：新增测试 fixture `testutil/TestLevels`（`copy(def).waves(...).rules(...).build()`，25 个分量全部可改、默认保持原值），五处抄本改为一行；`withWaves`/`withRules`/`withScene` 是三个最常用的短形式。顺带修掉一条**潜在 flake**：`MOVED_LEVEL_KEYS` 原来用 `Map.of`，两条消息的顺序在不同 JVM 运行里不定，而测试按下标断言 —— 改成 `LinkedHashMap`（诊断顺序稳定），测试的断言方式也随之不再依赖顺序。

## 内置关卡的校验从没被整体跑过
- **现象**：`LevelServer.reportLevelProblems` 会把关卡数据的每一处不一致收集起来 —— 但只在**进入这一关**的时候，写进日志。也就是说 18 个内置关卡的数据从没被作为一个整体检查过：卡池引用了不存在的植物、场景留了没涂的格子、对话指向不存在的角色，都得由碰巧打开那一关的人在游戏中途的日志里发现。
- **定论**：`BuiltInLevelsValidateTest` 对每个内置关卡跑**同一份检查清单**（`LevelValidator` 的各项 + `GameRules.validate` + `LevelMechanics.validate`），任何一条不干净就红。当前 18 关全绿 —— 这条守卫的价值不在今天，而在下一次改数据时：它把"进关卡才在日志里出现"变成"提交前就红"。

## `存档目录键` 的客户端抄本已经分叉
- **现象**：`LevelKey`（服务端）与 `LevelMove.saveKeyAfterMove`（客户端）各有一份键推导，本意是"编辑器换组不必往返服务器"。两份对世界名的净化处理不同（客户端把非法字符换成 `新世界`，服务端换成 `___`），于是同一个世界在两边指向不同目录。
- **定论**：规则上移到 `common/util/LevelKey`（`of` / `hex` / `escapePath` / `levelDir` / `statusFile`），两边都调它，抄本删除；世界名净化统一到 `WorldPaths`。测试分两层：`LevelKeyTest` 钉规则本身（含"不同 id 永不共目录"），`LevelMoveTest` 钉换组后文件真的落在了那个键下。

- **定论**：逐条按实测改正。裸类名这一类**不进守卫测试**：文档里大量出现的 `VaseShatter`、`BossExplosion`、`ParticleScale`、`PoolCleaner` 是原版资源名，`WorldSelectScreen`、`LevelGenerator` 是**故意**出现的"已删除/未实现"名字，做成断言只会逼出一张长长的白名单。裸的下驼峰名则**进了**守卫（`DocumentedSymbolsTest.everyBareCamelCaseNameInTheDocsExists`）：资源名与数据键都不可能长成那个形状，所以这个断言的失败一定是真漂移。
