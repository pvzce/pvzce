## 舞台几何写死成 9x5，泳池的第六行没有地方放
- **现象**：`LevelStage` 只有一组常数（草坪区 `256..976 × 80..580`、格子 80×100、9 列 5 行），`board()` 把任何尺寸的棋盘按"装进这块草坪"缩放。泳池的棋盘是**九列六行**（原版后院：行距 85px，第 1 行植物 y=80，与白天草坪同一个顶端），6 行按 5 行的区域缩放会整体缩到 83%，行中心既不落在美术的草带上、水面也不可能对得上。
- **定论**：几何由**背景图**决定 —— `LevelStage.Geometry` 是"草坪矩形 + 原生格子尺寸"，`geometryFor(background)` 是唯一的查表点（`background3`/`background4` → 泳池 9×6 / 80×85，其余 → 前院 9×5 / 80×100），`PvzceCamera` 与 `PvzceClient.camera()` 的缓存键因此带上背景，选卡预览与游戏内共用同一张表。棋盘区随舞台一起变成 `80..590`（顶边仍与前院一致），`LevelStageTest.poolBoardUsesTheBackyardsOwnSixLanes` 钉住它。

## 背景里的水池是一块空白矩形，和格子网格对不上
- **现象**：`background3/4` 里水池的**内壁**是一块平涂占位矩形（白天纯白、夜晚纯蓝），量出来是 x 253..961、y 295..433；而泳池的两条水行是 y 250..420。原版把水面 sprite 单独下移约 30px 画（僵尸的脚因此落在 y=300/385，正好在水里），本引擎的水面是按格子画的 —— 直接按行画会盖住池沿上沿、池底留一条白。
- **定论**：舞台多了一个**液面帧**（`LevelStage.LiquidFrame`，世界格坐标下的 origin + 格子尺寸；普通舞台是 `CELL` = 原点 0 / 格子 1×1）。泳池的帧由那块矩形反算：`(-0.0375, 0.2235) / (0.98333, 0.81176)`，行 2..4 因此正好落在 295..433 上。绘制走 `SceneTileRenderer` 的 liquid 层参数（世界路径与 GUI 预览路径各一份缩放），**涟漪也走同一个映射**（`InGameScreen` 把 splash 的格坐标过一遍帧）——否则水花会浮在水面之上。截图核对：水面严丝合缝落在池沿内，没有白边也没有溢出。

## 僵尸一进水就淹死，而泳池的两行全是水
- **现象**：`ZombieEntity.drownInWater` 对任何 `can_swim=false` 的落地僵尸生效，而泳池的两行是水 —— 3-1 的波次会把一格一格走进去的僵尸全部淹掉。
- **定论**：泳池的僵尸**是内容**：鸭子救生圈（普通/路障/铁桶三款，救生圈是 `Zombie.reanim` 里本来就有的 `Zombie_duckytube` 轨道，其他僵尸按图片名排除、这三款保留 —— 和锥桶、铁桶同一套做法）、潜水僵尸（`pvzce:submerge`）、海豚骑士（复用 `pvzce:vault`），五个定义都写 `can_swim: true`。**出怪的行也要说清楚**，于是 `WaveDef.Entry` 多了一个 `rows`：写了的条目只在列出的行里出怪，没写仍是"任意行"，`LevelValidator.validateWaves` 报行号越界与数量为 0 的条目。泳池五关因此能写成"救生圈走水里、走路的走草坪"，而不是靠引擎猜。

## 小推车只有草坪那一种
- **现象**：`MowerData` 只描述"哪些行有车"，客户端永远播 `mechanic/lawn_mower`；泳池的水行因此跑着割草机。
- **定论**：`MowerData.kinds` 是"哪一行放哪种车"的列表（行 + 内容 id + 可选音效）。行集合 = `rows`（未写=每行）∪ `kinds` 里点名的行；车型是内容 id，客户端按 `mechanic/<path>` 取动画文件，服务端按它取启动音效（`pool_cleaner` 用 `sfx/ambient/pool_cleaner`，未写则退回割草机的）。`refer/anim/PoolCleaner.reanim` 已转换：`anim_water` 的第 0 帧当停车姿势（两张行驶 mask 的轮子每帧都在转，整段当 idle 会原地空转）、`anim_suck` 当行驶。

## 3-3 与 3-4 的奖励在仓库里没有对应物
- **现象**：泳池首通要发的四张卡里，缠绕水草**连植物定义都没有**（更不用说能力），水壶**连工具定义都没有**；两者在原版都属于泳池那一段。
- **定论**：**缠绕水草** = 新植物（25 阳光、`#c:water_plant` 标签让它只能种在水里）+ 新能力 `pvzce:drag_under`（走进格子的一只落地僵尸被拖下水：瞬杀、护甲不挡、然后植物自己消耗掉；"拖下去"是 `anim_grab` 片段，实机效果立刻发生、片段只负责播完，与爆炸植物的 `linger_ticks` 同一个取舍）。原版连巨人一起免疫的那条**没有实现**：水草只能种在水里、水里只站得住会游泳的僵尸、而今天会游泳的全是普通体型 —— 规则够不着，等有了"会游泳的大块头"再加回去（能力类的注释里写了这一条）。
- **水壶** = 新工具（`pvzce:watering_can`，免费、无限次、600t 冷却，`pvzce:water` 效果）+ `PlantCapability.water()` 钩子（与 `wake()` 同形）。浇一次是**三件事**：回满血、催熟（有成长阶段的植物立刻长大，`ProducerCapability` 实现它）、以及"水分充足"十五秒（`PlantEntity.actionStep()` 让射手与生产者的倒计时每三拍走四拍 = 快 1/4）。点空格不消耗冷却；浇到会做事的植物会额外冒一次金光（`pvzce:potted_zen_glow`，那份为花园准备、一直没有调用点的粒子）。卡面用 `refer/im7/images/WateringCan.png`，手里的动画由 `ZenGarden_wateringcan.reanim` 转换而来。

## 3-5 不是选卡关，是原版的"小僵尸大麻烦"传送带
- **现象**：第一版把 3-5 做成了"固定卡 + 阳光"的选卡关（豌豆/樱桃/坚果/莲叶 + 阳光卡）。原版这一关是**传送带关**：`Level 3-5` 的类型就是 `Big Trouble Little Zombie`，植物**由传送带免费送来**（豌豆射手 25%、樱桃炸弹 35%、坚果墙 15%、莲叶 25%，**莲叶上限 18 张** —— 正好一格水面一张），因此这一关既没有阳光可收、也没有卡可选。
- **定论**：3-5 改成 `pvzce:conveyor`（`interval_ticks` 180 / `capacity` 7 / `initial_cards` 3，权重照原版、莲叶 `max_count: 18`）+ `slots: []` + `initial_sun: 0` + 关掉天降阳光（`sun_spawn_interval_min/max: 0`、不 `unlock_resources` 阳光）；僵尸条目 3-1 ~ 3-4 按原版各关的表对齐（3-1 去掉报纸、3-3 只留普通/路障/救生圈/潜水、3-4 去掉橄榄球与铁门），泳池几关的名单从此与原版逐关一致。

## 3-5 的小僵尸不是小鬼，是普通僵尸被缩小
- **现象**：第二版把"小号身体"理解成了小鬼（`pvzce:imp`，血量 120），再用规则 `zombie_speed_multiplier: 1.6` 表达"又小又快"。原版那一关并不换身体：场上的僵尸**就是普通僵尸本身被缩放**（小鬼的身体在原版是另一件事），血量取四分之一、移动与啃咬快一倍，**判定框却不跟着缩小**。
- **定论**：新增六个 `pvzce:mini_*` 定义（普通 / 旗帜 / 路障 / 橄榄球 / 鸭子救生圈 / 潜水），每个都**借父定义的整份动画文件** —— `animation: pvzce:zombie/basic/basic_zombie` 这类字段 + `render_scale: 0.5`，一张新图都没有。数值按"四分之一 / 两倍"落：血量 50（护甲一起取四分之一：路障 370→92，合计 142，原版表上写 140；橄榄球 1400→350，合计正好 400）、速度 = 父定义 ×2（0.46 / 0.36 / 0.86 / 0.40）、`bite_interval: 30`（"啃得也更快"）、`can_swim` 与父定义一致（水里仍然只有救生圈与潜水两款）。3-5 的 279 只僵尸于是全部是 `mini_*`，而 `zombie_speed_multiplier` **删掉**：一只小僵尸有多快属于这只小僵尸，不属于关卡。
- **顺带补上的一条引擎缝**：`EntityArt.animationFile()` 原先只读 `animation_dir`，看不见 `animation` 这个"整份文件改借"的字段（播放路径 `AnimationManager` 认它，别处不认），借身体的定义因此会解析到一个不存在的文件 —— 画出来就是一块缺失贴图。现在整份覆盖优先，契约由 `PoolAreaLevelsTest.everyNewContentIdResolvesToArtThatExists` 与 `EquipmentArtTest.aLittleZombieDrawsTheBodyItBorrowed` 钉住（借来的必须是**整副骨架**，旗帜那只还要握得住旗杆）。
- **判定框不用改**：`render_scale` 从设计上就是纯表现（服务端不读它），"缩小但判定不变"因此不需要任何新开关；`PoolAreaLevelsTest.theLittleZombiesAreTheNormalBodiesDrawnSmallerAndQuarted` 顺便钉住"父定义自己的 `render_scale` 仍是 1"。
- **3-2 去掉橄榄球僵尸**：用户的判断与原版 wiki 的 `Level 3-2`、`Football Zombie` 两张表冲突（两张表都把橄榄球列进 3-2，只是都在最后一波），这里按用户的判断去掉 —— 3-2 的名单变成普通 / 路障 / 铁桶 / 报纸 / 旗帜 + 救生圈三款。要按 wiki 恢复，只需在 `tools/write_pool_levels.py` 的 3-2 第 4、6、7 波加回 `football_zombie`（各一只）并重跑脚本。

## 顺带
- 出怪节奏按 2-6~2-9 的量级重排了一轮：五关的 `spawn_interval` 从 420 收到 140（越往后越紧）。3-5 的小僵尸因为只有 50 血、两三发豌豆就倒，数目从 151 加到 **279**（142 普通 / 74 救生圈 / 30 潜水 / 19 路障 / 11 橄榄球 / 3 旗帜），才撑得住原版那种"一群小的一起冲"的压迫感。
- `BuiltInLevelsValidateTest` 的检查清单与 `LevelServer` 的差一项（`validateBuffs`），这次顺手补齐；两份清单从此一致。
- `DayAreaLevelsTest` 钉住的 `yard/adventure/` 关卡列表加上 3-1 ~ 3-5（五关按用户要求先放进 `yard` 主题，分组页因此不变）。
