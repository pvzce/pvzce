# 接入 Jev 决策模型与「人机对战」关卡

> 用户要求：接一个 AI（Jev）进来，玩家在设置里填它的 API key 与 URL，加几个对战类关卡，
> Jev 作为植物方或僵尸方每隔几秒收一次场上信息与自身资源并决策一次；僵尸方攻破植物即胜，
> 植物方在僵尸方胜利前收集到足够阳光（基础 5000，后面更难）即胜；玩家可选任意一方；
> 植物只能种在左边五列、僵尸只能放在右边四列。

## 现象 → 定论

**1. Jev 不是聊天模型，端点和外层都不止一种。** 它是一类**结构化决策**接口：POST 一个
`state` 加一组 `questions`（`choice` / `score` / `noul`），拿回带概率与置信度的答案。实测
（OpenRouter，`https://openrouter.ai/api/alpha/decisions`，`model=typesafe/jev-1.13`）确认：
请求体是 `{model, state, questions}`，响应是 `{model, answers:{<问题键>:{type, choice|score|noul,
probabilities, confidence, legend?}}, usage}`。官方社区站把同样的答案包在
`{code, message, data:{answers}}` 里，网关型渠道放顶层。`JevDecision.parse` 因此**三级容错**
（`data.answers` → `answers` → 顶层逐键），并且**只接受它自己问过的候选项**：答案点名了没在
手牌里的卡就弃权，交给内置策略，而不是猜一个最近的。两次真实响应体收在
`JevProtocolTest` 里当夹具。

**2. 决策在服务端，凭据从客户端过一次网。** 服务端是权威，也是"没有客户端也要能跑"的那一半
（无头冒烟、测试），所以 HTTP 是服务端的（`JevClient`：单工作线程 + 主线程队列，一发在途，
12 秒超时，绝不阻塞 tick）。key 是玩家的，玩家在设置页填，存在
`config/pvzce-client.toml`，进关与保存时用 `JevSettingsC2S` 交给服务端**只放在内存**——
不进存档、不进日志（`JevSettings.toString` 打 `***`）。`-Dpvzce.jev.url|model|key` 或
`PVZCE_JEV_URL|MODEL|KEY` 是第二个门（无头与测试用），**启动参数优先于客户端**，所以客户端
没配 key 不会把服务端的凭据抹掉。

**3. 答案只是建议，落地前要过服务端自己那套规则。** `JevBrain.play` 把选中的卡重新解析、
查阵营、查钱、查区域、查格子，再走 `spawnPlant` / `spawnZombie`；任何一条不过就回退内置策略
并让 HUD 显示"Jev 未响应"。这里**踩到一个真实的坐标对调**：`JevDecision` 给的是行与列，落子
要的是 x 与 y，第一版把 `(row, column)` 当 `(x, y)` 传，于是每一手都被"区域外"拒绝——是
`VersusModeTest` 用假 Jev 端到端跑出来的，见 `踩坑清单.md`。

**4. 对战是一个机制（`pvzce:versus`），不是往普通关卡上加一段 AI。** 一个块写清整局：目标
阳光、双方开局阳光、僵尸方周期入账、吃植物返还比例、决策间隔、两边的卡组（**两边同一刻开始，
没有等待时间**：30 秒建造窗口那一版已被用户否掉并删掉）。卡组是**关卡的**：`slots` 留空、`seed_screen: false`（没有选卡页可问），玩家那一方的
卡来自 `SeedSelection.plan`（按选中的阵营取），AI 那一方从同一块的另一个列表取。`LevelServer`
构造函数也读同一个答案作为兜底，所以不经 `plan` 的构造路径（测试、编辑器预览）也拿得到卡组。

**5. 阳光只能"捡到手"才算，花掉不算。** 植物方的胜利条件是**累计拾取**到目标数，不是余额
（否则"种花—花钱"会自相矛盾）。计数点在 `LevelServer` 的收集路径上（`onResourceCollected`
钩子，点击与 AI 自动拾取同一条路）。**只有僵尸死亡掉阳光与天降阳光发给植物方**这条旧规矩
不动，但 `collectResourceFor` 改成按**掉落物归属的阵营**收集，于是：AI 植物方可以捡自己的
阳光（它没有人帮忙点），而人类僵尸方点不到对方的阳光。

**6. 僵尸方的钱来自周期入账 + 吃掉植物返还。** 它没有产出植物：每 `zombie_income_ticks`
入账一次，加上"被吃掉的植物按其阳光成本返还 `eat_refund_percent`"（默认 50%，三关都写 50）。
"谁吃掉的"只有咬合那一步知道（`ZombieEntity.bitePlant` 在伤害结算后问 `plant.isRemoved()`），
所以钩子开在那里而不是开在移除路径上——铲子、爆炸、关卡自己移除都会让一株植物消失，只有咬
是有嘴的。

**7. 平衡：先加过 30 秒建造窗口，用户否掉了，改成经济与开局阳光。**
第一次仿真的结论很直白：56 秒结束、植物方只收到 250/5000 阳光。当时的修法是加
`zombie_start_ticks`（构建窗口：期间僵尸方既不被付款也不被提问），跑出 14:32 / 17:30 / 20:19。
**用户随后明确否掉："不要让对面有等待时间，同时开始游戏"**——于是这个字段连同它的存档键、
HUD 读秒与语言键一起**删掉**，一行都没留在代码里。改成两边同一刻开始：植物方开局
**800 阳光**（不是"等一会儿"，是"多带点钱"），僵尸方每 5 秒入账 50（600/分钟），
三关目标仍是 5000 / 6000 / 7000，实测 **13:40 / 16:21 / 19:22**。

**用户接着指出两件事：僵尸方"一直放普通僵尸"、以及"顺便把植物也做了"。两件都是内置策略的毛病，
量出来的数字如下。**
- **僵尸方只会买最便宜的**：旧策略里"哪条车道空着就把最便宜的卡放进去"这一条几乎总命中，于是
  `出什么` 被 `放哪` 绑架了。实测一局 **191 只全是普通僵尸**（`mix={basic_zombie=191}`）。
  现在"买什么"与"放哪里"分开：**每三次采购里一次买最好的**（固定配比，不是"差一次进账就攒钱"——
  后者会与关卡收入形成正反馈：收入越高越买得起好牌，好牌又把每点阳光的伤害翻倍，实测同一套收入
  从公平变成碾压，**peak 20 只、三分钟结束**），另外两次买最便宜的保持压力；买得起最好时买最好，
  差一次进账就**等一手**（"允许 AI 等待一次"）。混合后：duel_1 `basic 75 + conehead 37`、
  duel_2 `basic 109 + conehead 15`、duel_3 `basic 95 + conehead 27 + pole_vaulter 10`。
- **植物方只会种向日葵**：同一条"买最便宜的"逻辑在植物侧就是"永远买产阳光的卡"。现在按**能力
  推出的角色**决策：产阳光的 `producer`、会攻击的 `shooter`、只挨打的 `wall`。顺序是"哪条车道
  有僵尸又没射手 → 补最好的射手；僵尸逼近 → 在它前面补墙；生产者不足 5 → 补产阳光的；
  否则给射手最少的车道补最好的射手"。实测反向对局（**脚本僵尸 vs 内置植物**，以前没有测量）
  从"78 秒被打穿"变成 **7~8 分钟植物方先收满 5000**，一局用了向日葵、豌豆、雪花豌豆、坚果墙
  四种卡。
- **决策节奏也要分开**：问 Jev 是一次网络往返，所以 `decision_ticks` 三秒；内置策略只是几次比较，
  也按三秒走就比玩家慢三倍——这正是植物 AI 78 秒被打穿的原因之一。现在内置策略 **0.5 秒**一次
  决策（`FALLBACK_INTERVAL_TICKS`），网络仍然三秒。
- **Jev 那边的提示词也补了**：卡面描述从能力推出来（"conehead_zombie — 75 sun, 560 hp, armoured"
  而不是只写价格），并且明说"**买不起的牌也列出来了；想要的那张只差一次进账就 hold，攒钱买它，
  每回合都买便宜的不如隔一回合买强的**"。

**用户还指出僵尸方"总是在僵尸死了后才放下一只"，这一条是真的，原因是收入太低**：旧的
25 阳光 / 6 秒 = 250/分钟，而一只普通僵尸 50 阳光，于是平均每 12 秒才出一只、全局同时在场
**峰值只有 2 只**（仿真实测 2/2/3），看起来就像在等上一只死。现在 50 阳光 / 5 秒 = 600/分钟，
全局 **192 / 209 / 251 只**、平均 **4.3 / 4.7 / 4.6 秒一只**、同时在场峰值 5（见验证段）。
结论：**"AI 看起来在等"先量出怪频率，不要先去改 AI 的决策逻辑**——它一次都没闲着。

**8. 区域是每方一个机制，钩子是新加的两个。** 植物用现成的 `pvzce:placement_zone`
（`canPlacePlant`）；僵尸新加 `pvzce:zombie_zone`，共用同一个 `PlacementZone` 数据记录与
校验器（只有报错里的名字不同）。`LevelMechanic` 因此多了两个钩子：`canPlaceZombie`
（僵尸方的放置否决，玩家与 AI 共用）与 `onPlantConsumed` / `onResourceCollected`
（两个观察者：吃植物返还、收集计数）。

**9. 选边以前只是高亮。** `LevelSetupScreen` 早就画了"选植物还是僵尸"，但服务端用的是
`LevelDef.humanTeam()`（`playable_teams` 的第一个），玩家点哪边都一样——代码注释自己写着
"等第二个可玩阵营出现才是真选择"。现在选中的阵营随入口包走
（`PlayLevelC2S` / `RestartLevelC2S` 的 `humanTeam`），服务端在构造关卡时就座到那一方
（席位、卡条、胜负判定都是同一个事实），并**写进存档**（`HumanTeam`）：续档时先读存档再
构造，否则一局对战会在续档时两边互换。奖励判据同时从"关卡 `win_team` 赢了"改成"**玩家所在
的阵营赢了**"——对现有 63 个关卡逐个核对过 `playable_teams[0] == win_team`，两种写法等价，
但对双可玩阵营的对战关才是对的。

**10. 凭据输入需要粘贴，而客户端从来没有剪贴板。** 一个 API key 是几十个随机字符，
`EditBox` 只能逐字符打，也没有 Ctrl+V。加了 `PvzceWindow.clipboard()` +
`Screen.pasteText` / `Overlay.pasteText` / `EditBox.appendText`（丢弃控制字符、按字段上限截断），
`PvzceClient.pollInput` 在 Ctrl/Cmd+V 时先于界面按键处理把剪贴板送进获得键盘的那个字段。

**11. 设置页是独立一屏，不是普通配置行。** `ConfigBuilder` 只有 float 项，凭据要文本框、
要粘贴、要能留空。所以新开 `JevSettingsScreen`（服务商预设三个按钮 + 地址/模型 + key + 完成），
从设置中心进；留空即"用内置对手"，`gui.pvzce.jev.*` 是它的语言键。

## 验证与边界

- `JevProtocolTest`（9 例）：请求形状、三种外层、`choice`/`noul`/`score`、宽松键解析
  （`basic_zombie` → `pvzce:basic_zombie`、`3` → `row_3`、`wait` → 弃权）、越界/畸形/错误包
  一律拒绝。两个响应体是**实测抓下来的**。
- `JevClientTest`（6 例）：用 JDK 自带的 `com.sun.net.httpserver` 起本地假 Jev，覆盖
  "决定走完全程"、401、不可用答案、在途拒绝第二次、超时后槽位归还、没 key 不发请求。
- `VersusSideChoiceTest`（3 例）：用真的 `ServerHarness` 走真包——`PlayLevelC2S.humanTeam`
  选僵尸方后，`LevelInitS2C.controlledTeamId` 是僵尸方、卡条里是僵尸卡（没有 `pvzce:sun`）；
  选植物方则相反（有阳光卡、没有僵尸卡）；**不带阵营**（冒烟钩子、编辑器测试那条路）落到
  关卡自己的第一个可玩阵营。
- `VersusModeTest`（11 例）：拾取目标判胜（开局的 150 不算）、周期入账、吃植物返还 50/50、
  内置策略**从不越区**（僵尸的生成 x ≥ 5、植物的列 ≤ 4）、**玩家也不能越区**
  （`placeZombie` 在区外被拒且拒绝文本是语言键）、假 Jev 端到端落子、机制自己的
  校验（错阵营的卡、没有阳光卡、写了波次），以及**关卡仿真**：`duel_1/2/3` 分别在
  14:32 / 17:30 / 20:19 由植物方收满 5000 / 6000 / 7000 结束（脚本化的植物方 =
  先补威胁车道的射手、再铺 6 株向日葵，僵尸方是内置策略）；以及**续档**：存盘再读，
  收集数与"自己是哪一方"都还在（这一条顺带暴露了"僵尸方一点阳光都没有"会被旧的
  `zombieSideIsStuck` 判负，所以关卡必须给它开局阳光与收入）。
- `JevLiveTest`：只有给了凭据才跑（`Assumptions` 跳过）。用真 key 对 OpenRouter 实调一次，
  在 `duel_1` 里跑到 `status=JEV`：`JEV-LIVE ticks=12720 status=JEV
  last=pvzce:basic_zombie at 2,8` —— 真端点给的那一手真的落到棋盘上了。
- **出怪频率、品种与重叠**（用户反馈的直接证据）：`theShippedLevelsRunToAnEnd` 报同时在场峰值、
  总出怪数、平均间隔、**到达时场上已有僵尸的比例**与**品种构成**。本轮定版：duel_1
  12:07 / 112 只 / 6.5 秒一只 / **111 of 112 次到达时场上已有僵尸** / `basic 75 + conehead 37`；
  duel_2 14:33 / 124 只 / 7.0 秒 / 74 of 124 / 三种中的两种；duel_3 16:52 / 132 只 / 7.7 秒 /
  85 of 132 / 三种（植物方胜三关）。"等上一只死"这条由 `overlapped` 直接否掉。
- **反向对局**（`thePlantOpponentBuildsARealDefense`，以前完全没测过）：脚本僵尸 vs **内置植物**
  ——植物方在 7~8 分钟收满 5000 取胜，一局用出向日葵、豌豆射手、雪花豌豆、坚果墙四种卡；
  同一条用例断言"不止一种卡"，是"植物只会种向日葵"这个 bug 的回归。
- **菜单全流程**（用户报的软锁那一条）：`smokeScreen=levels` + `smokeCollection` 打开对战集合，
  再用 `smokeClick` 的**多点多帧**形式按顺序点「关卡行 → 下一步 → 开始游戏」，日志给出
  `LevelCollectionScreen` → `LevelSetupScreen` → `InGameScreen` 这条链（证据 `.smoke/menu/`）。
  这条链以前没有任何自动化手段，所以 `smokeClick` 现在接受 `x,y;x,y;...`（冒烟指南 §4.4）。
- **对手家底面板**（用户要求的那一块）：`.smoke/menu/hud_1600.png` 里右下角同时可见
  "对手阳光 50 / 普通僵尸 / 路障僵尸"与自己的进度行，场上同时有两只僵尸。
  **它的钱会自己走**，所以下发判据必须带上它：`theOpponentWalletIsSyncedEvenWhenItNeverPlays`
  用一个"只发钱、永远买不起"的关卡钉住这一点（把条件改回去会立刻红）——这一条与
  `踩坑清单` 179 是同一类错误，同一个模式里犯了第二次。
- 一次冒烟（`pvzce.smokeLevel=pvzce:yard/versus/duel_1`，帧带落在 `.smoke/versus/`）：
  HUD 显示"我方阳光 N / 5000"、对手状态与最近一手（`普通僵尸 → 第 1 行`），
  `t_3600.png` 里能看到红色放置线右侧来的僵尸与场上植物。**这次截图抓到过一个真 bug**：
  构建窗口的读秒只在"别的字段变化"时才下发，于是客户端在整个窗口里都显示 30 秒，
  修法是让读秒也进"HUD 有变化"的判据。
