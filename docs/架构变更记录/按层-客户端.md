## 客户端自己维护 `TimeOfDayS2C.night`
> 原载 §6.1 状态镜像

- **现象**：日夜此前由客户端自己维护（`TimeOfDayS2C.night`），与服务端是两份。
- **定论**：日夜由 `common/level/DayNightCycle` 计算，服务端与客户端共用同一份。

## 睡着的植物每帧都在冒 Zzz，而且两张计时表从不回收
> 清理轮发现（现状见 §5.2 能力 · 睡觉会冒 Zzz）

- **现象**：`InGameScreen.tickSleepZzz` 把"下一次该冒泡的时刻"记成了**当前**时刻（`zzzNextNanos.put(id, now)`），于是那条 `now < due` 的判据只挡住了 `(id % 4) * ZZZ_STAGGER_NANOS`（150ms 一档），真正的呼吸间隔常量 `ZZZ_INTERVAL_NANOS`（620ms）从头到尾没有参与运算 —— 一株睡着的蘑菇大约每 0.15~0.45 秒吐一个 z，比原版快 1.4~4 倍，而那个常量自己是一段死代码。同两处计时表（`zzzNextNanos` / `zzzStep`）以实体 id 为键，却从不清理，关卡跑得越久表越大。
- **定论**：首次呼吸仍按 id 错开，此后每 `ZZZ_INTERVAL_NANOS` 一次（相位不收敛）；被打断很久（暂停、重载）时重新对表，而不是连发补上；每帧末按"这一帧真正睡着的植物"裁剪两张表。`Zzz` 是纯客户端表现，服务端一行未改。

## 模态输入分发靠"子类记得先调 `super`"
> 原载 §6.2 GUI

- **现象**：此前这是"子类记得先调 `super`"的约定，而 `LevelSelectScreen` 先判定了占满窗口的卡牌网格，于是"新建关卡"对话框的按钮全部点不动。
- **定论**：`mouseClicked` / `mouseMoved` / `mouseScrolled` 在 `Screen` 里是 `final`，先给模态对话框、再给 widget、最后才调界面自己的钩子（`onMouseClicked` 等），结构上不可能再绕过。

## 铲子卡被种子包盖住
> 原载 §6.2 GUI

- **现象**：原来 `CardPainter` 先画了铲子槽、`SeedCardRenderer` 又把种子包盖在上面，于是唯一一张不该像种子包的卡长得和种子包一模一样。
- **定论**：卡面是 `CardModel` 的一部分，铲子卡用 `SHOVEL_SLOT_BACKGROUND`（原版 `ShovelBank.png`）并 `fitBackground = true`，图标居中、底栏不印价格。

## 卡槽条与"放下卡"路径没有声音
> 原载 §6.2 GUI

- **现象**：选卡界面一直有拿起卡的声音，游戏内卡片条以前是哑的；再点一次已选中的卡、右键、点棋盘外这些"放下"路径也一声不响，看起来像那次点击没生效。
- **定论**：拿起与放下都走 `playCardSound`（植物/工具 `sfx/ui/seedlift`、铲子 `sfx/effect/shovel`），取消路径统一进 `cancelSelection`。

## 点不动的卡没有任何反馈
> 原载 §6.2 GUI

- **现象**：冷却中 / 阳光不够 / 次数用尽的卡以前什么也不做——服务端会在两步之后拒绝种植，而玩家那时已经挑好了格子、正等着有东西长出来。
- **定论**：`InGameScreen` 用 `SlotInfo.available` 当场判断，`refuseCard` 放 `sfx/ui/buzzer` 并让那张卡左右抖一下（`CardBar.Host.cardShake`，偏 6px、三条半周期），被拒的卡不进入选中态。

## 卡片充能条的分母写死成 300，而且涂的是"已经过去"的那一份
> 见 §4.4 玩家、卡槽与资源 / §6.2 GUI

- **现象**：卡条把"还剩多少冷却"除以写死的 `300`，再把**已经过去**的那一份从卡片底边向上涂暗。于是只有冷却恰好是 300 tick 的卡画对过：樱桃炸弹（1800）、火爆辣椒（3000）的充能条只在最后 300 tick 里动一下，其余时间整条是空的；而每张卡在冷却期间都是**越等越暗**，等到能用了才"啪"地亮回来——读起来像在放电而不是充电。关卡一旦缩放冷却（`seed_cooldown_multiplier`），所有卡从被消耗的那一刻起就显示成"已经充了一部分"。
- **定论**：分母改为随包下发的 `SlotInfo.cooldownTotal`（服务端 `LevelServer.effectiveCooldownTicks` 算出的、这一关实际收的那一段），`SlotInfo.cooldownRatio()` 是唯一的比值；涂的是**还没回来的那一份**、从顶边往下量，卡从底部长回来。

## 失败画面曾是一句 UI 字体的"失败！"
> 原载 §6.2 GUI

- **现象**：失败时原来只画一句 UI 字体的"失败！"。
- **定论**：改为原版 `ZombiesWon_.png` 的 `DefeatScreen`（逐帧抄 `refer/anim/ZombiesWon.reanim`，24 fps、12 帧），前面另有两拍演出（镜头朝房子平移 2.1 格、停在最后那只僵尸啃房子的画面约 1.2 秒）。

## 选卡屏的归位位置差半个 `panMax`
> 原载 §6.2 GUI

- **现象**：归位位置曾经是 `stage.x() + panMax`，而游戏内 `PvzceCamera` 显示的是 cover 之后**居中截取的中间一段**（图左边缘在 `stage.x()`）——两者差半个 `panMax`，交接那一刻画面会横向跳四分之一屏。
- **定论**：`panOffset = panProgress * panMax`：home 与游戏内对齐，路的终点仍是背景图右边缘贴住屏幕右边。

## 编辑器与列表：三份拷贝、短 id、旧测试图
> 原载 §6.2 GUI

- **现象**：关卡/音乐/卡池编辑器各有一份列表编辑算法，三份拷贝此前已经分叉（一处用交换、一处用摘除插入），同一按钮在两个编辑器里行为不同；物品列表画的是 `GuiText.shortId(id)`；编辑器植物/僵尸页的图标取 `textures/entities/<id>.png`——那是控制器美术之前的旧测试图，画出来和游戏里完全不是一个东西。
- **定论**：算法抽成 `ListEditorSupport`；`PaletteList` 是带贴图 + 名字的列表行，图标优先 `AnimationManager.iconTexture(id)`（控制器模型里最大的部件贴图或 flipbook 第一帧），取不到才回退平铺 PNG。

## 语言文件从第一阶段起就没有代码读它
> 原载 §6.2 GUI

- **现象**：`assets/<ns>/lang/<locale>.json` 从第一阶段就在仓库里，但**没有任何代码读它**，所以列表里显示的是英文 id。
- **定论**：`GuiLang` 是唯一入口（key 是 MC 的 `<namespace>.<path>`），编辑器、波次表、卡池页都走它，缺失的 key 回退到 path。

## 未分类页曾被从关卡推导而消失
> 原载 §6.2.1 关卡选择页（`LevelSelectScreen`）

- **现象**：从关卡里推导"未分类"这一页，会让它在"当前没有未分类关卡"时消失。
- **定论**：未分类页是**固定页**（`pvzce:uncategorized` 哨兵），客户端拼页签表时永远补上它；服务端只下发有内容的页，空页由客户端补齐。

## 关卡列表：4×4 卡片网格、选中只存下标
> 原载 §6.2.1 关卡选择页（`LevelSelectScreen`）/ §6.2.3 关卡编辑器（`EditorScreen`）

- **现象**：页面原来是 4×4 大卡片网格（一屏 4 关）；选中的关卡旧实现只存下标，刷新后同一个下标可能指向另一关，于是"高亮的卡"和"按钮作用到的关卡"不一致；列表里选中一张卡此前也只点亮「下一步」，「编辑关卡」永远是灰的。
- **定论**：现在是左侧主题列 + 顶部类别行 + 行列表（一屏 6~8 关）；`LevelSelectScreen` 记住关卡 **id**，每次刷新后按 id 重新解析行号（纯函数 `indexOfLevel`）；`updateActionButtons` 同时点亮两个按钮，并按选中关卡改名（进行中 → 「继续游戏」）。

## 旧关卡 `level_1` 已删除、旧存档不迁移
> 原载 §6.2.1 关卡选择页（`LevelSelectScreen`）

- **现象**：id 从 `pvzce:level_1` 变成 `pvzce:yard/adventure/level_1`，存档目录名（当时的 `levelKey` = `ns + "__" + path.replace('/','_')`）随之变化，旧目录留在磁盘上不再被读取；原来的 `level_1`（9×5、整份卡池、巨人）已删除。
- **定论**：这是"分类改了、进度从头开始"的既定取舍，不是丢失；`LevelKey` 后来改成十六进制转义的单射键，旧键同样不做迁移（见 §3.4）。

## 空台词行会画出一个空气泡
> 原载 §6.2.2 开场对话（`DialogueOverlay`）

- **现象**：`text` 为空的行（原版用它做表情演出）以前会画出一个空气泡 + 「点击继续」，看起来像漏翻了一句。
- **定论**：空台词 = 没有台词的一拍（`Frame.silent()`，`bubbleBox` 返回 `null`），只演立绘、点一下继续；`LevelValidator.validateDialogue` 不再把"没有台词"报成问题。

## 编辑器画布用静止贴图、格子被拉伸
> 原载 §6.2.3 关卡编辑器（`EditorScreen`）

- **现象**：旧实现的预设精灵是静止贴图，且格子被拉伸到填满画布。
- **定论**：画布走游戏自己的世界投影（`beginOverlayWorldView` + `SceneTileRenderer.render` + `AnimationManager.render`），落点来自同一份 `LevelStage.board(canvasW, canvasH, columns, rows)`，`cellAtCursor()` 是它的精确逆运算。

## 波次/音乐编辑：独立屏与对话框、动作栏重复入口
> 原载 §6.2.3 关卡编辑器（`EditorScreen`）

- **现象**：波次界面原本在独立的整屏 `WaveEditorScreen` 里、音乐在 `MusicEditorDialog` 里，真正的编辑藏在二级菜单；底部动作栏还挂着「编辑波次」和「音乐」两个入口，与导航栏同名页重复，一个目标两个入口。
- **定论**：两页都改成"列表/时间线 + 详情同屏"、占满整宽、没有二级菜单（只剩 `WaveEditorModel` / `MusicEditorModel`），动作栏只剩「保存 / 测试 / 返回」。

## 编辑器入口：写死 `openEditor("custom_level")`、测试直接开局
> 原载 §6.2.3 关卡编辑器（`EditorScreen`）

- **现象**：列表下方的「编辑关卡」此前入口写死 `openEditor("custom_level")`，每点一次都在编辑同一关，存成别的名字那份永远打不开；测试按钮原先直接发 `RequestLevelC2S`（＝让服务端开局），跳过了选卡界面，同一个关卡从列表打开却要选卡。
- **定论**：「编辑关卡」送**选中的关卡**进编辑器；测试按钮只保存，再交给 `PvzceClient.testEditedLevel` 等**服务端重载后的关卡列表**（`/reload` 后由 `PvzceServer.refreshLevelList` 补发）再打开选卡界面。

## 翻页的两种边界 bug
> 原载 §6.2.3 关卡编辑器（`EditorScreen`）

- **现象**：页数向下取整会让尾部若干行**没有页**（18 关 4 列 4 行可见时是 5 行，页数 floor(5/4)=1，指示器写"1/1"、两个箭头全灰、第 5 行永远看不到）；按 `totalRows - pageSize` 夹取会让相邻两页**重复同一行**（13 关 4 列 2 行可见时页曾是 0-1、2-3、3-4）。
- **定论**：算法抽到纯函数 `ListPaging`：首页行号永远是页大小的倍数、末页夹到 `(pageCount-1)*pageSize`、页数**向上取整**，`ListPagingTest.everyRowIsReachableOnExactlyOnePage` 对全部"行数 × 页大小"组合断言每一行恰好出现在一页上。

## `kind().equals("sun")` 让每一种掉落物都发光
> 原载 §6.3 渲染 / §8 约定 27

- **现象**：光源判定原本写的是 `kind().equals("sun")`，而 `EntityKind.RESOURCE` 的值**就是** `"sun"` —— 于是**每一种掉落物**（金币、钻石、能量豆）都被当作太阳，落地就在草坪上投一圈黄光。
- **定论**：判定一律比**内容 id**（`defIdString()` / `PvzceIds`）；`EntityKind.RESOURCE` 改为 `"resource"`（kind 字符串走 `EntitySpawnS2C`，故 `PROTOCOL_VERSION` = 10），`EntityLightTest` 钉住"只有阳光亮"与"kind 不等于任何内容 id"。

## 缺失贴图曾是一块白方块
> 原载 §6.3 渲染

- **现象**：取不到贴图时以前画的是一块**白方块**，和"故意画成空白"的精灵分不出来；而这类引用确实存在过（`textures/resource/generic`、`textures/resource/coin`、没有 `texture` 字段的内容）。
- **定论**：`EntityArt.MISSING_TEXTURE`（`textures/mission.png`，2×2 品红/黑棋盘格，`TextureManager` 对它单独用 `GL_NEAREST`）是缺失贴图唯一的样子，`PvzceClient.drawTextureRegion` / `drawTextureQuad` 与 `EntityArt.sprite(null)` 都回答它。

## 一次性音效变成"无限循环"的物理来源
> 原载 §6.5 声音与粒子

- **现象**：`AL_LOOPING` 是**源的属性、不是 buffer 的属性**——一个被要求循环过的源会把之后绑上来的任何 buffer 一直循环下去；大波提示占用的源马上会被下一个音效重用，于是一次性音效听起来变成了无限循环。
- **定论**：音频源在重新绑定 buffer 之前一律先 `alSourceStop`；`play()` 另有两道保护（同一事件 130ms 内去重、一个事件在自己的声音播完之前再次请求会被丢弃），都不是白名单。

## `ensureMenu` 的"空闲才播"与重开时的音乐重叠
> 原载 §6.5 声音与粒子

- **现象**：`PvzceMusicController.ensureMenu` 曾被写成"菜单轨空闲才播"，于是奖励页的 `zen_garden`（菜单轨）一直压着关卡列表——关卡列表请求 `choose_your_seeds` 时发现轨道忙，什么都不做；另一处只有"离开关卡"这条路会停乐（`clearLevelClientState()` → `music.leaveLevel()`），从存档提示框重开、编辑器「测试」不经过 leave，上一局的战斗轨会继续循环、压在新一局的轨道下面（表现为音乐重叠）。
- **定论**：`ensureMenu` 的语义是"同曲不重启、异曲要换"；每个新关卡实例由服务端在 `LevelInitS2C` **之前**补发三条 `MusicEventS2C.reset(track)`（`PvzceServer.silenceClientLevelMusic()`），同一实例的 resync 不发重置。

## `aNewLevelInstanceResetsTheClientsMusicAndAResyncDoesNot` 大约四次里红一次
> 原载 §关联用例（`ServerMenuFlowTest`）

- **现象**：这条用例在 resync 段偶发失败（`resyncing the running level must not touch its music`）。**与改动无关**：在未改动的 HEAD 上单跑 12 次复现 3 次。真正的原因是**测量窗口开早了**——新实例的开场音乐 cue 由 `processMusicCues` 在它的**第一 tick** 发出，而 `LevelInitS2C` 是在 `createLevel` 里同步发的，所以 cue 落在 init **之后**；用例一看到 init 就发 `ContinueLevelC2S`，这个 cue 有时就落进了 resync 的统计窗口，被当成"resync 动了音乐"。
- **定论**：等新实例真的 tick 过（`level().tickCount() > 1`）再取基线：那一 tick 之后，开场 cue 已经在窗口之外。修完连跑 10 次该类 + 3 次全量全绿。

## 粒子曾是效果名上的一个 `switch`
> 原载 §6.5.1 粒子（数据驱动）

- **现象**：粒子曾经是 `ParticleEngine` 里对效果名的一个 `switch`，只能画**纯色方块**——原版那 81 张粒子贴图与 112 个 emitter 脚本一张也用不上；内置效果 id 还是散落在能力里的字符串字面量，未知 id 只在客户端每秒报一次日志，症状（"这个效果不见了"）指向不了任何地方。
- **定论**：粒子由 `ParticleDef` 数据驱动（`data/<ns>/particles/<类目>/*.json`），内置 id 集中到 `PvzceParticles`（与 `PvzceSounds` 同形）。

## 金币光晕因没有加法混合被砍掉
> 原载 §6.5.1 粒子（数据驱动）/ §4.5 背包、金币与关卡奖励

- **现象**：原版的光晕用加法混合画，当时本渲染器没有加法模式，用普通 alpha 画出来是一块盖住底下东西的实心圆盘，金币光晕因此被整个砍掉——生成硬币美术时也排除了 `COINGLOW` 与 `DIAMOND_SHINE`。
- **定论（第一次）**：`RenderSystem.blendAdditive` / `blendNormal` 补上加法混合（普通粒子先画、发光粒子后画，整帧最多切两次混合状态）；硬币美术仍排除这两个 emitter。
- **后来的更正**：控制器部件现在也能声明 `"blend": "add"`（见下），阳光的两圈光晕就是这样画的。硬币的光晕**仍然不进模型**，但原因不同了：不是"画不出来"，而是它比币面宽（80px vs 43px），而一个控制器模型的所有骨骼共用一个缩放倍率，把它留在模型里会让币面被作者成目标尺寸的 54%。它该由粒子层负责。

## 未定义的效果会画一个红方块
> 原载 §6.5.1 粒子（数据驱动）/ §8 约定 22

- **现象**：曾经会给每个未知的效果名画一个红方块，让拼错看起来像个真效果。
- **定论**：未定义的效果**不画东西**，只按 id 报一次日志。

## 关卡列表按字符串排序，`1_10` 跑到 `1_2` 前面
> 原载 §6.2.1 关卡选择页 / §8 约定 45

- **现象**：列表与页签都按 `Identifier.toString()` 排序，而 id 是给人编号的文本：加进第 10 关（`1_10`）之后，它排在 `1_1` 与 `1_2` 之间 —— 关卡越全，列表越不像一条关卡链。
- **定论**：`LevelGrouping.compareIds` 做自然序比较（数字段按数值、其余按字符），服务端下发列表（`PvzceServer.sendLevelList`）与页签推导（`LevelTabs.build`）共用它；**不重命名任何已有 id**（id 是存档目录名与其它关卡的引用键）。

## 手套卡住不动，像有无限冷却
> 原载 §6.2 关卡内取消选卡

- **现象**：手套是"拿起 / 放下"两击，客户端为了让它能收第二击，把卡**跨点击保持选中**；而冷却在拿起那一刻就开始了。于是第二次点击落在同一张卡上时，`cardUsable` 看到的是"选中但没就绪"，直接按拒绝处理（buzzer + 抖动），植物吊在手套上等 15 秒超时 —— 玩家看到的是**手套用一次就永远冷却**，而卡片条上那张卡也确实一直是灰的。
- **定论**：`spendSelectedCard` 对所有卡（工具也算）**发出请求后立刻清掉选中**：一次完整使用之后卡就回手。服务端那半边的规则不动（`finishingMove` 让正在搬运的手套忽略自己的冷却，一次搬运只花一次使用次数）。

## 阵营是客户端替关卡决定"僵尸方不可选"
> 原载 §4.3 进入/重开关卡的协议语义

- **现象**：`LevelSetupScreen` 把僵尸方写死成"未解锁"（当时确实没有僵尸方卡组），于是"这一关只有植物方"是**构建的事实**而不是**关卡的数据**；同时"要不要问阵营"这一问在关卡列表、编辑器测试、冒烟钩子里各写了一遍，只有列表那一份问了。
- **定论**：`LevelDef.playable_teams` 声明可玩阵营（缺省＝全部），服务端按它下发每条 `TeamInfo.playable`；`enterLevelFromMenu` 是唯一的入口决策，"只有一个可玩队伍就跳过 `LevelSetupScreen`"也只在那一处判断。

## 爆炸范围写成半径，于是"3×3"要靠猜一个数
> 原载 §4.9 爆炸范围

- **现象**：`pvzce:explosive` 与 `damageArea` 一直只认**径向**距离，可是原版的灰烬线是按**格**说的：樱桃炸弹打的是"它那一格加上周围八格"，土豆雷只打"自己那一格"。当时的等效数是 `radius 1.5` 与 `radius 0.55` 这类**推出来的半径**（相邻格中心距 1.0，所以单格要 ≥0.5、3×3 要 ≥1.0 而 1.5 更宽），既没有说明它到底覆盖哪几格，也让"土豆雷自炸一格"要靠 `trigger_range` 0.5 与半径 0.55 之间的空隙勉强成立。
- **定论**：`radius` + `square` 直接读成**格数**（判据 `|Δ| ≤ radius + 0.5`）——土豆雷 0.5 = 自己那一格，樱桃炸弹 1.0 = 3×3，毁灭菇 3.0 = 7×7；火爆辣椒另走 `trigger: "row"` + `LevelAccess.damageRow`，因为"整行"是形状而不是距离：一个足够大的方格会连带打穿旁边的行，而"刚好 9 列宽"的半径在更宽的草坪上会短一截。

## 锤子是写死的 100000 点、走小推车的伤害类型
> 原载 §4.9 关卡自带的工具

- **现象**：`HAMMER_TOOL_DAMAGE = 100_000`，伤害类型写死 `pvzce:mower`（无视护甲）。于是木槌在草坪上等于一辆小推车：普通僵尸、路障、铁桶全都一下死，"路障要两下、铁桶要三下"这条原版规则在数据里根本表达不出来，换一把工具也无处声明它打多重。
- **定论**：`ToolDef.damage` / `damage_type`（缺省 200 点 / `pvzce:impact`），锤子自己在 `tools/hammer.json` 里写这两个数。200 是普通僵尸的血量，`impact` 让护甲照常吸收，于是普通 1 下 / 路障 2 下 / 铁桶 3 下由既有的 `ArmorCapability.absorb` 自动成立。

## 攻击不看阵营，所以"变成自己人"无从表达
> 原载 §5.2.2 阵营与魅惑

- **现象**：`zombiesInRow(row)` 返回这一行所有僵尸，射手、投手、近战、爆炸、子弹命中测试全都直接用它；伤害也从不过问来源与目标的阵营。于是"把一只僵尸变成我方"这件事在引擎里没有落点：要么在每一处攻击代码里加一句"这个僵尸是魅惑的吗"，要么让它变成一只仍然挨打的我方僵尸。
- **定论**：**"谁是敌人" = 不是同一支队伍**。`LevelServer.isEnemyOf` 是唯一判据，`LevelAccess.enemiesInRow(row, team)` 是攻击方的唯一读法（`damageArea` / `damageRow` 的 `sourceTeam` 同源），`zombiesInRow` 只留给"这一行有几只僵尸"。魅惑因此只剩一件事要做：`setTeam`；代价是胜负判定必须改数 `hostileZombieCount()`，否则关卡会在最后一只敌意僵尸死后仍然无法结束。

## 穿透子弹在每个重叠 tick 都造成一次伤害
> 原载 §5.2 子弹能力 / §5.2.1 伤害类型

- **现象**：`pierce` 只回答了"命中后不要消失"，没有回答"同一只僵尸还算不算目标"。子弹每 tick 都在僵尸的命中半径内，于是**每一 tick 都是一次新命中**：一发 20 点的大喷菇喷雾十个 tick 打死 200 血的僵尸，玩家看到的是"大喷菇秒杀一切"。这是引擎里的洞（原来没有任何穿透子弹，所以没人踩到），不是大喷菇的数值问题。
- **定论**：`ProjectileEntity` 记住这发子弹打过哪些僵尸（`hitIds`），`findTarget` 跳过它们。用集合而不是"上一只"，因为两只僵尸可以在同一格里。
- **顺带**：大喷菇的伤害类型从 `pvzce:ash` 换成新的 `pvzce:spray` —— 无视护甲（穿纱门）与 `burns`（烧成焦尸）是两件事，共用一个类型会让喷雾也留下焦尸。

## 大喷菇是一团气，却被做成了会飞的子弹
> 原载 §5.2 植物能力（`pvzce:cone`）

- **现象**：上面那条把"每 tick 重复命中"修好之后，剩下的问题还在：大喷菇的喷雾是一颗 `linear speed 2.4` + `pvzce:pierce` 的**真实弹体**，带着自己的精灵飞满 4 格。于是它必须借 `pierce` 加 `hitIds` 那套记账来**模拟**范围伤害，屏幕上的读法也从"贴着邻居呼气"变成"远程狙击手"——一团气不该有飞行时间。原版的大喷菇是一瞬间覆盖身前一整片的锥形，是**近战形状**，不是射程更短的射手。
- **定论**：新增 `pvzce:cone`（`ConeAttackCapability`）——**一个形状，结算一次**，与 `explosive(row)`、`freeze_all` 同族：同一 tick 取本行敌人、留下正前方 `range` 格内的、每只打一次，没有弹体也没有逐发记账。`fume_shroom.json` 改用它（`interval` 90 / `damage` 20 / `range` 4.0 / `damage_type` `pvzce:spray`，原版"前方 4 格"）。`pierce` 与 `hitIds` 留着（仍是合法能力、仍由同一个用例钉着），只是**内置内容已经没有穿透子弹**。
- **画面不能只 emit 一次**（`cloud_particle` / `cloud_count`）：粒子引擎把一条定义里的**每一颗粒子都放在 effect 生成的那一个点上**，只有 `motion` 会把它挪走 —— 所以一次 emit 就是植物脸上的一团，而不是一条气。原版没有这个问题：它的 `FumeCloud` 就是那颗**会飞的投射物精灵**，气之所以显得"铺开"是因为图在飞；伤害改成瞬发之后没有东西可飞了，于是把形状**画**出来：`cloud_count` 个发射点沿锥形均匀铺开，各自带 `pvzce:fume_cloud` 自己的前向漂移。
- **间距必须小于一团云的宽度**：间距是 `range / cloud_count`，而一团云约 0.7 格宽。4 格配 3 个 = 1.33 格间距 → 屏幕上是一串**断续的独立团**（用户直接反馈的就是这个）；6 个（`DEFAULT_CLOUD_COUNT`）约 0.67 格间距 → 叠成一条连续的带。**要加长光锥就得加数量，不是拉间距。**
- **同一条里抓到的第一个错**：`cloud_particle` 用 `optionalFieldOf("cloud_particle")` 读，JSON 不写这个字段时拿到的是 `Optional.empty()`，而空的意思按设计是"不画"。于是**凡是没有把这个字段写全的植物都一个粒子都不画** —— 默认值形同虚设。构造器现在把"缺省"规范化成 `DEFAULT_CLOUD_PARTICLE`，只有显式 `cloud_count: 0` 才是"只要伤害不要画面"。
- **同一条里抓到的第二个错**：**"在前面"必须按格子判断**。植物中心 1.5、枪口在 1.8，而走到植物身上那只僵尸的中心是 1.99 —— 比枪口更靠右、也在 4 格之内，所以只比 `cellX > muzzleX` 会让蘑菇对着**正在啃它的那只**喷气。判据改成 `zombie.gridX() > plant.gridX()` 再看射程。原版的喷雾从不打自己那格，`NightAreaTwoLevelsTest.theCloudReachesFourCellsForwardsAndNoFurther` 用三只僵尸（锥内 / 四格之外 / 踩在植物身上）钉住。
- **顺带**：`PvzceIds` 补上 `DAMAGE_SPRAY`（`spray` 是唯一一个没有常量的内置伤害类型，此前各处只能写字面量）；`LevelValidator.validateDamageTypes` 原来只查 `explosive` 与 `splash`，现在把 `freeze_all` 与 `cone` 一并查，并且各自报告**它自己真正的兜底类型**（原来一律写"回退到 `pvzce:projectile`"，对灰烬/splash/喷雾都是错的）。

## 手套的冷却从"拿起"挪到"放下"
> 原载 §6.2 卡槽条

- **现象**：上一轮为了让第二次点击能被接受，把"完整使用一次后取消选择"套到了所有卡上，同时手套的冷却仍在**拿起**那一刻开始。于是选中手套、拿起植物之后，卡进入冷却、条子把它画灰、`cardUsable` 拒绝再选它 —— 玩家拿起了植物却放不下去，手套"几乎无法使用"。
- **定论**：手套的冷却在**放下**（或搬运超时）时才计，因为那时这一次使用才算结束；客户端把手套当作"冷却中也可以点"的卡（`InGameScreen.gloveCard`），服务端仍然拒绝"手里没拿东西且在冷却"的点击。

## 背包页被图鉴取代，而图鉴的第一版做错了
> 原载 §6.2 图鉴

- **现象 A（背包）**：`InventoryScreen` 只做一件事 —— 把游戏知道的每张卡列成网格，没解锁的画灰加挂锁。它回答"我现在能带什么"，但玩家点开它时问的通常是"这东西到底是什么"，而那一页没有地方放这个问题。
- **现象 B（图鉴第一版）**：换成图鉴时**只看了素材、没看原版长什么样**。`refer/im7/images` 里有全套 `Almanac_*` 图，于是照着文件名把背景当"底板"、把卡片框当"详情卡"，做成"一条一页 + 左右箭头翻页"，每页一张卡 + 右侧数值与引文。做完一看就不是那个东西：原版**一页列出全部条目**（8×4 的货架）、右侧开一张详情卡、底部是"图鉴索引 / 关闭"两个按钮，索引页是两块大板各一个按钮 —— 用户一眼看出不对，是对的。
- **现象 C（预览全是错的）**：① 种子包图标按框的大小拉伸（框不是正方形），豌豆射手被压扁；② 僵尸那一条条卡画的是"动画里最大的那块贴图"，画出来是一条腿，没有该贴图时整片洋红（缺贴图占位）；③ 图窗里没有草地，原版每一件内容都站在草坪上。
- **现象 D（同一次里的三个连锁 bug）**：① 卡片框被九宫格拉到 660×150，木纹抹开；② 字号写在"原生单位"里再除法，而 `FontRenderer` 的 scale 本来就是 GUI 尺度，于是字比卡片大 3 倍；③ 详情文字推了剪刀，但卡框绘制结尾会 `beginGuiView()`，剪刀活不过那一步，于是简介与引文印在了图窗上。
- **定论**：版式按**原版截图量出来的常数**重做（货架 8×4 与 5 列、卡片 46×70 与 76×87、详情卡 324×484 与 324×497、两块索引板与两个页脚按钮的位置都写在常量里），整页 800×600 contain 缩放。四组 bug 的修法：卡片框**按自己的像素比例**画；字号就是全项目在用的 scale（0.8~1.5）；越界**用版式保证**（`drawWrapped` 收一个地板，越线的行不画）而不是剪刀；预览**一律走骨架动画**（`previews` 按条目缓存，进页面建、离开释放），脚下铺 `almanac_groundday`，静态回落只留给没有骨架的内容。颜料顺序也定死并写在注释里：不透明层 → 文字 → 动画预览。
- 四个取舍：**只收本项目已有的植物/僵尸**（原版 49 种里没实现的连 `refer/anim` 的 reanim 都不齐）；**僵尸全部可见**（没有"见过哪只僵尸"的记录）；**未解锁的植物也列出来并加挂锁**（原版不列，但"为什么我种不了坚果墙"更值得回答）；**僵尸详情跑真动画**（植物用种子包图标，那正是原版植物条目画的东西）。
- 原版素材从 `refer/im7/images` 转进 `assets/pvzce/textures/gui/almanac/`，JPG 一律转 PNG（贴图管理器只认 PNG）。
