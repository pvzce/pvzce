## 关卡只有"机制"，没有"玩家自己选的规则"
- **现象**：`mechanics` 是关卡说了算的东西（传送带、放置区、小推车），卡槽是玩家说了算的东西；两者之间没有第三种。于是"这一局自动捡阳光""这一局蘑菇射得更远"这类**玩家想开的开关**无处安放：写成 mechanic 就变成关卡强制的，写成 game rule 就只能改数据文件。
- **定论**：新增 **`LevelBuff`**（`api/content/LevelBuff` + 代码注册的 `PvzceRegistries.LEVEL_BUFFS` + `common/buff/BuiltInBuffs`），与 mechanic 同一套注册/查询形状但不是同一件事：关卡有权**钉死**某些增益（`"buffs": ["pvzce:auto_collect"]`，哪怕玩家背包里没有这个增益，与 `slots` 的固定卡同一条逻辑）或写哨兵 `pvzce:player_choice` **放开**给玩家选，还能用 `max_buff_slots` 声明本关能带几个（不写＝跟随背包新增的 `PlayerProfile.buffSlots`，默认 5）。没有写 `buffs` 的关卡**连增益页都不会出现**，所以 23 个内置关卡里已有数据的形状一个字节都没变。收选规则收在 `LevelBuffSelection`（纯函数），与 `SeedSelection` 一一对应：锁定项先放且永不筛掉、自选按提交顺序填到上限为止、上限先判后加、续档时存档里的 `Buffs` 优先（`null`＝那份存档早于增益系统，这才回落到世界偏好）。

## 射程这类"两半是同一个数"的效果，缩放点只有一个
- **现象**：`ProjectileRef.range` 同时决定"植物认为值不值得开火"（`ShooterCapability.hasTarget`）与"子弹什么时候消失"（`ProjectileEntity.maxRange`）。在任何一半上做增益都会得到"能射到但打不中"或"能打中但不射"。
- **定论**：**远距蘑菇**（`pvzce:mushroom_range`，×1.5）在 `LevelServer.spawnProjectile`/`spawnArcProjectile` 里缩放一次 —— 子弹是照着这份 ref 造出来的，而植物的判定读的是同一份 ref，两半不可能分叉。判定"谁是蘑菇"用**两个能力**（`pvzce:nocturnal` + `ShooterCapability`）而不是植物 id 列表：小喷菇与胆小菇吃得到，大喷菇的喷雾是 `ConeAttackCapability`（不是有射程的弹道）因此吃不到，阳光菇/魅惑菇/寒冰菇/毁灭菇没有射击能力也吃不到，而以后新加的蘑菇自动吃得到。`range` 为 0（整块草坪）的射击**不受乘数影响**——"整块草坪乘任何数还是整块草坪"。倍率每发射一次重读，所以中途改增益下一次射击就生效。

## 自动拾取一生成就收，会让掉落物根本没出现过
- **现象**：`LevelServer.tick` 里掉落物的生成包与 `ResourceCollectS2C` 若在同一批发出去，客户端只会看到"结算 +25 阳光"，草坪上什么都没出现过——向日葵刚产的那朵阳光会像凭空消失。
- **定论**：**自动拾取**（`pvzce:auto_collect`）用一张 `autoCollectTimers`（按实体 id）让每枚掉落物先躺 **15 tick** 再收，掉落在客户端眼里是"落地 → 被捡走"。它**不绕过关卡的收集规则**（`collectible`、本关是否解锁该资源、卡槽里有没有那张卡照旧判），只是被拒时**不出声**：每秒一条"没有对应资源卡，无法收集"会盖住它本来要帮的那块草坪。手动点击那条路一个字没变（包括聊天栏那行 `+25 阳光`）；自动那条路只发声音、闪光与飞向银行的动画，因为这些才是"你的阳光到了"的反馈。

## 一局带进去的增益，下一次要能自动帮我选上
- **现象**：玩家在选卡页勾了自动拾取，下一关的选卡页又是空白的——每一关都要重新勾一次不是选择，是手续。
- **定论**：`PlayerProfile.autoBuffs`，**每世界一份**（设计阶段定下：想要自动拾取的人是想在所有关卡都自动拾取）。它写的是"这一局实际生效的增益"（`PvzceServer.createLevel` 里 `rememberAutoBuffs`），所以"我上次带进去的"与"下次帮我预选的"永远是同一份，空列表是合法值（＝以后别帮我选）；**续档时不写**——那一局的选择是上一次会话做的，不是现在的表态。它随 `ProfileS2C` 下发（协议 22 → 23），并且**开局那一刻就补发一次**：不然客户端要等下一次关卡列表刷新才知道这个变化，而下一个选卡页很可能在那之前就打开了。命令入口 `/profile buffs [id...]` 与 `/profile buffslots <n>`。

## 卡牌悬停显名根本不存在
- **现象**：把鼠标放在种子卡上什么都不显示。名字一直在 `assets/pvzce/lang/zh_cn.json` 里（`pvzce.puff_shroom`），但没有任何一处画它；关卡增益的图标同样需要一个说法。
- **定论**：`client/gui/HoverTip` —— 深色底板 + 一行字、贴边翻面，是个**函数**而不是控件（不进 `widgets`，因此永远吃不掉点击）。三处共用：游戏内卡槽条、选卡页的卡池与增益池、关卡内的增益图标。触发条件一律是"光标下的东西确实在、且已经画完"（面板还在滑入、关卡已结束、正在拖卡时不画）。名字经 `SlotResolver` 解析到**内容** id 再查 `GuiLang`，所以"槽 id 与它给的植物不同名"的卡显示的是它实际给你的那个东西。

## 固定卡填满卡槽的关卡，加了增益页就必须让玩家进去
- **现象**：`previewOnly`（不画面板、2.1 秒后自动开局的过场）原来的判据是"卡片没得选"，而"没得选"在增益出现之后变成了两页的事：一个钉死整套卡组、却写了 `pvzce:player_choice` 的关卡会自动开局，玩家**永远没机会选增益**。
- **定论**：`previewOnly = 自己发卡 || (两页都没得选 && 没有已选增益 && 没有锁定增益)`。选卡页顶部随之多一排两个 tab（种子卡槽 / 关卡增益），两页共用同一套排版与绘制代码；"清空"**分页**执行（清了卡不等于要丢增益）。关卡内的增益图标画在**左下角、钱袋银行上方**：左下角本来是钱袋的地盘，但那块只在金币变化后显示 2.6 秒——正好是自动拾取开着时最常出现的那 2.6 秒，所以让开它而不是共用。

## `y` 的语义：旧渲染器锚在**基线**上，TTF 版锚在行盒顶部
- **现象**：字体本身画对了之后，整屏文字仍然统一偏低约一个 ascent —— 按钮标签垂在按钮下沿、玩家牌上的两行几乎叠在一起。
  实测（1280×720，同一批截图）：按钮内容中心与标签中心之差，旧位图渲染器是 **+17.5px**，TTF 版是 **+51px**。
- **定论**：旧渲染器把墨迹下沿放在 `y + (baselineRow - inkBottomRow)`，而 `baselineRow` 就是"基线所在的行"，
  所以那个和恰好把**基线**放在 `y` 上（对坐在基线上的字与带下伸的字都精确成立）。TTF 版把 `y` 解释成"行盒顶部"，
  于是每个调用点都向下平移了一个 ascent。fb8a7ee 只把 `client.font()` 机械替换成 `client.fonts().<role>()`，
  **一行 y 公式都没改**，所以 240 多个调用点（`Button` 的居中、`TitleScreen` 玩家牌、`HintBox`、`HoverTip`、
  `AwardScreen` 的底板…）仍然全是按基线锚点写的。修法是把锚点改回基线（`drawGlyph` 直接把 `y` 当基线），
  并把 `Fonts`/`FontRenderer` 的坐标说明、`ascent()`（现在是"基线之上的高度"，供调用点自己居中用）一并改对；
  修完实测按钮标签中心差 **+14px**，与旧版的 +17.5px 同量级（剩下的差是两种字面墨迹比例不同，不是锚点）。
  `GlyphAtlasTest.glyphInkSitsOnTheAnchorRatherThanUnderIt` 钉住"墨迹在锚点之上"。

## 顺带修掉：`buffs` 的 JSON 形状与 codec 不匹配
- **现象**：`LevelBuffPlan` 一开始写成"带自己 codec 的 record"，于是 `"buffs"` 被读成**对象**，而关卡文件里写的是数组（`"buffs": ["pvzce:auto_collect"]`），19 个关卡全部 `Not a JSON object` 加载失败。这是写测试时立刻暴露的：端到端用例跑真实数据包，而纯函数用例用的是 Java 构造器，两边一个红一个绿。
- **定论**：两个字段**扁平地**解在 `LevelTail` 上（`LevelBuffPlan.mapCodec()` 经 `RecordCodecBuilder.of` 接进去），与 `slots` / `max_seed_slots` 的形状一致，作者的写法与记录的字段一对一。**这也是为什么要有一个跑真实数据包的端到端用例**：只测纯函数的话，"Java 里能构造"与"文件里能读出来"是两件事。

## 关卡增益应当是打出来的，不是一开始就有的

- **现象**：`LEVEL_BUFFS` 一注册，两个内置增益对任何放开增益的关卡都立刻可选——玩家在第 1-6 关就能勾"自动拾取"，而原版里这类能力是**通关给的**。更具体地说：1-9 与 2-9 原本是"不给植物、只给一袋钱"的两关，它们的奖励位空着。
- **定论**：增益做成**第三个袋子**（`PlayerProfile.unlockedBuffs`，自己的 NBT 键 `UnlockedBuffs`，与卡、关卡购买并列）：没被某一关发过的增益**列在池子里但带锁**（`SeedOptions.LOCKED_OPTION` 复用价格字段；客户端画挂锁、点它只响一声），`LevelBuffSelection.sanitize` **不收**它 —— 服务端这一侧才是门，池子上的标记只是把门画出来。**1-9 首通发 `pvzce:auto_collect`（自动拾取），2-9 首通发 `pvzce:mushroom_range`（远距蘑菇）**，于是便利增益在 Day 收尾就到手、"蘑菇射得更远"赶在 2-10 那条蘑菇传送带之前（这两个增益在实现里一度写反，2026-09 按体验顺序改正），而 2-5 / 2-10 那种关卡自己钉死的增益照旧不需要玩家拥有（关卡的"我这一关就是这样"优先于背包，与固定卡同一条逻辑）。奖励类型是 `{"type":"buff","id":...}`，与 `unlock` 同样**幂等**、**任何一次通关都补发**，所以早就通关过的老世界也拿得到；那两关的 `repeat`/掉币继续是引擎默认值，显式写出来只是因为 `rewards` 块现在存在了。
- **顺带改掉一个命名**：`PlayerProfile.owns` → `ownsCard`。第三个袋子一进来，"owns 什么"就不再自明，而一个叫 `owns` 的方法读起来像"这个玩家拥有它吗"，实际只回答卡——增益问的是 `ownsBuff`。同一个改动也让奖励结算里 `profile.ownsCard` 与 `profile.ownsBuff` 并排出现时不必靠注释区分。
- **奖励页与草坪上那一件东西**随之多一档：解锁的增益排在资源物品之前、卡之后（`LevelRewardS2C.unlockedBuff`，**协议 23 → 24**）。它画的是**种子包的框 + 增益自己的图标**，因为这一页说的是"你拿到了新东西"，钱袋会说出相反的话；结算页的文字换成 `pvzce.award.new_buff` 与一句"选卡时可以带上它"。
- **操作入口**：`/profile buff <id>` 发一个增益（冒烟与测试用，等价于通关 1-9 / 2-9 的那一步）。

## 远距蘑菇"没有生效"：缩放做了，判定没做

- **现象**：把 `pvzce:mushroom_range` 打开，小喷菇的孢子确实飞得更远（`ProjectileRef.scaledRange` 正确、`LevelServer.sporeRangeMultiplier` 返回 1.5、所有单测都绿），但**在游戏里看不出任何区别**。实测两次运行完全一样：首次开火时僵尸距离 2.9925 格、孢子最远飞到 2.27 格。
- **定论**：`ProjectileRef.range` 是**一件事的两个半边**——植物"值不值得开火"（`ShooterCapability.hasTarget` 里的 `shot.covers(muzzleX, z.cellX())`）与子弹"什么时候消失"（`ProjectileEntity.maxRange`）。原实现只在 `LevelServer.spawnProjectile` 里缩放（子弹那一半），判定那一半读的仍是定义里原始的 `range`，所以植物始终等到 3 格以内才开火，而它现在能打到 4.5 格这件事从来没有机会发生。修法是把这条规则收进**一处**：`PlantShots.scaled(ref, plant, level)`（倍率来自新的 `LevelAccess.sporeRangeMultiplier(plant)`，`LevelServer` 实现它），射击能力拿它瞄准、`spawnProjectile` 拿它造子弹——同一个调用，两半不可能再分叉。
- **为什么原来的测试看不出来**：测"孢子飞了多远"永远测不出这个 bug——僵尸会自己走进射程，无 buff 的那次也会开火，两次测量于是**完全一致**。新用例 `MushroomRangeBuffTest` 测的是**首次开火那一刻僵尸在多远**（2.99 格 vs 4.19 格），这才是 `covers` 决定的那件事。它跑在真正的夜关 2-1 上：白天的蘑菇在睡觉，一枪不开——那也会被读成"增益没生效"。
- **顺带**：探针关卡一开始连 `teams` 都写成空的（`LevelServer` 不会补默认队伍，僵尸根本进不了实体流），所以最早两次测量是"没有任何敌人"的假象；写这种"直接驱动 LevelServer"的用例时，队伍、昼夜、波次三样都得是关卡自己的。
- **另一个顺带**：`BackpackAndCoinsTest` 里"召唤的僵尸必须到达客户端"是一个既有的偶发失败——`awaitPacket(EntitySpawnS2C.class)` 返回的是**最后一个**同类型包，而天上掉的阳光也是 `EntitySpawnS2C`，阳光恰好落进窗口时断言就在跟一枚阳光比对。改成等"kind 是 zombie 的那一个"。
