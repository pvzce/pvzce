# 第二首歌、判定字旁的乘数、结算页的战报

> 用户三条：判定字右边也要写「×几」（连续 PERFECT 的乘数）；关卡结束后的页面要能看到这一把的得分；
> 再加一首歌——`refer/ms0` 里的 `minigame` 那首。

## 现象与根因

- **乘数只有一处**：连续 PERFECT 只在右侧那行统计里，而玩家的眼睛在判定线上；"打出了第 27 个
  PERFECT"这件事在打的那一刻没有任何反馈。
- **结束页没有战报**：赢的那一页（`AwardScreen`）只画金币与解锁物；输的那一页画的是
  `存活 N 波 · 击杀 M · 用时 T`——而**节奏关卡根本没有波**（僵尸是按歌算出来的，见上一轮），
  所以那行在这一模式里是错的，不是缺的。`GameStateS2C` 只带 waves/kills/ticks 三个数，
  节奏模式的四项判定、连击、辣椒一个都没上过网。
- **生成器是单曲形状**：`MUSIC / BPM / OFFSET_TICKS / FIRST_BEAT / END_BEAT / ONSETS` 各一份，
  而"一首歌"其实是**六个数加一张表**，它们只在同一首歌上同时成立。加第二首要动的是这个形状，
  不是再加一个常量。
- **验证工具缺一块**：`smokeKeys` 按**帧**排程，而一帧不是一 tick；更要命的是**一个音符会被
  窗口内第一次按下吃掉**，所以"一直按"把每个音符都按成 FAIR/GOOD——这一模式的奖励（连击、×N、
  辣椒、战报）在冒烟里一张图都拍不到。上一轮的 `todo.md` 里就记着这条缺口。

## 定论

- **判定字右边的「×N」**（`InGameScreen.drawRhythmVerdict`）：只有 PERFECT 有，**连续 ≥2 才写**
  （第一个不算连击，而一个每两颗音符就闪一次的「×1」是在玩家追着音符看的地方添噪声）。
  它 LEFT 对齐在字的右缘之外，跟着同一条弹入曲线缩放与上浮——**不是**按"行宽的一半"居中，
  因为字是绕自己的中心放大的，锚点若忽略这一点，最要紧的那一帧里徽标会滑进字里。
- **战报走 `GameStateS2C`**：新增一个 `RhythmScore` 块（四项判定 + 最高连击 + 最高连续 PERFECT +
  辣椒次数 + 一个 `played` 标志），**关卡结束的那一刻由服务端读**，而不是拿 HUD 那条每 6 tick 一次的
  流（那一条在歌尾会差最后几个音符）。`played` 是显式的一个布尔而不是"全是 0 就算没有"：
  "这一关没有谱面"与"有谱面但一个音符都没判到"是两件事，后者是一局真实的（ albeit 难看的）run。
  协议 46 → 47，golden 重录。
- **最高连续 PERFECT 是新记的统计量**（`State.bestPerfectStreak`，进存档）：连击本身在任何有一发
  GOOD 的局里最后都是 0，而"我离下一个辣椒差多少"正是玩家想看的那个数。
- **两个结束页都画**（`RhythmScoreText.lines` 是唯一出处）：赢在结算页的羊皮纸上（标题 + 两行），
  输在失败浮层上（把"存活 N 波"整行换掉——那一行在这一模式里本来就是错的）。
  **结算页的排版是胶片逼出来的**：战报从纸条顶往下长、金币三行从纸条底往上锚（为了不撞「继续」
  按钮），纸条只有五行高，于是两块叠在一起（`PERFECT 8` 和 `本局收集的金币` 同一行）。
  定论：**有战报时金币降级成一行脚注**（`金币 +600 · 总数 8890`），页面读作"战报 + 它值多少"。
- **一首歌 = 一条 `RhythmCharts.Song`**：music / bpm / offsetTicks / firstBeat / endBeat / onsets
  一起走，外加两个前缀（关卡 id 的前缀与列表名的前缀）。`SONGS` 现在两条：
  `ULTIMATE_BATTLE`（110.00 BPM、第 0 拍 14 tick、340 拍，id 前缀 `rhythm`、名字「节奏草坪」——
  **与已发布四关完全一致，一个字节都不动**）与 `EGYPT_MINIGAME`（`refer/ms0/ancient_egypt_minigame.ogg`，
  用 `tools/rhythm_onsets.py` 量出 **94.00 BPM / 第 0 拍 0.2862 s = 17 tick / 最后一小节 295.75 拍**，
  id 前缀 `minigame`、名字「节奏草坪 · 小游戏」）。`Tier` 里的 `displayName` 换成 `label`
  （"简单"），完整名字由歌拼出来。新四关 `yard/rhythm/minigame_{easy,normal,hard,expert}`，
  难度系数同一套 0.6/1.0/1.5/2.2。
- **两个歌各一个集合**（`#pvzce:collections/rhythm_minigame`），并排在节奏草坪页。
  顺序由"集合排在它第一个成员的 id 上"这条规则自然给出：`minigame_easy` < `rhythm_easy`，
  所以**小游戏那个盒子在前**——没有为它加任何元数据，这是同一条规则的另一面（要调就调 id 前缀）。
- **编辑器的曲目字段认歌**：`RhythmCharts.songOf(music)` 命中哪首就用哪首的 tempo / 拍格 / 收尾，
  没命中就按字段里的 BPM 出匀速拍点谱（原有降级）。四档仍然只填**一个**难度系数。
- **`pvzce.smokeAutoPlay`**（冒烟钩子）：每帧读关卡自己的谱面与服务端下发的锚点，哪条 lane 的下一个
  未按音符进了 PERFECT 窗口就按哪条，走的是同一条按键队列。它不是给真实 run 用的 bot，而是
  **这一模式唯一的取证手段**——没有它，连击、×N、辣椒、战报全都只能靠推理。

## 验到了什么

- `RhythmScoreTextTest`（新）：没有谱面时零行（两个屏幕都不画块）；一局读成"四项判定"+"连击/连续/
  辣椒"两行；`judged()` 是四项之和。
- `RhythmTest` 增补：歌尾的 `GameStateS2C` 带着战报、四个数与服务端的 tally 一致；没有谱面的关卡
  报 `played=false` 而不是报零；最长连续 PERFECT 在被打断之后仍然记得。
- `RhythmChartsTest` 改成两首歌都过一遍：确定性、已发布文件与生成器逐字段一致、每档都终止于**它那首歌**
  的最后一小节、每档的 `waves` 为空且 `difficulty` 递增。
- `LevelCollectionsTest.everySongHasItsOwnBox` + `ServerMenuFlowTest`：七个盒子、两首歌都在节奏页上。
- 冒烟（`.smoke/rhythm-song2/`，四次启动各拍一件事）：`perfect_streak_badge.png` 是
  **`PERFECT ×26`**（判定字旁的乘数）；`jalapeno_rows.png` 是 **30 连击那一帧**——「火爆辣椒！」
  横幅 + **满屏每行一道火龙** + `PERFECT ×30`；`award_report.png` 是结算页上的战报
  （`本局战报 / PERFECT 8 · GOOD 0 · FAIR 0 · MISS 0 / 最高连击 8 · 最高连续 PERFECT 8 · 火爆辣椒 0 /
  金币 +600 · 总数 8890`）；`miss_verdict.png` 是失败浮层那条路径上的判定字。
- 结算页那两张图**各拍到了一个问题并因此改了两处**：战报与金币行叠字（见上），以及"领奖励"的
  点按坐标（`gui_scale = 2` 时 GUI 只有 640x360，记进 `踩坑清单` 152）。
- 一整首歌（189 秒 ≈ 11k tick）在无头运行里跑不完（服务端与渲染抢 CPU，关卡时钟只到约 22 tps，
  一首歌要九分钟墙钟），所以结算页是用一张**12 拍的冒烟专用短谱面**（`.smoke/gd/datapacks/report_smoke/`，
  与仓库里既有的 `*_smoke` 数据包同一形状）走到"放完 → 判胜 → 领奖励 → 结算页"的。
  真实四档打满全场的端到端仍然缺证据，记在 `todo.md`。
