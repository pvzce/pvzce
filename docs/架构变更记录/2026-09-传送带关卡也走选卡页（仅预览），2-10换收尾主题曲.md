## 传送带关卡直接进关，于是它们的僵尸预览没有地方显示
- **现象**：1-5 / 1-10 / 2-10 的卡组由关卡自己发，所以客户端在 `enterLevelFromMenu` 里对它们直接 `requestFreshRunDirectly`（"选卡页会让玩家挑一套马上被丢掉的卡"）。代价是**这一屏也是唯一显示"这一关会来哪些僵尸"的地方**：关卡列表只有一行名字，于是这三个关卡的僵尸阵容在整个界面上看不到。
- **定论**：卡组没得选的关卡照样走选卡页，只是那一页是**仅预览过场** —— `ChooseSeedsScreen` 多一个输入 `dealsItsOwnCards`（客户端按机制问 `PvzceClient.dealsItsOwnCards`，与编辑器页签、服务端卡组用的是同一个答案），它和"固定卡填满卡槽"一起决定 `previewOnly`：画面板与卡池都不画、点击落在草坪上、播完开场对话后 2.1 秒自动开局（与 1-1 完全同一条路径）。四条入口（关卡列表、暂停菜单重开、存档提示框重开、编辑器测试）里那三段"传送带直接进"的特例随之删除，`openSeedSelectionForRestart` 只剩"取不到关卡信息"这一个回落。顺带删掉客户端那个随之失去调用点的 `hasNothingToChoose(LevelInfo)`（`SeedOptions.hasNothingToChoose` 仍是唯一判据）。
- 关卡的过场因此多了三样它本来就有、只是看不到的东西：草坪（按关卡自己的昼夜渲染）、开场对话、僵尸预览 —— 见 `UI切换与导航架构.md` §4。

## 2-10 的音乐是普通夜曲，不是收尾关的主题
- **现象**：2-10 是夜晚的最后一关、也是第三个传送带关卡，但音乐沿用了全夜通用的 `music/moongrains`；同类的 1-10（Day 区收尾的传送带关）用的是 `music/ultimate_battle`。
- **定论**：2-10 换成 `music/ultimate_battle`，与 1-10 同一首（收尾关就是这两个）。`tools/write_night_levels.py` 里也加了 `music` 参数（缺省仍是 `moongrains`），免得下次重生成时又漂回夜曲。

## 阳光掉落是一枚硬币：间隔随机到没有形状
> 本次重做（现状见 `架构-服务端.md` §4.7 经济）

- **现象**：天上掉的阳光是**每 tick 独立掷一次**（`rules.sun_spawn_chance`，1-1~1-9 写 0.0017）。平均值对得上"约十秒一颗"，但分布是几何分布：**一局 75 秒的 1-1 里可能只掉两颗，也可能掉十颗**，中间还能夹一次 30 秒的干旱与一次一秒三颗的爆发。原因是这份实现没有"上一颗什么时候掉的"这个状态 —— 掷骰子没有记忆，"平均十秒"只保证长期平均。
- **定论**：改成**区间计时器**。新规则 `pvzce:sun_spawn_interval_min` / `_max`（默认 480 / 720 = 8~12 秒）与 `sun_spawn_initial_ticks`（默认 300 = 首颗 5 秒，开局是唯一允许天空准时的时刻）；`SunDropClock` 在每次掉落时抽下一个间隔（含两端），倒计时**进关卡存档**，读档不会白送一颗。**`min = max = 0` 就是开关**（取代 `sun_spawn_chance: 0`），`sun_spawn_chance` 规则与其 13 处关卡引用一并删除。迁移时把 0.0017 换成**均值相同的区间**（1-1~1-4 用 420~660、长关卡 540~840、其余 480~720），所以这次改的是"间隔的形状"，不是收入。`SunDropClockTest` 钉住三件事：每次间隔都落在区间内、零区间一颗不掉、倒计时随存档往返。

## 前三个关卡的草坪是"没铺完的"：用一行 / 三行草皮贴图
- **现象**：1-1~1-3 的背景本来就是原版的 `background1unsodded`（整片裸土），但地形层又把草皮格画了上去，于是屏幕上是一整片修剪过的草坪 —— 与原版"刚开始只有中间一两行铺了草"的样子不符。这三关的 `height` 也确实是 1 / 3 / 3 行，可施工的那几行落在草坪正中，上下留白。
- **定论**：**把草皮烘进背景**，生成 `background1_1row.png`（1 行）与 `background1_3row.png`（3 行）：1-1 指前者、1-2/1-3 指后者，三关照旧 `hidden_scene_elements: ["pvzce:grass"]`（格子仍然是 grass，否则种不下去）。这与 1-4 之后"草坪本来就在背景图里"是同一种做法 —— 本项目表达不了"一行 = 九格的同一张图"（场景元素是一格一张）。
- **烘的来源是 `background1.png`，不是 `refer` 里那两张行贴图**：`sod1row` / `sod3row` 与成品背景是同一份美术，但四周带一圈**透明黑边**（阴影），手工合成时那圈黑会以暗晕形式糊在泥土上（实测与背景泥土的平均色差 ~113，肉眼就是一条脏边）。成品背景里的草皮行是**同样的像素、正确的光影**，直接按行裁下来贴到 `background1unsodded` 上，零缩放、零调色，只在裁切处的上下沿做 4px 羽化。`tools/bake_sod_backdrop.py` 就是这件事，且可重跑。
- **竖向的过渡是"外扩后淡出"，不是"直接切在行边界"**：成品背景的五行**全是草**，行与行之间没有草→土的边可以照抄，直接切在行边界就是把一条直线横在泥土上（原版的行贴图自带约 20px 的草→土过渡，切在边界等于把它整段丢掉）。现在的做法是草皮带向行外各多取 **24px**，再从裁切线到行边界做升余弦淡出 —— 行内像素与原版**逐像素相同**（最大差 0），行外 24px 内是柔和过渡。横向上同理（外侧 6px）。
- **裁切的边界要按"美术里草到哪"取，不是按"棋盘到哪"取**：成品背景的草皮比可种区宽 —— 房子那侧多约 8px、路沿那侧多约 20px（原版把整张草皮都画了）。第一版照可种区 256..976 裁，两侧的草被齐齐切掉，看上去就是"路沿和草地接得不对劲"。现在按实测的草皮范围（**x=251..996**，取最长连续草段）裁，只在外侧各留 8px 泥土边并做 6px 淡出；验证方式是"烤出来的图里绿像素范围 = 原版的绿像素范围"。
- **对齐**：草皮行取五行的**正中间**，与 `LevelStage.board` 对不足五行棋盘的居中方式一致 —— 1-1 是第 2 行（上下各两行裸土）、1-2/1-3 是第 1~3 行（上下各一行），烘出来的草皮正好压在玩家能种的那几格上。验证：两张图逐行绿占比分别是 `[0,0,100,0,0]` 与 `[0,100,100,100,0]`。

## 出怪节奏只有一张固定表：清场之后只能干等
> 本次重做（现状见 `架构-服务端.md` §4.7.2）

- **现象**：波次表能写"第几秒来第几波、一波里每几秒出一只"，但**没法表达三件关卡真正需要的事**。其一，玩家把场上清空之后仍要等完作者写给"更慢的玩家"的倒计时 —— 快的人白等、慢的人刚好；其二，一波僵尸只能按写死的间隔涓流，打死一只不会让下一只来得更快，于是"剩六只却每五秒一只"；其三，一波的组成必须逐个写出，而"这一波值多少威胁"是另一回事（普通 1 分、铁桶 3 分、巨人 12 分）。
- **定论**：新增关卡机制 **`pvzce:wave_pacing`**（数据 `WavePacingData`，注册在 `LevelMechanics`，与 deck / mower 一样**有隐式默认**：不声明也拿到引擎默认节奏）。四种模式：`fixed`（现状）、`stockpile`（场上本波僵尸少于 `max_alive` 时按差额缩短间隔，到上限就停手）、`survival_ratio`（本波放完后，死亡达到 `kill_ratio` 就让下一波倒计时每 tick 多跑一拍）、`budget`（用点数在 `pool` 里随机组合，`entries` 作为兜底）。按**波次编号（从 1 开始）**的覆盖表选择"哪一波用哪个机制"，与波次页显示的编号一致。
- **清场奖励是默认行为**：`clear_reward_factor`（默认 3）在**场上无僵尸且上一波放完**时加速倒计时，但**前段不加速**（`clear_reward_grace_ticks`，默认 10 秒）—— 奖励是"少等一会儿"，不是"下一波立刻贴脸"。第一版把整段倒计时按 3 倍跑，结果 1-2 变成三波连发；缓冲窗口就是那次教训的产物。
- **每波倒计时的目标是冻结的**：目标在倒计时开始的那一 tick 定下（`nextWaveTargetTicks`），之后不再变。目标若在倒计时途中变小，而计数器被夹在目标上，这一波就**永远到不了终点** —— 这是"只出一波就不动了"的成因，也是本次唯一一个把整关跑成死循环的 bug。
- **`due` 判定要求倒计时真的跑过**：上一波还在放怪时计数器被冻结在 0，而 0 会被"到期"读成"等待结束"，于是后续每一波都在前一波被触发的下一 tick 瞬发。判定加上 `waveIntervalTicks > 0` 之后，放怪窗口与倒计时不再互相冒充。
- **等待的起算统一为"等待 + 1 拍"**：计数器在装填的下一拍才减、减到 0 时出怪，于是 **300 的间隔＝301 拍、1200 的死亡门＝1201 拍**。这条边界是所有波次表 `delay` 的隐含契约（`WaveSystemTest` 一直按它断言），重做期间它被破坏过两次，症状都是"整体早一拍"。
- **每波自己算存量**：`waveOwner / aliveByWave / killsByWave / arcByWave / releasedWaves` 记"这一波的僵尸还有几只站着、死了几只"，因为关卡的 `aliveZombieCount()` 回答的是"整片草坪"。读档时按**最新波优先**重新认领场上的僵尸（实体 id 不跨进程），代价是一波在读档后可能多补一次存量。
- **死亡门会收紧**：`early_kill_delay_factor`（默认 0.75，下限 1 秒）让"打死一只才出下一只"的 20 秒上限每超时一次缩短四分之一 —— 打不死第一只的玩家会依次遇到 20 / 15 / 11 / 8 秒，而不是卡在第一只上。
- **工作量证明**：`WavePacingMetricsTest` 对 23 张表跑三档击杀速度，输出总时长 / 最长空场 / 空场占比 / 并发峰值（`-Ppvzce.smoke=pvzce.pacingReport=true` 打表），默认只断言"最慢档也能通关"。**12 张关卡按它的数据重调了两轮**（只动 `delay` 与 `spawn_interval`）：1-7 从 17222 拍到 10292、1-8 从 19172 到 11402、1-9 从 24932 到 14462、2-4 从 25022 到 16742，最长空场从 13~14 秒降到 7~10 秒。传送带关（1-5 / 1-10 / 2-10）与墓碑关 2-5 保持原节奏 —— 前者的压力来自卡的发牌速度，后者的波次只是进度条。

## 出怪速度没有旋钮：想调快只能重写整张波次表
- **现象**：关卡能调"僵尸走多快"（`zombie_speed_multiplier`）和"卡片冷却多长"（`seed_cooldown_multiplier`），但**僵尸多快出现**只能一个一个改 `waves[].delay` 与 `waves[].spawn_interval`。两张收尾的传送带关（1-10 / 2-10）因此没法只调节奏：它们的压力来自"卡按固定节奏发、僵尸来得更快"，而这半边没有一处能写。
- **定论**：新规则 **`pvzce:zombie_spawn_speed_multiplier`**（缺省 1，范围 0.1~20）。它是**速率**倍率（越大越快，与 `zombie_speed_multiplier` 同一读法）：`WaveDirector` 在取波间隔（`effectiveWaveDelay`）与取波内出怪间隔（`effectiveSpawnInterval`）时都除以它 —— 两处一个读法，不存在"只快了一半"的写法。不缩放的东西也写明：`warning_ticks`（横幅的提前量是给玩家看的）与 `spawn_interval` 的 15 tick 下限（"一波不是一次性倒出来"这条缩放后仍然成立）。规则经 `WaveDirector.Host.zombieSpawnSpeedMultiplier()` 读，与波次需要的其它东西同一个接口。
- **1-10 / 2-10 写成 `2.0`**：同一张波次表按两倍速播，而传送带的发牌速度（4 秒一张）不变。
- **顺带修掉一个构造顺序问题**：`WaveDirector` 在 `LevelServer` 构造里比 `this.rules` 先赋值，而它构造时就会算第一波的延迟（现在要读这条规则）—— 规则赋值挪到 `WaveDirector` 之前，否则是构造期的空指针。`ZombieSpawnSpeedTest` 钉住"2 倍速就是整条时间线砍半"（第一只的 tick 正好一半，第四只在 2 tick 误差内一半）与两个关卡的数据。
