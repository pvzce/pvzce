## 5. 实体与能力系统

### 5.1 共用实体基类

`com.pvzce.api.entity.Entity` 同时被服务端与客户端继承：

| 层 | 类 | 额外内容 |
|---|---|---|
| 共用 | `Entity` | id、defId、cellX/cellY、绝对 height、surfaceId、health、animation、**网格边界**、`gridX()/gridY()`、`entityKind()`、`layer()` |
| 服务端 | `PvzceEntity extends Entity` | team、removed、独立 `AttributeContainer`、`tick(LevelServer)`、`saveState()/restoreState()`（对称，强制实现） |
| 服务端 | `PlantEntity` / `ZombieEntity` / `ProjectileEntity` / `ResourceDropEntity` / `CardDropEntity`（恐怖花瓶与花瓶里砸出来的种子包：血量就是它的剩余时间） | 能力实例列表（`CardDropEntity` 没有能力，也不吃伤害） |
| 客户端 | `ClientEntity extends Entity` | kind、layer（来自包）、只读属性结果、`AnimationComponent` |

`ClientEntity.from(EntitySpawnS2C)` 与 `apply(EntityUpdateS2C)` 是包→状态的**唯一**应用点；网格由两侧用同一份逻辑从 cell 派生，所以 `EntitySpawnS2C` **不再传 gridX/gridY**。

**客户端在两次采样之间补间**（`ClientEntity.visualCellX/Y/Height`）：`LevelServer.syncSlots` 每 3 tick 同步一次实体位置（20 Hz），而客户端画 60~260 帧——直接画包里的坐标就是一条 20 Hz 的阶梯：站住五帧、跳一下。速度越慢越明显，而"被豌豆打"恰恰是玩家盯着单只僵尸看的时候。
- 补间是**渲染位置**：`cellX()` / `height()` 仍然是服务端的数，命中测试、相机换算与所有断言读到的都还是权威值。
- 线性、按墙钟推进、夹在区间内；从一个**正在画的位置**开始（而不是上一包的位置），所以迟到的包不会让实体先倒回去再往前滑。
- `height` 也在里面：掉落物的下落是靠 height 表达的，只补 x/y 会让太阳的下降仍是 20 Hz。
- `SYNC_PERIOD_NANOS` 与 `tickCount % 3` 是**一对**，改一个要改另一个。

### 5.1.1 地表、通路与空间位置

`WorldPosition(x, y, elevation)` 的 x/y 是棋盘平面坐标，elevation 是相对棋盘基准面的绝对高度，
单位均为格。`Entity.position` 与 `ClientEntity.visualPosition` 分别提供权威值和补间值；
`projectedY` 在投影阶段计算 y + elevation。实体高度包含地表、承载物和自身运动，不再叠客户端水面补偿。
`surfaceId` 表示实体所在通路，与植物的叠放 `layer` 是两个独立事实。

`SceneBoard` 是两侧共用的场景状态：每个通路一份 `SceneGrid`；`Cell` 保存基础元素、可选覆盖物、
`SurfaceProfile` 和厚度。profile 是 `clamp(elevation + slope_x*x + slope_y*y, min, max)`；
屋顶、水面与平台均通过同一 `elevationAt` 采样。覆盖冰、弹坑、墓碑或容器不会修改基础高度。
旧屋顶和泳池背景的兼容几何在 `SceneBoard.forLevel` 导入时解析，运行时只读解析后的曲线。
显式元素 profile 优先于泳池兼容曲线。

`LevelDef.scene` 属于默认通路 `pvzce:ground`，可选 `surfaces` 增加稀疏通路：

```json
"surfaces": [{
  "id": "example:bridge", "name": "桥面",
  "profile": {"elevation": 1.4}, "thickness": 0.2,
  "scene": {"pvzce:grass": ["4,2", "5,2", "6,2"]}
}]
```

没有声明的格不提供支撑；`initial_entities` 可用 `surface` 指定通路。额外通路的 profile 属于通路，
材质更换保留该曲线；初始覆盖物继承同格已声明的基础材质，未声明基础时使用草地。
`SceneElementDef.overlay` 声明覆盖物，`profile` 可声明默认通路的地形曲线。
**默认通路的起伏只有这一条来源**：一格的高度是它自己的场景元素的曲线（`elevation + slope_x·x + slope_y·y`，按 `min`/`max` 夹住），
不是逐格手填的数（屋顶与泳池那两条曲线就是这么来的）；额外通路的起伏则完全由它自己的 `profile` 决定，与格子上画什么无关。
`yard/minigame/terraced_hillside` 两层各用了一条：**坡地是默认地表**，后院（`pvzce:grass`）经一列
`hillside_bank_low`（`slope_x` 0→0.4）升到 `hillside_mid`（平顶 0.4），再经 `hillside_bank_high`（0.4→0.8）
升到 `hillside_high`（平顶 0.8）——两级梯田与左侧后院同属一层、靠斜坡过渡，因为默认地表是唯一能放小推车
（`MowerMechanic` 只认默认地表）也是关卡校验要求铺满的那一层。**第二层是梯田正下方那条稀疏通路**
（`pvzce:under_terrace`，平顶 0，只盖第 4~8 列，其中两列草坪当葵田），高度取自己的 profile，
它排在坡地之下、被梯田的瓦片压住，只在梯田边缘那条缝里露出来；玩家用 PgUp/PgDn 切过去种，
而走在坡地上的僵尸不会到那一层，所以那里是安全的。
高度决定谁能打到谁：同一层内按实际身体高度命中，低处的平射会死在土坡上、抛射能越过；
射手的目标查询按通路过滤（`enemiesInRow(row, team, surface)`），所以另一层上的人和僵尸彼此不在视野里。
同一套元素曲线反过来用就是 `yard/minigame/reef_passage`：海里两道礁石（0.45 与 0.85）是**僵尸要翻的高地**、
码头与海面是低处，礁石正面吃掉低处的平射，礁顶的射手才够得着礁后的水面。
已有构造器和动作入口保留默认通路适配，扩展能力通过显式 surface 与 `WorldPosition` 入口传递来源。

近战、啃咬、叠放与行攻击按通路查询；平射/抛掷按实际身体高度与轨迹碰撞。
`SceneBoard.firstObstruction` 连续裁剪每 tick 的线段，检测基础地形内部和桥面实体厚度；
零厚度面仍阻挡穿越，沿面运动不会被当成穿越。**传送门是这条判定唯一的例外**：僵尸、平射与滑行中的小推车
跨过 `PortalMechanic` 的门时位置被瞬移，那一 tick 的遮挡判定不从穿门前的坐标起算
（否则子弹会横穿门所绕开的那道墙、死在自己刚绕过的地方）；出口本身落在实心地形里时，
下一 tick 从出口起算的判定照常销毁它。门的**换位范围**由数据给：`PortalData.relocate_min_x`
是"换位时最靠左能到哪一列"（默认 0 = 整块棋盘），因为随机挪位置一旦挪进房前，玩家没有反应时间。
`yard/minigame/tunnel_corridor` 就是靠这两条成立的关卡：山体够高让每一行的平射都死在坡面上，
唯一能打到山那边的路径是穿门（0.6 的山头也让投手的弧线抛得过去，作为第二条路）。
爆炸使用 `LevelAccess.reachedByBlast` 的空间范围与障碍判断，
伤害和附带状态共用 `enemiesInArea`，磁吸装备也检查空间可达性。
全场冻结等明确声明为全场的能力仍作用于全场。`SurfaceLinksMechanic` 处理显式单向坡道连接：
僵尸沿指定方向跨过同排列中心时更新通路和支撑高度，浮空身体不经过坡道；波次条目可指定 `surface`。
无支撑边缘的掉落和自动选层见 `todo.md`。

### 5.1.2 单体数值属性

`EntityAttribute` 是注册表里的数值定义（id、默认值、上下界、是否同步），注册入口是
`BuiltInRegistries.ATTRIBUTES`；mod 在首次冻结前通过 `Registry.register` 注册，数据包可以写
`data/<ns>/attributes/<name>.json`。`AttributeContainer` / `AttributeInstance` 属于单个服务端实体，
通过 `PvzceEntity.attributes()` 添加已注册属性、修改基值、设置或移除具名 `AttributeModifier`。
同一修饰器 id 在同一属性里只保留一份；同种实体及注册表定义不会被一起改动。

求值顺序固定：基值加 `add_value` → 对加算后的基值叠加 `add_multiplied_base` →
逐个乘 `1 + amount`（`add_multiplied_total`）→ 按属性定义夹值。修饰器按 id 排序，计算不依赖
加入或保存顺序；基值和 amount 拒绝非有限数。内置属性及上下界只有 `EntityAttributes` 一处，
内容定义里的生命/速度/啃咬字段为实例提供初始基值，能力结构仍由能力定义提供。
属性使用 double 求值；生命、伤害与间隔在游戏的整数消费点四舍五入。

- 所有服务端实体带 `max_health` 和 `render_scale`；僵尸额外带 `movement_speed`、`attack_damage`、
  `attack_interval`、`armor_durability_multiplier`。绘制倍率乘在内容美术倍率上，不改判定盒、放置和攻击范围。
- `ZombieDef.attributes`、`WaveDef.Entry.attributes`、`InitialEntityDef.attributes` 共用 `AttributeOverrides`：
  数字简写为基值，或写带可选 `base` 与 `modifiers` 的对象；新属性自动按注册默认值添加。
  波次/预放置覆盖在首次发布前生效，僵尸先叠加定义属性与生成生命倍率；新实体以最终上限满血进入。
- 运行时降低最大生命夹住当前血量；提高上限不自动回血。护甲耐久倍率变更保持各件的剩余比例，
  破损画面、断臂与 Boss 阶段阈值读实例上限；生成生命倍率保留为 `spawn_health` 总值乘算修饰器。
- 实体基态的 `Attributes` 保存基值及持久修饰器，`persistent:false` 的修饰器不落盘；恢复替换该属性的修饰器，
  不在构造器初值上重复叠加。未知属性在存档恢复时跳过；数据定义与生成配置的未知属性在加载/校验时报告。
- `EntityAttributesS2C` 发送开启同步的属性的完整计算结果，生成/全量镜像必发，变更触发发布，客户端不计算游戏属性。
  `EntitySpawnS2C.maxHealth/scale` 是同一服务端属性的初始投影；后续快照更新 `ClientEntity.maxHealth/renderScale`。
  波次待出怪队列与蹦极货物保存生成配置，实体自己的属性保存到自身基态。

```java
// mod 初始化时注册；运行时给某一个服务端实体添加。
Identifier reach = Identifier.parse("example:reach");
Registry.register(BuiltInRegistries.ATTRIBUTES, reach, new EntityAttribute(reach, 1, 0, 8, true));
entity.attributes().add(reach).setBaseValue(2);
entity.attributes().get(EntityAttributes.RENDER_SCALE).setBaseValue(0.5);
```

更广的数值迁移和编辑器属性控件/静态预览边界见 `todo.md`。

### 5.2 能力（Capability）

行为由**可注册、可组合的能力对象**表达，不是实体里的字符串 switch。

- 接口：`PlantCapability` / `ZombieCapability` / `ProjectileCapability`（`api/content/capability`）。
- 类型注册表：`BuiltInRegistries.PLANT_CAPABILITIES` 等，条目是 `CapabilityType<T>(id, MapCodec<T>)`。
- 列表元素：`TypedCapability<T>(Identifier type, T value)`，JSON 里形如 `{"type":"pvzce:shooter", ...}`。
- 每个实体构造时 `instantiate()` 出一份**实例**，状态（冷却、引信、护甲血量…）保存在实例里，因此新增一种行为不需要给实体加字段。
- 存档：每个能力把状态写进以类型 id 为键的子标签（`capabilities: {"pvzce:shooter": {...}}`），实体基类负责遍历。

内置能力**以注册表为准，正文不抄第二份名单**：植物见 `PlantCapabilities.bootstrap()`、僵尸见
`ZombieCapabilities.bootstrap()`、子弹见 `ProjectileCapabilities.bootstrap()`（三者各自注册进
`BuiltInRegistries` 的对应注册表），要完整清单读它们。举例：植物有 `shooter` `thrower` `producer`
`explosive(timed|proximity|row)` `melee` `cone` `squash` `nocturnal` `charm` `echo_relay`，
僵尸有 `armor` `vault` `bounce` `float` `summon_dancers` `submerge` `zamboni`（行走/啃咬循环留在
`ZombieEntity`，所有僵尸共享）。

> `bounce` 与 `vault` 是**同一份实现的两种读法**（`VaultCapability` 的第二个 codec）：跳跳僵尸每个周期
> 都重新找一株植物跳过去，撑杆僵尸只跳一次。滞空窗口、位移缓动与"高坚果挡得住"这三条只有一份，
> 因为它们是同一个动作。`bobsled` 的雪橇血量与随从、`jack_in_the_box` 的距离引信（不是计时器）
> 各自写在自己的能力里，两个都以原版常量为默认值。
>
> **一次跳跃的位移是美术自己的曲线，不是一条缓动**：`VAULT_TRAVEL_KEYS` / `VAULT_LIFT_KEYS`
> 由 `tools/vault_curve.py` 从**转换后**的 `jump` 片段里读出来（躯干管水平、最低的那只脚管抬升），
> `DEFAULT_JUMP_DISTANCE` 就是那段位移的实测值（1.0908 格）。两者必须一起改：
> `PoleVaultTest.theArtAndTheSimulationAgreeOnWhereTheZombieIs` 把表钉在片段上。
> 跳跳僵尸的 `anim_pogo` 只提供弹簧压缩，水平跨越沿用 `AIRBORNE_FROM/TO` 缓动窗口，
> 同一窗口内由服务端实体高度提供正弦起落，落地恢复地表高度。
> 海豚骑士共用这套表，但它的片段只有 115 拍（撑杆的是 210）——见 `todo.md`。
屋顶内容能力：植物 `garlic` / `umbrella`，僵尸 `ladder` / `catapult`。

内置子弹能力：`linear` `arc` `homing` `splash` `status` `pierce` `shatter`。

`HomingMotionCapability` 从发射植物所在位置起飞，有限转向追踪全场敌军，优先空中目标，
同优先级按距离和实体 id 选择；目标死亡或不可达后重选。`ProjectileEntity` 以真实位置和高度判定命中，
不使用直线弹丸的过线判据；方向与发射状态随能力保存。猫尾草的每枚尖刺独立锁定目标。

`PlantCapability.onRestored` 在恢复状态并加入关卡后派发，用于重建清雾等运行时登记；
它不重放 `onPlaced` 的即时行为。`RevealCapability` 重新登记，移除仍由 `onRemoved` 注销。
倭瓜能力全程免疫伤害，`walk_over` 标签让啃食扫描越过它。
`WakeBelowCapability` 只唤醒同格主体放置层的植物，壳层南瓜与底层承载物不参与选择。

**铃兰与共鸣苔组成有限接力网络**（`pvzce:echo_relay` / `pvzce:echo_conduit`，`EchoRelayCapability` / `EchoConduitCapability`）：`EchoNetwork` 按格子 BFS 遍历同队、存活、醒着且占据格子的节点，同格距离为零，正交邻格为一步；只有铃兰按距离各发一枚普通地面声波，苔只延伸路径。网络任一节点前方有地面目标即可发起接力，尾声之后整组休息，环路不反复触发，新成员不能跳过共享冷却。多节点接力三轮后共鸣六秒，爆发期间不蓄下一轮；真正独唱不蓄能。当前铃兰数量决定共鸣强度：一株 1.5 倍，每多一株增加 0.25，最多三倍；默认值由 `PvzceConstants` 提供。自身共鸣与本 tick 行激活取较大者，行配置为倍率上限。上层植物通过同队、严格位于其定义放置层下方的共鸣苔分享加速，断线或来源消失撤销；苔本身不增加强度。`PlantEntity.actionRate` 合并普通植物的网络、规则与浇水倍率，铃兰自己的剩余工作量单独消费同一网络倍率，不重复乘算。`RateClock` 逐 tick 积累当前倍率并保存小数余量，各攻击/生产能力持有自己的时钟；攻击间隔与阳光生产加速，引信、成长与卡槽冷却保持各自真实 tick。铃兰保存剩余工作量、接力尾声、蓄能、自身共鸣期限、待发声波与动画期限，`hasPendingWork` / `tickPending` 继续兑现已安排工作。放置与叠层仍只有 `PlantPlacement` 一处，共鸣苔使用陆地 carrier 标签；实体绘制层不用于上下承载判定。

**"胆小"是射手的一个字段，不是第二种射手**（`pvzce:shooter.hide_within`，缺省 0 = 从不躲）：胆小菇的孢子、冷却、目标搜索与豌豆射手完全一样，不同的只有一条——**有任何能打的僵尸进到它一格以内，它就缩起来、并且完全停止射击**。`ShooterCapability.tick` 把这一条问在冷却之前，所以缩着的这段时间连冷却都不走；"它会打谁"与"它怕谁"共用同一个 `canBeHitByGround` 判据，被魅惑的僵尸与够不着的空中僵尸都不吓它。模型里 `hide` 是一次性的低头、`hide_loop` 是保持，两者由 clip 自己的 `on_end` 串起来（服务端只知道"现在躲着"，不知道 clip 有多长——与土豆雷的 `armed`/`armed_loop` 同一形状）。

**"打三下冻住、打在冰上碎"是一条弹丸规则，计数落在僵尸身上**（`pvzce:shatter`，冰爆菇的冰弹）：每发先按自己的伤害结一次（`target.damage(def, damage, level)`，与普通弹丸同一条路），再给僵尸的 `addBuildup(pvzce:iceboom_chill, 1)` 加一；到 `hits_to_freeze`（默认 3）就上 `IMMOBILIZED` 并把计数清零，已经冻着的目标则改用 `pvzce:shatter` 打 `shatter_multiplier`（默认 3）倍的伤害。**计数必须在僵尸身上**：弹丸是命中即销毁的，记在弹丸实例里的计数永远到不了 2，单测直接调 `onHit` 却会通过——"三发冻结"在实机里就是永远不触发。`ZombieEntity.addBuildup/buildup` 是**带键的计数**（与 `statuses` 并列，没有时钟），进僵尸自己的存档；键是**共享**的（`PvzceIds.ICEBOOM_CHILL`），所以两株冰系植物会一起攒同一份冰。**这个能力回答了 `replacesDirectHit`**，因此三条分支都必须自己把伤害打出去——少一处就是"僵尸被打了半天不掉血"。温度判据是 `ZombieEntity.frozen()`（即 `IMMOBILIZED`），碎冰这一下用 `pvzce:shatter` 类型（`ignores_front_armor`），冻住之后举在身前的东西挡不住它。

**寒冰菇冻的是"全场"，所以它的形状是行不是半径**（`pvzce:freeze_all`）：同一 tick 里给每一行的每只僵尸上 `IMMOBILIZED`（**6 秒**）、20 点 `pvzce:splash` 伤害、16 秒 50% 的 `SLOW`，然后植物消失（美术里没有"爆炸"这一姿态，它本来就是一瞬的事）。**被冻住的僵尸是"停住"而不是"变慢"**：服务端不再让它移动/啃咬，并把这个状态当 `EntityUpdateS2C.frozen` 发出去（与 `chilled` 分开：后者只缩放速度），客户端据此做两件它自己做不了的事 —— 在脚下画出原版的冰锥（`textures/entities/status/frozen_spikes`，用 `icetrap` 那张图），并把这条 clip 的时钟按住（`AnimationPlayback.setPaused`：解冻时把时间轴整体后移，动画从被冻住的那一帧接着放）。没有这一段，被冻的僵尸会在原地继续走完整套走路循环，看起来像"卡住了"而不是"冻住了"。**"冻不住谁"是标签不是分支**：`#pvzce:freeze_immune` 里的僵尸（气球、遁地的矿工）照吃伤害与寒冷，只是不被冻住——原版对它们的区别正是这两件事分开。引信期间它与灰烬类一样不可啃（`invulnerable`），这也让"种下去就冻"这一秒不会被一只路过的僵尸取消。

**召唤是僵尸的能力，队形是它的数据**（`pvzce:summon_dancers`，舞王僵尸）：进场以 `approach_speed`（月亮步，0.67 格/秒）走到 `summon_at_x`，停下、举手 `summon_ticks`，然后按原版的十字队形招出 `count` 名伴舞（同排前一格 / 同排后一格 / 上一排 / 下一排），此后每 `resummon_ticks` 检查一次队形、缺人就补。**"哪个位置缺人"是每 tick 按位置重新数出来的**，不是记住自己生成过哪些实体：实体 id 不写进存档，记住的那份名单读档后会指向不存在的实体，舞王会再招一整队。伴舞生成在**舞王当前的队伍**上，所以被魅惑的舞王招出来的伴舞天然帮植物打——原版那个成就没有一行专门的代码。

**寒冷同时拖慢腿和嘴**（`ZombieStatus.SLOW` 的两处读法）：`moveSpeed` 乘 `magnitude`，啃咬间隔按 `1/magnitude` 拉长（`ZombieEntity.biteIntervalTicks`）。原版的"寒冷"是一个状态减速两件事，只减走路会让寒冰射手与寒冰菇的减速比原版弱一半。

**`pierce` 是"穿过并命中下一只"，不是"每 tick 再打一次"**：`ProjectileEntity` 记着这发子弹**打过哪些僵尸**（`hitIds`），`findTarget` 跳过它们。没有这一条时，一发 20 点的穿透子弹会在它和僵尸重叠的每一 tick 各打一次 —— 200 血的僵尸十个 tick 内死光，看起来就是"秒杀一切"（`NightAreaTwoLevelsTest.oneBurstDamagesEachZombieOnce` 钉住"一发最多打一次"）。用 id 集合而不是"上一只"：两只僵尸挤在同一格时，只记上一只会让子弹从另一侧反复打第一只。**内置植物里没有穿透子弹**（大喷菇走 `pvzce:cone`，见下一条）：内置数据包里只剩 `data/pvzce/projectiles/fume.json` 这一份带 `pvzce:pierce` 的孤儿定义（没有任何植物引用它，但它仍会被加载），机制本身由同一个用例钉着。

**大喷菇是"即时光锥"，不是短射程射手**（`pvzce:cone`）：那团气**同时出现在整个锥形范围里**、命中里面站着的每一只、然后消失，所以它是 `explosive(row)` 与 `freeze_all` 的同族——**一个形状，结算一次**——而不是一颗要飞到每只僵尸身上的子弹。做成子弹时它必须借 `pvzce:pierce` 加 `hitIds` 那套"穿过并记住打过谁"的记账来**模拟**范围伤害，屏幕上还读成"远程狙击手"而不是"贴着邻居呼气"：一团气不该有飞行时间。字段是 `interval`（90）/ `damage`（20）/ `range`（4，原版"前方 4 格"）/ `damage_type`（缺省 `pvzce:spray`，于是**穿纱门、不穿帽子**）/ `cloud_particle` / `cloud_count`。**"在前面"是按格子判断的，不是按枪口线**：植物中心 1.5、枪口 1.8，而走到植物身上那只僵尸的中心是 1.99 —— 比枪口更靠右、也在 4 格之内，所以只比 `cellX` 会让蘑菇对着**正在啃它的那只**喷气（原版的喷雾从不打自己那格）。判据因此是 `zombie.gridX() > plant.gridX()` 再加射程，`NightAreaTwoLevelsTest.theCloudReachesFourCellsForwardsAndNoFurther` 三只僵尸（锥内 / 四格之外 / 踩在植物身上）一起钉住。

**气是"画"出来的，不是"飞"出来的**（`cloud_particle` / `cloud_count`）：粒子引擎把一条定义里的**每一颗粒子都放在 effect 生成的那一个点上**，只有 `motion` 会把它挪走，所以一次 emit 只是植物脸上的一团。原版没有这个问题——它的 `FumeCloud` 就是那颗**会飞的投射物精灵**，气显得铺开是因为图在飞；这里的伤害是瞬发的、没有东西可飞，所以形状是**画**出来的：`cloud_count` 个发射点沿锥形均匀铺开，各自带 `pvzce:fume_cloud` 的前向漂移。**间距（`range / cloud_count`）必须小于一团云的宽度**，否则画出来是一串断续的独立团而不是一条气。**这条约束跨两个文件**——云的大小写在粒子里（`look.scale`，见 `data/pvzce/particles/misc/fume_cloud.json`）、铺几个写在能力里（`ConeAttackCapability.DEFAULT_CLOUD_COUNT`，JSON 用 `cloud_count` 覆写），所以**把粒子调小就要把 `cloud_count` 调大**，否则又会出现缝；这两个数都不要在正文里抄，改一处就要同时看另一处。`NightAreaTwoLevelsTest.theCloudIsDrawnAsALineWithOneSound` 钉住间距、行高与"声音只挂一个发射点"。

**睡觉会冒 Zzz**：睡着的植物每隔 0.62 秒在头顶偏左吐一个 "z"，三个尺寸轮着来（小→中→大），所以一次呼吸是一条斜向上的螺旋。三个尺寸是**三份粒子定义**（`pvzce:zzz_1/2/3`）而不是运行时缩放 —— 粒子的尺寸是定义里的一个数（见 `架构-客户端.md` §6.5.1），三份定义让发射端只需轮询一个列表。美术由 `tools/gen_zzz_sprite.py` 生成（原版没有 Zzz 的贴图，它是用原版自己的字体画出来的；本项目字体图集是文本图集，切不出单字，所以在工具里渲染一次）。**发射在客户端**（`InGameScreen.tickSleepZzz`）："哪些植物睡着了"是服务端已经发布的状态（`sleep`），"哪些植物会睡"在客户端加载的动画文件里，而睡觉是**持续事实**而不是事件 —— 从服务端发就要为每一次呼吸发一个包，在客户端只是一个墙钟计时器加零个包。每个实体各自计时并按 id 错开，一排蘑菇不会齐步喘气。

**睡觉是关卡时钟的函数，不是存下来的标志位**（`pvzce:nocturnal`，蘑菇）：`asleep = !awake && !level.isNight()`，所以入夜、`/time` 回拨、读一份夜里的存档都不会留下"白天醒着/夜里睡着"的分裂状态。真正进存档的只有一件事——咖啡豆的唤醒（`Awake`），它一旦成立就永久有效。**抑制行为只有一处**：`PlantEntity.tick` 在植物睡着时跳过所有没有 `ticksWhileAsleep` 的能力，于是射手、生产者、引信一起停下，而不是每个新能力各自记得判断白天黑夜；`NocturnalCapability` 自己 opt-in，因为它负责发布 `sleep` 动画（美术必须定义这个 clip，否则客户端会静默回退到 `idle`，`AnimationResourceLoaderTest` 钉住这一条）。

**咖啡豆只做一件事：唤醒**（`pvzce:wake_below`）。它对下方的植物调 `PlantEntity.wake()`，返回值说明"真的叫醒了一个"（播 `wake_sound`），对醒着的植物**什么都不发生**——豆子照样被消耗，这是原版的取舍，也是"它不是一颗瞬产阳光的按钮"的唯一表达。唤醒钩子不管能量豆：大招是另一套设计（`02` 文档 §2.2.5），不挂在同一个钩子上。

**生产总量与掉落颗数分别定义**：`ProducerCapability.amount`（成长后为 `currentAmount`）是每轮总量，
`drop_count` 默认 1，配置多颗时平均拆分并分配余数。双子向日葵总量 50、两颗各 25，
每 12 模拟 tick 弹出下一颗，落点间距 0.6 格；这些常量位于 `PvzceConstants`。
单颗沿用 `ResourceDef.riseScatter`，多颗通过 `LevelAccess.spawnProducedResource` 的横向漂移参数
指定分开的落点。生产周期仍由各实例的 `RateClock` 消费行动倍率，弹出延迟不占用生产周期。
后续掉落队列保存剩余 tick、数额、缩放与漂移；续档保留未弹出的颗粒，已经掉落的资源仍按既有规则不恢复。

**浇水与唤醒同形：由能力回答"这水用来做什么"**（`PlantCapability.water(plant, level)`，缺省什么都不做）。工具那一侧只有一句"挨个问每个能力"，内容那一侧才决定效果——今天只有 `ProducerCapability` 回答"我还没长大"，于是把成长计时压到 1、当场长大（阳光菇是它的用例）；浇在别的植物上就只剩下面那两件实体的事。**回满血与加速时钟属于实体**：浇水状态由 `PlantEntity.water` 保存，生产者自己的钩子负责催熟。
`PlantEntity.actionRate` 合并规则、回声、护理与天气倍率；水壶与肥料的加速取较高值。
肥料通过 `PvzceConstants` 定义 30 秒内攻击与生产速度 ×2，仅刷新 `fertilizedTicks`，
不回血、不调用能力的催熟钩子，剩余模拟 tick 进存档。
攻击能力或阳光生产者可施肥，其它植物 / 空格被工具入口拒绝且不扣冷却。

**缠绕水草用"地形"杀僵尸，而不是伤害**（`pvzce:drag_under`）：把自己格子里最近的一只**地面层**僵尸拖下水——`victim.damage(victim.health(), pvzce:drag_under, level)` 一击必杀，而 `drag_under` 这个伤害类型声明 `ignores_armor`，所以铁桶和普通僵尸沉得一样快。够得着谁由两条判据决定：`layer() == EntityLayers.GROUND`（气球在天上、矿工在草坪下）与 `canBeHitByGround()`（潜航中的潜水僵尸也不算——它连子弹都打不到，水草自然拖不动）。**效果是即时的、美术不是**：被杀的那一 tick 就播 `grab`，此后 `drag_ticks`（24）里植物仍然占着格子、倒数完才 `remove()`，与爆炸植物"伤害当 tick 结算、画多留一会儿"是同一个取舍。它可种在水地形或注水花盆上（`#c:water_plant` 标签），也能拖走花盆所在格的普通陆地敌人；拥有 `HammerCapability` 的巨人被排除。它在 3-3 首通时发给玩家。

**自爆的身体不留尸体**：`ZombieEntity.damageBody` 给每个死者留 `CORPSE_TICKS = 360`（6 秒）好让死亡动画被看到，唯一例外是**自己把自己炸掉的身体**（`selfDestructed`）：小丑僵尸爆炸时 `explode()` 会在伤害范围结算之后直接 `zombie.remove()`，也不掉头——爆炸云就是全部的葬礼，一具在原地站六秒的僵尸是玩家报过的现象。

**爆炸会开瓶**：`LevelAccess.breakContainers(centerX, centerY, radius)` 是"把半径内的容器各按一次点击打开"的那一个入口，今天只有小丑僵尸的爆炸调用它（`plant_radius` 那一圈）——它先是两次伤害结算，然后才开瓶，刚从瓶里出来的僵尸因此不会被放它出来的那一下顺带炸死。容器自己的打开仍是 `LevelServer.smashPot` / `smashVase` 两条（卡掉成种子包、僵尸出来、阳光落地）。

**"被容器放出来"是一个独立的事件**（`ZombieCapability.onReleased`）：波次把僵尸放进某一行、墓碑让它钻出来、恐怖花瓶把它放出来 —— 第三种和前两种的区别是"它没有走过那一段路"，所以任何**按走过的距离**计数的东西（今天是小丑僵尸的引信）都要在那一刻重新开始。`ZombieEntity.onReleased` 只做一次遍历，实体本身不认识哪个能力在乎。

**倭瓜的四拍与"压扁"这一档伤害**（`pvzce:squash`，`SquashCapability`）：`idle` → **看一眼**（`look_left`/`look_right`，原版 `anim_lookleft`/`anim_lookright`，按目标在哪一侧选，0.25 秒；**"嗯？"就在这一拍**，是能力自己的 `sound`）→ `grow`（起跳，**引信 75 tick 就是这条 clip 的片长**，短一截就会"蹲下之后跳到一半被打断"）→ 落地（伤害 + 落地声是植物 `sounds.explode` 的第二版"嗯？"）→ `explode`（压扁的落地姿势，held 40 tick 后自毁）。**跳跃的位移是实体自己的**：`advanceLeap` 在 wind-up 的后 65% 里同时插值 `cellX`（到目标那一格、往自己来的一侧偏 0.3 格）与 `height`（`JUMP_HEIGHT = 0.6` 格的抛物线，落地归位）—— 原版那两条 clip 是在原地拉伸/压扁的，照播只会"平移"。伤害类型是 **`pvzce:crush`**：`ignores_armor`（铁桶照样压扁）但**不** `burns` —— 用 `ash` 会让被压死的僵尸变成烧焦的尸体（不掉头、不掉手）。这两条不变量都有测试钉着（`AnimationResourceLoaderTest` 的"引信 ≥ 起跳片长 / linger ≥ 落地片长"）。

**潜水的僵尸只有浮上来才打得到**（`pvzce:submerge`，潜水僵尸）：站在 `#c:water` 格里、且那一格**没有东西可吃**时它待在水下——发布 `swim` clip、`canBeHitByGround()` 为假（与气球在空中的是同一个钩子，所以平射自然打空，子弹那一侧没有特例）、并按 `submerged_speed`（0.7）减速。**一格里有植物它就浮上来啃**，回到普通僵尸的判定——那就是这株植物的全部反制：在它游过来的时候用不需要直线的伤害（倭瓜、樱桃、水草）解决，或者让它游到莲叶上。上岸（不在水里）就是普通走路僵尸，所以把它放进草坪关卡的波次表也不用改数据。"不淹死"仍然是定义上的 `can_swim` 那一句，这个能力只管"值不值得打"。

**射程是这一发子弹的属性**（`ProjectileRef.range`，0 = 不限）：同一个数既是"值不值得开火"的判据（`ProjectileRef.covers`），也是子弹什么时候自己消失的判据（`ProjectileEntity` 从出膛点量起）。小喷菇就是靠它做到"三格之内才打"——如果只写一半，要么它对着够不着的僵尸空放，要么孢子飞过整个草坪。

**描述标记能力**：`MarkerCapability` 的所有行为钩子保持默认空实现；`PlantCapabilities.DEFENSE`（防御）
与 `PlantCapabilities.CARRIER`（承载）共用它的 codec，但各自有稳定注册ID。坚果墙/高坚果声明防御，
睡莲/花盆声明承载，实际抗伤与承载规则仍由生命值及放置定义决定。描述标记可以参与能力配方与能力分组，
不额外加血、改伤害或放宽叠放。

### 5.2.1 伤害类型（`pvzce:damage_type`）

**「一次命中吃不吃护甲」是内容的声明，不是调用点的方法名。** 所有命中都只有**一个入口**：

```
ZombieEntity.damage(amount, DamageTypeDef, level)     ← 所有命中都到这里
        ├─ type.ignoresArmor() == true  → 直接 damageBody
        └─ type.ignoresArmor() == false → 先问僵尸的护甲能力（onImpact：先 front 再 top；
                                          ignoresFrontArmor 的那一类跳过 front 那一步）
```

- **`ignores_front_armor` 是"护甲"这个问题的第二半**：正面那件（纱门、报纸）挡不挡，和头上那件（路障、铁桶、橄榄球面罩）挡不挡，是两件事 —— 原版的大喷菇正是"穿门不穿帽"，而一个布尔只能回答其中之一。声明在伤害类型上，`ArmorCapability` 在两条命中路径上都读它。
- **定义在数据里**：`data/<ns>/damage_types/<名>.json`，字段是 `id`、`ignores_armor`、`ignores_front_armor`（可选）、`burns`（可选）、`dismembers`（可选），与
  `level_theme` 同形的薄条目；静态兜底在 `BuiltInRegistries.registerDamageTypes()`，与其它注册表同规矩。
- **`burns` 是第二个字段**：`pvzce:ash` 声明 `burns: true`，所以被灰烬打死的僵尸播 `death_burned` —— 一套**另一个模型**（原版 `Zombie_charred.reanim`，见 §5.2 末段），不是同一套骨骼上的另一个 clip。字段在伤害类型上而不是在死亡代码里排一张 id 表：mod 自己的火焰伤害要能回答"这一下烧不烧"，而不必改代码。
- **内置的种类以注册表为准**：`data/pvzce/damage_types/` 下的每个条目就是一种（静态兜底在
  `BuiltInRegistries.registerDamageTypes()`），**正文不抄这份名单**——它已经不止六种，点总数只会过期。举例：
  `pvzce:ash`（灰烬类爆炸，无视护甲且 `burns`）、`pvzce:splash`（投手溅射，无视护甲 —— 原版西瓜的范围
  伤害也是打身体）、`pvzce:mower`（小推车，无视护甲，「不是磨掉而是清掉」且自带分尸效果）、
  `pvzce:projectile`（普通子弹）、`pvzce:impact`（保龄球、巨人的拳头、锤子）、
  `pvzce:spray`（大喷菇的喷雾：`ignores_front_armor` —— 穿过纱门与报纸，被帽子吸走，且 `burns: false`）、
  `pvzce:crush`（倭瓜的压扁）、`pvzce:shatter`（碎冰）、`pvzce:drag_under`（缠绕水草）。
- **谁声明**：凡是带 `damage_type` 字段的能力都能声明它 —— 今天有 `pvzce:explosive`、`pvzce:splash`、
  `pvzce:cone`、`pvzce:spike`、`pvzce:squash`、`pvzce:freeze_all`（各能力的 `CODEC` 是唯一出处）；
  定义里带该字段的子弹与工具（`ProjectileDef`、`ToolDef`）同理。子弹的**直击**不需要声明 ——
  它走的那条路本来就叫「子弹」，`onProjectileHit` 的层路由（平射先 front、没盾就落 top；抛射只碰 top）
  说的是「这一发从哪来」，与伤害类型正交。
- **未注册的 id 回退到 `pvzce:projectile`**（护甲照常生效），所以拼错的类型不会变成「无视护甲的外挂」；
  `ZombieEntity.damageType(id)` 是唯一解析处。
- **一个数字只乘一次**：`RULE_PLANT_DAMAGE_MULTIPLIER` 在
  `ZombieEntity.damage` 里乘一次，所以这条规则的含义不取决于走了哪条路。
- **加一种伤害类型** = 放一个 JSON + 在能力里写 `damage_type`；要新的**行为**（吸血、击退）才需要给
  `DamageTypeDef` 加字段。

**火系爆炸还多一件事：融冰**（`ExplosiveCapability.melts_ice`，今天写着的是樱桃炸弹与火爆辣椒）：
爆炸的足迹里凡是 `pvzce:ice` 的格子当场写回草地（`LevelAccess.meltIce` / 辣椒走 `meltIceRow` 的整行）。
它是**显式开关而不是"爆炸都会融"**：土豆雷与玩偶匣也是爆炸，但它们不是火；冰面自己的时钟（`ice_melt`）
住在关卡那边（见 `架构-服务端.md`）。
**弹坑是"植物那一格"，不是"爆炸那一片"**（`ExplosiveCapability.CRATER_RADIUS = 0.5`）：`leaves_crater` 的爆炸（毁灭菇）只在**自己脚下那一格**留下 `pvzce:crater`，与 `radius` 无关 —— 一个 7×7 的爆炸如果连草坪一起挖掉 7×7，玩家为一次清场付出的代价就是半个草坪在恢复期不能种，而原版给的正是"种在哪、就放弃哪一格"这一个选择。

**装备的三种显现（`EquipmentDef`）**：

- **数据在僵尸定义上**：`"equipment": [ {"art":"cone","piece":"pvzce:cone","drop_particle":"pvzce:zombie_traffic_cone"} ]`。`art` 是**动画模型里的骨骼族前缀**（`cone` → `cone_1`/`cone_2`/`cone_3`），`piece` 指向护甲条目（**护甲驱动**：按耐久的三档磨损，耐久归零即消失），没有 `piece` 的条目由**本体血量**驱动（旗帜：`health_below` 之下换成破损那张，死亡时掉落）。
- **第三种图是烘进模型里的**：`tools/reanim_to_pvzce_all.py` 的 `damage_states` 给宿主骨骼复制出 `cone_2`/`cone_3`（**同一套动画键、自己的贴图、每个 clip 里都 `visible: false`**），因为破损的贴图在原版里根本没有被任何 track 引用，转换器看不见它们。三个档位因此不是三个 clip、更不是三份 800KB 的动画文件。
- ** peas 必须先打帽子**：`ArmorCapability.onProjectileHit` 把**平射**弹先路由到 `front`（盾牌/铁门），**没有盾牌就落到 `top` 上**（帽子挡平射，正如它挡抛射），而抛射只碰 `top`（抛物线越过铁门）——这正是两个槽位存在的理由。所以路障僵尸的有效血量是 570、铁桶是 1300，与原版一致；`MiniGameTest` 用保龄球钉的 370/1100 数值窗口不受影响（那条路本来就先 front 后 top）。
- **画哪一张是客户端的事**：`client/renderer/EquipmentArt` 实现 `BoneArt`，每帧拿到模型与解算好的姿势，选出这一帧该画的那一张。两条规则写在里面：**只在这一帧本来就画这个家族时**才替换（报纸僵尸的"喘气"clips 故意不画报纸，不能被贴回去），以及**从最接近的可用档位往回取**（旗帜只有 1 和 3 两张图）。分母是定义里所有护甲条目的耐久之和，分子是 `EntitySpawnS2C.armor`。**这条除法只对"一件护甲"精确**：`armor` 是**总剩余护甲**，今天每个僵尸都只有一件（路障/铁桶/铁门/报纸），所以它就是那一件的比例；一件以上的僵尸两条目会一起按平均值磨损——要做对得让线上带每件各自的剩余值（变长列表），或者把"最前面那件的比例"单独发一位。
- **掉落**：`ArmorCapability` 只在**真的打碎**那一发发这件装备自己的掉落粒子，普通命中用火花；死亡时还戴着的装备一并掉落（`ZombieEntity.dropEquipment`），已经被打碎的不再出现。
- **一件装备可以自带一条手臂**（`EquipmentDef.host` + `arm_bones`）：原版美术是**分层**的，不是父子骨骼——
  同一只手可以有两份精灵、都挂在 root 下、各自带一份自己的动画轨道。旗帜僵尸就是这种情况：拿旗的手在
  `Zombie_flagpole.reanim` 里，而普通僵尸那一整套 `innerarm_*` / `outerarm_*` 照样在画，于是它一边举旗
  一边还垂着两条手臂。`host` 说明"这只手在不在场上"，`arm_bones` 列出该被换掉的普通手臂骨骼，**两者只画一个**。
  范围刻意是"`host` 在画的那几帧"而不是整只僵尸：死亡 clip 把旗子收走、那只手也一起没了，这时必须把普通
  手臂**还回来**，否则僵尸会无臂倒下。`hidden_bones`（在 `ZombieDef` 上）是同一类问题的粗暴版本——无条件不画。
  > **抛掷物粒子的单位**：原版用 `GroundConstraint` 标出的那一族（头、手臂、路障、铁桶、旗帜）是刚体抛掷物，转换器对它们改用原版真正使用的单位（像素/秒、度/秒，`PROP_SPEED_DIVISOR`）：帽子 2.5 格/秒、手臂 0.5 格/秒、自旋约 1 圈/秒。其余 122 条仍按"像素/帧"换算，所以它们的速度比原版小 60 倍、自旋大 60 倍——对一团"冒出来就淡掉"的烟来说看不出来，但**碎片类**（`VaseShatter.xml`、`ZamboniExplosion.xml` 的零件、`BossExplosion.xml` 的碎块、`WallnutEat*.xml`、`CatapultExplosion.xml`，都在 `refer/im7/particles/` 下）本该四散飞开，现在是原地淡出。它们和抛掷物在结构上是同一族（有 `Acceleration`、没有 `Friction`，共 33 条），把 `to_definition` 里的判据从 `thrown` 放宽到"没有 Friction 的弹道发射器"即可一次修好；没有一起改是因为那会同时改变每一处爆炸与溅射的手感，需要单独过一遍截图。
    - **自旋那一半大概率也读错了单位**：`ParticleSpinSpeed` 在抛掷物那一族按"度/秒"读（`[-720 720]` 只有这样才是一颗会翻滚的头），但其余 122 条被乘了 60（`spin_factor = FPS`），于是毁灭菇的菌盖片转成 **15000 度/秒**——每帧 0.7 圈，画出来是噪声而不是翻滚。蘑菇云是在定义里**手写**了合理自旋（±220 度/秒）绕开它；要把这条顺带修掉，就得和上面那族单位一起改、一起过一遍截图。
    - **转换器的"两个数字"还会读成错误尺寸**：`ParticleScale .5,60 0` 里的范围+曲线写法被 `range_of()` 取成 `(0, 60)`，落进 `scale` 就是 **0**——`pvzce:powie`（原版那团橙色爆炸云）从转换出来那天起就没画出来过，因为它被渲染器当成"尺寸 0"跳过。按手写定义修好了它，但 `tools/` 里那条读法还在，其它 `value,time value` 形状的发射器仍是同样的坑。
  > **`ParticleMotion.gravity` 的符号**：字段语义是"**向下**的加速度大小"（引擎里是 `vy -= gravity * dt`），所以写入的必须是正数——写成负数会让**每一件抛掷物都往天上飞**（"僵尸头颅直接飞上天"）。符号与字段语义一致后，抛掷物飞出去会落回**它自己那一行**的草地：手臂 0.19 格、路障 0.64 格、旗帜 0.97 格、被碾的头 11.2 格（原版就是把它甩出画面）。
  > **落地线是相对出生点的**：`bounce` 的地面在**出生点下方 0.42 格**，不是世界坐标的某个固定值——后者只有第 0 行是对的，第 1 行以上扔出去的东西会一路掉出草坪下沿。
- **头颅是抛出来的粒子**：模型在死亡 clip 里把 `head`/`jaw`/`tongue`/`hair` 全部设为不可见（原版就是这么画的），
  所以头由 `pvzce:zombie_head` 粒子抛出，`ZombieDef.drops_head` 决定哪几种僵尸抛（巨人/Boss 整个倒下、
  气球僵尸的头随气球走，都是 false）。这个粒子是"**小弧线弹出、落地即停**"：速度 2.3、角度 125°、摩擦 0.25，靠 `ParticleMotion.ground_friction` 实现（落地时 `vx *= friction`，缺省 **1** = 保留"一直滑"的行为，另外 139 个粒子定义的手感不变）。**原地掉落、原地淡出**。
- **烧死是另一套模型，不是另一个 clip**：`DamageTypeDef.burns`（`pvzce:ash` 为真）的致命一击把状态设成 `EntityAnimations.DEATH_BURNED`，而这一支走的是 **`Zombie_charred.reanim` 的焦尸**（`animations/zombie/charred/zombie_charred.json`，clip 名就叫 `death_burned`）。僵尸 JSON 用**已有的**逐状态覆写字段把它接上：`"animations": {"death_burned": "pvzce:zombie/charred/zombie_charred"}` —— 没有新包、没有 `PROTOCOL_VERSION` 变化，因为 `animation_dir` 本来就是客户端从本地数据包读的。焦尸与活僵尸**没有共用骨骼**（一堆灰 + 一个头骨），所以它不是"同一模型换贴图"，这也是为什么它必须是另一份模型文件。
- **死亡动画与尸体**：僵尸死亡时会 `setAnimation(DEATH)` 并在世界上**留 6 秒**（`ZombieEntity.CORPSE_TICKS`）——死亡 clip 是 3.25 秒（巨人 4.9 秒）且 `on_end: hold`。尸体期间它不走路、不啃、不被打、不计入 `aliveZombieCount`（`ZombieEntity.isAlive()`），所有"这一行有哪些僵尸"的扫描（`LevelServer.zombiesInRow`、割草机、植物 AI）都问 `isAlive()` 而不是 `isRemoved()`。**最后一杀的那次同步是强制的**（`LevelServer.entitySyncPending`）：实体状态每 3 tick 发一次，而死亡之后同一 tick 里 `checkEnd` 就可能结束关卡、此后再不 tick，包必须在这一 tick 送出去——否则玩家会看到一个活生生的僵尸站在已经结束的棋盘上。尸体不进存档迁移（`corpseTicks` 进 `saveState`，读档回来仍是尸体）。
  > **`on_end: hold` 的一次性 clip 不会被"重播"**：只要请求的状态还是**当前活动 clip**、且它是 `HOLD` 收尾，`AnimationManager.isAlreadyPlaying` 就认为"这个状态正在播"——服务端每隔几 tick 重发实体状态，不会让死亡动画在尸体存在的 6 秒里从头播 2~3 遍（尸体刚倒下又站起来）。只有交给别的 clip（`on_end: idle` / `next`）之后再请求才会重新开始；`shoot`、`explode` 这类需要反复触发的动作因此照旧。
  > **`on_end: <clip>` 的交接是同一个状态的续集**：`AnimationPlayback.chained` 记着"屏幕上这条 clip 是请求的状态自己交出来的"，重发那个状态不会把它推回去重播——胆小菇的缩头（`hide`）靠它接上流泪的 `hide_loop`，否则 `hide` 一播完就被重开、哭泣永远上不了屏。`on_end: idle` 的交接**不是**链条（那是"动作结束、回到待机"），所以 `shoot` / `explode` 仍然可以反复触发。
- **半血掉手臂**：`drops_arm`（默认 true）的僵尸，血量降到一半时 `ZombieEntity.damageBody` 发 `zombie_arm` 粒子 + 断肢音，客户端按**同步过来的血量**永久隐藏 `outerarm_*` 五个骨骼——这条判据是"血量的跨越"，不是存下来的标志位，所以读一份 40% 血的存档不会再多掉一条手臂。**这个开关是"模型画得出来吗"**：客户端隐藏的是那五个固定名字的骨骼，所以巨人/Boss/小鬼以及手臂骨骼另有命名的报纸、气球、撑杆僵尸都显式写了 `drops_arm: false`——否则粒子飞出去而手臂还在（或留下一只悬空的手）。**判据还有一条"头上得先空出来"**：半血 + `armor <= 0` 才掉手臂，所以路障/铁桶僵尸是"路障先掉、再掉到它自己血量的一半（200 的一半）"才断臂——两半判据都从同步状态读得出来（血量与 `armor`），服务端发粒子的条件与客户端隐藏骨骼的条件是同一句话。
- **没有胡子**：`ZOMBIE_*_EXCLUDE` 里的 `MUSTACHE` 排除了原版只在"胡子彩蛋"里画的那条 `Zombie_mustache` track，五个共享 `Zombie.reanim` 的僵尸模型都不长胡子。
- **量身高时脱帽**：`EntityConfig.measure_exclude_regex` 把路障/铁桶/铁门/报纸的装备骨骼排除在**量尺寸的那个包围盒**之外（骨骼照旧导出、照旧绘制）。包围盒是 `target_box` 要适配的东西，所以不排除装备骨骼就会**连帽子一起**压到 0.95 格：身体比普通僵尸小 15%（模型 0.565 宽 vs 0.625），看起来"小一圈"。这四种僵尸的身体盒与普通僵尸逐字段一致（83.9×127.5px，`body` 骨骼的平移完全相同），帽子照常戳在头顶之上。脚底不动（帽子不会伸到脚下面），所以除了水平原点会随帽子偏心挪几个像素之外没有副作用。

**受击不改姿势**（`ZombieEntity.walkOrEat`）：僵尸没有受击动画，挨打时的反馈是命中粒子和音效，腿继续走。**实体状态变化会立刻发布**：`Entity.setAnimation` 会置一个脏标记，`LevelServer.syncSlots` 见到就当场同步，不再等 `tickCount % 3`——否则只活一个 tick 的状态（射手的 `shoot` 前那一 tick 的 `idle`）三次里会漏掉两次。

### 5.2.2 阵营与魅惑（`pvzce:charm`）

**"谁是敌人"只有一个答案：不是同一支队伍。** `LevelServer.isEnemyOf(other, self)`（两个队伍**都在**时才过滤，任一侧缺失＝这一击不是阵营对阵营的行为，照旧落下），而所有攻击都问它：

| 问法 | 谁在问 |
|---|---|
| `LevelAccess.enemiesInRow(row, team)` | 射手的索敌、投手、近战、地雷的触发、保龄球的连撞、子弹的命中测试 |
| `damageArea` / `damageRow` 的 `sourceTeam` | 灰烬爆炸、溅射、Boss 的砸地、火爆辣椒 |
| `leaveCraters(centerX, centerY, radius, square)` | 声明了 `leaves_crater` 的爆炸（目前只有毁灭菇）：把爆炸覆盖到的**裸地**格变成 `pvzce:crater`，footprint 与 `damageArea` 同一套算法（范围是格子而不是距离，见 `LevelServer.isBareGround`） |
| 锤子 | `enemiesInRow(y, plantPlayer.team())` |

`zombiesInRow(row)`（**不过滤**）留给"这一行有几只僵尸"这类问题：渲染、`aliveZombieCount`、关卡的胜负判定。

**魅惑菇（`pvzce:charm`）只做一件事：把吃它的那只僵尸移到植物方的 `Team`**（`PvzceEntity.setTeam`，因此实体 id、位置、护甲、正在飞的子弹指向全都保持不变 —— 删掉再生成一个新实体做不到这一点）。其余全部是上面那条规则的自然结果：

- 玩家的射手/爆炸/锤子**不再打它**（它已经是我方）；
- 它自己**不再吃植物**、而是**掉头往回走**、咬它撞上的**敌方僵尸**（`ZombieEntity.walkOrEat` 里唯一的 `isCharmed()` 分支 —— 必须在这里，因为"朝房子走并吃植物"就是僵尸的定义）。方向只有一处：`ZombieEntity.walkDirection()`（`-1` = 朝房子，`+1` = 被魅惑后往回），移动、索敌（`enemyZombieInFront` 按同一个方向乘 delta）与客户端的镜像都读它；
- 于是它从**右边**离场（走到棋盘右缘即移除），而不是走到房子前站着——"回自己那边的房子去了"；
- 走到最左边**不会判负**（`checkReachedEdge` 只对仍朝房子走的那一类上报），也不会让关卡**卡在无法结束**（胜负判定数的是 `hostileZombieCount()`，不是 `aliveZombieCount()`）；
- 客户端按 `EntityUpdateS2C.charmed` 给它上一层紫色（`EntityVisuals.CHARMED_TINT_R/G/B` 三个分量）**并把整只立绘水平镜像**（`AnimationPlayback.flipX`，控制器与帧序列两个后端都实现）—— 不然它会背朝自己前进的方向走。队伍 id 随同一个包下发 —— 只有僵尸会为真，所以它是那个包上的两个布尔之一，而不是一张状态表。

**它刻意不做的事**：不还回僵尸（被打死时它是我方实体，所以不掉币 —— 这就是魅惑的代价，与原版一致）、不清护甲（原版的铁桶魅惑后照样戴桶）、不清减速。**一次一只**：`CharmCapability` 自己有一段休息时间（`cooldown_ticks`，缺省 660 ≈ 11 秒），休息期间再被咬也不会二次生效，也不会被消耗。

**被消耗的植物可以有退场动画**：`PlantCapability.vanishAnimation()`（clip 名 + 持续 tick）让"这张卡被用掉了"有一拍可以演。今天只有咖啡豆用它（原版 `Coffeebean.reanim` 的 `anim_crumble`，1.25 秒 → 75 tick）：种下去叫醒下面的植物（或什么都没叫醒）之后**立刻退出玩法**（`isRemoved()` 为真、`occupiesCell()` 为假、同一格马上可以再种），但身体还留在场上把 clip 播完 —— 这是"**玩法已经结束，只是动画还没追上**"的唯一表达，而不是给植物加第二条命。没有声明 clip 的植物仍然一帧消失。tick 数是**写在数据里的**而不是从动画文件读的：服务端不读动画资源（那是客户端的层，不依赖它才让关卡能在没有渲染器时仿真），数字对不上时以仿真为准。

**"按不按时钟打"与"被点名时打一次"是能力自己的两个答案**（`PlantCapability.holdsFire()` / `strike()`）：前者说"我整个存在的意义就是攻击，所以一个让草坪停火的关卡可以把我停掉"——射手、投手、近战、锥形喷吐、地刺与回声接力回答 true，生产者 / 成长 / 引信一类照常走自己的时钟（**引信不是时钟**：樱桃炸弹是玩家付过钱的一次性动作）；后者是"现在打一次，别管你自己的冷却"，由节奏关卡的音符调用（`PlantEntity.queueStrikes(n)`，每 4 tick 一次，避免一轮多发叠在同一格）。两个钩子必须成对实现：回答了 `holdsFire` 却不实现 `strike` 的植物，在一个停火的关卡里会整关什么都不做。**停火停的是「新攻击」，不是「已经许诺出去的活」**：连发的后几发（双发第 2 发、机枪后 3 发）与大嘴花的咀嚼都发生在**后续 tick** 上，所以还有一对钩子 `hasPendingWork(plant)` / `tickPending(plant, level)`——停火时 `PlantEntity` 用后者替代 `tick`，只推进那笔欠账（`tickPending` 里不许做新决定、不许查冷却、不许找目标）。少了这一对，双发在这一关和单发一模一样（3 轮完美 60 伤害 vs 应有的 120），大嘴花咬一口就永远卡在嚼的状态（见 `踩坑清单` 146）。已经实现的攻击能力里，射手与回声接力被点名时**不找目标也开火**（那一发就是玩家按下去的回执），投手与近战没有目标时什么都不做（抛出去的与咬下去的总得有个落点）。

`bowl` 是唯一会让植物**离开自己格子**的能力（保龄球坚果，见 `架构-服务端.md` §4.9）：它顺带定义了 `PlantCapability.occupiesCell`（默认 true），`plantAt` 会跳过回答 false 的植物，所以"僵尸不啃滚动的坚果"不是啃咬循环里的特例。僵尸侧的对称物是 `ZombieCapability.onImpact(zombie, damage, level)`：给"不是子弹的撞击"（保龄球、巨人的拳头）留的护甲拦截口，与 `onProjectileHit` 分开是因为没有子弹可以描述这次命中（没有层、没有命中音效），而"护甲先吃"这条规则仍然适用——并且**先查 front 再查 top**，因为帽子（路障/铁桶）在 `onProjectileHit` 的层路由下只挡抛物线。

`behavior` 字段仍在，但**降级为可选预设**（`PlantBehaviorPresets` / `ZombieBehaviorPresets` / `ProjectileBehaviorPresets`）：显式 `capabilities` 优先，为空时才按 `behavior` 展开；预设是纯语法糖。

### 5.3.1 屋顶与空中拦截

`SceneElementDef.profileFor` 提供原生屋顶曲线，由 `SceneBoard` 统一采样（§5.1.1）；默认数字在 `PvzceConstants`。
`roof_flat` / `roof_slope` 属于 ground，属于不可直接种植的屋顶，花盆使上层植物获得 plantable 支撑。
`PlantPlacement` 的 requires_ground 植物在屋顶也要花盆；豌豆等平射在碰到高于自身的屋顶时消失。
卷心菜 / 玉米 / 西瓜 / 冰西瓜由 `ThrowerCapability` 搜索可被抛射命中的活目标并解抛射（气球沿用既有抛射命中规则）。

`GarlicCapability` 的被咬钩子把步行僵尸转入相邻行。
`UmbrellaLeafCapability.block` 搜索周围九格所有叠层，发布张开动作；篮球与蹦极共用此拦截入口。
`LadderCapability` 把携带的磁性护甲转成 `PlantEntity.laddered`；普通步行通过，磁力菇与火系爆炸清除。
`CatapultCapability` 停车后发敌方弧线篮球，目标是本行左侧第一株植物；没有目标或弹药耗尽时继续行驶。
`BungeeCapability` 在下降 / 上升阶段位于空中、停底时可被攻击；可保存待投送的内容 id 与血量倍率。
`ProjectileEntity` 保存队伍、点目标与目标高度，恢复的篮球继续攻击植物。

### 5.4 为什么 `LevelAccess` 在 `api/entity`

能力是**服务端行为**，必须能放子弹、算范围伤害、读同排僵尸、播音效。把这些操作收敛成一个只读+动作的小接口（`LevelAccess`），比让能力直接依赖 `LevelServer` 更可控；实现只有 `LevelServer` 一个。接口里的实体参数是服务端类型（`PlantEntity` 等），这是 L2→L2 的引用，不是 api→server 的方向污染。

### 5.5 放置与叠放（标签驱动）

能不能种、能不能叠，**没有任何硬编码 id 参与**，只有两张表：标签 + `PlacementDef`。

```
@c:ground / @c:plantable / @c:water / @c:unplantable / @c:grave  （scene_element 注册表）
@c:plantable / @c:carrier / @c:requires_ground /
@c:water_plant / @c:plant_only / @c:grave_only          （plant 注册表）
```

**判定**：`PlantPlacement.canPlace(plant, ctx, x, y)` 是纯函数，只读上面这些标签与 `PlacementDef`：

| 植物带 | 需要 |
|---|---|
| `#c:plant_only` | 任意植物在它**下面**（咖啡豆） |
| `#c:water_plant` | 地形 `#c:water` 或满水承载物（莲叶、缠绕水草） |
| `#c:grave_only` | 地形 `#c:grave`（墓碑破坏者）—— 排在 `#c:requires_ground` 之前，因为墓碑同时是 `#c:unplantable` |
| `#pvzce:rises_from_ground` | 不是放置规则，而是**表现**规则：这一格中途被种下时要从土里钻出来（见 `架构-客户端.md` §6.3）。内置陆地墓碑和水中墓碑都打了这个标签 |
| `#c:requires_ground` | 地形 `#c:ground` 或 `#c:plantable`（花盆、土豆雷） |
| `#c:carrier` | 地形 `#c:ground` 或 `#c:water`（载体自己先落地） |
| 其余 | 地形，或**下面**某个植物，带 `#c:plantable` |

普通叠放的两个关键点，都是"顺序无关"的来源：

1. **只看比自己层低的东西**（`layerIndex(other) < layerIndex(self)`）。豌豆和土豆雷都在 layer 1，谁也够不着谁，所以"雷种不进花盆""豌豆不会长在雷上"与**种植顺序无关**。
2. **互斥由 `group` 说，不由层号说**。`group` 留空＝同格可多个（咖啡豆）；普通植物默认 `plantable`（一格一个）；载体默认 `carrier`（盆上不能套盆）。

注水状态归 `PlantEntity.waterFilled`，随 NBT 保存，搬移沿用实体状态。
`PlantLayer.waterFilled` 把它带入纯放置判定：满水承载物不再提供 `#c:plantable`，
且屏蔽当前格的陆生地形支撑；陆生植物需要上层荷叶。水生植物可直接种在满水盆。
一张水生载体可叠在单独的满水载体上，这是 carrier 互斥的例外；已有上层植物时仍拒绝。
盆和荷叶的实体排序及承载高度依旧由既有放置高度入口累计，荷叶升级香蒲只消费荷叶。
铲除上层不清水，移除盆清水；天气不改变它，僵尸不会因此把屋顶当泳池。
`idle_water` 通过既有实体状态同步让花盆绘制水生轨道，无需新包。

`LevelServer` 只提供 `PlantPlacement.Ctx`（该格的 `Terrain` + 自下而上的 `PlantLayer` 列表），`canPlacePlant` 一行转发；`PlantAIPlayer` 也走同一条。`SceneElementDef` **不存**能种什么；新增地形 = 加一个元素定义 + 在 `data/c/tags/scene_element/` 里打标签。

> **僵尸那一侧的水是定义上的一个布尔**：`ZombieDef.can_swim`（`ZombieEntity.drownInWater` 对落地僵尸生效，水里淹死的那一下发水花、涟漪与 `death_water`），它不是标签也不是能力 —— "会不会淹死"是这具身体的性质，`#c:water` 只需要地形打标签。泳池的僵尸（三款救生圈、潜水、海豚骑士）都写 `can_swim: true`，其中潜水僵尸带 `pvzce:submerge`，海豚骑士复用现成的 `pvzce:vault`（跳过第一株植物），三款救生圈各带一条 `pvzce:float`（只决定泳姿 clip，见 `data/pvzce/zombies/ducky_tube_zombie.json`）；"会不会淹死"始终由 `can_swim` 回答，与能力列表无关。
>
> **救生圈不是新美术**：`Zombie_duckytube` 是 `Zombie.reanim` 里本来就有的轨道，五款陆地变体（普通/路障/铁桶/旗帜/铁门）按图片名把它排除（`ZOMBIE_*_EXCLUDE`），三款救生圈僵尸用的 `DUCKY_*_EXCLUDE` 保留它 —— 与路障/铁桶/旗帜同一套"配件筛选"做法，救生圈因此是模型自己的一根骨头，不需要运行时贴上去。

`#c:unplantable` 在其它地形允许条件前拒绝种植，仅 `#c:grave_only` 保留墓碑专用例外。
`water_grave` 同时属于水、墓碑和不可种植标签，睡莲及水生植物不能占用它，墓碑吞噬者可以。
吞墓只清覆盖物；基础水面保留，水中吞墓结束发水花与种水音效。固定出怪点空缺期间的保留规则由关卡机制附加。

`PlacementDef.width` 是横向占格宽度，缺省为一，与垂直 `count` 分开。
`PlantPlacement.originX` / `coversCell` / `upgradeAnchorX` 统一实体原点、覆盖和升级锚点。
多格实体中心位于整个覆盖区域的中心；每个覆盖格均接受地形、互斥与关卡机制检查。
玉米加农炮占相邻两格，从任一基座操作都消费同一对玉米投手，格子查询返回同一实体。
存档记录 `footprintWidth`，旧单格保存的炮在恢复时补偿中心，左侧原点保持不变。

### 5.6 每帧/每 tick 的执行顺序

服务端 `LevelServer.tick`：音乐线索 → 波次（`WaveDirector.tick`）→ 波次与时间同步 → 阳光掉落 → 场景（弹坑恢复/墓碑）→ `flushPending` → 植物（能力 tick）→ AI（可选）→ 僵尸（能力 tick + 移动 + 啃咬 + 死亡掉币）→ 子弹 → 资源掉落 → 移除回收 → 卡槽同步（每 20 tick 或冷却归零）→ 实体增量（每 3 tick）→ 胜负判定。

> 波次那一步是 `WaveDirector.tick()`：它自己记倒计时、放怪队列、开门闸门与预警横幅，
> 通过 `WaveDirector.Host`（由 `LevelServer` 实现）要"这一行有几只僵尸/放一只僵尸/中间响一声"
> 这类它没有的东西。存档里的 `NextWaveIndex` / `PendingWaveSpawns` 等键仍写在 `level.dat` 上，
> 由 `WaveDirector.save/restore` 负责那一块。

客户端 `PvzceClient.run` 每帧：`window.pollEvents` → `connection.tick()` → `pollInput` → `screen.initIfNeeded/tick` → `music.tick` → `animations.tick` → `render`（`clipping.reset()` 在帧末兜底）。

### 5.7 天气对植物能力的组合

`LevelAccess` 的天气钩子默认返回 1；服务端从 `WeatherState` 取得统一策略。
`WeatherMechanic.mushroom` 按夜行能力识别蘑菇，吸金磁另按自身能力归入；向日葵与双子向日葵
使用产速系数。灰烬分类使用 `ExplosiveCapability` 的伤害类型和玉米加农炮能力。

普通攻击与生产由 `PlantEntity.actionRate` 消费天气速度。爆炸、全场冻结和两种磁铁的
专用 `RateClock` 只增加天气计时倍率，进度进存档；不会因此额外启用护理或回声加速。
`PlantShots` 的弹丸射程、`ConeAttackCapability` 的光锥与气体粒子、`SpikeCapability` 的范围、
磁铁搜索和毁灭菇半径都由同一射程钩子调整。忧郁菇雨天覆盖相邻两行，即五行。
`TorchwoodCapability` 在雨天停止点燃，阴天缩放点燃后的总伤害；毁灭菇的蘑菇与灰烬规则分别组合。

花盆上的射手发射高度包含承载高度；`ProjectileEntity` 按目标脚底到
`PvzceConstants.COMBAT_BODY_HEIGHT` 的身体区间判定，并检查地形遮挡；承载射手与上下层命中均有真实回归。

雨天寒冰时长 ×1.5、冰系溅射范围 ×1.25，伤害/减速强度不变；晴、阴保持基础寒冰值。
`StatusDurations.cold` 在施加时组合既有时长规则与天气，黄油走普通 `scale`；
`coldFreeze` 保持寒冰菇全场冻结独立于减速规则的边界。续档直接还原剩余状态时长。
`StatusOnHitCapability` 以 SLOW 识别寒冰；与溅射能力组合时，冰瓜的范围伤害和状态均使用
`LevelAccess.enemiesInArea`（轴向距离、方块范围再加半格、仅存活敌军），失去原目标时以落点为中心。
普通西瓜不会扩大范围，冰瓜不会重复结算直接伤害。寒冰菇另组合蘑菇行动速度。

### 5.12 动作释放、控制状态与溅射落点

普通射击和地刺类攻击通过 `PlantEntity.beginAction` 保留姿态并推进动作序号；
`SpikeCapability.particle` 可在真实攻击时发射孢子。客户端自行结束一次性动作，服务端不根据渲染进度结算。
玉米投手主弹伤害为 20，`butter_damage` 为 40，默认值分别由 `PvzceConstants.KERNEL_DAMAGE` /
`BUTTER_DAMAGE` 提供；变体伤害独立于主弹。投手先选玉米或黄油，再安排释放；投手手部偏移只在 `PlantShots` 定义，释放与飞行界限只在
`PvzceConstants` 定义。`ArcMotionCapability` 按完整起始高度和目标高度求解，并按离散积分校正初速。
发射路径不修改目标实体；未出手的短暂投射队列与射手连发尾声一样暂不进存档。

`ZombieStatus.IMMOBILIZED` 表示冰冻，`BUTTERED` 表示黄油；`ZombieEntity.isImmobilized`
合并二者的运动抑制，网络镜像分别提供两项视觉事实。
`SplashImpactCapability` 把范围内每只敌军送进同一护甲路由，但两者的伤害不同：被命中的那只吃投射物的满伤，其余吃 `splash_damage`（melon / winter_melon 写 40，原版数值；不写＝投射物伤害的一半）。把满伤发给半径内每一只是「西瓜一个人清一路」的来源，见 `docs/03-第三阶段-精修完善.md` 里那条「疑似过强」的记账。
`ZombieCapability.onProjectileHit` 的额外布尔参数可关闭每个目标的命中效果，
落点统一选择弹丸自己的 `impact_particle`；护甲破碎掉落仍发生。
爆炸类内容仍可显式指定灰烬伤害类型。
