## 4. 服务端

### 4.1 线程与主循环

`PvzceGame.main` 装配：`BuiltInRegistries.bootstrap()` → 调用 `main`/`client` 入口点 → `Connection.createMemoryPair()` → 起服务器线程 → 客户端主循环。

`PvzceServer.run()` 顺序（**顺序有意义**）：
1. `PvzcePackets.register()`、`BuiltInRegistries.bootstrap()`
2. 建目录、`resourceManager.init(gameDir)`
3. **`invokeServerEntrypoints()`** —— 必须在数据加载之前，否则内容注册表已冻结，mod 注册内容会抛异常
4. `reloadData(false)` —— 冻结内容注册表
5. 循环：处理命令/stdin/网络 → `tickRate.advance()` → `level.tick(bridge)` → 每 250ms 发 `DebugInfoS2C`

`PvzceTickRateManager` 负责 60tps 基准、`/tick rate|freeze|step|sprint`。

### 4.2 `LevelServer`

权威关卡。要点：

- 实现 `LevelAccess`（`api/entity/LevelAccess`）—— 能力、AI、命令通过它访问关卡，而不是直接摸内部字段。
- **所有实体入场只经过 `spawn*`**：`spawnPlant` / `spawnZombie` / `spawnProjectile` / `spawnArcProjectile` / `spawnResource`。`addEntity` 会设置关卡尺寸（网格派生用关卡真实尺寸，**不是**默认 9×5）。
- `spawnPlant` 是**唯一的植物创建路径**（玩家、AI、命令、关卡初始实体、存档恢复全部走它），负责叠放高度、花盆偏移、`onPlaced`、`onRemoved`。
- `bridge` 是环境字段：`tick()` 与玩家动作 API 用 `withBridge`（try/finally）设置，因此任何提前 return 都不会泄漏。
- 场景是 `SceneBoard`（空间契约见 `架构-实体与能力.md` §5.1.1），坐标解析统一走 `SceneCells.parse`；额外地表、初始实体归属由 `LevelValidator` 校验。
- **弹坑有两条命**：`LevelServer.leaveCraters` 把爆炸覆盖到的裸地变成 `pvzce:crater`（`ExplosiveCapability.leaves_crater`，毁灭菇开着；**覆盖范围是植物自己那一格** —— `CRATER_RADIUS = 0.5`，与爆炸半径无关），`tickScene` 每 tick 给每个 `CRATER` 面计一个数：到 `crater_recovery - CRATER_FADE_TICKS` 时换成 `pvzce:crater_fading`（原版那张"正在填回去"的图），到 `crater_recovery` 时解除覆盖、恢复基础地表。**这是地形而不是客户端的特效**：能种什么由地形决定，所以"正在回填的弹坑"也是一格不能种的地（`#c:unplantable` 里两个都列着），客户端只负责画它被告知的那一格。**同一张 `tickScene` 里还有冰面的时钟**：`pvzce:ice`（冰车压出来的那一格）按 `ice_melt`（默认 30 秒，0 = 不化）逐格计时，到点解除覆盖并 `sendSceneCell`；火爆辣椒与樱桃炸弹的 `melts_ice` 则让它们在爆炸当帧就走同一条路（`LevelAccess.meltIce` / `meltIceRow`，辣椒是整行）。冰只铺在允许的裸地/屋顶上，不覆盖墓碑或花瓶；时钟按 `(surface, x, y)` 分开计数。
- 日夜：`PvzceClock` + `common/level/DayNightCycle`（纯函数，客户端共用）。**不要在别处重算周期数学**。
- `LevelValidator` 在构造末尾收集关卡数据的全部问题（未知规则/非法取值/未知卡槽/畸形场景/未知初始实体/波次条目）并一次性打印，**不中断构造**。波次那一条是 `validateWaves`：条目点名了这块棋盘没有的行、或 `count <= 0`（写了等于没写）。**同一份清单在 `BuiltInLevelsValidateTest` 里也跑一遍**，所以给 `LevelServer.reportLevelProblems` 添一项而忘了添给测试是不可能发生的（这一对曾经差一项 `validateBuffs`）。
- 波次：`WaveDirector` 一处管住全部节奏 —— 构造时 `normalizeWaves`（末波必为 FINAL），之后 `WaveDirector.tick` 推进，`PendingWaveSpawn` 队列按 `WaveDef.SPAWN_INTERVAL_TICKS` 逐个放怪。
- **音乐是"当前曲目"而不是"发过的事件"**：`processMusicCues` 每发一条 `MusicEventS2C` 都把 `currentMusicCue` 更新成它（`stop` 或无事件的 cue 清空），`restore` 按存档里的 `NextMusicCueIndex` 把 cue 表重放到该位置，`sendFullState` 在 init 之后把当前曲目重发一次。**这是续档能接着放对的曲子、以及第二个玩家加入时不静音的唯一原因**：cue 是事件，客户端来晚了就永远听不到那条 tick 0 的 cue（重发同曲在客户端是幂等的）。
- **小游戏关卡由 `mechanics` 列表描述**（见 §4.9）：`conveyor`（传送带）把卡槽变成带子，`placement_zone`（可种植区）由 `canPlacePlant` 统一判定，`mower`（小推车）决定哪些行有推车，`tool`（关卡自带的工具，可声明成"点击即用"）决定空手点击做什么，`grave_spawner`（会补的墓碑）让僵尸从墓碑里持续冒出来，`grave_field`（开局墓碑）在关卡建好时把墓碑随机撒在远离房子的半场，`fog`（迷雾，世界 4）只影响客户端画什么，`storm`（雷雨，4-10）同样只影响画什么但它**随时间变**（服务端每 tick 发布一次 `(打击编号, 曝光)`，曝光由服务端的形状表算出，客户端据此画黑暗与闪电、并按同一个数决定藏不藏实体），`vase_field`（开局花瓶，4-4）把装着卡的花瓶按写死的坐标摆好。**没有声明 card source 的关卡隐式得到 `deck`、没有声明 `mower` 的关卡隐式得到"每行一辆"**，两个默认都在 `LevelMechanics.effective` 里决定。
- **`plantAt` 会跳过不占格的植物**：`PlantEntity.occupiesCell()` 为假（只有 `pvzce:bowl` 会这样回答）时，僵尸不啃、手套不搬、铲子不铲。这是"植物正在离开这一格"唯一的表达方式，而不是给僵尸的啃咬循环加特例。

### 4.2.1 按通路执行与续档

`spawnPlant`、`spawnZombie`、工具、持卡和手动瞄准提供显式 surface 入口，服务端重新验证支撑格和放置规则。
叠放、啃咬、护理、冰面与行攻击查询携带来源通路；实体派生的弹丸、资源、召唤物与特效继承来源。
旧动作入口适配默认地表；空间爆炸的旧入口先采样默认地表，再转入统一空间判定。
`emitEffect` 的空间入口直接发送 `WorldPosition`，旧 x/y 入口表示默认地表上的平面位置。

场景存档保存 base、覆盖元素、surface、显示名、profile 与 thickness；实体保存 surface 和绝对高度。
全量进场与增量场景更新均从 `SceneBoard` 发包。缺少 surface 的旧实体按默认通路恢复，
旧泳池高度与弹丸目标高度按差值迁移；旧种子雨的平面位移转为独立高度，迁移不改写调用方 NBT。
资源的上浮、下落与落地在各自通路采样实际支撑高度；种子雨保持平面落点，使用 height 表达下落。
既有冰面/弹坑剩余时钟尚不进存档，见 `todo.md`。

### 4.3 进入/重开关卡的协议语义

两个包都能"进入关卡"，语义不同，**不要混用**：

**阵营由关卡声明，不由客户端猜**：`LevelDef.playable_teams`（写在 `win_team` 旁边，缺省＝`teams` 全部可玩）说明这一关有哪几方是人能玩的，服务端按它算出每一条 `LevelListS2C.TeamInfo.playable` 下发。**只有一个可玩队伍时 `LevelSetupScreen` 整个被跳过**（判据 `PvzceClient.offersTeamChoice`，判定点只有 `enterLevelFromMenu` 一处，关卡列表、冒烟钩子与编辑器「测试」都经过它），于是内置关卡从列表点进去就是选卡页/开局，不再先问一次"要当植物还是僵尸"。一个可玩队伍都没有（数据写错）时仍然显示这一屏：看得见的菜单比"以空阵营开局"好。

| 包 | 谁发 | 语义 |
|---|---|---|
| `RequestLevelC2S(restart)` | 关卡列表的「下一步/继续游戏」与 `LevelSetupScreen` 的「开始游戏」 | "进入这个关卡"。已经在跑同一关卡且 `restart=false` → **原样 resync 当前实例**（相当于继续）；`restart=true` → 重开 |
| `StartLevelC2S(restart, seeds)` | 选卡界面的「开始游戏」 | **"用这套卡组开一局"**。选卡只发生在一局开始之前，所以目标关卡若已经在跑且 `restart=false`，服务端会**重开并应用这套卡组**，而不是 resync |

**进入决策只有一处**：`PvzceClient.enterLevelFromMenu(info)`，判据是列表给的 `LevelInfo.hasRunningSave()`（读的是**独立的 `runningSave` 字段**，不是 `status` 字符串 —— 见下方「通关优先于进行中」）：

- **有存档** → 直接发 `RequestLevelC2S(restart=false)`：服务端 `createLevel` 先把整个存档（棋盘/实体/波次/钱包/卡槽）加载并下发，**然后**才发 `LevelSavePromptS2C`，客户端在已加载的关卡之上弹出「发现存档」。**不经过关卡准备，也不经过选卡** —— 存档里已经有卡组和阵营，为一局即将被继续的游戏挑卡是没有意义的。
- **无存档**（含"已通关"）→ 关卡准备（`LevelSetupScreen`，选阵营）→ 选卡界面 → `StartLevelC2S(restart=false, seeds)`。

列表里的「进行中」是**某个世界**的 `saves/<world>/levels/<LevelKey>/level.dat` 存在与否，所以：

> **通关优先于"进行中"**：通关标记是"这一关已经通关"，**一旦写下就不会被收回** —— 重玩一局已通关的关卡、那局打输了、或者中途退出，这一关仍然是已通关。判定用的是 `isLevelCompleted`（只看标记文件），它同时是解锁规则里 `clearedLevels` 的来源，所以"有一局重玩等着继续"不会把后面的关卡重新锁上。
>
> **"有没有存档"是另一件事，走另一个字段**：`LevelInfo.runningSave`。`status` 只负责列表行上显示什么（有存档就显示"进行中"，否则显示"已通关"），`LevelInfo.hasRunningSave()` 读的是 `runningSave`；进入判定先看 `runningSave`，有就直接加载存档并在其上询问，完全不经过关卡准备与选卡。

- 世界选择页有**「全解锁」开关**：勾上再创建世界会发 `CreateWorldC2S(world, true)`，服务端写出 `UnlockAll` 档案（沙盒世界拥有所有卡，包括以后新增的）。世界目录仍由客户端创建（列表直接读盘），档案由服务端写。
- `PvzceClient.setCurrentWorld()` 换世界时**丢弃已缓存的列表**（否则会把上一个世界的进行中标签用在另一个世界上，而它正是进入决策的输入）；
- 服务端 `refreshLevelList()`（`/reload` 后主动补发）按**客户端最后一次请求的世界**下发，而不是服务端自己的 `currentWorld`（关卡之间它是 null，会被规范化成 `world`）。

选卡界面不关闭自身，等 `LevelInitS2C` 到达后由 `PvzceClient.onLevelInit()` 用 `setScreenReplacing` 重建整个界面栈，所以暂停对话框/选卡界面不会残留在新关卡下面。

**暂停菜单的「重新开始」**（`PvzceClient.restartCurrentLevel()`）走的是"先真正关闭当前关卡，再进入该关卡的正常选卡流程"：

1. 发 `LeaveLevelC2S`，服务端 `leaveLevel()` 会**先存档再 shutdown**，因此放弃重开也不会丢进度（关卡列表里仍显示"进行中"，可继续）；
2. 客户端清空本关全部镜像状态（`clearLevelClientState()`：实体/粒子/动画/音乐/存档提示/镜像），并用 `setScreenReplacing` 把界面栈换成选卡界面 —— 旧关卡不会以冻结实例留在下面；
3. 「开始游戏」→ `StartLevelC2S(restart=true, seeds)`：服务端 `createLevel(restart=true)` 会**删掉第 1 步写的存档**并开新局；
4. 「返回」/ESC → `showLevelList()`，回到当前世界的关卡列表（**不会**回到刚被关闭的关卡）。

### 4.4 玩家、卡槽与资源

- `SlotResolver.resolve(id)` 是**"这张卡是什么"的唯一答案**（服务端卡槽、客户端选卡池、校验共用）。未知 id 会记录一次并跳过。
- `DeckCardSource` 用 `PvzcePlayer.deckSlots` 建卡槽，而它内部走 `SlotResolver`，因此"选卡界面能选的"与"服务端发放的"必然一致（`PvzcePlayer` 本身只管一支已建好的卡槽，不负责造卡）。
- `Team` 持有共享资源与解锁集合；`Slot` 持有 index/kind/content/costSun/**cooldownTicks**/cooldownLeft/usesLeft。
- **卡片冷却 = 卡自己的数 × 关卡倍率**，两半各在一处：
  - 卡自己的数（`Slot.cooldownTicks`）在建卡槽时从 `SlotResolver.ResolvedCard` 抄下来（槽定义优先、否则回落到植物/工具定义），传送带发的卡是 0；
  - 关卡倍率是规则 `pvzce:seed_cooldown_multiplier`（缺省 1），**唯一换算点**是 `LevelServer.effectiveCooldownTicks(slot)` → `CardCooldown.effective(base, multiplier)`，两条消耗路径（种植物 `DeckCardSource.spend`、用工具 `LevelServer.useToolInternal`）都调它，`toSlotInfo` 也调它并把结果放进 `SlotInfo.cooldownTotal`。
  - 于是卡条画的充能是"还剩多少 / 这张卡在本关一共多少"，两个数同源；**不要在客户端重新推一遍倍率**，也不要让某一处直接 `startCooldown(卡自己的数)` —— 那样关卡缩放的只有等待、画出来的却是另一段长度。改倍率（`/gamerule`）对**已经在条上的卡**立即生效：倍率在消耗那一刻读，不在发牌时烘进 `Slot`。

### 4.5 背包、金币与关卡奖励

**背包、卡池与关卡奖励**：

**背包（`PlayerProfile` + `SeedOptions.cardPool`）**

- 解锁只覆盖**植物与工具卡**；资源卡**不背包锁**（`requiresUnlock` 对资源返回 false），但**仍然要占卡槽**：`pvzce:sun` 的 `collectible_without_card` 是 `false`，银行只在卡槽条里有阳光卡时才画出来，收阳光正是那张卡买到的东西。所以每个关卡的 `slots` 都列着 `pvzce:sun`，`SeedOptions.cardPool` 也照常把它摆在选卡池里。判定只有一处：`SlotResolver.requiresUnlock`（服务端 `PlayerProfile.owns` 与客户端 `ClientProfile.owns` 都调它，两份"锁没锁"不允许分叉）。
- **关卡的 `slots` 是本关固定卡，无视背包**：关卡可以"借"卡给玩家（教学关给一张土豆雷），所以 `SeedSelection.sanitize` 只过滤**自选**，从不过滤关卡钉住的卡。玩家能自选的池子 = 背包已解锁卡 − 固定卡，填到解析后的总卡槽数。
- **总卡槽数只有一个来源**：`LevelDef.effectiveMaxSeedSlots(profileSlots)` —— 关卡**写了** `max_seed_slots` 就用它（1-1 的 2、1-4 的 8 是关卡设计），**没写**就用背包的 `seedSlots`（默认 8）。"没写"因此是 `LevelDef.UNSET_MAX_SEED_SLOTS`（-1）而不是某个数字：拿字面量 6 去比会把升级过的背包悄悄压回去。服务端在 `SeedContext` 里解析一次（`SeedContext.all` / `forProfile`），`LevelPayload` 带的就是解析后的数，所以选卡界面看到的行数与服务端收得下的卡数不可能分叉；`/profile slots <n>` 是背包这半边的操作入口（商店以后走同一个 `PlayerProfile.setSeedSlots`）。
- **卡池只有一个来源**：`SeedOptions.cardPool(def, owns)`（已解锁卡 + 关卡自己的卡），`PvzceServer.sendLevelList` 与 `LevelServer.SeedContext.forProfile` 都用它，所以"选卡界面看得到的"与"服务端收得下的"是同一份。`SeedOptions.forLevel(def)`（不过滤）仍用于测试与编辑器预览。
- 固定卡已填满总卡槽时没有可选空间：判定抽在 `SeedOptions.hasNothingToChoose(pool, maxSlots, lockedIds)`（**纯函数**，屏幕与"存档提示框重开"两处共用），选卡屏进入**预览模式**（见 §6.2 的"选卡屏的入场编排"一段）；存档提示框的「重新开始」则直接重开。
  > 判据是"总卡槽数 − 关卡固定卡数"，**不是"已选卡数"**：用"已选卡数"去减会把"记住的卡组正好填满卡槽"（1-2 第二次进入）读成"没得选"而自动开局，玩家再也不能换卡。
- 新世界默认解锁 `PvzceIds.STARTER_PLANT`（豌豆射手）+ `STARTER_TOOL`（铲子）；`CreateWorldC2S(world, unlockAll)` 让"创建世界"对话框的**全解锁**勾选写出 `UnlockAll` 档案。沙盒用**标志**而不是展开成 id 列表，这样以后新增的内容也自动解锁。

**金币（四种面额，`PvzceIds.COIN_DENOMINATIONS`）**

- 金币不是一种资源而是**四种**，因为原版就是四种不同的东西（白/银币 10、金币 50、钻石 1000、钱袋 250）：一个 `pvzce:coin` 无法告诉玩家刚捡到的是 10 还是 1000。它们是普通 `ResourceDef`，`default_value` 就是面值，`collectible_without_card: true`（捡钱不需要卡槽，也不看 `Team.unlockedResources`）。资源目录 `data/pvzce/resources/{coin_silver,coin_gold,diamond,money_bag}.json`。
- **掉落时 `amount` 直接写成面值**（`defaultValue × coin_drop_amount`），所以队伍那份资源计数本身就读作金币数，HUD 与钱包只需要**求和**，换算阶梯只存在于资源定义里一处。
- **没用上的小推车折成金币**：胜利结算时 `RewardSettlement.settle` 数出还停在车道上的车（`LevelServer.readyMowerCount` → `MowerMechanic.Rig.readyCount`），每辆按**金库里的金币**计价（`mowerCoinValue()` 读 `pvzce:coin_gold` 的 `default_value`，不是字面量），并进本局 bonus。失败一辆也不算——没有"没被突破的车道"这回事。客户端在**点击奖励**那一刻让每辆车的原地冒出一枚金币飞向左下钱袋，计数用的是包里的 `mowers`（不是自己数的），并且把这笔加进 HUD 的金币收款条，否则金币飞向一个不动的数字（§4.5 的"点击奖励"一段）。
  > **车必须同时消失**：金币从车的位置起飞、车还在原地站着，读起来就不是"车变成了金币"。
  `ClientMechanics.consumeParkedMowers(level)` 是**读并标记**的同一个调用（`parkedMowers` 只读），
  被标记的行不再绘制。它不是 `STATE_USED`（那是"僵尸从这条道过去了"、服务端说的），而是纯客户端
  的一次核销——关卡在胜利那一刻就停止 tick 了，服务端没有第二句话要说。
- 美术：三个硬币/钻石由 `tools/reanim_to_pvzce_all.py --entity coin_silver --entity coin_gold --entity diamond --input-dir refer/im5/reamin` 从原版 reanim 生成，钱袋是单张 `textures/entities/money_bag.png`（`ResourceDropEntity` 的平铺贴图回退路径）。**生成时排除了 `COINGLOW` 与 `DIAMOND_SHINE`**。
  `refer/anim` 是**完整**的原版动画集（146 个 reanim），`refer/im5/reamin` 只有硬币那几个；新增内容优先去 `refer/anim` 找。
  **硬币是「弹出来」的**：四种面额都是 `drop_motion: rise`，`rise_height: 0.3`、`rise_scatter: 0.25` —— 从僵尸身上弹起 0.3 格再落下，落点随机左右偏移最多 0.25 格（同一个僵尸一次掉好几枚，方向一致会看起来像同一个东西复制）。向日葵产的那朵阳光仍然是 `rise_height` 默认的 0.5、`rise_scatter` 为 0：它属于那朵花，要落回原处。横向位移由 `LevelServer.spawnResource` 用关卡自己的 `Random` 掷出后交给实体（实体不自己掷骰子，否则读档会重掷）；`riseTicks`/`riseOriginX`/`driftX` 都写入实体 NBT；关卡恢复目前不重建已掉落的阳光/金币。双子葵尚未弹出的第二颗由生产能力自己的待发队列恢复。
  **掉落尺寸**：四种面额都声明了 `render_scale`（三枚硬币 0.25 ≈ 0.2 格，钱袋 0.55），因为掉落物的默认大小是 0.8 格 —— 一枚硬币按 0.8 格画出来比一格草坪还显眼，看着像一块发光的圆盘而不是硬币。
  **动画掉落物的尺寸契约**：掉落物和植物、僵尸同一套规则 —— **画多大就是模型里写多大，再乘 `render_scale`（两个轴同倍率）**。没有任何自动拟合：曾经那套"只把宽度拟合到 0.8 格、高度取自动画文件"的写法是自相矛盾的（模型尺寸必须写成拟合结果的那个数），而且它按**模型最大边**拟合，于是"比本体还宽的光晕"决定本体多大——金币的光圈 80px、币面 43px，币面被画成自己美术的 54%，宽度那一轴还要再被压一次。现在：转换器把每个掉落物的 reanim 缩放到 `EntityVisuals.AUTHORED_DROP_CELLS`（0.34 格，两边共用同一个常量），光晕这类"比本体大"的贴图不进模型（它是粒子/加色层的活），运行时只乘 `render_scale`。`CoinVisualLayoutTest.everyDenominationsModelHasTheSameShapeAsItsArt` 钉住"模型比例 == 美术比例"（非等比就会被画扁）与"作者尺寸就是约定尺寸"。钱袋没有动画、走贴图兜底路径，那条路两个轴都乘 `render_scale`，本来就是对的。
  **产阳光是无声的**：原版向日葵产阳光时不出声，那声属于拾取，由 `ResourceDef.pickup_sound` 在玩家真去点的时候放。金盏花保留自己的出币声（它的掉落是小钱，不是这一关赖以运转的资源）。
  **拾取音效也按资源分开**：`ResourceDef.pickup_sound`（缺省 `sfx/ui/collect`）。阳光用收集音，三枚硬币用 `sfx/ui/coin`，钻石用 `sfx/ui/diamond`。
  **拾取闪光按资源分开**：`ResourceDef.pickup_effect`（可选）是「捡起这个资源时放什么效果」，缺省**什么都不放**。阳光声明 `pvzce:lantern_shine`（200x200 的黄色柔光，每颗 0.7 格、一次 10 颗，**原样保留**）；四种面额**不声明** —— 同一片黄光画在硬币上是把半块草坪糊成黄色，而捡币本来就有收集音效与飞向钱袋的动画在说「收到了」。`LevelServer.collectResourceInternal` 只负责发声音，粒子 id 从资源定义里取。
- **关卡内**的僵尸死亡按 `rewards.coin_drop_chance` 掉 `rewards.coin_drop`（默认 `pvzce:coin_silver`）这枚币（`LevelAccess.zombieDied` → `LevelServer.zombieDied`；实体只报告"我死了"，掉落是关卡数据的事）。金盏花产银币（10 / 24s）。
- **关卡结束**时 `RewardSettlement.settle` 把本局收集的金币写进钱包（**胜负都入账**），再按首通/重复发放关卡奖励。**金币**的首通判定是 `level_status` 文件在不在（`levelStatus(...).isEmpty()`），所以重复通关拿的是 `repeat` 那份。**`first_clear` 里的解锁不看这个判定**：只要关卡声明了某张卡的解锁、而背包里还没有它，**任何一次通关都会补发**，已经拥有则是空操作。两者必须分开 —— 首通标记只说明"这一关已经通关"，不说明"这份奖励发出去过"。

**关卡奖励（`LevelRewards`）**

- 关卡 JSON 的 `rewards` 块：`first_clear` / `repeat` 是 `{type:"unlock"|"coins"|"resource", id?, amount?}` 列表，外加 `coin_drop`（掉哪种币，资源 id）/ `coin_drop_chance` / `coin_drop_amount`。默认值 = `LevelRewards.DEFAULT`（首通不给额外奖励、重复给 100 金币、25% 掉 1 枚银币）。`first_clear` 的 **unlock 条目是幂等的**：见下一节"结算与展示"前的说明 —— 已拥有即空操作，缺失就补发，与首通标记无关。
- **`resource` 是第三种奖励形状**：钱包只装得下一个数，所以"发一颗钻石"就是"发它值的那 1000 金币"，而**面值来自资源定义自己的 `default_value`**（`RewardSettlement.applyLevelRewards` 读它，不在关卡里再写一遍 1000）。它和 `coins` 一样按首通/重复分支走，并且比 `coins` 多带一件事：奖励包里的 `ITEM` 条目让客户端**画那个东西本身**——草坪上落下来的是钻石、飞进钱袋的也是钻石、结算页相框里落的还是钻石。
- `type` 是字符串判别式，**DFU codec 看不出拼错的类型**（`"unlcok"` 会正常解码然后什么都不发），所以 `LevelValidator.validateRewards` 必须跑：未知 type、缺 `id`、未知卡/未知资源、`amount <= 0`、掉率 >0 但数量 0 都报出来。

**结算与展示：奖励先落在草坪上，再由玩家领取**

一局胜利**不会**直接弹出奖励页。顺序是（全部在客户端，服务端只发两个包）：

```
GameStateS2C(plant 胜)   → 不播胜利音乐（onGameState 对植物方胜利刻意跳过）
LevelRewardS2C           → InGameScreen.showReward：种子卡/奖励物/钱袋落在**最后一只僵尸死亡的那一格**，从上方落下
等待期                    → 奖励自己闪烁，头顶一枚**上下滑动的金色箭头**（不写"点击领取"）
玩家点击奖励              → 胜利音乐立刻开始；**剩余小推车与奖励各自变成金币飞向左下钱袋**；
                           同时奖励慢慢移到屏幕中央（1.9s）
移到中央                  → 原地再放大一点（0.6s）
放大完成                  → 白光从奖励位置向外扩散（0.7s）→ 全白保持 0.35s → 淡出 0.4s（奖项页在这段淡出里打开）
```

  共约 4s。**等待期只有一枚箭头，不写字**：原版不往草坪上写字，它指着那个东西、让闪烁说完剩下的，
  一眼能看懂，也不用翻译。它用的是**原版自己的贴图**（`refer/im7/particles/DownArrow.png` → `textures/gui/hud/down_arrow.png`），
  不是自绘的：原版那套里就有一个 `AwardPickupArrow.xml`，第二个 emitter 正是 `IMAGE_DOWNARROW`
  加一条 `Position` 曲线 `0 EaseInOutWeak 10 EaseInOutWeak 0`——下去十帧再回来。所以这里照抄的是
  同一张图、同一条曲线，只差把它摆到该在的位置上（32px ÷ 原版 80px/格 = 0.4 格宽）。**白光是从奖励身上长出来的，不是全屏渐变**——它从奖励当时的矩形中心开始、
  半径取"到窗口最远角的距离"，所以扩散结束时无论宽高比如何都已经盖住每一条边；`renderRewardLight`
  画的是一个正方形而不是圆盘，GUI 没有圆和加法混合，而这个速度下方形读起来就是"光从那个方向过来"。
  奖励被领取的**同一步**就发射白光起点（`claimReward` 记录 `rewardRect()` 的中心），所以"移中"与
  "发光"是同一拍开始的。

- `LevelRewardS2C(levelId, collectedCoins, bonusCoins, totalCoins, grants, ...)` 在 `GameStateS2C` 之后发；它**只是表现**，钱包在发包之前就写好了，客户端不领取也照样拿到金币。
- **`grants` 是一张列表，不是三个字段**：一次通关可能同时发好几样东西（一张卡 + 一个增益 + 一份资源），而它以前是"一个解锁 / 一个增益 / 一个物品"三个单值字段——第二张卡会被照发但**页面上没有任何提示**。列表顺序就是结算页的绘制顺序（`CARD` → `BUFF` → `ITEM`），`headline()` 取表头即"这一局最大的新闻"，相框与草地上掉的东西都用它；`hasUnlock()` / `unlockedCard()` / `unlockedBuff()` / `hasRewardItem()` 这些旧问题全部由表头回答，调用点一个没改。
- 奖励掉落物**不是实体**：它是 `InGameScreen` 里的一个世界坐标点 + 三个时间戳（落下 / 领取 / 音乐），因此不进存档、不参与判定，也不需要服务端同意。`rewardRect()` 是**唯一的**矩形来源，绘制与点击命中都读它（点击落点与贴图不可能分叉）。
- **掉落物有三种样子，按表头判定**：解锁卡 → 种子卡；没有卡但有资源 → 那个资源的美术（钻石画成正方形，不拉进种子包的比例里）；两者都没有 → 钱袋。这三条与 `AwardScreen` 的分支**一一对应**，所以"草坪上看到的"和"结算页相框里看到的"是同一件东西。
- **落点是"最后一杀"**：`LevelRewardS2C` 带 `dropX/dropY`，来自 `LevelServer.lastKillX/Y`（`zombieDied` 里先记位置再掷掉币，所以不掉币的僵尸也算）。没有僵尸的关卡为空值，客户端回落到草坪中央。
- **胜利音乐属于"点击"那一瞬间**，既不属于"关卡结束"也不属于"移到中央"：`PvzceClient.onGameState` 对植物方胜利直接 return，stinger 由 `InGameScreen.claimReward()` 在点击的同一步播放（与升移动画同时开始）。失败没有奖励可领，所以结束时立刻播。
- **金币飞进左下角的钱袋**：每种掉落物飞向**自己的**银行（`bankTarget`：阳光→左上阳光银行，金币→左下钱袋）。按每条动画自己的银行判断：金币只要求钱袋（它本来就是「有变化才显示 2.6s」的回执），阳光才要求阳光银行。
- **兜底**：奖励躺够 `REWARD_AUTO_CLAIM_NANOS`（20s）没被点就自动领取 —— 金币早已入账，这个计时器只是为了不让走开的玩家回来面对一个冻结、且唯一出口是一个他已经不记得要点的精灵的棋盘。
- 没有奖励包的胜利（改过的服务端）走兜底：大号「胜利！」+ 点击任意处离开。
- `AwardScreen` 用 `refer/im5` 的原版奖励页美术，**播 `pvzce:music/zen_garden`**（`ensureMenu`）：关卡已经结束，这一页讲的是玩家带走了什么。表头是解锁卡 → 种子卡落进相框；否则是资源 → **那个资源落进相框**；都没有 → **本局的金币**（一进场就自己撒一次币 + `pvzce:sfx/ui/moneyfalls`，不需要点）。"继续"走 `PvzceClient.finishLevelAndShowList()`（回关卡列表而不是世界列表）。
  - **正文按 `grants` 逐条列**：标题（获得新植物！/ 获得关卡增益！/ 获得战利品！）+ 每样东西的**名字与它自己的 `.desc`**（图鉴里那句话）。金币降成页脚一行——钱包只动了一个数，而这一页讲的是带走了什么。放不下时按"**名字优先于句子**"贪心填，剩下的写成"还有 N 件"而不是截断。
  - **两处锚点**：正文从美术的 `NOTE_TOP` 往下排，金币行锚在 `NOTE_BOTTOM` 与"继续"按钮上沿的**较高者**——按钮是这一页唯一必须按得到的东西，而 4:3 底图被 16:9 窗口上下裁过，原版那三行所在的位置不一定在按钮上面。
  > **这一页是收据，不是第二个领钱的地方**：钱袋留在草坪上炸开、金币飞进玩家一路看着的那个 bank，这一页只报账。
  > 页面**淡入**（`FADE_IN_NANOS`）：它是在白光结束的那一帧打开的，硬切会把白光唯一的意义抹掉。
  - 标题画在**窗口顶部**而不是美术坐标里：奖励页底图是 4:3 且 cover 适配，宽屏下美术顶部那条木牌会被裁掉。
- 奖励页的「继续」用 `Button.Style.SEED_CHOOSER`（木质）而不是默认的金属边框按钮：这一页是木板，金属按钮属于对话框。
- 波次进度用原版 `refer/im6` 的三张图（`FlagMeter` 的上下两条分别是空轨与绿色填充、`FlagMeterParts` 的僵尸头/杆/旗、`FlagMeterLevelProgress` 的铭牌），画在**右下角**，每一块都有含义：`[关卡名] [轨道 + 绿色进度]`，**`LEVEL PROGRESS` 铭牌贴在条的正下方居中**（上沿就是条的下沿，中间不能留缝：它和条是同一件仪表），**僵尸头骑在绿色进度的前沿**（它是进度标记，不是固定在一端的装饰），**只有 huge/final 波才插旗**（小波插旗会让旗子失去"大波要来了"这个唯一含义）。
  - **比例照原图**：条按 `158×23` 的原尺寸 × `METER_SCALE`（0.9，和阳光银行 `70/78` 同一把尺子）画，不拉伸 —— 拉长会把两端圆角压成椭圆、把旗子摊开。
  - **方向从右往左**，和原版一致：绿色填充锚在右端、前沿向左推进，旗子也按镜像排在 `1 - (i+0.5)/总波数`（第一波的旗在最右）。
  - 填充用的是**关卡总进度** `(当前波 + 波内进度) / 总波数`，不是当前这一波的进度 —— 这样前沿正好在该波到来时扫过对应的旗子。
  - 贴图是**上下翻转**加载的（UV (0,0) 在左下角，见 `TextureManager`），所以按 PNG 行号写的矩形要经 `vRangeForRows` 换算。
- **奖励里的钱袋也在草坪上炸开**：`rewards.bonusCoins`（小推车折价 + 重复通关金币等）在没有解锁卡时
  就是那一袋钱，`InGameScreen.payForRewardBag` 按面值换算成若干枚金币（每 100 一枚、至少一枚、最多 12 枚，
  单枚价值 = 总额 / 枚数，所以加起来正好是到账的那笔），从钱袋的矩形中心飞进左下 bank。用的币种是**本关
  `rewards.coin_drop`**（关关卡用银币就飞银币），计数同样加进 HUD 的收款条（`claimedRewardCoins`）。
  > **袋子只赔"小推车之外"的那一份**：`bonusCoins` 是一笔已经含了小推车折价的总额，而小推车各自在
  > 自己的位置上变成一枚金币（`payForParkedMowers`）。两条动画都从总额出发就等于**把车钱画了两遍**、
  > 也让 HUD 的收款条比钱包多走一截，所以 `InGameScreen.rewardOnlyCoins()`（`bonusCoins - mowerCoins`）
  > 是袋子/奖励物这一份，两个 `claimed*Coins` 加起来正好是 `bonusCoins`。
  > 有 `rewardItem` 时袋子换成**那一个资源**飞进钱袋（价值就是那份金币数），而不是把它拆成十枚银币。
- 关卡内金币计数用原版 `coin_bank` 美术画在**左下角**（阳光银行占左上、波次条占右下，左下角永远是草坪），而且是**收据而不是常驻控件**：只在金币数变化后显示 2.6s（末 0.6s 淡出），新关卡开局不会凭空闪一个 0。`bankTarget(resourceId)` 决定收集动画飞向哪个银行 —— 金币落到阳光上会说明错的事情。
- 图鉴页 `AlmanacScreen`（关卡选择页的「图鉴」按钮，原背包页已删除）把**未解锁的植物也画出来**：已解锁的照常画，未解锁的是同一张卡片上的"未解锁"提示 —— 只列已拥有的回答"我现在能做什么"，列出未解锁的回答"为什么我种不了坚果墙"，后者才是玩家真正的问题。它只读，不改档案。内容与文案见 `架构-客户端.md` §6.2.5。
- 关卡选择页右上角显示本世界金币（`textures/gui/award/money_bag`，缺图回退金币贴图）。

### 4.5.1 关卡增益（`LevelBuff`）

**增益是玩家在选卡页决定的一局规则**，与关卡的 `mechanics` 是两件事：mechanic 是"这一关是什么形状"
（关卡说了算），buff 是"这一局怎么打"（玩家说了算，关卡有权钉死或放开）。它在代码里注册
（`PvzceRegistries.LEVEL_BUFFS` + `BuiltInBuffs`），关卡 JSON 只写 id。

```jsonc
// data/pvzce/levels/yard/adventure/1_6.json
"buffs": ["pvzce:player_choice"],   // 放开给玩家选（哨兵，本身不是增益）
"max_buff_slots": 3                 // 不写＝跟随背包（PlayerProfile.buffSlots，默认 5）
```

- **增益是奖励，不是背包自带的**：`PlayerProfile.unlockedBuffs` 是第三个袋子（与卡、关卡购买并列，
  自己的 NBT 键 `UnlockedBuffs`），一个增益只有**被某一关发过**才能在选卡页勾上。
  奖励类型是 `{"type": "buff", "id": "pvzce:mushroom_range"}`（`LevelRewards.Reward#buff`）：
  与 `unlock` 一样**幂等**、**任何一次通关都补发**（首通标记只说"这关通过了"，不说"这份奖励发过了"），
  所以老世界即使早就通关了 1-9 也照样拿得到。**两个内置增益分别由 1-9 与 2-9 首通发出**
  （`rewards.first_clear` 里那一条；这两关的 `repeat`/掉币是引擎默认值，显式写出来只是因为块存在了）。
  发出去之后**不单独下发那份名单**：世界已经有了背包档案，而"这个玩家能不能勾这个增益"正是
  `LevelBuffSelection.chooserPool(def, owns)` 在拼池子时算的一件事——未获得的增益**仍然列在池子里，
  但那一项带锁**（`SeedOptions.LOCKED_OPTION`，复用价格字段；`client/gui/screens/ChooseSeedsScreen`
  画挂锁、点它只响一声），`LevelBuffSelection.sanitize` 也不收它。池子因此是这条规则的**唯一一份**：
  服务端那一侧才是门，客户端画的锁就是门上那把锁，没有第二处会跟它分叉。
  关卡自己钉的增益**不需要玩家拥有**（关卡的"我这一关就是这样"优先于背包，与固定卡同一条逻辑）。
  `/profile buff <id>` 是发增益的操作入口（冒烟/测试用）。
- **两个内置增益**：`pvzce:auto_collect`（自动拾取阳光与金币）与 `pvzce:mushroom_range`
  （发射孢子的蘑菇射程 ×1.5）。前者落地后 **15 tick** 才收（`LevelServer.AUTO_COLLECT_DELAY_TICKS`）——
  与生成同一 tick 收走会让掉落物**根本没出现过**（生成包与收集包同一批发出去），
  而且它**不绕过**关卡的收集规则：需要阳光卡的关卡照样需要那张卡，只是不再需要玩家去点。
  后者只对"有 `pvzce:nocturnal` **且**有 `ShooterCapability`"的植物生效（`LevelBuffs.isSporeShooter`），
  所以小喷菇/胆小菇吃得到、大喷菇的喷雾（`ConeAttackCapability`）与阳光菇/寒冰菇/毁灭菇吃不到；
  `range` 无上限的射击**不受影响**（整块草坪乘任何数还是整块草坪）。
- **唯一换算点是 `PlantShots.scaled(ref, plant, level)`**：子弹的寿命与植物的"值不值得开火"读的是
  同一个数（`ProjectileRef.range`），所以**两半都必须读缩放后的那一份**——射击能力拿它决定何时开火
  （`ShooterCapability.hasTarget`），`LevelServer.spawnProjectile` 拿它造子弹。倍率本身来自
  `LevelAccess.sporeRangeMultiplier(plant)`（实现是 `LevelServer`），每发射一次重读、不烘进植物，
  因此中途改了增益下一次射击就生效。
  **约束：射程这件事有"飞多远"与"肯不肯开火"两半，两半都必须读同一个倍率。** 缩放只做在
  `spawnProjectile` 里是不够的——判定那半边若读定义里原始的 `range`，"孢子飞得更远"会成立、植物却照旧在 3 格
  才肯开火，玩家看到的是增益完全没生效。`MushroomRangeBuffTest` 因此钉的是"**首次开火那一刻**僵尸在多远"：
  只看孢子飞多远测不出来，僵尸会自己走进射程，两次测量完全一样。
- **收选规则在 `LevelBuffSelection`（纯函数）**，与 `SeedSelection` 三件套一一对应：
  关卡自己钉的增益先放且永不筛掉（哪怕玩家背包里没有、甚至注册表里没有）、自选按提交顺序填到
  `LevelDef.effectiveMaxBuffSlots(profile.buffSlots())` 为止、上限**先判后加**；
  `planForRun` 把"续档"这一个特例收在一处（存档里的 `Buffs` 列表优先，`null`＝那份存档早于增益系统，
  此时才回落到世界偏好）。
- **一个世界一份自动启用名单**：`PlayerProfile.autoBuffs`，入口是选卡页的增益页。
  它写的是**这一局实际生效的增益**（`PvzceServer.createLevel` 里 `rememberAutoBuffs`），
  所以"我上次带进去的"与"下次帮我预选的"永远是同一份；空列表是合法值（＝以后别帮我选）。
  续档时不写（那一局的选择是上一次会话做的，不是现在的表态）。命令入口：`/profile buffs [id...]`、
  `/profile buffslots <n>`。
- **协议**：`LevelPayload` 多三样 —— `buffPool`（可选池，与卡片池同一形状的 `SeedOption`，
  kind 是 `buff`）、`maxBuffSlots`（**已解析**的数量，客户端不重算）、`activeBuffs`（这一局实际生效的、
  服务端解析后的集合，HUD 只画被告知的东西）；`PlayLevelC2S` 多 `selectedBuffs`；
  `ProfileS2C` 多 `buffSlots` 与 `autoBuffs`（**协议 22 → 23**）；已获得的增益名单不另发一份，它体现在 `buffPool` 里每一项的锁标记上。
- **不进存档的两样东西**：`autoCollectTimers`（每 tick 按当前在场掉落物重建）与掉落物的"刚生成"标记；
  进存档的是 `Buffs` 列表本身，所以续档播放的规则与存档时一致。
- **界面**：选卡页顶部两个 tab（种子卡槽 / 关卡增益）共用同一套排版与绘制代码，
  `previewOnly` 现在要求**两页都没得选**（1-1 那种固定卡满格但仍放开增益的关卡，玩家必须能进去选）；
  关卡内的增益图标画在**左下角、钱袋银行上方**（`BuffIconRow`，钱袋只闪 2.6 秒且会盖住同一角），
  悬停显示名字。悬停提示只有一份实现（`client/gui/HoverTip`），卡槽条与选卡页也用它。
- **奖励页与草坪上的那一件东西有三档优先级**：解锁的**增益** → `resource` 物品 → 钱袋，
  卡永远第一（`LevelRewardS2C.unlockedBuff` 是新字段，**协议 23 → 24**）。增益画的是**种子包的框 + 增益自己的图标**：
  这一页说的是"你拿到了新东西"，钱袋会说出相反的话；结算页的文字也换成 `pvzce.award.new_buff`。
- **两个内置关卡策略**：1-6~1-9 与 2-1~2-4 / 2-6~2-9 写 `pvzce:player_choice`（放开），
  所有「卡不是自己挑的」关卡（1-5 / 1-10 / 2-5 / 2-10 / 3-5 / 3-10 / 4-5：五个传送带关、打地鼠与恐怖花瓶）钉 `pvzce:auto_collect`，
  `yard/minigame/sleep_deprivation` 钉 `pvzce:mushroom_range`（整关都是蘑菇）；
  1-1~1-4 不写 `buffs`（教学关不堆概念），没写 `buffs` 的关卡连增益页都不会出现。

### 4.6 命令

`PvzceCommands.create(server)` 构建 Brigadier 树。分类参数来自 `PvzceRegistries.byCategory()`；`IdentifierArgumentType.forCategory` 的补全也来自同一张表（含复数别名）。时间查询用 `PvzceClock` / `DayNightCycle` 的共享函数。

### 4.7 AI

**`PlantAIPlayer`**：每 120 tick 决策一次，通过 `LevelServer.spawnPlant` 种下，因此与玩家种植完全同构。三种角色（防御/经济/进攻）的植物 id 可由关卡环境变量 `pvzce:ai_defense_plant` / `ai_economy_plant` / `ai_offense_plant` 覆盖，取不到时回退到内置选择。它只在声明了 `pvzce:plant_ai` 的关卡里开（今天是无尽与变异那两处）。

**`JevBrain` + `JevClient` + `pvzce:versus`**：对战关的对手。Jev 是 TypeSafe 的 System One
**决策模型**（不是聊天模型）：POST 一个 `state` 加一组 `questions`（`choice` / `score` / `noul`），
拿回带概率与置信度的结构化答案。三件事分得很清：

- `JevPrompt`（`common/jev`）是**问什么**：把场上信息压成一份 state（本方阳光、目标进度、
  已过秒数、手牌与能否负担、逐行的植物/僵尸、允许的列），再问三问——**出哪张卡**（`hold`
  是候选项之一，"这一手不出"是一个决策而不是失败）、**哪一行**、**哪一列**。纯数据 + JSON，
  所以请求形状可以离开服务端单测。
- `JevDecision` 是**答案怎么读**：三级容错（`data.answers` → `answers` → 顶层逐键）、宽松键
  匹配（`basic_zombie` → `pvzce:basic_zombie`、`3` → `row_3`、`wait` → 弃权），并且**只接受
  自己问过的候选项**——答案点名了不在手牌里的卡就弃权，交给内置策略。实测过的响应体收在
  `JevProtocolTest` 里。
- `JevClient` 是**怎么送**：单工作线程 + 主线程队列，**一发在途**（在途时拒绝第二次请求，
  等它回来比问一份马上要过期的状态更划算），12 秒超时，从不阻塞 tick，**不重试**（下一次
  决策更便宜也更新鲜）。凭据来自 `AiSettings`：客户端在进关与保存时用 `AiSettingsC2S` 交给
  服务端（只在内存，不进存档、不进日志），`-Dpvzce.jev.url|model|key` 或
  `PVZCE_JEV_URL|MODEL|KEY` 是启动参数门，**启动参数优先**。

`JevBrain.tick` 每 tick 被 `VersusMechanic` 叫一次：读答案、**按服务端自己的规则复核**
（阵营、钱、区域、格子，全部走 `canPlace*` 与 `spawn*`），过了才落子；没过或没答案就回退内置
策略，并把这件事写进 HUD 的状态（`Status.BUILTIN` / `JEV` / `FALLBACK`）。它还负责**替 AI 那一方
捡阳光**（只捡自己队伍的、只捡已经落地的）——植物方没有人帮忙点，而它的胜利条件正是收集阳光。

**内置策略**是按"像样的玩家"写的，并且**按卡的能力分角色**（`producer` / `shooter` / `wall`，
不是按 id 猜），因为"买最便宜的"这条在两侧各错一次：僵尸方变成永远只出普通僵尸（实测一局 191 只
全是它），植物方变成永远只种向日葵。
- **僵尸方**：**买什么**与**放哪里**分开。每三次采购里一次买"最好的"（固定配比——"差一次进账就
  攒钱"会与关卡收入形成正反馈：收入高了买得起好牌，好牌又把每点阳光的伤害翻倍，实测同一套收入
  会从公平变成 peak 20 只、三分钟结束），其余两次买最便宜的保持压力；买得起最好就买最好，
  差一次进账就等一手。放置优先空车道，其次僵尸最少的车道，落在自己区域最靠前的一列。
- **植物方**：有僵尸又没有射手的车道先补最好的射手；僵尸逼近就在它前面补墙；产阳光的不足 5 株
  时补产阳光的；否则给射手最少的车道补射手。
- **节奏**：内置策略 **0.5 秒**决策一次；`decision_ticks`（3 秒）是**问 Jev 的**节奏——网络往返
  才值三秒，几次比较不值，而按三秒走的内置植物 AI 实测 78 秒就被打穿。
它也是没填 key 的玩家实际面对的对手。

### 4.7.1 `pvzce:versus`：一局对战的全部数据

`VersusData`（`api/content`）一个块写清整局：`sun_goal`（植物方的目标，**只算捡到手的阳光**）、
`plant_initial_sun` / `zombie_initial_sun`、`zombie_income_sun` / `zombie_income_ticks`、
`eat_refund_percent`（被吃掉的植物按其阳光成本的百分之几返还给吃它的那一方）、
`decision_ticks`（默认 3 秒）、以及两边的卡组 `plant_cards` / `zombie_cards`（植物的卡组里带
`pvzce:shovel`：种错了要能挖；AI 的手牌只看 PLANT/ZOMBIE 两种 kind，所以铲子只到玩家手里）。
**两边同一刻开始，没有等待时间**：植物方的先手是它的 `plant_initial_sun`（三关都是 800）与天降
阳光，僵尸方的是它自己的开局阳光与周期入账（50 阳光 / 5 秒）。曾经有过一个 30 秒建造窗口
（`zombie_start_ticks`），用户否掉后连同字段一起删了——"这一方先别动"不该存在于一个对战模式里。

- **卡组是关卡的**：对战关的 `slots` 留空、`seed_screen: false`（没有选卡页可问）。玩家那一方
  的卡由 `SeedSelection.plan(..., humanTeam)` 从机制块取，`LevelServer` 构造函数在"选择为空"
  时也读同一份（不然不经 plan 的构造路径会拿到空卡条）。植物方的卡组**必须含 `pvzce:sun`**，
  否则它永远捡不到自己比赛的资源——`VersusData.validate` 会报出来。
- **计数点**：`LevelServer` 的收集路径上调 `LevelMechanic.onResourceCollected`，点击与 AI 自动
  拾取同一条路，所以"捡到手"只有一个口径（花掉不减、开局赠送不算）。
- **返还点**：`ZombieEntity.bitePlant` 在伤害结算后问 `plant.isRemoved()`，再调
  `LevelServer.plantConsumed`。铲子、爆炸、关卡自己的移除都不会触发它。
- **胜负**：植物方收满目标 → `LevelServer.plantGoalReached()` → `markEnd(plant)`；僵尸方沿用
  `zombieReachedLeft`（有小推车的行要先被推掉）。`checkEnd` 里"波次出完且草坪干净"那条现在要求
  **关卡确实有波次**，否则一个 0 波的对战关在第一 tick 就会被判植物方胜。
- **放置区**：植物用现成的 `pvzce:placement_zone`；僵尸用 `pvzce:zombie_zone`，两者共用
  `PlacementZone` 这个数据记录与校验器（只有报错里的名字不同）。`LevelServer.canPlaceZombie` 是
  玩家与 AI 共用的那道门。
- **HUD**（`VersusClientMechanic`）：**右下角两块面板**。上面一块是**对手的家底**（用户要求）：
  "对手阳光 N" + 它手里那副牌（关卡给那一方的卡组），**最近打出的那张高亮**、其余压暗——
  "它还有多少钱、下一只可能是什么"是玩家在对局里一直想知道的事。金额与牌面都来自服务端
  （`State.opponentSun` / `State.opponentHand`），客户端一个数都不猜。下面一块是自己的比赛进度：
  "我方阳光 N / M"（玩家当僵尸方时是"对方植物方阳光 N / M"）+ 对手是谁（Jev / 内置策略 /
  Jev 未响应）与对手最近一手及行号。状态用 `MechanicSyncS2C` 走机制自己的 `PacketStruct.Codec`
  （加字段不动协议版本）。位置是被一次截图纠正的：它最早画在底部居中，而那里正是关卡**开场提示**
  条的位置；右下角在对战关是空的——常驻那里的波次条由关卡的波次表画，而对战关没有波次。

#### 4.7.1.1 两层 AI：指挥官（大模型）与 Jev（战术）

对战模式的对手由**两层**组成，各有一条独立通道、独立节奏，因为目标是两种：

| | Jev（战术） | 指挥官（战略） |
|---|---|---|
| 协议 | `{model, state, questions}` → 类型化答案（`JevProtocolTest`） | OpenAI 兼容 chat completions → 文本 |
| 节奏 | `decision_ticks`（3 秒），受压时 2 秒 / 1.5 秒 | 平静 20 秒（植物方）/ 30 秒（僵尸方），受压 15 秒 / 10 秒 |
| 线程 | `JevClient`，12 秒超时 | `CommanderClient`，45 秒超时，**独立工作线程** |
| 凭据 | `AiSettings.jev()`（`pvzce.jev.*`） | `AiSettings.commander()`（`pvzce.commander.*`） |
| 输出 | 一张卡 + 一行一列 | 一句话方向，进 Jev 请求的 `state.commander_plan` |

- **慢的不许占快的槽位**：思考模型一次要几秒到几十秒，而战术决策每三秒一次，所以两个客户端各
  自"一发在途"，各自的工作线程。
- **指挥官看的是简报**（`JevBrain.commanderSnapshot`）：我方、胜负条件与进度、阳光、**收入节奏**、
  手牌与价格（买不起标负号）、每行的植物/僵尸（带格子、x、血量）、以及**它上一次写的计划**
  （否则它会不断重复同一条）。名单写成**闭集**（"只有这些（完整列表）"+"不要提到列表之外的"），
  因为没有这句话时模型会点到这场根本没有的卡（实测 5 次 1 次）。
- **回答是结构化的，而且先核对再使用**：第一行必须是手牌里的卡 id 或 `hold`，`acceptPlan` 解析并
  核对（容忍前缀/反引号/各种分隔符），核不过**整条拒绝**并 WARN（理由也是针对那张不存在的卡写的）；
  核过了卡 id 单独作为 `state.commander_card` 交给 Jev，散文进 `state.commander_plan`，并附一句
  "局面与它冲突时按局面办"。
- **默认关思考**：`deepseek-flash` 不关时会把预算全烧在 `reasoning_content` 上、`content` 为空；
  请求带 `{"thinking":{"type":"disabled"}}`，遇到 400/422 去掉重试一次并记住。
- **它对玩家可见的只有 F3**：`VersusMechanic.State.commanderPlan/commanderBusy` 下发，
  `DebugOverlay` 画在右下角、对战面板上方。这两个字段自己会变，所以它们自己进下发判据。
- **没有指挥官时一切照旧**：`directive` 为空 → 提示词不带 `commander_plan`，Jev 独立工作。

#### 4.7.1.2 对手也有一条卡条（冷却、价格、次数）

对手的落子与玩家的点击走**同一条收费路径** `LevelServer.chargeCard(owner, slot)`：在冷却里就不行、
扣阳光、扣一次使用次数、开始冷却；被棋盘拒绝时 `restoreCard(slot)` 把三者一起还回去。AI 的卡条是
`LevelServer.opponentPlayer`（`PvzcePlayer`，牌来自对战块的 `cardsFor(对方)`），与玩家的卡条并列
创建、并列每 tick 走冷却，但**不发包**——客户端要知道的是对手做了什么（`State.lastCardId`），不是
它手上每张牌剩几秒。

> 这一条是用户报的："AI 直接无视冷却了"。旧路径只扣阳光。植物卡的冷却最长（豌豆 5 秒、高坚果
> 30 秒），僵尸卡只有 1 秒——所以这个 bug 在僵尸侧几乎看不出来，在植物侧是实打实的便宜。

两份提示词里也各有一个冷却事实：Jev 的 `your_cards[].ready` / `cooldown_seconds`，指挥官的简报
里写"冷却中 N 秒"。

### 4.7.2 选边：`humanTeam` 从客户端走到存档

一个关卡可以声明多个可玩阵营（`playable_teams`），`LevelSetupScreen` 上点的那个阵营随入口包
（`PlayLevelC2S` / `RestartLevelC2S` 的 `humanTeam`）到服务端，在 `LevelServer` 构造时就座到那一方
（席位、卡条、胜负判定是同一次解析），并写进存档（`HumanTeam`）。续档时 `PvzceServer` **先读存档
再构造关卡**，否则一局对战会在续档时两边互换。奖励判据是"**玩家所在的阵营赢了**"
（`RewardSettlement.isPlayerWin`）：在有多个可玩阵营的关卡上，这与"关卡 `win_team` 赢了"不再等价。

---

AI 到这一层为止：`PlantAIPlayer` 是给无尽头**看着自己打**的基础策略，`JevBrain` 是对战关的
对手，两者都没有规划器与难度档位。其余关卡的僵尸仍由波次表与 `WaveDirector` 驱动（没有
`WaveGenerator`）；可以调的**节奏**已经在数据里（`pvzce:wave_pacing` 的清场奖励与四种模式，
见 §4.7.3）。

### 4.7.3 资源掉落：三种落地方式

资源落地由 `ResourceDef.drop_motion` 决定（`fall` / `rise` / `landed`），并且**同一份资源可以两种都有**：天上掉的阳光是 `fall`，向日葵产的那一朵经 `LevelAccess.spawnProducedResource` 明确要求 `rise`（先上浮 0.5 格再落回原点）。金币一律 `landed` —— 生成即在原地。

**击杀掉阳光**是关卡自己的经济：规则 `pvzce:zombie_sun_drop_chance`（概率，缺省 0）与 `pvzce:zombie_sun_drop_count`（一次掉几颗，缺省 3）。`LevelServer.dropZombieSun` 在僵尸死亡位置结算：每颗阳光**按 `landed` 直接落在死亡格或它相邻的格里**（散开一格是为了三颗不叠成一个像素，且落在草坪内），不是从天而降 —— 掉落物是这一击杀的产物，从天上来会读成"关卡自己在掉阳光"。概率是**按这个颗数读的**：3% 掉三颗与 9% 掉一颗收入相近，但前者是更少、更值钱的瞬间。2-5 是唯一用到它的关卡（没有产出植物、天上也不掉）。

阳光的亮度是**分层**问题，两层修法各管一半：它的动画是三层叠加——一个很小的亮核心（36px）加两圈更大的半透明光晕（79/116px），所以放大后看着"又亮又没有实体"。

- **颜色归资源自己**：`ResourceDef.tint`（`data/pvzce/resources/sun.json` 的 `"tint": [0.58, 0.50, 0.15]`；缺省是 `DropTint.DEFAULT` 的 0.5 灰）。阳光的两圈光晕本身偏白（B 通道高到 180），加在饱和黄色的核心上就是"加白"，所以那份暖色乘色是让核心的黄色透出来的那一半。它挂在资源上而不是做成一刀切：金币要原来的灰，阳光要黄，`EntityVisuals.dropTint(defId)` 只负责查表。
- **强度归光晕自己的 alpha**：转换器 `EntityConfig.additive_alpha_scale`（`tools/reanim_to_pvzce_all.py` 里 sun 那份配置写 0.7）把叠加层的 alpha 按比例压进 `animations/resource/sun.json` 的 `alpha` 关键帧。加法混合是"越叠越亮"，三层满 alpha 必然糊成一团白；压到七成既保留光晕的形状，又不再盖掉核心。

**掉落物的大小与形状只有一处可改**：`EntityVisuals.DROP` 给出掉落物的默认大小（0.8 格，宽高同一个值），**单个内容还可以用自己的 `render_scale` 覆盖它**（见下）。阳光、银币、金币的动画都按同一个倍率缩放，影子不再被单独拉宽，所以画成圆的阳光在草坪上就是圆的。下落时长 300 tick。

**爆炸闪光会膨胀**：`pvzce:pow`（灰烬类与 Boss 落地的爆炸）声明了 `scale_curve`，画出来的边长从 0.04 格长到 0.1 格（`scale` 0.2 × 曲线 0.2→0.5，曲线本身是绝对尺寸，与原版 `ParticleScale` 同单位）。
原版 `Pow.xml` 的 `ParticleScale` 是 `.2 .5,7`——一个范围加一个曲线类型，而转换器把三个数字读成了
(value, time) 关键帧，于是整条增长被压平成"全程 0.2 格"，爆炸看起来只有一个很小的贴图。
引擎一直支持 `scale_curve`，少的是那份数据；`[a b]` 形式的范围现在由转换器读成直线，
带时间/曲线类型的（`,7`、`,60 0`）仍保持常数——**手写**这类曲线是唯一的办法，`pvzce:pow` 就是手写的。
`ParticleDefinitionTest.theExplosionFlashGrowsOverItsLife` 钉住它。

**实体渲染缩放（`render_scale`）**：`PlantDef` / `ZombieDef` / `ProjectileDef` / `ResourceDef` 都能声明 `render_scale`（`ContentDefs.RENDER_SCALE_CODEC`，默认 1，夹在 0.05~8），客户端据此把该内容的art 整体放大或缩小，**两个轴同倍率，所以形状不变**。它是纯表现：不参与命中盒、收集半径或任何服务端模拟，因此**不进包、不占 `PROTOCOL_VERSION`** —— 客户端本来就会加载同一份数据包，两侧各自从定义里读同一个数。取值只在 `EntityArt.renderScale` 一处解析（动画路径 `AnimationManager.scalesFor`、无动画时的贴图兜底、以及影子 `InGameScreen.drawShadow` 都调它）。阳光用 `render_scale: 2.2`；它的三层光晕在 `animations/resource/sun.json` 里按模型自己的尺寸叠（核心 0.14 格、中圈 0.30、外圈 0.46，外圈约 3.2 倍于核心），这样放大的是整颗太阳而不是只有中心，两圈光晕各自声明 `"blend": "add"`。

### 4.7.4 波次节奏：每波自己的出怪间隔

**冒险关的这张表不是手写的，是原版四张表的复算**：1-1～5-9 的 `waves` 由 `tools/original_levels.py`（`gZombieWaves` / `gZombieDefs` / `gZombieAllowedLevels` / `Board::PickZombieWaves`）掷一次定死、`tools/write_adventure_levels.py` 写出。所以每波的 `delay` 是原版的 1800（首波；1-2 是 5000、mini-boss 章节末关是 100、其它传送带关是**本项目自己的 600**）/ 2500+随机 0~600 / 旗帜波之后 4500，旗帜波带 750 tick 预警，`spawn_interval` 统一取下限 15（原版把一波一次性倒出来，这是最接近它的写法）。**要调手感就改生成器再重跑，不要手改关卡 JSON**：`OriginalAdventureLevelsTest` 校验整条冒险；用户指定的 5-10 使用 5-9 敌人池和 mini-boss 预算，替代原版僵王战（见 §4.17）。

`spawn_interval`（tick，可缺省）写在**每一波**上，不是关卡上，也不是全局常量：简单关卡的第一波 8 秒一只、最后一波 6 秒一只；困难关卡最后一波 2.5 秒一只。缺省 300 tick（5 秒），**下限 15 tick**（`WaveDef.spawnInterval()`）。
「把前期的节奏放慢」与「最终波多快」必须分开。

**整条出怪时间线可以被关卡整体加速**：规则 `pvzce:zombie_spawn_speed_multiplier`（缺省 1；今天只有无尽与变异声明它，内置冒险关均不写）把**波与波之间的 `delay`** 与**一波之内逐个出怪的 `spawn_interval`** 同时除以它 —— 同一个倍数读两处（`WaveDirector.effectiveWaveDelay` 与 `effectiveSpawnInterval`），所以"加快出怪"不可能只快一半。它与 `zombie_speed_multiplier`（已经在场上的僵尸走多快）是两件事：前者是"下一只多快出现"，后者是"已经出现的那只多快走"。`warning_ticks` 不缩放（横幅的提前量是给玩家看的，不是出怪节奏本身）；缩放的 `spawn_interval` 仍受 15 tick 下限约束（那一条是"一波不是一次性倒出来"，缩放之后依然成立）。**它存在的理由**是"不想重写整张波次表就调快节奏"；1-10 / 2-10 曾经用它当 mini-boss 的密度替代，现在密度由波次表自己带（原版 `IsMiniBossLevel` 把每波点数 ×3），所以冒险关不再需要这个旋钮。

**节奏关卡的谱面是关卡数据、分数是服务端算的**（`pvzce:rhythm` + `RhythmMechanic`）。谱面的时钟
**从准备阶段结束那一刻起算**（`State.startTick`），所以摆阵期间不会有音符被判漏；**歌也在这一刻起**
（`MusicCue.Trigger.WAVES_START`，`LevelServer` 在 `beginWaves()` 记下 `wavesStartTick`，两组 cue
各按自己的基准判 due），两个 fade 都写 0 —— 淡入就是一个不等于 cue 时刻的起始时刻。**这个起点会
下发给客户端**（`RhythmMechanic.Status` 经 `MechanicSyncS2C`，锚定时一次、之后每 6 tick 一次、读档后再一次）：
客户端的镜像里"准备阶段结束"比服务端晚，自己猜会差一整个摆阵期，而差值一过窗口（12 tick）
**每一个按键包都会被拒**——判定客户端算的前提是两边数同一件事。客户端发来
`RhythmHitC2S`（哪一条 lane、哪个音符、它自己算的偏差），服务端回答四件事：这条 lane 存在吗、
谱面上真有这个 tick 吗、算过没有、离现在远不远；算上了就按两边**较好的那个距离**记
PERFECT / GOOD / FAIR（`RhythmChartData.gradeOf`，窗口是飞行行程的 5% / 10% / 15%），
PERFECT 从那一列的一株植物身上 `spawnProducedResource(SUN, perfect_sun)` 掉一颗真阳光
（关卡固定带 `pvzce:auto_collect`，所以 0.25 秒后被拾取；那一列没有植物就不掉）。
**命中的音符是给植物的命令**：`RhythmChartData.volleys(grade)`（PERFECT = `attack_volleys`，
GOOD / FAIR 由它推出 2/3、1/3，MISS = 0），`RhythmMechanic` 对该列（或行）的每一株植物
`queueStrikes(n)`，植物每 4 tick 打一次自己的攻击（**一轮要打完整**：连发类植物的后几发与大嘴花的咀嚼属于「已经许诺出去的活」，由 `PlantCapability.hasPendingWork`/`tickPending` 在停火状态下继续推进）。这一关的植物**平时不开火**：
`plants_hold_fire`（默认 true）→ `LevelServer.plantsHoldFire()` → `PlantEntity.tick` 跳过
`PlantCapability.holdsFire()` 的能力（射手 / 投手 / 近战 / 喷菇 / 地刺），
所以"不按键就没有输出"是一条机制，而不是数值。走到 `end_beat`（歌的最后一个小节）时先
`sweepLawn()`（残敌即死、不付阳光金币）再 `declareVictory()`：这一关的胜负是"活到歌尾"，
漏音符只进结算统计（`RhythmMechanic.Score` 的 perfect/good/fair/missed 一并进存档）。
有谱面的关卡 `forbidsSpeedChange()`：2x 不会让音符变快，只会把玩家的反应时间砍半。

**这些关卡的僵尸不再写在关卡里，而是算出来的**（用户要求："不要有波数了，无限出僵尸，过关条件必须
是完成铺面，关卡只需要设置一个难度系数"）。`RhythmChartData.difficulty` 是那条唯一的话，**默认 0
= 关**（手写谱面照旧用自己关卡的波表）：正数才打开模式自己的僵尸时钟，池子 / 解锁 / 数量 / 间隔 /
血量成长全部自动算。**"轮"在节奏关卡里是"歌里的位置"**（`RhythmWaves.roundFor`：
`1 + 谱面进度 × 调度表的 count_ramp_rounds × 系数`），所以系数 1 表示整首歌把调度表走一遍、2.2 表示
走两遍还多；谱面时钟只往前走，**轮数单调，池子只会更强**。生成器是无尽那一个（`EndlessWaves.wave`），
连"水行只放会水的"这条行安全都是白拿的；调度表是共享的 `EndlessSchedules.rhythmLawn()`
（id `pvzce:rhythm_lawn`，普通僵尸开场，逐段解锁到橄榄 / 门板；没有巨人——键盘回答不了的墙——
也没有矿工与气球，那是判定线盖不到的层）。四档的系数是 `RhythmCharts.TIER_DIFFICULTY`
（0.6 / 1.0 / 1.5 / 2.2），`zombie_speed_multiplier` 与 `zombie_spawn_speed_multiplier` 仍各说各的
（僵尸走多快、来得多密，与"来的是什么"无关）。**没有波表也没有波数**：`waves: []`，
`Host.showsWaveCount()` 对这类关卡答 false → `WaveProgressS2C.totalWaves` 与 `LevelServer.totalWaves()`
都是 0 → 右下角那条进度条整条不画；**大波横幅保留**（预警走 `warningActive` 而不是总数，而
`WaveWarningFinal` 需要 `WaveType.FINAL`，生成器只发 HUGE/SMALL，所以永远不会误报"最后一波"）。
回合滚动是静默的（`tickRoundClear` 对这类关卡直接 `beginNextRound(bridge, false)`：歌中间没有选卡，
也不发"第 N 轮开始"）。**赢法只有一条**：走到 `end_beat` 清场判胜——波次导演在"波是生成的"关卡上从不
自行判胜。校验因此加两条：带系数的谱面**必须写 `end_beat`**（否则是一局只能输的关卡），
**也不能再写波表**（两个答案，一个会输）。选卡页的僵尸预览对它也成立：`payloadFor` 的
`previewZombies` 读不到关卡自己的表时问生成器要"开场那一波"（`RhythmWaves.preview` /
`EndlessMechanic.previewWaves`），所以无尽关卡也一并有了预览。

**这条消息还带走了整份"战况"**：`Status(tick, energy, perfect, good, fair, missed, combo,
bestCombo, streak, multiplier, jalapenos)` —— 一个机制只有一种载荷（`MechanicSyncS2C` 只按机制 id
分发），所以锚点和能量条不能各发一条。**HUD 上"这局打得怎么样"的每一个数字都取这条消息**，
客户端的本地计数只用来当帧回答按键（判定字、那一列的闪光）；两个理由都是胶片给的：
两边对同一次按键盘**按设计**可能给出不同的判定（服务端取两个时钟里更好的那个），并排画出来就是
`PERFECT 0 · 连续 PERFECT ×1` 这种自相矛盾；而续档之后客户端的计数从 0 重来，服务端的没有。

**能量条与连续 PERFECT 是节奏模式的第二条经济**（数值全在 `PvzceConstants`）：
PERFECT +100 / GOOD +50 / FAIR +20 / 漏掉一个音符 -10，并且**每秒 -5**（按 tick 小数累加，
5/秒就是每 tick 1/12 点）；上下限 0 与 `ENERGY_MAX`(15000)，两档在 `ENERGY_DOUBLE_AT`(6000)
与 `ENERGY_TRIPLE_AT`(12000) —— 上限必须高于最高那一档，否则那一档是个够不着的数。建造阶段不涨不减（谱面还没开始），
暂停时 `gameState` 不是 RUNNING，同样停。**条子的两档买的是子弹数**：≥`ENERGY_DOUBLE_AT`(6000)
时每株植物的每次攻击 ×2，≥`ENERGY_TRIPLE_AT`(12000) 时 ×3。这个倍率经
`LevelAccess.projectileCountMultiplier(plant)`（`sporeRangeMultiplier` 的邻居，`LevelServer`
覆写为读本机制）落到射手 `ShooterCapability.fire` 的三处 `shot.count()`、投手
`ThrowerCapability.lob`（没有 burst 字段，借射手的 `MULTIPLIED_BURST_DELAY`=6 tick 间隔，并带一个
`PendingLob` 队列，否则 hold-fire 关卡会把余下的抛射吞掉）与玉米加农炮的 `launchAimedProjectile`；
僵尸的豌豆走 `spawnZombieProjectile`，不乘。**叠加关系**：PERFECT 的 `attack_volleys`(3) 次齐射
× ≥5000 的 3 发 = 9 发。

**一首歌是一条记录，不是一组常量**（`RhythmCharts.Song`：music / bpm / offsetTicks / firstBeat /
endBeat / onsets + 关卡 id 与名字的前缀）。`SONGS` 现在两首——终极之战（110.00 BPM / 第 0 拍 14 tick /
340 拍，前缀 `rhythm`）与小游戏（94.00 BPM / 第 0 拍 17 tick / 295.75 拍，前缀 `minigame`），
两者的分析都由 `tools/rhythm_onsets.py` 从文件量出。**一首歌 = 四张关卡**（四档难度系数 0.6/1.0/1.5/2.2），
每首歌一个集合，并排在节奏草坪页。编辑器的曲目字段认歌：命中哪首就用哪首的 tempo / 拍格 / 收尾。

**连续 PERFECT 到 30 / 50 / 80 / 100（之后每 +20）就在每一行放一个火爆辣椒**
（`PERFECT_STREAK_MILESTONES` / `PERFECT_STREAK_STEP` / `nextStreakReward`）。计数是**严格的
连续 PERFECT**：GOOD、FAIR、漏音符都清零（`combo` 是另一个更老的计数器，任何计上的音符都加）。
放辣椒**不在 `judge` 里发**，而是 `judge` 只把 `state.pendingJalapenos` 加一、`tick` 里
`release()` 才点火：`LevelServer.emitEffect` 在 `bridge == null` 时是空操作，而按键包是在
`level.tick` **之前**处理的 —— 在包处理期放火，五道火龙既没有画面也没有声音。
一行的爆炸是 `ExplosiveCapability.fireRow(level, row, damage, damageType, meltsIce, sound, team)`
（从 `detonate` 的 ROW 分支抽出来的同一处几何：行伤害 + 融冰 + 每格一道 `JALAPENO_FIRE`），
伤害 / 伤害类型 / 是否融冰 / 音效全部**从辣椒的植物定义读**（`PvzceIds.JALAPENO`），
所以数据包改了辣椒，奖励跟着改。

**一局打完有一份战报**（`GameStateS2C.RhythmScore`，随"这局结束了"那条包一起发）：
四项判定 + 最高连击 + **最高连续 PERFECT**（`State.bestPerfectStreak`，新记的统计量，因为它才是辣椒的
那个"差多少"；连击本身在任何有一发 GOOD 的局里最后都是 0）+ 辣椒次数，外加一个 `played` 标志
（"这关没有谱面"与"有谱面但一个音符都没判到"是两件事）。**在关卡结束的那一刻读**，而不是复用 HUD 那条
每 6 tick 一次的流——那一条在歌尾会差最后几个音符。协议 47。

**关卡集合是 level 注册表上的 tag**（`LevelCollections`）。名字在语言文件里
（`level_collection.<ns>.<去掉 collections/ 前缀的路径>`，客户端 `LevelPage.collectionLabel` 解析），
**页、图标、排序键都取自它的第一个成员**：`#pvzce:collections/day_lawn` 的第一个成员是
`yard/adventure/1_1`，于是这个盒子出现在冒险页、用 1-1 的图标、并且在 1-1 该在的位置上排序 ——
一套元数据都不用手写，四个章节自然按 1-1/2-1/3-1/4-1 排。成员顺序 = tag 文件里的顺序
（`RegistryTagView.orderedIds`；`TagSet` 内部是 LinkedHashSet，只有视图那层用 `Set.copyOf`
丢过顺序），所以变异是 easy/normal/hard/hell/tutorial 而不是字典序。**成员照旧下发**
（集合页要画它们的锁、存档与奖杯），只是在 `LevelListS2C.LevelInfo` 上多带一个 `collectionId`，
页面的 `LevelPage.rowsFor` 把带它的行滤掉 —— 一个关卡在页面上只出现一次。盒子自己是一行
`LevelInfo`（`collection` 字段非空、`payload` 为空），`sendLevelList` 把两种行按各自的排序键
合到一条有序表里再下发；"按排序键索引的 Map"曾经把盒子那一行覆盖掉（集合的排序键就是第一个
成员的 id），修法是成对收集后再排序。

**列表行的图标规则在 `LevelIcons`**（原来它是 `PvzceServer` 的私有方法）：场景里有 `roof` 就是
屋顶、有 `water` 且 `night_length > 0` 就是夜晚泳池，否则 day / night / pool —— 集合也用它，
所以"一个泳池关长什么样"只有一个答案。

**准备阶段一律没有卡片冷却**（`LevelServer.effectiveCooldownTicks`：`isPreparing()` 时直接返回 0）。
这是唯一的换算点（牌堆、传送带、工具都走它，卡槽条的充能也读它），所以一处就够；
它同时是关卡的规则（`pvzce:seed_cooldown_multiplier`，`<= 0` 即"整关无冷却"，节奏草坪就是 0）。
理由写在那个方法里：准备阶段是"拿给定的一笔阳光摆阵"，一张要等的卡是**没有关卡在背后的等待**。

**玩家坐哪一边是关卡数据说的**（`LevelDef.humanTeam()`，空 = 植物方）。我是僵尸的五关把
`playable_teams` 写成僵尸方，于是 `LevelServer` 把玩家落在那一队、初始阳光发给那一队，
`markEnd` 也按"赢家是不是玩家这一队"给 `WON`/`LOST`。两边的动作各有一条放置路径：
`placePlant`（要求玩家在植物方）与 `placeZombie`（要求玩家在僵尸方，卡是 `Slot.Kind.ZOMBIE`）。
解谜关的草坪由 `pvzce:plant_garden` 摆（手写 `initial_entities` 或一轮一轮随机），
"吃完一片换下一片"就是它的整个规则。

**`pvzce:wave_pacing` 决定这张表怎么跑**（数据 `WavePacingData`，机制与 deck / mower 一样有隐式默认，所以不声明也有节奏）。默认的**清场奖励**：场上无僵尸且上一波放完时，倒计时按 `clear_reward_factor`（默认 3）加速，但**前段不加速** —— `clear_reward_grace_ticks`（默认 10 秒）整段照付，只有它之后的余量被压缩。四种模式按**波次编号（1 开始）**选择：`fixed`（照表）、`stockpile`（场上本波僵尸不足 `max_alive` 时按差额缩短间隔，到上限停手）、`survival_ratio`（本波放完后死亡达到 `kill_ratio` 就让下一波每 tick 多跑一拍）、`budget`（按点数在 `pool` 里随机组合）。每波倒计时的目标在开始那一 tick **冻结**（`nextWaveTargetTicks`），`due` 还要求 `waveIntervalTicks > 0` —— 少了任何一条，冻结在 0 的计数器都会被读成"到期"，关卡会在第一波之后连发。开局两波的死亡门每次超时按 `early_kill_delay_factor`（默认 0.75，下限 1 秒）收紧。

**等待的边界是"等待 + 1 拍"**：`ticksUntilNext` 在装填的下一拍才减、减到 0 出怪，所以 300 的 `spawn_interval` 是每 301 拍一只、1200 的死亡门是 1201 拍。所有波次表的 `delay` 都按这条契约写。

**节奏有度量**：`WavePacingMetricsTest` 对每张已发布关卡跑三档击杀速度，输出总时长 / 最长空场 / 空场占比 / 并发峰值（`-Ppvzce.smoke=pvzce.pacingReport=true`），默认只断言最慢档能通关。改关卡节奏前先看它。

**`delay` 是两波之间的间隔，从上一波触发那一 tick 起算**，而上一波还在放怪时这个计数器**冻结**
（`WaveDirector.tick` 里 `currentWaveStillReleasing()` 为真就不推进 `waveIntervalTicks`），只有第一波例外。两半都是必须的：

- **从触发起算**：这是所有波次表写 `delay` 时用的口径 —— 原版 `Board::UpdateZombieSpawning` 在放出一波的那一拍就把下一波的倒计时重置成 2500+rand(600)，出怪窗口跑在间隔**里面**。反过来（从"放完"起算）会把每一波的出怪窗口再收一遍费：20~30 只的大波要放 4.7~6.5 秒，玩家体感就是"这波清完了还要干等半天"。这条曾经写成"必须从放完起算"，理由是"否则两波一起出" —— 那其实只需要下面那一半，见 `docs/架构变更记录.md`。
- **放怪期间冻结**：从触发起算时，上一波的队列还在跑、下一波的倒计时就跑到头了，两波的队列于是同时放怪 —— 关卡把前几波写成 10 秒一只，玩家看到的却是两波混在一起的 4~6 秒，这就是 1-2 / 1-3「僵尸一起出」的来源。

净效果是 `出怪窗口 + max(delay - 出怪窗口, 0)`：永远不混波，等待也不会超过作者写的 `delay` 加上他自己那一波的出怪时间。写数据时 `(数量-1) × 间隔 ≤ 下一波 delay` 仍然是个好习惯（让一波放完再喘一口气），但**违反它不会让两波混在一起**：后果只是"上一波刚放完，下一波立刻就来"。回归用例在 `WaveDelayOriginTest`（`WaveSystemTest.theNextWaveWaitsForThePreviousOneToFinishReleasing` 钉住不混波那一半）。

**波间倒计时可以被"本波被打残"直接砍到 200 拍**（`WaveDirector.healthDrainApplies`，原版 `Board::UpdateZombieSpawning` 的
`mZombieHealthToNextWave`）：开波时掷一次"本波已放出的血量 × 50%~65%"当线，场上该波剩余血量（身体 + 护甲，
`TotalZombiesHealthInWave` 的两个分量）掉到线下就把目标压到 `HEALTH_DRAIN_TICKS`（200 拍 ≈ 3.3 秒）。
这是**原版节奏的骨架**，不是可选优化：那张表的 `delay`（2500~3100、旗帜波后 4500）是"玩家没打赢"时的节奏，
原版靠这条把打赢时的等待压成三秒，本项目此前没有它 —— 于是"清完场还要干等十几秒"。

- 线是**这一波**的，不是整片草坪的（`TotalZombiesHealthInWave(mCurrentWave - 1)`）：补货型的波从后面补上来时不能把下一波扣住。
- 线读的是这一波**已经放出来**的血量，所以是**倒计时开始那一拍**掷的（`rollHealthDrainTarget`），不是波触发那一拍：
  波触发与它上一波最后一个僵尸的出生在同一拍里，触发时掷会掷到 0。
- 它只会把目标**往前压**（`Math.min(当前目标, 计数器 + 200)`）：本项目这个计数器是往上数的，原版那句"还剩 200 拍"
  翻译过来就是"从现在起再数 200 拍"，写成"每拍重新定一次终点"会让倒计时永远到不了。
- **关卡可以关掉它**：`pvzce:wave_pacing` 的 `"health_drain": false`（缺省 true）。变异教程那种"剧本才是重点"的关卡需要它，
  否则玩家把每波秒清就会在最后一个剧本事件之前把关卡打完。`WavePacingData.clearRewardOff()` 也会一并关掉它（同一个承诺：
  "倒计时可以被砍短"）。

**开局两波：没写 `spawn_interval` 的 `small` 波不看自己的间隔，看玩家什么时候把上一只打死**：
`WaveDef.holdUntilDead(waveIndex)` 给出这一波要等上一只僵尸多久，实现点在 `LevelServer` 的两处门：

| 门 | 规则 |
|---|---|
| 波内（`PendingWaveSpawn`） | 上一只**一死就出下一只**；`1200` tick（20 秒）还没死就照出，不拖住关卡。这个等待**取代**缺省的 300 tick 间隔，不是叠加 |
| 波间（`openingWaveStillOnTheField`） | 倒计时**照常走**（清得早不会白等），只把**已经到点的到达**扣住，等场上清空；同样 20 秒封顶。被扣住时大波横幅继续挂着，所以大波不会在横幅熄灭之后才静悄悄地来 |

**约束：延迟照常跑，只扣住"到达"，不要冻结倒计时。** 冻结倒计时会让玩家把场上清干净之后还要再空等一整个
`delay`（大波前最明显）。现在：玩家清得快 = 完全按关卡节奏，清得慢 = 该到的那一波等到清完（≤20 秒）立刻来。

- **`spawn_interval` 写了就退出这套门控**（`WaveDef.declaresSpawnInterval()`）：门控回答的是"这一波该多快"，
  而写了间隔的波已经自己回答了。不这么办的话门控会把那个数字整个换掉 —— 1-5 的第二只路障写着
  `"spawn_interval": 15` 却是第 50 秒才出来的，就是这么来的；内置冒险模式每一波都写着 15，所以每一关的开局
  都变成了"每只等 20 秒"。想按自己写的间隔出怪，写出 `spawn_interval` 即可。
- **默认只对每一关的前 2 波（`WaveDef.EARLY_WAVE_COUNT`）且必须是 `small` 波**生效：一次 9~12 只的 huge/final 是"这一关把家底全掏出来"，一只一只等会把两分钟的波拉成二十分钟。
- 三态字段 `hold_until_dead`：**缺省**＝按上面的默认规则；**写 0**＝完全不门控；**写正数**＝换成那个封顶值，写了 `spawn_interval` 也照样门控。写 0 与不写在数据里是两件事，所以字段是 `Optional<Integer>`（与 `mower.rows` 同一个理由）。
- 门控是**滚动**的：第 2 只等第 1 只、第 3 只等第 2 只；超时放行之后，下一只只看它前面那一只。
- 两个门与队列的等待状态都进存档（`OpeningGate*` / `HoldTicks` / `TicksUntilNext`），所以读档续上的开局不会突然变回旧节奏。**唯独"正在等哪一只"不存**：实体 id 出自进程内的计数器（`Entity.NEXT_ID`），存下来的数字在下一个进程里可能指向另一只僵尸；读档后的队列改按封顶值走，直到它再放出一只可以跟的僵尸为止。
- `spawn_interval` 本身也是三态的（`Optional<Integer>`）：**不写**＝缺省 300 tick 且吃开局门控，**写 300**＝就是 300 且不门控。这个区别只有门控读它，出怪间隔本身两者一样。

**每一个出怪条目可以点名自己走哪几行**（`WaveDef.Entry.rows`，不写＝任意行）：`WaveDirector` 把条目自己的行列表抄进放怪队列的每一项（`QueuedZombie`），出怪时在它列的行里按顺序轮取（`rowFor`）；没有列表的条目照旧用队列开局洗过的那份全场行序（`shuffledRows`）。这是泳池"两行水、四行草"所必需的：会游泳的救生圈僵尸只该落在水里、走路的只该落在草坪上 —— 写错一边就是陆地僵尸淹死在水池里，或者救生圈在草坪上划船。行列表与僵尸 id **平行**进存档（队列里多了 `ZombieRows` 键，紧挨着 `Zombies`；队列自己那份洗好的行序仍是 `Rows`），**没有这个键的存档读回来是"任意行"**，所以老存档续档的节奏一个字节不变。校验在 `LevelValidator.validateWaves`（见 §4.2）。

### 4.7.5 大波提示的生命周期

`waveWarningActive` 只在 `tick()` 里被清除，所以**任何让关卡停止 tick 的结束都必须自己清它**。`markEnd` 会一并清掉提示与进度，判据里写着 `remaining > 0`（`nextWaveDelayTicks` 在最后一波释放后是 `-1` 这个哨兵值），两条都有回归用例分别钉住。

**公告在存档恢复后不会重播**：`announcedWaves` 不是存档字段，所以 `restore()` 会按 `NextWaveIndex` 把它重新填满 —— 索引之前的波次都已经进场过，也就都已经宣告过，`triggerWave` 因此看不到空的已宣告集合。客户端另有一道保险（`InGameScreen.playEffectSound`）：同一个关卡实例内，`awooga` / `hugewave` 在 90 秒内只会真的播一次，其余服务端路径重复发也不会再响；呻吟之类该重复的音效不受影响。

**公告本身由 `announcedWaves` 集合保证每个波次索引只播一次**：`triggerWave` 是唯一发射点、且会推进索引，所以干净的一局本来就只播一次——但那是"碰巧"而不是保证，从存档中途恢复或将来有人直接调用 `triggerWave` 都可能让警报响第二遍。

**大波音效属于"预警"，不属于"到达"**：`hugewave`（原版 Dave 那句 "A huge wave of zombies is approaching!"）由 `updateWaveWarning` 在预警窗口**开启的那一 tick**发出（`announceWaveWarning`，按波次索引去重），与屏幕上那行红字同一拍淡入。它不能等到**波次到达**时才响：那时红字已经淡出，玩家会先读到"一大波正在接近"、几秒后才听见同一句话。final 波到达时照旧只放 `awooga` + `FINAL WAVE` 横幅，两者本来就是同一拍。**没有预警窗口的大波**（`warning_ticks` 为 0）会退回"到达时播一次"，两种路径互斥——预警已经宣告过的索引不会再在 `triggerWave` 里补一次。

### 4.8 关卡解锁条件

**关卡可以声明自己需要什么**：

```jsonc
// data/pvzce/levels/yard/adventure/1_2.json
"unlock": {
  "requires": [
    { "type": "level", "id": "pvzce:yard/adventure/1_1" },  // 通关该关
    { "type": "card",  "id": "pvzce:sunflower" },           // 已解锁该卡
    { "type": "coins", "amount": 500 }                      // 持有金币
  ],
  "cost": 1000,      // 可选：花这笔金币一次性买下本关
  "hidden": false    // true = 未解锁时整行不出现（隐藏关）
}
```

- **默认不上锁**：没写 `unlock` 块的关卡永远可玩，所以既有自定义关卡、数据包、编辑器新建的关卡全部不受影响。`LevelDef.unlock()` 缺省是 `LevelUnlock.NONE`。
- 规则实现是 `common/core/` 的 **`LevelUnlocks`（纯函数）**，与 `LevelGrouping` 同一层、同一纪律：读一个 `Context{已通关集合, 已购买集合, ownsCard 谓词, 金币, 沙盒}`，产出 `State{unlocked, buyable, cost, unmet, reason, hidden}`。服务端求值、客户端**接收结论**（`UnlockInfo` 随 `LevelInfo` 下发），所以两侧不可能对"这关开没开"有不同看法。
- **门槛是服务端的**：`createLevel` 在任何东西被拆掉之前重新求值一次并拒绝（"关卡 X 尚未解锁：通关 1_1"）。菜单只是把这个结论画出来；跳过菜单的客户端也走不进去。
- **购买是一次性的**：`UnlockLevelC2S(levelId, worldName)` 只说要买哪一关，价格由服务端从关卡定义读，钱包从档案读 —— 改过的客户端只能选择买哪关，不能选择花多少。买下后写进 `PlayerProfile.UnlockedLevels`（与 `Unlocked` **分开存**：关卡 id 与卡 id 长得很像，混在一起会让一次买关变成解锁一张卡）。包必须带世界名：购买是按世界的，而菜单期间没有正在运行的关卡。
- **金币门槛与买断是两件事**：`coins` 条件查余额（花到别处就可能重新锁上），`cost` 是花掉并永久记下。两者都支持。
- **循环会被点出来**：`LevelUnlocks.findCycles` 在加载时报告互相等待的关卡链 —— 那种关卡永远进不去，而运行中的游戏不会说为什么。
- 操作入口：`/profile info | unlock <关卡> | unlockall`。`/profile unlock` 是把某关标记为已购买（不收费），用于冒烟、测试与被链条挡住的演示关。
- 编辑器有独立的 **「解锁」页**：前置关卡、所需卡（两个逗号分隔输入框）、金币价、隐藏关开关，**边输边校验**（未知关卡 / 未知卡 / 自己作为自己的前置当场标红），保存时整块写出；页面上放不下的条件类型（如 `coins`）会被**原样保留**，不会因为"编辑了一下"被删掉。
- 内置冒险模式：1-2 需通关 1-1，1-3 需通关 1-2，1-4 需前三关（并示范 `cost: 500` 的金币买断）。

**关卡分类的兜底在客户端**：未分类页是**固定页**（`LevelPage.tabs` 永远补上它，客户端左侧列因此永远有"未分类"按钮）
——服务端只下发有内容的页，空页由客户端补齐。`LevelValidator` 尚未校验"关卡 id 的两段像主题/类别但未注册"
（目前只有 `PvzceServer.validateLevelGroups` 在重载时记日志）。

### 4.9 小游戏关卡（传送带 / 放置区 / 保龄球）

**原创关卡「回声温室」**（`pvzce:yard/minigame/echo_conservatory`）直接开放，固定八张卡组借给新档回声铃兰与共鸣苔，普通成本与冷却仍走 `placePlant`；首通解锁铃兰，共鸣苔在首通与重玩奖励中均可解锁到普通选卡池。预置的相邻铃兰与教程提示用于展示连接，关卡波表、初始阳光与奖励都只在这份关卡 JSON 中定义。

**移动共鸣行**（`pvzce:resonance`，`ResonanceData` / `ResonanceMechanic`）把运行时钟放在每个 `LevelServer` 的机制状态里：当前行由起始行与时钟推导，周期上移、到顶循环。每 tick 扫描与此行相交的铃兰或共鸣苔节点，按 `EchoNetwork` 拓扑激活整个网络，同组去重；`plant_rate` 是本 tick 激活的倍率上限，实际加速随网络中的铃兰数量变化，承载在苔上的植物也分享攻击与阳光生产加速；不发独立的额外声波，离行或断开后不再续授倍率。该行敌方地面僵尸的速度由 `LevelMechanic.zombieSpeedMultiplier` 经 `LevelAccess` 乘进已有难度与减速计算，离行即时恢复。时钟进入关卡存档；当前行、下一行与剩余 tick 共用 `ResonanceMechanic.Status` 的包编解码。`LevelMechanic.sendState` 由 `LevelServer.sendFullState` 调用，暂停进场与续档也能立刻收到当前状态；运行同步仍走 `MechanicSyncS2C`。机制编辑器提供换行间隔、起始行、僵尸倍率与网络加速上限，缺省值由 `PvzceConstants` 提供。旧数据里的 `pulse_ticks` / `damage` 不再参与机制。

1-5「坚果保龄球」是第一种**结构与普通关不同**的关卡，三件事都是关卡数据：

```jsonc
// data/pvzce/levels/yard/adventure/1_5.json
"slots": [],                       // 卡组不是"关卡固定的几张"，而是"没有卡组"
"initial_sun": 0,
```

**传送带（`conveyor`）**

- 服务端 `ConveyorBelt`（`server/level/`）持有队列与时钟：每 `interval_ticks` 从加权池里抽一张，`capacity` 满则**停止出货**（原版行为：囤卡要付代价），`initial_cards` 是开局就在带上的张数。
- **带上的卡就是玩家的卡槽**：`plantPlayer.slots()` 是传送带的投影，`BeltCardSource.rebuildBar` 在每次变化后按带上的顺序重建，`placePlantInternal` 里种下一张就是 `belt.take(id)`——**不扣阳光、不进冷却**。
- **每张卡有一个永不复用的 id，位置不是身份**：带上的位置每消耗一张就整体前移，若客户端点的是"第 2 格"，一次竞态就会种出另一张卡。`SlotInfo.index` 因此是卡自己的 id，`PvzcePlayer.slot(int)` 按 `Slot.index()` 查（普通卡组里两者本来就是同一个值），过期的点击会**指名一张已经不在带上的卡**并被拒绝，而不是种错东西。
- **同步用整表替换而不是增量**：`MechanicSyncS2C`（带 `pvzce:conveyor` 机制 id，载荷是整张 `BarState`；`PROTOCOL_VERSION` 因此 = 18）。`SlotSyncS2C` 是按 index upsert，**说不出"没了"**——被用掉的卡会一直留在客户端的卡槽条上。传送带一次最多六张、几分钟才变一次，整表发最省心。`LevelInitS2C` 里的 `slots` 已经是带上的内容（`sendFullState` 与 `slotInfos()` 同源），所以进场不需要额外包。
- `LevelPayload` 因此多两个字段：`conveyor`（这张卡槽条是不是传送带）与 `beltCapacity`（UI 画多宽的带子）。两者都由服务端下发而不是客户端读本地数据包——带的**内容**本来就是服务端状态，客户端不该有第二份"这关是不是传送带"的判断。
- **存档**：带上的卡与下次出货倒计时写进 `level.dat` 的 `Belt` 块（`LevelServer.save/restore`）。恢复时先恢复带、再重建卡槽条，`restoreSlots` 于是能按 id 找回每张卡。
- **传送带关卡经过选卡界面，但那只是一次过场**：卡组由关卡自己发，所以选卡页对它们不画面板、不画卡池、也不收玩家的选择（判据是机制给的 `PvzceClient.dealsItsOwnCards(levelId)`，读本地关卡定义，与 `lockedSlotsFor` 同一层，客户端把它交给 `ChooseSeedsScreen` 的 `previewOnly`）；播完开场对话后它自己开始。**为什么不让它们直接进关**：选卡页的草坪预览 + 僵尸预览是列表之外唯一展示"这一关会来什么"的地方（细节见 `UI切换与导航架构.md` §4）。服务端 `createLevel` 对传送带关卡直接传空卡组，`SeedSelection.readSaved` 也不读——卡组就是带子。
- 美术是原版的 `ConveyorBelt.png`（胎面），从 `refer/im7/images/` 拷进 `textures/gui/hud/conveyor_belt.png`；它**铺满整个托盘**并持续向左滚动，卡片骑在上面（细节见 §6.2）。带子画在**屏幕顶部**（原版位置，且传送带关卡本来就没有阳光银行）。
- **带子只发植物，工具与资源留在托盘右侧**：`BeltCardSource.rebuildBar` 先按带上的顺序铺植物卡，再把 `plantPlayer` 原有的**非植物**卡（工具、资源）原样追加在后面。所以传送带关卡**可以、也应该在 `slots` 里写 `pvzce:shovel`** —— 那不是"第二份卡组"，而是"这个玩家身上有的工具"，与传送带变异保住铲子/浇水壶走的是同一条路径（`MutationManagerTest` 钉住）。校验器 `ConveyorMechanic.validate` 因此只拒绝**植物**卡（"带子发植物，列了也不会发"），工具与资源不受这条约束。
- **每张卡可以声明发多少张**（`cards[].max_count`，不写 = 不限）：原版 2-10 的墓碑破坏者是 **13 张**，因为那一关草坪上正好十三个墓碑，第十四张没有用处。计数由传送带自己记（`ConveyorBelt.dealt`，**发出就算**，用掉没用掉都算），发满的卡退出池子、其余权重重新归一；计数与队列一起进存档，续档不会把第十四张补发出来。这是全游戏唯一一处会发完的卡。
- **1-10 是第二个传送带关卡**，也是昼夜**会变**的那一关：池子是原版 Day 区的七种植物，4 秒一张、容量 6、开局 3 张，天上不掉阳光（传送带发的卡本来就免费），出怪速度 **×2**（`zombie_spawn_speed_multiplier: 2.0`：传送带发牌不变，僵尸来得快一倍）。规则 `day_length: 3600` + `night_length: 360000` = 一分钟白天、之后整局夜晚；对照 2-1 的 `day_length: 0` + 正数 `night_length` = **整关固定夜晚**（没有白天可回，见 `DayNightCycle.alwaysNight`，客户端第一帧就是暗的）。关卡细节见 §6.2.1。

**2-10 是第三个传送带关卡，也是夜晚的收尾**：池子是原版 Night 区的七种植物（小喷菇 10 / 大喷菇 15 / 墓碑破坏者 20（上限 13 张）/ 魅惑菇 10 / 胆小菇 15 / 寒冰菇 15 / 毁灭菇 15），4 秒一张、容量 6、开局 2 张，同样没有阳光经济，音乐与 1-10 一样是收尾关的 `music/ultimate_battle`，出怪速度与 1-10 一样是 `zombie_spawn_speed_multiplier: 2.0`（两张收尾关的波次表按两倍速播，而传送带的发牌速度不变 —— 这两个关卡的压力就是这么来的）；草坪上由 `grave_field` 撒 **13 个墓碑**，所以它既是一关"传送带给你什么就得用什么"，也是一关"清不清墓碑"的选择题。

**放置区（`placement_zone`）**

- 一个闭区间矩形，缺省的边就是棋盘边界（`{"min_x":0,"max_x":3}` 不必知道关卡多宽）。语义是"这一关的草坪只有这块能种"。
- **判定只有一处**：`LevelServer.canPlacePlant` 先查区域再查 `PlantPlacement`。玩家、手套、植物 AI 都走它；**故意不走的两条路是 `/spawn plant` 与关卡的 `initial_entities`**——那是关卡作者在摆东西，不是在玩。
- 客户端从 `LevelPayload` 拿到同一个矩形，画出**红线**（画在世界层，和服务器判定的是同一组数），悬停格子按"在不在区内"显示绿/红。红线画在普通草地上正是它必须是关卡数据而不是地形的原因：地形做的话，红线下面的草坪就得变成另一种地块。

**保龄球（`pvzce:bowl` 能力 + `pvzce:bowling_nut` 植物）**

- 新植物 `pvzce:bowling_nut` 复用坚果墙的美术与动画文件（`animations/plant/defense/bowling_nut.json`，只多一个绕自身中心旋转的 `roll` clip），卡面美术复用 `textures/gui/cards/wall_nut`，走新卡 `slots/bowling_nut.json`。**普通关卡的坚果墙完全不受影响**。
- 行为在 `BowlCapability`（`common/capability/plant/`）：种下即向右滚（`speed` 格/秒，出货 5），**永远向前**——撞到僵尸不会掉头，而是被撞进相邻车道（`ricochet`）；左右边界是出口（滚出右侧即消失），**上下边界是墙**，撞到会反弹。车道的选择偏向草坪中间（顶/底行必向内，中间行五五开）。
  > 保龄球的核心是**斜向弹开继续前进**、在密集的僵尸群里连撞：方向反转与"上下反弹"是两件事，混在一起就两种都做不对。
- **命中有自己的声音**：`BowlCapability.impactSound(hit)` / `impactPitch(hit)` 让连击里的每一跳在 `sfx/projectile/bowlingimpact` 与 `…impact2` 之间轮替，音高随连击微升。这不是装饰：`hitCooldown` 是 6 tick（100 ms），而 `SoundEngine` 会把 130 ms 内**同一个**事件的重复折叠掉，一个 id 会吃掉长连击里的大部分命中。这里原来写的是 `EFFECT_BONK` —— 那是木槌自己的声音（`LevelServer` 的锤子分支是全仓库另一个调用点）。
- **伤害走 `ZombieEntity.damageImpact`，不走 `damageBody`**：`damageBody` 是爆炸用的、按设计无视护甲，用它会让铁桶一击死。`damageImpact` 让护甲先吃伤害（`ZombieCapability.onImpact`，`ArmorCapability` 实现）。击数因此是**数值窗口**而不是特例：本项目"护甲吸收到碎为止、碎的那一下不穿透到身体"，所以一次伤害必须够打死 200 血、又不够打穿 370 路障，同时两次要够打穿 1100 铁桶——即 `[550, 1100]`，`DEFAULT_DAMAGE = 650` 落在这个区间里，得到普通 1 击 / 路障 2 击 / 铁桶 3 击。
  > `onImpact` 要**先找 front 再找 top**：路障/铁桶在本项目里是 `position: top`（帽子），而掷物按子弹层选槽位（地面子弹打 front），保龄球没有子弹可描述，若只查 front 就会一路打到身体——路障与铁桶都是一击死，上面那条数值窗口也就永远用不上。
- **滚动中的坚果不是"格子里的植物"**：`BowlCapability.occupiesCell` 返回 false，`plantAt` 跳过它，所以僵尸不会停下来啃、铲子铲不掉。滚动的坚果仍然被模拟、被绘制、能被打。
- **连击掉币**：第 N 次命中掉 (N-1) 枚币（第 2 只起），币种来自关卡 `rewards.coin_drop`（`LevelAccess.dropCoin`，与僵尸掉币同一个"关卡决定值多少"的入口），所以关卡不写奖励时不会凭空多出一种货币。
- 1-5 的波次是**11 波 116 只**（普通 / 旗帜 / 路障，后段少量铁桶），出怪间隔 30~60 tick、**波间隔 600 tick**，第一波 240 tick（4 秒）就开打，约 1 分 45 秒；僵尸**移速 ×1.5**（关卡规则 `pvzce:zombie_speed_multiplier`）。传送带因此是 **150 tick 一张**（原版 n-5 的节奏）。首通奖励解锁 `pvzce:potato_mine`，音乐是原版的 `pvzce:music/loon_boon`（n-5 传送带关的曲子）。
  > 这一关的节奏是"**1.5 倍频率、一半数量、1.5 倍移速**"：原版 n-5 的僵尸密度配上传送带是 5 秒一张卡，`(数量-1) × 出怪间隔` 会顶到波间隔，所以每一波都必须能在下一波到来之前放完，而 1.5 倍的移速把"一半数量"补回成同样的压迫感。
  > **它没有小推车**（`rows: []`），与原版一致：漏一只就是直接输——这正是这一关的难点，而不是待补的缺口（小推车本身已经实现，见下）。

**关卡自带的工具（`tool`）**

- **花瓶关不再声明它了**：4-5 原先靠一把 `default: true` 的锤子砸瓶，现在砸瓶是棋盘自己的规则（见下面的"空手点容器"），所以那一关没有木槌光标、没有价格也没有冷却。
- 一个关卡可以把某个已注册的工具**按自己的条件**交给玩家：`{"type":"pvzce:tool","tool":"pvzce:hammer","default":true,"cooldown":0,"cost":{"resources":{}}}`。`cooldown` / `cost` 是**关卡对这把工具的覆盖**（不写则沿用工具自己的数），`default: true` 让它成为**这一关空手点击的动作** —— 2-5 的鼠标就是木槌。
- **它不是卡**：不占卡槽、不印价格、不进卡包顺序、没有充能条。所以它不参与 `Slots` 的任何逻辑，服务端走 `LevelServer.useGrantedTool`（唯一与卡片路径共享的是 `applyToolEffect` —— 锤子在两条路上是同一把锤子），客户端走 `UseGrantedToolC2S(tool, x, y)`，**客户端只说它看见的是哪把工具，关卡是不是真的给了它由服务端查自己的 `mechanics`**。
- **默认工具与选卡互斥**：手上没有卡时点击才是工具。选中的卡永远优先，所以"我想种东西"不会被木槌抢走。
- `ToolMechanic.declared/of/cooldownTicks/sunCost` 是这些数的唯一读法：服务端、客户端与校验器都从这里问，`ToolMechanic.validate` 报未知工具 id。
- **指哪打哪**：`ToolDef.range`（缺省 0.9 格）是挥击在**点击点周围**的触及半径，锤子按世界坐标判 `|Δy| ≤ range && |Δx| ≤ range × 1.15`（x 略宽，因为僵尸画得比一个格瘦）—— 目的不是"打相邻格"，而是"点在哪就打哪"。2-5 的僵尸速度是 2.2 倍，等玩家把光标挪进它**当前所在的那一格**时它已经走出去了，按格判定必然打空。命中与否的反馈在客户端是**光标本身挥的那一下**（木槌的 `attack` clip，见 §6），服务端只补一声 bonk；`range` 不画成地面上的提示图。铲子、手套这类作用于**格子**的工具 `range` 留 0，规则不变。
- **一次挥击打多少是工具自己的数**：`ToolDef.damage` / `damage_type`（`tools/hammer.json` 写 `damage: 200, damage_type: "pvzce:impact"`）。200 = 普通僵尸的血量，`impact` = 护甲照常先吃，于是**普通 1 下 / 路障 3 下 / 铁桶 7 下**（370 与 1100 各按 200 一点一点磨，碎了以后还要一下打 200 血的**身体**）—— 这套数字是本项目"护甲吸收整击、碎的那一下不穿透"那条规则的结果（`ArmorCapability.absorb`），原版的"路障 2 下、铁桶 3 下"来自另一条规则（每一下削一层、破甲那一下直接打身体）。**木槌不再是小推车**：原来那个写死的 100000 点 `pvzce:mower` 让草坪上一切都一击死，铁桶和普通僵尸一样便宜。**打空不收费**：`applyToolEffect` 对锤子返回"有没有打中"，没打中就是一次被拒绝的点击 —— 不扣阳光、不进冷却、不响。
- **浇水的效果（`pvzce:water`）也是 `applyToolEffect` 的一条分支**，落在 `LevelServer.waterPlant`：一格里有植物时，它一次做完三件事 —— **回满血**（`PlantEntity.water(WATERED_TICKS)` 返回真补了多少，`WATERED_TICKS = 15s`，所以半血的坚果墙浇一下就是修好）、**挨个问能力**"这水用来做什么了"（`PlantCapability.water(plant, level)`，今天只有 `ProducerCapability` 回答"我还没长大"，于是当场催熟）、以及由此开始的**加速时钟**（`PlantEntity.actionStep()`：每三拍走四拍，射手与生产者的冷却都从它减，持续那 15 秒）。**点空格返回 `false`**：没浇到东西就不花冷却、不消耗次数，与锤子打空同一条规矩。水壶自己的数在数据里（`tools/watering_can.json`：免费、600t 冷却、`uses: -1` 无限次，美术是原版花园那壶 —— `ZenGarden_wateringcan.reanim` 转成的 `animations/tool/watering_can.json` 与卡面 `textures/gui/cards/watering_can`），关卡的覆盖规则与其它工具一样；它在 3-4 首通时发给玩家。水花按**植物自己的位置**放（不是点击的那格）：植物是按格子偏移画的（莲叶偏低、花盆偏高），落在格底的水花会从它旁边的草里冒出来；真的做成了事（补到血或催熟）的植物额外冒一次金光（`pvzce:potted_zen_glow`），水声是 `sfx/effect/watering`。
- **花盆注水（`pvzce:fill_pot`）**由 `LevelServer.fillFlowerPot` 处理，只接受格内单独一只未满水花盆。
  `PlantEntity.fillWater` 永久置满水状态并同步 `idle_water`，不修改场景水地形，不回血或授予护理加速。
  水桶定义为免费、600 tick 冷却与无限次，6-4 首通永久解锁；失败返回 false，因此不扣充能。
  上层种植与荷叶叠放的规则见 `架构-实体与能力.md` §5.5；水桶图标和倾倒动画为程序自产。


**花瓶（`pvzce:vase` 工具）**

- 4-4 的首通奖励，也是"关卡送的植物藏在哪儿"这个玩法：**一次点击，三件事由格子决定** —— 空格子放下一个花瓶（`setScene(pvzce:vase)`，花瓶格在 `#c:unplantable` 里，所以那格从此种不了东西）；花瓶上**带着植物卡**点击把卡塞进去（花瓶变 `pvzce:vase_full`）；**空手**点击把它砸开（格子回到草坪，`sfx/effect/vase_breaking`，里面的卡交回卡槽）——"空手点它直接砸开"这句话从这一轮起才真的成立：不需要先选中花瓶工具卡，见下面的"空手点容器"。
- **"塞卡"走的是落卡报文（`PlacePlantC2S`），不是工具报文**：服务端**故意不知道客户端手上选了什么**，而"选了植物卡再点花瓶"这一击同时带着卡槽号与格子，所以那一条分支在 `LevelServer.placePlantInternal` 里、且**排在可种植判定之前**（花瓶格本来就不可种植）。`UseToolC2S` 因此没有加"手上是什么"字段 —— 加了就是把客户端的选中状态变成服务端真相。
- **卡在点击时付款**（走卡源自己的 `spend`：普通卡组扣阳光并进冷却，传送带取走那张卡），砸开时**免费交回**。这样"存进花瓶再拿出来种"与"直接种"总价一样，而"存进去躲过一次涨价"不成立。一只花瓶只装一张卡，满了就明说。
- **砸出来的植物是掉在地上的种子包**（`CardDropEntity`，见下面"恐怖花瓶"一节）：`smashVase` 调 `LevelServer.spawnCardDrop(card, x, y)`，卡不再直接进卡槽 —— 同一种植物的第二只容器在卡槽上留不下任何痕迹，玩家看到的是"这只瓶子是空的"。捡起来 → 拿到手上 → 免费种下，走 `LevelServer.pickUpCardDrop` / `plantHeldCard` / `releaseHeldCard`（协议 34）。
- **不是植物的卡仍交给卡源**（`CardSource.receiveCard`）：普通卡组往条上加一张（同一张卡已在条上就叠回去），**传送带放到带子上** —— 带子的卡槽是它队列的投影，塞在旁边的卡下一次重建就没了。默认实现是 `LevelServer.addCardToBar`。这条只剩"容器里装的是工具"这一个入口（`vase_field` 的作者可以写任何卡 id），因为能"拿到手上"的只有能种下去的东西。
- **手套能搬花瓶**（用户要求）：`carriedVaseFrom` + `carriedVaseCard`，与搬植物的 `carriedPlantId` 同一套两击式。**拿起时不改任何格子**，所以超时放弃不需要还原；放下时才把旧格复位、新格写入，卡跟着走。放到自己那一格是空操作（那一条必须在"这格已经有东西"之前判）。

**会补的墓碑（`grave_spawner`）**

- 通用模式以 `min_graves` / `initial_graves` / `graves_per_wave` 指定散布墓碑的目标数，`GraveSpawnerData.standingTarget`
  计算目标，`GraveScatter` 只把普通墓碑放到空的陆地格。`interval` 是全局冒怪时钟，每次随机选择一座可用墓碑。
- `phased: true` 是 2-5「打地鼠」的专用进度：按波次选择普通、路障、铁桶及连发数量，最后一波一次性开墓。
  它不能与固定坐标或时间阶段同时声明；旧构造函数与未声明新字段的数据保持默认行为。
- `fixed_graves: true` 保留关卡开局墓碑的坐标和元素 id，不散布额外墓碑。清除后经过 `respawn_ticks` 原地恢复；
  暂时空缺的原始墓碑格由机制拒绝种植，有墓碑时交给 `PlantPlacement` 判断。正在被吞噬的墓碑不参与随机冒怪。
- `phases` 按递增 `at_tick` 声明 `interval` 与 `zombies` 池，重复 id 是权重。第一阶段前不冒怪，阶段开始立即冒一只；
  预览与校验合并全部阶段的僵尸 id。阶段索引、全局时钟及固定格剩余重生时间进入 `GraveSpawner` 存档。
- 所有持续供给在 `wavesReleased()` 后停止冒怪和补墓，让终局能够清空；`graves_spawn_night` 是独立规则，
  可以在最后一波打开已有墓碑。波次仍负责进度与结算，墓碑全供给关卡也需要非空波次表。
- `LevelServer.clearGrave` 仅清覆盖物，保留基础地形。`placeGrave` 仍拒绝陆地墓碑落水；显式带水标签的墓碑只在空水面恢复。
  水墓碑与水中僵尸升起使用水花，普通墓碑使用土粒。

**海岛奇兵（`yard/minigame/island_raiders`）**

关卡数据提供左岸两列草地和六路水面，中央六座 `water_grave` 为固定出怪点，十秒重生。
按时间阶段持续冒救生圈僵尸，后段加入路障；十波右端少量进攻逐步加入潜水与海豚。
自选卡、六辆小推车、30 秒准备，最后一波释放后清场取胜；3-5 通关解锁。音乐循环使用非官方指定曲目。
精确数值以关卡 JSON 为准，真人经济与全海底图的验证边界见 `todo.md`。

**开局墓碑（`grave_field`）**

- 夜关草坪的常态：`{"type":"pvzce:grave_field","count":7}`。原版从 2-1 起每一关开局都在**远离房子的那半场**随机撒墓碑（2-1 四座、2-7 十一座、2-10 十三座），本项目原来是**在 `scene` 里手写坐标**（一处一格的固定布局），表达不了"七座，随便哪"。
- **撒的时机是关卡构造完成的那一刻**（`onLevelCreated`）：选卡页预览、客户端的第一个快照、任何一次"这格能不能种"的问询看到的都是同一块草坪。它没有运行状态，也不进存档 —— **棋盘本身就是状态**（`saveScene` 写全部格子，恢复时整块覆盖），所以续档不会重新撒一遍、也不会与旧墓碑叠加。
- **随机来自关卡自己的 `random`**（与掉阳光、波次分线同一个源），不另开一个未播种的骰子；墓碑数、列范围（缺省 `region: 0.5` = 远半场）、四种墓碑美术（`grave`/`grave_cross`/`grave_slab`/`grave_wide` 轮流）都是机制的数据。
- **撒的实现只有一处**（`GraveScatter`，`grave_spawner` 补墓碑也走它）：洗牌区域内的格子后逐个 `placeGrave`，而不是"掷一个点、撞上已有墓碑就放弃" —— 13 座落在 5×5 的半场里，掷点重试会留下八座。`placeGrave` 自己拒绝已有植物、没铺草的格子**以及水格**（墓碑盖在草坪上，不是替换掉草坪，更不是插进泳池）。
- **它和 `graves_spawn_night` 是一对**：墓碑是障碍物，最后一波由规则一次性把每座开一遍（2-5 那种持续冒怪是 `grave_spawner` 的事，两者互不影响）。2-1/2-4 原本手写的墓碑已改成这个机制（格子还给草坪）——同一块草坪每次开局的墓碑位置不同，与原版一致。

**空手点容器（`SmashContainerC2S`，协议 33）**

- **一条棋盘规则，不是一件工具**：卡槽里没选东西、关卡又没有 `default` 工具时，点到一个容器就是"砸开它"。
  容器 = 玩家的花瓶两式 + 恐怖花瓶两式（`PvzceIds.isSmashableContainer`，客户端与服务端共用这一份判据）。
- **客户端负责手势，服务端负责结果**：客户端在该格召唤一把纯动画的木槌（`InGameScreen.summonMallet`，
  点下去就播、不等回话），同时发 `SmashContainerC2S(x, y)`；服务端只回答"砸掉的是什么"。
  **报文里没有工具 id**：锤子不是任何一方手里的东西，`UseGrantedToolC2S` 的语义（关卡给我的那件工具）
  与它无关，所以它有自己的 id 与自己的包。
- 拿植物卡点花瓶仍然是"把卡存进去"（走落卡报文的那条老路），选着花瓶工具卡点它仍然是工具自己的手势；
  这两条都没有变。

**开局花瓶（`vase_field`，本项目自己的机制，今天没有关卡在用）**

- 它把**装着卡的花瓶按写死的坐标**摆好：`{"type":"pvzce:vase_field","vases":[{"x":1,"y":0,"card":"pvzce:sunflower"}, …]}`，坐标写死（墓碑那套随机撒是为了"每次草坪不同"，而花瓶是关卡送的礼物，礼物每次落在别处是掷骰子而不是难度曲线）。4-4 曾经是它的用户；按原版重做之后冒险模式的花瓶关是 4-5，而那一关摆的是**另一种东西**（`scary_potter`，见下一条），所以它现在只剩测试夹具在用 —— 留着是因为它对数据包仍然是一种可用的书写方式。

**恐怖花瓶（`scary_potter`，4-5）**

- 原版第 35 关的骨架，也是**冒险模式唯一没有波次的一关**：三个回合，每回合把花瓶撒在从 `from_column` 到最后一列的格子上，瓶里装一张植物卡、一只僵尸，或者一份资源（`kind: "sun"`，见下），砸光所有瓶且场上没有僵尸就进下一回合，最后一回合清空即通关。
- 数据长这样：`{"type":"pvzce:scary_potter","rounds":[{"from_column":6,"leaf_count":0,"pots":[{"kind":"plant","id":"pvzce:pea_shooter","count":5},{"kind":"zombie","id":"pvzce:basic_zombie","count":4}]}, …]}`。`leaf_count` 是原版 `ScaryPotterChangePotType`：这么多只植物瓶画成绿叶瓶（告诉玩家里面有植物），其余全是问号瓶。
- **瓶子撒在哪里是这一关自己的随机**（`onLevelCreated` 与每回合开始时洗牌选格），关卡只写「从第几列起、各有多少只」：原版也是这么做的，写死就成了一道背下来的题。
- **内容归机制，不归关卡的花瓶表**：玩家的花瓶（`pvzce:vase`，里面那张卡在 `LevelServer.vaseContents`）与关卡的恐怖花瓶（`pvzce:pot_question` / `pvzce:pot_leaf`，内容在 `ScaryPotterMechanic` 的 `State` 里）是两种物件，各有各的美术与归属 —— 混成一个 id 会让「锤子砸下去该给卡还是该放僵尸」没有答案。状态随存档的 `ScaryPotter` 分区进出（回合号 + 每个瓶里是什么）。
- **砸瓶是棋盘自己的规则，不是一件工具**：空手点击一个容器 → 客户端发 `SmashContainerC2S(x, y)`，服务端 `LevelServer.smashContainer` 按格子回答"关卡的瓶子（`smashPot`）/ 玩家的花瓶（`smashVase`）/ 什么都不是"。"哪些格子算容器"只有一处判据（`PvzceIds.isSmashableContainer`：两个花瓶 + 两种瓶子），客户端与它共用同一份答案。4-5 因此**不再声明 `pvzce:tool`**，也就没有木槌光标、价格与冷却。
- **剑与犁分开**：关卡真的声明了 `default: true` 的锤子时（今天只剩 2-5），`applyToolEffect` 的 `pvzce:hammer` 分支仍然先开瓶再打 `range` 范围内的僵尸（一次挥击两件事都做）；而空手点容器这一条**只开容器**——召唤出来的锤子是动画，不是那把有伤害的工具。
- **瓶子里的资源是一束三只**：`kind: "sun"` 的瓶子砸开时掉 `PvzceConstants.SCARY_POT_SUN_DROPS = 3` 只、每只按资源自己的 `defaultValue`（阳光 25），落点按 `SCARY_POT_SUN_SPREAD = 0.42` 格错开、**最右列整束往里挪**（`LevelServer.spawnResourceBundle`）。这是 4-5 唯一的阳光来源（天上不掉、瓶里的植物不产），另一半来自 `zombie_sun_drop_chance: 0.1` 的击杀掉落；第 1 回合两只阳光瓶 = 150，正好是这一关唯一那张卡（樱桃炸弹）的价钱。
- **这一关不出现选卡页**：`seed_screen: false` 是关卡自己说的（不是从卡槽数推的），客户端从列表点进去直接开局；卡组是 `[pvzce:sun, pvzce:cherry_bomb]` 两张锁定卡（`max_seed_slots: 2`，仍然"没什么可挑"）。阳光卡必须在条上：资源 `collectible_without_card: false`，没有它连自动拾取都会被拒，银行 HUD 也不画。瓶子砸出来的植物**不进卡槽**（它是地上的种子包），所以卡槽从头到尾就是这两张。
- **瓶子里的植物是一件地上的物件**：`CardDropEntity`（`EntityKind.CARD_DROP`）躺在瓶子原来的格子上 20 秒（`CARD_DROP_LIFETIME_TICKS`），最后 5 秒闪烁（`CARD_DROP_FLASH_TICKS`，客户端按实体 `health` 画 —— 那**就是**它的剩余时间）；点一下拿到手上（`HeldCardS2C`，手里那株**不走时钟**），再点草坪格免费种下（`plantHeldCard`，不碰卡源：容器就是付款），右键放回原地（`ReleaseHeldCardC2S`）。拿在手上 = `LevelServer.heldCardDropId`，与手套的 `carriedPlantId` 是两回事（两者互斥：`pickUpCardDrop` 与 `movePlant` 各问一句）。**存档时手里的包回到地上**（手是玩家的，不是关卡的状态），包本身照旧存进 `Entities`（它是唯一会被恢复的掉落物：阳光丢了是 25 点，包丢了是玩家已经拿到的一张卡）。
- **回合之间清理场地**：`ScaryPotterMechanic.tick` 在摆下一回合之前调 `LevelServer.clearLawn()`（纯移除：不回阳光、不掉落、不触发死亡效果），并播报一句。原版就是这么做的，而且不做的话下一回合的瓶子会被玩家的植物挤掉 —— 摆不满时缺的从声明队尾开始丢，实测第 2 回合 20 只只摆 14 只、丢的**全是僵尸瓶**，那一回合就没有僵尸了。**"清场"包括种子包**：植物、草坪上的包、以及玩家手里那一株（清掉手牌时同时发 `HeldCardS2C.NONE`），`LawnSweep` 把清掉的数量带回来给播报用 —— 留着的包等于给下一回合留了一份存货（用户退回的第一版就是漏了它）。
- **三回合的配比**：植物瓶/僵尸瓶 = 6/7、8/9、9/13（阳光 2/3/3，每回合正好填满 15/20/25 格）。**僵尸不少于植物**是一条被用户拍板的平衡规则（每个植物瓶给一整株植物，植物多到两倍时这一关就没难度了），`ScaryPotterTest` 里有一条把它写成断言。
- **瓶子放出来的僵尸知道自己是"被放出来的"**：`smashPot` 的僵尸分支在生成后调一次 `ZombieEntity.onReleased`（能力钩子 `ZombieCapability.onReleased`）—— 它的语义是"容器开的口，不是波次把它放进某一行"。今天只有小丑僵尸用它：引信是走过的距离，被放出来的**当场开箱**（跳过那段路），然后照旧播满 110 tick 的开箱动画才炸——这段前摇是原版自己的节拍（`PHASE_JACK_IN_THE_BOX_POPPING`），也是玩家救场的机会。爆炸时还会调 `LevelAccess.breakContainers`（半径内每个恐怖花瓶/玩家的花瓶各走一遍 `smashPot`/`smashVase`），所以"先砸哪只瓶子"是这一关真正的决定。别的东西（比如"出土的僵尸"）要按同一个问题接进来。
- **砸开的样子是容器自己的碎片**：`smashPot`/`smashVase` 发 `PvzceParticles.POT_SHATTER` / `POT_SHATTER_LEAF` / `VASE_SHATTER`（绿叶瓶掉绿片，按砸之前那一格画的是哪种瓶子选），不再是樱桃炸弹的 `EXPLOSION_POW`；碎片是项目自己的容器贴图切出来的九块（`tools/gen_pot_chunks.py`），参数取自原版 `refer/im7/particles/VaseShatter.xml`（原版碎片贴图不在 `refer/` 里，见该工具的说明）。
- **花瓶工具不能盖住瓶子**：玩家的花瓶只能放在**裸地**上（草/裸地/屋顶两式，且没有植物）。原先 `useVase` 只问有没有植物，于是一次误点会把瓶子变成空花瓶、内容还留在机制账上——这一关就永远打不完了；`recoverLostPots` 是给这种存档的自愈：账上还有而棋盘上没有的瓶子会重新立起来，被植物占住的划掉。
- **赢了谁来说**：0 波的关卡永远满足不了 `checkEnd` 的 `allWavesReleased()`，所以最后一回合清空时由机制调 `LevelServer.declareVictory()`。新写「没有波次的关卡」时先回答这一句，否则那一关既不会赢也不会结束。
- 美术取自原版 `Scary_Pot.png`（`tools/gen_scary_pots.py` 切出问号瓶与绿叶瓶两种，128×128、与其他场景贴图同规格），两个场景元素都在 `#c:unplantable` 里。
- 它与 `grave_field` 同一层、同一时机（`onLevelCreated`），但**只做"摆格子"这一件事**：`LevelServer.fillVase(x, y, card)` 同时写场景元素（`pvzce:vase_full`）与内容表。关卡作者不需要在 `scene` 块里再写一遍那些格子，两处写同一件事就是两处会各说各话。
- **内容表在 `LevelServer.vaseContents` 而不是机制里**，随存档的 `VaseContents` 分区与 `scene` 分区一起进出：满花瓶的**画面**与"里面有哪张卡"必须同生同死，分开存就会出现"画着满的、砸开是空的"。砸掉的花瓶不需要单独记 —— 砸掉就是把格子写回草坪，`scene` 已经记了。这同样是"关卡机制"与"关卡状态"的分界：机制声明**关卡的形状**，状态跟着**场景**走。
- 三只花瓶的点击行为（放下、塞卡、砸开）与手套搬运见 §4.9 的工具一节。

**小推车（`mower`）**

- **不声明就每行一辆**：`LevelMechanics.effective` 给每个没写 `mower` 的关卡补上 `MowerData.EVERY_ROW`，所以"关卡文件里没提"这件事的含义是"这是普通草坪"，而不是"这里没有推车"。只有 `rows` **空数组**才是"一辆都没有"。
- **声明方式**：`{"type":"pvzce:mower"}` = 每行；`{"rows":[0,4]}` = 只有这两行；`{"rows":[]}` = 没有。缺省与空数组是两件事，所以字段是 `Optional<List<Integer>>`（codec 分不出来就等于两种语义都说不清）。
- **每行放哪种车也是数据**（`MowerData.kinds`）：`{"row":2,"kind":"pvzce:pool_cleaner","sound":"pvzce:sfx/ambient/pool_cleaner"}` = 第 2 行站的是泳池清洁器、启动放它自己的声音。**有车的行 = `rows`（未写＝每行）∪ `kinds` 点名的行**（`rowsFor` 去重、升序；点名一种车就等于承认那一行有车），所以泳池五关只写 `rows: [0,1,4,5]` 加两条 `kinds` 就说清了"草坪四行割草机、水行清洁器"。`kindFor(row)` 是"这一行是哪辆车、什么声音"的唯一读法：没点名的行是 `pvzce:lawn_mower`，没写 `sound` 就用割草机那一声。
  > **车型是内容 id，不是枚举、也不是布尔**：服务端不按它分支 —— `Rig` 只把 `MowerKind` 抄进每一行（`Rig.Mower.kind`）并在启动时取它的 `sound`，客户端按 `mechanic/<path>` 取动画。所以"再加一种车"不需要改 `MowerMechanic`，屋顶的 `RoofCleaner` 落地时只是又一个 id。
- **行为就是原版那三条**：车停在第 0 列左侧（`IDLE_X = -0.5`）；该行**地面层**僵尸走到 `cellX <= 0.05`（第 0 列左沿，啃食中的僵尸在 0.5 左右不会误触发）时启动；此后以 `SPEED = 3.3` 格/秒向右推进，碾过该行一切**地面层**目标；越过右边界后 `STATE_USED`，永久消失。
  > **飞行与挖掘中的僵尸不碾**：判据是僵尸自己的 `layer()`（与子弹路由同一个），所以气球僵尸从推车头上飞过、矿工还在地下时都不受影响——它们走到房子里照样算输，与原版一致。
  > **碾压无视护甲**：`damageBody(health)` 而不是 `damageImpact`。`damageImpact` 是"护甲先吃、碎的那一下不穿透"，用它推车会撞碎铁桶却打不死里面的僵尸（见上面保龄球那段的同一条规则）。
- **状态在 `LevelServer.mechanicState(id, create)` 里**：注册表里的 mechanic 是**单例**，两个关卡不能共用一辆草坪推车，所以每个关卡按 mechanic id 向关卡要一个槽位来放自己的 `Rig`（客户端有同名镜像 `ClientLevel.mechanicState`）。关卡本身不知道槽里是什么。
- **同步**：`MechanicSyncS2C` + `MowerMechanic.State`（整表：每行的 `state` 与 `x`），只在**状态变化**与**有车在滚**时每 3 tick 发一次；没被触发的关卡一个字节都不发。客户端 `MowerClientMechanic` 用这份状态画车，**画哪些行与画什么车**都来自 `LevelPayload` 里解析后的 mechanic 块（`MowerData.rowsFor` / `kindFor`）—— 线上那两个数里没有车型，也不需要。
- **存档**：`Rig` 通过 `collectSave/applySave` 写进 `level.dat` 的 `Mowers` 块，恢复时 `applySave` 置脏，于是客户端进场后会收到一次真实状态（用过的车不会重新出现）。
- **美术**：`tools/reanim_to_pvzce_all.py --entity lawn_mower` 把原版 `LawnMower.reanim` 的 `anim_normal` 掩码转成 `animations/mechanic/lawn_mower.json`（0.74×0.62 格），泳池清洁器同理（`--entity pool_cleaner`，`PoolCleaner.reanim` → `animations/mechanic/pool_cleaner.json`：`anim_water` 的单帧（`range: [11, 11]`）当停放姿势、`anim_suck` 当行驶）。这一族机制道具**不是注册内容**（没有注册表条目，`kinds` 里那串 id 只在数据与美术路径之间当键），所以播放走 `ArtTarget`——一个自己带动画文件 id 的 `Animatable`，渲染、时钟、模型与实体完全共用。
  - **两个 clip：`idle` 与 `drive`**。原 reanim 的轮子轨道在 `anim_normal` 的**每一帧**都在转，整段导出成一个循环 clip 会得到"停在路边轮子却一直在转"的车；转换器的 `range: [0, 0]` 把 `idle` 冻在第 0 帧（停放姿势），`drive` 才是滚动的那个，`MowerClientMechanic` 按 `STATE_READY`/`STATE_ROLLING` 选 clip。冻结用的是现成的 `range` 选项，没有为它加新语法。
- **粒子**：`PvzceParticles` 里那三个原版发射器终于有主了——`mowered_zombie_head` / `mowered_zombie_arm`（被碾的僵尸）与 `mower_cloud`（行进时的尘烟）；启动音是 `sfx/effect/lawnmower`。
- **玩家可以手动放车**（长按）：鼠标停在还停着的车上按住 `MOWER_HOLD_NANOS`（0.5s）就发 `ReleaseMowerC2S(row)`，服务端 `LevelServer.releaseMower` 重新校验（**这一行有车、而且车还停着**、关卡还在跑）后走**同一个** `Rig.start`——同一个音效、同一个速度、同一套碾压与消耗。放手即取消，所以普通点击不可能误触发（车是一次性资源，用在已经处理过的波次上就是这一整行后面都空着）。
  - 按 **row** 而不是坐标：车停在棋盘左沿之外半格（`IDLE_X = -0.5`），那里没有格子，所以长按的命中测试在 `onMouseClicked` 里**先于**棋盘边界判定，用的是世界坐标下的圆形半径（与掉落物拾取同一个 `0.45` 格）。
  - 按住时在车**上方**画一条进度条（不是圆环：车有个高把手，环绕会压在把手上）；进度条在 GUI 空间、用**画在屏幕上的**车位置定位，所以光标哪怕飘几像素也不会丢手势。
  - **请求不带"能否放行"**：客户端只说哪一行，`Rig.release` 在服务端回答"行上没有车"和"车已经没了"是同一个 `false`，重复包是空操作而不是第二次发射。
  - 音效**延迟到下一个 tick**：请求落在两个 tick 之间，那时 `emitEffect` 没有 bridge；`Mower.launchSoundPending` 让 rig 在自己的下一次 tick 上补放，而状态变化是立即的（下一次实体同步就要带上"正在滚"）。
  - 关卡一结束就取消未完成的长按：把已经计进"幸存车"的那辆偷偷花掉是错的。
- **结算**：没被用掉的车按金币折价进本局奖励，客户端在点击奖励时逐辆变成金币飞向钱袋（见 §4.5）。`Rig.readyCount()` 是"还剩几辆"的唯一答案，服务端与客户端（`ClientMechanics.parkedMowers`，读同一份镜像状态）都从它出发。

**钉耙（`rake`）**

- **它是商店物品，不是卡**：`PlayerProfile.ownsRake()`（买过，或沙盒）为真时，`LevelServer.withPlayerMechanics` 给每个**没有自己声明 `pvzce:rake`** 的关卡补一条 `RakeData.RANDOM`。三态与 `MowerData` 同形：不写 = 玩家那把，写了 = 这一关自己决定，写 `"rows": []` = 这一关不要（1-5 / 2-5 / 4-5 就是这么说的）。
- **站在从右数第 2 列**（`RakeMechanic.COLUMNS_FROM_RIGHT`，9 列即第 7 列的中心），只在**草地**行上：候选行里是水的被 `Rig.place` 剔掉（`rowsFor` 是文件的事实，`rowIsWater` 是棋盘的事实）。触发判据是"僵尸的 `cellX` 到达那一格的中心"，不是格线 —— 与木槌同一条"问点，不问格"的规矩。
- **1800 伤害、`pvzce:mower` 伤害类型**：无视护甲、会分尸（原版踩上去头会掉），普通/路障/铁桶/橄榄球都死，巨人 3000 血不死。用过即消失、进存档（`Rake` 块），续档不会复活。
- **它替玩家决定第一只僵尸走哪条道**：`LevelServer.forcedOpeningLane` 是 `WaveDirector.Host` 上的新问题（默认 -1），导演只在**本关第一只**僵尸上问它。强制经过 `usableLanes` 筛一遍，所以"走路的被塞进泳池"这类错误不会发生 —— 建议，不是覆盖。
- **"没有"也要说**：`rows: []` 也会发一次 `State(x, row = -1, spent)`，因为客户端无论如何都有一个 overlay。
- 客户端画的是服务端发来的 `x`（`State` 三个字段：`x` / `row` / `spent`），"钉耙站在哪"因此只有一处答案。

**爆炸范围是"格"而不是"距离"，而且必须覆盖触发范围**：`pvzce:explosive` 的 `square` 把 `radius` 从半径读成**格数**（`LevelServer.damageArea(..., square)` 判据是 `|Δ| ≤ radius + 0.5`，半个格是植物自己那一格的半宽），这就是原版的写法：土豆雷 `radius 0.5` = 自己那一格，樱桃炸弹 `radius 1.0` = 周围 3×3，毁灭菇 `radius 3.0` = 7×7。`trigger: "row"`（火爆辣椒）**整行**结算，走 `LevelAccess.damageRow` —— 一个足够大的方格会连带打穿旁边几行，而一个只够 9 列宽的半径在更宽的草坪上会短一截。`detonate` 另有一条不变量：**爆炸的覆盖范围至少覆盖触发范围**（方格按 `radius + 0.5` 算覆盖），否则触发那一 tick 的距离正好落在爆炸之外，每一次引爆都必然落空；`potato_mine` 的 `trigger_range` 因此是 0.5（僵尸真正踩进格子才炸）。

**冷却按原版**：土豆地雷 30 秒（1800 tick）、樱桃炸弹 50 秒（3000 tick）、墓碑破坏者与大喷菇各 7.5 秒（450 tick）。

**每一株爆炸物画自己的特效**：`ExplosiveCapability.particles` 缺省是 `["pvzce:pow"]`（原版灰烬线那一闪），樱桃炸弹与毁灭菇各自点名自己的组合，**土豆地雷也必须点名** —— 它原来没写，于是画的是樱桃三件套里中间那件。地雷自己的三件在原版 `PotatoMine.xml` 里就有、也早就转好了：`potato_mine_flash`（闪光）、`potato_mine_word`（"SPUDOW!"）、`potato_mine`（炸开的土豆泥）。`AnimationResourceLoaderTest.theBlastsNameParticlesThatExistAndArePlaced` 现在把地雷一起点名，并单独断言它**不等于**缺省值。

### 4.10 变异关卡（庭院无尽 / `MutationManager`）

四个难度档的关卡（`yard/endless/mutation_easy|normal|hard|hell`）**在代码里定义**（`common/level/mutation/MutationLevels`，注册于 `BuiltInRegistries.bootstrap()` 末尾），共享同一套东西：9×6 泳池白天、**14 卡槽**、**10 增益槽**、草坪四行割草机 + 水行泳池清洁器、`endless` 的轮次生成器，以及本节的变异系统。
> **14 是这一档自己的数，不是背包上限。** `MAX_SEED_SLOTS` 仍是 12（背包、`/profile slots`、编辑器卡池、生存无尽都读它）；变异关卡需要更宽的卡槽条来回答一块会自己改写规则的草坪，所以它写自己的常量。

**为什么是代码而不是 JSON**：四关之间只差一个 `mutation_difficulty` 规则，而真正的内容（变异目录、无尽波表）本来就只能是代码 —— 一个机制要改游戏规则、换卡槽条、改地形，JSON 表达不了。

**变异的存档只覆盖变异自己那一半**：列表、抽到的数字、各自的倒计时与「谁在发牌」进 `level.dat` 的 `Mutations` 块；
它对世界做过的事（弹坑、墓碑、水草、卡槽条内容）仍由存档的各个既有分区承担，恢复时**不重放**。
加一条带新状态的新变异时，记得实现 `Mutation.saveState` / `loadState`，否则它的倒计时会在续档时重新开始。

### 4.10.1 无尽关卡是怎么跑的（轮次驱动）

**一个机制，两种关卡。** `pvzce:endless` 只做一件事：**接管波次来源**。普通关的波次写在 `waves` 里、由导演照着读；无尽关的波次由 `common/level/endless/EndlessWaves` 按 `(日程, 轮号, 波号)` **当场生成**。除此之外无尽关就是普通关：棋盘、卡槽、割草机、结算全部照旧。

**"轮"是什么。** 一轮 = 固定波数（`min(30, 11 + (n-1))`，第 1 轮 11 波、第 2 轮 12 波…第 20 轮起 30 波），打完**且场上清空**才算一轮结束。结束那一刻关卡**冻结**（`tick` 在 `tickRoundClear` 处直接返回：不模拟、不接受种植与工具），发 `RoundClearS2C`，客户端弹"第 N 轮完成"，玩家确认后进选卡页，选完发 `ReselectCardsC2S`，服务端换卡组、`beginNextRound`、解冻。

**轮间保留什么。** 草坪、阳光、割草机、卡冷却**全都不动**，只换卡组 —— 这是这一模式是"一局"而不是"一串关卡"的全部理由。卡组来自背包已解锁的植物，张数是变异档自己的 14（见上）。

**兜底。** 服务端不会无限等：`round_clear_timeout_ticks`（规则，0 = 引擎默认 60 秒）到点就用旧卡组继续，客户端收到新轮次的 `RoundSyncS2C` 会把过期的结算弹窗关掉（`PvzceClient.onRoundStarted`）。等待时长单独计数（`roundClearWaitedTicks`），因为轮间 `tickCount` 是冻结的。

**波次不进协议、不进存档。** `LevelInitS2C.waveTypes` 只装第一轮的（换轮由 `RoundSyncS2C` 带新一轮的清单），存档只写 `LoadVersion=2` / `WaveRound` / `WaveIndexInRound`。这正是把 3990 条定长表换掉的原因：那张表的上限由 `PacketByteBuf.MAX_COLLECTION_SIZE` 决定，而且每个客户端都要收下整张表。

**新增关卡。** `pvzce:yard/survival/endless_pool`（分类 `pvzce:survival`，"生存无尽"）是**不带变异**的原版形态，`server/level/EndlessLevels` 在代码里构造；四关变异无尽照旧，只是把 `endless` 块换成指名 `pvzce:mutation_endless`。

### 4.10.2 变异 × 轮次

- **变异跨轮持续**：换轮不重置变异列表、不重开宽限期。它改过的规则、卡槽、场景就是这一局的规则，草坪都保留了，没有理由把成因清掉。
- **规则进存档时要"退出去"**：速率型变异把因子**乘进规则本身**，所以存档直接写实时值的话，恢复时 `applyFromSave` 会再乘一次（因子被平方）。`LevelServer.save` 因此把规则交给 `MutationManager.rulesForSave`：按到达顺序逐个把因子除回去写进文件，再把内存里的值原样放回；文件里只留"变异 id + 它抽到的数"，恢复时重算一遍。**同一条变异叠两份时要按顺序连除**，两个因子都对实时值除一次会写下一个中间值（见 `架构变更记录.md` 的那一条）。

**一、变异是什么**

- 一个变异 = 一个 `Mutation` 实现（`common/level/mutation/`），注册进 `BuiltInRegistries.MUTATIONS`。它**不是机制**：机制由关卡声明、实例共享、按 id 查数据块；变异由引擎随机抽出、**可以被撤销**，所以接口的每个钩子都是成对的（`apply` 返回状态、`revert` 收回去）。
- **注册表条目是共享单例**，所以变异**不得**在字段里存关卡状态：倒计时、它改过的格子、它抽到的数字，全部走 `apply` 返回的对象，或者问关卡。38 条内置变异都遵守这一条。
- **`Roll`**：变异在生效那一瞬间抽一次数字（`multiplier` 在 `0.5~1.5` 上按难度档放大），之后冻住 —— "阳光 ×1.4 的变异"必须一直是 ×1.4，否则叠加型关卡会每次 tick 自己重抽。抽取用关卡自己的 `random`，同一局可复现。
- **难度档**（`MutationDifficulty`，关卡 `rules.pvzce:mutation_difficulty`）：简单 10 个 / 120s / ×1，中等 20 / 90s / ×1.5，困难 30 / 60s / ×2，地狱 50 / 30s / ×3。倍率同时作用在**抽签区间两端**（`[0.5k, 1.5k]`，最后按规则自身的定义域 clamp）与**变异自己的时钟**（`scaledInterval`）。首条变异由 `mutation_initial_ticks`（默认 1800 = 30s）单独给出宽限期，与档位无关。

**二、列表、挤出与压制**（`MutationManager`，关卡持有）

- 列表按**到达顺序**，上限 = 档位；满了以后**丢最旧的那个**（简单直白的 FIFO，玩家看面板就能预判下一个要掉的是谁）。
- **"生效"是推导出来的、不是就地翻标志**：每次列表变化重算一遍（`canRun` 说不行的进入"待机"，被别的变异压制的进入"被压制"），再和上一轮 diff 去 `apply`/`revert`。好处是**被压制的变异在被挤出后自己就活了**，不需要任何人记住"它当初被谁压着"。
- **压制关系**只有一条，而且**只作用于卡槽**：两条都碰卡槽的变异互相压制，**谁最后到达谁说了算**。碰卡槽有两半 —— **发牌者**（`CardDealingMutation`，把整条卡槽换成自己的，例如传送带）与**改写者**（`RewriteBarMutation`，改卡槽**内部**的卡，例如卡槽替换）。两者争同一个"当前持条者"的位置，最后到的那个拿。
  - **顺序由调用方提供，实现自己不用判断**：`MutationManager.isHeldBack(entry, index)` 只把排在它**后面**的条目拿去问 `Mutation.suppressedBy`，所以二十个实现里没有一处需要知道谁先谁后。
  - **改写者的活儿要在卡槽重建之后再铺一次**：关卡在换持条者、重选卡等时刻会从玩家选的卡重建自己的卡槽，那次重建不认识任何变异。`LevelServer.rebuildCardBar` 因此在末尾调 `MutationManager.reapplyBarRewrite()`，由 `RewriteBarMutation.rewriteBar` 把这一轮的改写重新铺上去。
  > **约束：压制只看"谁后来"，不看优先级数值。** 默认实现拿 `cardSourcePrecedence()` 比大小会被读成
  > "优先级是全目录的 rank"，于是带子的 10 压住其余 17 条的 0，速率/天气/地形类变异一起停止 tick，
  > 而 `evictOldest` 永不挤出发牌者，它们再也回不来。判据是三条：`MutationManagerTest.onlyBarMutationsHoldEachOtherBack`
  > （只有碰卡槽的互相压）、`MutationManagerTest.theBarFallsToWhicheverMutationArrivedLast`（两个顺序各测一遍）、
  > `MutationManagerTest.aRewriteIsLaidBackOnTopOfARebuiltBar`（重建之后改写还在）。
  > 两次踩坑的经过见 `架构变更记录/` 的变异相关卷。
- 挤出时跳过"正在持条的那一个"（发牌者或改写者），除非列表里只剩它 —— 否则会因为一条传送带把卡槽条带走而卡死。

**三、四条新规则与一变一改**

| `plant_action_speed_multiplier` | `PlantEntity.actionRate()` → 每个能力自己的 `RateClock` | 植物攻击速率变异 |
| `sun_rate_multiplier` | `SunDropClock.rollInterval`（天降）+ `ProducerCapability`（植物产阳光） | 阳光速率变异 |
| `plant_sun_cost_multiplier` | `DeckCardSource.spend`（收银台，不是卡面价） | 植物阳光消耗变异 |
| `mutation_difficulty` / `_initial_ticks` / `_interval_multiplier` | `MutationManager` | 关卡文件（前三档由代码定义） |
| `mutation_seed_cooldown_factor` | `LevelServer.effectiveCooldownTicks`（与关卡的 `seed_cooldown_multiplier` **相乘**） | 坚果保龄球变异（半冷却） |
| `zombie_health_multiplier` | `LevelServer.spawnZombie`（**创建时读一次**，与波次自己的成长倍率相乘） | 僵尸强化变异 |
| `plant_health_multiplier` | `LevelServer.spawnPlantInternal`（**种下时读一次**，结果存进 `PlantEntity.fullHealth`） | 植物脆化变异 |

> 卡牌冷却刻意分成**两条规则**：关卡自己那条属于关卡，变异那条属于变异。谁撤销谁只退自己那一份，两个变异同时改也不会互相抹掉。`GameRuleType` 这一轮多了 `EnumRule`（有名有姓的规则值，编辑器画选择行而不是滑杆）与 `named()`。

**四、变异与它们各自的作用点**

第一批 18 条（下表），第二批 20 条见本节末尾（分批提交，表随提交增长）。

| 变异 | 实现要点 |
|---|---|
| 卡槽替换 `slot_replace` | 按**能力组合**分组（`PlantAbilityGroups`：能力 id 排序后的集合就是组键，多能力植物按全部能力入组，无能力植物自成一组），组内从**玩家背包**随机换，替补不足就保留原卡；触发瞬间洗一次即冻住；旧卡槽整份存进状态，撤销时原样放回 |

| 阳光速率 / 植物攻击速率 / 僵尸移动速率 / 僵尸出怪速率 / 植物阳光消耗 | `RateMutation` 一条类五个实例：抽到倍率 → 写规则 → 状态只记自己那份因子 → 撤销时除回去 |

**四之二、第二批变异（分批提交，表随提交增长）**

| 变异 | 实现要点 |
|---|---|
| 僵尸强化 `zombie_health` / 植物脆化 `plant_fragile` / 卡片冷却 `card_cooldown` | `RateMutation` 的三个实例：前两条各写一条新的血量规则（**创建时读一次**），"脆化"用 `invert`（除以 roll）并把上限夹到 1 —— 叫脆化的变异不能反过来给玩家更硬的植物；冷却复用关卡的 `seed_cooldown_multiplier` |
| 阳光暴雨 `sun_shower` | 自己的倒计时（600t / 档位倍率）+ `LevelServer.dropSkySun`：掉的是**天空那颗太阳的同一颗**（从天上落下、要玩家点），不是击杀掉落用的就地动作；`applyFromSave` 只恢复时钟 |
| 卡槽封锁 `slot_lock` | 见上面"一张卡被锁住时"：锁的是 1~2 张**植物**卡（工具与资源卡永远不锁 —— 锁了铲子等于拿走玩家改错的机会） |
| 卡槽轮盘 `slot_roulette` | `RewriteBarMutation`：每 1500t / 档位倍率把**一张**植物卡换成背包里的随机植物，**会重复**（与一次性的 `slot_replace` 正相反）；旧卡槽整份进状态，撤销时原样放回 |

> **"在行动"的集合按条目记，不按 id 记**：变异**可以重复抽到**（权重允许，面板上也确实是两条），而两条同 id 的条目在一份 `Set<Identifier>` 里会互相冒充 —— "撤销不再行动的那些"那一步里，后到那份的 id 替先到那份回答了"我在行动"，被压制的那一份继续 tick，而存档恢复后又是对的，于是只在"存一次档"的测试里现形。

**五、客户端表现（细节见 §6.2）**

> 底图是例外之一：`MutationEffects` 里有一个"换图"的效果（`POOL_NIGHT` → `background4`），因为底图属于客户端、而且没有任何包能改它。新局本身用**白天**底图（`background3`，与 3-x 相同）。

`MutationStateS2C` 一次下发**整个列表**（不可能由关卡定义推出来，因为变异会走）：档位、上限、间隔、距下一条的 tick、每条的 id / 状态 / 抽到的数字 / 主体、卡槽条种类、特效位（暗色遮罩 / 锤子光标）、本局**运行时发放的工具**（锤子）、以及这一局**当前生效的关卡增益**。心跳 40 tick 一次（面板的倒计时靠它走），列表变化立即发，增益变化也立即发（`buffsChanged` 强制发一次）。

**六、存档（`level.dat` 的 `Mutations` 块）**

整份列表进存档：到达时钟、档位、每条的 id / 抽到的数字 / 主体 / 它自己的状态，外加"谁在发牌"与那条卡槽条的状态（传送带的队列）。**只存变异自己的状态，不存它对世界做过的事** —— 弹坑、墓碑、水草、增益、规则、卡槽条内容都在存档自己的分区里，重放会重复。

恢复走三个钩子（`Mutation.applyFromSave` / `saveState` / `loadState`），在 `LevelServer.restore` 的**卡槽条之前**执行：发牌的变异决定 bar 是哪一条，而 `restoreSlots` 按 index 匹配，顺序反了冷却就会写进错误的卡槽。

| 变异 | 恢复时做什么 |
|---|---|
| 阳光/攻击/僵尸速度/出怪/价格（5 条）、天黑、坚果保龄球 | **再写一次规则**：存档里的规则是关卡自己的值，变异那一份（倍率）不在其中；写回方式与首次生效完全相同 |
| 卡槽替换 | **重建 bar**（关卡构造时建的是玩家自己那份），发过的卡存进状态，挤出时能原样还回 |
| 传送带 | 卡槽条由 `MutationCardSource` 重建，队列由 `CardSource.collectSave/applySave` 恢复 |
| 打地鼠 / 墓碑生长 / 僵尸危机 / 水草蔓延 | 恢复倒计时与预算；工具（锤子）重新发放（它在关卡的工具列表里，不在存档里）；**不再冒怪、不再长墓碑、不再蔓延** |
| 世界末日 | **不再引爆**：它存的是"已经放过 N 株"，弹坑已经是地形 |
| 孟德尔 / 两种爆炸 / 增益变动 | 无事可做：前三个只在事件上起作用，增益由存档自己的增益列表恢复（恢复后客户端从下一次 `MutationStateS2C` 拿到它） |
| 阳光暴雨 / 卡槽轮盘 | 恢复倒计时与（轮盘的）当前卡槽；**不再掉太阳、不再换卡**：已经掉出来的太阳与当前卡槽都在存档自己的分区里 |

> **带状态的变异要实现 `MutationManager.SaveHandle`**：`Mutation.saveState()` 没有关卡也没有状态参数（接口要为不需要它们的变异保持轻），所以管理器在调用前后把状态**递**进去。这原本是一条 `instanceof` 链，加一条带状态的变异要在链上改两处（设一次、清一次），漏一处就是"续档后倒计时重来"这种安静的错误。

**六之二、一张卡被锁住时，画与拒必须是同一个答案**

`MutationStateS2C.lockedSlots` 是"哪些卡槽被变异锁了"的唯一来源：`MutationManager.lockedSlots()` 把每条**正在行动**的变异的 `isSlotLocked` 折成一个升序列表，服务端在落卡路径上问同一个方法（`isSlotLocked(index)`），客户端把它画成卡上的挂锁。两边各自去问每条变异就会有两份实现，而"画着锁却能种"或"没锁却被拒"都是玩家一眼能看见的错。

**七、其它**

- **击杀统计**同一轮加进 `GameStateS2C`（波数 / 击杀 / 存活 tick），失败屏显示"存活 N 波 · 击杀 M · 用时 T"，无尽模式靠它给出唯一的成绩。
- **`endless` 波表上限 3990**：不是玩法决定，是 `PacketByteBuf.MAX_COLLECTION_SIZE` 决定的（见 `架构变更记录.md`）。
- **`/gamerule mutation_initial_ticks` 立即生效**：首条倒计时在"还没有变异到达"之前按规则实时夹紧（`Math.min`），之后才交给正常间隔 —— 改动立刻生效，又不会把已经走到的间隔拉短。
- **传送带变异的卡池是"这一局的植物卡"**：它替换的是玩家卡槽里 `kind == plant` 的那些卡，工具卡与资源卡原样留在卡槽条上；托盘容量等于被替换的植物卡数量（下限 6），随 `MutationStateS2C.beltCapacity` 上线（客户端读不到变异的传送带块，这正是它以前画成一格宽的原因）。
- **`/mutation add <id>` / `/mutation list`**：按名字把一个变异放上场，用于复现、截图与手感测试 —— 引擎自己掷骰，这是唯一能点名某一个变异的入口（`MutationManager.add`）。
- **游戏规则随存档走**：`level.dat` 的 `Rules` 块写的是**运行中的**规则值（JSON 文本，经各自的 codec 往返），不是关卡定义里那份。没有它，任何运行期改过规则的东西（变异、`/gamerule`）一读档就消失 —— 这条缺口在变异之前就存在，只是没人碰过。**两个例外是"折进规则里的因子"**：变异的倍率（`MutationManager.rulesForSave`）与世界的难度档（见下一条）在写文件前都被除回去，因为两者读档时都会重新乘一遍。
- **四档难度是一个"折进规则里的因子"，不是一条规则**（`common/level/Difficulty`）：`easy/normal/hard/hell` 四个数（僵尸血 / 移速 / 出怪间隔 / 阳光产出）在关卡构造时**乘进** `zombie_health_multiplier` / `zombie_speed_multiplier` / `zombie_spawn_speed_multiplier`（间隔是倒数，`spawnInterval()` 读作"间隔乘多少"）/ `sun_rate_multiplier`，所以模拟里没有任何一处需要知道难度存在。`NORMAL` 四个因子全是 1 且 `ruleFactors()` 返回空表 —— "普通 = 原版"因此是**构造上成立**的，测试、植物 AI、编辑器预览（都没有档案）自然也玩原版。
  - **它随世界存**（`profile.dat` 的 `Difficulty`，缺键读作普通），服务端权威，客户端只拿到一个名字用来画角标。切换走 `SetDifficultyC2S` / `/difficulty <档>`，**运行中的关卡一起改**：先把旧档的因子除出去再乘新的，"关卡自己写的数"因此不会丢；已经放出来的僵尸保持生成时读到的值（生成时读一次的两条规则就是这么定的），下一只才用新档。
  - 写文件时这四个规则要**再除一次难度**（和变异因子同一段代码、同一个理由）：文件里存的是关卡自己的数，读档时 `applyDifficulty()` 再折回来。少了这一步，续档会把难度平方。
- **`DiscardLevelSaveC2S`：存档提示的「重新开始」立刻丢弃那一局**。丢弃原本发生在"下一次开局真正开始"时，而中间隔着一个可以退出的选卡页 —— 玩家退回来后那份被拒绝的存档还在，于是又被问一次、又能继续那个（比如）夜晚的局。现在客户端在打开选卡页**之前**发这个包，服务端只在两处接受它：正在询问这一关（`savePromptPending` 且 id 相符），或已经退出关卡（`level == null`）；正在玩的关卡的文件不删。
