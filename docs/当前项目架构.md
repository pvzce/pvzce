# PVZCE 当前项目架构

> 本文档描述**代码实际形态**（as-built），与 `00`~`03` 的规划文档区分开：规划文档说明"要做什么"，本文说明"现在是什么、在哪里改、往哪扩"。
> 规模基准：`pvzce-game` 300+ 个源文件 / 约 4.1 万行，`pvzce-loader` 141 个文件 / 约 2.3 万行（Fabric Loader fork），`pvzce-api` 11 个文件。内容：26 种植物、12 种僵尸、140 个粒子定义。

> 界面冒烟与截图见 `冒烟与截图指南.md`；UI 导航本身见 `UI切换与导航架构.md`；历史（曾经的缺陷与定论）见 `架构变更记录.md`。

## 1. 一句话架构

PVZCE 是一个**独立运行的桌面游戏**，用 Fabric Loader（fork 后内嵌）加载第三方模组，本体分为"平台层 → 框架层 → 内容层 → 表现层"，服务端 60tps 权威模拟、客户端镜像表现，二者通过**包交换**通信（单机也是内存包队列，不是直接方法调用）。

```
┌──────────────────────────────────────────────────────────────┐
│ L4 入口      launcher/PvzceGame → KnotClient（loader fork）   │
├──────────────────────────────────────────────────────────────┤
│ L3 表现      client/{gui, renderer, animation, sound, particle}
│              服务端状态只读镜像，不参与判定                     │
├──────────────────────────────────────────────────────────────┤
│ L2 内容      api/content（Def record + Codec）                │
│              common/capability（可组合能力实现）               │
│              server/{entity, level, ai, command, gamerule}    │
├──────────────────────────────────────────────────────────────┤
│ L1 框架      api/registry · api/tag · common/nbt · Identifier  │
│              common/resource（资源/数据包）                    │
│              common/network（包 + 传输）· common/level（共享态）│
├──────────────────────────────────────────────────────────────┤
│ L0 平台      net.fabricmc.loader（fork）· LWJGL · DFU · Gson   │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向**：L2 依赖 L1 与 `com.pvzce.api`；L3 只读 L1/L2 的注册表与状态；`com.pvzce.api.content.capability` 的方法签名引用服务端实体类型 —— 这是**唯一一处有意的例外**，因为能力本身就是服务端行为，详见 §5.4。

## 3. 框架层

### 3.1 注册表

- 接口 `com.pvzce.api.registry.Registry<T>`，实现 `MappedRegistry<T>`，由 `RegistryAccess` 持有。
- 静态（代码）与动态（数据包）两层：`register` 只能在本体首次冻结前调用；`registerDynamic` 可在每次重载时替换。
- **`RegistryEntryAddedCallback` 由 `MappedRegistry.register/registerDynamic` 统一触发**（`BuiltInRegistries.registerStatic` 只是薄包装）。不要绕开 `Registry.register` 直接写 map。
- `PvzceRegistries` 声明全部注册表键（单数 id，如 `pvzce:plant`）；`PvzceDataLoader.CONTENT_REGISTRIES` 声明**目录名**（复数，如 `plants/`）。**`byCategory()` 是命令层/补全层/标签层共用的分类表** —— 新增注册表只需在这三处各加一行（其中 `byCategory` 一处即可让命令与补全同时生效）。
- 目前注册表：plant、zombie、projectile、resource、slot、tool、scene_element、game_rule、env_var_type、sound_event、level、level_theme、level_category、**damage_type**、plant_capability、zombie_capability、projectile_capability。

### 3.2 `Identifier`

`namespace:path`，规则同 MC（小写 + 数字 + `_ - . /`）。**空 namespace / 空 path 一律非法**，`tryParse` 返回 `null`；`:path` 仍按原版语义解析为默认命名空间。所有"缺失"判定都依赖 `tryParse == null`，因此不要再引入接受空串的解析路径。

### 3.3 资源包 / 数据包

- 栈：内置 `ClasspathPack`（开发期目录、发布期 fat jar）→ `resourcepacks/` → `datapacks/`，高优先级覆盖低优先级。
- `PvzceResourceManager` 提供 `getResource/getAsset/getData/listResources/listResourceStacks`；所有路径拼接走 `PackPaths`（**不要**自己拼 `prefix + "/"`）。
- 数据包目录约定：`data/<ns>/<注册表目录>/<相对路径>.json`，**id 由完整相对路径决定**（`plants/tier1/pea.json` → `ns:tier1/pea`），文件内显式 `id` 会覆盖它；同一注册表内 id 冲突会报错。包根就是命名空间，与 MC 一致。
- 标签：`data/<ns>/tags/<注册表目录或注册表 id>/<名字>.json`，单数与复数**两种拼写都接受**；格式 `{"replace":false,"values":["ns:id","#ns:other"]}`。标签 id = 命名空间 + 注册表目录下的相对路径，与 MC 一致（`data/c/tags/plant/plantable.json` → `#c:plantable`）。
- **标签按注册表分开**：`#c:plantable` 在 `scene_element` 与在 `plant` 里是两个互不影响的标签（同 MC）。`PvzceTags.RegistryTagView` 把"注册表 + 标签"绑在一起查询，避免同名的两个标签被读串。
- 约定标签（`c` 命名空间）承载**全部放置规则**，内置包在 `data/c/tags/{scene_element,plant}/` 下提供；模组往同名标签追加条目即可扩展，`PvzceTags.PLACEMENT_TAGS` 是完整清单，缺一个会在关卡构造时被 `LevelValidator.validatePlacementTags()` 点名。
- 加载结果 `LoadResult{loaded, errors}`：`PvzceServer.reloadData` 统一上报；客户端重载也会记录标签错误。

### 3.4 NBT 与存档

- `common/nbt` 是自研 MC 兼容实现：根必须是 compound；数组/列表长度有上限并报 `IOException`；`put/add` 拒绝 null；**数值 getter 跨类型放宽**（写成 int、读成 float 是合法的）。
- 版本：`PvzceConstants.SAVE_DATA_VERSION` 写进每份存档；**没有迁移链**——项目未发布，不存在需要迁移的存档，读到 `GameState` 缺失或非 running 的记录一律当没有存档（`LevelServer.restore`）。
- **每个关卡一个文件**：`saves/<world>/levels/<key>/level.dat`，内含 DataVersion / LevelId / GameState / Winner / Tick / 波次进度 / 队伍资源与解锁 / 卡槽 / **Belt（传送带上的卡与下次出货倒计时）** / 场景网格 / **Entities 快照列表**。`saves/<world>/level_status/<key>.dat` 记录通关。
- **存档目录键 `key` 必须是单射的**（`LevelKey`，纯函数）：= `十六进制(命名空间) + "__" + 转义(path)`（`%`→`%25`、`/`→`%2F`）：命名空间段只用 `[0-9a-f]`，路径段不会出现这些字符，两半各自单射，所以不同关卡 id 永远不共目录（`LevelKeyTest.distinctIdsNeverShareAKey` 用一批"命名空间与路径都由同一批字符组成"的恶意 id 钉住）。目录名不像 `ns + "__" + path` 那么好读，这是有意的取舍。
- **旧键的存档不做改名**：项目未发布，不存在用旧键写出的存档。若本机留着早期版本的 `saves/`，它的进度按既定取舍从头开始。
- 客户端也有一份同样的键推导（`LevelMove`）：编辑器换组要能在没有服务器往返的情况下搬存档，两处必须完全一致，`LevelMoveTest` 与 `LevelKeyTest` 各钉一半。
- 关卡目录/文件名规则集中在 `PvzceServer` 的 `sanitizeWorldName` / `levelKey` / `worldPath` / `levelDir`，客户端同名世界也用同一正则（`[^A-Za-z0-9_-] → _`）。
- **每个世界一份玩家档案**：`saves/<world>/profile.dat`（`PlayerProfile`），三个字段：`Coins`（金币钱包，**没有上限**）、`Unlocked`（已解锁卡 id 列表，外加 `UnlockAll` 沙盒标志）与 `SeedSlots`（背包卡槽数，默认 `PvzceConstants.DEFAULT_SEED_SLOTS` = 8，上限 `MAX_SEED_SLOTS` = 12，扩容入口是 `PlayerProfile.addSeedSlots`）。钱包只有"32 位字段不溢出"这一条边界（`COIN_LIMIT`），四个币种资源的 `max_stack` 与它同值。这是**唯一跨关卡存在**的状态 —— 队伍资源、卡槽都随关卡生灭。缺文件 / 空记录 / 读失败都回落到 `PlayerProfile.starter()`（豌豆射手 + 铲子），旧世界因此照常可玩。写点只有 `onLevelFinished`、`leaveLevel`、`createLevel` 换世界前与 `PvzceServer.run()` 的 `finally`；**不要在 `stop()`（关停钩子线程）里写文件**。

### 3.5 网络

- **协议表只有一张**：`PvzcePackets`，每行 = `id + 方向 + 类 + 解码器`。C2S id `< 64`，S2C `>= 64`。`PROTOCOL_VERSION` 随 `LevelInitS2C` 下发，客户端版本不符直接拒绝加载。
- **手动放小推车**：`ReleaseMowerC2S(row)`（`PROTOCOL_VERSION` = 15）只带行号，能不能放由服务端算（见 §4.9）。
- **传送带的整表同步**：`BeltSyncS2C(cards)`（`PROTOCOL_VERSION` = 9）替换客户端的整个卡槽条——见 §4.9，它存在的理由是 `SlotSyncS2C` 的 upsert 说不出"这张卡没了"。
- **背包/金币/解锁/卡槽**：`ProfileS2C(coins, unlocked, unlockAll, unlockedLevels, seedSlots)` 同时携带**卡**、**已购买关卡**与**背包卡槽数**，前两组 id 分开存（见 §4.8），卡槽数随档案走（`PROTOCOL_VERSION` 因此 = 13）。
- **实体同步带护甲值**：`EntitySpawnS2C` / `EntityUpdateS2C` 末尾各多一个 `armor` 字段（剩余护甲，`NO_ARMOR = -1` 表示这个实体根本没有护甲能力）。**0 与 -1 不是一回事**：0 是"戴过护甲、现在被打光了"（路障僵尸的光头状态），-1 是"从来没戴过"；客户端按这个差值决定是画破帽子还是不画帽子（见 §6.3 的 `EquipmentArt`）。服务端只发数字，**档位贴图是客户端的事**——`ArmorDef.durability` 是分母，客户端拿同一个数自己除（`PROTOCOL_VERSION` 因此 = 14）。
- **奖励包多两个字段**：`LevelRewardS2C(..., mowers, mowerCoins)`——本局结束还剩几辆小推车、它们折了多少钱。金额单独发是为了**表现与账目一致**：客户端逐辆车的金币动画按这个数生成，不去数自己的镜像（见 §4.5）。
- **卡条、关卡行与奖励各多一个事实**（`PROTOCOL_VERSION` 因此 = 17）：`SlotInfo.cooldownTotal`——这张卡在本关的冷却一共多少 tick，卡条拿它当分母画充能（见 §4.4）；`LevelInfo.cleared`——这一关在这个世界里**通关过至少一次**，列表行右侧的奖杯读它（见 §6.2.1）；`LevelRewardS2C.rewardItem` / `rewardItemAmount`——这一局发到手的是哪个资源、几个（见 §4.5）。
- `PacketRegistry.register` 对重复 id / 重复类**抛异常**；未知 id 明确报错，不会串包。
- 序列化：
  - 集合/可选/identifier 一律用 `PacketByteBuf` 的 helper（长度对剩余字节校验，越界抛 `DecoderException`）。
  - 字段 ≥3 个的包用 `PacketStruct`：**每个字段的 getter / writer / reader 写在同一行**，`encode`/`decode` 遍历同一列表，从结构上消除"写读顺序漂移"。
  - 新增包：在 `PvzcePackets` 加常量 + 一行 `def(...)`，并在 `PacketProtocolTest.samplePackets()` 加样本（否则 `theSampleSetCoversTheWholeProtocol` 会失败）。
- **背包/金币带来三个包**（`PROTOCOL_VERSION` 因此 = 4）：`ProfileS2C(coins, unlocked, unlockAll)`（随关卡列表与每次变更下发）、`LevelRewardS2C(levelId, collectedCoins, bonusCoins, totalCoins, unlockedCard)`（结算，表现用）、`CreateWorldC2S(worldName, unlockAll)`（世界目录在客户端建，档案由服务端写）。
- 传输：`MemoryPacketTransport`（单机，双向队列，`close()` 会传播）与 `TcpPacketTransport`（LAN 骨架、**非阻塞**、帧长上限 16MiB）。`Connection` 负责编解码、分发、异常记录与关闭传输；解码失败会带堆栈断开而不是静默丢弃。

## 4. 服务端

### 4.1 线程与主循环

`PvzceGame.main` 装配：`BuiltInRegistries.bootstrap()` → 调用 `main`/`client` 入口点 → `Connection.createMemoryPair()` → 起服务器线程 → 客户端主循环。

`PvzceServer.run()` 顺序（**顺序有意义**）：
1. `PvzcePackets.register()`、`BuiltInRegistries.bootstrap()`
2. 建目录、`resourceManager.init(gameDir)`
3. **`invokeServerEntrypoints()`** —— 必须在数据加载之前，否则内容注册表已冻结，mod 注册内容会抛异常
4. `reloadData(false)` —— 冻结内容注册表
5. 循环：处理命令/stdin/网络 → `tickRate.advance()` → `level.tick(bridge)` → 每 250ms 发 `DebugInfoS2C`

`PvzceTickRateManager` 负责 60tps 基准、`/tick rate|freeze|step|sprint`。

### 4.2 `LevelServer`

权威关卡。要点：

- 实现 `LevelAccess`（`api/entity/LevelAccess`）—— 能力、AI、命令通过它访问关卡，而不是直接摸内部字段。
- **所有实体入场只经过 `spawn*`**：`spawnPlant` / `spawnZombie` / `spawnProjectile` / `spawnArcProjectile` / `spawnResource`。`addEntity` 会设置关卡尺寸（网格派生用关卡真实尺寸，**不是**默认 9×5）。
- `spawnPlant` 是**唯一的植物创建路径**（玩家、AI、命令、关卡初始实体、存档恢复全部走它），负责叠放高度、花盆偏移、`onPlaced`、`onRemoved`。
- `bridge` 是环境字段：`tick()` 与玩家动作 API 用 `withBridge`（try/finally）设置，因此任何提前 return 都不会泄漏。
- 场景是 `SceneGrid<SceneElementDef>`，坐标解析统一走 `SceneCells.parse`（畸形条目被忽略并记录，不会让关卡构造抛异常）。
- 日夜：`PvzceClock` + `common/level/DayNightCycle`（纯函数，客户端共用）。**不要在别处重算周期数学**。
- `LevelValidator` 在构造末尾收集关卡数据的全部问题（未知规则/非法取值/未知卡槽/畸形场景/未知初始实体）并一次性打印，**不中断构造**。
- 波次：`normalizeWaves`（末波必为 FINAL）→ `tickWaves` → `PendingWaveSpawn` 队列按 `WaveDef.SPAWN_INTERVAL_TICKS` 逐个放怪。
- **小游戏关卡由 `mechanics` 列表描述**（见 §4.9）：`conveyor`（传送带）把卡槽变成带子，`placement_zone`（可种植区）由 `canPlacePlant` 统一判定，`mower`（小推车）决定哪些行有推车，`tool`（关卡自带的工具，可声明成"点击即用"）决定空手点击做什么，`grave_spawner`（会补的墓碑）让僵尸从墓碑里持续冒出来。**没有声明 card source 的关卡隐式得到 `deck`、没有声明 `mower` 的关卡隐式得到"每行一辆"**，两个默认都在 `LevelMechanics.effective` 里决定。
- **`plantAt` 会跳过不占格的植物**：`PlantEntity.occupiesCell()` 为假（只有 `pvzce:bowl` 会这样回答）时，僵尸不啃、手套不搬、铲子不铲。这是"植物正在离开这一格"唯一的表达方式，而不是给僵尸的啃咬循环加特例。

### 4.3 进入/重开关卡的协议语义

两个包都能"进入关卡"，语义不同，**不要混用**：

**阵营由关卡声明，不由客户端猜**：`LevelDef.playable_teams`（写在 `win_team` 旁边，缺省＝`teams` 全部可玩）说明这一关有哪几方是人能玩的，服务端按它算出每一条 `LevelListS2C.TeamInfo.playable` 下发。**只有一个可玩队伍时 `LevelSetupScreen` 整个被跳过**（判据 `PvzceClient.offersTeamChoice`，判定点只有 `enterLevelFromMenu` 一处，关卡列表、冒烟钩子与编辑器「测试」都经过它），于是内置关卡从列表点进去就是选卡页/开局，不再先问一次"要当植物还是僵尸"。一个可玩队伍都没有（数据写错）时仍然显示这一屏：看得见的菜单比"以空阵营开局"好。

| 包 | 谁发 | 语义 |
|---|---|---|
| `RequestLevelC2S(restart)` | 关卡列表的「下一步/继续游戏」与 `LevelSetupScreen` 的「开始游戏」 | "进入这个关卡"。已经在跑同一关卡且 `restart=false` → **原样 resync 当前实例**（相当于继续）；`restart=true` → 重开 |
| `StartLevelC2S(restart, seeds)` | 选卡界面的「开始游戏」 | **"用这套卡组开一局"**。选卡只发生在一局开始之前，所以目标关卡若已经在跑且 `restart=false`，服务端会**重开并应用这套卡组**，而不是 resync |

**进入决策只有一处**：`PvzceClient.enterLevelFromMenu(info)`，判据是列表给的 `LevelInfo.hasRunningSave()`（读的是**独立的 `runningSave` 字段**，不是 `status` 字符串 —— 见下方「通关优先于进行中」）：

- **有存档** → 直接发 `RequestLevelC2S(restart=false)`：服务端 `createLevel` 先把整个存档（棋盘/实体/波次/钱包/卡槽）加载并下发，**然后**才发 `LevelSavePromptS2C`，客户端在已加载的关卡之上弹出「发现存档」。**不经过关卡准备，也不经过选卡** —— 存档里已经有卡组和阵营，为一局即将被继续的游戏挑卡是没有意义的。
- **无存档**（含"已通关"）→ 关卡准备（`LevelSetupScreen`，选阵营）→ 选卡界面 → `StartLevelC2S(restart=false, seeds)`。

列表里的「进行中」是**某个世界**的 `saves/<world>/levels/<LevelKey>/level.dat` 存在与否，所以：

> **通关优先于"进行中"**：通关标记是"这一关已经通关"，**一旦写下就不会被收回** —— 重玩一局已通关的关卡、那局打输了、或者中途退出，这一关仍然是已通关。判定用的是 `isLevelCompleted`（只看标记文件），它同时是解锁规则里 `clearedLevels` 的来源，所以"有一局重玩等着继续"不会把后面的关卡重新锁上。
>
> **"有没有存档"是另一件事，走另一个字段**：`LevelInfo.runningSave`。`status` 只负责列表行上显示什么（有存档就显示"进行中"，否则显示"已通关"），`LevelInfo.hasRunningSave()` 读的是 `runningSave`；进入判定先看 `runningSave`，有就直接加载存档并在其上询问，完全不经过关卡准备与选卡。

- 世界选择页有**「全解锁」开关**：勾上再创建世界会发 `CreateWorldC2S(world, true)`，服务端写出 `UnlockAll` 档案（沙盒世界拥有所有卡，包括以后新增的）。世界目录仍由客户端创建（列表直接读盘），档案由服务端写。
- `PvzceClient.setCurrentWorld()` 换世界时**丢弃已缓存的列表**（否则会把上一个世界的进行中标签用在另一个世界上，而它正是进入决策的输入）；
- 服务端 `refreshLevelList()`（`/reload` 后主动补发）按**客户端最后一次请求的世界**下发，而不是服务端自己的 `currentWorld`（关卡之间它是 null，会被规范化成 `world`）。

选卡界面不关闭自身，等 `LevelInitS2C` 到达后由 `PvzceClient.onLevelInit()` 用 `setScreenReplacing` 重建整个界面栈，所以暂停对话框/选卡界面不会残留在新关卡下面。

**暂停菜单的「重新开始」**（`PvzceClient.restartCurrentLevel()`）走的是"先真正关闭当前关卡，再进入该关卡的正常选卡流程"：

1. 发 `LeaveLevelC2S`，服务端 `leaveLevel()` 会**先存档再 shutdown**，因此放弃重开也不会丢进度（关卡列表里仍显示"进行中"，可继续）；
2. 客户端清空本关全部镜像状态（`clearLevelClientState()`：实体/粒子/动画/音乐/存档提示/镜像），并用 `setScreenReplacing` 把界面栈换成选卡界面 —— 旧关卡不会以冻结实例留在下面；
3. 「开始游戏」→ `StartLevelC2S(restart=true, seeds)`：服务端 `createLevel(restart=true)` 会**删掉第 1 步写的存档**并开新局；
4. 「返回」/ESC → `showLevelList()`，回到当前世界的关卡列表（**不会**回到刚被关闭的关卡）。

### 4.4 玩家、卡槽与资源

- `SlotResolver.resolve(id)` 是**"这张卡是什么"的唯一答案**（服务端卡槽、客户端选卡池、校验共用）。未知 id 会记录一次并跳过。
- `PvzcePlayer.createPlantPlayer` 直接用 `SlotResolver`，因此"选卡界面能选的"与"服务端发放的"必然一致。
- `Team` 持有共享资源与解锁集合；`Slot` 持有 index/kind/content/costSun/**cooldownTicks**/cooldownLeft/usesLeft。
- **卡片冷却 = 卡自己的数 × 关卡倍率**，两半各在一处：
  - 卡自己的数（`Slot.cooldownTicks`）在建卡槽时从 `SlotResolver.ResolvedCard` 抄下来（槽定义优先、否则回落到植物/工具定义），传送带发的卡是 0；
  - 关卡倍率是规则 `pvzce:seed_cooldown_multiplier`（缺省 1），**唯一换算点**是 `LevelServer.effectiveCooldownTicks(slot)` → `CardCooldown.effective(base, multiplier)`，两条消耗路径（种植物 `DeckCardSource.spend`、用工具 `LevelServer.useToolInternal`）都调它，`toSlotInfo` 也调它并把结果放进 `SlotInfo.cooldownTotal`。
  - 于是卡条画的充能是"还剩多少 / 这张卡在本关一共多少"，两个数同源；**不要在客户端重新推一遍倍率**，也不要让某一处直接 `startCooldown(卡自己的数)` —— 那样关卡缩放的只有等待、画出来的却是另一段长度。改倍率（`/gamerule`）对**已经在条上的卡**立即生效：倍率在消耗那一刻读，不在发牌时烘进 `Slot`。

### 4.5 背包、金币与关卡奖励

**背包、卡池与关卡奖励**：

**背包（`PlayerProfile` + `SeedOptions.cardPool`）**

- 解锁只覆盖**植物与工具卡**；资源卡**不背包锁**（`requiresUnlock` 对资源返回 false），但**仍然要占卡槽**：`pvzce:sun` 的 `collectible_without_card` 是 `false`，银行只在卡槽条里有阳光卡时才画出来，收阳光正是那张卡买到的东西。所以每个关卡的 `slots` 都列着 `pvzce:sun`，`SeedOptions.cardPool` 也照常把它摆在选卡池里。判定只有一处：`SlotResolver.requiresUnlock`（服务端 `PlayerProfile.owns` 与客户端 `ClientProfile.owns` 都调它，两份"锁没锁"不允许分叉）。
- **关卡的 `slots` 是本关固定卡，无视背包**：关卡可以"借"卡给玩家（教学关给一张土豆雷），所以 `sanitizeSeedSelection` 只过滤**自选**，从不过滤关卡钉住的卡。玩家能自选的池子 = 背包已解锁卡 − 固定卡，填到解析后的总卡槽数。
- **总卡槽数只有一个来源**：`LevelDef.effectiveMaxSeedSlots(profileSlots)` —— 关卡**写了** `max_seed_slots` 就用它（1-1 的 2、1-4 的 8 是关卡设计），**没写**就用背包的 `seedSlots`（默认 8）。"没写"因此是 `LevelDef.UNSET_MAX_SEED_SLOTS`（-1）而不是某个数字：拿字面量 6 去比会把升级过的背包悄悄压回去。服务端在 `SeedContext` 里解析一次（`SeedContext.all` / `forProfile`），`LevelPayload` 带的就是解析后的数，所以选卡界面看到的行数与服务端收得下的卡数不可能分叉；`/profile slots <n>` 是背包这半边的操作入口（商店以后走同一个 `PlayerProfile.setSeedSlots`）。
- **卡池只有一个来源**：`SeedOptions.cardPool(def, owns)`（已解锁卡 + 关卡自己的卡），`PvzceServer.sendLevelList` 与 `LevelServer.SeedContext.forProfile` 都用它，所以"选卡界面看得到的"与"服务端收得下的"是同一份。`SeedOptions.forLevel(def)`（不过滤）仍用于测试与编辑器预览。
- 固定卡已填满总卡槽时没有可选空间：判定抽在 `SeedOptions.hasNothingToChoose(pool, maxSlots, lockedIds)`（**纯函数**，屏幕与"存档提示框重开"两处共用），选卡屏进入**预览模式**（见 §6.2 的"选卡屏的入场编排"一段）；存档提示框的「重新开始」则直接重开。
  > 判据是"总卡槽数 − 关卡固定卡数"，**不是"已选卡数"**：用"已选卡数"去减会把"记住的卡组正好填满卡槽"（1-2 第二次进入）读成"没得选"而自动开局，玩家再也不能换卡。
- 新世界默认解锁 `PvzceIds.STARTER_PLANT`（豌豆射手）+ `STARTER_TOOL`（铲子）；`CreateWorldC2S(world, unlockAll)` 让"创建世界"对话框的**全解锁**勾选写出 `UnlockAll` 档案。沙盒用**标志**而不是展开成 id 列表，这样以后新增的内容也自动解锁。

**金币（四种面额，`PvzceIds.COIN_DENOMINATIONS`）**

- 金币不是一种资源而是**四种**，因为原版就是四种不同的东西（白/银币 10、金币 50、钻石 1000、钱袋 250）：一个 `pvzce:coin` 无法告诉玩家刚捡到的是 10 还是 1000。它们是普通 `ResourceDef`，`default_value` 就是面值，`collectible_without_card: true`（捡钱不需要卡槽，也不看 `Team.unlockedResources`）。资源目录 `data/pvzce/resources/{coin_silver,coin_gold,diamond,money_bag}.json`。
- **掉落时 `amount` 直接写成面值**（`defaultValue × coin_drop_amount`），所以队伍那份资源计数本身就读作金币数，HUD 与钱包只需要**求和**，换算阶梯只存在于资源定义里一处。
- **没用上的小推车折成金币**：胜利结算时 `PvzceServer.awardProfile` 数出还停在车道上的车（`LevelServer.readyMowerCount` → `MowerMechanic.Rig.readyCount`），每辆按**金库里的金币**计价（`mowerCoinValue()` 读 `pvzce:coin_gold` 的 `default_value`，不是字面量），并进本局 bonus。失败一辆也不算——没有"没被突破的车道"这回事。客户端在**点击奖励**那一刻让每辆车的原地冒出一枚金币飞向左下钱袋，计数用的是包里的 `mowers`（不是自己数的），并且把这笔加进 HUD 的金币收款条，否则金币飞向一个不动的数字（§4.5 的"点击奖励"一段）。
  > **车必须同时消失**：金币从车的位置起飞、车还在原地站着，读起来就不是"车变成了金币"。
  `ClientMechanics.consumeParkedMowers(level)` 是**读并标记**的同一个调用（`parkedMowers` 只读），
  被标记的行不再绘制。它不是 `STATE_USED`（那是"僵尸从这条道过去了"、服务端说的），而是纯客户端
  的一次核销——关卡在胜利那一刻就停止 tick 了，服务端没有第二句话要说。
- 美术：三个硬币/钻石由 `tools/reanim_to_pvzce_all.py --entity coin_silver --entity coin_gold --entity diamond --input-dir refer/im5/reamin` 从原版 reanim 生成，钱袋是单张 `textures/entities/money_bag.png`（`ResourceDropEntity` 的平铺贴图回退路径）。**生成时排除了 `COINGLOW` 与 `DIAMOND_SHINE`**。
  `refer/anim` 是**完整**的原版动画集（146 个 reanim），`refer/im5/reamin` 只有硬币那几个；新增内容优先去 `refer/anim` 找。
  **硬币是「弹出来」的**：四种面额都是 `drop_motion: rise`，`rise_height: 0.3`、`rise_scatter: 0.25` —— 从僵尸身上弹起 0.3 格再落下，落点随机左右偏移最多 0.25 格（同一个僵尸一次掉好几枚，方向一致会看起来像同一个东西复制）。向日葵产的那朵阳光仍然是 `rise_height` 默认的 0.5、`rise_scatter` 为 0：它属于那朵花，要落回原处。横向位移由 `LevelServer.spawnResource` 用关卡自己的 `Random` 掷出后交给实体（实体不自己掷骰子，否则读档会重掷）；`riseTicks`/`riseOriginX`/`driftX` 都进存档，飞行中途存档能原地续上。
  **掉落尺寸**：四种面额都声明了 `render_scale`（三枚硬币 0.25 ≈ 0.2 格，钱袋 0.55），因为掉落物的默认大小是 0.8 格 —— 一枚硬币按 0.8 格画出来比一格草坪还显眼，看着像一块发光的圆盘而不是硬币。
  **动画掉落物的尺寸契约**：掉落物和植物、僵尸同一套规则 —— **画多大就是模型里写多大，再乘 `render_scale`（两个轴同倍率）**。没有任何自动拟合：曾经那套"只把宽度拟合到 0.8 格、高度取自动画文件"的写法是自相矛盾的（模型尺寸必须写成拟合结果的那个数），而且它按**模型最大边**拟合，于是"比本体还宽的光晕"决定本体多大——金币的光圈 80px、币面 43px，币面被画成自己美术的 54%，宽度那一轴还要再被压一次。现在：转换器把每个掉落物的 reanim 缩放到 `EntityVisuals.AUTHORED_DROP_CELLS`（0.34 格，两边共用同一个常量），光晕这类"比本体大"的贴图不进模型（它是粒子/加色层的活），运行时只乘 `render_scale`。`CoinVisualLayoutTest.everyDenominationsModelHasTheSameShapeAsItsArt` 钉住"模型比例 == 美术比例"（非等比就会被画扁）与"作者尺寸就是约定尺寸"。钱袋没有动画、走贴图兜底路径，那条路两个轴都乘 `render_scale`，本来就是对的。
  **产阳光是无声的**：原版向日葵产阳光时不出声，那声属于拾取，由 `ResourceDef.pickup_sound` 在玩家真去点的时候放。金盏花保留自己的出币声（它的掉落是小钱，不是这一关赖以运转的资源）。
  **拾取音效也按资源分开**：`ResourceDef.pickup_sound`（缺省 `sfx/ui/collect`）。阳光用收集音，三枚硬币用 `sfx/ui/coin`，钻石用 `sfx/ui/diamond`。
  **拾取闪光按资源分开**：`ResourceDef.pickup_effect`（可选）是「捡起这个资源时放什么效果」，缺省**什么都不放**。阳光声明 `pvzce:lantern_shine`（200x200 的黄色柔光，每颗 0.7 格、一次 10 颗，**原样保留**）；四种面额**不声明** —— 同一片黄光画在硬币上是把半块草坪糊成黄色，而捡币本来就有收集音效与飞向钱袋的动画在说「收到了」。`LevelServer.collectResourceInternal` 只负责发声音，粒子 id 从资源定义里取。
- **关卡内**的僵尸死亡按 `rewards.coin_drop_chance` 掉 `rewards.coin_drop`（默认 `pvzce:coin_silver`）这枚币（`LevelAccess.zombieDied` → `LevelServer.zombieDied`；实体只报告"我死了"，掉落是关卡数据的事）。金盏花产银币（10 / 24s）。
- **关卡结束**时 `PvzceServer.awardProfile` 把本局收集的金币写进钱包（**胜负都入账**），再按首通/重复发放关卡奖励。**金币**的首通判定是 `level_status` 文件在不在（`levelStatus(...).isEmpty()`），所以重复通关拿的是 `repeat` 那份。**`first_clear` 里的解锁不看这个判定**：只要关卡声明了某张卡的解锁、而背包里还没有它，**任何一次通关都会补发**，已经拥有则是空操作。两者必须分开 —— 首通标记只说明"这一关已经通关"，不说明"这份奖励发出去过"。

**关卡奖励（`LevelRewards`）**

- 关卡 JSON 的 `rewards` 块：`first_clear` / `repeat` 是 `{type:"unlock"|"coins"|"resource", id?, amount?}` 列表，外加 `coin_drop`（掉哪种币，资源 id）/ `coin_drop_chance` / `coin_drop_amount`。默认值 = `LevelRewards.DEFAULT`（首通不给额外奖励、重复给 100 金币、25% 掉 1 枚银币）。`first_clear` 的 **unlock 条目是幂等的**：见下一节"结算与展示"前的说明 —— 已拥有即空操作，缺失就补发，与首通标记无关。
- **`resource` 是第三种奖励形状**：钱包只装得下一个数，所以"发一颗钻石"就是"发它值的那 1000 金币"，而**面值来自资源定义自己的 `default_value`**（`PvzceServer.applyRewards` 读它，不在关卡里再写一遍 1000）。它和 `coins` 一样按首通/重复分支走，并且比 `coins` 多带一件事：`LevelRewardS2C.rewardItem` / `rewardItemAmount` 让客户端**画那个东西本身**——草坪上落下来的是钻石、飞进钱袋的也是钻石，结算页的相框里落的是钻石。**相框只装得下一件**，所以同一列表里第一条资源奖励才被画出来（与 `unlock` 只报第一张卡同一条约定）；其余的照常折算进钱包。
- `type` 是字符串判别式，**DFU codec 看不出拼错的类型**（`"unlcok"` 会正常解码然后什么都不发），所以 `LevelValidator.validateRewards` 必须跑：未知 type、缺 `id`、未知卡/未知资源、`amount <= 0`、掉率 >0 但数量 0 都报出来。

**结算与展示：奖励先落在草坪上，再由玩家领取**

一局胜利**不会**直接弹出奖励页。顺序是（全部在客户端，服务端只发两个包）：

```
GameStateS2C(plant 胜)   → 不播胜利音乐（onGameState 对植物方胜利刻意跳过）
LevelRewardS2C           → InGameScreen.showReward：种子卡/奖励物/钱袋落在**最后一只僵尸死亡的那一格**，从上方落下
等待期                    → 奖励自己闪烁，头顶一枚**上下滑动的金色箭头**（不写"点击领取"）
玩家点击奖励              → 胜利音乐立刻开始；**剩余小推车与奖励各自变成金币飞向左下钱袋**；
                           同时奖励慢慢移到屏幕中央（1.9s）
移到中央                  → 原地再放大一点（0.6s）
放大完成                  → 白光从奖励位置向外扩散（0.7s）→ 全白保持 0.35s → 淡出 0.4s（奖项页在这段淡出里打开）
```

  共约 4s。**等待期只有一枚箭头，不写字**：原版不往草坪上写字，它指着那个东西、让闪烁说完剩下的，
  一眼能看懂，也不用翻译。它用的是**原版自己的贴图**（`refer/im7/particles/DownArrow.png` → `textures/gui/hud/down_arrow.png`），
  不是自绘的：原版那套里就有一个 `AwardPickupArrow.xml`，第二个 emitter 正是 `IMAGE_DOWNARROW`
  加一条 `Position` 曲线 `0 EaseInOutWeak 10 EaseInOutWeak 0`——下去十帧再回来。所以这里照抄的是
  同一张图、同一条曲线，只差把它摆到该在的位置上（32px ÷ 原版 80px/格 = 0.4 格宽）。**白光是从奖励身上长出来的，不是全屏渐变**——它从奖励当时的矩形中心开始、
  半径取"到窗口最远角的距离"，所以扩散结束时无论宽高比如何都已经盖住每一条边；`renderRewardLight`
  画的是一个正方形而不是圆盘，GUI 没有圆和加法混合，而这个速度下方形读起来就是"光从那个方向过来"。
  奖励被领取的**同一步**就发射白光起点（`claimReward` 记录 `rewardRect()` 的中心），所以"移中"与
  "发光"是同一拍开始的。

- `LevelRewardS2C(levelId, collectedCoins, bonusCoins, totalCoins, unlockedCard, rewardItem, rewardItemAmount, ...)` 在 `GameStateS2C` 之后发；它**只是表现**，钱包在发包之前就写好了，客户端不领取也照样拿到金币。
- 奖励掉落物**不是实体**：它是 `InGameScreen` 里的一个世界坐标点 + 三个时间戳（落下 / 领取 / 音乐），因此不进存档、不参与判定，也不需要服务端同意。`rewardRect()` 是**唯一的**矩形来源，绘制与点击命中都读它（点击落点与贴图不可能分叉）。
- **掉落物有三种样子，按包的字段依次判定**：有解锁卡 → 种子卡；没有卡但有 `rewardItem` → 那个资源的美术（钻石画成正方形，不拉进种子包的比例里）；两者都没有 → 钱袋。这三条与 `AwardScreen` 的分支**一一对应**，所以"草坪上看到的"和"结算页相框里看到的"是同一件东西。
- **落点是"最后一杀"**：`LevelRewardS2C` 带 `dropX/dropY`，来自 `LevelServer.lastKillX/Y`（`zombieDied` 里先记位置再掷掉币，所以不掉币的僵尸也算）。没有僵尸的关卡为空值，客户端回落到草坪中央。
- **胜利音乐属于"点击"那一瞬间**，既不属于"关卡结束"也不属于"移到中央"：`PvzceClient.onGameState` 对植物方胜利直接 return，stinger 由 `InGameScreen.claimReward()` 在点击的同一步播放（与升移动画同时开始）。失败没有奖励可领，所以结束时立刻播。
- **金币飞进左下角的钱袋**：每种掉落物飞向**自己的**银行（`bankTarget`：阳光→左上阳光银行，金币→左下钱袋）。按每条动画自己的银行判断：金币只要求钱袋（它本来就是「有变化才显示 2.6s」的回执），阳光才要求阳光银行。
- **兜底**：奖励躺够 `REWARD_AUTO_CLAIM_NANOS`（20s）没被点就自动领取 —— 金币早已入账，这个计时器只是为了不让走开的玩家回来面对一个冻结、且唯一出口是一个他已经不记得要点的精灵的棋盘。
- 没有奖励包的胜利（改过的服务端）走兜底：大号「胜利！」+ 点击任意处离开。
- `AwardScreen` 用 `refer/im5` 的原版奖励页美术，**播 `pvzce:music/zen_garden`**（`ensureMenu`）：关卡已经结束，这一页讲的是玩家带走了什么。`unlockedCard` 非空 → 种子卡落进相框；否则 `rewardItem` 非空 → **那个资源落进相框**（下面两行照常写它值多少金币，因为钱包是唯一真的变了的东西）；都没有 → **本局的金币**（一进场就自己撒一次币 + `pvzce:sfx/ui/moneyfalls`，不需要点）。"继续"走 `PvzceClient.finishLevelAndShowList()`（回关卡列表而不是世界列表）。
  > **这一页是收据，不是第二个领钱的地方**：钱袋留在草坪上炸开、金币飞进玩家一路看着的那个 bank，这一页只报账。
  > 页面**淡入**（`FADE_IN_NANOS`）：它是在白光结束的那一帧打开的，硬切会把白光唯一的意义抹掉。
  - 标题画在**窗口顶部**而不是美术坐标里：奖励页底图是 4:3 且 cover 适配，宽屏下美术顶部那条木牌会被裁掉。
- 奖励页的「继续」用 `Button.Style.SEED_CHOOSER`（木质）而不是默认的金属边框按钮：这一页是木板，金属按钮属于对话框。
- 波次进度用原版 `refer/im6` 的三张图（`FlagMeter` 的上下两条分别是空轨与绿色填充、`FlagMeterParts` 的僵尸头/杆/旗、`FlagMeterLevelProgress` 的铭牌），画在**右下角**，每一块都有含义：`[关卡名] [轨道 + 绿色进度]`，**`LEVEL PROGRESS` 铭牌贴在条的正下方居中**（上沿就是条的下沿，中间不能留缝：它和条是同一件仪表），**僵尸头骑在绿色进度的前沿**（它是进度标记，不是固定在一端的装饰），**只有 huge/final 波才插旗**（小波插旗会让旗子失去"大波要来了"这个唯一含义）。
  - **比例照原图**：条按 `158×23` 的原尺寸 × `METER_SCALE`（0.9，和阳光银行 `70/78` 同一把尺子）画，不拉伸 —— 拉长会把两端圆角压成椭圆、把旗子摊开。
  - **方向从右往左**，和原版一致：绿色填充锚在右端、前沿向左推进，旗子也按镜像排在 `1 - (i+0.5)/总波数`（第一波的旗在最右）。
  - 填充用的是**关卡总进度** `(当前波 + 波内进度) / 总波数`，不是当前这一波的进度 —— 这样前沿正好在该波到来时扫过对应的旗子。
  - 贴图是**上下翻转**加载的（UV (0,0) 在左下角，见 `TextureManager`），所以按 PNG 行号写的矩形要经 `vRangeForRows` 换算。
- **奖励里的钱袋也在草坪上炸开**：`rewards.bonusCoins`（小推车折价 + 重复通关金币等）在没有解锁卡时
  就是那一袋钱，`InGameScreen.payForRewardBag` 按面值换算成若干枚金币（每 100 一枚、至少一枚、最多 12 枚，
  单枚价值 = 总额 / 枚数，所以加起来正好是到账的那笔），从钱袋的矩形中心飞进左下 bank。用的币种是**本关
  `rewards.coin_drop`**（关关卡用银币就飞银币），计数同样加进 HUD 的收款条（`claimedRewardCoins`）。
  > **袋子只赔"小推车之外"的那一份**：`bonusCoins` 是一笔已经含了小推车折价的总额，而小推车各自在
  > 自己的位置上变成一枚金币（`payForParkedMowers`）。两条动画都从总额出发就等于**把车钱画了两遍**、
  > 也让 HUD 的收款条比钱包多走一截，所以 `InGameScreen.rewardOnlyCoins()`（`bonusCoins - mowerCoins`）
  > 是袋子/奖励物这一份，两个 `claimed*Coins` 加起来正好是 `bonusCoins`。
  > 有 `rewardItem` 时袋子换成**那一个资源**飞进钱袋（价值就是那份金币数），而不是把它拆成十枚银币。
- 关卡内金币计数用原版 `coin_bank` 美术画在**左下角**（阳光银行占左上、波次条占右下，左下角永远是草坪），而且是**收据而不是常驻控件**：只在金币数变化后显示 2.6s（末 0.6s 淡出），新关卡开局不会凭空闪一个 0。`bankTarget(resourceId)` 决定收集动画飞向哪个银行 —— 金币落到阳光上会说明错的事情。
- 背包页 `InventoryScreen`（关卡选择页的「背包」按钮）把**未解锁卡也画出来**：只列已拥有的回答"我现在能做什么"，列出未解锁的回答"为什么我种不了坚果墙"，后者才是玩家真正的问题。它只读，不改档案；右上角除了钱包还画出**当前卡槽数**（`pvzce.inventory.slots`），因为那正是"关卡没写 `max_seed_slots` 时我能带几张卡"的答案。
- 关卡选择页右上角显示本世界金币（`textures/gui/award/money_bag`，缺图回退金币贴图）。

### 4.7.1 资源掉落：三种落地方式

资源落地由 `ResourceDef.drop_motion` 决定（`fall` / `rise` / `landed`），并且**同一份资源可以两种都有**：天上掉的阳光是 `fall`，向日葵产的那一朵经 `LevelAccess.spawnProducedResource` 明确要求 `rise`（先上浮 0.5 格再落回原点）。金币一律 `landed` —— 生成即在原地。

阳光的亮度是**分层**问题：它的动画是三层叠加——一个很小的亮核心（36px）加两圈更大的半透明光晕（79/116px），所以放大后看着"又亮又没有实体"。修法是**调低两圈光晕的 alpha**（3 → 0.45、2 → 0.55），而不是整体压暗：整体压暗（`EntityVisuals.DROP_TINT`）同时也会把金币变灰，而光晕本身仍然在洗白草坪。

**掉落物的大小与形状只有一处可改**：`EntityVisuals.DROP` 给出掉落物的默认大小（0.8 格，宽高同一个值），**单个内容还可以用自己的 `render_scale` 覆盖它**（见下）。阳光、银币、金币的动画都按同一个倍率缩放，影子不再被单独拉宽，所以画成圆的阳光在草坪上就是圆的。下落时长 300 tick。

**爆炸闪光会膨胀**：`pvzce:pow`（灰烬类与 Boss 落地的爆炸）声明了 `scale_curve`，画出来的边长从 0.04 格长到 0.1 格（`scale` 0.2 × 曲线 0.2→0.5，曲线本身是绝对尺寸，与原版 `ParticleScale` 同单位）。
原版 `Pow.xml` 的 `ParticleScale` 是 `.2 .5,7`——一个范围加一个曲线类型，而转换器把三个数字读成了
(value, time) 关键帧，于是整条增长被压平成"全程 0.2 格"，爆炸看起来只有一个很小的贴图。
引擎一直支持 `scale_curve`，少的是那份数据；`[a b]` 形式的范围现在由转换器读成直线，
带时间/曲线类型的（`,7`、`,60 0`）仍保持常数——**手写**这类曲线是唯一的办法，`pvzce:pow` 就是手写的。
`ParticleDefinitionTest.theExplosionFlashGrowsOverItsLife` 钉住它。

**实体渲染缩放（`render_scale`）**：`PlantDef` / `ZombieDef` / `ProjectileDef` / `ResourceDef` 都能声明 `render_scale`（`ContentDefs.RENDER_SCALE_CODEC`，默认 1，夹在 0.05~8），客户端据此把该内容的art 整体放大或缩小，**两个轴同倍率，所以形状不变**。它是纯表现：不参与命中盒、收集半径或任何服务端模拟，因此**不进包、不占 `PROTOCOL_VERSION`** —— 客户端本来就会加载同一份数据包，两侧各自从定义里读同一个数。取值只在 `EntityArt.renderScale` 一处解析（动画路径 `AnimationManager.scalesFor`、无动画时的贴图兜底、以及影子 `InGameScreen.drawShadow` 都调它）。阳光用 `render_scale: 1.2`；它的三层光晕在 `animations/resource/sun.json` 里按"外圈约 1.6 倍于核心"排布，这样放大的是整颗太阳而不是只有中心，两圈光晕各自声明 `"blend": "add"`。

### 4.7.2 波次节奏：每波自己的出怪间隔

`spawn_interval`（tick，可缺省）写在**每一波**上，不是关卡上，也不是全局常量：简单关卡的第一波 8 秒一只、最后一波 6 秒一只；困难关卡最后一波 2.5 秒一只。缺省 300 tick（5 秒），**下限 15 tick**（`WaveDef.spawnInterval()`）。
「把前期的节奏放慢」与「最终波多快」必须分开。

**`delay` 是两波之间的间隔，从上一波把僵尸放完那一 tick 起算**（`tickWaves` 在 `pendingWaveSpawns` 还有货时冻结 `waveIntervalTicks`，只有第一波例外）。
这一点是**必须**的，不是优化：从触发时刻起算时，上一波的出怪队列还在跑、下一波的倒计时就已经开始，两波的队列于是同时放怪 —— 关卡把前几波写成 10 秒一只，玩家看到的却是两波混在一起的 4~6 秒，这就是 1-2 / 1-3「僵尸一起出」的来源。`updateWaveWarning` 里那句「`waveIntervalTicks` 也会在放怪期间跑过 `nextWaveDelayTicks`」的注释是同一件事的另一面。
写数据时仍应满足 `(数量-1) × 间隔 ≤ 下一波 delay`（让一波放完再等一会儿才来下一波），但**违反它不再会让两波混在一起**：现在的后果只是"上一波刚放完，下一波立刻就来"。

**开局两波不看 `spawn_interval`，看玩家什么时候把上一只打死**：
`WaveDef.holdUntilDead(waveIndex)` 给出这一波要等上一只僵尸多久，实现点在 `LevelServer` 的两处门：

| 门 | 规则 |
|---|---|
| 波内（`PendingWaveSpawn`） | 上一只**一死就出下一只**；`1200` tick（20 秒）还没死就照出，不拖住关卡。这个等待**取代** `spawn_interval`，不是叠加 |
| 波间（`openingWaveStillOnTheField`） | 倒计时**照常走**（清得早不会白等），只把**已经到点的到达**扣住，等场上清空；同样 20 秒封顶。被扣住时大波横幅继续挂着，所以大波不会在横幅熄灭之后才静悄悄地来 |

> 这里曾经写成"上一波没清完就**冻结倒计时**"，结果玩家把场上清干净之后还要再空等一整个 `delay`（大波前最明显）。现在的模型是：**延迟照常跑，只扣住到达** —— 玩家清得快 = 完全按关卡节奏，清得慢 = 该到的那一波等到清完（≤20 秒）立刻来。

- **默认只对每一关的前 2 波（`WaveDef.EARLY_WAVE_COUNT`）且必须是 `small` 波**生效：一次 9~12 只的 huge/final 是"这一关把家底全掏出来"，一只一只等会把两分钟的波拉成二十分钟。
- 三态字段 `hold_until_dead`：**缺省**＝按上面的默认规则；**写 0**＝完全不门控（回到纯 `spawn_interval`）；**写正数**＝换成那个封顶值。写 0 与不写在数据里是两件事，所以字段是 `Optional<Integer>`（与 `mower.rows` 同一个理由）。
- 门控是**滚动**的：第 2 只等第 1 只、第 3 只等第 2 只；超时放行之后，下一只只看它前面那一只。
- 两个门与队列的等待状态都进存档（`OpeningGate*` / `HoldTicks` / `TicksUntilNext`），所以读档续上的开局不会突然变回旧节奏。**唯独"正在等哪一只"不存**：实体 id 出自进程内的计数器（`Entity.NEXT_ID`），存下来的数字在下一个进程里可能指向另一只僵尸；读档后的队列改按封顶值走，直到它再放出一只可以跟的僵尸为止。
- 这条规则**不是**靠调大 `spawn_interval` 实现的：间隔是"关卡认为多快"，门控是"玩家实际多快"，两者混在一起会让同一个数字在别人机器上表现不同。

### 4.7.3 大波提示的生命周期

`waveWarningActive` 只在 `tick()` 里被清除，所以**任何让关卡停止 tick 的结束都必须自己清它**。`markEnd` 会一并清掉提示与进度，判据里写着 `remaining > 0`（`nextWaveDelayTicks` 在最后一波释放后是 `-1` 这个哨兵值），两条都有回归用例分别钉住。

**公告在存档恢复后不会重播**：`announcedWaves` 不是存档字段，所以 `restore()` 会按 `NextWaveIndex` 把它重新填满 —— 索引之前的波次都已经进场过，也就都已经宣告过，`triggerWave` 因此看不到空的已宣告集合。客户端另有一道保险（`InGameScreen.playEffectSound`）：同一个关卡实例内，`awooga` / `hugewave` 在 90 秒内只会真的播一次，其余服务端路径重复发也不会再响；呻吟之类该重复的音效不受影响。

**公告本身由 `announcedWaves` 集合保证每个波次索引只播一次**：`triggerWave` 是唯一发射点、且会推进索引，所以干净的一局本来就只播一次——但那是"碰巧"而不是保证，从存档中途恢复或将来有人直接调用 `triggerWave` 都可能让警报响第二遍。

**大波音效属于"预警"，不属于"到达"**：`hugewave`（原版 Dave 那句 "A huge wave of zombies is approaching!"）由 `updateWaveWarning` 在预警窗口**开启的那一 tick**发出（`announceWaveWarning`，按波次索引去重），与屏幕上那行红字同一拍淡入。它不能等到**波次到达**时才响：那时红字已经淡出，玩家会先读到"一大波正在接近"、几秒后才听见同一句话。final 波到达时照旧只放 `awooga` + `FINAL WAVE` 横幅，两者本来就是同一拍。**没有预警窗口的大波**（`warning_ticks` 为 0）会退回"到达时播一次"，两种路径互斥——预警已经宣告过的索引不会再在 `triggerWave` 里补一次。

### 4.8 关卡解锁条件

**关卡可以声明自己需要什么**：

```jsonc
// data/pvzce/levels/yard/adventure/1_2.json
"unlock": {
  "requires": [
    { "type": "level", "id": "pvzce:yard/adventure/1_1" },  // 通关该关
    { "type": "card",  "id": "pvzce:sunflower" },           // 已解锁该卡
    { "type": "coins", "amount": 500 }                      // 持有金币
  ],
  "cost": 1000,      // 可选：花这笔金币一次性买下本关
  "hidden": false    // true = 未解锁时整行不出现（隐藏关）
}
```

- **默认不上锁**：没写 `unlock` 块的关卡永远可玩，所以既有自定义关卡、数据包、编辑器新建的关卡全部不受影响。`LevelDef.unlock()` 缺省是 `LevelUnlock.NONE`。
- 规则实现是 `common/core/` 的 **`LevelUnlocks`（纯函数）**，与 `LevelGrouping` 同一层、同一纪律：读一个 `Context{已通关集合, 已购买集合, ownsCard 谓词, 金币, 沙盒}`，产出 `State{unlocked, buyable, cost, unmet, reason, hidden}`。服务端求值、客户端**接收结论**（`UnlockInfo` 随 `LevelInfo` 下发），所以两侧不可能对"这关开没开"有不同看法。
- **门槛是服务端的**：`createLevel` 在任何东西被拆掉之前重新求值一次并拒绝（"关卡 X 尚未解锁：通关 1_1"）。菜单只是把这个结论画出来；跳过菜单的客户端也走不进去。
- **购买是一次性的**：`UnlockLevelC2S(levelId, worldName)` 只说要买哪一关，价格由服务端从关卡定义读，钱包从档案读 —— 改过的客户端只能选择买哪关，不能选择花多少。买下后写进 `PlayerProfile.UnlockedLevels`（与 `Unlocked` **分开存**：关卡 id 与卡 id 长得很像，混在一起会让一次买关变成解锁一张卡）。包必须带世界名：购买是按世界的，而菜单期间没有正在运行的关卡。
- **金币门槛与买断是两件事**：`coins` 条件查余额（花到别处就可能重新锁上），`cost` 是花掉并永久记下。两者都支持。
- **循环会被点出来**：`LevelUnlocks.findCycles` 在加载时报告互相等待的关卡链 —— 那种关卡永远进不去，而运行中的游戏不会说为什么。
- 操作入口：`/profile info | unlock <关卡> | unlockall`。`/profile unlock` 是把某关标记为已购买（不收费），用于冒烟、测试与被链条挡住的演示关。
- 编辑器有独立的 **「解锁」页**：前置关卡、所需卡（两个逗号分隔输入框）、金币价、隐藏关开关，**边输边校验**（未知关卡 / 未知卡 / 自己作为自己的前置当场标红），保存时整块写出；页面上放不下的条件类型（如 `coins`）会被**原样保留**，不会因为"编辑了一下"被删掉。
- 内置冒险模式：1-2 需通关 1-1，1-3 需通关 1-2，1-4 需前三关（并示范 `cost: 500` 的金币买断）。

### 4.9 小游戏关卡（传送带 / 放置区 / 保龄球）

1-5「坚果保龄球」是第一种**结构与普通关不同**的关卡，三件事都是关卡数据：

```jsonc
// data/pvzce/levels/yard/adventure/1_5.json
"slots": [],                       // 卡组不是"关卡固定的几张"，而是"没有卡组"
"initial_sun": 0,
"rules": { "pvzce:sun_spawn_chance": 0,     // 天上不掉阳光（0 = 永不掉落，已有规则）
           "pvzce:zombie_speed_multiplier": 1.5 },
"mechanics": [
  { "type": "pvzce:conveyor", "interval_ticks": 150, "capacity": 6, "initial_cards": 2,
    "cards": [ { "id": "pvzce:bowling_nut", "weight": 1 } ] },
  { "type": "pvzce:placement_zone", "min_x": 0, "max_x": 3 },   // 红线：只能种在左四列
  { "type": "pvzce:mower", "rows": [] }                         // 原版这一关没有小推车
]
```

**传送带（`conveyor`）**

- 服务端 `ConveyorBelt`（`server/level/`）持有队列与时钟：每 `interval_ticks` 从加权池里抽一张，`capacity` 满则**停止出货**（原版行为：囤卡要付代价），`initial_cards` 是开局就在带上的张数。
- **带上的卡就是玩家的卡槽**：`plantPlayer.slots()` 是传送带的投影，`rebuildBeltSlots()` 在每次变化后按带上的顺序重建，`placePlantInternal` 里种下一张就是 `belt.take(id)`——**不扣阳光、不进冷却**。
- **每张卡有一个永不复用的 id，位置不是身份**：带上的位置每消耗一张就整体前移，若客户端点的是"第 2 格"，一次竞态就会种出另一张卡。`SlotInfo.index` 因此是卡自己的 id，`PvzcePlayer.slot(int)` 按 `Slot.index()` 查（普通卡组里两者本来就是同一个值），过期的点击会**指名一张已经不在带上的卡**并被拒绝，而不是种错东西。
- **同步用整表替换而不是增量**：`BeltSyncS2C(List<SlotInfo>)`（`PROTOCOL_VERSION` 因此 = 9）。`SlotSyncS2C` 是按 index upsert，**说不出"没了"**——被用掉的卡会一直留在客户端的卡槽条上。传送带一次最多六张、几分钟才变一次，整表发最省心。`LevelInitS2C` 里的 `slots` 已经是带上的内容（`sendFullState` 与 `slotInfos()` 同源），所以进场不需要额外包。
- `LevelPayload` 因此多两个字段：`conveyor`（这张卡槽条是不是传送带）与 `beltCapacity`（UI 画多宽的带子）。两者都由服务端下发而不是客户端读本地数据包——带的**内容**本来就是服务端状态，客户端不该有第二份"这关是不是传送带"的判断。
- **存档**：带上的卡与下次出货倒计时写进 `level.dat` 的 `Belt` 块（`LevelServer.save/restore`）。恢复时先恢复带、再重建卡槽条，`restoreSlots` 于是能按 id 找回每张卡。
- **传送带关卡不经过选卡界面**：卡组由关卡自己发，选卡页会让玩家挑一套马上被丢掉的卡。`PvzceClient.usesConveyorBelt(levelId)` 读本地关卡定义（与 `lockedSlotsFor` 同一层），三条入口（关卡列表 / 暂停菜单重开 / 存档提示框重开 / 编辑器测试）都走它。服务端 `createLevel` 对传送带关卡直接传空卡组，`readSavedSeedSelection` 也不读——卡组就是带子。
- 美术是原版的 `ConveyorBelt.png`（胎面），从 `refer/im7/images/` 拷进 `textures/gui/hud/conveyor_belt.png`；它**铺满整个托盘**并持续向左滚动，卡片骑在上面（细节见 §6.2）。带子画在**屏幕顶部**（原版位置，且传送带关卡本来就没有阳光银行）。
- **1-10 是第二个传送带关卡**，也是昼夜**会变**的那一关：池子是原版 Day 区的七种植物，4 秒一张、容量 6、开局 3 张，天上不掉阳光（传送带发的卡本来就免费）。规则 `day_length: 3600` + `night_length: 360000` = 一分钟白天、之后整局夜晚；对照 2-1 的 `day_length: 0` + 正数 `night_length` = **整关固定夜晚**（没有白天可回，见 `DayNightCycle.alwaysNight`，客户端第一帧就是暗的）。关卡细节见 §6.2.1。

**放置区（`placement_zone`）**

- 一个闭区间矩形，缺省的边就是棋盘边界（`{"min_x":0,"max_x":3}` 不必知道关卡多宽）。语义是"这一关的草坪只有这块能种"。
- **判定只有一处**：`LevelServer.canPlacePlant` 先查区域再查 `PlantPlacement`。玩家、手套、植物 AI 都走它；**故意不走的两条路是 `/spawn plant` 与关卡的 `initial_entities`**——那是关卡作者在摆东西，不是在玩。
- 客户端从 `LevelPayload` 拿到同一个矩形，画出**红线**（画在世界层，和服务器判定的是同一组数），悬停格子按"在不在区内"显示绿/红。红线画在普通草地上正是它必须是关卡数据而不是地形的原因：地形做的话，红线下面的草坪就得变成另一种地块。

**保龄球（`pvzce:bowl` 能力 + `pvzce:bowling_nut` 植物）**

- 新植物 `pvzce:bowling_nut` 复用坚果墙的美术与动画文件（`animations/plant/defense/bowling_nut.json`，只多一个绕自身中心旋转的 `roll` clip），卡面美术复用 `textures/gui/cards/wall_nut`，走新卡 `slots/bowling_nut.json`。**普通关卡的坚果墙完全不受影响**。
- 行为在 `BowlCapability`（`common/capability/plant/`）：种下即向右滚（`speed` 格/秒，出货 5），**永远向前**——撞到僵尸不会掉头，而是被撞进相邻车道（`ricochet`）；左右边界是出口（滚出右侧即消失），**上下边界是墙**，撞到会反弹。车道的选择偏向草坪中间（顶/底行必向内，中间行五五开）。
  > 保龄球的核心是**斜向弹开继续前进**、在密集的僵尸群里连撞：方向反转与"上下反弹"是两件事，混在一起就两种都做不对。
- **伤害走 `ZombieEntity.damageImpact`，不走 `damageBody`**：`damageBody` 是爆炸用的、按设计无视护甲，用它会让铁桶一击死。`damageImpact` 让护甲先吃伤害（`ZombieCapability.onImpact`，`ArmorCapability` 实现）。击数因此是**数值窗口**而不是特例：本项目"护甲吸收到碎为止、碎的那一下不穿透到身体"，所以一次伤害必须够打死 200 血、又不够打穿 370 路障，同时两次要够打穿 1100 铁桶——即 `[550, 1100]`，`DEFAULT_DAMAGE = 650` 落在这个区间里，得到普通 1 击 / 路障 2 击 / 铁桶 3 击。
  > `onImpact` 要**先找 front 再找 top**：路障/铁桶在本项目里是 `position: top`（帽子），而掷物按子弹层选槽位（地面子弹打 front），保龄球没有子弹可描述，若只查 front 就会一路打到身体——路障与铁桶都是一击死，上面那条数值窗口也就永远用不上。
- **滚动中的坚果不是"格子里的植物"**：`BowlCapability.occupiesCell` 返回 false，`plantAt` 跳过它，所以僵尸不会停下来啃、铲子铲不掉。滚动的坚果仍然被模拟、被绘制、能被打。
- **连击掉币**：第 N 次命中掉 (N-1) 枚币（第 2 只起），币种来自关卡 `rewards.coin_drop`（`LevelAccess.dropCoin`，与僵尸掉币同一个"关卡决定值多少"的入口），所以关卡不写奖励时不会凭空多出一种货币。
- 1-5 的波次是**11 波 116 只**（普通 / 旗帜 / 路障，后段少量铁桶），出怪间隔 30~60 tick、**波间隔 600 tick**，第一波 240 tick（4 秒）就开打，约 1 分 45 秒；僵尸**移速 ×1.5**（关卡规则 `pvzce:zombie_speed_multiplier`）。传送带因此是 **150 tick 一张**（原版 n-5 的节奏）。首通奖励解锁 `pvzce:potato_mine`，音乐是原版的 `pvzce:music/loon_boon`（n-5 传送带关的曲子）。
  > 这一关的节奏是"**1.5 倍频率、一半数量、1.5 倍移速**"：原版 n-5 的僵尸密度配上传送带是 5 秒一张卡，`(数量-1) × 出怪间隔` 会顶到波间隔，所以每一波都必须能在下一波到来之前放完，而 1.5 倍的移速把"一半数量"补回成同样的压迫感。
  > **它没有小推车**（`rows: []`），与原版一致：漏一只就是直接输——这正是这一关的难点，而不是待补的缺口（小推车本身已经实现，见下）。

**关卡自带的工具（`tool`）**

- 一个关卡可以把某个已注册的工具**按自己的条件**交给玩家：`{"type":"pvzce:tool","tool":"pvzce:hammer","default":true,"cooldown":0,"cost":{"resources":{}}}`。`cooldown` / `cost` 是**关卡对这把工具的覆盖**（不写则沿用工具自己的数），`default: true` 让它成为**这一关空手点击的动作** —— 2-5 的鼠标就是木槌。
- **它不是卡**：不占卡槽、不印价格、不进卡包顺序、没有充能条。所以它不参与 `Slots` 的任何逻辑，服务端走 `LevelServer.useGrantedTool`（唯一与卡片路径共享的是 `applyToolEffect` —— 锤子在两条路上是同一把锤子），客户端走 `UseGrantedToolC2S(tool, x, y)`，**客户端只说它看见的是哪把工具，关卡是不是真的给了它由服务端查自己的 `mechanics`**。
- **默认工具与选卡互斥**：手上没有卡时点击才是工具。选中的卡永远优先，所以"我想种东西"不会被木槌抢走。
- `ToolMechanic.declared/of/cooldownTicks/sunCost` 是这些数的唯一读法：服务端、客户端与校验器都从这里问，`ToolMechanic.validate` 报未知工具 id。
- **指哪打哪**：`ToolDef.range`（缺省 0.9 格）是挥击在**点击点周围**的触及半径，锤子按世界坐标判 `|Δy| ≤ range && |Δx| ≤ range × 1.15`（x 略宽，因为僵尸画得比一个格瘦）—— 目的不是"打相邻格"，而是"点在哪就打哪"。2-5 的僵尸速度是 2.2 倍，等玩家把光标挪进它**当前所在的那一格**时它已经走出去了，按格判定必然打空。客户端用同一个数画一个半透明圆盘（`InGameScreen.drawAimDisc`，画在实体之下）作为准星；铲子、手套这类作用于**格子**的工具 `range` 留 0，规则不变。
- **一次挥击打多少是工具自己的数**：`ToolDef.damage` / `damage_type`（`tools/hammer.json` 写 `damage: 200, damage_type: "pvzce:impact"`）。200 = 普通僵尸的血量，`impact` = 护甲照常先吃，于是**普通 1 下 / 路障 3 下 / 铁桶 7 下**（370 与 1100 各按 200 一点一点磨，碎了以后还要一下打 200 血的**身体**）—— 这套数字是本项目"护甲吸收整击、碎的那一下不穿透"那条规则的结果（`ArmorCapability.absorb`），原版的"路障 2 下、铁桶 3 下"来自另一条规则（每一下削一层、破甲那一下直接打身体）。**木槌不再是小推车**：原来那个写死的 100000 点 `pvzce:mower` 让草坪上一切都一击死，铁桶和普通僵尸一样便宜。**打空不收费**：`applyToolEffect` 对锤子返回"有没有打中"，没打中就是一次被拒绝的点击 —— 不扣阳光、不进冷却、不响。

**会补的墓碑（`grave_spawner`）**

- 2-5「打地鼠」的骨架：`{"type":"pvzce:grave_spawner","zombies":[...],"min_graves":9,"initial_graves":9,"interval":600,"min_x":4,"max_x":8}`。僵尸**从墓碑里钻出来**（`LevelServer.raiseZombieFromGrave`，与夜关最后一波开墓用的是同一个实现），被清掉的墓碑会补回 `min_graves` 座，补的位置在该矩形里随机、且只落在空格上（有植物或已有墓碑的格子跳过）。
- 它与 `graves_spawn_night`（每座墓碑在**最后一波**开一次）是**两件事**，可以同时存在：2-5 把它关掉了，因为它的墓碑就是这一关的全部人口，再开一次是第二条没被设计过的入口。
- 每座墓碑各管各的倒计时（`interval` 到点从**随机一座**已存在的墓碑里放一只），所以墓碑数量本身就是压力：清得越多，单位时间里冒出来的越少。

**小推车（`mower`）**

- **不声明就每行一辆**：`LevelMechanics.effective` 给每个没写 `mower` 的关卡补上 `MowerData.EVERY_ROW`，所以"关卡文件里没提"这件事的含义是"这是普通草坪"，而不是"这里没有推车"。只有 `rows` **空数组**才是"一辆都没有"。
- **声明方式**：`{"type":"pvzce:mower"}` = 每行；`{"rows":[0,4]}` = 只有这两行；`{"rows":[]}` = 没有。缺省与空数组是两件事，所以字段是 `Optional<List<Integer>>`（codec 分不出来就等于两种语义都说不清）。
- **行为就是原版那三条**：车停在第 0 列左侧（`IDLE_X = -0.5`）；该行**地面层**僵尸走到 `cellX <= 0.05`（第 0 列左沿，啃食中的僵尸在 0.5 左右不会误触发）时启动；此后以 `SPEED = 3.3` 格/秒向右推进，碾过该行一切**地面层**目标；越过右边界后 `STATE_USED`，永久消失。
  > **飞行与挖掘中的僵尸不碾**：判据是僵尸自己的 `layer()`（与子弹路由同一个），所以气球僵尸从推车头上飞过、矿工还在地下时都不受影响——它们走到房子里照样算输，与原版一致。
  > **碾压无视护甲**：`damageBody(health)` 而不是 `damageImpact`。`damageImpact` 是"护甲先吃、碎的那一下不穿透"，用它推车会撞碎铁桶却打不死里面的僵尸（见上面保龄球那段的同一条规则）。
- **状态在 `LevelServer.mechanicState(id, create)` 里**：注册表里的 mechanic 是**单例**，两个关卡不能共用一辆草坪推车，所以每个关卡按 mechanic id 向关卡要一个槽位来放自己的 `Rig`（客户端有同名镜像 `ClientLevel.mechanicState`）。关卡本身不知道槽里是什么。
- **同步**：`MechanicSyncS2C` + `MowerMechanic.State`（整表：每行的 `state` 与 `x`），只在**状态变化**与**有车在滚**时每 3 tick 发一次；没被触发的关卡一个字节都不发。客户端 `MowerClientMechanic` 用这份状态画车，行来自 `LevelPayload` 里的 mechanic 块。
- **存档**：`Rig` 通过 `collectSave/applySave` 写进 `level.dat` 的 `Mowers` 块，恢复时 `applySave` 置脏，于是客户端进场后会收到一次真实状态（用过的车不会重新出现）。
- **美术**：`tools/reanim_to_pvzce_all.py --entity lawn_mower` 把原版 `LawnMower.reanim` 的 `anim_normal` 掩码转成 `animations/mechanic/lawn_mower.json`（0.74×0.62 格）。它不是内容（没有注册表条目），所以播放走 `ArtTarget`——一个自己带动画文件 id 的 `Animatable`，渲染、时钟、模型与实体完全共用。
  - **两个 clip：`idle` 与 `drive`**。原 reanim 的轮子轨道在 `anim_normal` 的**每一帧**都在转，整段导出成一个循环 clip 会得到"停在路边轮子却一直在转"的车；转换器的 `range: [0, 0]` 把 `idle` 冻在第 0 帧（停放姿势），`drive` 才是滚动的那个，`MowerClientMechanic` 按 `STATE_READY`/`STATE_ROLLING` 选 clip。冻结用的是现成的 `range` 选项，没有为它加新语法。
- **粒子**：`PvzceParticles` 里那三个原版发射器终于有主了——`mowered_zombie_head` / `mowered_zombie_arm`（被碾的僵尸）与 `mower_cloud`（行进时的尘烟）；启动音是 `sfx/effect/lawnmower`。
- **玩家可以手动放车**（长按）：鼠标停在还停着的车上按住 `MOWER_HOLD_NANOS`（0.5s）就发 `ReleaseMowerC2S(row)`，服务端 `LevelServer.releaseMower` 重新校验（**这一行有车、而且车还停着**、关卡还在跑）后走**同一个** `Rig.start`——同一个音效、同一个速度、同一套碾压与消耗。放手即取消，所以普通点击不可能误触发（车是一次性资源，用在已经处理过的波次上就是这一整行后面都空着）。
  - 按 **row** 而不是坐标：车停在棋盘左沿之外半格（`IDLE_X = -0.5`），那里没有格子，所以长按的命中测试在 `onMouseClicked` 里**先于**棋盘边界判定，用的是世界坐标下的圆形半径（与掉落物拾取同一个 `0.45` 格）。
  - 按住时在车**上方**画一条进度条（不是圆环：车有个高把手，环绕会压在把手上）；进度条在 GUI 空间、用**画在屏幕上的**车位置定位，所以光标哪怕飘几像素也不会丢手势。
  - **请求不带"能否放行"**：客户端只说哪一行，`Rig.release` 在服务端回答"行上没有车"和"车已经没了"是同一个 `false`，重复包是空操作而不是第二次发射。
  - 音效**延迟到下一个 tick**：请求落在两个 tick 之间，那时 `emitEffect` 没有 bridge；`Mower.launchSoundPending` 让 rig 在自己的下一次 tick 上补放，而状态变化是立即的（下一次实体同步就要带上"正在滚"）。
  - 关卡一结束就取消未完成的长按：把已经计进"幸存车"的那辆偷偷花掉是错的。
- **结算**：没被用掉的车按金币折价进本局奖励，客户端在点击奖励时逐辆变成金币飞向钱袋（见 §4.5）。`Rig.readyCount()` 是"还剩几辆"的唯一答案，服务端与客户端（`ClientMechanics.parkedMowers`，读同一份镜像状态）都从它出发。

**爆炸范围是"格"而不是"距离"，而且必须覆盖触发范围**：`pvzce:explosive` 的 `square` 把 `radius` 从半径读成**格数**（`LevelServer.damageArea(..., square)` 判据是 `|Δ| ≤ radius + 0.5`，半个格是植物自己那一格的半宽），这就是原版的写法：土豆雷 `radius 0.5` = 自己那一格，樱桃炸弹 `radius 1.0` = 周围 3×3，毁灭菇 `radius 3.0` = 7×7。`trigger: "row"`（火爆辣椒）**整行**结算，走 `LevelAccess.damageRow` —— 一个足够大的方格会连带打穿旁边几行，而一个只够 9 列宽的半径在更宽的草坪上会短一截。`detonate` 另有一条不变量：**爆炸的覆盖范围至少覆盖触发范围**（方格按 `radius + 0.5` 算覆盖），否则触发那一 tick 的距离正好落在爆炸之外，每一次引爆都必然落空；`potato_mine` 的 `trigger_range` 因此是 0.5（僵尸真正踩进格子才炸）。

**冷却按原版**：土豆地雷 30 秒（1800 tick）、樱桃炸弹 50 秒（3000 tick）、墓碑破坏者与大喷菇各 7.5 秒（450 tick）。


## 5. 实体与能力系统（本轮重构的核心）

### 5.1 共用实体基类

`com.pvzce.api.entity.Entity` 同时被服务端与客户端继承：

| 层 | 类 | 额外内容 |
|---|---|---|
| 共用 | `Entity` | id、defId、cellX/cellY、height、health、animation、**网格边界**、`gridX()/gridY()`、`entityKind()`、`layer()` |
| 服务端 | `PvzceEntity extends Entity` | team、removed、`tick(LevelServer)`、`saveState()/restoreState()`（对称，强制实现） |
| 服务端 | `PlantEntity` / `ZombieEntity` / `ProjectileEntity` / `ResourceDropEntity` | 能力实例列表 |
| 客户端 | `ClientEntity extends Entity` | kind、layer（来自包）、`AnimationComponent` |

`ClientEntity.from(EntitySpawnS2C)` 与 `apply(EntityUpdateS2C)` 是包→状态的**唯一**应用点；网格由两侧用同一份逻辑从 cell 派生，所以 `EntitySpawnS2C` **不再传 gridX/gridY**。

**客户端在两次采样之间补间**（`ClientEntity.visualCellX/Y/Height`）：`LevelServer.syncSlots` 每 3 tick 同步一次实体位置（20 Hz），而客户端画 60~260 帧——直接画包里的坐标就是一条 20 Hz 的阶梯：站住五帧、跳一下。速度越慢越明显，而"被豌豆打"恰恰是玩家盯着单只僵尸看的时候。
- 补间是**渲染位置**：`cellX()` / `height()` 仍然是服务端的数，命中测试、相机换算与所有断言读到的都还是权威值。
- 线性、按墙钟推进、夹在区间内；从一个**正在画的位置**开始（而不是上一包的位置），所以迟到的包不会让实体先倒回去再往前滑。
- `height` 也在里面：掉落物的下落是靠 height 表达的，只补 x/y 会让太阳的下降仍是 20 Hz。
- `SYNC_PERIOD_NANOS` 与 `tickCount % 3` 是**一对**，改一个要改另一个。

### 5.2 能力（Capability）

行为不再是实体里的字符串 switch，而是**可注册、可组合的能力对象**。

- 接口：`PlantCapability` / `ZombieCapability` / `ProjectileCapability`（`api/content/capability`）。
- 类型注册表：`BuiltInRegistries.PLANT_CAPABILITIES` 等，条目是 `CapabilityType<T>(id, MapCodec<T>)`。
- 列表元素：`TypedCapability<T>(Identifier type, T value)`，JSON 里形如 `{"type":"pvzce:shooter", ...}`。
- 每个实体构造时 `instantiate()` 出一份**实例**，状态（冷却、引信、护甲血量…）保存在实例里，因此新增一种行为不再需要给实体加字段。
- 存档：每个能力把状态写进以类型 id 为键的子标签（`capabilities: {"pvzce:shooter": {...}}`），实体基类负责遍历。

内置植物能力：`shooter` `thrower` `producer` `explosive(timed|proximity)` `melee` `wake_below` `bowl` `nocturnal`。
内置僵尸能力：`armor` `vault` `fly` `dig` `hammer` `boss_phases`（行走/啃咬循环留在 `ZombieEntity`，所有僵尸共享）。
内置子弹能力：`linear` `arc` `splash` `status` `pierce`。

**`pierce` 是"穿过并命中下一只"，不是"每 tick 再打一次"**：`ProjectileEntity` 记着这发子弹**打过哪些僵尸**（`hitIds`），`findTarget` 跳过它们。没有这一条时，一发 20 点的大喷菇喷雾会在它和僵尸重叠的每一 tick 各打一次 —— 200 血的僵尸十个 tick 内死光，看起来就是"秒杀一切"（`NightAreaTwoLevelsTest.oneSprayDamagesEachZombieOnce` 钉住"一发最多打一次"）。用 id 集合而不是"上一只"：两只僵尸挤在同一格时，只记上一只会让子弹从另一侧反复打第一只。

**睡觉会冒 Zzz**：睡着的植物每隔 0.62 秒在头顶偏左吐一个 "z"，三个尺寸轮着来（小→中→大），所以一次呼吸是一条斜向上的螺旋。三个尺寸是**三份粒子定义**（`pvzce:zzz_1/2/3`）而不是运行时缩放 —— 粒子的尺寸是定义里的一个数（见 §6.5.1），三份定义让发射端只需轮询一个列表。美术由 `tools/gen_zzz_sprite.py` 生成（原版没有 Zzz 的贴图，它是用原版自己的字体画出来的；本项目字体图集是文本图集，切不出单字，所以在工具里渲染一次）。**发射在客户端**（`InGameScreen.tickSleepZzz`）："哪些植物睡着了"是服务端已经发布的状态（`sleep`），"哪些植物会睡"在客户端加载的动画文件里，而睡觉是**持续事实**而不是事件 —— 从服务端发就要为每一次呼吸发一个包，在客户端只是一个墙钟计时器加零个包。每个实体各自计时并按 id 错开，一排蘑菇不会齐步喘气。

**睡觉是关卡时钟的函数，不是存下来的标志位**（`pvzce:nocturnal`，蘑菇）：`asleep = !awake && !level.isNight()`，所以入夜、`/time` 回拨、读一份夜里的存档都不会留下"白天醒着/夜里睡着"的分裂状态。真正进存档的只有一件事——咖啡豆的唤醒（`Awake`），它一旦成立就永久有效。**抑制行为只有一处**：`PlantEntity.tick` 在植物睡着时跳过所有没有 `ticksWhileAsleep` 的能力，于是射手、生产者、引信一起停下，而不是每个新能力各自记得判断白天黑夜；`NocturnalCapability` 自己 opt-in，因为它负责发布 `sleep` 动画（美术必须定义这个 clip，否则客户端会静默回退到 `idle`，`AnimationResourceLoaderTest` 钉住这一条）。

**咖啡豆只做一件事：唤醒**（`pvzce:wake_below`）。它对下方的植物调 `PlantEntity.wake()`，返回值说明"真的叫醒了一个"（播 `wake_sound`），对醒着的植物**什么都不发生**——豆子照样被消耗，这是原版的取舍，也是"它不是一颗瞬产阳光的按钮"的唯一表达。`PlantCapability` 里原来那条 `boost()`（立即射击/立即产出）随之删除：能量豆的大招是另一套设计（`02` 文档 §2.2.5），不该挂在同一个钩子上。

**射程是这一发子弹的属性**（`ProjectileRef.range`，0 = 不限）：同一个数既是"值不值得开火"的判据（`ProjectileRef.covers`），也是子弹什么时候自己消失的判据（`ProjectileEntity` 从出膛点量起）。小喷菇就是靠它做到"三格之内才打"——如果只写一半，要么它对着够不着的僵尸空放，要么孢子飞过整个草坪。

### 5.2.1 伤害类型（`pvzce:damage_type`）

**「一次命中吃不吃护甲」是内容的声明，不是调用点的方法名。** 以前这件事由「代码调了哪个方法」表达：
`ZombieEntity.damageBody` 无视护甲（爆炸、推车）、`damageImpact` 先走护甲（保龄球、巨人的拳头）、
`damage(ProjectileDef,…)` 按子弹层路由（豌豆、西瓜）—— 三条并列的入口，内容作者看不到也改不了答案，
「灰烬类无视护甲」只是一句注释。现在只有**一个入口**：

```
ZombieEntity.damage(amount, DamageTypeDef, level)     ← 所有命中都到这里
        ├─ type.ignoresArmor() == true  → 直接 damageBody
        └─ type.ignoresArmor() == false → 先问僵尸的护甲能力（onImpact：先 front 再 top）
```

- **定义在数据里**：`data/<ns>/damage_types/<名>.json`，两个字段（`id`、`ignores_armor`），与
  `level_theme` 同形的薄条目；静态兜底在 `BuiltInRegistries.registerDamageTypes()`，与其它注册表同规矩。
- **`burns` 是第二个字段**：`pvzce:ash` 声明 `burns: true`，所以被灰烬打死的僵尸播 `death_burned` —— 一套**另一个模型**（原版 `Zombie_charred.reanim`，见 §5.2 末段），不是同一套骨骼上的另一个 clip。字段在伤害类型上而不是在死亡代码里排一张 id 表：mod 自己的火焰伤害要能回答"这一下烧不烧"，而不必改代码。
- **内置五种**：`pvzce:ash`（灰烬类爆炸，无视护甲且 `burns`）、`pvzce:splash`（投手溅射，无视护甲 —— 原版西瓜的范围
  伤害也是打身体）、`pvzce:mower`（小推车与锤子工具，无视护甲，「不是磨掉而是清掉」）、
  `pvzce:projectile`（普通子弹）、`pvzce:impact`（保龄球、巨人的拳头）。
- **谁声明**：`pvzce:explosive.damage_type` 与 `pvzce:splash.damage_type`。子弹的**直击**不需要声明 ——
  它走的那条路本来就叫「子弹」，`onProjectileHit` 的层路由（平射先 front、没盾就落 top；抛射只碰 top）
  说的是「这一发从哪来」，与伤害类型正交。
- **未注册的 id 回退到 `pvzce:projectile`**（护甲照常生效），所以拼错的类型不会变成「无视护甲的外挂」；
  `ZombieEntity.damageType(id)` 是唯一解析处。
- **一个数字只乘一次**：`RULE_PLANT_DAMAGE_MULTIPLIER` 从旧的三个入口各自相乘，改成在
  `ZombieEntity.damage` 里乘一次，所以这条规则的含义不再取决于走了哪条路。
- **加一种伤害类型** = 放一个 JSON + 在能力里写 `damage_type`；要新的**行为**（吸血、击退）才需要给
  `DamageTypeDef` 加字段。

**装备的三种显现（`EquipmentDef`）**：

- **数据在僵尸定义上**：`"equipment": [ {"art":"cone","piece":"pvzce:cone","drop_particle":"pvzce:zombie_traffic_cone"} ]`。`art` 是**动画模型里的骨骼族前缀**（`cone` → `cone_1`/`cone_2`/`cone_3`），`piece` 指向护甲条目（**护甲驱动**：按耐久的三档磨损，耐久归零即消失），没有 `piece` 的条目由**本体血量**驱动（旗帜：`health_below` 之下换成破损那张，死亡时掉落）。
- **第三种图是烘进模型里的**：`tools/reanim_to_pvzce_all.py` 的 `damage_states` 给宿主骨骼复制出 `cone_2`/`cone_3`（**同一套动画键、自己的贴图、每个 clip 里都 `visible: false`**），因为破损的贴图在原版里根本没有被任何 track 引用，转换器看不见它们。三个档位因此不是三个 clip、更不是三份 800KB 的动画文件。
- ** peas 必须先打帽子**：`ArmorCapability.onProjectileHit` 把**平射**弹先路由到 `front`（盾牌/铁门），**没有盾牌就落到 `top` 上**（帽子挡平射，正如它挡抛射），而抛射只碰 `top`（抛物线越过铁门）——这正是两个槽位存在的理由。所以路障僵尸的有效血量是 570、铁桶是 1300，与原版一致；`MiniGameTest` 用保龄球钉的 370/1100 数值窗口不受影响（那条路本来就先 front 后 top）。
- **画哪一张是客户端的事**：`client/renderer/EquipmentArt` 实现 `BoneArt`，每帧拿到模型与解算好的姿势，选出这一帧该画的那一张。两条规则写在里面：**只在这一帧本来就画这个家族时**才替换（报纸僵尸的"喘气"clips 故意不画报纸，不能被贴回去），以及**从最接近的可用档位往回取**（旗帜只有 1 和 3 两张图）。分母是定义里所有护甲条目的耐久之和（今天每个僵尸只有一件），分子是 `EntitySpawnS2C.armor`。
- **掉落**：`ArmorCapability` 只在**真的打碎**那一发发这件装备自己的掉落粒子，普通命中改回火花；死亡时还戴着的装备一并掉落（`ZombieEntity.dropEquipment`），已经被打碎的不再出现。
- **一件装备可以自带一条手臂**（`EquipmentDef.host` + `arm_bones`）：原版美术是**分层**的，不是父子骨骼——
  同一只手可以有两份精灵、都挂在 root 下、各自带一份自己的动画轨道。旗帜僵尸就是这种情况：拿旗的手在
  `Zombie_flagpole.reanim` 里，而普通僵尸那一整套 `innerarm_*` / `outerarm_*` 照样在画，于是它一边举旗
  一边还垂着两条手臂。`host` 说明"这只手在不在场上"，`arm_bones` 列出该被换掉的普通手臂骨骼，**两者只画一个**。
  范围刻意是"`host` 在画的那几帧"而不是整只僵尸：死亡 clip 把旗子收走、那只手也一起没了，这时必须把普通
  手臂**还回来**，否则僵尸会无臂倒下。`hidden_bones`（在 `ZombieDef` 上）是同一类问题的粗暴版本——无条件不画。
  > **抛掷物粒子的单位**：原版用 `GroundConstraint` 标出的那一族（头、手臂、路障、铁桶、旗帜）是刚体抛掷物，转换器对它们改用原版真正使用的单位（像素/秒、度/秒，`PROP_SPEED_DIVISOR`）：帽子 2.5 格/秒、手臂 0.5 格/秒、自旋约 1 圈/秒。其余 122 条仍按每帧读数（它们的速度靠原版的 `Friction` 衰减，而本项目没有转 friction，见 §9 已知缺口）。
  > **`ParticleMotion.gravity` 的符号**：字段语义是"**向下**的加速度大小"（引擎里是 `vy -= gravity * dt`），所以写入的必须是正数——写成负数会让**每一件抛掷物都往天上飞**（"僵尸头颅直接飞上天"）。符号与字段语义一致后，抛掷物飞出去会落回**它自己那一行**的草地：手臂 0.19 格、路障 0.64 格、旗帜 0.97 格、被碾的头 11.2 格（原版就是把它甩出画面）。
  > **落地线是相对出生点的**：`bounce` 的地面在**出生点下方 0.42 格**，不是世界坐标的某个固定值——后者只有第 0 行是对的，第 1 行以上扔出去的东西会一路掉出草坪下沿。
- **头颅是抛出来的粒子**：模型在死亡 clip 里把 `head`/`jaw`/`tongue`/`hair` 全部设为不可见（原版就是这么画的），
  所以头由 `pvzce:zombie_head` 粒子抛出，`ZombieDef.drops_head` 决定哪几种僵尸抛（巨人/Boss 整个倒下、
  气球僵尸的头随气球走，都是 false）。这个粒子是"**小弧线弹出、落地即停**"：速度 2.3、角度 125°、摩擦 0.25，靠 `ParticleMotion.ground_friction` 实现（落地时 `vx *= friction`，缺省 **1** = 保留"一直滑"的行为，另外 139 个粒子定义的手感不变）。**原地掉落、原地淡出**。
- **烧死是另一套模型，不是另一个 clip**：`DamageTypeDef.burns`（`pvzce:ash` 为真）的致命一击把状态设成 `EntityAnimations.DEATH_BURNED`，而这一支走的是 **`Zombie_charred.reanim` 的焦尸**（`animations/zombie/charred/zombie_charred.json`，clip 名就叫 `death_burned`）。僵尸 JSON 用**已有的**逐状态覆写字段把它接上：`"animations": {"death_burned": "pvzce:zombie/charred/zombie_charred"}` —— 没有新包、没有 `PROTOCOL_VERSION` 变化，因为 `animation_dir` 本来就是客户端从本地数据包读的。焦尸与活僵尸**没有共用骨骼**（一堆灰 + 一个头骨），所以它不是"同一模型换贴图"，这也是为什么它必须是另一份模型文件。
- **死亡动画与尸体**：僵尸死亡时会 `setAnimation(DEATH)` 并在世界上**留 6 秒**（`ZombieEntity.CORPSE_TICKS`）——死亡 clip 是 3.25 秒（巨人 4.9 秒）且 `on_end: hold`。尸体期间它不走路、不啃、不被打、不计入 `aliveZombieCount`（`ZombieEntity.isAlive()`），所有"这一行有哪些僵尸"的扫描（`LevelServer.zombiesInRow`、割草机、植物 AI）都问 `isAlive()` 而不是 `isRemoved()`。**最后一杀的那次同步是强制的**（`LevelServer.entitySyncPending`）：实体状态每 3 tick 发一次，而死亡之后同一 tick 里 `checkEnd` 就可能结束关卡、此后再不 tick，包必须在这一 tick 送出去——否则玩家会看到一个活生生的僵尸站在已经结束的棋盘上。尸体不进存档迁移（`corpseTicks` 进 `saveState`，读档回来仍是尸体）。
  > **`on_end: hold` 的一次性 clip 不会被"重播"**：只要请求的状态还是**当前活动 clip**、且它是 `HOLD` 收尾，`AnimationManager.isAlreadyPlaying` 就认为"这个状态正在播"——服务端每隔几 tick 重发实体状态，不会让死亡动画在尸体存在的 6 秒里从头播 2~3 遍（尸体刚倒下又站起来）。只有交给别的 clip（`on_end: idle` / `next`）之后再请求才会重新开始；`shoot`、`explode` 这类需要反复触发的动作因此照旧。
- **半血掉手臂**：`drops_arm`（默认 true）的僵尸，血量降到一半时 `ZombieEntity.damageBody` 发 `zombie_arm` 粒子 + 断肢音，客户端按**同步过来的血量**永久隐藏 `outerarm_*` 五个骨骼——这条判据是"血量的跨越"，不是存下来的标志位，所以读一份 40% 血的存档不会再多掉一条手臂。**这个开关是"模型画得出来吗"**：客户端隐藏的是那五个固定名字的骨骼，所以巨人/Boss/小鬼以及手臂骨骼另有命名的报纸、气球、撑杆僵尸都显式写了 `drops_arm: false`——否则粒子飞出去而手臂还在（或留下一只悬空的手）。**判据还有一条"头上得先空出来"**：半血 + `armor <= 0` 才掉手臂，所以路障/铁桶僵尸是"路障先掉、再掉到它自己血量的一半（200 的一半）"才断臂——两半判据都从同步状态读得出来（血量与 `armor`），服务端发粒子的条件与客户端隐藏骨骼的条件是同一句话。
- **没有胡子**：`ZOMBIE_*_EXCLUDE` 里的 `MUSTACHE` 排除了原版只在"胡子彩蛋"里画的那条 `Zombie_mustache` track，五个共享 `Zombie.reanim` 的僵尸模型都不长胡子。
- **量身高时脱帽**：`EntityConfig.measure_exclude_regex` 把路障/铁桶/铁门/报纸的装备骨骼排除在**量尺寸的那个包围盒**之外（骨骼照旧导出、照旧绘制）。包围盒是 `target_box` 要适配的东西，所以不排除装备骨骼就会**连帽子一起**压到 0.95 格：身体比普通僵尸小 15%（模型 0.565 宽 vs 0.625），看起来"小一圈"。这四种僵尸的身体盒与普通僵尸逐字段一致（83.9×127.5px，`body` 骨骼的平移完全相同），帽子照常戳在头顶之上。脚底不动（帽子不会伸到脚下面），所以除了水平原点会随帽子偏心挪几个像素之外没有副作用。

**受击不改姿势**（`ZombieEntity.walkOrEat`）：僵尸没有受击动画，挨打时的反馈是命中粒子和音效，腿继续走。曾经有过一个持续 8 tick 的 `hit` 状态，但那个 clip 是僵尸的**站立**姿势，于是走进豌豆流里的僵尸每挨一下就在原地僵 1/8 秒、回来时重开走路循环、还要把撑杆（或手臂）跳到一个属于另一个 clip 的姿势；现在连数据里的 `hit` clip 也一并去掉了。**实体状态变化会立刻发布**：`Entity.setAnimation` 会置一个脏标记，`LevelServer.syncSlots` 见到就当场同步，不再等 `tickCount % 3`——否则只活一个 tick 的状态（射手的 `shoot` 前那一 tick 的 `idle`）三次里会漏掉两次。

### 5.2.2 阵营与魅惑（`pvzce:charm`）

**"谁是敌人"只有一个答案：不是同一支队伍。** `LevelServer.isEnemyOf(other, self)`（两个队伍**都在**时才过滤，任一侧缺失＝这一击不是阵营对阵营的行为，照旧落下），而所有攻击都问它：

| 问法 | 谁在问 |
|---|---|
| `LevelAccess.enemiesInRow(row, team)` | 射手的索敌、投手、近战、地雷的触发、保龄球的连撞、子弹的命中测试 |
| `damageArea` / `damageRow` 的 `sourceTeam` | 灰烬爆炸、溅射、Boss 的砸地、火爆辣椒 |
| 锤子 | `enemiesInRow(y, plantPlayer.team())` |

`zombiesInRow(row)`（**不过滤**）留给"这一行有几只僵尸"这类问题：渲染、`aliveZombieCount`、关卡的胜负判定。

**魅惑菇（`pvzce:charm`）只做一件事：把吃它的那只僵尸移到植物方的 `Team`**（`PvzceEntity.setTeam`，因此实体 id、位置、护甲、正在飞的子弹指向全都保持不变 —— 删掉再生成一个新实体做不到这一点）。其余全部是上面那条规则的自然结果：

- 玩家的射手/爆炸/锤子**不再打它**（它已经是我方）；
- 它自己**不再吃植物**、而是沿本行前进咬**敌方僵尸**（`ZombieEntity.walkOrEat` 里唯一的 `isCharmed()` 分支 —— 必须在这里，因为"朝房子走并吃植物"就是僵尸的定义）；
- 走到最左边**不会判负**（`checkReachedLeft` 对已魅惑的僵尸不再上报），也不会让关卡**卡在无法结束**（胜负判定数的是 `hostileZombieCount()`，不是 `aliveZombieCount()`）；
- 客户端按 `EntityUpdateS2C.charmed` 给它上一层紫色（`EntityVisuals.CHARMED_TINT`），队伍 id 随同一个包下发 —— 只有僵尸会为真，所以它是那个包上的两个布尔之一，而不是一张状态表。

**它刻意不做的事**：不还回僵尸（被打死时它是我方实体，所以不掉币 —— 这就是魅惑的代价，与原版一致）、不清护甲（原版的铁桶魅惑后照样戴桶）、不清减速。**一次一只**：`CharmCapability` 自己有一段休息时间（`cooldown_ticks`，缺省 660 ≈ 11 秒），休息期间再被咬也不会二次生效，也不会被消耗。

**被消耗的植物可以有退场动画**：`PlantCapability.vanishAnimation()`（clip 名 + 持续 tick）让"这张卡被用掉了"有一拍可以演。今天只有咖啡豆用它（原版 `Coffeebean.reanim` 的 `anim_crumble`，1.25 秒 → 75 tick）：种下去叫醒下面的植物（或什么都没叫醒）之后**立刻退出玩法**（`isRemoved()` 为真、`occupiesCell()` 为假、同一格马上可以再种），但身体还留在场上把 clip 播完 —— 这是"**玩法已经结束，只是动画还没追上**"的唯一表达，而不是给植物加第二条命。没有声明 clip 的植物保持原来的一帧消失。tick 数是**写在数据里的**而不是从动画文件读的：服务端不读动画资源（那是客户端的层，不依赖它才让关卡能在没有渲染器时仿真），数字对不上时以仿真为准。

`bowl` 是唯一会让植物**离开自己格子**的能力（保龄球坚果，见 §4.9）：它顺带定义了 `PlantCapability.occupiesCell`（默认 true），`plantAt` 会跳过回答 false 的植物，所以"僵尸不啃滚动的坚果"不是啃咬循环里的特例。僵尸侧的对称物是 `ZombieCapability.onImpact(zombie, damage, level)`：给"不是子弹的撞击"（保龄球、巨人的拳头）留的护甲拦截口，与 `onProjectileHit` 分开是因为没有子弹可以描述这次命中（没有层、没有命中音效），而"护甲先吃"这条规则仍然适用——并且**先查 front 再查 top**，因为帽子（路障/铁桶）在 `onProjectileHit` 的层路由下只挡抛物线。

`behavior` 字段仍在，但**降级为可选预设**（`PlantBehaviorPresets` / `ZombieBehaviorPresets` / `ProjectileBehaviorPresets`）：显式 `capabilities` 优先，为空时才按 `behavior` 展开；预设是纯语法糖。

### 5.4 为什么 `LevelAccess` 在 `api/entity`

能力是**服务端行为**，必须能放子弹、算范围伤害、读同排僵尸、播音效。把这些操作收敛成一个只读+动作的小接口（`LevelAccess`），比让能力直接依赖 `LevelServer` 更可控；实现只有 `LevelServer` 一个。接口里的实体参数是服务端类型（`PlantEntity` 等），这是 L2→L2 的引用，不是 api→server 的方向污染。

### 5.5 放置与叠放（标签驱动）

能不能种、能不能叠，**没有任何硬编码 id 参与**，只有两张表：标签 + `PlacementDef`。

```
@c:ground / @c:plantable / @c:water / @c:unplantable / @c:grave  （scene_element 注册表）
@c:plantable / @c:carrier / @c:requires_ground /
@c:water_plant / @c:plant_only / @c:grave_only          （plant 注册表）
```

**判定**：`PlantPlacement.canPlace(plant, ctx, x, y)` 是纯函数，只读上面这些标签与 `PlacementDef`：

| 植物带 | 需要 |
|---|---|
| `#c:plant_only` | 任意植物在它**下面**（咖啡豆） |
| `#c:water_plant` | 地形 `#c:water`（莲叶） |
| `#c:grave_only` | 地形 `#c:grave`（墓碑破坏者）—— 排在 `#c:requires_ground` 之前，因为墓碑同时是 `#c:unplantable` |
| `#c:requires_ground` | 地形 `#c:ground` 或 `#c:plantable`（花盆、土豆雷） |
| `#c:carrier` | 地形 `#c:ground` 或 `#c:water`（载体自己先落地） |
| 其余 | 地形，或**下面**某个植物，带 `#c:plantable` |

两个关键点，都是"顺序无关"的来源：

1. **只看比自己层低的东西**（`layerIndex(other) < layerIndex(self)`）。豌豆和土豆雷都在 layer 1，谁也够不着谁，所以"雷种不进花盆""豌豆不会长在雷上"与**种植顺序无关**。
2. **互斥由 `group` 说，不由层号说**。`group` 留空＝同格可多个（咖啡豆）；普通植物默认 `plantable`（一格一个）；载体默认 `carrier`（盆上不能套盆）。

`LevelServer` 只提供 `PlantPlacement.Ctx`（该格的 `Terrain` + 自下而上的 `PlantLayer` 列表），`canPlacePlant` 一行转发；`PlantAIPlayer` 也走同一条。`SceneElementDef` **不存**能种什么；新增地形 = 加一个元素定义 + 在 `data/c/tags/scene_element/` 里打标签。

### 5.6 每帧/每 tick 的执行顺序

服务端 `LevelServer.tick`：音乐线索 → 波次 → 波次与时间同步 → 阳光掉落 → 场景（弹坑恢复/墓碑）→ `flushPending` → 植物（能力 tick）→ AI（可选）→ 僵尸（能力 tick + 移动 + 啃咬 + 死亡掉币）→ 子弹 → 资源掉落 → 移除回收 → 卡槽同步（每 20 tick 或冷却归零）→ 实体增量（每 3 tick）→ 胜负判定。

客户端 `PvzceClient.run` 每帧：`window.pollEvents` → `connection.tick()` → `pollInput` → `screen.initIfNeeded/tick` → `music.tick` → `animations.tick` → `render`（`clipping.reset()` 在帧末兜底）。

## 6. 客户端

### 6.1 状态镜像

`ClientLevel` 是服务端状态的**只读镜像**：实体表、卡槽、场景（`SceneGrid<String>`）、队伍（按 team 分别存放的资源）、波次/日夜/目标速率/断线原因。`ClientLevel.init(...)` 与 `reset()` 共用 `clearTransientState()`，所以两者不会分叉。

日夜由共享的 `DayNightCycle` 计算，客户端不自己维护 `TimeOfDayS2C.night`。

### 6.2 GUI

- `Screen`：`init/render/tick/鼠标键盘` + **对话框栈** + **`FocusManager`（键盘焦点唯一属主）**。`onResize()` 会重建基础 widget 并把已打开的对话框按新尺寸放回（对话框不会因改窗口而消失）。
- 子类用 `modalDialog()` 取"当前最上层模态对话框"，不要自己倒序扫描 `widgets`。
- **模态输入分发是强制的**：`mouseClicked` / `mouseMoved` / `mouseScrolled` 在 `Screen` 里是 `final`，先发给模态对话框、没有再发给 widget，最后才调**界面自己的钩子** `onMouseClicked` / `onMouseMoved` / `onMouseScrolled`（逻辑 GUI 坐标）。界面要处理自己的点击区域就覆写钩子，**不要**覆写 `mouseClicked`（覆写会被 `final` 挡住，模态分发不可能被绕过）。少数必须在原始像素坐标下工作的调用（游戏内相机）用 `rawMouseX/Y` 换算。
- `addWidget` / `showDialog` 会自动把 `EditBox` 接到焦点管理器；`widgets` 里消费点击的控件拿走焦点，其它情况释放焦点。
- `Clipping`：GUI 空间裁剪栈（`client.clipping().push/pop/pushPixels`），GUI→framebuffer 换算只有一份（`guiMouseX/Y` 的精确逆运算），支持嵌套求交；帧末 `reset()`。
- `SeedCardRenderer`：卡片绘制的**唯一**实现（游戏内卡槽与选卡界面共用），`CardKind` 决定底栏显示价格还是"收集"。**传送带上的卡不印价格**（`SlotInfo.NO_PRICE = -1`）：它不是"价格恰好为 0"，而是"这张卡是发给你的"，印个 0 会读成一次免费交易。
  - **卡面（chrome）是 `CardModel` 的一部分**：`background` 为空就是种子包；**铲子卡用 `SHOVEL_SLOT_BACKGROUND`（原版 `ShovelBank.png`）**，图标居中、底栏不印价格。
  - **卡槽条里每一张卡一样高**：`fitBackground` 只在"整张卡画的是别人的原图"时用（今天的奖励种子包），**工具卡不用它** —— `ShovelBank.png` 接近正方形，按自身比例居中画会把**整张卡**（连图标）缩到卡片高度的约四分之三，于是铲子/手套/锤子在同一排里比植物矮一截。工具卡的图要走卡片比例：植物卡是 100×140 的卡面 + 一张方形图标，工具照做即可（`textures/gui/cards/hammer.png` 就是这么渲染出来的，见 `tools/render_controller_icons.py` 的 `TOOL_ENTITIES`）。
- **拿起卡有声音，放下也有**：卡片条上按下（点击或拖拽都算）时，植物/工具卡放原版的 `sfx/ui/seedlift`，**铲子放 `sfx/effect/shovel`**；选卡界面与游戏内卡片条都走它。**把卡放回去是同一个手势倒过来，所以是同一个声音**（`playCardSound`）——再点一次已选中的卡、右键、点棋盘外都走 `cancelSelection`，一样有声。
- **关卡内的卡槽条有两种形态**（`InGameScreen.renderSlots`）：普通关卡是底部一排种子卡；**传送带关卡是顶部的履带**——托盘由原版 `ConveyorBelt_backdrop.png` 九宫格成框（`NinePatch.drawNineSlice`，边框按 GUI 像素固定，不随托盘拉伸），原版 `ConveyorBelt.png` 的胎面**画在框内**（`BELT_FRAME_X/Y` 是边框厚度，也是胎面的内缩量）并持续向左滚动。**裁剪必须用胎面自己的矩形**（`beltX/beltY/beltWidth/beltHeight`）：平铺的相位不落在框边上，首尾两块会伸到胎面之外，裁到托盘就会把左右两条边框盖掉（上下两条因为胎面在内缩框里所以看不出来，这正是「上下有框、左右没有」的来源）；卡片**骑在带上**从右端滑入、向左走到队尾停住，前面的卡被用掉时后面的会跟着往前挪（位置按卡 id 记录在客户端，见 §4.9）。胎面与卡片用同一个速度常数，否则卡会像在冰上滑。卡按带上顺序排列（**不**走 `orderCardSlots` 的"资源→植物→工具"分组：队列的顺序本身就是信息），点击命中按**当前绘制位置**判定。托盘宽度按 `belt_capacity` 固定，窄窗口下缩小卡片以保证不钻到暂停按钮底下。
  > 胎面纹理只在**去掉 1 像素边框后的中段**才是每 6 像素周期的，所以平铺取的是 `u ∈ [1/502, 499/502]` 这一段：整图平铺会把一条 2 像素的接缝每几秒滚过屏幕一次。
- **列表要"点一下就进去"时 → `AbstractSelectionList.setOnRowClick`**（标题页的玩家列表）。不要指望界面自己的 `onMouseClicked`：控件先吃掉点击，钩子根本不会被调用。
- **关卡内取消选卡**：再点一次已经选中的那张卡就放下它（右键与点击棋盘外同样取消），并放选中时那一声。
- **一次完整使用之后卡就回手**：`spendSelectedCard` 对所有卡（工具也算）都在发出请求后清掉 `selectedCard`。手套曾经是例外 —— 它是"拿起 / 放下"两击，于是卡在两次点击之间**保持选中**，而手套的冷却在**拿起那一刻**就开始了，卡条对"选中但没就绪"的卡画的是灰的、`cardUsable` 也会当场拒绝第二次点击（`sfx/ui/buzzer` + 抖动）：表现就是**手套卡住不动、像有无限冷却**，而植物还吊在手套上等 15 秒超时。服务端那半边的规则没变（`finishingMove`：正在拿东西的手套忽略自己的冷却，一次搬运只花一次使用次数），变的是客户端不再把"下一次点击要花掉的东西"留在一张已经冷却的卡上。
- **不能用的卡在点下去的那一刻就说"不"**：`InGameScreen` 用 `SlotInfo.available`（服务端把冷却、次数、价格三件事折成的同一个答案）当场判断：`refuseCard` 放 `sfx/ui/buzzer` 并让那张卡左右抖一下（`CardBar.Host.cardShake`，只有被拒的那张偏 6px，三条半周期后归零）。**不进入选中态**——被拒的卡不可以变成"下一次点击要花掉的东西"。
- **拖拽放卡**：在卡槽上按下就把卡拿起来（`draggingCard`），松手时若光标在棋盘内就直接种下/使用；松手在卡槽条上则保留选中，于是「点一下再点格子」的老手势一个字节没变 —— 两条路最后都走 `spendSelectedCard`。拖动时卡片图标跟着光标画，悬停格子的高亮仍然说明会落在哪。
- **按住扫过即拾取**：在棋盘上按住左键拖动，光标扫过的阳光/金币直接收集（`onMouseDragged` → `resourceDropAt` → `CollectResourceC2S`，同一个掉落物只发一次）。一次点击只能捡一个掉落物，而草坪上常常同时躺着五颗阳光 —— 让玩家逐个瞄准是纯体力活。
- **拖动预览（种植幽灵）**：选中的是**植物**卡时，光标悬停的格子上画一个该植物 idle 动画的半透明副本（`InGameScreen.renderPlacementPreview`，alpha 0.5，`client.pushEntityAlpha` 压住动画路径里写死的 alpha 1）。它点击选中与拖拽两种手势都显示，图形走的是实体渲染的同一个 `drawEntityArt`，所以预览与种下去之后长得一模一样。**位置必须写格中心**：光标给的是格子下标，而实体坐标是格中心（服务端 `new PlantEntity(...)` 传的是 `grid + 0.5`），直接把下标塞进 `setCellX/Y` 会让幽灵比真正种下去的植物低半格、左半格。**它不判断能不能种**：地形与叠放只有服务端知道（`PlantPlacement` 的 Ctx 需要服务端实体），客户端只保留了它确实知道的那一条——关卡放置区的绿/红悬停高亮。
- **开场与大波用原版贴图**（`client/gui/components/BannerAnimation`）：关卡开始的三拍是原版 `StartReady/StartSet/StartPlant.png`，最终波是原版 `FinalWave.png`，两者的时间轴逐帧抄自 `refer/anim/StartReadySetPlant.reanim` 与 `refer/anim/FinalWave.reanim`（12 fps），偏移按自身宽度归一化，所以画面尺寸变了动作比例不变；画在 **GUI 空间、窗口中央**（横幅是"游戏在对玩家说话"，不随棋盘缩放）。`FINAL WAVE` 由**最终波自己的 `awooga` 音效**触发，与那句音效是同一拍。"一大波僵尸正在接近！"仍是文本（原版也是用它自己的字体画的，资源里没有对应贴图），但动效改成原版那样：淡入 + 轻微放大、宽度按窗口自适应、后面垫一层黑字保证在草坪上读得清。
- **失败画面也是原版的**（`client/gui/components/DefeatScreen`）：黑幕淡到 0.5、`ZombiesWon_.png` 从中心放大到屏幕的 70%，逐帧抄自 `refer/anim/ZombiesWon.reanim`（24 fps，12 帧）。**它前面有两拍演出**（`InGameScreen.tickDefeat`）：镜头先朝房子平移 2.1 格（`PvzceCamera.panned`，**上限由 `maxPanX()` 给出**——背景图左边缘不能被推进画面里），停在最后那只僵尸啃房子的画面上约 1.2 秒（客户端把最靠左的地面僵尸按在 `eat`，并每隔 0.6s 补一声咬合音；关卡已经停止 tick，镜子里的它永远停在 `walk`，所以这是**唯一一处客户端改动画**的地方），然后才轮到失败画面。**平移期间点击不生效**（ESC 随时可以走），否则玩家随手一点就会跳过唯一说明"刚才发生了什么"的那一幕。
> 两个手势都走 `Screen` 的 `onMouseDragged` / `onMouseReleased` 钩子（与 `onMouseClicked` 同规矩：`mouseDragged`/`mouseReleased` 在 `Screen` 里是 `final`，先给模态对话框、再给控件、最后才给界面）。选中的卡是"下一次点击要花掉的东西"，是一种必须能不进不退地离开的模式。
- **选卡屏的入场编排，和它的"仅预览"模式**（`ChooseSeedsScreen`）：背景从"游戏内实际会看到的那一帧"（图左边缘贴在 `stage.x()`）向右**平移一个 `panMax`** 到路边、僵尸预览淡入、木牌从左侧滑入；`hasNothingToChoose()`（见 §4.5）为真时**只有前两拍**——不画木牌、卡池、顶栏与三个按钮，僵尸走完就自己平移回草坪开局（`PREVIEW_EXIT_NANOS = PAN_NANOS`，与出场同长），也就是原版 1-1 的样子：没有选卡页，只有一段过场。
  > **归位与游戏内必须用同一个 `panOffset`**：游戏内 `PvzceCamera` 显示的是 cover 之后**居中截取的中间一段**（图左边缘在 `stage.x()`），所以 `panOffset = panProgress * panMax`：home 与游戏内对齐，路的终点是背景图右边缘贴住屏幕右边。
- **不能选卡的关卡不进选卡页**：`SeedOptions.hasNothingToChoose` 为真时 `openSeedSelection` 仍然开这个屏（对话、平移、预览都在这儿），但它只是过场；**存档提示框的「重新开始」**则连过场都不走，直接 `RestartLevelC2S`——那一局玩家已经看过一次入场了。
- **底部提示框（`hud/HintBox` + `hud/LevelHints`）**：原版屏幕下方那个灰色半透明框，现在有了：
  `HintBox` 是纯 UI（一条台词 + 墙钟计时 + 淡入淡出 + 自绘圆角框），`LevelHints` 是关卡脚本
  （读 `LevelDef.hints()`，把 `on_start` / `on_resource` / `on_card_refused` 三个触发点接到它上面）。
  - **一条台词，且拒绝优先**：卡被拒绝是对玩家刚做的动作的回答，被教学文本盖住就正好在玩家问的那一刻
    把答案吞了，所以 `TUTORIAL` 顶不掉还在显示的 `REFUSAL`，反过来可以。
  - `duration_ticks` 缺省 160（约 2.7s），**写 0 = 常驻**，直到关卡结束或被下一条顶掉。
  - 触发点全部由客户端自己看得见（关卡起来、点了掉落物、点了用不了的卡），所以**没有新包、没有
    `PROTOCOL_VERSION` 变化**，关卡定义也照旧从本地数据包读（与对话、传送带同一层）。
  - 两句拒绝台词是**内置**的（`pvzce.cooldown` / `pvzce.not_enough`），关卡只决定"要不要有这个提示"
    （写一条 `{"trigger":"on_card_refused"}`），因为"冷却中"在每个关卡里都是同一句话。
  - 画在 **GUI 空间**（和波次横幅同一个理由：这是游戏在跟玩家说话，不该随棋盘缩放或平移），
    层高 0.45——在 HUD 之上、卡槽条与对话框之下，提示永远不会盖住它正在说的那些卡。
- `GuiText` / `GuiStatusText`：短 id、数字格式化/解析（带范围夹紧）、存档状态文案。
- `GuiLayout`：只负责按钮行高适配（`fitHeight`/`gapFor`）。
- `Screen.coverFit(...)`：cover 适配的唯一实现，返回 `CoverFit`，界面用它把"按背景图素坐标写死的面板矩形"映射成点击区域（背景怎么画、点击区就怎么算）。
- `ListEditorSupport`：关卡/音乐/卡池编辑器共用的列表编辑算法（刷新并保持选中、保留指定项、上移下移、删除后选中谁），**只有这一份**。
- `GuiLang`：`assets/<ns>/lang/<locale>.json` → 显示名。key 是 MC 的 `<namespace>.<path>`。编辑器、波次表、卡池页都走它，缺失的 key 回退到 path（不是 `namespace:path`）。
- `PaletteList`：带**贴图 + 名字**的列表行（`Kind` 决定贴图族：实体 / 场景 / 资源 / 纯色块）。
- **实体图标优先取动画资源**：`AnimationManager.iconTexture(id)` 取控制器模型里最大的部件贴图（或 flipbook 的第一帧），`PaletteList.iconFor(client, …)` 优先用它，取不到才回退 `textures/entities/<id>.png`。那张平铺 PNG 只是没有控制器动画时的兜底测试图，画出来和游戏里不是一个东西。
- 配置界面：`config/ConfigScreen` 用**一次 `layoutRows()`** 同时驱动"摆滑块"和"画标签"；滑块 `onChange` 只在值真变时触发，**落盘走 `onCommit`（拖拽结束）**。

### 6.2.1 关卡选择页（`LevelSelectScreen`）
- **左上角有一个「剧情：开/关」开关**（`storyToggle`）：关掉后进入任何关卡都**不播开场对话**（`PvzceClient.levelDialogue` 直接返回空表，所以选卡页与关卡内两条路一起静默；提示框 `hints` 不受影响）。它是**客户端配置**（`config/pvzce-client.toml` 的 `story`，缺省 `true`），不进配置界面：理由是"这场对话我已经读过了"是一次性回答，而不是每局都要重新决定的画面选项。按钮沿用世界里那个"标签即状态"的做法（`剧情：开` ↔ `剧情：关`），点击即存盘。
- **关卡的分类就是它的 id 路径**：`levels/yard/adventure/1_1.json` 加载成
`pvzce:yard/adventure/1_1`，第一段是主题、第二段是类别、其余是关卡自己的名字。规则只有一份实现
`api/util/LevelGrouping`（纯函数），服务端分组、客户端过滤、编辑器换组都调它 —— 读取依据是
**id 而不是文件位置**，因为文件里的显式 `"id"` 优先于路径，两者可以不一致。

- 主题与类别是**数据驱动的注册表**：`level_theme` / `level_category`，目录是
  `data/<ns>/level_themes/`、`level_categories/`，文件是 `id` + `order`（+ 可选 `trophy`）
  （**没有 name**：显示名与植物/僵尸一样走 `GuiLang` 的 `<ns>.<path>` key）。类别只声明一次、
  可被任意主题使用；某主题下出现哪些类别，由**该主题下实际存在的关卡**推出，所以加一批关卡
  不需要额外声明页签，也不会出现"打开是空的分类页"。主题顺序 = `order`，未分类页永远最后。
- **`trophy: true` 的类别，通关一门就在列表行右侧得一枚金杯**（原版 `refer/im7/images/trophy.png` → `textures/gui/screen/level/minigame_trophy.png`，按原比例画，行里的关卡名与 id 给它让位）。它是**类别的性质**：说的是"这一类关卡通关算一枚奖章"，所以同一类别下所有关卡共用，新加一关不用声明。判据是 `LevelInfo.cleared`（**通关过至少一次**）而不是行上那个标签 —— 已通关的关再开一局中途退出时行上写的是"进行中"，奖杯不会因此消失（与 §4.3「通关优先于进行中」是同一条事实的另一半）。`LevelSelectScreen.showsTrophy` 是唯一判定处（未知类别回答 false，客户端缺包也能画列表）。
- id 不足两段（`demo_level`、`yard/one_off`）、或引用了未注册的主题/类别 → **未分类**页
  （`pvzce:uncategorized` 哨兵）。**未分类页是固定页**：客户端在拼页签表时永远补上它，所以左侧列永远有"未分类"按钮、也永远能在那里新建关卡。服务端只下发有内容的页，空页由客户端补齐。`PvzceServer.validateLevelGroups()` 在 `/reload` 时把
  "谁因为什么落到未分类"打进日志，否则症状（关卡不在我放的地方）指向不了任何东西。
- 页签表由服务端下发（`LevelTabsS2C`，与关卡列表一起发；`PROTOCOL_VERSION` 因此 = 3），
  客户端**只渲染被告知的内容**：自己从关卡列表里收集页签的实现在"服务端资源包与客户端不同"
  时会给出与关卡不一致的导航，也无法表达顺序。`LevelInfo` 带 `theme`/`category` 两个字段，
  `LevelPage` 负责"这一页有哪些关卡"（纯函数，见 `LevelPage` / `LevelSelectSelectionTest`）。
- 页面形态：**左侧主题列 + 顶部类别行 + 行列表**（一关一行，一屏 6~8 关）。右侧仍是 `ListPaging` 翻页（箭头 + 滚轮），页码指示器在列表下方。
- `LevelCreateDialog` 的主题/类别两行按钮**预选当前正在看的页**，id 预览实时显示
  `<命名空间>:<主题>/<类别>/<名字>`；**命名空间是独立的一个输入框**（默认 `pvzce`，自由文本 +
  标识符命名空间字符校验），数据包/模组不必再被塞进内置命名空间；**未分类页保留自由 id**
  （该桶的定义就是"id 里没有主题"），手打 `namespace:` 时也仍然自由。文件路径、id 的
  "创建后只读"规则都不变。
- 编辑器信息页可**换组**，保存时 `LevelMove` 一并完成：**换 id + 移关卡文件 + 搬该关存档目录
  与通关标记**（旧的 `sourceFile` 在新文件写好之后才删，失败则整体不动）。id 是存档目录名、
  通关标记与其它关卡引用的键，所以这是**唯一**允许改 id 的操作，且是显式的，不藏在改名里。
- **冒险模式 Day 区（1-1~1-10）按原版铺开**（`levels/yard/adventure/1_{1..10}.json`），草坪一行行放开、每关首通给下一关要用的卡：

   **2-2~2-5 是 Night 区的其余四关**，奖励同样按原版顺延一位（原版 2-2 阳光菇 / 2-3 大喷菇 / 2-4 墓碑破坏者 / 2-5 不给植物，而阳光菇已经由本项目的 2-1 发出，所以 2-2 发大喷菇、2-3 发墓碑破坏者、2-4 发锤子、2-5 走引擎默认钱袋）。**2-2** 引入铁桶僵尸；**2-3** 引入纱门僵尸（`door_zombie`，正面护甲），也正是大喷菇的喷雾**穿透且无视护甲**（`ProjectileDef.damage_type: pvzce:ash`）第一次有用的地方——平射弹先撞 `front`，喷雾直接落身体；**2-4** 是墓碑最多的一关（原版的 7 个：`6,0 / 8,1 / 5,2 / 7,2 / 6,3 / 8,3 / 7,4`），撑杆僵尸回归。

   **2-5「打地鼠」的数值**：`zombie_speed_multiplier: 2.2`（原版这一关的僵尸明显快过普通关：9 格约 11 秒走完），`zombie_sun_drop_chance: 0.08`（**没有阳光产出、天上也不掉，击杀是这一关唯一的阳光来源**），波次总量是原版的 3 倍（132 只 / 6 波），出怪间隔减半（75~210 tick），`graves_spawn_night: true` —— 于是**墓碑有两种出怪方式**：`grave_spawner` 全程持续冒，最后一波再由 `graves_spawn_night` 把每座墓碑一次性开一遍（两条规则各管各的，见 §4.9）。

   **2-5「打地鼠」是第一种"点击就是工具"的关卡**（`pvzce:tool` 机制 + `grave_spawner` 机制，见 §4.9）：卡槽钉死墓碑破坏者 / 土豆雷 / 樱桃炸弹三张（原版的三张，`max_seed_slots: 3`），**没有小推车**（`mower.rows: []`），天上不掉阳光，僵尸全程由墓碑**持续冒出**（不是从马路走进来），被砸掉的墓碑会补到九座。**鼠标就是木槌**：没选卡时点格子即用锤子，**无冷却、不花阳光**（关卡声明的 `cooldown: 0` + 空 `cost`）；同一把锤子在其它关卡是**卡**，30 秒冷却、50 阳光（`tools/hammer.json`），也是 2-4 的首通奖励。音乐沿用 n-5 的 `loon_boon`，首通解锁**魅惑菇**（原版这一关不给植物，但本项目的奖励链需要一个位置给它；见 §5.2 的 `pvzce:charm`）。这一关同样**不经过选卡界面**（`slots.size() == max_seed_slots`，走"仅预览"过场）。

   **2-1~2-5 各有一段紫夜白的开场对话**（`dialogue.lines`，全部 `side: left`，除了 2-3 的头两句站在右边、2-4 的最后一句在中间 —— "她从右边走回左边"这件事就是靠 `side` 演的），立绘名指向 `textures/gui/dialogue/purwhite/<名字>.png`。

   **2-1 是 Night 区的第一关，也是"整关固定夜晚"的第一个用例**：`day_length: 0` + `night_length: 360000`（没有白天可回，所以 `DayNightCycle.alwaysNight` 让客户端第一帧就是暗的，不再需要 1-10 那种"先给一 tick 白天"的写法），`sun_spawn_chance: 0` 天上不掉阳光，音乐换成原版夜间的 `music/moongrains`，奖励解锁**阳光菇**（原版 2-1 发的是小喷菇，而小喷菇已经由本项目的 1-10 发出，所以顺延一位——夜关没有天上阳光，正好需要它）。草坪上按原版放了 **4 个墓碑**（右半边四格，四种不同的原版墓碑美术：`grave`/`grave_cross`/`grave_slab`/`grave_wide`，都在 `#c:unplantable` 里，所以那四格只能绕开），僵尸里新增**读报僵尸**。**`graves_spawn_night` 在这一关关掉了**：引擎那条规则是每 tick 每个墓碑摇一次（四座墓碑约合 4 秒一只），而原版只有 2-5「打地鼠」才从墓碑里产怪——2-1 的墓碑是障碍物，不是产怪口（要开回来只改一个布尔）。

### 6.2.1b 标题页：谁要玩游戏（`TitleScreen` / `PlayerPickerDialog`）

- **玩家列表就是世界列表**：一个世界目录就是一名玩家的存档（`saves/<名字>/`），所以原版的"你是谁"和本项目的"选世界"从来是同一个问题。
- **标题页上只有名字**：左上角一块木牌（`renderPlayerBoard`）写着当前玩家的名字，底下是「谁要玩游戏？」。整块牌子就是按钮，点击弹出 `PlayerPickerDialog`。牌子**不是控件** —— `Button` 只画一行居中的文字，而这是两行不同字号、都要落在牌子里面，所以牌子由界面自己画、点击由 `Screen.onMouseClicked`（界面自有点击区的规定位置，见 §6.2）处理。
- **`PlayerPickerDialog` 只负责切换**：列表＝世界列表，加名字输入框、全解锁开关与「新玩家 / 删除选中 / 切换到这个玩家」。选中一个名字**只高亮**，真正改阵营的是「切换到这个玩家」；它也**不会打开关卡列表** —— 那是菜单上「开始游戏」的事，一个点击同时"换人"和"出发"会让两件事变成同一个手势。标题页的木牌在对话框后面，切换后下一帧就显示新名字，这就是反馈。
- **对话框的边框按 `frameScale` 缩着画**：九宫格石框在原图里约 209 像素边框，3 倍 UI 下框本身就吃掉小对话框的大半个身子，列表＋输入框＋四个按钮放不进剩下的地方。`Dialog.frameScale(0.55)` 是同一份雕花按比例变薄，切片形状不变；`Dialog.inlineTitle()` 则把标题从"挂在框上的木牌"换成框内一行字（木牌约 38 单位高，内容密的对话框没有地方留给它）。
- **点名字就是进关卡** 这条只属于**关卡列表**：那边列表多了一个 `onRowClick` 回调（`AbstractSelectionList.setOnRowClick`），因为控件会吃掉自己的点击 —— 界面自己的 `onMouseClicked` 钩子只在"没有控件接手"时才跑，所以"先选中、再让界面决定"这条路对列表根本不成立。
- 世界选择不再是一屏 `WorldSelectScreen`：它已删除，`PvzceClient.showWorldSelect()` 变成 `showTitle()` 的别名（离开关卡、协议不符、关卡列表的声明根都还叫这个名字，它们不该各自知道"玩家选择在哪一屏上"）。
- **`${user_name}`**：关卡对话的台词里可以写这个占位符，替换发生在 `DialogueOverlay.create` 建帧的时候（不是画的时候）—— 一行台词因此只有一个最终文本，打字机、换行与"点击继续"量的都是同一个串，晚到的改名不会让半截句子在玩家眼前改变长度。值是 `PvzceClient.currentWorld()`，也就是玩家在标题页选的名字。写错的花括号不会被吃掉，原样显示，作者一眼能看见。

### 6.2.2 开场对话（`DialogueOverlay`）

关卡可以有一段**开局对话**：数据是关卡 JSON 的 `dialogue` 块（每行 = 角色 / 立绘 / 台词 / 语音 /
站位 / 该行的动画）加一个 `dialogue_character` 注册表（显示名、立绘目录、大小、气泡贴图），所以**加一个新角色
不用改代码**。运行时的唯一实现是 `client/gui/components/DialogueOverlay`：立绘贴说话那一侧的屏幕
下沿，气泡用 `box_left`/`box_right` 单图九宫格画在对侧（尾巴落在左下/右下那 56×24 的角里，改贴图时
别把尾巴挪出角外），台词按气泡内宽逐字换行、**逐字打出**（打字机），左键推进、ESC 跳过整段。
播放有两处入口——走选卡页的关卡在选卡页里播（镜头横摇之前），直接进关卡的（传送带关、编辑器测试）在关卡内播并暂停整关——**两处都从 `PvzceClient.levelDialogue` 取台词**，所以关卡选择页的「剧情」开关（§6.2.1）在这两处同时生效：关掉后连 overlay 都不会建，不是"把字藏起来"。

- **入场与出场是整段对话的首尾各一次**（`dialogue.enter` / `dialogue.exit`，缺省 `slide`，可写 `none`）：第一句的立绘从**自己那一侧**滑入（左角色从左、右角色从右，`center` 没有"自己那一侧"，于是**从下方升起**），最后一句点完时同一个方向滑出，**滑完才调 `onFinish`**——所以"人退场了，镜头才开始走/关卡才开始"。ESC 跳过整段**不补动画**（玩家刚说了"我不看了"，再让他等一段动画是唯一不能做的事）。中间换说话人**不动画**：`"首尾各一次"` 就是这个意思，换人直接切，也正是这两个效果能被读成"这场对话开始了/结束了"的原因。几何是三个纯函数（`DialogueMotion`：滑入滑出的偏移、抖动的阻尼正弦、缩放的插值），时长在它的常量里（滑入滑出 0.35s、抖动 0.35s、缩放 0.25s）。
- **每条台词可以带一个动画**（`line.animation`，缺省 `none`）：`{"type":"shake","amount":2}`（**抖一次**：阻尼正弦，幅度 = 窗口宽的 1.2% × `amount`，0 表示不抖）或 `{"type":"scale","scale":1.25}`（**改这条立绘的大小**：从上一句留下的尺寸平滑过渡到该倍率，下一句没写就回到 1）。缩放**以底边为基准**（人是长高了，不是飘起来了），代价是超过约 1.11 之后**头顶会被窗口裁掉**——`MAX_SCALE` 因此只有 1.6，这是"贴底立绘还能放大多少"的答案，不是一个凑整的数。抖动与缩放都作用在**整块立绘矩形**上，气泡锚在立绘边缘，所以两者一起走（气泡不会站在原地看人走开）。首句的动画与入场滑入同时开始，这是有意的：一句喊叫本来就该在人物进场的同时发生。
- **站位有三档**：`side` 取 `left` / `center` / `right`。`center` 把立绘摆在窗口正中（同一尺寸，占窗口高 90%），
  气泡**居中压在下半部**（底边仍是 70% 那条下巴线）——"旁边"在正中间没有意义，左右两种答案都会把气泡尾巴指向空草坪。
  编辑器「对话」页的位置按钮在左→中→右之间循环，写回文件的就是这三个词。
- **台词可以为空**：`text` 为空 = **没有台词的一拍**，只演立绘、一个气泡都不画（`Frame.silent()`，`bubbleBox` 返回
  `null`），点一下继续。原版用它做表情演出。
  `LevelValidator.validateDialogue` 因此不再把"没有台词"报成问题，只把拼错的 `side` 报出来。

- **它是一个 `Dialog`（modal）**，不是新机制：`Screen` 把鼠标 / 键盘 / 滚轮事件先给最上层模态对话框，
  所以"对话期间选卡与按钮点不动"是结构上成立的，不需要在每个宿主界面里各写一份输入闸门。
- **排版跟角色走，不跟屏幕走**：立绘占窗口高度的 90%（×角色 `scale`）、贴下沿，气泡按**台词自身**的宽度收窄
  （短句就是一个小气泡），底边固定在窗口高度 70% 处（说话人的下巴高度），行数多了就向上长；气泡里台词右下角
  有一行小字「点击继续」（`pvzce.dialogue.click_continue`）。气泡靠角色的那一侧锚在**立绘宽度的 80%** 处
  （`BUBBLE_PORTRAIT_ANCHOR_RATIO`）而不是贴图边缘：立绘是整幅带透明边距的图，锚在贴图边缘会在角色和气泡之间
  留出一大块空白。立绘在左时气泡在右，反之亦然；两者都在 `DialogueOverlay` 的常量里，要调只改那几个数。
  换行后如果最后一行只剩一个字，会把上一行最后一个字挪下来（`avoidOrphans`）——"…僵尸的世 / 界" 是对的换行，
  但不好看。台词字号上限 1.35（随窗口高度增长），气泡内边距也在同一组常量里。
- **打字机**：每秒 28 字（`TYPEWRITER_CHARS_PER_SECOND`），句末标点额外停 0.18s、句内标点 0.09s
  （`pauseAfter`），所以读起来像说话而不是电传打字机。揭示进度**由墙钟推导**（`lineStartNanos` +
  `revealedCharacters`），不是每帧累加，掉帧不会让台词变慢。**气泡按整句排版、只画已打出的前缀**
  （`typedPrefix`），所以打字过程中气泡不会忽大忽小；「点击继续」小字只在整句打完后才出现——打字途中
  那一下点击的语义是"补全整句"，写"继续"会骗人。
- **两个宿主**，取决于这一局怎么进的：走**选卡界面**的关卡在 `ChooseSeedsScreen` 里播——对话期间镜头
  停在最左（房子一侧），草坪与僵尸预览照常渲染，对话结束后才走既有的"横摇 → 木牌滑入 → 选卡 / 自动开始"时间线（`panStartNanos`，无对话时就是 `startNanos`）；**传送带关卡**这类没有选卡界面的直接进
  `InGameScreen`，对话在草坪上播，`entryNanos`（"准备… 安放… 种植！"横幅）推迟到对话结束，
  期间发 `PauseGameC2S(true)` 冻住关卡、结束时恢复。
- **触发条件是"新开一局"**，不是"第一次玩"：选卡界面只在没有存档时打开（`enterLevelFromMenu`），
  所以它自己就能判定；直接进关卡的那条路（传送带、编辑器测试、暂停菜单重开）由 `PvzceClient` 用
  `directDialogueLevelId` 把"这一局是新开的"带过关卡初始化的往返。继续一局存档不播，通关后再玩会再播。
- 客户端从**本地数据包**读对话（与 `usesConveyorBelt` / `lockedSlotsFor` 同一层），所以没有新包、
  没有 `PROTOCOL_VERSION` 变化。
- 校验：`LevelValidator.validateDialogue` 报未知角色 / 拼错的 `side` / 拼错的 `enter`·`exit` / 未知的
  `animation.type` / 非法立绘名（加载时随其它关卡问题一起打；这些值都像 `side` 一样解成 `UNKNOWN`
  而不是让整个关卡解析失败，`UNKNOWN` 的表现就是缺省行为，所以拼错不会把对话变样，只会被报出来），`validateDialogueAssets` 在 `/reload` 时按 `PvzceResourceManager.hasTexture`
  报缺失的立绘与气泡贴图（`[PVZCE/对话]`）。立绘名必须是**文件名**：`Identifier` 的 path 允许 `/`，
  不过滤的话 `../别人的角色/smile` 会解析出本角色目录之外。
- **台词里的 `${user_name}` 会被换成玩家名**（标题页选的那个名字，见 §6.2.1b）：替换在 `DialogueOverlay.create` 建帧时做一次，所以一行台词只有一个最终文本，打字机、换行与"点击继续"量的都是同一个串。写错的花括号原样显示，作者一眼能看见。
- 编辑器有独立的**「对话」页**（列表 + 角色/立绘两个选择器 + 台词/语音/位置 + **动画**），保存时只覆盖
  `dialogue.lines`，块内其它字段（`enter`/`exit`、以后的 `trigger` 之类）原样保留；台词框每帧提交进模型，所以
  换行、点别的台词或直接按保存都不会丢掉刚打的那句。「动画」是一个循环按钮（无 → 抖动 → 缩放）+ 一个数值框
  （抖动幅度 / 缩放倍率，选"无"时禁用）；**只有非"无"的行才写 `animation` 块**（"没有动画"就是字段不存在，
  给每条台词都写一遍 `{"type":"none"}` 是让作者每次都要读过去的噪音），页面上不认识的类型**整个对象原样写回**
  （与解锁页对无法编辑的条件类型同一条规矩）。

### 6.2.3 关卡编辑器（`EditorScreen`）

一页一个主题，导航栏切换：**地形 / 植物 / 僵尸 / 规则 / 波次 / 卡池 / 音乐 / 信息**。前三个共用左侧内容面板 + 中间画布 + 右侧操作面板；其余页把中间与右侧合成一块面板。

- **画布走游戏自己的世界投影**（`beginOverlayWorldView` + `SceneTileRenderer.render` + `AnimationManager.render`），不是 GUI 空间的一堆 quad。所以预设植物/僵尸**播的是游戏内动画**，格子形状也和游戏内一致 —— 画布的落点来自同一份 `LevelStage.board(canvasW, canvasH, columns, rows)`，而 `cellAtCursor()` 是它的精确逆运算。
- 预览实体在 `syncCanvasEntities()` 里建 `ClientEntity` 并**手动 `attachAnimationManager`**：动画管理器平时由 `ClientLevel` 在 spawn 时注入，编辑器不走 spawn 包，不接就没有动画。`releaseCanvasAnimations()` 在每次重建与退出时释放 playback（与选卡预览同一个泄漏点）。
- **规则页对注册表生成**：遍历 `GAME_RULES`，布尔 → 开关按钮，数值 → 滑块 **+ 数值输入框**（滑块表达不了 0..12000 的 tick）。滑块范围来自 `RULE_RANGES`，与 `BuiltInRegistries.registerGameRules` 的注册值对应；只写被改过的规则，其余留空以继承默认值，列表上标"已改"。
- **波次页**：**表格 + 详情同屏**，占满整宽（`fullContentArea()`）。左表：一波一行（序号 / 类型 / 间隔 / 预警 / 僵尸组成 / 合计）；右栏：选中波次的类型 / 间隔 / 预警 / 数量，加「组成」与「可选僵尸」两个列表；底部：新增/删除/上移/下移/自动填充/末波倍率。**没有二级菜单**，波次数据与 JSON 在 `WaveEditorModel` 里。
- **音乐页**：同样是**时间线 + 详情同屏**、占满整宽。左：cue 列表（tick / 轨道 / 事件）；右：tick / 音量 / 淡入、轨道 / 循环 / 停止、事件选择（点选即应用，读 `SOUND_EVENTS` 里所有 `music/` 条目）。也没有二级菜单，数据在 `MusicEditorModel` 里。
- **底部动作栏只有「保存 / 测试 / 返回」**，编辑入口只从导航栏进。
- **卡池页**：**两列**——左边是本关卡的卡（顺序即游戏内卡槽顺序），右边是全部卡（按 kind 分「植物·资源·工具」三段，带分段标题）。按钮排在列表**下方的独立两行**里，不压列表；右列里本关已选的卡带一个右对齐的「已选」角标。
- **卡槽规则只有一条**：**关卡列出的卡就是固定的**（进入关卡必发、选卡界面不能取消），**总卡槽数减去关卡卡数就是玩家自选的空间**。没有 per-card 的 fixed 开关，也没有 `seed_selection` 这种第二份"哪些是可选"的声明 —— 位置即语义。`LevelDef.seedPlan(allCards)` 是这条规则的唯一实现：`lockedSlots` = 关卡的卡（按顺序、去重），`pickableSlots` = 全部卡减去已固定的，`maxSlots` = 总卡槽数。
- `max_seed_slots` 在 `LevelDef` 的规范构造器里**自动抬到不小于关卡卡数**：关卡列了 13 张却声明 6 个卡槽，只可能是数据写错，截断会静默丢掉作者自己的设计。`LevelValidator.validateSeedSelection` 会把"关卡卡数 ≥ 总卡槽数（玩家没有可选）"和"卡池引用未知卡"报出来。
- 服务端 `sanitizeSeedSelection` 先放关卡的卡、再按提交顺序补玩家的选择直到总卡槽满；不认识的卡与重复卡丢弃。选卡界面对固定卡画挂锁角标、点击无效、"清空"只清玩家自己选的。客户端绕不过这些 —— 服务端会重新算一遍。
- 想给玩家留选择空间：关卡卡数 < 总卡槽数即可（编辑器卡池页顶部实时显示「总卡槽 / 关卡固定 / 玩家可选」三个数）。
- **信息页**：关卡名称、描述、初始阳光、**奖励**（首通解锁卡 / 重复通关金币 / 僵尸掉币概率 / 每次掉币数量）；关卡 ID **只读**（创建后不可改，存档、卡池、其它关卡都引用它）。奖励块**整块由编辑器写出**（它只有四个字段），手写的多条 `first_clear` 会在保存时被规范化成"至多一张卡 + 一条金币"。
- **保存**：`buildLevelJson(previous, ...)` 从**载入时的 JSON** 出发，只覆盖编辑器拥有的字段，所以 teams、`env_vars`、其它工具写的元数据、更新版本新增的字段都不会因为"编辑了一下"而消失。写入路径优先回写**载入时那个文件**（`sourceFile`），内置关卡才落到 `datapacks/user_levels/`。
- **新建流程**：`LevelSelectScreen` 的「新建关卡」→ `LevelCreateDialog`（主题 / 类别 / 名称 / id / 尺寸）→ 编辑器；id 与名称从此分离，主题/类别默认取**当前正在看的页**，id 预览实时拼成 `pvzce:<主题>/<类别>/<名字>`。列表下方的「编辑关卡」按钮把**选中的关卡**送进编辑器。
- **「测试」与「从列表打开」走同一条路**：测试按钮只保存，然后交给 `PvzceClient.testEditedLevel`：它等**服务端重载后的关卡列表**再打开选卡界面 —— 必须等，否则选卡界面描述的是保存前的那份定义。`/reload` 命令因此会主动补发一次关卡列表（`PvzceServer.refreshLevelList`），客户端不必猜重载要多久。
- **列表分页**：左右箭头与滚轮都是**翻页**，不是滚动。算法抽到 `client/gui/layout/ListPaging`（纯函数，可单测）：首页行号永远是页大小的倍数，末页夹到 `(pageCount-1)*pageSize`，页数**向上取整**（最后一页只装残余行，可能不满）。`ListPagingTest.everyRowIsReachableOnExactlyOnePage` 对全部"行数 × 页大小"组合断言**每一行恰好出现在一页上** —— 它同时挡住两类翻页 bug：页数向下取整会让尾部若干行**没有页**，按 `totalRows - pageSize` 夹取会让相邻两页**重复同一行**。不重复靠"末页也从页边界开始"，不靠砍掉末页。
- 底部动作栏是**四个**按钮：下一步 / 编辑关卡 / **背包** / 返回；右上角是**本世界的金币**（`drawCoinCounter`，`money_bag` 贴图，缺图回退金币贴图）。
- 「返回」走 `LevelSelectScreen.goBack()`：栈里还有上一屏就 `closeScreen()`，否则 `showWorldSelect()`。通关后客户端是用 `showLevelList()` **整体替换**屏幕栈的，此时栈里只有这一屏，直接用 `closeScreen()`（它拒绝弹出最后一屏）会让按钮**完全失效**；ESC 也走同一条路。
- 列表里选中一张卡会**同时**点亮「下一步」和「编辑关卡」（`updateActionButtons`）。这个按钮还会按选中关卡改名（进行中 → 「继续游戏」，见 §4.3）。
- **选中的是关卡本身，不是格子**：`LevelSelectScreen` 记住选中关卡的 **id**，每次列表刷新（换世界、`/reload`、编辑器存档）后按 id 重新解析行号（`indexOfLevel`，纯函数），所以"高亮的卡"与"按钮作用到的关卡"必然是同一个。

### 6.3 渲染

- `RenderSystem`：极薄的 GL 门面（混合/深度、投影、纹理缓存绑定、时令光照 uniform、**世界空间点光源** `setPointLight`：上限 `ShaderProgram.MAX_POINT_LIGHTS`，着色器里按半径做 `smoothstep` 叠加）。
  **只有阳光是光源**（`PvzceClient.lightsTheBoard`，按**内容 id** `pvzce:sun` 判定；白天暖黄、夜里偏冷）。**实体 kind 是类别（plant/zombie/projectile/resource），永远不是内容 id**：`EntityKind.RESOURCE` 是 `"resource"`（kind 字符串走 `EntitySpawnS2C`，故 `PROTOCOL_VERSION` = 10），`EntityLightTest` 同时钉住「只有阳光亮」与「kind 不等于任何内容 id」。
- `SpriteRenderer`：`textured` / `texturedQuad` / `solid` / `shadow` / `projectedShadow`（投影阴影是真梯形，远边有纵向跨度）。
- `PvzceCamera`：把格子坐标映射到背景图上的草坪。**`inBoard` 接收的是 GLFW 原始自上而下的鼠标 Y，内部会翻转**；与 `worldX/worldY`、`screenX/screenY` 同一坐标系语义。
- `EntityTextures`：内容 id → 纹理 id 的唯一换算（保留命名空间）。**转发给 `EntityArt.sprite`**，因为路径不再能从 id 推出来：内置美术按类目分层（`textures/entities/plant/attacker/pea_shooter/`），所以定义里用 `texture` 字段显式声明；没声明的（mod 的常规写法）仍然按 id 推。
- **缺失贴图只有一个样子**：`EntityArt.MISSING_TEXTURE`（`textures/mission.png`，2×2 品红/黑棋盘格，`TextureManager` 对它单独用 `GL_NEAREST`，否则放大后四个方块会被插值糊成一片紫色渐变）。`PvzceClient.drawTextureRegion` 与 `drawTextureQuad` 取不到贴图时画的就是它（`drawMissingTexture`），动画部件也走同一条路——它和"故意画成空白"的精灵不会混淆。`EntityArt.sprite(null)` 也回答它。
- `EntityArt`（`common/core`）：**"这个内容 id 用哪份美术"的唯一答案**，两个问题一次查表 —— 播哪个**动画文件**（`animationFile`，读定义里的 `animation_dir`，缺省回落到 id 路径）与没有动画时画哪张**兜底贴图**（`sprite`，资源注册表里的资源另外回落到它自己的 `icon`）。渲染器、编辑器图标、选卡图标与 `AnimationManager` 都从这里取。
- `EntityVisuals`：每类实体的视觉常量（脚→动画锚点抬升、贴图兜底尺寸/偏移、渲染层、排序桶）唯一来源。新增实体种类只改这一张表。
- `LevelStage` / `SceneTileRenderer` / `FontRenderer`：背景舞台、场景瓦片、位图字体。

#### 6.3.1 液体渲染（`client/renderer/liquid/`）

场景元素带 `liquid` 字段时不再走贴图，改由一个**独立的水面 pass** 绘制。它不是第二套精灵管线，而是"几何一次批量、图案全在 shader 里"的一条通道：

| 类 | 职责 |
|---|---|
| `LiquidDef`（`api/content`） | 渲染参数的**唯一载体**：色板、不透明度、深度尺度、泡沫、波形、焦散、高光、静态帧数。`data/<ns>/liquids/*.json` |
| `LiquidGeometry` | 纯函数几何：8 连通 BFS 求**离岸距离**（深度场），外加每格四边/四角的接壤掩码。可单测，不需要 GL |
| `LiquidBatch` | 每格两个三角形，一次 `glDrawArrays`；VAO/VBO 建一次复用 |
| `LiquidShader` | `#version 150 core` 独立 program + 自带 attrib 绑定（0..3） |
| `LiquidRipples` | 固定 16 槽环形缓冲，满了丢**最旧**（新溅的水花才是玩家在看的） |
| `LiquidTextures` | 场景元素 id → 液体定义的唯一解析点（带缓存，`/reload` 时清） |
| `LiquidRenderer` | uniform 上传、画质档 → 特征位、关闭 shader 时的烘焙帧降级 |

**顶点属性**：在共享的 `POSITION(3)+COLOR(4)+UV(2)` 后**追加** `LIQUID(4)`（共 13 float），所以现有所有绘制路径一行未改。`aLiquid` 打包为：格坐标（+1 使符号可承载"该侧是否有岸"）、接壤掩码、角落掩码、深度（3 bit）。**注意坐标轴是反的**：north 标志在 x、掩码的 north 在 y，详见 `LiquidVertexFormat` 的注释。

**着色器次序**（顺序即正确性，改一处要想清楚）：
底图（按**世界格坐标**连续平铺，不是每格重开）→ 水色吸收（`opacity` 是"水占多少"而不是 alpha）→ 焦散网 → 日光高光 → 菲涅尔 → 泡沫与临陆内缩 → 昼夜色调。
**水体不透明**，只有临陆边缘羽化；内部格之间不软化，否则会在湖心露出接缝。

**画质档**（`config/pvzce-client.toml` 的 `water_quality`，视频设置可切）只切特征位与采样量，**不切几何**，所以三档的水面形状完全一致。`shaders_enabled=false` 时整条 pass 换成 `textures/scene/water_frames/water_*.png`（`tools/gen_water_frames.py` 生成，由 `static_frames` 决定帧数并循环）。

**涟漪**：服务端 `LevelServer.emitRipple*` 是唯一权威点（僵尸入水已接入），经 `EffectEventS2C` 的 `ripple`/`ripple_strength` 字段下发，客户端按液体 id 解析后入槽。涟漪是纯表现，走墙钟而不是 tick，所以暂停时水面照常流动。

### 6.4 动画

- `AnimationManager`：playback 表 + 文件缓存。`play()` 的幂等判据是**当前活动 clip**（循环 clip 在播则不动；已结束的一次性 clip 允许重开），不是 `requestedState`。
- `MovingTarget`（`client/api`）：`Animatable` 里"有地面速度"的那一半。走路/飞行这类 clip 的**作者速率由实测位移推**（`AnimationPlayback.measureLocomotion`），而位移只有实体才有，所以它是一个独立接口而不是 `Animatable` 上的一个方法——机制道具、UI 预览、掉落物都播 clip 但没有地面速度，给它们编一个位置只会让答案变成假的。位置读的是**绘制位置**（`drawnX/drawnY`），不是权威坐标：脚要踩的是屏幕上那条线。
- `AnimationPlayback`：共用的时间/过渡/事件/生命周期；两个后端 `FlipbookPlayback`（帧序列）与 `ControllerPlayback`（骨骼控制器）。
- `Timeline`：**唯一的时间线数学**（循环 wrap、非循环夹紧、帧查找、延迟默认值）。新增采样方式请走它。
- `AnimationResourceLoader`：clip 公共字段（`loop/on_end/next/transition`）与"animations 条目必须是对象"的校验都只有一份。
- 缓存：文件存在但解析失败与文件不存在**分开记录**；`invalidate()` 在资源重载时清空两者（否则一个坏关键帧会永久禁用该动画）。

### 6.5 声音与粒子

- `SoundEngine`（OpenAL）：事件表来自 `assets/pvzce/sounds.json`；音高有统一夹紧范围。**音频源在重新绑定 buffer 之前一律先 `alSourceStop`**：源是 16 个一组的环形缓冲，6 秒的大波提示占用的那个源马上会被下一个音效重用，而 `AL_LOOPING` 是**源的属性、不是 buffer 的属性** —— 一个被要求循环过的源会把之后绑上来的任何 buffer 一直循环下去。`play()` 另有两道保护：同一事件 130ms 内的重复被折叠（齐射不会糊成电流声），以及**一个事件在自己的声音播完之前再次请求会被丢弃而不是叠加**（`nextSource` 返回 -1）—— 上游把同一个事件每帧发几百次时，玩家听到的仍然只是那一个声音，而不是环形缓冲绕圈循环。两道保护都不是"哪些音效只能播一次"的白名单（会公告自己的音效换过一次，白名单也得跟着换）。`-Dpvzce.traceSounds=true` 会按秒打印实际播放的事件计数，用于诊断这类问题。
- `PvzceMusicController`：菜单/关卡/静音轨与淡入淡出；`ensureMenu(track)` 在**同曲已播时不重启**（界面 `init()` 会在每次改窗口大小时重跑）。
- `PvzceMusicController.ensureMenu(event)` 的语义是**"同曲不重启，异曲要换"**：菜单之间的交接（奖励页 → 关卡列表 → 选卡页）因此真正换曲，而窗口缩放反复调 `init()` 依旧不会重头播。
- **音乐属于"一局"**：轨道名（`menu`/`background`/`battle`/`stinger`）以 `MusicEventS2C.TRACK_*` 为唯一定义（关卡数据与客户端控制器共用同一批字面量）。关卡时间线在波次处把背景轨换成战斗轨，而**只有"离开关卡"这条路会停乐**（`clearLevelClientState()` → `music.leaveLevel()`），重开与编辑器「测试」都不经过它。**每个新关卡实例**由服务端在 `LevelInitS2C` **之前**补发三条 `MusicEventS2C.reset(track)`（`PvzceServer.silenceClientLevelMusic()`）——顺序有意义：init 才是启动新轨道的那一步。**同一实例的 resync 不发重置**（它的音乐就是当前状态，`startLevel` 的"同曲不重启"也因此得以保留）。
- `ParticleEngine.tick(seconds)`：**按时间步进**（不是按帧），单帧步长上限 0.1s；寿命以 60tps 的 tick 授权、内部按秒积分。

#### 6.5.1 粒子（数据驱动）

粒子是**数据驱动**的：原版那 81 张粒子贴图与 112 个 emitter 脚本都能用上。

| 位置 | 职责 |
|---|---|
| `ParticleDef`（`api/content`） | 定义载体，**JSON 是扁平的而 record 是嵌套的**：`look`（贴图/帧序列/寿命/缩放/自旋/透明度曲线/颜色）与 `motion`（速度/角度/重力/阻力/落地），另加 `additive`、`count`、`count_spread`。`data/<ns>/particles/<类目>/*.json` |
| `PvzceParticles`（`common`） | 内置能力默认引用的效果 id。**与 `PvzceSounds` 同形**：不要在能力里散落字符串字面量（未知 id 只在客户端每秒报一次日志，症状"这个效果不见了"指向不了任何地方） |
| `ParticleEngine`（`client/particle`） | 世界空间贴图粒子：帧动画、旋转 quad、**加法混合**两趟批处理（普通粒子先画、发光粒子后画，整帧最多切两次混合状态） |
| `RenderSystem.blendAdditive/blendNormal` | 加法混合。原版的光晕就是加法画的，用普通 alpha 画出来是一块盖住底下东西的实心圆盘 |

- **未定义的效果不画东西**，只按 id 报一次日志，所以拼错不会伪装成一个真效果。
- **`scale` 就是"画多大"，单位是格**（引擎里直接 `size = particle.scale`）。它来自原版的 `ParticleScale`，而原版的取值恰好约等于"精灵像素 / 80"——僵尸手臂 26px → 0.325，星爆 8px → 0.1，都对得上。原版那几件抛掷物（头颅 64×61、手臂 26×50）是**独立的一整块精灵**，所以按原值画出来比僵尸身上那颗头大 2.5 倍；`pvzce:zombie_head` 与 `pvzce:zombie_arm` 因此被调到 0.4 / 0.33（约等于模型上那颗头的宽度），既能看清是"一颗头"，也不会盖住半块草坪。
- **曲线表**：`alpha_curve` / `scale_curve` 是 `[[时间, 值], ...]`，时间已归一化到 0..1。直线淡出由 `alpha_from`/`alpha_to` 两个端点表达，只有真正弯曲的（先胀后消的烟、脉冲的光）才带表 —— 这也是转换器 `tools/particles_to_pvzce.py` 的判断依据。
- **单位**：距离是世界格、时间是秒。转换器按 60fps、80 像素/格换算原版的「每帧像素」（330 px/frame 的抛射速度 → 247 格/秒），文件头记录了全部换算因子。
- **贴图来源有三处**：`refer/im7/particles`（粒子贴图）、`refer/anim`（emitter 引用的 reanim 部件，如僵尸帽子）、`refer/im7/images`（零散图，如泥土、水花）。转换器按名字归一化（忽略大小写与下划线）在三处查找，并把结果拷成小写文件名 —— `Identifier` 的 path 只允许小写，而原版文件名是驼峰。
- **精灵表切分**：原版用 `<ImageFrames>`/`<ImageRow>`/`<ImageCol>` 把一格里横排的多帧画在一张 PNG 上，本渲染器一帧一张贴图，所以转换器在生成时把它切开（8 帧 × 2 行的 `dirtsmall` 就是这样变成 `dirtsmall_1..8` 的）。

## 7. 扩展点（mod 怎么做）

| 想加什么 | 做法 |
|---|---|
| 新植物/僵尸/子弹 | 放 `data/<你的ns>/{plants,zombies,projectiles}/*.json`，用已有 capability 组合即可，**不需要写代码**。三线射手的三行齐射、分裂豌豆的向后射都只是 `ProjectileRef` 的字段（`row_offset`/`backward`/`rows`），不是新能力。原版僵尸的"帽子"（路障/铁桶/铁门/旗帜）是 `Zombie.reanim` 主文件里按图片筛选出来的，见 `tools/reanim_to_pvzce_all.py` 的 `ZOMBIE_*_EXCLUDE` |

## 8. 约定（避免重新长出重复实现）

改相关逻辑时请顺着这条改，不要新开一份：

1. 颜色/音效/队伍/规则的 id → `PvzceSounds` / `PvzceIds`。
2. 数值常量（tick 率、默认棋盘、初始阳光、卡片冷却…）→ `PvzceConstants`；每秒↔每 tick 换算是 `PvzceConstants.TICKS_PER_SECOND`，不要写 `60`。
3. 关卡访问 → `LevelAccess`（不要新开接口）。
4. 植物创建 → `LevelServer.spawnPlant`（不要 `new PlantEntity`）。
5. 卡槽解析 → `SlotResolver`。
6. 内容 id → 纹素/纹理 → `EntityTextures`；实体视觉常量 → `EntityVisuals`。
7. GUI 裁剪 → `Clipping`；GUI 焦点 → `FocusManager`；卡片绘制 → `SeedCardRenderer`；文本/数字 → `GuiText`。
8. 时间线数学 → `Timeline`；日夜 → `DayNightCycle`；缓动/插值 → `MathUtil`（`easeInOut` 只有这一份）。
9. 包字段声明 → `PacketStruct`；集合序列化 → `PacketByteBuf` helper。
10. 路径拼接 → `PackPaths`；注册表目录表 → `CONTENT_REGISTRIES`；注册表分类 → `PvzceRegistries.byCategory()`；**关卡存档目录键 → `LevelKey.of`**（客户端镜像在 `LevelMove.saveKeyAfterMove`，两处必须同步改）。
11. 实体存档 → `saveState/restoreState`（成对实现，不要只写一半）。
12. 关卡数据校验 → `LevelValidator`（新增检查项加在这里，不要散落到构造函数里抛异常）。
13. 编辑器列表操作 → `ListEditorSupport`；背景 cover 适配 → `Screen.coverFit`；命令分类/补全 → `PvzceRegistries.byCategory()`（不要新写 switch）。
13b. 界面自己的鼠标/滚轮判定 → `Screen.onMouseClicked` / `onMouseMoved` / `onMouseScrolled`（**不要**覆写 `mouseClicked`，它是 `final`，模态分发靠它保证）。
14. 场景元素是否液体 → `LiquidTextures.liquidFor`（**读元素定义的 `liquid` 字段**，不要按贴图是否存在判断）；液体参数 → `LiquidDef`；水面绘制 → `LiquidTextures.renderWorld` / `renderGuiBoard`（游戏内与选卡预览共用同一实现，只有一个投影参数不同）。
15. 能不能种 → `PlantPlacement.canPlace`（**纯函数，只读 `#c:` 标签与 `PlacementDef`**）。不要在别处再写一份判定：`LevelServer.canPlacePlant` 只是把关卡适配成 `PlantPlacement.Ctx`，`PlantAIPlayer` 也调它。瓦片能种什么**不写进场景元素定义**，要加地形就在 `data/c/tags/scene_element/` 里打标签。
16. 堆叠层与互斥 → `PlacementDef` 的 `layer`/`count`/`group`（载体 `layer 0`、地面植物 `1`、植物上的植物 `2`；`group` 留空＝同格可多个）。判定只看**比自己层低**的东西，所以种植顺序不影响结果。
17. 关卡属于哪一页 → `LevelGrouping`（**纯函数，只读 id 路径**）。不要在别处再写一份：服务端 `PvzceServer.groupOf`、客户端 `LevelPage`、编辑器的换组都调它；页签顺序与名单由服务端 `LevelTabs` 从注册表推出发给客户端。
18. 卡是否被背包锁住 → `SlotResolver.requiresUnlock`（服务端 `PlayerProfile.owns` 与客户端 `ClientProfile.owns` 都调它）；选卡池 → `SeedOptions.cardPool`（**唯一一份**，"客户端看得到"与"服务端收得下"靠它对齐）。关卡固定卡**永远不过滤**。
19. 玩家档案（金币 / 已解锁卡）→ `PlayerProfile` + `PvzceServer.profileFor/saveProfile`（缓存按世界名，换世界前先 `flushProfile()`）。不要在别处再读一次 `profile.dat`，也不要在关停钩子里写文件。
20. 通关发什么 → 关卡 `rewards` 块 + `PvzceServer.awardProfile`（首通/重复/掉币的**唯一**结算点）；新增奖励类型要同时改 `LevelRewards` 与 `LevelValidator.validateRewards`。金币掉落只经 `LevelAccess.zombieDied`，实体不读关卡奖励数据。
21. 内容 id → 用哪份美术 → `EntityArt`（动画文件与兜底贴图两个问题一次查表）。不要在渲染器/编辑器/选卡里各拼一次路径：内置美术按类目分层后，路径已经不能从 id 推出来。
22. 命中反馈/特效的粒子 id → `PvzceParticles`（与 `PvzceSounds` 同形）。未定义的效果**不画东西**，只按 id 报一次日志。
22b. 缺失贴图 → `EntityArt.MISSING_TEXTURE`（渲染器、`EntityArt.sprite(null)` 与 `TextureManager` 的采样方式都读它）。不要在绘制处自己造一块纯色占位。
22c. 总卡槽数 → `LevelDef.effectiveMaxSeedSlots(profileSlots)`（关卡声明优先，未声明用背包的 `PlayerProfile.seedSlots`）。判断"关卡有没有自己声明"用 `declaresMaxSeedSlots()`，不要拿 `maxSeedSlots` 和某个数字比 —— 未声明是 `UNSET_MAX_SEED_SLOTS`（-1），不是 6。
24. 「这一格能不能放」的规则只有 `PlantPlacement` 一份；工具点击可否执行由 `LevelServer.applyToolEffect` 返回布尔值表示，**被拒绝的点击不消耗使用次数也不进冷却**。移动植物走 `spawnPlant` + `restoreStateWithoutPosition`：位置由新格子决定，状态（血量、年龄、能力）跟着走 —— 直接 `restoreState` 会把坐标一起写回去，等于没搬。
25. 关卡能不能进 → `LevelUnlocks.evaluate`（**纯函数**，`Context` 里只有已通关/已购买/背包/金币/沙盒）。服务端求值、客户端收结论（`UnlockInfo`），不要在界面里判断；入口门槛在 `PvzceServer.createLevel` 重新求值一次，不要只信列表。购买价只从关卡定义读，永远不信客户端。
26. 实体归类 → 美术目录（`textures/entities/<类目>/…`）与动画目录（`animation_dir`）用**同一套类目**，分类表只有一份：`tools/group_entity_assets.py` 的 `ENTITIES`，以及重新生成美术时 `tools/reanim_to_pvzce_all.py` 的 `EntityConfig.group`。**内容 id 永远不带类目** —— 改目录不会让关卡、标签、存档或语言 key 失效。
27. 实体类别 → `EntityKind` 的四个常量，**它们是类别不是内容 id**：判断「这是不是某个具体资源/植物」一律比内容 id（`defIdString()` / `PvzceIds`），不要比 kind（见 §6.3 的世界点光源）。
28. 捡起一个资源放什么效果 → `ResourceDef.pickup_effect`（可缺省＝不放）。不要在收集代码里按资源分类写分支：阳光与硬币不是同一种拾取，共用一份粒子参数必然有一边是错的。
29. 传送带的产出/容量/消耗/存档 → `ConveyorBelt`（服务端唯一实现）；卡槽条是它的**投影**（`rebuildBeltSlots`），不要在别处再维护一份"带上有哪些卡"。
30. "这一格能不能种"的第二半（**关卡允许的范围**）→ 关卡 `placement_zone` + `LevelServer.canPlacePlant`。不要写进地形标签：红线是画在普通草地上的，改地形会把草坪一起改掉。客户端画线/悬停从 `LevelPayload` 的同一条矩形读。
31. 爆炸的范围与触发 → `ExplosiveCapability.detonate` 的**不变量「爆炸半径 ≥ 触发范围」**。新写 proximity 内容时 `trigger_range > radius` 也不会静默打不中（`ExplosiveCapability` 会取大），但数据仍应写成想要的值。
31b. 爆炸之后植物还要在场上留多久 → `ExplosiveCapability.LINGER_TICKS`（30 tick）。爆炸是**瞬时**的（伤害当 tick 结算），留下的是那一幅画：植物随即 `occupiesCell` 为假（僵尸走过去、铲子够不着），计数归零自己 `remove()`。**不要**在关卡里另开一份「爆炸植物延迟移除」名单，也不要在客户端补一段「等动画播完再删」。
32. 植物是否占格（僵尸能否啃、工具能否取）→ `PlantCapability.occupiesCell` + `LevelServer.plantAt`。不要在僵尸的啃咬循环或工具里判断具体植物 id。
32b. **一次命中吃不吃护甲** → 注册的 `DamageTypeDef`（`pvzce:ash` / `pvzce:projectile` / `pvzce:impact` / `pvzce:splash` / `pvzce:mower`）。所有伤害都从 `ZombieEntity.damage(amount, type, level)` 走，不要在能力里另开一条「直接扣血」的路；要新的护甲规则就给类型加字段，不要在第 4 个方法里再写一遍。
32c. **植物能不能被打死** → `PlantCapability.invulnerable` + `PlantEntity.damageFrom`。「咬不动」与「铲不掉」是两件事：前者问 `invulnerable`，后者问 `occupiesCell`（灰烬类在引信期间只回答前者）。
33. 这一行有没有小推车、它在哪 → `MowerMechanic` 的 `Rig`（服务端唯一实现，状态经 `LevelServer.mechanicState` 存在关卡上，客户端镜像在 `ClientLevel.mechanicState`）。**不要另开一份"哪行有推车"的判断**：默认值（每行一辆）只由 `LevelMechanics.effective` 加，行列表只由 `MowerData.rowsFor` 展开。
34. 一条不绑定实体的动画（机制道具、以后可能的 UI 表演）→ `ArtTarget` + `AnimationManager`。它的 `fileFor` 认得这种目标并直接读文件 id；不要在机制里另写一个渲染器。
35. 僵尸身上会磨损的装备 → `EquipmentDef`（`art` 骨骼族 + 可选 `piece` 护甲 + `drop_particle`）。档位判定与"这帧该画哪一张"只有 `EquipmentArt` 一份（`BoneArt` 钩子）；**不要把状态编译成动画 clip**（三个档位 × 六个 clip × 800KB），也不要再加第二个"挨打时掉什么"的分支：伤害吸收只经 `ArmorCapability.absorb`，掉落粒子从定义里取。
36. "这一关有没有得选卡" → `SeedOptions.hasNothingToChoose(pool, maxSlots, lockedIds)`（**纯函数**）。选卡屏的预览模式与存档提示框的重开都问它；判据是**总卡槽数 − 关卡固定卡数**，不是"已选卡数"。
37. 屏幕上那句提示 → `HintBox`（唯一实现）+ `LevelHints`（唯一触发点）。不要在界面里另写一个"显示一行字两秒"的东西：拒绝优先、一条一条来、墙钟计时都在里面。
38. 僵尸画哪些骨骼 → `EquipmentArt.visibleBones`（唯一实现）。装备的档位、断臂、`hidden_bones`、装备自带手臂与普通手臂的互斥，全部在这一个函数里决定；**不要**在渲染器或 clip 里加特例。
39. 粒子落地后的水平行为 → `ParticleMotion.ground_friction`（缺省 1 = 保留"一直滑"的手感）。要"原地停下"就在**数据**里调小，不要改引擎。
40. 小推车的"还在 / 没了" → `MowerMechanic.Rig`（服务端）+ `ClientMechanics.consumeParkedMowers`（客户端核销）。不要在界面里再维护一份"哪些车已经变成金币了"。
41. 实体画在哪个坐标 → `ClientEntity.visualCellX/Y/Height`（**渲染用**；`cellX()` 永远是服务端的数）。不要在渲染器里自己补间，也不要把补间写回 `cellX()`：那会让命中测试和存档读到没有权威性的中间值。
42. 一个状态要持续多久 → **服务端计数器**（`hitTicks`、`biteCooldown`、`corpseTicks`），不是"客户端自己播完再说"。服务端不知道 clip 有多长，也不该知道；它只知道"这个状态现在成立"，而客户端用一个带 transition 的 clip 把它演出来。
43. 植物睡不睡 → `PlantCapability.asleep`（由 `LevelAccess.isNight()` 与咖啡豆的唤醒标志推出）+ `PlantEntity.tick` 的跳过规则。**不要在能力里各自判断白天黑夜**：睡着时"什么都不做"是实体统一跳过的，新能力默认就被覆盖；`pvzce:nocturnal` 只负责发布 `sleep` 动画与永久唤醒。
44. 一发子弹能飞多远 → `ProjectileRef.range`（0 = 不限），**同一个数**既是"值不值得开火"（`ProjectileRef.covers`）也是"子弹何时消失"（`ProjectileEntity` 从出膛点量起）。不要把射程写进子弹定义：同一个孢子可以被不同射程的植物发射。
45. 关卡列表的顺序 → `LevelGrouping.compareIds`（自然序：数字段按数值比）。服务端下发列表与页签推导都调它，**不要**再写一份 `String.compareTo`——`1_10` 会跑到 `1_2` 前面。
46. 开局两波多久出一只 → `WaveDef.holdUntilDead(waveIndex)`（**唯一**的规则出处）+ `LevelServer` 的两处门（波内 `PendingWaveSpawn`、波间 `openingWaveStillOnTheField`）。**不要**靠调大 `spawn_interval` 来"放慢前期"：那是在替玩家猜速度，而门控问的是玩家自己。
47. 一张卡冷却多久 → 卡自己的数（`Slot.cooldownTicks`，建条时从 `SlotResolver` 抄）× 关卡规则 `pvzce:seed_cooldown_multiplier`，换算只有一处：`LevelServer.effectiveCooldownTicks` / `CardCooldown.effective`。**消耗时才算**（种植物与用工具两条路都调它），`SlotInfo.cooldownTotal` 把同一个数发给客户端当充能条的分母 —— 不要在某一处直接 `startCooldown(卡自己的数)`，也不要在客户端拿本地的规则再推一遍。
48. 列表行上那枚奖杯 → 类别定义的 `trophy` + `LevelInfo.cleared`（**通关过至少一次**），判定只在 `LevelSelectScreen.showsTrophy`。**不要读 `status` 字符串**：有存档时它写的是"进行中"，而奖杯不该被一局重玩收回去。
49b. **空手点击做什么** → 关卡 `mechanics` 里的 `pvzce:tool`（`default: true`），读法只有 `ToolMechanic.defaultTool/declared`。不要在界面里按关卡 id 判断"这一关是打地鼠"。
49c. **谁在玩这一关** → `LevelDef.playableTeamDefs()` / `offersTeamChoice()`（服务端求值，客户端读 `TeamInfo.playable`）。不要在界面里写"僵尸方没有卡组所以不可选"。
49d. **爆炸打多大一片** → `pvzce:explosive` 的 `radius` + `square`（格）或 `trigger: "row"`（整行），落到 `LevelAccess.damageArea(..., square)` / `damageRow`。不要用一个大到能覆盖整行的方格来假装"整行"。
49f. **这一下打谁** → `LevelAccess.enemiesInRow(row, team)` / `LevelServer.isEnemyOf`（"不是同一队"），`zombiesInRow` 只用于"这一行有几只"。不要在攻击代码里判断某个实体是不是被魅惑的：阵营本身就是答案。
49g. **被消耗的植物怎么退场** → `PlantCapability.vanishAnimation()`（clip + tick）。它让玩法结束与画面结束分开，但只有这一处：`isRemoved()` 一为真就不再占格、不再被瞄准，剩下的只是 `PlantEntity.vanishing()` 在倒数。不要在关卡里另开一份"等动画播完再删"的名单。
49e. **这一下算不算"烧"** → 伤害类型的 `burns`（`DamageTypeDef`），到 `ZombieEntity.damageBody(amount, level, burns)` 与 `EntityAnimations.DEATH_BURNED`。不要在死亡代码里排一张"哪些伤害 id 会烧"的名单。
49. 关卡发的"东西"而不是"钱" → `rewards` 的 `resource` 条目（面值来自资源定义的 `default_value`）+ `LevelRewardS2C.rewardItem`，客户端三处（草坪掉落、领取动画、结算页相框）都从包里那一个字段决定画什么。不要在客户端按关卡 id 判断"这一关发钻石"。

## 9. 已知缺口与预留接口

按规划文档仍待补齐（**不是**本轮重构遗留）：

- **联机**：`TcpPacketTransport` 已修好语义但未接线；缺握手、`server.properties`、玩家身份/Team 占位、断线重连与 delta 重放。
- **夜行植物与"永远夜晚"**：`pvzce:nocturnal` 的睡觉规则从 2-1 起有了真正的用例，`DayNightCycle.alwaysNight`（`day_length: 0` + `night_length > 0`）也已经能表达"整关都是夜晚"，墓碑的清除从 2-3 起由墓碑破坏者（`#c:grave_only` 标签 + `pvzce:grave_buster` 能力）承担。仍然缺的是**其余夜关的植物**（寒冰菇、催眠菇、惊吓菇……）与**焦尸美术的细分**：`Zombie_charred_*`（巨人 / 矿工 / 小鬼各有自己的焦尸）还没转，今天所有僵尸都用同一具通用焦尸。
- **注册表同步**：客户端目前依赖本地资源/数据包自行解析注册表；联机时应改为服务端按注册表下发定义（`PvzceDataLoader.RegistryData` 预留了"哪个注册表需要同步"的位置，但目前只有目录名与 codec 两个字段）。
- **客户端资源同步**：客户端自己解析资源/数据包（`PvzceClient.run` 里另建了一个 `PvzceResourceManager`），联机时应改为服务端下发。
- **渲染**：`RenderSystem` 无矩阵栈、无批合并；每个 quad 都会创建/销毁 VAO+VBO（`FontRenderer` 每个字形一次）；深度测试关闭，层级完全依赖提交顺序与 z 常量。
- **动画**：`AnimationHandle` 的返回值在调用点被丢弃；骨骼混合/Spine 未接入。
- **GUI**：`Dialog` 的内容区未扣除九宫格边框高度（`NinePatch.DIALOG_TOP/BOTTOM`），因此大对话框的按钮会跨到边框上。`MusicEditorDialog` 与 `LevelSaveDialog` 仍受这条影响。
- **关卡分类**：未分类页是**固定页**（`LevelPage.tabs` 永远补上它，客户端左侧列因此永远有"未分类"按钮）——服务端只下发有内容的页，空页由客户端补齐；`LevelValidator` 尚未校验"关卡 id 的两段像主题/类别但未注册"（目前只有 `PvzceServer.validateLevelGroups` 在重载时记日志）。
- **编辑器**：画布只支持地形/预设实体；`EditorScreen` 与 `WaveEditorScreen` 都还靠 `palette.selected()` 每帧回读选中项（列表没有选中变化事件）。关卡只写进 `datapacks/user_levels`，没有"另存为"（改名要新建一关）。**编辑器不认识 `conveyor` 与 `placement_zone`**：它只覆盖自己拥有的字段（`buildLevelJson` 从载入的 JSON 出发），所以手写的这两块不会被保存动作删掉，但也没有 UI 去编辑它们——小游戏关卡目前是手写数据。
- **AI**：只有植物方的基础策略，没有规划器/难度档位；僵尸方无出怪策略器（`WaveGenerator` 未实现）。
- **金币没有消费去处**：钱包、掉币、通关结算、结算页都做了，但**还没有商店**（Crazy Dave 的商店/图鉴都没做）。金币目前只是进度展示，这是有意的阶段性取舍。
- **僵尸方没有背包**：`PlayerProfile` 只记录植物/工具；"僵尸也一张张解锁"要等僵尸方能被玩家操作（对战模式）时才有意义。
- **背包只有一页**：`InventoryScreen` 是只读网格，没有图鉴详情、没有排序/筛选；卡片顺序就是注册表顺序。
- **奖项页自己的排版仍偏矮**：`AwardScreen` 的相框与羊皮纸是照 4:3 底图坐标写死的，宽屏下
  `coverFit` 会把顶部木牌裁掉、下方文字挤在一起（"金币 +100 / 金币总数"两行会叠到羊皮纸外）。
  与提示框、白光无关，是这一页自己的缩放问题，尚未处理。
- **编辑器只编辑一个首通解锁**：`rewards.first_clear` 手写多条时，编辑器只认第一条 `unlock` 并在保存时把**多余的 unlock** 规范化掉（会打一行日志）。它没有 UI 的条目（今天的 `resource`）会**原样读写回去**，不会被保存动作删掉 —— 判定在 `InfoPage.readRewardLists`（纯函数，`InfoPageRewardsTest` 钉住）。
- **水面**：深度是**每格**量化（8 连通步数，6 bit 里占 3 bit），所以 5 行关卡的深浅只有两三档、交界是矩形台阶；要根治需在 `LiquidGeometry` 里把深度场双线性上采样成逐像素值。编辑器画布（`EditorScreen.renderCanvasBlock`）仍是自己画，未走 `LiquidTextures`，所以编辑器里的水与游戏内不一致。`tools/preview_water.py` 是 shader 的 CPU 镜像，靠人工同步常量 —— 已有测试保证 shader 可编译与 uniform 齐全，但**参数**仍需人工保持一致。
- **音乐状态不随存档回放**：客户端只按"进入关卡"播默认曲（`startLevel` 的 default）并接收之后的 cue；服务端恢复存档时 `NextMusicCueIndex` 已越过的那条 cue（例如波次处切战斗轨）不会补发，所以续一局打到一半的关卡会先听到默认曲。要根治得让服务端按轨道记录"当前曲目"并在 `sendFullState` 里重发（重发同曲在客户端是幂等的，正是 `startLevel` 的同曲不重启要保护的语义）。
- **种植反馈**：悬停预览已经做了（植物 id 的 idle 动画幽灵 + 放置区绿/红，见 §6.2），但"**能不能种**"仍然只有服务端知道：客户端画的是"如果种下去长这样"，不是"这里能种"。要补全得把 `PlantPlacement` 的 `Ctx` 从"传 `PlantDef` 对象"改成"传 id 自取注册表"，因为 `ClientEntity` 只拿得到 defId。
- **小推车只有草坪那一种**：原版还有水里的 `PoolCleaner`（`refer/anim/PoolCleaner.reanim` 已经在仓库里）与屋顶的 `RoofCleaner`；数据侧 `MowerData` 只描述"哪些行有车"，没有"哪种车"。要做成内容的话，下一步是把车型做成一个字段或一个内容 id，而不是给 `MowerMechanic` 加 if。
- **装备档位只对"一件护甲"精确**：`EntitySpawnS2C.armor` 是**总剩余护甲**，客户端拿它除以定义里所有护甲条目的耐久之和。今天每个僵尸都只有一件（路障/铁桶/铁门/报纸），所以这条除法就是那一件的比例；一件以上的僵尸两条目会一起按平均值磨损——要做对得让线上带每件各自的剩余值（变长列表），或者把"最前面那件的比例"单独发一位。
- **编辑器画布不显示装备档位**：画布上的僵尸是满血预览实体，`armor` 取 `NO_ARMOR`，`EquipmentArt` 把它当成"没磨损"画完整的那一张。想在编辑器里摆"破了的路障"需要一个新的预览状态，不在本轮范围内。
- **粒子单位只覆盖"抛掷物"那一族**：`tools/particles_to_pvzce.py` 的 `PROP_SPEED_DIVISOR` 只作用于原版用 `GroundConstraint` 标出的抛掷物（头/手臂/帽子/旗帜等 20 条定义，见 §5.2）。剩下 122 条仍按"像素/帧"换算，所以它们的速度比原版小 60 倍、自旋大 60 倍——对一团"冒出来就淡掉"的烟来说看不出来，但**碎片类**（`VaseShatter`、`ZamboniExplosion` 的零件、`BossExplosion` 的碎块、`WallnutEat*`、`CatapultExplosion`）本该四散飞开，现在是原地淡出。它们和抛掷物在结构上是同一族（有 `Acceleration`、没有 `Friction`，共 33 条），把 `to_definition` 里的判据从 `thrown` 放宽到"没有 Friction 的弹道发射器"即可一次修好；没有一起改是因为那会同时改变每一处爆炸与溅射的手感，需要单独过一遍截图。
- **测试**：`@PvzceGametest` 注册式集成测试与渲染冒烟（离屏 FBO + 图 diff）**未建**，所以界面没有自动化验证 —— 这批工具是第三阶段的规划（见 `03-第三阶段-精修完善.md` §3.6.1）。现状是 JUnit 单测/集成测试：`./gradlew :pvzce-game:test`（约 20s，`:pvzce-api:test` 另有 2 例）。
  - 服务端/客户端流程可以直接起真的 `PvzceServer`/`PvzceClient` + `Connection.createMemoryPair()` 来测：`testutil/ServerHarness` 与 `testutil/ClientHarness` 是这两个 harness 的唯一实现（此前有 5 份各写各的副本）。
  - **一轮改动验到什么程度见 `验证约定.md`**（按需，不是每轮全量 + 截图）；`pvzce.smoke*` 的完整参数表见 `冒烟与截图指南.md`，这里不再重复维护一份。
  - 曾经的偶发失败（未播种的 `LevelServer.random` 撞上"取第一个掉落物"、保存/恢复的时序假设）已经改成确定性断言，不再有"单独跑必过"的用例。
