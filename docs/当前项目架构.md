## 1. 一句话架构

PVZCE 是一个**独立运行的桌面游戏**，用 Fabric Loader（fork 后内嵌）加载第三方模组，本体分为"平台层 → 框架层 → 内容层 → 表现层"，服务端 60tps 权威模拟、客户端镜像表现，二者通过**包交换**通信（单机也是内存包队列，不是直接方法调用）。

```
┌──────────────────────────────────────────────────────────────┐
│ L4 入口      launcher/PvzceGame → KnotClient（loader fork）   │
├──────────────────────────────────────────────────────────────┤
│ L3 表现      client/{gui, renderer, animation, sound, particle}
│              服务端状态只读镜像，不参与判定                     │
├──────────────────────────────────────────────────────────────┤
│ L2 内容      api/content（Def record + Codec）                │
│              common/capability（可组合能力实现）               │
│              server/{entity, level, ai, command, gamerule}    │
├──────────────────────────────────────────────────────────────┤
│ L1 框架      api/registry · api/tag · common/nbt · Identifier  │
│              common/resource（资源/数据包）                    │
│              common/network（包 + 传输）· common/level（共享态）│
├──────────────────────────────────────────────────────────────┤
│ L0 平台      net.fabricmc.loader（fork）· LWJGL · DFU · Gson   │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向**：L2 依赖 L1 与 `com.pvzce.api`；L3 只读 L1/L2 的注册表与状态。
分层靠**包约定**维持，没有编译期约束（`api`/`common`/`server`/`client` 在同一个 source set 里），
所以"哪些反向引用是有意的"必须写清楚 —— 今天有**三类**，其余方向都是 0 处：

| 例外 | 处数 | 为什么 |
|---|---|---|
| `common.capability/**` → `server.entity.{Plant,Zombie,Projectile}Entity` | 30 | 能力就是服务端行为，它的钩子必须拿到实体本身（详见 §5.4） |
| `common.level.mechanic/**` → `server.level.LevelServer`（+ `cardsource.CardSource`） | 9 | 机制是关卡级行为，需要 `mechanicState` 与小推车/墓碑这类**关卡**操作，这些不在 `LevelAccess` 上 |
| `api.content/**`、`api.entity/**` → `common.*`（21 处）与 `server.entity`/`server.Team`（7 处） | 28 | 定义里带着**行为预设表**（`PlantBehaviorPresets` 等）与能力接口，它们必须指名实现类；`api.entity.LevelAccess` 的返回类型是 `PlantEntity`/`Team`，那是服务端实体在内容层的唯一入口 |

这三类都是**双向耦合**的一半：`common.capability` 与 `api.content` 互相引用（预设表 ↔ 能力接口）。
真要拆干净得把能力接口搬进 `pvzce-api` 模块、把预设表搬出定义包，是一次独立重构，不是顺手能清的；
在那之前它们由 `LayerDependencyTest` **按文件名白名单**钉住，第三类不会再多一处。

`common` → `client`、`server` → `client`、`client` → `server` 都是 **0 处**；纯数据类型的跨层引用已被清掉
（`Slot` 在 `common.core`，存档键规则在 `common.util.LevelKey`，两边共用一份）。这三条零容忍的规则和
上面三类例外一起写成 `LayerDependencyTest`，加一处反向 import 就会红 —— 文档里的表格因此不再只是表格。

## 9. 已知缺口与预留接口

按规划文档仍待补齐（**不是**本轮重构遗留）：

- **联机**：TCP 未接线（骨架已删，见 §3.5）；缺握手、`server.properties`、玩家身份/Team 占位、断线重连与 delta 重放。协议层不受影响：`PacketTransport` 是接口，换一个实现即可。
- **夜行植物与"永远夜晚"**：`pvzce:nocturnal` 的睡觉规则从 2-1 起有了真正的用例，`DayNightCycle.alwaysNight`（`day_length: 0` + `night_length > 0`）也已经能表达"整关都是夜晚"，墓碑的清除从 2-3 起由墓碑破坏者（`#c:grave_only` 标签 + `pvzce:grave_buster` 能力）承担。仍然缺的是**其余夜关的植物**（寒冰菇、催眠菇、惊吓菇……）与**焦尸美术的细分**：`Zombie_charred_*`（巨人 / 矿工 / 小鬼各有自己的焦尸）还没转，今天所有僵尸都用同一具通用焦尸。
- **注册表同步**：客户端目前依赖本地资源/数据包自行解析注册表；联机时应改为服务端按注册表下发定义（`PvzceDataLoader.RegistryData` 预留了"哪个注册表需要同步"的位置，但目前只有目录名与 codec 两个字段）。
- **客户端资源同步**：客户端自己解析资源/数据包（`PvzceClient.run` 里另建了一个 `PvzceResourceManager`），联机时应改为服务端下发。
- **渲染**：`RenderSystem` 无矩阵栈、无批合并；每个 quad 都会创建/销毁 VAO+VBO（`FontRenderer` 每个字形一次）；深度测试关闭，层级完全依赖提交顺序与 z 常量。
- **动画**：`AnimationHandle` 的返回值在调用点被丢弃；骨骼混合/Spine 未接入。
- **GUI**：`Dialog` 的内容区未扣除九宫格边框高度（`NinePatch.DIALOG_TOP/BOTTOM`），因此大对话框的按钮会跨到边框上。`LevelSaveDialog` 仍受这条影响（曾经举的第二个例子 `MusicEditorDialog` 已不存在：编辑器各页现在住在 `EditorScreen` 里，不再是自己弹的对话框）。
- **关卡分类**：未分类页是**固定页**（`LevelPage.tabs` 永远补上它，客户端左侧列因此永远有"未分类"按钮）——服务端只下发有内容的页，空页由客户端补齐；`LevelValidator` 尚未校验"关卡 id 的两段像主题/类别但未注册"（目前只有 `PvzceServer.validateLevelGroups` 在重载时记日志）。
- **编辑器**：画布只支持地形/预设实体；`CanvasPage` 每帧用 `palette.selected()` 回读选中项（列表有行点击回调 `setOnRowClick`，但没有"选中变了"的事件，所以只能回读）。关卡只写进 `datapacks/user_levels`，没有"另存为"（改名要新建一关）。**编辑器不认识 `conveyor` 与 `placement_zone`**：它只覆盖自己拥有的字段（`buildLevelJson` 从载入的 JSON 出发），所以手写的这两块不会被保存动作删掉，但也没有 UI 去编辑它们——小游戏关卡目前是手写数据。
- **AI**：只有植物方的基础策略，没有规划器/难度档位；僵尸方无出怪策略器（`WaveGenerator` 未实现）。
- **金币没有消费去处**：钱包、掉币、通关结算、结算页都做了，但**还没有商店**（Crazy Dave 的商店/图鉴都没做）。金币目前只是进度展示，这是有意的阶段性取舍。
- **僵尸方没有背包**：`PlayerProfile` 只记录植物/工具；"僵尸也一张张解锁"要等僵尸方能被玩家操作（对战模式）时才有意义。
- **背包只有一页**：`InventoryScreen` 是只读网格，没有图鉴详情、没有排序/筛选；卡片顺序就是注册表顺序。
- **奖项页自己的排版仍偏矮**：`AwardScreen` 的相框与羊皮纸是照 4:3 底图坐标写死的，宽屏下
  `coverFit` 会把顶部木牌裁掉、下方文字挤在一起（"金币 +100 / 金币总数"两行会叠到羊皮纸外）。
  与提示框、白光无关，是这一页自己的缩放问题，尚未处理。
- **编辑器只编辑一个首通解锁**：`rewards.first_clear` 手写多条时，编辑器只认第一条 `unlock` 并在保存时把**多余的 unlock** 规范化掉（会打一行日志）。它没有 UI 的条目（今天的 `resource`）会**原样读写回去**，不会被保存动作删掉 —— 判定在 `InfoPage.readRewardLists`（纯函数，`InfoPageRewardsTest` 钉住）。
- **水面**：深度是**每格**量化（8 连通步数，6 bit 里占 3 bit），所以 5 行关卡的深浅只有两三档、交界是矩形台阶；要根治需在 `LiquidGeometry` 里把深度场双线性上采样成逐像素值。编辑器画布走的**就是**同一趟液体渲染（`CanvasPage.renderBoard` → `SceneTileRenderer` → `LiquidTextures`，只是把投影换成 `beginOverlayWorldView`），所以"编辑器里的水与游戏内不一致"已经不是问题 —— 曾有一版编辑器自己逐格画，那段代码连同这句话一起删了。`tools/preview_water.py` 是 shader 的 CPU 镜像，靠人工同步常量 —— 已有测试保证 shader 可编译与 uniform 齐全，但**参数**仍需人工保持一致。
- **音乐状态不随存档回放**：客户端只按"进入关卡"播默认曲（`startLevel` 的 default）并接收之后的 cue；服务端恢复存档时 `NextMusicCueIndex` 已越过的那条 cue（例如波次处切战斗轨）不会补发，所以续一局打到一半的关卡会先听到默认曲。要根治得让服务端按轨道记录"当前曲目"并在 `sendFullState` 里重发（重发同曲在客户端是幂等的，正是 `startLevel` 的同曲不重启要保护的语义）。
- **种植反馈**：悬停预览已经做了（植物 id 的 idle 动画幽灵 + 放置区绿/红，见 §6.2），但"**能不能种**"仍然只有服务端知道：客户端画的是"如果种下去长这样"，不是"这里能种"。要补全得把 `PlantPlacement` 的 `Ctx` 从"传 `PlantDef` 对象"改成"传 id 自取注册表"，因为 `ClientEntity` 只拿得到 defId。
- **编辑器画布不画关卡背景**：关卡可以指定 `background`，游戏与选卡预览都按它画，但画布仍然是"地形画在一块空底上"——作者选完背景图看不见它，也看不见 `hidden_scene_elements` 的效果（画布故意不隐藏，否则作者看不见自己画了什么）。要补齐得让画布按 `LevelStage.cover` 的那套投影把 1400x600 的舞台画进它自己的小视口。
- **弹坑只有草坪那一版**：原版还有屋顶（`crater_roof_left/center`）与水面（`crater_water_day/night`）的弹坑美术，都在 `refer/im7/images` 里，但 `LevelServer.isBareGround` 只把草坪与裸地变成弹坑 —— 屋顶与水面需要各自的贴图与尺寸，是一件内容活。
- **小推车只有草坪那一种**：原版还有水里的 `PoolCleaner`（`refer/anim/PoolCleaner.reanim` 已经在仓库里）与屋顶的 `RoofCleaner`；数据侧 `MowerData` 只描述"哪些行有车"，没有"哪种车"。要做成内容的话，下一步是把车型做成一个字段或一个内容 id，而不是给 `MowerMechanic` 加 if。
- **装备档位只对"一件护甲"精确**：`EntitySpawnS2C.armor` 是**总剩余护甲**，客户端拿它除以定义里所有护甲条目的耐久之和。今天每个僵尸都只有一件（路障/铁桶/铁门/报纸），所以这条除法就是那一件的比例；一件以上的僵尸两条目会一起按平均值磨损——要做对得让线上带每件各自的剩余值（变长列表），或者把"最前面那件的比例"单独发一位。
- **编辑器画布不显示装备档位**：画布上的僵尸是满血预览实体，`armor` 取 `NO_ARMOR`，`EquipmentArt` 把它当成"没磨损"画完整的那一张。想在编辑器里摆"破了的路障"需要一个新的预览状态，不在本轮范围内。
- **粒子单位只覆盖"抛掷物"那一族**：`tools/particles_to_pvzce.py` 的 `PROP_SPEED_DIVISOR` 只作用于原版用 `GroundConstraint` 标出的抛掷物（头/手臂/帽子/旗帜等 20 条定义，见 §5.2）。剩下 122 条仍按"像素/帧"换算，所以它们的速度比原版小 60 倍、自旋大 60 倍——对一团"冒出来就淡掉"的烟来说看不出来，但**碎片类**（`VaseShatter`、`ZamboniExplosion` 的零件、`BossExplosion` 的碎块、`WallnutEat*`、`CatapultExplosion`）本该四散飞开，现在是原地淡出。它们和抛掷物在结构上是同一族（有 `Acceleration`、没有 `Friction`，共 33 条），把 `to_definition` 里的判据从 `thrown` 放宽到"没有 Friction 的弹道发射器"即可一次修好；没有一起改是因为那会同时改变每一处爆炸与溅射的手感，需要单独过一遍截图。
- **测试**：`@PvzceGametest` 注册式集成测试与渲染冒烟（离屏 FBO + 图 diff）**未建**，所以界面没有自动化验证 —— 这批工具是第三阶段的规划（见 `03-第三阶段-精修完善.md` §3.6.1）。现状是 JUnit 单测/集成测试：`./gradlew :pvzce-game:test`（约 20s，`:pvzce-api:test` 另有 2 例）。
  - 服务端/客户端流程可以直接起真的 `PvzceServer`/`PvzceClient` + `Connection.createMemoryPair()` 来测：`testutil/ServerHarness` 与 `testutil/ClientHarness` 是这两个 harness 的唯一实现（此前有 5 份各写各的副本）。
  - **一轮改动验到什么程度见 `验证约定.md`**（按需，不是每轮全量 + 截图）；`pvzce.smoke*` 的完整参数表见 `冒烟与截图指南.md`，这里不再重复维护一份。
  - 曾经的偶发失败（未播种的 `LevelServer.random` 撞上"取第一个掉落物"、保存/恢复的时序假设）已经改成确定性断言，不再有"单独跑必过"的用例。
