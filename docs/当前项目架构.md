# PVZCE 当前项目架构

> 本文档描述**代码实际形态**（as-built），与 `00`~`03` 的规划文档区分开：规划文档说明"要做什么"，本文说明"现在是什么、在哪里改、往哪扩"。
> 规模基准：`pvzce-game` 300+ 个源文件 / 约 4.1 万行，`pvzce-loader` 141 个文件 / 约 2.3 万行（Fabric Loader fork），`pvzce-api` 11 个文件。内容：24 种植物、12 种僵尸、140 个粒子定义。
> 测试：`./gradlew :pvzce-game:test`，当前 365 个用例（合计约 8s）。

---

## 1. 一句话架构

PVZCE 是一个**独立运行的桌面游戏**，用 Fabric Loader（fork 后内嵌）加载第三方模组，本体分为"平台层 → 框架层 → 内容层 → 表现层"，服务端 60tps 权威模拟、客户端镜像表现，二者通过**包交换**通信（单机也是内存包队列，不是直接方法调用）。

```
┌──────────────────────────────────────────────────────────────┐
│ L4 入口      launcher/PvzceGame → KnotClient（loader fork）   │
├──────────────────────────────────────────────────────────────┤
│ L3 表现      client/{gui, renderer, animation, sound, particle}
│              服务端状态只读镜像，不参与判定                     │
├──────────────────────────────────────────────────────────────┤
│ L2 内容      api/content（Def record + Codec）                │
│              common/capability（可组合能力实现）               │
│              server/{entity, level, ai, command, gamerule}    │
├──────────────────────────────────────────────────────────────┤
│ L1 框架      api/registry · api/tag · common/nbt · Identifier  │
│              common/resource（资源/数据包）                    │
│              common/network（包 + 传输）· common/level（共享态）│
├──────────────────────────────────────────────────────────────┤
│ L0 平台      net.fabricmc.loader（fork）· LWJGL · DFU · Gson   │
└──────────────────────────────────────────────────────────────┘
```

**依赖方向**：L2 依赖 L1 与 `com.pvzce.api`；L3 只读 L1/L2 的注册表与状态；`com.pvzce.api.content.capability` 的方法签名引用服务端实体类型 —— 这是**唯一一处有意的例外**，因为能力本身就是服务端行为，详见 §5.4。

## 3. 框架层

### 3.1 注册表

- 接口 `com.pvzce.api.registry.Registry<T>`，实现 `MappedRegistry<T>`，由 `RegistryAccess` 持有。
- 静态（代码）与动态（数据包）两层：`register` 只能在本体首次冻结前调用；`registerDynamic` 可在每次重载时替换。
- **`RegistryEntryAddedCallback` 由 `MappedRegistry.register/registerDynamic` 统一触发**（`BuiltInRegistries.registerStatic` 只是薄包装）。不要绕开 `Registry.register` 直接写 map。
- `PvzceRegistries` 声明全部注册表键（单数 id，如 `pvzce:plant`）；`PvzceDataLoader.CONTENT_REGISTRIES` 声明**目录名**（复数，如 `plants/`）。**`byCategory()` 是命令层/补全层/标签层共用的分类表** —— 新增注册表只需在这三处各加一行（其中 `byCategory` 一处即可让命令与补全同时生效）。
- 目前注册表：plant、zombie、projectile、resource、slot、tool、scene_element、game_rule、env_var_type、sound_event、level、level_theme、level_category、plant_capability、zombie_capability、projectile_capability。

### 3.2 `Identifier`

`namespace:path`，规则同 MC（小写 + 数字 + `_ - . /`）。**空 namespace / 空 path 一律非法**，`tryParse` 返回 `null`；`:path` 仍按原版语义解析为默认命名空间。所有"缺失"判定都依赖 `tryParse == null`，因此不要再引入接受空串的解析路径。

### 3.3 资源包 / 数据包

- 栈：内置 `ClasspathPack`（开发期目录、发布期 fat jar）→ `resourcepacks/` → `datapacks/`，高优先级覆盖低优先级。
- `PvzceResourceManager` 提供 `getResource/getAsset/getData/listResources/listResourceStacks`；所有路径拼接走 `PackPaths`（**不要**自己拼 `prefix + "/"`）。
- 数据包目录约定：`data/<ns>/<注册表目录>/<相对路径>.json`，**id 由完整相对路径决定**（`plants/tier1/pea.json` → `ns:tier1/pea`），文件内显式 `id` 会覆盖它；同一注册表内 id 冲突会报错。包根就是命名空间，与 MC 一致 —— 内置包曾经写成 `data/pvzce/pvzce/plants/`（加载器要求命名空间后必须有一个字面量 `pvzce` 段），把自己的命名空间拼了两遍。
- 标签：`data/<ns>/tags/<注册表目录或注册表 id>/<名字>.json`，单数与复数**两种拼写都接受**；格式 `{"replace":false,"values":["ns:id","#ns:other"]}`。标签 id = 命名空间 + 注册表目录下的相对路径，与 MC 一致（`data/c/tags/plant/plantable.json` → `#c:plantable`）。曾经兼容的 `data/<ns>/tags/pvzce/<注册表>/<名>.json` 三段式已随包根扁平化一并删除。
- **标签按注册表分开**：`#c:plantable` 在 `scene_element` 与在 `plant` 里是两个互不影响的标签（同 MC）。`PvzceTags.RegistryTagView` 把"注册表 + 标签"绑在一起查询，避免同名的两个标签被读串。
- 约定标签（`c` 命名空间）承载**全部放置规则**，内置包在 `data/c/tags/{scene_element,plant}/` 下提供；模组往同名标签追加条目即可扩展，`PvzceTags.PLACEMENT_TAGS` 是完整清单，缺一个会在关卡构造时被 `LevelValidator.validatePlacementTags()` 点名。
- 加载结果 `LoadResult{loaded, errors}`：`PvzceServer.reloadData` 统一上报；客户端重载也会记录标签错误。

### 3.4 NBT 与存档

- `common/nbt` 是自研 MC 兼容实现：根必须是 compound；数组/列表长度有上限并报 `IOException`；`put/add` 拒绝 null；**数值 getter 跨类型放宽**（写成 int、读成 float 是合法的）。
- 版本：`PvzceConstants.SAVE_DATA_VERSION` 写进每份存档；**没有迁移链**——项目未发布，不存在旧档，读到 `GameState` 缺失或非 running 的记录一律当没有存档（`LevelServer.restore`）。
- **每个关卡一个文件**：`saves/<world>/levels/<key>/level.dat`，内含 DataVersion / LevelId / GameState / Winner / Tick / 波次进度 / 队伍资源与解锁 / 卡槽 / **Belt（传送带上的卡与下次出货倒计时）** / 场景网格 / **Entities 快照列表**。`saves/<world>/level_status/<key>.dat` 记录通关。
- **存档目录键 `key` 必须是单射的**（`LevelKey`，纯函数）：旧的 `ns + "__" + path.replace('/','_')` 让 `pvzce:a/b` 与 `pvzce:a_b` 共用同一个存档目录与通关标记 —— 后保存的关卡静默覆盖前一个。现在 = `十六进制(命名空间) + "__" + 转义(path)`（`%`→`%25`、`/`→`%2F`）：命名空间段只用 `[0-9a-f]`，路径段不会出现这些字符，两半各自单射，所以不同关卡 id 永远不共目录（`LevelKeyTest.distinctIdsNeverShareAKey` 用一批"命名空间与路径都由同一批字符组成"的恶意 id 钉住）。目录名不像以前那么好读，这是有意的取舍。
- **旧键的存档不做改名**：项目未发布，不存在用旧键写出的存档，所以启动时那次「旧键 → 新键」扫描已删除（`LevelKey.legacyMigration` / `PvzceServer.migrateLegacySaveKeys`）。若本机留着早期版本的 `saves/`，它的进度按既定取舍从头开始。
- 客户端也有一份同样的键推导（`LevelMove`）：编辑器换组要能在没有服务器往返的情况下搬存档，两处必须完全一致，`LevelMoveTest` 与 `LevelKeyTest` 各钉一半。
- 关卡目录/文件名规则集中在 `PvzceServer` 的 `sanitizeWorldName` / `levelKey` / `worldPath` / `levelDir`，客户端同名世界也用同一正则（`[^A-Za-z0-9_-] → _`）。
- **每个世界一份玩家档案**：`saves/<world>/profile.dat`（`PlayerProfile`），只有两个字段：`Coins`（金币钱包，上限 `PvzceConstants.COIN_CAP` = 9990）与 `Unlocked`（已解锁卡 id 列表，外加 `UnlockAll` 沙盒标志）。这是**唯一跨关卡存在**的状态 —— 队伍资源、卡槽都随关卡生灭。缺文件 / 空记录 / 读失败都回落到 `PlayerProfile.starter()`（豌豆射手 + 铲子），旧世界因此照常可玩。写点只有 `onLevelFinished`、`leaveLevel`、`createLevel` 换世界前与 `PvzceServer.run()` 的 `finally`；**不要在 `stop()`（关停钩子线程）里写文件**。

### 3.5 网络

- **协议表只有一张**：`PvzcePackets`，每行 = `id + 方向 + 类 + 解码器`。C2S id `< 64`，S2C `>= 64`。`PROTOCOL_VERSION` 随 `LevelInitS2C` 下发，客户端版本不符直接拒绝加载。
- **传送带的整表同步**：`BeltSyncS2C(cards)`（`PROTOCOL_VERSION` = 9）替换客户端的整个卡槽条——见 §4.9，它存在的理由是 `SlotSyncS2C` 的 upsert 说不出"这张卡没了"。
- **背包/金币/解锁**：`ProfileS2C(coins, unlocked, unlockAll, unlockedLevels)` 同时携带**卡**与**已购买关卡**两组 id，二者分开存（见 §4.8）。
- `PacketRegistry.register` 对重复 id / 重复类**抛异常**；未知 id 明确报错，不会串包。
- 序列化：
  - 集合/可选/identifier 一律用 `PacketByteBuf` 的 helper（长度对剩余字节校验，越界抛 `DecoderException`）。
  - 字段 ≥3 个的包用 `PacketStruct`：**每个字段的 getter / writer / reader 写在同一行**，`encode`/`decode` 遍历同一列表，从结构上消除"写读顺序漂移"。
  - 新增包：在 `PvzcePackets` 加常量 + 一行 `def(...)`，并在 `PacketProtocolTest.samplePackets()` 加样本（否则 `theSampleSetCoversTheWholeProtocol` 会失败）。
- **背包/金币带来三个包**（`PROTOCOL_VERSION` 因此 = 4）：`ProfileS2C(coins, unlocked, unlockAll)`（随关卡列表与每次变更下发）、`LevelRewardS2C(levelId, collectedCoins, bonusCoins, totalCoins, unlockedCard)`（结算，表现用）、`CreateWorldC2S(worldName, unlockAll)`（世界目录在客户端建，档案由服务端写）。
- 传输：`MemoryPacketTransport`（单机，双向队列，`close()` 会传播）与 `TcpPacketTransport`（LAN 骨架、**非阻塞**、帧长上限 16MiB）。`Connection` 负责编解码、分发、异常记录与关闭传输；解码失败会带堆栈断开而不是静默丢弃。

## 4. 服务端

### 4.1 线程与主循环

`PvzceGame.main` 装配：`BuiltInRegistries.bootstrap()` → 调用 `main`/`client` 入口点 → `Connection.createMemoryPair()` → 起服务器线程 → 客户端主循环。

`PvzceServer.run()` 顺序（**顺序有意义**）：
1. `PvzcePackets.register()`、`BuiltInRegistries.bootstrap()`
2. 建目录、`resourceManager.init(gameDir)`
3. **`invokeServerEntrypoints()`** —— 必须在数据加载之前，否则内容注册表已冻结，mod 注册内容会抛异常
4. `reloadData(false)` —— 冻结内容注册表
5. 循环：处理命令/stdin/网络 → `tickRate.advance()` → `level.tick(bridge)` → 每 250ms 发 `DebugInfoS2C`

`PvzceTickRateManager` 负责 60tps 基准、`/tick rate|freeze|step|sprint`。

### 4.2 `LevelServer`

权威关卡。要点：

- 实现 `LevelAccess`（`api/entity/LevelAccess`）—— 能力、AI、命令通过它访问关卡，而不是直接摸内部字段。
- **所有实体入场只经过 `spawn*`**：`spawnPlant` / `spawnZombie` / `spawnProjectile` / `spawnArcProjectile` / `spawnResource`。`addEntity` 会设置关卡尺寸（网格派生用关卡真实尺寸，**不是**默认 9×5）。
- `spawnPlant` 是**唯一的植物创建路径**（玩家、AI、命令、关卡初始实体、存档恢复全部走它），负责叠放高度、花盆偏移、`onPlaced`、`onRemoved`。
- `bridge` 是环境字段：`tick()` 与玩家动作 API 用 `withBridge`（try/finally）设置，因此任何提前 return 都不会泄漏。
- 场景是 `SceneGrid<SceneElementDef>`，坐标解析统一走 `SceneCells.parse`（畸形条目被忽略并记录，不会让关卡构造抛异常）。
- 日夜：`PvzceClock` + `common/level/DayNightCycle`（纯函数，客户端共用）。**不要在别处重算周期数学**。
- `LevelValidator` 在构造末尾收集关卡数据的全部问题（未知规则/非法取值/未知卡槽/畸形场景/未知初始实体）并一次性打印，**不中断构造**。
- 波次：`normalizeWaves`（末波必为 FINAL）→ `tickWaves` → `PendingWaveSpawn` 队列按 `WaveDef.SPAWN_INTERVAL_TICKS` 逐个放怪。
- **小游戏关卡有两块关卡级数据**（见 §4.9）：`conveyor`（传送带）和 `placement_zone`（可种植区）。前者把卡槽变成 `ConveyorBelt`，后者由 `canPlacePlant` 统一判定。
- **`plantAt` 会跳过不占格的植物**：`PlantEntity.occupiesCell()` 为假（只有 `pvzce:bowl` 会这样回答）时，僵尸不啃、手套不搬、铲子不铲。这是"植物正在离开这一格"唯一的表达方式，而不是给僵尸的啃咬循环加特例。

### 4.3 进入/重开关卡的协议语义

两个包都能"进入关卡"，语义不同，**不要混用**：

| 包 | 谁发 | 语义 |
|---|---|---|
| `RequestLevelC2S(restart)` | 关卡列表的「下一步/继续游戏」与 `LevelSetupScreen` 的「开始游戏」 | "进入这个关卡"。已经在跑同一关卡且 `restart=false` → **原样 resync 当前实例**（相当于继续）；`restart=true` → 重开 |
| `StartLevelC2S(restart, seeds)` | 选卡界面的「开始游戏」 | **"用这套卡组开一局"**。选卡只发生在一局开始之前，所以目标关卡若已经在跑且 `restart=false`，服务端会**重开并应用这套卡组**，而不是 resync |

**进入决策只有一处**：`PvzceClient.enterLevelFromMenu(info)`，判据是列表给的 `LevelInfo.hasRunningSave()`（读的是**独立的 `runningSave` 字段**，不是 `status` 字符串 —— 见下方「通关优先于进行中」）：

- **有存档** → 直接发 `RequestLevelC2S(restart=false)`：服务端 `createLevel` 先把整个存档（棋盘/实体/波次/钱包/卡槽）加载并下发，**然后**才发 `LevelSavePromptS2C`，客户端在已加载的关卡之上弹出「发现存档」。**不经过关卡准备，也不经过选卡** —— 存档里已经有卡组和阵营，为一局即将被继续的游戏挑卡是没有意义的。
- **无存档**（含"已通关"）→ 关卡准备（`LevelSetupScreen`，选阵营）→ 选卡界面 → `StartLevelC2S(restart=false, seeds)`。

> 曾经的实现把关卡列表的「下一步」一律送进关卡准备 → 选卡，于是进行中的关卡也会先出现选卡界面，而玩家提交卡组后服务端走的却是"加载存档 + 提示框"（`StartLevelC2S(restart=false)` 命中存档），表现为**选卡结束后才弹出重开/继续提示框**。现在这条顺序结构上不可能出现：`hasRunningSave()` 为真时根本不进这两屏。列表右侧按钮随之改名为「继续游戏」。
>
> 这条保证后来又被同一个形状破坏过一次：把"有没有存档"折进 `status` 之后，"已通关 + 有一局放弃的重玩"（两者同时成立）被压成一个值，进入判定于是看不到存档，同一个"选完卡才弹框"的症状复发。`runningSave` 因此是**独立字段**。

列表里的「进行中」是**某个世界**的 `saves/<world>/levels/<LevelKey>/level.dat` 存在与否，所以：

> **通关优先于"进行中"**：通关标记是"这一关曾经打通过"，**一旦写下就不会被收回** —— 重玩一局已通关的关卡、那局打输了、或者中途退出，这一关仍然是已通关。判定用的是 `isLevelCompleted`（只看标记文件），它同时是解锁规则里 `clearedLevels` 的来源，所以"有一局重玩等着继续"不会把后面的关卡重新锁上。
>
> **"有没有存档"是另一件事，走另一个字段**：`LevelInfo.runningSave`。`status` 只负责列表行上显示什么（有存档就显示"进行中"，否则显示"已通关"），`LevelInfo.hasRunningSave()` 读的是 `runningSave`。曾经把存档状态塞进 `status` 字符串里，于是"已通关 + 有一局放弃的重玩"这种**两者同时成立**的情况无法表达：进入判定以为没有存档 → 打开选卡界面 → 选完卡提交后服务端才发现有存档 → 才弹出"继续/重开"对话框。现在进入判定先看 `runningSave`，有就直接加载存档并在其上询问，完全不经过关卡准备与选卡。

- 世界选择页有**「全解锁」开关**：勾上再创建世界会发 `CreateWorldC2S(world, true)`，服务端写出 `UnlockAll` 档案（沙盒世界拥有所有卡，包括以后新增的）。世界目录仍由客户端创建（列表直接读盘），档案由服务端写。
- `PvzceClient.setCurrentWorld()` 换世界时**丢弃已缓存的列表**（否则会把上一个世界的进行中标签用在另一个世界上，而它正是进入决策的输入）；
- 服务端 `refreshLevelList()`（`/reload` 后主动补发）按**客户端最后一次请求的世界**下发，而不是服务端自己的 `currentWorld`（关卡之间它是 null，会被规范化成 `world`）。

> 曾经的实现把 `StartLevelC2S(restart=false)` 也当成"resync 当前实例"处理：服务端已经换成新关卡，客户端却收到一个描述**仍在运行的旧实例**的 `LevelInitS2C`，玩家选的卡组被静默丢弃，于是表现为"没有真正重新开始、旧关卡也没关掉"。现在这条路径必定重开。

选卡界面不关闭自身，等 `LevelInitS2C` 到达后由 `PvzceClient.onLevelInit()` 用 `setScreenReplacing` 重建整个界面栈，所以暂停对话框/选卡界面不会残留在新关卡下面。

**暂停菜单的「重新开始」**（`PvzceClient.restartCurrentLevel()`）走的是"先真正关闭当前关卡，再进入该关卡的正常选卡流程"：

1. 发 `LeaveLevelC2S`，服务端 `leaveLevel()` 会**先存档再 shutdown**，因此放弃重开也不会丢进度（关卡列表里仍显示"进行中"，可继续）；
2. 客户端清空本关全部镜像状态（`clearLevelClientState()`：实体/粒子/动画/音乐/存档提示/镜像），并用 `setScreenReplacing` 把界面栈换成选卡界面 —— 旧关卡不会以冻结实例留在下面；
3. 「开始游戏」→ `StartLevelC2S(restart=true, seeds)`：服务端 `createLevel(restart=true)` 会**删掉第 1 步写的存档**并开新局；
4. 「返回」/ESC → `showLevelList()`，回到当前世界的关卡列表（**不会**回到刚被关闭的关卡）。

> 旧实现是把选卡界面 `push` 在仍在运行的关卡之上：按 ESC 会退回旧关卡的暂停菜单，看起来就是"选了重新开始，旧关卡却还开着"。这条路径（`openCurrentLevelSeedSelection`）已删除。

### 4.4 玩家、卡槽与资源

- `SlotResolver.resolve(id)` 是**"这张卡是什么"的唯一答案**（服务端卡槽、客户端选卡池、校验共用）。未知 id 会记录一次并跳过。
- `PvzcePlayer.createPlantPlayer` 直接用 `SlotResolver`，因此"选卡界面能选的"与"服务端发放的"必然一致。
- `Team` 持有共享资源与解锁集合；`Slot` 持有 index/kind/content/costSun/cooldown/usesLeft。

### 4.5 背包、金币与关卡奖励

三件事以前都不存在：**玩家没有身份**（`Team` 的资源与 `Slot` 的卡组都随关卡生灭），**卡池不看玩家**（关卡列什么就能用什么），**通关没有奖励**。现在：

**背包（`PlayerProfile` + `SeedOptions.cardPool`）**

- 解锁只覆盖**植物与工具卡**；资源卡**不背包锁**（`requiresUnlock` 对资源返回 false），但**仍然要占卡槽**：`pvzce:sun` 的 `collectible_without_card` 是 `false`，银行只在卡槽条里有阳光卡时才画出来，收阳光正是那张卡买到的东西。所以每个关卡的 `slots` 都列着 `pvzce:sun`，`SeedOptions.cardPool` 也照常把它摆在选卡池里。判定只有一处：`SlotResolver.requiresUnlock`（服务端 `PlayerProfile.owns` 与客户端 `ClientProfile.owns` 都调它，两份"锁没锁"不允许分叉）。
- **关卡的 `slots` 是本关固定卡，无视背包**：关卡可以"借"卡给玩家（教学关给一张土豆雷），所以 `sanitizeSeedSelection` 只过滤**自选**，从不过滤关卡钉住的卡。玩家能自选的池子 = 背包已解锁卡 − 固定卡，填到 `max_seed_slots`。
- **卡池只有一个来源**：`SeedOptions.cardPool(def, owns)`（已解锁卡 + 关卡自己的卡），`PvzceServer.sendLevelList` 与 `LevelServer.SeedContext.forProfile` 都用它，所以"选卡界面看得到的"与"服务端收得下的"是同一份。`SeedOptions.forLevel(def)`（不过滤）仍用于测试与编辑器预览。
- 固定卡已填满 `max_seed_slots` 时没有可选空间：`ChooseSeedsScreen.hasNothingToChoose()` 让选卡页放完僵尸预览与面板后**自动开始**（原版 1-1 没有选卡界面）。
- 新世界默认解锁 `PvzceIds.STARTER_PLANT`（豌豆射手）+ `STARTER_TOOL`（铲子）；`CreateWorldC2S(world, unlockAll)` 让"创建世界"对话框的**全解锁**勾选写出 `UnlockAll` 档案。沙盒用**标志**而不是展开成 id 列表，这样以后新增的内容也自动解锁。

**金币（四种面额，`PvzceIds.COIN_DENOMINATIONS`）**

- 金币不是一种资源而是**四种**，因为原版就是四种不同的东西（白/银币 10、金币 50、钻石 1000、钱袋 250）：一个 `pvzce:coin` 无法告诉玩家刚捡到的是 10 还是 1000。它们是普通 `ResourceDef`，`default_value` 就是面值，`collectible_without_card: true`（捡钱不需要卡槽，也不看 `Team.unlockedResources`）。资源目录 `data/pvzce/resources/{coin_silver,coin_gold,diamond,money_bag}.json`。
- **掉落时 `amount` 直接写成面值**（`defaultValue × coin_drop_amount`），所以队伍那份资源计数本身就读作金币数，HUD 与钱包只需要**求和**，换算阶梯只存在于资源定义里一处。
- 美术：三个硬币/钻石由 `tools/reanim_to_pvzce_all.py --entity coin_silver --entity coin_gold --entity diamond --input-dir refer/im5/reamin` 从原版 reanim 生成，钱袋是单张 `textures/entities/money_bag.png`（`ResourceDropEntity` 的平铺贴图回退路径）。**生成时排除了 `COINGLOW` 与 `DIAMOND_SHINE`**：原版用加法混合画它们，本渲染器没有加法模式，普通 alpha 画出来是一块盖住硬币的大黄饼。
  `refer/anim` 是**完整**的原版动画集（146 个 reanim），`refer/im5/reamin` 只有硬币那几个；新增内容优先去 `refer/anim` 找。
  **硬币是「弹出来」的**：四种面额都是 `drop_motion: rise`，`rise_height: 0.3`、`rise_scatter: 0.25` —— 从僵尸身上弹起 0.3 格再落下，落点随机左右偏移最多 0.25 格（同一个僵尸一次掉好几枚，方向一致会看起来像同一个东西复制）。向日葵产的那朵阳光仍然是 `rise_height` 默认的 0.5、`rise_scatter` 为 0：它属于那朵花，要落回原处。横向位移由 `LevelServer.spawnResource` 用关卡自己的 `Random` 掷出后交给实体（实体不自己掷骰子，否则读档会重掷）；`riseTicks`/`riseOriginX`/`driftX` 都进存档，飞行中途存档能原地续上。
  **掉落尺寸**：四种面额都声明了 `render_scale`（三枚硬币 0.25 ≈ 0.2 格，钱袋 0.55），因为掉落物的默认大小是 0.8 格 —— 一枚硬币按 0.8 格画出来比一格草坪还显眼，看着像一块发光的圆盘而不是硬币。
  **动画掉落物的尺寸契约**（踩过一次坑，写下来）：走动画的掉落物，绘制**宽度**是 `0.8 × render_scale` 格，**高度**则取自动画文件自己写的尺寸（`render_scale` 不作用于竖向）。所以下调 `render_scale` 只会把它压窄、不会变小 —— 当时的症状正是「金币只被压扁、大小没变」。现在三枚硬币的动画模型都**按 `0.8 × render_scale` 写成正方形**（0.4×0.4 格），于是它们既是圆的、也真的变小了；`CoinVisualLayoutTest.aCoinsArtIsAuthoredAtTheSizeRenderScaleDrawsIt` 钉住这条（模型非正方形、或尺寸与 `render_scale` 对不上就失败）。钱袋没有动画、走贴图兜底路径，那条路两个轴都乘 `render_scale`，本来就是对的。
  **拾取音效也按资源分开**：`ResourceDef.pickup_sound`（缺省 `sfx/ui/collect`）。阳光继续用收集音；三枚硬币用 `sfx/ui/coin`（钻石用 `sfx/ui/diamond`）—— 以前捡币放的是阳光那声，保龄球连击一次掉一串币，听起来像在下阳光。
  **拾取闪光按资源分开**：`ResourceDef.pickup_effect`（可选）是「捡起这个资源时放什么效果」，缺省**什么都不放**。阳光声明 `pvzce:lantern_shine`（200x200 的黄色柔光，每颗 0.7 格、一次 10 颗，**原样保留**）；四种面额**不声明** —— 同一片黄光画在硬币上是把半块草坪糊成黄色，而捡币本来就有收集音效与飞向钱袋的动画在说「收到了」。`LevelServer.collectResourceInternal` 只负责发声音，粒子 id 从资源定义里取。
- **关卡内**的僵尸死亡按 `rewards.coin_drop_chance` 掉 `rewards.coin_drop`（默认 `pvzce:coin_silver`）这枚币（`LevelAccess.zombieDied` → `LevelServer.zombieDied`；实体只报告"我死了"，掉落是关卡数据的事）。金盏花产银币（10 / 24s）。
- **关卡结束**时 `PvzceServer.awardProfile` 把本局收集的金币写进钱包（**胜负都入账**），再按首通/重复发放关卡奖励。**金币**的首通判定是 `level_status` 文件在不在（`levelStatus(...).isEmpty()`），所以重复通关拿的是 `repeat` 那份。**`first_clear` 里的解锁不看这个判定**：只要关卡声明了某张卡的解锁、而背包里还没有它，**任何一次通关都会补发**，已经拥有则是空操作。两者必须分开 —— 首通标记只说明"这一关以前打通过"，不说明"这份奖励发出去过"：1-4 的手套就是反例，关卡在玩家通关之后才加上这条奖励，此后每次通关都走 repeat 分支，奖励页永远显示钱袋。

**关卡奖励（`LevelRewards`）**

- 关卡 JSON 的 `rewards` 块：`first_clear` / `repeat` 是 `{type:"unlock"|"coins", id?, amount?}` 列表，外加 `coin_drop`（掉哪种币，资源 id）/ `coin_drop_chance` / `coin_drop_amount`。默认值 = `LevelRewards.DEFAULT`（首通不给额外奖励、重复给 100 金币、25% 掉 1 枚银币）。`first_clear` 的 **unlock 条目是幂等的**：见下一节"结算与展示"前的说明 —— 已拥有即空操作，缺失就补发，与首通标记无关。
- `type` 是字符串判别式，**DFU codec 看不出拼错的类型**（`"unlcok"` 会正常解码然后什么都不发），所以 `LevelValidator.validateRewards` 必须跑：未知 type、缺 `id`、未知卡、`amount <= 0`、掉率 >0 但数量 0 都报出来。

**结算与展示：奖励先落在草坪上，再由玩家领取**

一局胜利**不会**直接弹出奖励页。顺序是（全部在客户端，服务端只发两个包）：

```
GameStateS2C(plant 胜)   → 不播胜利音乐（onGameState 对植物方胜利刻意跳过）
LevelRewardS2C           → InGameScreen.showReward：种子卡/钱袋落在**最后一只僵尸死亡的那一格**，从上方落下
玩家点击奖励              → 胜利音乐立刻开始，同时奖励慢慢移到屏幕中央（1.9s）
移到中央                  → 原地再放大一点（0.6s）
再等 0.4s                 → openAwardScreen(...) → AwardScreen（先停 stinger，再放 zen_garden）
```

  共约 2.9s，比"移动完就进页面"多约半秒：到位与"被展示"是两拍，少了放大那一下，奖励像是凭空消失进了页面。

- `LevelRewardS2C(levelId, collectedCoins, bonusCoins, totalCoins, unlockedCard)` 在 `GameStateS2C` 之后发；它**只是表现**，钱包在发包之前就写好了，客户端不领取也照样拿到金币。
- 奖励掉落物**不是实体**：它是 `InGameScreen` 里的一个世界坐标点 + 三个时间戳（落下 / 领取 / 音乐），因此不进存档、不参与判定，也不需要服务端同意。`rewardRect()` 是**唯一的**矩形来源，绘制与点击命中都读它（点击落点与贴图不可能分叉）。
- **落点是"最后一杀"**：`LevelRewardS2C` 带 `dropX/dropY`，来自 `LevelServer.lastKillX/Y`（`zombieDied` 里先记位置再掷掉币，所以不掉币的僵尸也算）。没有僵尸的关卡为空值，客户端回落到草坪中央。
- **胜利音乐属于"点击"那一瞬间**，既不属于"关卡结束"也不属于"移到中央"：`PvzceClient.onGameState` 对植物方胜利直接 return，stinger 由 `InGameScreen.claimReward()` 在点击的同一步播放（与升移动画同时开始）。失败没有奖励可领，所以结束时立刻播。
- **金币飞进左下角的钱袋**：每种掉落物飞向**自己的**银行（`bankTarget`：阳光→左上阳光银行，金币→左下钱袋）。这条动画原来被一句 `if (animations.isEmpty() || !hasSunBank()) return;` 整体挡住 —— 传送带关卡（1-5）没有阳光卡、也就没有阳光银行，于是**金币被收集后直接消失**，根本看不到飞进钱袋。现在按每条动画自己的银行判断：金币只要求钱袋（它本来就是「有变化才显示 2.6s」的回执），阳光才要求阳光银行。
- **兜底**：奖励躺够 `REWARD_AUTO_CLAIM_NANOS`（20s）没被点就自动领取 —— 金币早已入账，这个计时器只是为了不让走开的玩家回来面对一个冻结、且唯一出口是一个他已经不记得要点的精灵的棋盘。
- 没有奖励包的胜利（改过的服务端）保持旧行为：大号「胜利！」+ 点击任意处离开。
- `AwardScreen` 用 `refer/im5` 的原版奖励页美术，**播 `pvzce:music/zen_garden`**（`ensureMenu`）：关卡已经结束，这一页讲的是玩家带走了什么。`unlockedCard` 非空 → 种子卡落进相框；否则 → 钱袋，点一下撒金币（纯表演 + `pvzce:sfx/ui/moneyfalls`）。"继续"走 `PvzceClient.finishLevelAndShowList()`（回关卡列表而不是世界列表）。
  - 标题画在**窗口顶部**而不是美术坐标里：奖励页底图是 4:3 且 cover 适配，宽屏下美术顶部那条木牌会被裁掉。
- 奖励页的「继续」用 `Button.Style.SEED_CHOOSER`（木质）而不是默认的金属边框按钮：这一页是木板，金属按钮属于对话框。
- 波次进度用原版 `refer/im6` 的三张图（`FlagMeter` 的上下两条分别是空轨与绿色填充、`FlagMeterParts` 的僵尸头/杆/旗、`FlagMeterLevelProgress` 的铭牌），画在**右下角**，每一块都有含义：`[关卡名] [轨道 + 绿色进度]`，**`LEVEL PROGRESS` 铭牌贴在条的正下方居中**（上沿就是条的下沿，中间不能留缝：它和条是同一件仪表），**僵尸头骑在绿色进度的前沿**（它是进度标记，不是固定在一端的装饰），**只有 huge/final 波才插旗**（小波插旗会让旗子失去"大波要来了"这个唯一含义）。
  - **比例照原图**：条按 `158×23` 的原尺寸 × `METER_SCALE`（0.9，和阳光银行 `70/78` 同一把尺子）画，不拉伸 —— 拉长会把两端圆角压成椭圆、把旗子摊开。
  - **方向从右往左**，和原版一致：绿色填充锚在右端、前沿向左推进，旗子也按镜像排在 `1 - (i+0.5)/总波数`（第一波的旗在最右）。
  - 填充用的是**关卡总进度** `(当前波 + 波内进度) / 总波数`，不是当前这一波的进度 —— 这样前沿正好在该波到来时扫过对应的旗子。
  - 贴图是**上下翻转**加载的（UV (0,0) 在左下角，见 `TextureManager`），所以按 PNG 行号写的矩形要经 `vRangeForRows` 换算。
- 关卡内金币计数用原版 `coin_bank` 美术画在**左下角**（阳光银行占左上、波次条占右下，左下角永远是草坪），而且是**收据而不是常驻控件**：只在金币数变化后显示 2.6s（末 0.6s 淡出），新关卡开局不会凭空闪一个 0。`bankTarget(resourceId)` 决定收集动画飞向哪个银行 —— 金币落到阳光上会说明错的事情。
- 背包页 `InventoryScreen`（关卡选择页的「背包」按钮）把**未解锁卡也画出来**：只列已拥有的回答"我现在能做什么"，列出未解锁的回答"为什么我种不了坚果墙"，后者才是玩家真正的问题。它只读，不改档案。
- 关卡选择页右上角显示本世界金币（`textures/gui/award/money_bag`，缺图回退金币贴图）。

### 4.6 命令

`PvzceCommands.create(server)` 构建 Brigadier 树。分类参数来自 `PvzceRegistries.byCategory()`；`IdentifierArgumentType.forCategory` 的补全也来自同一张表（含复数别名）。时间查询用 `PvzceClock` / `DayNightCycle` 的共享函数。

### 4.7 AI

`PlantAIPlayer`：每 120 tick 决策一次，通过 `LevelServer.spawnPlant` 种下，因此与玩家种植完全同构。三种角色（防御/经济/进攻）的植物 id 可由关卡环境变量 `pvzce:ai_defense_plant` / `ai_economy_plant` / `ai_offense_plant` 覆盖，取不到时回退到内置选择。

### 4.7.1 资源掉落：三种落地方式

阳光、金币、能量豆原先**都**从空中 2.2 格处落下（同一个 `ResourceDropEntity`，同一个 `START_HEIGHT`），于是僵尸掉的金币从天上飘下来，向日葵产的阳光出现在花上方两格。

现在由 `ResourceDef.drop_motion` 决定（`fall` / `rise` / `landed`），并且**同一份资源可以两种都有**：天上掉的阳光是 `fall`，向日葵产的那一朵经 `LevelAccess.spawnProducedResource` 明确要求 `rise`（先上浮 0.5 格再落回原点）。金币一律 `landed` —— 生成即在原地。

阳光的亮度是**分层**问题：它的动画是三层叠加——一个很小的亮核心（36px）加两圈更大的半透明光晕（79/116px），所以放大后看着"又亮又没有实体"。修法是**调低两圈光晕的 alpha**（3 → 0.45、2 → 0.55），而不是整体压暗：整体压暗（`EntityVisuals.DROP_TINT`）同时也会把金币变灰，而光晕本身仍然在洗白草坪。

**掉落物的大小与形状只有一处可改**：`EntityVisuals.DROP` 给出掉落物的默认大小（0.8 格，宽高同一个值），**单个内容还可以用自己的 `render_scale` 覆盖它**（见下）。阳光、银币、金币的动画都按同一个倍率缩放，影子不再被单独拉宽，所以画成圆的阳光在草坪上就是圆的。此前倍率只作用在**宽度**上 —— 阳光按 0.95 格宽缩放、高度却按动画自带的 0.37 格，屏幕上是 1.7:1 的椭圆；`AnimationManager.xScaleFor` 里那段"再乘一次 `spriteXScale`"是同一件事的第二份补偿，去掉后几何在屏幕上正好是 1:1。下落时长从 150 tick 放宽到 300 tick：原来太阳还没被看到就已经落地了。

**实体渲染缩放（`render_scale`）**：`PlantDef` / `ZombieDef` / `ProjectileDef` / `ResourceDef` 都能声明 `render_scale`（`ContentDefs.RENDER_SCALE_CODEC`，默认 1，夹在 0.05~8），客户端据此把该内容的art 整体放大或缩小，**两个轴同倍率，所以形状不变**。它是纯表现：不参与命中盒、收集半径或任何服务端模拟，因此**不进包、不占 `PROTOCOL_VERSION`** —— 客户端本来就会加载同一份数据包，两侧各自从定义里读同一个数。取值只在 `EntityArt.renderScale` 一处解析（动画路径 `AnimationManager.xScaleFor`、无动画时的贴图兜底、以及影子 `InGameScreen.drawShadow` 都调它）。阳光用 `render_scale: 1.2`；它的三层光晕在 `animations/resource/sun.json` 里按"外圈约 1.6 倍于核心"重排，这样放大的是整颗太阳而不是只有中心。

### 4.7.2 波次节奏：每波自己的出怪间隔

`spawn_interval`（tick，可缺省）写在**每一波**上，不是关卡上，也不是全局常量：简单关卡的第一波 8 秒一只、最后一波 6 秒一只；困难关卡最后一波 2.5 秒一只。缺省 300 tick（5 秒）。

之前它是 `WaveDef.SPAWN_INTERVAL_TICKS` 一个全局常量（15 tick → 改 60 tick → 仍然太快），所以「把前期的节奏放慢」会连带把最终波也放慢 —— 这两件事必须分开。

约束是**一波放完必须早于下一波到来**（`(数量-1) × 间隔 ≤ 下一波 delay`），否则下一波的进度条会在上一波还在走的时候就开始读秒。内置四个冒险关卡都按这条核对过。

### 4.7.3 大波提示的生命周期

`waveWarningActive` 只在 `tick()` 里被清除，所以**任何让关卡停止 tick 的结束都必须自己清它**。曾经有两个漏洞，都是同一个形状：

- `nextWaveDelayTicks` 在最后一波释放后是 `-1`（"没有下一波"的哨兵值，不是"还剩 -1 tick"）。判据 `remaining > 0` 没写，负数让区间检查恒真，于是提示从最后一波起一直亮着。
- 关卡在提示亮着时结束（打完最后一只僵尸获胜、或僵尸进屋落败），`markEnd` 停止 tick，提示就永远留在屏幕上。

现在 `markEnd` 会一并清掉提示与进度，并且有回归用例分别钉住这两条。

**公告在存档恢复后不会重播**：`announcedWaves` 不是存档字段，所以 `restore()` 会按 `NextWaveIndex` 把它重新填满 —— 索引之前的波次都已经进场过，也就都已经宣告过。此前续一局停在最后一波的存档，`triggerWave` 看到一个空的已宣告集合，会把 siren 与 hugewave 再放一遍；6.5 秒的 `sfx/ambient/hugewave` 正好压在最后一波进场的窗口上，听起来就是"最后一波的音效在循环"。客户端另有一道保险（`InGameScreen.playEffectSound`）：同一个关卡实例内，`awooga` / `hugewave` 在 90 秒内只会真的播一次，其余服务端路径重复发也不会再响；呻吟之类该重复的音效不受影响。

公告本身由 `announcedWaves` 集合保证**每个波次索引只播一次**：`triggerWave` 是唯一发射点、且会推进索引，所以干净的一局本来就只播一次——但那是"碰巧"而不是保证，从存档中途恢复或将来有人直接调用 `triggerWave` 都可能让警报响第二遍。

> 排查记录：`awooga`/`hugewave` 在**服务端整局只各发一次**（有整局计数的用例），`SoundEngine.play` 也确认 `AL_LOOPING=false`、音源状态正常。也就是说"无限循环"不可能来自服务端重复发射；这里加的一次性集合是把仅剩的那条路径堵死。

### 4.8 关卡解锁条件

**此前关卡没有任何门槛**：服务端把关卡注册表整个发给客户端，每一行都可点，所谓"进度"就是玩家自己挑的顺序。现在关卡可以声明自己需要什么。

```jsonc
// data/pvzce/levels/yard/adventure/1_2.json
"unlock": {
  "requires": [
    { "type": "level", "id": "pvzce:yard/adventure/1_1" },  // 通关该关
    { "type": "card",  "id": "pvzce:sunflower" },           // 已解锁该卡
    { "type": "coins", "amount": 500 }                      // 持有金币
  ],
  "cost": 1000,      // 可选：花这笔金币一次性买下本关
  "hidden": false    // true = 未解锁时整行不出现（隐藏关）
}
```

- **默认不上锁**：没写 `unlock` 块的关卡永远可玩，所以既有自定义关卡、数据包、编辑器新建的关卡全部不受影响。`LevelDef.unlock()` 缺省是 `LevelUnlock.NONE`。
- 规则实现是 `common/core/` 的 **`LevelUnlocks`（纯函数）**，与 `LevelGrouping` 同一层、同一纪律：读一个 `Context{已通关集合, 已购买集合, ownsCard 谓词, 金币, 沙盒}`，产出 `State{unlocked, buyable, cost, unmet, reason, hidden}`。服务端求值、客户端**接收结论**（`UnlockInfo` 随 `LevelInfo` 下发），所以两侧不可能对"这关开没开"有不同看法。
- **门槛是服务端的**：`createLevel` 在任何东西被拆掉之前重新求值一次并拒绝（"关卡 X 尚未解锁：通关 1_1"）。菜单只是把这个结论画出来；跳过菜单的客户端也走不进去。
- **购买是一次性的**：`UnlockLevelC2S(levelId, worldName)` 只说要买哪一关，价格由服务端从关卡定义读，钱包从档案读 —— 改过的客户端只能选择买哪关，不能选择花多少。买下后写进 `PlayerProfile.UnlockedLevels`（与 `Unlocked` **分开存**：关卡 id 与卡 id 长得很像，混在一起会让一次买关变成解锁一张卡）。包必须带世界名：购买是按世界的，而菜单期间没有正在运行的关卡。
- **金币门槛与买断是两件事**：`coins` 条件查余额（花到别处就可能重新锁上），`cost` 是花掉并永久记下。两者都支持。
- **循环会被点出来**：`LevelUnlocks.findCycles` 在加载时报告互相等待的关卡链 —— 那种关卡永远进不去，而运行中的游戏不会说为什么。
- 操作入口：`/profile info | unlock <关卡> | unlockall`。`/profile unlock` 是把某关标记为已购买（不收费），用于冒烟、测试与被链条挡住的演示关。
- 编辑器有独立的 **「解锁」页**：前置关卡、所需卡（两个逗号分隔输入框）、金币价、隐藏关开关，**边输边校验**（未知关卡 / 未知卡 / 自己作为自己的前置当场标红），保存时整块写出；页面上放不下的条件类型（如 `coins`）会被**原样保留**，不会因为"编辑了一下"被删掉。
- 内置冒险模式：1-2 需通关 1-1，1-3 需通关 1-2，1-4 需前三关（并示范 `cost: 500` 的金币买断）。

### 4.9 小游戏关卡（传送带 / 放置区 / 保龄球）

1-5「坚果保龄球」是第一种**结构与普通关不同**的关卡，三件事原先都不存在，现在都是关卡数据：

```jsonc
// data/pvzce/levels/yard/adventure/1_5.json
"slots": [],                       // 卡组不是"关卡固定的几张"，而是"没有卡组"
"initial_sun": 0,
"rules": { "pvzce:sun_spawn_chance": 0 },   // 天上不掉阳光（0 = 永不掉落，已有规则）
"conveyor": { "interval_ticks": 300, "capacity": 6, "initial_cards": 2,
              "cards": [ { "id": "pvzce:bowling_nut", "weight": 1 } ] },
"placement_zone": { "min_x": 0, "max_x": 3 }   // 红线：只能种在左四列
```

**传送带（`conveyor`）**

- 服务端 `ConveyorBelt`（`server/level/`）持有队列与时钟：每 `interval_ticks` 从加权池里抽一张，`capacity` 满则**停止出货**（原版行为：囤卡要付代价），`initial_cards` 是开局就在带上的张数。
- **带上的卡就是玩家的卡槽**：`plantPlayer.slots()` 是传送带的投影，`rebuildBeltSlots()` 在每次变化后按带上的顺序重建，`placePlantInternal` 里种下一张就是 `belt.take(id)`——**不扣阳光、不进冷却**。
- **每张卡有一个永不复用的 id，位置不是身份**：带上的位置每消耗一张就整体前移，若客户端点的是"第 2 格"，一次竞态就会种出另一张卡。`SlotInfo.index` 因此是卡自己的 id，`PvzcePlayer.slot(int)` 按 `Slot.index()` 查（普通卡组里两者本来就是同一个值），过期的点击会**指名一张已经不在带上的卡**并被拒绝，而不是种错东西。
- **同步用整表替换而不是增量**：`BeltSyncS2C(List<SlotInfo>)`（`PROTOCOL_VERSION` 因此 = 9）。`SlotSyncS2C` 是按 index upsert，**说不出"没了"**——被用掉的卡会一直留在客户端的卡槽条上。传送带一次最多六张、几分钟才变一次，整表发最省心。`LevelInitS2C` 里的 `slots` 已经是带上的内容（`sendFullState` 与 `slotInfos()` 同源），所以进场不需要额外包。
- `LevelPayload` 因此多两个字段：`conveyor`（这张卡槽条是不是传送带）与 `beltCapacity`（UI 画多宽的带子）。两者都由服务端下发而不是客户端读本地数据包——带的**内容**本来就是服务端状态，客户端不该有第二份"这关是不是传送带"的判断。
- **存档**：带上的卡与下次出货倒计时写进 `level.dat` 的 `Belt` 块（`LevelServer.save/restore`）。恢复时先恢复带、再重建卡槽条，`restoreSlots` 于是能按 id 找回每张卡。
- **传送带关卡不经过选卡界面**：卡组由关卡自己发，选卡页会让玩家挑一套马上被丢掉的卡。`PvzceClient.usesConveyorBelt(levelId)` 读本地关卡定义（与 `lockedSlotsFor` 同一层），三条入口（关卡列表 / 暂停菜单重开 / 存档提示框重开 / 编辑器测试）都走它。服务端 `createLevel` 对传送带关卡直接传空卡组，`readSavedSeedSelection` 也不读——卡组就是带子。
- 美术是原版的 `ConveyorBelt.png`（胎面），从 `refer/im7/images/` 拷进 `textures/gui/hud/conveyor_belt.png`；它**铺满整个托盘**并持续向左滚动，卡片骑在上面（细节见 §6.2）。带子画在**屏幕顶部**（原版位置，且传送带关卡本来就没有阳光银行）。

**放置区（`placement_zone`）**

- 一个闭区间矩形，缺省的边就是棋盘边界（`{"min_x":0,"max_x":3}` 不必知道关卡多宽）。语义是"这一关的草坪只有这块能种"。
- **判定只有一处**：`LevelServer.canPlacePlant` 先查区域再查 `PlantPlacement`。玩家、手套、植物 AI 都走它；**故意不走的两条路是 `/spawn plant` 与关卡的 `initial_entities`**——那是关卡作者在摆东西，不是在玩。
- 客户端从 `LevelPayload` 拿到同一个矩形，画出**红线**（画在世界层，和服务器判定的是同一组数），悬停格子按"在不在区内"显示绿/红。红线画在普通草地上正是它必须是关卡数据而不是地形的原因：地形做的话，红线下面的草坪就得变成另一种地块。

**保龄球（`pvzce:bowl` 能力 + `pvzce:bowling_nut` 植物）**

- 新植物 `pvzce:bowling_nut` 复用坚果墙的美术与动画文件（`animations/plant/defense/bowling_nut.json`，只多一个绕自身中心旋转的 `roll` clip），卡面美术复用 `textures/gui/cards/wall_nut`，走新卡 `slots/bowling_nut.json`。**普通关卡的坚果墙完全不受影响**。
- 行为在 `BowlCapability`（`common/capability/plant/`）：种下即向右滚（`speed` 格/秒，出货 5），**永远向前**——撞到僵尸不会掉头，而是被撞进相邻车道（`ricochet`）；左右边界是出口（滚出右侧即消失），**上下边界是墙**，撞到会反弹。车道的选择偏向草坪中间（顶/底行必向内，中间行五五开）。
  > 曾经的实现是"撞到就反向"，于是坚果命中第一只僵尸后就一路朝房子滚回去，一颗只能打一只——而保龄球的核心恰恰是**斜向弹开继续前进**、在密集的僵尸群里连撞。方向反转与"上下反弹"是两件事，混在一起就两种都做不对。
- **伤害走 `ZombieEntity.damageImpact`，不走 `damageBody`**：`damageBody` 是爆炸用的、按设计无视护甲，用它会让铁桶一击死。`damageImpact` 让护甲先吃伤害（`ZombieCapability.onImpact`，`ArmorCapability` 实现）。击数因此是**数值窗口**而不是特例：本项目"护甲吸收到碎为止、碎的那一下不穿透到身体"，所以一次伤害必须够打死 200 血、又不够打穿 370 路障，同时两次要够打穿 1100 铁桶——即 `[550, 1100]`，`DEFAULT_DAMAGE = 650` 落在这个区间里，得到普通 1 击 / 路障 2 击 / 铁桶 3 击。
  > `onImpact` 要**先找 front 再找 top**：路障/铁桶在本项目里是 `position: top`（帽子），而掷物按子弹层选槽位（地面子弹打 front），保龄球没有子弹可描述，若只查 front 就会一路打到身体——路障与铁桶都是一击死，上面那条数值窗口也就永远用不上。
- **滚动中的坚果不是"格子里的植物"**：`BowlCapability.occupiesCell` 返回 false，`plantAt` 跳过它，所以僵尸不会停下来啃、铲子铲不掉。滚动的坚果仍然被模拟、被绘制、能被打。
- **连击掉币**：第 N 次命中掉 (N-1) 枚币（第 2 只起），币种来自关卡 `rewards.coin_drop`（`LevelAccess.dropCoin`，与僵尸掉币同一个"关卡决定值多少"的入口），所以关卡不写奖励时不会凭空多出一种货币。
- 1-5 的波次是**11 波约 228 只**（普通 / 旗帜 / 路障，后段少量铁桶），出怪间隔 30~60 tick、波间隔 900 tick，**第一波 360 tick（6 秒）就开打**（之前的 1200 tick 让开局有 20 秒空草坪），约 3 分钟；传送带因此是 **150 tick 一张**（原版 n-5 的节奏，僵尸多了 10 倍，5 秒一张发不过来）。首通奖励解锁 `pvzce:potato_mine`，音乐是原版的 `pvzce:music/loon_boon`（n-5 传送带关的曲子）。
  > 这一关**没有割草机**：项目里根本还没有割草机实体，所以漏一只就是直接输。原版 1-5 靠割草机兜底，这里的难度相应更高——要么补割草机，要么把波次调松。

**顺带修掉的 bug：土豆地雷炸了但僵尸无伤**。触发用 `trigger_range`（0.6）、伤害用 `radius`（0.55），僵尸每 tick 走 0.003 格，所以**进入触发圈的那一 tick 距离约 0.599，正好在爆炸范围之外**——每一次引爆都必然落空。现在 `ExplosiveCapability.detonate` 有一条不变量：**爆炸半径至少覆盖触发范围**（`max(radius, trigger_range)`，近战雷再与 `MIN_RADIUS` 取大），同时把 `potato_mine` 的 `trigger_range` 改成 0.5（僵尸真正踩进格子才炸）。数据与代码都改，是因为两者各修一半都"能玩"，但只有合起来才既是原版行为、又不会在下一份 `trigger_range > radius` 的内容上复发。


## 5. 实体与能力系统（本轮重构的核心）

### 5.1 共用实体基类

`com.pvzce.api.entity.Entity` 同时被服务端与客户端继承：

| 层 | 类 | 额外内容 |
|---|---|---|
| 共用 | `Entity` | id、defId、cellX/cellY、height、health、animation、**网格边界**、`gridX()/gridY()`、`entityKind()`、`layer()` |
| 服务端 | `PvzceEntity extends Entity` | team、removed、`tick(LevelServer)`、`saveState()/restoreState()`（对称，强制实现） |
| 服务端 | `PlantEntity` / `ZombieEntity` / `ProjectileEntity` / `ResourceDropEntity` | 能力实例列表 |
| 客户端 | `ClientEntity extends Entity` | kind、layer（来自包）、`AnimationComponent` |

`ClientEntity.from(EntitySpawnS2C)` 与 `apply(EntityUpdateS2C)` 是包→状态的**唯一**应用点；网格由两侧用同一份逻辑从 cell 派生，所以 `EntitySpawnS2C` **不再传 gridX/gridY**。

### 5.2 能力（Capability）

行为不再是实体里的字符串 switch，而是**可注册、可组合的能力对象**。

- 接口：`PlantCapability` / `ZombieCapability` / `ProjectileCapability`（`api/content/capability`）。
- 类型注册表：`BuiltInRegistries.PLANT_CAPABILITIES` 等，条目是 `CapabilityType<T>(id, MapCodec<T>)`。
- 列表元素：`TypedCapability<T>(Identifier type, T value)`，JSON 里形如 `{"type":"pvzce:shooter", ...}`。
- 每个实体构造时 `instantiate()` 出一份**实例**，状态（冷却、引信、护甲血量…）保存在实例里，因此新增一种行为不再需要给实体加字段。
- 存档：每个能力把状态写进以类型 id 为键的子标签（`capabilities: {"pvzce:shooter": {...}}`），实体基类负责遍历。

内置植物能力：`shooter` `thrower` `producer` `explosive(timed|proximity)` `melee` `boost_below` `bowl`。
内置僵尸能力：`armor` `vault` `fly` `dig` `hammer` `boss_phases`（行走/啃咬循环留在 `ZombieEntity`，所有僵尸共享）。
内置子弹能力：`linear` `arc` `splash` `status` `pierce`。

`bowl` 是唯一会让植物**离开自己格子**的能力（保龄球坚果，见 §4.9）：它顺带定义了 `PlantCapability.occupiesCell`（默认 true），`plantAt` 会跳过回答 false 的植物，所以"僵尸不啃滚动的坚果"不是啃咬循环里的特例。僵尸侧的对称物是 `ZombieCapability.onImpact(zombie, damage, level)`：给"不是子弹的撞击"（保龄球、巨人的拳头）留的护甲拦截口，与 `onProjectileHit` 分开是因为没有子弹可以描述这次命中（没有层、没有命中音效），而"护甲先吃"这条规则仍然适用——并且**先查 front 再查 top**，因为帽子（路障/铁桶）在 `onProjectileHit` 的层路由下只挡抛物线。

`behavior` 字段仍在，但**降级为可选预设**（`PlantBehaviorPresets` / `ZombieBehaviorPresets` / `ProjectileBehaviorPresets`）：显式 `capabilities` 优先，为空时才按 `behavior` 展开；预设是纯语法糖。

### 5.4 为什么 `LevelAccess` 在 `api/entity`

能力是**服务端行为**，必须能放子弹、算范围伤害、读同排僵尸、播音效。把这些操作收敛成一个只读+动作的小接口（`LevelAccess`），比让能力直接依赖 `LevelServer` 更可控；实现只有 `LevelServer` 一个。接口里的实体参数是服务端类型（`PlantEntity` 等），这是 L2→L2 的引用，不是 api→server 的方向污染。

### 5.5 放置与叠放（标签驱动）

能不能种、能不能叠，**没有任何硬编码 id 参与**，只有两张表：标签 + `PlacementDef`。

```
@c:ground / @c:plantable / @c:water / @c:unplantable   （scene_element 注册表）
@c:plantable / @c:carrier / @c:requires_ground /
@c:water_plant / @c:plant_only                          （plant 注册表）
```

**判定**：`PlantPlacement.canPlace(plant, ctx, x, y)` 是纯函数，只读上面这些标签与 `PlacementDef`：

| 植物带 | 需要 |
|---|---|
| `#c:plant_only` | 任意植物在它**下面**（咖啡豆） |
| `#c:water_plant` | 地形 `#c:water`（莲叶） |
| `#c:requires_ground` | 地形 `#c:ground` 或 `#c:plantable`（花盆、土豆雷） |
| `#c:carrier` | 地形 `#c:ground` 或 `#c:water`（载体自己先落地） |
| 其余 | 地形，或**下面**某个植物，带 `#c:plantable` |

两个关键点，都是"顺序无关"的来源：

1. **只看比自己层低的东西**（`layerIndex(other) < layerIndex(self)`）。豌豆和土豆雷都在 layer 1，谁也够不着谁，所以"雷种不进花盆""豌豆不会长在雷上"与**种植顺序无关**——旧实现里这两件事结果是相反的。
2. **互斥由 `group` 说，不由层号说**。`group` 留空＝同格可多个（咖啡豆）；普通植物默认 `plantable`（一格一个）；载体默认 `carrier`（盆上不能套盆）。

`LevelServer` 只提供 `PlantPlacement.Ctx`（该格的 `Terrain` + 自下而上的 `PlantLayer` 列表），`canPlacePlant` 一行转发；`PlantAIPlayer` 也走同一条。`SceneElementDef` **不存**能种什么（旧的 `accepts` 字段是同一套规则的第二份手写副本，已删除）；新增地形 = 加一个元素定义 + 在 `data/c/tags/scene_element/` 里打标签。

### 5.6 每帧/每 tick 的执行顺序

服务端 `LevelServer.tick`：音乐线索 → 波次 → 波次与时间同步 → 阳光掉落 → 场景（弹坑恢复/墓碑）→ `flushPending` → 植物（能力 tick）→ AI（可选）→ 僵尸（能力 tick + 移动 + 啃咬 + 死亡掉币）→ 子弹 → 资源掉落 → 移除回收 → 卡槽同步（每 20 tick 或冷却归零）→ 实体增量（每 3 tick）→ 胜负判定。

客户端 `PvzceClient.run` 每帧：`window.pollEvents` → `connection.tick()` → `pollInput` → `screen.initIfNeeded/tick` → `music.tick` → `animations.tick` → `render`（`clipping.reset()` 在帧末兜底）。

## 6. 客户端

### 6.1 状态镜像

`ClientLevel` 是服务端状态的**只读镜像**：实体表、卡槽、场景（`SceneGrid<String>`）、队伍（按 team 分别存放的资源）、波次/日夜/目标速率/断线原因。`ClientLevel.init(...)` 与 `reset()` 共用 `clearTransientState()`，所以两者不会分叉。

日夜由共享的 `DayNightCycle` 计算；客户端不再自己维护 `TimeOfDayS2C.night`。

### 6.2 GUI

- `Screen`：`init/render/tick/鼠标键盘` + **对话框栈** + **`FocusManager`（键盘焦点唯一属主）**。`onResize()` 会重建基础 widget 并把已打开的对话框按新尺寸放回（对话框不会因改窗口而消失）。
- 子类用 `modalDialog()` 取"当前最上层模态对话框"，不要自己倒序扫描 `widgets`。
- **模态输入分发是强制的**：`mouseClicked` / `mouseMoved` / `mouseScrolled` 在 `Screen` 里是 `final`，先发给模态对话框、没有再发给 widget，最后才调**界面自己的钩子** `onMouseClicked` / `onMouseMoved` / `onMouseScrolled`（逻辑 GUI 坐标）。界面要处理自己的点击区域就覆写钩子，**不要**覆写 `mouseClicked`。此前这是"子类记得先调 `super`"的约定，而 `LevelSelectScreen` 先判定了占满窗口的卡牌网格，于是"新建关卡"对话框的按钮全部点不动；现在结构上不可能再绕过。少数必须在原始像素坐标下工作的调用（游戏内相机）用 `rawMouseX/Y` 换算。
- `addWidget` / `showDialog` 会自动把 `EditBox` 接到焦点管理器；`widgets` 里消费点击的控件拿走焦点，其它情况释放焦点。
- `Clipping`：GUI 空间裁剪栈（`client.clipping().push/pop/pushPixels`），GUI→framebuffer 换算只有一份（`guiMouseX/Y` 的精确逆运算），支持嵌套求交；帧末 `reset()`。
- `SeedCardRenderer`：卡片绘制的**唯一**实现（游戏内卡槽与选卡界面共用），`CardKind` 决定底栏显示价格还是"收集"。**传送带上的卡不印价格**（`SlotInfo.NO_PRICE = -1`）：它不是"价格恰好为 0"，而是"这张卡是发给你的"，印个 0 会读成一次免费交易。
- **关卡内的卡槽条有两种形态**（`InGameScreen.renderSlots`）：普通关卡是底部一排种子卡；**传送带关卡是顶部的履带**——托盘由原版 `ConveyorBelt_backdrop.png` 九宫格成框（`NinePatch.drawNineSlice`，边框按 GUI 像素固定，不随托盘拉伸），原版 `ConveyorBelt.png` 的胎面**画在框内**（`BELT_FRAME_X/Y` 是边框厚度，也是胎面的内缩量）并持续向左滚动。**裁剪必须用胎面自己的矩形**（`beltX/beltY/beltWidth/beltHeight`）：平铺的相位不落在框边上，首尾两块会伸到胎面之外，裁到托盘就会把左右两条边框盖掉（上下两条因为胎面在内缩框里所以看不出来，这正是「上下有框、左右没有」的来源）；卡片**骑在带上**从右端滑入、向左走到队尾停住，前面的卡被用掉时后面的会跟着往前挪（位置按卡 id 记录在客户端，见 §4.9）。胎面与卡片用同一个速度常数，否则卡会像在冰上滑。卡按带上顺序排列（**不**走 `orderCardSlots` 的"资源→植物→工具"分组：队列的顺序本身就是信息），点击命中按**当前绘制位置**判定。托盘宽度按 `belt_capacity` 固定，窄窗口下缩小卡片以保证不钻到暂停按钮底下。
  > 胎面纹理只在**去掉 1 像素边框后的中段**才是每 6 像素周期的，所以平铺取的是 `u ∈ [1/502, 499/502]` 这一段：整图平铺会把一条 2 像素的接缝每几秒滚过屏幕一次。
- **关卡内取消选卡**：再点一次已经选中的那张卡就放下它（右键与点击棋盘外同样取消）。
- **拖拽放卡**：在卡槽上按下就把卡拿起来（`draggingCard`），松手时若光标在棋盘内就直接种下/使用；松手在卡槽条上则保留选中，于是「点一下再点格子」的老手势一个字节没变 —— 两条路最后都走 `spendSelectedCard`。拖动时卡片图标跟着光标画，悬停格子的高亮仍然说明会落在哪。
- **按住扫过即拾取**：在棋盘上按住左键拖动，光标扫过的阳光/金币直接收集（`onMouseDragged` → `resourceDropAt` → `CollectResourceC2S`，同一个掉落物只发一次）。一次点击只能捡一个掉落物，而草坪上常常同时躺着五颗阳光 —— 让玩家逐个瞄准是纯体力活。
> 两个手势都走 `Screen` 的 `onMouseDragged` / `onMouseReleased` 钩子（与 `onMouseClicked` 同规矩：`mouseDragged`/`mouseReleased` 在 `Screen` 里是 `final`，先给模态对话框、再给控件、最后才给界面）。选中的卡是"下一次点击要花掉的东西"，是一种必须能不进不退地离开的模式。
- `GuiText` / `GuiStatusText`：短 id、数字格式化/解析（带范围夹紧）、存档状态文案。
- `GuiLayout`：只负责按钮行高适配（`fitHeight`/`gapFor`）。
- `Screen.coverFit(...)`：cover 适配的唯一实现，返回 `CoverFit`，界面用它把"按背景图素坐标写死的面板矩形"映射成点击区域（背景怎么画、点击区就怎么算）。
- `ListEditorSupport`：关卡/音乐/卡池编辑器共用的列表编辑算法（刷新并保持选中、保留指定项、上移下移、删除后选中谁）。三份拷贝此前已经分叉（一处用交换、一处用摘除插入），同一按钮在两个编辑器里行为不同。
- `GuiLang`：`assets/<ns>/lang/<locale>.json` → 显示名。key 是 MC 的 `<namespace>.<path>`。语言文件从第一阶段就在仓库里但**没有任何代码读它**，所以列表里显示的是英文 id；现在编辑器、波次表、卡池页都走它，缺失的 key 回退到 path（不是 `namespace:path`）。
- `PaletteList`：带**贴图 + 名字**的列表行（`Kind` 决定贴图族：实体 / 场景 / 资源 / 纯色块）。此前物品列表画的是 `GuiText.shortId(id)`。
- **实体图标优先取动画资源**：`AnimationManager.iconTexture(id)` 取控制器模型里最大的部件贴图（或 flipbook 的第一帧），`PaletteList.iconFor(client, …)` 优先用它，取不到才回退 `textures/entities/<id>.png`。那张平铺 PNG 是控制器美术之前的旧测试图，画出来和游戏里完全不是一个东西 —— 编辑器的植物/僵尸页此前列的就是它。
- 配置界面：`config/ConfigScreen` 用**一次 `layoutRows()`** 同时驱动"摆滑块"和"画标签"；滑块 `onChange` 只在值真变时触发，**落盘走 `onCommit`（拖拽结束）**。

### 6.2.1 关卡选择页（`LevelSelectScreen`）

**关卡的分类就是它的 id 路径**：`levels/yard/adventure/1_1.json` 加载成
`pvzce:yard/adventure/1_1`，第一段是主题、第二段是类别、其余是关卡自己的名字。规则只有一份实现
`api/util/LevelGrouping`（纯函数），服务端分组、客户端过滤、编辑器换组都调它 —— 读取依据是
**id 而不是文件位置**，因为文件里的显式 `"id"` 优先于路径，两者可以不一致。

- 主题与类别是**数据驱动的注册表**：`level_theme` / `level_category`，目录是
  `data/<ns>/level_themes/`、`level_categories/`，文件只有 `id` + `order` 两个字段
  （**没有 name**：显示名与植物/僵尸一样走 `GuiLang` 的 `<ns>.<path>` key）。类别只声明一次、
  可被任意主题使用；某主题下出现哪些类别，由**该主题下实际存在的关卡**推出，所以加一批关卡
  不需要额外声明页签，也不会出现"打开是空的分类页"。主题顺序 = `order`，未分类页永远最后。
- id 不足两段（`demo_level`、`yard/one_off`）、或引用了未注册的主题/类别 → **未分类**页
  （`pvzce:uncategorized` 哨兵）。**未分类页是固定页**：客户端在拼页签表时永远补上它，所以左侧列永远有"未分类"按钮、也永远能在那里新建关卡 —— 从关卡里推导这一页会让它在"当前没有未分类关卡"时消失（曾经的 bug）。服务端只下发有内容的页，空页由客户端补齐。`PvzceServer.validateLevelGroups()` 在 `/reload` 时把
  "谁因为什么落到未分类"打进日志，否则症状（关卡不在我放的地方）指向不了任何东西。
- 页签表由服务端下发（`LevelTabsS2C`，与关卡列表一起发；`PROTOCOL_VERSION` 因此 = 3），
  客户端**只渲染被告知的内容**：自己从关卡列表里收集页签的实现在"服务端资源包与客户端不同"
  时会给出与关卡不一致的导航，也无法表达顺序。`LevelInfo` 带 `theme`/`category` 两个字段，
  `LevelPage` 负责"这一页有哪些关卡"（纯函数，见 `LevelPage` / `LevelSelectSelectionTest`）。
- 页面形态：**左侧主题列 + 顶部类别行 + 行列表**（一关一行，一屏 6~8 关；原来是 4×4 大卡片
  网格，一屏 4 关）。右侧仍是 `ListPaging` 翻页（箭头 + 滚轮），页码指示器在列表下方。
- `LevelCreateDialog` 的主题/类别两行按钮**预选当前正在看的页**，id 预览实时显示
  `<命名空间>:<主题>/<类别>/<名字>`；**命名空间是独立的一个输入框**（默认 `pvzce`，自由文本 +
  标识符命名空间字符校验），数据包/模组不必再被塞进内置命名空间；**未分类页保留自由 id**
  （该桶的定义就是"id 里没有主题"），手打 `namespace:` 时也仍然自由。文件路径、id 的
  "创建后只读"规则都不变。
- 编辑器信息页可**换组**，保存时 `LevelMove` 一并完成：**换 id + 移关卡文件 + 搬该关存档目录
  与通关标记**（旧的 `sourceFile` 在新文件写好之后才删，失败则整体不动）。id 是存档目录名、
  通关标记与其它关卡引用的键，所以这是**唯一**允许改 id 的操作，且是显式的，不藏在改名里。
- **冒险模式前三关按原版铺开**（`levels/yard/adventure/1_{1,2,3}.json`），草坪一行行放开、每关首通给下一关要用的卡：

  | 关卡 | 草坪 | 固定卡 / 总卡槽 | 自选 | 僵尸 | 首通奖励 |
  |---|---|---|---|---|---|
  | 1-1 | 9×1 | 豌豆射手 + 阳光卡 / 2（无可选） | — | 普通 ×5（1/2/2） | 向日葵 |
  | 1-2 | 9×3 | 豌豆射手 + 阳光卡 / 4 | 2 张：向日葵、铲子 | 普通 + **旗帜**（11 只，一大波） | 樱桃炸弹 |
  | 1-3 | 9×3 | 豌豆射手 + 阳光卡 / 5 | 3 张：向日葵、樱桃炸弹、铲子 | 普通 + **路障** + 旗帜（15 只，两波大波） | 坚果墙 |
  | 1-4 | 9×5 | 豌豆射手 + 阳光卡 + 向日葵 + 坚果墙 / 8 | 4 张（自由练习） | 普通 + 路障 + 铁桶 + 旗帜 | 手套 |
  | 1-5 | 9×5 | **传送带**（无卡组、无阳光） | — | 约 228 只（11 波，开局 6 秒出怪，普通/旗帜/路障 + 后段铁桶） | 土豆地雷 |

  三关都是初始阳光 50、`sun_spawn_chance 0.0017`（约 10s 一颗自然阳光）、重复通关 100 金币、掉银币。**1-1 固定整套卡组**（`max_seed_slots = slots.size()`），选卡页放完预览自动开始；1-2/1-3 留出空槽，背包第一次真正说话（自选池 = 已解锁卡 − 固定卡），选卡页因此不再自动开始。1-3 的自选三张正好凑成原版的"三株植物 + 铲子"。1-4 是铺满五行的自由练习关。`LevelValidator` 把"固定卡占满卡槽"当**提示**而不是错误报出来，因为那正是 1-1 想要的形状。原来的 `level_1`（9×5、整份卡池、巨人）已删除。

   **1-5 是第一种小游戏关卡**：卡槽条是**顶部的滚动履带**（`conveyor`），天上不掉阳光、初始阳光 0、没有阳光卡，只能种在左四列（`placement_zone`），种下的坚果永远向前滚、撞到僵尸就被弹进相邻车道（植物 `pvzce:bowling_nut` + 能力 `pvzce:bowl`），首通解锁土豆地雷，音乐是原版 n-5 的 `loon_boon`。它**不经过选卡界面**（从关卡准备直接开局）。机关细节见 §4.9。
- **1-2/1-3 需要的新僵尸**：`flag_zombie`（旗帜）与 `conehead_zombie`（路障，护甲 370 —— 原版数值，铁桶是 1100）。两者都是 `Zombie.reanim` 这一个主文件的**配件筛选**结果（`ZOMBIE_FLAG_EXCLUDE` / `ZOMBIE_CONE_EXCLUDE`），不需要新美术。
- **旧存档不迁移**：id 从 `pvzce:level_1` 变成 `pvzce:yard/adventure/level_1`，存档目录名
  （`levelKey` = `ns + "__" + path.replace('/','_')`）随之变化，旧目录留在磁盘上不再被读取 ——
  这是"分类改了、进度从头开始"的既定取舍，不是丢失。

### 6.2.2 开场对话（`DialogueOverlay`）

关卡可以有一段**开局对话**：数据是关卡 JSON 的 `dialogue` 块（每行 = 角色 / 立绘 / 台词 / 语音 /
左或右）加一个 `dialogue_character` 注册表（显示名、立绘目录、大小、气泡贴图），所以**加一个新角色
不用改代码**。运行时的唯一实现是 `client/gui/components/DialogueOverlay`：立绘贴说话那一侧的屏幕
下沿，气泡用 `box_left`/`box_right` 单图九宫格画在对侧（尾巴落在左下/右下那 56×24 的角里，改贴图时
别把尾巴挪出角外），台词按气泡内宽逐字换行、**逐字打出**（打字机），左键推进、ESC 跳过整段。

- **它是一个 `Dialog`（modal）**，不是新机制：`Screen` 把鼠标 / 键盘 / 滚轮事件先给最上层模态对话框，
  所以"对话期间选卡与按钮点不动"是结构上成立的，不需要在每个宿主界面里各写一份输入闸门。
- **排版跟角色走，不跟屏幕走**：立绘占窗口高度的 90%（×角色 `scale`）、贴下沿，气泡按**台词自身**的宽度收窄
  （短句就是一个小气泡），底边固定在窗口高度 70% 处（说话人的下巴高度），行数多了就向上长；气泡里台词右下角
  有一行小字「点击继续」（`pvzce.dialogue.click_continue`）。气泡靠角色的那一侧锚在**立绘宽度的 80%** 处
  （`BUBBLE_PORTRAIT_ANCHOR_RATIO`）而不是贴图边缘：立绘是整幅带透明边距的图，锚在贴图边缘会在角色和气泡之间
  留出一大块空白。立绘在左时气泡在右，反之亦然；两者都在 `DialogueOverlay` 的常量里，要调只改那几个数。
  换行后如果最后一行只剩一个字，会把上一行最后一个字挪下来（`avoidOrphans`）——"…僵尸的世 / 界" 是对的换行，
  但不好看。台词字号上限 1.35（随窗口高度增长），气泡内边距也在同一组常量里。
- **打字机**：每秒 28 字（`TYPEWRITER_CHARS_PER_SECOND`），句末标点额外停 0.18s、句内标点 0.09s
  （`pauseAfter`），所以读起来像说话而不是电传打字机。揭示进度**由墙钟推导**（`lineStartNanos` +
  `revealedCharacters`），不是每帧累加，掉帧不会让台词变慢。**气泡按整句排版、只画已打出的前缀**
  （`typedPrefix`），所以打字过程中气泡不会忽大忽小；「点击继续」小字只在整句打完后才出现——打字途中
  那一下点击的语义是"补全整句"，写"继续"会骗人。
- **两个宿主**，取决于这一局怎么进的：走**选卡界面**的关卡在 `ChooseSeedsScreen` 里播——对话期间镜头
  停在最左（房子一侧），草坪与僵尸预览照常渲染，对话结束后才走原本的"横摇 → 木牌滑入 → 选卡 / 自动开始"
  时间线（`panStartNanos`，无对话时就是原来的 `startNanos`）；**传送带关卡**这类没有选卡界面的直接进
  `InGameScreen`，对话在草坪上播，`entryNanos`（"准备… 安放… 种植！"横幅）推迟到对话结束，
  期间发 `PauseGameC2S(true)` 冻住关卡、结束时恢复。
- **触发条件是"新开一局"**，不是"第一次玩"：选卡界面只在没有存档时打开（`enterLevelFromMenu`），
  所以它自己就能判定；直接进关卡的那条路（传送带、编辑器测试、暂停菜单重开）由 `PvzceClient` 用
  `directDialogueLevelId` 把"这一局是新开的"带过关卡初始化的往返。继续一局存档不播，通关后再玩会再播。
- 客户端从**本地数据包**读对话（与 `usesConveyorBelt` / `lockedSlotsFor` 同一层），所以没有新包、
  没有 `PROTOCOL_VERSION` 变化。
- 校验：`LevelValidator.validateDialogue` 报未知角色 / 拼错的 `side` / 空台词 / 非法立绘名（加载时随
  其它关卡问题一起打），`validateDialogueAssets` 在 `/reload` 时按 `PvzceResourceManager.hasTexture`
  报缺失的立绘与气泡贴图（`[PVZCE/对话]`）。立绘名必须是**文件名**：`Identifier` 的 path 允许 `/`，
  不过滤的话 `../别人的角色/smile` 会解析出本角色目录之外。
- 编辑器有独立的**「对话」页**（列表 + 角色/立绘两个选择器 + 台词/语音/左右），保存时只覆盖
  `dialogue.lines`，块内其它字段（以后的 `trigger` 之类）原样保留；台词框每帧提交进模型，所以
  换行、点别的台词或直接按保存都不会丢掉刚打的那句。

### 6.2.3 关卡编辑器（`EditorScreen`）

一页一个主题，导航栏切换：**地形 / 植物 / 僵尸 / 规则 / 波次 / 卡池 / 音乐 / 信息**。前三个共用左侧内容面板 + 中间画布 + 右侧操作面板；其余页把中间与右侧合成一块面板。

- **画布走游戏自己的世界投影**（`beginOverlayWorldView` + `SceneTileRenderer.render` + `AnimationManager.render`），不是 GUI 空间的一堆 quad。所以预设植物/僵尸**播的是游戏内动画**，格子形状也和游戏内一致 —— 画布的落点来自同一份 `LevelStage.board(canvasW, canvasH, columns, rows)`，而 `cellAtCursor()` 是它的精确逆运算。旧实现的精灵是静止贴图，且格子被拉伸到填满画布。
- 预览实体在 `syncCanvasEntities()` 里建 `ClientEntity` 并**手动 `attachAnimationManager`**：动画管理器平时由 `ClientLevel` 在 spawn 时注入，编辑器不走 spawn 包，不接就没有动画。`releaseCanvasAnimations()` 在每次重建与退出时释放 playback（与选卡预览同一个泄漏点）。
- **规则页对注册表生成**：遍历 `GAME_RULES`，布尔 → 开关按钮，数值 → 滑块 **+ 数值输入框**（滑块表达不了 0..12000 的 tick）。滑块范围来自 `RULE_RANGES`，与 `BuiltInRegistries.registerGameRules` 的注册值对应；只写被改过的规则，其余留空以继承默认值，列表上标"已改"。
- **波次页**：**表格 + 详情同屏**，占满整宽（`fullContentArea()`）。左表：一波一行（序号 / 类型 / 间隔 / 预警 / 僵尸组成 / 合计）；右栏：选中波次的类型 / 间隔 / 预警 / 数量，加「组成」与「可选僵尸」两个列表；底部：新增/删除/上移/下移/自动填充/末波倍率。**没有二级菜单** —— 这套界面原本在独立的整屏 `WaveEditorScreen` 里，现已移入本页，那个类只剩下数据与 JSON（`WaveEditorModel`）。
- **音乐页**：同样是**时间线 + 详情同屏**、占满整宽。左：cue 列表（tick / 轨道 / 事件）；右：tick / 音量 / 淡入、轨道 / 循环 / 停止、事件选择（点选即应用，读 `SOUND_EVENTS` 里所有 `music/` 条目）。也没有二级菜单 —— 原本是 `MusicEditorDialog`，现只剩 `MusicEditorModel`。
- **底部动作栏只剩「保存 / 测试 / 返回」**。此前还挂着「编辑波次」和「音乐」两个入口，与导航栏的同名页重复；一个目标两个入口，正是那两个页面长期半成品的原因（真正的编辑在二级菜单里）。
- **卡池页**：**两列**——左边是本关卡的卡（顺序即游戏内卡槽顺序），右边是全部卡（按 kind 分「植物·资源·工具」三段，带分段标题）。按钮排在列表**下方的独立两行**里，不压列表；右列里本关已选的卡带一个右对齐的「已选」角标。
- **卡槽规则只有一条**：**关卡列出的卡就是固定的**（进入关卡必发、选卡界面不能取消），**总卡槽数减去关卡卡数就是玩家自选的空间**。没有 per-card 的 fixed 开关，也没有 `seed_selection` 这种第二份"哪些是可选"的声明 —— 位置即语义。`LevelDef.seedPlan(allCards)` 是这条规则的唯一实现：`lockedSlots` = 关卡的卡（按顺序、去重），`pickableSlots` = 全部卡减去已固定的，`maxSlots` = 总卡槽数。
- `max_seed_slots` 在 `LevelDef` 的规范构造器里**自动抬到不小于关卡卡数**：关卡列了 13 张却声明 6 个卡槽，只可能是数据写错，截断会静默丢掉作者自己的设计。所有旧关卡都是"整份卡池 + 默认 6"，于是它们全部变成**固定卡组** —— 这正是"关卡选了就是固定"套用到已有数据上的结果。`LevelValidator.validateSeedSelection` 会把"关卡卡数 ≥ 总卡槽数（玩家没有可选）"和"卡池引用未知卡"报出来。
- 服务端 `sanitizeSeedSelection` 先放关卡的卡、再按提交顺序补玩家的选择直到总卡槽满；不认识的卡与重复卡丢弃。选卡界面对固定卡画挂锁角标、点击无效、"清空"只清玩家自己选的。客户端绕不过这些 —— 服务端会重新算一遍。
- 想给玩家留选择空间：关卡卡数 < 总卡槽数即可（编辑器卡池页顶部实时显示「总卡槽 / 关卡固定 / 玩家可选」三个数）。
- **信息页**：关卡名称、描述、初始阳光、**奖励**（首通解锁卡 / 重复通关金币 / 僵尸掉币概率 / 每次掉币数量）；关卡 ID **只读**（创建后不可改，存档、卡池、其它关卡都引用它）。奖励块**整块由编辑器写出**（它只有四个字段），手写的多条 `first_clear` 会在保存时被规范化成"至多一张卡 + 一条金币"。
- **保存**：`buildLevelJson(previous, ...)` 从**载入时的 JSON** 出发，只覆盖编辑器拥有的字段，所以 teams、`env_vars`、其它工具写的元数据、更新版本新增的字段都不会因为"编辑了一下"而消失。写入路径优先回写**载入时那个文件**（`sourceFile`），内置关卡才落到 `datapacks/user_levels/`。
- **新建流程**：`LevelSelectScreen` 的「新建关卡」→ `LevelCreateDialog`（主题 / 类别 / 名称 / id / 尺寸）→ 编辑器；id 与名称从此分离，主题/类别默认取**当前正在看的页**，id 预览实时拼成 `pvzce:<主题>/<类别>/<名字>`。列表下方的「编辑关卡」按钮把**选中的关卡**送进编辑器 —— 此前入口是写死 `openEditor("custom_level")`，所以每点一次都在编辑同一关，存成别的名字那份永远打不开。
- **「测试」与「从列表打开」走同一条路**：编辑器的测试按钮原先直接发 `RequestLevelC2S`（＝让服务端开局），于是跳过了选卡界面，同一个关卡从列表打开却要选卡。现在测试按钮只保存，然后交给 `PvzceClient.testEditedLevel`：它等**服务端重载后的关卡列表**再打开选卡界面 —— 必须等，否则选卡界面描述的是保存前的那份定义。`/reload` 命令因此会主动补发一次关卡列表（`PvzceServer.refreshLevelList`），客户端不必猜重载要多久。
- **列表分页**：左右箭头与滚轮都是**翻页**，不是滚动。算法抽到 `client/gui/layout/ListPaging`（纯函数，可单测）：首页行号永远是页大小的倍数，末页夹到 `(pageCount-1)*pageSize`，页数**向上取整**（最后一页只装残余行，可能不满）。`ListPagingTest.everyRowIsReachableOnExactlyOnePage` 对全部"行数 × 页大小"组合断言**每一行恰好出现在一页上** —— 它同时挡住两类翻页 bug：页数向下取整会让尾部若干行**没有页**（18 关 4 列 4 行可见时是 5 行，页数 floor(5/4)=1，指示器写"1/1"、两个箭头全灰、第 5 行永远看不到），而按 `totalRows - pageSize` 夹取会让相邻两页**重复同一行**（13 关 4 列 2 行可见时页曾是 0-1、2-3、3-4）。不重复靠"末页也从页边界开始"，不靠砍掉末页。
- 底部动作栏是**四个**按钮：下一步 / 编辑关卡 / **背包** / 返回；右上角是**本世界的金币**（`drawCoinCounter`，`money_bag` 贴图，缺图回退金币贴图）。
- 「返回」走 `LevelSelectScreen.goBack()`：栈里还有上一屏就 `closeScreen()`，否则 `showWorldSelect()`。通关后客户端是用 `showLevelList()` **整体替换**屏幕栈的，此时栈里只有这一屏，直接用 `closeScreen()`（它拒绝弹出最后一屏）会让按钮**完全失效**；ESC 也走同一条路。
- 列表里选中一张卡会**同时**点亮「下一步」和「编辑关卡」（`updateActionButtons`）。此前只有「下一步」被点亮，所以在列表里选自己的关卡后「编辑关卡」永远是灰的；现在这个按钮还会按选中关卡改名（进行中 → 「继续游戏」，见 §4.3）。
- **选中的是关卡本身，不是格子**：`LevelSelectScreen` 记住选中关卡的 **id**，每次列表刷新（换世界、`/reload`、编辑器存档）后按 id 重新解析行号（`indexOfLevel`，纯函数）。旧实现只存下标，刷新后同一个下标可能指向另一关，于是"高亮的卡"和"按钮作用到的关卡"不一致。

### 6.3 渲染

- `RenderSystem`：极薄的 GL 门面（混合/深度、投影、纹理缓存绑定、时令光照 uniform、**世界空间点光源** `setPointLight`：上限 `ShaderProgram.MAX_POINT_LIGHTS`，着色器里按半径做 `smoothstep` 叠加）。
  **只有阳光是光源**（`PvzceClient.lightsTheBoard`，按**内容 id** `pvzce:sun` 判定；白天暖黄、夜里偏冷）。这里踩过一次坑：判定原本写的是 `kind().equals("sun")`，而 `EntityKind.RESOURCE` 的值**就是** `"sun"` —— 于是**每一种掉落物**（金币、钻石、能量豆）都被当作太阳，落地就在草坪上投一圈黄光。**实体 kind 是类别（plant/zombie/projectile/resource），永远不是内容 id**：`EntityKind.RESOURCE` 已改为 `"resource"`（kind 字符串走 `EntitySpawnS2C`，故 `PROTOCOL_VERSION` = 10），`EntityLightTest` 同时钉住「只有阳光亮」与「kind 不等于任何内容 id」。
- `SpriteRenderer`：`textured` / `texturedQuad` / `solid` / `shadow` / `projectedShadow`（投影阴影是真梯形，远边有纵向跨度）。
- `PvzceCamera`：把格子坐标映射到背景图上的草坪。**`inBoard` 接收的是 GLFW 原始自上而下的鼠标 Y，内部会翻转**；与 `worldX/worldY`、`screenX/screenY` 同一坐标系语义。
- `EntityTextures`：内容 id → 纹理 id 的唯一换算（保留命名空间）。**转发给 `EntityArt.sprite`**，因为路径不再能从 id 推出来：内置美术按类目分层（`textures/entities/plant/attacker/pea_shooter/`），所以定义里用 `texture` 字段显式声明；没声明的（mod 的常规写法）仍然按 id 推。
- `EntityArt`（`common/core`）：**"这个内容 id 用哪份美术"的唯一答案**，两个问题一次查表 —— 播哪个**动画文件**（`animationFile`，读定义里的 `animation_dir`，缺省回落到 id 路径）与没有动画时画哪张**兜底贴图**（`sprite`，资源注册表里的资源另外回落到它自己的 `icon`）。渲染器、编辑器图标、选卡图标与 `AnimationManager` 都从这里取。
- `EntityVisuals`：每类实体的视觉常量（脚→动画锚点抬升、贴图兜底尺寸/偏移、渲染层、排序桶）唯一来源。新增实体种类只改这一张表。
- `LevelStage` / `SceneTileRenderer` / `FontRenderer`：背景舞台、场景瓦片、位图字体。

#### 6.3.1 液体渲染（`client/renderer/liquid/`）

场景元素带 `liquid` 字段时不再走贴图，改由一个**独立的水面 pass** 绘制。它不是第二套精灵管线，而是"几何一次批量、图案全在 shader 里"的一条通道：

| 类 | 职责 |
|---|---|
| `LiquidDef`（`api/content`） | 渲染参数的**唯一载体**：色板、不透明度、深度尺度、泡沫、波形、焦散、高光、静态帧数。`data/<ns>/liquids/*.json` |
| `LiquidGeometry` | 纯函数几何：8 连通 BFS 求**离岸距离**（深度场），外加每格四边/四角的接壤掩码。可单测，不需要 GL |
| `LiquidBatch` | 每格两个三角形，一次 `glDrawArrays`；VAO/VBO 建一次复用 |
| `LiquidShader` | `#version 150 core` 独立 program + 自带 attrib 绑定（0..3） |
| `LiquidRipples` | 固定 16 槽环形缓冲，满了丢**最旧**（新溅的水花才是玩家在看的） |
| `LiquidTextures` | 场景元素 id → 液体定义的唯一解析点（带缓存，`/reload` 时清） |
| `LiquidRenderer` | uniform 上传、画质档 → 特征位、关闭 shader 时的烘焙帧降级 |

**顶点属性**：在共享的 `POSITION(3)+COLOR(4)+UV(2)` 后**追加** `LIQUID(4)`（共 13 float），所以现有所有绘制路径一行未改。`aLiquid` 打包为：格坐标（+1 使符号可承载"该侧是否有岸"）、接壤掩码、角落掩码、深度（3 bit）。**注意坐标轴是反的**：north 标志在 x、掩码的 north 在 y，详见 `LiquidVertexFormat` 的注释。

**着色器次序**（顺序即正确性，改一处要想清楚）：
底图（按**世界格坐标**连续平铺，不是每格重开）→ 水色吸收（`opacity` 是"水占多少"而不是 alpha）→ 焦散网 → 日光高光 → 菲涅尔 → 泡沫与临陆内缩 → 昼夜色调。
**水体不透明**，只有临陆边缘羽化；内部格之间不软化，否则会在湖心露出接缝。

**画质档**（`config/pvzce-client.toml` 的 `water_quality`，视频设置可切）只切特征位与采样量，**不切几何**，所以三档的水面形状完全一致。`shaders_enabled=false` 时整条 pass 换成 `textures/scene/water_frames/water_*.png`（`tools/gen_water_frames.py` 生成，由 `static_frames` 决定帧数并循环）。

**涟漪**：服务端 `LevelServer.emitRipple*` 是唯一权威点（僵尸入水已接入），经 `EffectEventS2C` 的 `ripple`/`ripple_strength` 字段下发，客户端按液体 id 解析后入槽。涟漪是纯表现，走墙钟而不是 tick，所以暂停时水面照常流动。

### 6.4 动画

- `AnimationManager`：playback 表 + 文件缓存。`play()` 的幂等判据是**当前活动 clip**（循环 clip 在播则不动；已结束的一次性 clip 允许重开），不是 `requestedState`。
- `AnimationPlayback`：共用的时间/过渡/事件/生命周期；两个后端 `FlipbookPlayback`（帧序列）与 `ControllerPlayback`（骨骼控制器）。
- `Timeline`：**唯一的时间线数学**（循环 wrap、非循环夹紧、帧查找、延迟默认值）。新增采样方式请走它。
- `AnimationResourceLoader`：clip 公共字段（`loop/on_end/next/transition`）与"animations 条目必须是对象"的校验都只有一份。
- 缓存：文件存在但解析失败与文件不存在**分开记录**；`invalidate()` 在资源重载时清空两者（否则一个坏关键帧会永久禁用该动画）。

### 6.5 声音与粒子

- `SoundEngine`（OpenAL）：事件表来自 `assets/pvzce/sounds.json`；音高有统一夹紧范围。**音频源在重新绑定 buffer 之前一律先 `alSourceStop`**：源是 16 个一组的环形缓冲，6 秒的大波提示占用的那个源马上会被下一个音效重用，而 `AL_LOOPING` 是**源的属性、不是 buffer 的属性** —— 一个被要求循环过的源会把之后绑上来的任何 buffer 一直循环下去，这正是"某个一次性音效变成无限循环"的物理来源。`play()` 另有两道保护：同一事件 130ms 内的重复被折叠（齐射不会糊成电流声），以及**一个事件在自己的声音播完之前再次请求会被丢弃而不是叠加**（`nextSource` 返回 -1）—— 上游把同一个事件每帧发几百次时，玩家听到的仍然只是那一个声音，而不是环形缓冲绕圈循环。两道保护都不是"哪些音效只能播一次"的白名单（会公告自己的音效换过一次，白名单也得跟着换）。`-Dpvzce.traceSounds=true` 会按秒打印实际播放的事件计数，用于诊断这类问题。
- `PvzceMusicController`：菜单/关卡/静音轨与淡入淡出；`ensureMenu(track)` 在**同曲已播时不重启**（界面 `init()` 会在每次改窗口大小时重跑）。
- `PvzceMusicController.ensureMenu(event)` 的语义是**"同曲不重启，异曲要换"**：它曾被写成"菜单轨空闲才播"，于是奖励页的 `zen_garden`（菜单轨）会一直压着关卡列表 —— 关卡列表请求 `choose_your_seeds` 时发现轨道忙，什么都不做。改回"异曲即切"后，菜单之间的交接（奖励页 → 关卡列表 → 选卡页）才真正换曲，而窗口缩放反复调 `init()` 依旧不会重头播。
- **音乐属于"一局"**：轨道名（`menu`/`background`/`battle`/`stinger`）以 `MusicEventS2C.TRACK_*` 为唯一定义（关卡数据与客户端控制器共用同一批字面量）。关卡时间线在波次处把背景轨换成战斗轨，而**只有"离开关卡"这条路会停乐**（`clearLevelClientState()` → `music.leaveLevel()`）；从存档提示框重开、编辑器「测试」都不经过 leave，于是上一局的战斗轨会继续循环、压在新一局的轨道下面（表现为音乐重叠）。所以**每个新关卡实例**由服务端在 `LevelInitS2C` **之前**补发三条 `MusicEventS2C.reset(track)`（`PvzceServer.silenceClientLevelMusic()`）——顺序有意义：init 才是启动新轨道的那一步。**同一实例的 resync 不发重置**（它的音乐就是当前状态，`startLevel` 的"同曲不重启"也因此得以保留）。
- `ParticleEngine.tick(seconds)`：**按时间步进**（不是按帧），单帧步长上限 0.1s；寿命以 60tps 的 tick 授权、内部按秒积分。

#### 6.5.1 粒子（数据驱动）

粒子曾经是 `ParticleEngine` 里对效果名的一个 `switch`，只能画**纯色方块** —— 原版那 81 张粒子贴图与 112 个 emitter 脚本一张也用不上。现在：

| 位置 | 职责 |
|---|---|
| `ParticleDef`（`api/content`） | 定义载体，**JSON 是扁平的而 record 是嵌套的**：`look`（贴图/帧序列/寿命/缩放/自旋/透明度曲线/颜色）与 `motion`（速度/角度/重力/阻力/落地），另加 `additive`、`count`、`count_spread`。`data/<ns>/particles/<类目>/*.json` |
| `PvzceParticles`（`common`） | 内置能力默认引用的效果 id。**与 `PvzceSounds` 同形**：此前这些 id 是散落在能力里的字符串字面量，而未知 id 只在客户端每秒报一次日志，症状（"这个效果不见了"）指向不了任何地方 |
| `ParticleEngine`（`client/particle`） | 世界空间贴图粒子：帧动画、旋转 quad、**加法混合**两趟批处理（普通粒子先画、发光粒子后画，整帧最多切两次混合状态） |
| `RenderSystem.blendAdditive/blendNormal` | 加法混合。原版的光晕就是加法画的，用普通 alpha 画出来是一块盖住底下东西的实心圆盘（金币光晕当年因此被整个砍掉） |

- **未定义的效果不画东西**，只按 id 报一次日志（曾经会给每个未知名字画一个红方块，让拼错看起来像个真效果）。
- **曲线表**：`alpha_curve` / `scale_curve` 是 `[[时间, 值], ...]`，时间已归一化到 0..1。直线淡出由 `alpha_from`/`alpha_to` 两个端点表达，只有真正弯曲的（先胀后消的烟、脉冲的光）才带表 —— 这也是转换器 `tools/particles_to_pvzce.py` 的判断依据。
- **单位**：距离是世界格、时间是秒。转换器按 60fps、80 像素/格换算原版的「每帧像素」（330 px/frame 的抛射速度 → 247 格/秒），文件头记录了全部换算因子。
- **贴图来源有三处**：`refer/im7/particles`（粒子贴图）、`refer/anim`（emitter 引用的 reanim 部件，如僵尸帽子）、`refer/im7/images`（零散图，如泥土、水花）。转换器按名字归一化（忽略大小写与下划线）在三处查找，并把结果拷成小写文件名 —— `Identifier` 的 path 只允许小写，而原版文件名是驼峰。
- **精灵表切分**：原版用 `<ImageFrames>`/`<ImageRow>`/`<ImageCol>` 把一格里横排的多帧画在一张 PNG 上，本渲染器一帧一张贴图，所以转换器在生成时把它切开（8 帧 × 2 行的 `dirtsmall` 就是这样变成 `dirtsmall_1..8` 的）。

## 8. 约定（避免重新长出重复实现）

以下每一条都对应一处**曾经存在两份以上实现并已经分叉**的地方。改相关逻辑时请顺着这条改，不要新开一份：

1. 颜色/音效/队伍/规则的 id → `PvzceSounds` / `PvzceIds`。
2. 数值常量（tick 率、默认棋盘、初始阳光、卡片冷却…）→ `PvzceConstants`；每秒↔每 tick 换算是 `PvzceConstants.TICKS_PER_SECOND`，不要写 `60`。
3. 关卡访问 → `LevelAccess`（不要新开接口）。
4. 植物创建 → `LevelServer.spawnPlant`（不要 `new PlantEntity`）。
5. 卡槽解析 → `SlotResolver`。
6. 内容 id → 纹素/纹理 → `EntityTextures`；实体视觉常量 → `EntityVisuals`。
7. GUI 裁剪 → `Clipping`；GUI 焦点 → `FocusManager`；卡片绘制 → `SeedCardRenderer`；文本/数字 → `GuiText`。
8. 时间线数学 → `Timeline`；日夜 → `DayNightCycle`；缓动/插值 → `MathUtil`（`easeInOut` 只有这一份：`ChooseSeedsScreen` 的私有副本已改为转发）。
9. 包字段声明 → `PacketStruct`；集合序列化 → `PacketByteBuf` helper。
10. 路径拼接 → `PackPaths`；注册表目录表 → `CONTENT_REGISTRIES`；注册表分类 → `PvzceRegistries.byCategory()`；**关卡存档目录键 → `LevelKey.of`**（客户端镜像在 `LevelMove.saveKeyAfterMove`，两处必须同步改）。
11. 实体存档 → `saveState/restoreState`（成对实现，不要只写一半）。
12. 关卡数据校验 → `LevelValidator`（新增检查项加在这里，不要散落到构造函数里抛异常）。
13. 编辑器列表操作 → `ListEditorSupport`；背景 cover 适配 → `Screen.coverFit`；命令分类/补全 → `PvzceRegistries.byCategory()`（不要新写 switch）。
13b. 界面自己的鼠标/滚轮判定 → `Screen.onMouseClicked` / `onMouseMoved` / `onMouseScrolled`（**不要**覆写 `mouseClicked`，它是 `final`，模态分发靠它保证）。
14. 场景元素是否液体 → `LiquidTextures.liquidFor`（**读元素定义的 `liquid` 字段**，不要按贴图是否存在判断）；液体参数 → `LiquidDef`；水面绘制 → `LiquidTextures.renderWorld` / `renderGuiBoard`（游戏内与选卡预览共用同一实现，只有一个投影参数不同）。
15. 能不能种 → `PlantPlacement.canPlace`（**纯函数，只读 `#c:` 标签与 `PlacementDef`**）。不要在别处再写一份判定：`LevelServer.canPlacePlant` 只是把关卡适配成 `PlantPlacement.Ctx`，`PlantAIPlayer` 也调它。瓦片能种什么**不再写进场景元素定义**（旧的 `accepts` 字段已删除），要加地形就在 `data/c/tags/scene_element/` 里打标签。
16. 堆叠层与互斥 → `PlacementDef` 的 `layer`/`count`/`group`（载体 `layer 0`、地面植物 `1`、植物上的植物 `2`；`group` 留空＝同格可多个）。判定只看**比自己层低**的东西，所以种植顺序不影响结果。
17. 关卡属于哪一页 → `LevelGrouping`（**纯函数，只读 id 路径**）。不要在别处再写一份：服务端 `PvzceServer.groupOf`、客户端 `LevelPage`、编辑器的换组都调它；页签顺序与名单由服务端 `LevelTabs` 从注册表推出发给客户端。
18. 卡是否被背包锁住 → `SlotResolver.requiresUnlock`（服务端 `PlayerProfile.owns` 与客户端 `ClientProfile.owns` 都调它）；选卡池 → `SeedOptions.cardPool`（**唯一一份**，"客户端看得到"与"服务端收得下"靠它对齐）。关卡固定卡**永远不过滤**。
19. 玩家档案（金币 / 已解锁卡）→ `PlayerProfile` + `PvzceServer.profileFor/saveProfile`（缓存按世界名，换世界前先 `flushProfile()`）。不要在别处再读一次 `profile.dat`，也不要在关停钩子里写文件。
20. 通关发什么 → 关卡 `rewards` 块 + `PvzceServer.awardProfile`（首通/重复/掉币的**唯一**结算点）；新增奖励类型要同时改 `LevelRewards` 与 `LevelValidator.validateRewards`。金币掉落只经 `LevelAccess.zombieDied`，实体不读关卡奖励数据。
21. 内容 id → 用哪份美术 → `EntityArt`（动画文件与兜底贴图两个问题一次查表）。不要在渲染器/编辑器/选卡里各拼一次路径：内置美术按类目分层后，路径已经不能从 id 推出来。
22. 命中反馈/特效的粒子 id → `PvzceParticles`（与 `PvzceSounds` 同形）。未定义的效果**不画东西**，只按 id 报一次日志，所以拼错不会伪装成"一个难看的红方块"。
24. 「这一格能不能放」的规则只有 `PlantPlacement` 一份；工具点击可否执行由 `LevelServer.applyToolEffect` 返回布尔值表示，**被拒绝的点击不消耗使用次数也不进冷却**。移动植物走 `spawnPlant` + `restoreStateWithoutPosition`：位置由新格子决定，状态（血量、年龄、能力）跟着走 —— 直接 `restoreState` 会把坐标一起写回去，等于没搬。
25. 关卡能不能进 → `LevelUnlocks.evaluate`（**纯函数**，`Context` 里只有已通关/已购买/背包/金币/沙盒）。服务端求值、客户端收结论（`UnlockInfo`），不要在界面里判断；入口门槛在 `PvzceServer.createLevel` 重新求值一次，不要只信列表。购买价只从关卡定义读，永远不信客户端。
26. 实体归类 → 美术目录（`textures/entities/<类目>/…`）与动画目录（`animation_dir`）用**同一套类目**，分类表只有一份：`tools/group_entity_assets.py` 的 `ENTITIES`，以及重新生成美术时 `tools/reanim_to_pvzce_all.py` 的 `EntityConfig.group`。**内容 id 永远不带类目** —— 改目录不会让关卡、标签、存档或语言 key 失效。
27. 实体类别 → `EntityKind` 的四个常量，**它们是类别不是内容 id**：判断「这是不是某个具体资源/植物」一律比内容 id（`defIdString()` / `PvzceIds`），不要比 kind —— `EntityKind.RESOURCE` 曾经的值就是 `"sun"`，于是「是不是阳光」这个问题对金币也回答「是」（见 §6.3 的世界点光源）。
28. 捡起一个资源放什么效果 → `ResourceDef.pickup_effect`（可缺省＝不放）。不要在收集代码里按资源分类写分支：阳光与硬币不是同一种拾取，共用一份粒子参数必然有一边是错的。
29. 传送带的产出/容量/消耗/存档 → `ConveyorBelt`（服务端唯一实现）；卡槽条是它的**投影**（`rebuildBeltSlots`），不要在别处再维护一份"带上有哪些卡"。
30. "这一格能不能种"的第二半（**关卡允许的范围**）→ 关卡 `placement_zone` + `LevelServer.canPlacePlant`。不要写进地形标签：红线是画在普通草地上的，改地形会把草坪一起改掉。客户端画线/悬停从 `LevelPayload` 的同一条矩形读。
31. 爆炸的范围与触发 → `ExplosiveCapability.detonate` 的**不变量"爆炸半径 ≥ 触发范围"**。新写 proximity 内容时 `trigger_range > radius` 不再是"打不中"的静默 bug（`ExplosiveCapability` 会取大），但数据仍应写成想要的值。
32. 植物是否占格（僵尸能否啃、工具能否取）→ `PlantCapability.occupiesCell` + `LevelServer.plantAt`。不要在僵尸的啃咬循环或工具里判断具体植物 id。

## 9. 已知缺口与预留接口

按规划文档仍待补齐（**不是**本轮重构遗留）：

- **联机**：`TcpPacketTransport` 已修好语义但未接线；缺握手、`server.properties`、玩家身份/Team 占位、断线重连与 delta 重放。
- **注册表同步**：客户端目前依赖本地资源/数据包自行解析注册表；联机时应改为服务端按注册表下发定义（`PvzceDataLoader.RegistryData` 预留了"哪个注册表需要同步"的位置，但目前只有目录名与 codec 两个字段）。
- **客户端资源同步**：客户端自己解析资源/数据包（`PvzceClient.run` 里另建了一个 `PvzceResourceManager`），联机时应改为服务端下发。
- **渲染**：`RenderSystem` 无矩阵栈、无批合并；每个 quad 都会创建/销毁 VAO+VBO（`FontRenderer` 每个字形一次）；深度测试关闭，层级完全依赖提交顺序与 z 常量。
- **动画**：`AnimationHandle` 的返回值在调用点被丢弃；骨骼混合/Spine 未接入。
- **GUI**：`Dialog` 的内容区未扣除九宫格边框高度（`NinePatch.DIALOG_TOP/BOTTOM`），因此大对话框的按钮会跨到边框上。编辑器已不再把主要编辑面放进对话框（波次改成整屏、卡池/音乐改成页），但 `MusicEditorDialog` 仍是对话框，且它和 `LevelSaveDialog` 一样受这条影响。
- **关卡分类**：未分类页是**固定页**（`LevelPage.tabs` 永远补上它，客户端左侧列因此永远有"未分类"按钮）——服务端只下发有内容的页，空页由客户端补齐；`LevelValidator` 尚未校验"关卡 id 的两段像主题/类别但未注册"（目前只有 `PvzceServer.validateLevelGroups` 在重载时记日志）。
- **编辑器**：画布只支持地形/预设实体；`EditorScreen` 与 `WaveEditorScreen` 都还靠 `palette.selected()` 每帧回读选中项（列表没有选中变化事件）。关卡只写进 `datapacks/user_levels`，没有"另存为"（改名要新建一关）。**编辑器不认识 `conveyor` 与 `placement_zone`**：它只覆盖自己拥有的字段（`buildLevelJson` 从载入的 JSON 出发），所以手写的这两块不会被保存动作删掉，但也没有 UI 去编辑它们——小游戏关卡目前是手写数据。
- **AI**：只有植物方的基础策略，没有规划器/难度档位；僵尸方无出怪策略器（`WaveGenerator` 未实现）。
- **金币没有消费去处**：钱包、掉币、通关结算、结算页都做了，但**还没有商店**（Crazy Dave 的商店/图鉴都没做）。金币目前只是进度展示，这是有意的阶段性取舍。
- **僵尸方没有背包**：`PlayerProfile` 只记录植物/工具；"僵尸也一张张解锁"要等僵尸方能被玩家操作（对战模式）时才有意义。
- **背包只有一页**：`InventoryScreen` 是只读网格，没有图鉴详情、没有排序/筛选；卡片顺序就是注册表顺序。
- **编辑器只编辑一个首通解锁**：`rewards.first_clear` 手写多条时，编辑器只认第一条并在保存时把其余规范化掉（会打一行日志）。
- **水面**：深度是**每格**量化（8 连通步数，6 bit 里占 3 bit），所以 5 行关卡的深浅只有两三档、交界是矩形台阶；要根治需在 `LiquidGeometry` 里把深度场双线性上采样成逐像素值。编辑器画布（`EditorScreen.renderCanvasBlock`）仍是自己画，未走 `LiquidTextures`，所以编辑器里的水是旧观感。`tools/preview_water.py` 是 shader 的 CPU 镜像，靠人工同步常量 —— 已有测试保证 shader 可编译与 uniform 齐全，但**参数**仍需人工保持一致。
- **音乐状态不随存档回放**：客户端只按"进入关卡"播默认曲（`startLevel` 的 default）并接收之后的 cue；服务端恢复存档时 `NextMusicCueIndex` 已越过的那条 cue（例如波次处切战斗轨）不会补发，所以续一局打到一半的关卡会先听到默认曲。要根治得让服务端按轨道记录"当前曲目"并在 `sendFullState` 里重发（重发同曲在客户端是幂等的，正是 `startLevel` 的同曲不重启要保护的语义）。
- **种植反馈**：`PlantPlacement` 是纯函数，但客户端还没有用它做悬停预览——悬停只画一个绿方块，能不能种要等服务端拒绝才知道（规划文档 2.2.1 要的"绿=可种、红=不可种"）。要做的话得把 `PlantPlacement` 的 `Ctx` 从"传 `PlantDef` 对象"改成"传 id 自取注册表"，因为 `ClientEntity` 只拿得到 defId。
- **测试**：`@PvzceGametest` 注册式集成测试与渲染冒烟（离屏 FBO + 图 diff）未建；当前为 JUnit 单测/集成测试 360 例。已知 `SaveSystemTest.continueRestoresZombiesOnField` 偶发失败（保存/恢复的时序假设偏紧），单独跑必过，与本轮改动无关。界面靠截图人工核对：

  ```
  ./gradlew :pvzce-game:run -Ppvzce.smoke="pvzce.smokeEditor=pvzce:yard/adventure/demo_level \
      pvzce.smokeEditorPage=rule pvzce.smokeFrames=150 pvzce.captureFrame=140 \
      pvzce.capturePath=/tmp/editor.png"
  ```

  `pvzce.smoke*` 由 `run` 任务转发进游戏 JVM（Gradle 的 `-D` 只到 daemon，进不了 fork 的 JavaExec）。可用项：

  | 属性 | 作用 |
  |---|---|
  | `smokeEditor=<关卡 id>` | 打开编辑器的某个关卡 |
  | `smokeNewEditor=<新 id>` | 走"新建关卡"路径 |
  | `smokeEditorPage=<页 key>` | 切到某页（terrain/plant/zombie/rule/wave/cards/music/info） |
  | `smokeWaveEditor` | 在编辑器上叠开波次表格 |
  | `smokePlace=<kind=id@x,y;…>` | 在画布上放预设实体（先放置后保存） |
  | `smokeSave` | 保存一次（验证写入往返） |
  | `smokeScreen=levels\|create\|mods\|settings\|console\|inventory\|award\|award_money` | 直接打开某个界面（`inventory` 是背包，`award`/`award_money` 用合成奖励包渲染结算页的两个分支） |
  | `smokeTab=<主题>/<类别>` | 关卡列表直接翻开某一页（`levels` 默认停在第 0 页，其余页签不点开就没法截图） |
  | `smokeCommands=<cmd>\|<cmd>` | 关卡起来后按真命令路径执行控制台命令（`/spawn`、`/resource`…），用于摆出需要特定场面的截图。**命令里的空格写成 `+`** —— `pvzce.smoke` 本身按空白切分，直接写空格会被截断到第一个参数 |
  | `smokeReward=unlock\|money` | 在 `smokeLevel` 开的关卡里合成一次通关奖励：奖励落到草坪上、可点击、领完进结算页（替代"植物方获胜 + `LevelRewardS2C`"两个包，那两个包本身有单测） |
  | `smokeClick=<guiX,guiY>` / `smokeClickLabel=<按钮文字>` | 模拟点击（后者按标签找对话框按钮，不受窗口尺寸影响） |
  | `smokeDragTo=<guiX,guiY>` + `smokeDragFrame=<帧>` | 从 `smokeClick` 的按下点拖到这个 GUI 点再松手（拖动放卡 / 扫过拾取都靠它，单点点击测不出来） |
  | `-Ppvzce.gameDir=<目录>`（Gradle 属性，不是 `pvzce.smoke*`） | 覆盖存档/配置目录（默认 `~/.pvzce`）。**截图冒烟请务必带上**，否则会把这一次运行写进开发者真正的游戏目录 |

  写出的 PNG 方向正确（`capture()` 只翻一次行）。

  > 注意：本仓库导出的截图经查看工具预览时会呈现 180° 旋转（文字上下颠倒 + 左右镜像），核对画面时先旋转 180°。`capture()` 本身只做一次竖直翻转，写出的 PNG 与 framebuffer 一致。
