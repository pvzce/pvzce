# PVZCE 架构总览与开发路线

> 项目：PVZCE（PvZ 社区版）——以 PvZ 玩法为核心、与 Minecraft 代码设计同构的游戏框架。
> 本文档为四份开发文档的总纲：`00`（本文）、`01`（第一阶段·核心底层）、`02`（第二阶段·广度开发）、`03`（第三阶段·精修完善）。

---

## 0.1 项目定位

PVZCE 是一个**独立运行的桌面游戏**（不是 Minecraft 模组），同时具备与 Minecraft 相似的三层扩展能力：

| 扩展形态 | 与 MC 的对应 | 说明 |
|---|---|---|
| **模组（Mod）** | Fabric 模组 | 含代码的游戏扩展，通过自研（fork 自 Fabric Loader 的）模组加载器加载 |
| **资源包（Resource Pack）** | MC 资源包 | 覆盖纹理、音效、语言、动画等表现资源，`assets/<ns>/...` 目录约定 |
| **数据包（Data Pack）** | MC 数据包 | 数据驱动注册内容（植物、僵尸、子弹、卡槽、关卡、游戏规则……），`data/<ns>/...` 目录约定 |

核心设计原则：**标识符、资源路径、JSON 数据格式、注册表机制、客户端/服务端分离、tick 循环等一切机制"尽量与 MC 相同"**；渲染底层为 LWJGL，抽象层对齐 `com.mojang.blaze3d` 与 `net.minecraft.client.renderer` 的结构。

### 与常规 MC 模组开发的关键差异

- 游戏本体与加载器**打包为同一个可执行 jar**（shadow/fat jar）。
- 游戏时钟为 **60 tick/s**（MC 为 20），全部逻辑时序按 60tps 设计。
- 每个关卡内存在**多 Team、多玩家**（PlantTeam / ZombieTeam），Team 共享资源、独立显示、独立掉落。
- 关卡内实体为**网格制**（默认 5×9），不是 MC 的自由三维世界；叠加（场景元素/植物）规则自成一系。

## 0.2 已确认的技术决策（问答结论汇总）

以下决策已在规划阶段与项目所有者确认，是全部文档的约束条件：

| # | 决策项 | 结论 |
|---|---|---|
| D1 | 模组加载器 | **不另写**。直接 fork 整个 [Fabric Loader](../refer/fabric-loader/) 源码，裁剪 Minecraft 专属部分后改造，**以 shadow 方式打包进游戏本体** |
| D2 | 包名 | **不重定位**，保留 `net.fabricmc.*` 原包名（游戏自包含、无环境冲突） |
| D3 | 游戏内置 API | **自研 `com.pvzce.api`**（仅参考 Fabric API 的事件/生命周期/网络设计，不复制源码、不提供 `net.fabricmc.fabric.*`） |
| D4 | Cloth Config / ModMenu / GeckoLib | 第二阶段按用户修订：**不保留原包名**，在 `com.pvzce.*` 自研必要子集（GeckoLib 后置） |
| D5 | mod 开发环境 | **无需 remap/混淆**：第三方 mod = 普通 Gradle 工程 + 依赖 `pvzce-game`（API 面）与 `pvzce-loader` 两个 jar，无需 Loom |
| D6 | 画面形态 | **3D 渲染引擎 + 锁定侧视相机**（PvZ2 风格）；第二阶段实际交付 sprite 后端，Spine/GeckoLib/方块后端接口预留 |
| D7 | 网络架构 | 参考 MC 的**服务器/客户端分离**：单机 = 集成服务器（同进程双线程）；多客户端联机第一阶段仅要求"能连"，网络协议骨架在第一阶段建好，细节后续阶段打磨 |
| D8 | 存档 | **NBT**，对齐 MC（`level.dat` 风格 + `data/` 目录分类），NBT 结构自研、API 对齐 [net/minecraft/nbt](../refer/decompiled-26.1.2-client/net/minecraft/nbt/) |
| D9 | 数据文件格式 | **与 MC 完全对齐**：`pack.mcmeta`、`assets/<ns>/`、`data/<ns>/`、Identifier（`namespace:path`）、Codec（DFU）驱动的 JSON 注册表、tags |
| D10 | 配置文件 | 第二阶段使用 **Cloth Config API**（fork 版）；第一阶段配置功能整体后置，TOML 库（toml4j）留待第二阶段接入 |
| D11 | 数值基准 | 默认内容数值表取**原版 PvZ1 近似平衡值**，第三阶段做校准（见 03 文档） |
| D12 | Java 版本 | **Java 21**（LTS，与 MC 1.20.5+ 同代）；构建 Gradle 8.x |
| D13 | 第一阶段范围 | 最小可玩 demo（窗口 + 渲染管线 + 双注册表 + 最小关卡 + 1 植物 + 1 僵尸 + 子弹 + 种植消耗 + 胜负） |
| D14 | GUI 框架 | **第二阶段**（仿 MC Screen/Widget）；第一阶段只做最小交互（种子卡槽 + 鼠标拖拽） |
| D15 | 第三阶段重点 | **玩法平衡与新手体验、联机与 AI 打磨**；性能/特效/社区工具链排入第四阶段 |

## 0.3 术语表

| 术语 | 定义 |
|---|---|
| tick | 游戏逻辑最小时间单位；PVZCE 固定 **60 tick/s**，服务端循环执行 |
| 注册表 / Registry | 类型化 ID→对象表；分**静态**（代码注册）与**动态**（数据包注册，关卡主要由动态注册承担） |
| 关卡 / Level | 一局游戏；含场景大小、场景元素、团队、规则、环境变量、出怪配置 |
| Team | 关卡内的阵营（PlantTeam / ZombieTeam / System）；Team 共享资源，非本 Team 不能操作其实体 |
| 玩家 / Player | 真人或 AI；每个至少两人的 Team 若无真人则由 AI 玩家代管 |
| 场景元素 / SceneElement | 占据 1×1 格子的地形类元素（草地/裸地/水池/平直屋顶/倾斜屋顶/墓碑/弹坑…），有叠放规则 |
| 卡槽 / Slot | 资源卡 / 植物卡 / 工具卡三类；是玩家可拖放的操作入口 |
| 资源 / Resource | 阳光、红石、能量豆等；有对应资源卡才可收集 |
| 环境变量 | 关卡作用域的 KV 数据通道，任意组件可读写、关卡 JSON 可注入 |
| 游戏规则 / GameRule | 可注册的关卡级规则（如白昼长度、阳光概率、弹坑恢复时间），关卡可启用/禁用/设值 |
| 实体 / Entity | 植物、僵尸、子弹；均为服务端权威逻辑对象 |
| 动画状态 | 服务端仲裁、客户机播放的具名动画事件（idle/attack/death…） |
| 模组 / Mod | `fabric.mod.json` + 代码 + 附带资源/数据包的 jar；加载器 fork 自 Fabric Loader |
| 资源包/数据包 | 仅含资源与数据的覆盖包，无代码 |
| Identifier | `namespace:path` 标识符，规则与 MC 相同（只允许小写字母、数字、`_`、`-`、`.`、`/`） |

## 0.4 总体架构

### 0.4.1 分层

```
┌────────────────────────────────────────────────────────────────────────┐
│ L4 平台入口   KnotClient / KnotServer（fork 自 fabric-loader）          │
│               PvzceGameProvider（替换 MinecraftGameProvider）           │
├────────────────────────────────────────────────────────────────────────┤
│ L3 表现层     client: RenderSystem/BufferBuilder/TextureManager        │
│               精灵/Spine/GeckoLib/方块 后端 · GUI(Screen/Widget)        │
│               特效/粒子 · 声音 · ModMenu/Cloth 界面                     │
├────────────────────────────────────────────────────────────────────────┤
│ L2 内容层     Plant/Zombie/Projectile/Resource/Slot/Tool/SceneElement   │
│               Level/Team/GameRule/EnvVar/AnimationState/关卡编辑器      │
│               （绝大多数内容由动态注册表提供，含内容 JSON 定义）          │
├────────────────────────────────────────────────────────────────────────┤
│ L1 框架层     Registry(静态/动态) · Identifier · Codec(DFU) · NBT       │
│               ResourceManager(资源包/数据包加载) · 事件总线             │
│               Network(Payload 注册 + 收发) · Tick(60tps) · 存档 · 命令  │
├────────────────────────────────────────────────────────────────────────┤
│ L0 平台层     net.fabricmc.loader（fork）· com.pvzce.api（自研）         │
│               me.shedaniel.clothconfig2（fork）· com.terraformersmc.modmenu（fork）│
│               com.geckolib（fork）· com.mojang.datafixerupper（依赖）    │
│               底层库：LWJGL(glfw/openal/opengl) · Gson · SLF4J/Log4j    │
└────────────────────────────────────────────────────────────────────────┘
```

**模块耦合规则**：L0/L1（common）不依赖 L2 具体内容；L2 只依赖 L1 与 API；L3 只依赖 L1/L2 的注册表与状态；L4 只做装配。渲染 API（`com.pvzce.client.api.*`）对服务端完全不可见。

### 0.4.2 运行时拓扑（单机 = 集成服务器）

```
┌─ 进程 ───────────────────────────────────────────────────────┐
│ 主线程(Client)：窗口/输入/渲染循环（帧率不限，与 tick 解耦）    │
│    │ 网卡抽象（MemoryConnection 仅第一阶段实现）              │
│ 服务线程(Server)：PvzceServer.tick() @60tps                   │
│    │                                                          │
│ 共享内存通道：ServerMessageQueue → ClientMessageQueue          │
│ 存档/配置：~/.pvzce/saves/<world>/ ；mods/ ；config/           │
└──────────────────────────────────────────────────────────────┘
```

联机模式（后续阶段）：客户端进程 + 独立服务进程（同协议、同 `com.pvzce.api.network` 通道），因此**第一阶段就必须按"包交换"方式编写所有状态同步**，而不是直接方法调用。

### 0.4.3 代码包结构

**游戏本体（`com.pvzce.*`）**

```
com.pvzce.launcher        —— 入口：Knot 装配（游戏与加载器同 jar）
com.pvzce.api             —— 公开给 mod 的稳定 API（注册表、事件、关卡、网络、内容构建器）
com.pvzce.common          —— 服务端/客户端共享：Identifier、Registry、Codec、NBT、资源加载、实体基类、内容定义 record
com.pvzce.server          —— PvzceServer、Level、Team、tick 循环、AI、存档
com.pvzce.client          —— 窗口、RenderSystem/BufferBuilder/TextureManager、精灵渲染、GUI、音效、输入
com.pvzce.client.api      —— 客户端渲染扩展点（模型/纹理/动画后端注册）
```

**fork 保留包名**：`net.fabricmc.loader.*`、`net.fabricmc.api.*`（Loader 本体）。`me.shedaniel.clothconfig2.*`、`com.terraformersmc.modmenu.*`、`com.geckolib.*` 待第二阶段 fork 时同样保留原名。

## 0.5 构建与分发

### 0.5.1 Gradle 工程结构

单仓库、多模块（`settings.gradle` 参考 [fabric-loader/settings.gradle](../refer/fabric-loader/settings.gradle) 与 [geckolib/settings.gradle.kts](../refer/geckolib/settings.gradle.kts) 的多模块拆分习惯）：

```
pvzce-root/
├─ settings.gradle
├─ gradle.properties          # java/toolchain、lwjgl、dfu 版本
├─ pvzce-loader/              # ← fork 自 refer/fabric-loader（裁剪后）
├─ pvzce-api/                 # ← 自研 com.pvzce.api（设计参考 refer/fabric-api，不含其源码）
├─ pvzce-game/                # 本体：common+server+client，shadow 打 fat jar
│   └─ src/main/java/com/pvzce/...
├─ pvzce-mod-template/        # 第三方 mod 开发模板（无 remap、普通 gradle）
└─ docs/                      # 本套文档
```

### 0.5.2 打包（shadow）

`pvzce-game` 使用 Gradle `com.gradleup.shadow`（或 fabric-loader 同样用的 shadow 配置，见 [fabric-loader/build.gradle](../refer/fabric-loader/build.gradle)）把所有依赖合并为：

```
dist/pvzce-<version>.jar        # 可执行：java -jar pvzce-xxx.jar
```

合并规则：
- `net.fabricmc.*`（loader + api）→ 本体 jar，不 relocate；
- `me.shedaniel.*`、`com.terraformersmc.*`、`com.geckolib.*` → 本体 jar，不 relocate；
- `com.mojang.*`（datafixerupper、brigadier、serialization、blaze3d 相关**需自己重写**，见 0.6）→ 仅 DFU/brigadier 等纯库保留；
- 排除各 fork 项目的 `fabric.mod.json`（本体的 mod 元数据由 `pvzce-loader` 作为"内置模组"提供，机制见 01 文档 1.3 节）。

### 0.5.3 Maven 发布与 mod 开发

PVZCE 发布到本地/远程 Maven：

```
com.pvzce:pvzce-game:<ver>    # API 面（com.pvzce.api + 公开 common 类）
com.pvzce:pvzce-loader:<ver>  # 提供 net.fabricmc.loader/net.fabricmc.api 类
```

第三方 mod 的 `build.gradle`（无需 remap、无需 Loom，对应决策 D5）：

```gradle
plugins { id 'java' }
repositories { maven { url 'https://maven.pvzce.dev/releases' } mavenCentral() }
dependencies {
    implementation 'com.pvzce:pvzce-game:1.0.0'      // API 面
    implementation 'com.pvzce:pvzce-loader:1.0.0'    // 加载器 API（编译用）
    implementation 'com.pvzce:pvzce-api:1.0.0'       // 自研 com.pvzce.api 的 API 面
}
jar {
    from('src/main/resources')  // fabric.mod.json + assets/ + data/
}
```

运行 mod 的方式：放入游戏目录 `mods/`（与 MC 一致）。
