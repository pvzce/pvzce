# 关卡机制注册表 + 拼装式编辑器 · 设计方案

> 状态：**阶段 1–4 全部实施完成**（编辑器页面已全部独立成类，见 §9.6/§9.7）。
> 目标（已确认）：**关卡类型可注册**（编辑器据此实现不同关卡功能）、**编辑器页面拼装化**（几个参数构造一个新页）、**关卡 JSON 拼装化**（内存 codec 组合，磁盘仍是单文件）。
> 已确认的六条决策见 §0；文末 §8 是已拍板的小项，§9 记录实际落地时的偏差与文件位置。

## 0. 已确认的决策

| # | 决策 | 含义 |
|---|---|---|
| 1 | **可组合的机制列表** | 关卡声明 `"mechanics": [ ... ]`；机制可叠加，不是互斥的关卡类型枚举 |
| 2 | **七个层面全都要** | 数据 codec、服务端模拟、存档、网络、客户端表现与流程、编辑器页面、校验 |
| 3 | **页面注册表 + 声明式字段表** | 页面可注册；页内由字段描述符声明，通用渲染器画控件 |
| 4 | **只做内存 codec 拼装** | 磁盘上仍是一关一个 `.json`，不做文件级 `$ref` / include |
| 5 | **隐式默认 deck** | 关卡不写"卡槽来源"机制时自动套普通卡组；1-5 显式写 `pvzce:conveyor` |
| 6 | **旧键废弃** | `conveyor` / `placement_zone` 两个顶层键移入 `mechanics` 块，不再兼容 |

推进方式：**先出方案（本文件），你确认后再分阶段实现**。验证强度按 `验证约定.md`：默认按需，不要求每阶段全量测试 + 截图；本文件各阶段末尾记的"测试全绿（N 例）+ 截图清单"是当时的交付记录，不是今后每轮的验收条件。

## 1. 现在的问题（本方案要消掉的东西）

1. **`belt != null` 是一个散落的服务端分支**：出现在关卡构造、`syncSlots`、`placePlantInternal`、`PvzceServer.createLevel`、`save/restore` 五处。它是全项目唯一"卡槽条不是 `Slot` 列表"的路径，任何新卡槽来源（矿车、传送带变体、僵尸方发卡）都要再抄一遍这五处。
2. **客户端同一个事实有两个来源**：`ClientLevel.conveyor()`（服务端下发，决定画哪条卡槽条）与 `PvzceClient.usesConveyorBelt()`（读本地关卡定义，决定开哪屏）。这是有意的（前者是服务端状态、后者只决定界面），但两处都在比 `hasConveyor()`，加入第三种卡槽来源时会变成四份判断。
3. **关卡的两块小游戏数据是"半机制"**：`LevelDef` 里 `Optional<LevelBelt> belt` 与 `PlacementZone placementZone` 是具名字段，`LevelTail` 已经为了绕开 DFU 16 字段上限把字段分块——加第三、第四个机制时，这个 record 只会继续膨胀。
4. **`LevelPayload` 同时写死了两个机制的字段**（`conveyor`、`beltCapacity`、zone 四个 int）；`PROTOCOL_VERSION` 已经到 10。
5. **编辑器不认识这两个机制**：`EditorScreen`（3404 行）用私有 `enum Page`（10 页）+ `PAGES` 数组驱动导航栏，三处 `switch (page)`（建控件 / 渲染 / 输入）分发，页面状态是类里的散装成员；`conveyor` 与 `placement_zone` 完全没有 UI，所以做一个小游戏关卡目前只能手写 JSON。
6. **`buildLevelJson` 有 4 个重载**：每加一个"编辑器拥有的块"（rewards → unlock → dialogue）就多一个转发重载，参数表已经 17 个参数。

## 2. 总体设计

### 2.1 关卡机制（`LevelMechanic`）

一个新注册表 `level_mechanic`，条目 = 机制定义对象（**数据 + 服务端 + 校验 + 编辑器字段**），客户端表现另注册（见 §2.5，理由同项目分层）。

```java
// api/content/mechanic/LevelMechanic.java —— 纯数据面，不引用 server/client
public interface LevelMechanic<D extends LevelMechanic.Data> {
    MapCodec<D> codec();                       // 机制的 JSON 块（无数据块时用 MapCodec.unit(EMPTY)）
    D defaults();                              // 块缺省时的数据
    default boolean cardSource() { return false; }   // true = 互斥的"卡槽来源"机制
    default List<String> validate(LevelDef def, D data) { return List.of(); }
    default List<FieldSpec> editorFields() { return List.of(); }   // 空 = 该机制暂无可视化编辑

    // —— 服务端钩子（默认空实现，需要哪个覆写哪个）——
    default Optional<CardSource> cardSource(LevelServer level, D data) { return Optional.empty(); }
    default void onLevelCreated(LevelServer level, D data) {}
    default void tick(LevelServer level, D data) {}
    default boolean canPlacePlant(LevelServer level, D data, PlantDef def, int x, int y) { return true; }
    default void collectSave(LevelServer level, D data, CompoundTag root) {}
    default void applySave(LevelServer level, D data, CompoundTag root) {}

    // —— 网络（写读只声明一次，两侧共用同一个 codec，杜绝漂移）——
    default PacketStruct.Codec<D> payloadCodec() { return null; }
}
```

- 注册表放 `BuiltInRegistries.LEVEL_MECHANICS`（代码注册，同 `PLANT_CAPABILITIES` 的做法），键加在 `PvzceRegistries`；它不是数据包注册表，所以 `PvzceDataLoader.REGISTRIES` **不需要**新条目。
- JSON 里的列表元素是**扁平**的，与能力 JSON 同形（复用 `TypedCapability.codec(...)` 的 `partialDispatch("type", ...)` 写法）：

```jsonc
"mechanics": [
  { "type": "pvzce:conveyor", "interval_ticks": 150, "capacity": 6, "initial_cards": 2,
    "cards": [ { "id": "pvzce:bowling_nut", "weight": 1 } ] },
  { "type": "pvzce:placement_zone", "min_x": 0, "max_x": 3 }
]
```

- `LevelDef` 增加 `List<TypedMechanic> mechanics`（`TypedMechanic(Identifier type, Data value)`），从 `LevelTail` 里**移除** `belt` 与 `placementZone` 两个字段并换成 `mechanics`（`LevelTail` 8 → 7 个字段）。这就是"JSON 拼装"的落点：**每个机制只管自己的 `MapCodec`，`LevelDef` 只负责把它们的块拼成一个数组**，加机制不再改 `LevelDef` 的字段表。

### 2.2 两类机制：卡槽来源（互斥）与通用机制（可叠加）

- **卡槽来源机制**（`cardSource() == true`）：`pvzce:deck`（隐式默认）与 `pvzce:conveyor`。**至多一个**，校验报错（"两个卡槽来源，卡槽条该听谁的"）。
- **通用机制**：`pvzce:placement_zone`、`pvzce:mower`（割草机，**隐式默认每行一辆**），以及将来的出怪策略、特殊胜负条件等，可任意叠加。

`deck` 是**标记型**机制（无数据块）：卡组的实际数据仍是顶层 `slots` / `max_seed_slots` / `initial_sun` / `unlock_resources`——它们是"默认卡槽来源"的数据，也是编辑器卡池页与 `SeedOptions` 一直在读的字段，搬进机制块会把所有数据包与选卡逻辑一起搅动，收益为零。这个不对称是有意的，会写进文档。
判定统一收成一个入口：`LevelDef.cardSource()`（显式声明的卡槽来源机制，否则 `pvzce:deck`）。

### 2.3 服务端：`CardSource` 收敛（消掉 `belt != null`）

```java
// server/level/cardsource/CardSource.java
public interface CardSource {
    List<Slot> slots();
    void tick(Random random);
    boolean spend(ServerBridge bridge, Slot slot);   // 扣阳光+冷却 or 从带上取走
    String barKind();                                // 给客户端/调试："deck" / "conveyor"
    CompoundTag save();
    void restore(CompoundTag tag);
    boolean changed();
    void clearChanged();
}
```

- `DeckCardSource`：现有普通路径（`PvzcePlayer.createPlantPlayer` + `Slot.tick()` + `team.consume` + `startCooldown` + `SlotSyncS2C` + `SeedSelection` 存档）。
- `BeltCardSource`：包装现有 `ConveyorBelt`（队列与时钟不动），卡槽条是它的投影，消耗走 `take(id)`，同步走整表包，存档走 `Belt` 块。
- 效果：`LevelServer` 的 5 处 belt 分支 → 0 处；`placePlantInternal` 只剩"取出卡 → 交给 `cardSource.spend`"；`PvzceServer.createLevel` 的 `def.hasConveyor() ? List.of() : sanitize(...)` 变成"卡槽来源是不是 deck"这一个问题（仍然问一次，但问的是机制）。
- `LevelServer.conveyorBelt()` 这类泄漏内部结构的访问器删除（`MiniGameTest` 改为通过机制/`CardSource` 断言）。

### 2.4 网络：机制的通用通道

- `LevelPayload` 去掉写死的 `conveyor` / `beltCapacity` / `zone*`，改为：

```java
List<TypedMechanicPayload> mechanics;   // { Identifier type; byte[] data }，data 由机制自己的 payloadCodec 编解码
```

  仍提供 `zoneMinX..` 的**转发 getter**（从机制数据里读），这样 `InGameScreen` 的红线、`ClientLevel.inPlacementZone` 不用立刻改；等阶段 4 客户端表现钩子落地后再删。
- 新增 `MechanicSyncS2C(Identifier type, byte[] payload)` 作为机制的增量包通道：`BeltSyncS2C` 的内容变成 `pvzce:conveyor` 机制的 payload。好处是**协议表不再随机制增长**，第三方 mod 也能给自己的机制推状态（`PvzceNetworking` 目前是空壳，这是它第一个真实用途）。机制内部仍必须用 `PacketStruct` / `PacketByteBuf` helper 声明字段（仓库纪律第 9 条）。
- `PROTOCOL_VERSION` 10 → 11；`PacketProtocolTest.samplePackets()` 增加新包与新 payload 样本。

### 2.5 客户端：表现与流程按机制注册

客户端不能从 `common` 反向依赖，所以表现面是**按 id 关联的第二张注册表**（`client/mechanic/ClientMechanic`，在 `ClientModInitializer` 入口点注册；内置三个机制在客户端 bootstrap 时成对注册，一个方法里三行，肉眼看得到它们是一件事）：

```java
public interface ClientMechanic<D> {
    Identifier id();
    default void onLevelInit(ClientLevel level, D data) {}
    default CardBarRenderer cardBar() { return null; }        // null = 默认种子卡槽条
    default WorldOverlay worldOverlay() { return null; }      // 红线这类世界层绘制
    default boolean skipsSeedChooser() { return false; }      // 开局走哪屏
    default List<EditorPage> editorPages() { return List.of(); }  // 见 §2.6
}
```

同时把 `InGameScreen` 里已经写好的两套卡槽条抽成组件（这是纯搬运，行为不变）：

```
client/gui/hud/cardbar/CardBarRenderer.java   接口：layout / render / hitTest / tick
client/gui/hud/cardbar/SeedCardBar.java       现有 renderSlots()（底部种子卡槽）
client/gui/hud/cardbar/BeltCardBar.java       现有 renderBelt() + advanceBeltCards() + updateBeltLayout()
```

`InGameScreen` 只保留"问当前卡槽来源要一个 renderer"这一行；`PvzceClient.usesConveyorBelt()` 改为问机制的 `skipsSeedChooser()`（仍读本地定义，语义不变）。

### 2.6 编辑器：页面注册表 + 声明式字段表

```
client/gui/editor/EditorPage.java        页面接口：id / labelKey / order / visibleFor(def) / build / render / input
client/gui/editor/EditorPageRegistry.java 页面注册表（内置页 + 机制页，mod 可注册）
client/gui/editor/FormPage.java          由 List<FieldSpec> 自动生成的通用页（用户要的"几个参数造一个页"）
client/gui/editor/FieldWidgets.java      FieldSpec → 控件 的唯一工厂
```

- **`FieldSpec`（纯数据，放 `api/content/mechanic/FieldSpec.java`）**：`Text` / `MultilineText` / `Int`（min/max/step）/ `Float` / `Bool` / `Choice` / `Ref`（带注册表作用域的 id 引用 + 补全）/ `List`（子字段 + 增删上下移，复用 `ListEditorSupport`）/ `Map`（键值表）/ `Json`（逃生舱：编辑器不建模、原样保留的块）。每个字段带：JSON 路径、i18n key、默认值、`removeWhenEmpty`（复刻现在"空 unlock / 空 dialogue 就删块"的语义）。
- **页面可见性由机制决定**：卡池页 `visibleFor = 有 deck 机制`，传送带页由 `pvzce:conveyor` 提供；于是 1-5 在编辑器里看不到"卡池"、多出"传送带"。这正是"在编辑器中实现不同关卡功能"。
- **机制页自动生成**：`LevelMechanic.editorFields()` 交给 `FormPage` 即可得到一个"能编辑机制的 JSON 块"的页面——注册一个机制就同时得到数据、服务端行为、校验与编辑页。表达力不足时退化到手写 `Json` 字段或专用页（如场景画布）。
- **`LevelJsonDraft`（纯函数，`common/core/`，可单测）**：从载入的 `JsonObject` 出发，页面声明自己**拥有哪些 JSON 路径**，保存时只覆盖这些路径，其余原样保留（含 `removeWhenEmpty` 的删块规则）。它一次性取代 `buildLevelJson` 的 4 个重载与 17 个参数，并保持既有契约：**不认识的新字段、别的工具写的元数据、teams 都不会因为"编辑了一下"消失**。现有 `EditorLevelJsonTest` 的断言按新 API 重写为**等价性用例**（同一份输入，新旧两条路径产出同一 JSON）。

### 2.7 七层钩子的落点一览

| 层 | 落点 | 现状对应物 |
|---|---|---|
| 数据 | `LevelMechanic.codec()` + `LevelDef.mechanics` | `Optional<LevelBelt>` / `PlacementZone` 具名字段 |
| 服务端 | `onLevelCreated` / `tick` / `canPlacePlant` / `cardSource` | `belt != null` 五处分支 |
| 存档 | `collectSave` / `applySave` | `level.dat` 的 `Belt` 块 |
| 网络 | `payloadCodec` + `MechanicSyncS2C` | `LevelPayload` 写死字段 + `BeltSyncS2C` |
| 客户端 | `ClientMechanic`（卡槽条 / 世界层 / 开局流程） | `ClientLevel.conveyor()` + `InGameScreen` 内的两套卡槽条 |
| 编辑器 | `editorFields()` → `FormPage` | 无（只能手写 JSON） |
| 校验 | `LevelMechanic.validate` + `LevelValidator` 汇总 | `validateSeedSelection` 的 belt 分支 + `validatePlacementZone` |

## 3. 内置机制的迁移映射

| 机制 id | 数据（JSON 块） | 层 | 备注 |
|---|---|---|---|
| `pvzce:deck` | 无（用顶层 `slots`/`max_seed_slots`/`initial_sun`/`unlock_resources`） | 卡槽来源 | 隐式默认；显式写出仅用于编辑器页可见性与将来做变体 |
| `pvzce:conveyor` | 现 `LevelBelt`：`interval_ticks`/`capacity`/`initial_cards`/`cards[{id,weight}]` | 卡槽来源 + 网络 + 存档 | 复用 `ConveyorBelt` 本体，不重写队列逻辑 |
| `pvzce:placement_zone` | 现 `PlacementZone`：`min_x`/`max_x`/`min_y`/`max_y` | 通用 | `LevelServer.canPlacePlant` 的判定点不变，改成遍历机制 |

**植物行为（`pvzce:bowl` 能力）不进入机制系统**：它是内容层（`PlantCapability`），普通关卡给坚果墙挂上同一个能力就能玩保龄球玩法。这一点要在文档里写清，否则"机制"会被当成"小游戏 = 机制"的同义词。

## 4. 数据迁移

**1-1 ~ 1-4**：JSON 不变（不写 `mechanics`，隐式 deck）。`slots` / `initial_sun` / `sun_spawn_chance` 全部保持原样。
**1-5**：

```diff
-  "conveyor": { "interval_ticks": 150, "capacity": 6, "initial_cards": 2, "cards": [ ... ] },
-  "placement_zone": { "min_x": 0, "max_x": 3 },
+  "mechanics": [
+    { "type": "pvzce:conveyor", "interval_ticks": 150, "capacity": 6, "initial_cards": 2,
+      "cards": [ { "id": "pvzce:bowling_nut", "weight": 1 } ] },
+    { "type": "pvzce:placement_zone", "min_x": 0, "max_x": 3 }
+  ],
   "slots": [],
```

**旧键如何处理**：`LevelDef.CODEC` 不再认识 `conveyor` / `placement_zone`，出现即报错。倾向**在 loader 层让它解析失败并给出可操作的错误消息**（"`conveyor` 已移入 `mechanics`，应为 …"），而不是静默忽略——静默忽略的产物是"一个没有传送带的传送带关卡"，症状指向不了任何东西。这一条见 §8 待确认。

`slots: []` 仍要写：`slots` 的 codec 默认值是内置卡池，省略会让一个传送带关卡同时带着一份卡组（校验会报"两个卡槽来源"）。

## 6. 风险与取舍

1. **接口面很宽**：机制的 7 层钩子如果一次性铺满，会出现一个"什么都能干"的大接口。控制手段：全部 default 空实现，只有真正需要的机制覆写；客户端表现是独立注册表，不进 `LevelMechanic`。
2. **协议与存档再次变更**：`PROTOCOL_VERSION` 11、`LevelPayload` 结构变化、`BeltSyncS2C` 变成机制 payload。项目未发布，按既定取舍接受；`PacketProtocolTest` 必须同步。
3. **声明式字段表的表达力**：场景画布、波次表格、卡池双列这些复合页面不适合拆成字段表。第一版保留它们为**手写页**（用同一个 `EditorPage` 接口），字段表只覆盖"表单型"页面；`Json` 字段是逃生舱。
4. **迁移期的中间态**：阶段 3 与 4 之间用一张迁移表把尚未搬走的页面接进框架，阶段 4 结束时删除；页面机制自始至终只有 `EditorPage` 一套，见 §9.6。
5. **`InGameScreen`（1912 行）会被拆**：卡槽条与红线搬出去后它变小，但这是一次高风险搬运——阶段 2 只做"原样搬运 + 一行分发"，不改绘制逻辑。
6. **AI 与机制**：`PlantAIPlayer` 目前完全绕过卡槽来源（直接 `consume` 阳光 + `spawnPlant`）；机制化之后"AI 在传送带关卡乱种"仍然是可能的（只是现在没开）。本方案**不修**它，只在文档里记为已知缺口——修它属于"AI 策略"，不该混进这次重构。

## 8. 决议记录（已拍板）

1. **旧键的处理强度**：**加载照常，由 `LevelValidator` 报错**。旧 `conveyor` / `placement_zone` 键被忽略，关卡能加载，校验器给出一条"该键已移入 `mechanics`，应为 …"的错误 —— 与 `validateRewards` 对拼错 `type` 的处理同一策略：坏数据不阻断加载，但必须被点名。
2. **机制互斥**：**只做"卡槽来源至多一个"**，在卡槽来源解析处硬编码；`LevelMechanic` 不加 `excludes()` / `requires()`。将来真出现第二类互斥关系时再抽象。
3. **`pvzce:deck` 无数据块**：`codec()` 用 `MapCodec.unit`，卡组数据仍在顶层 `slots` / `max_seed_slots` / `initial_sun` / `unlock_resources`。
4. **编辑器页面可见性**：机制不适用时**直接隐藏**页签（传送带关卡没有"卡池"页）；页签栏随机制增删。
5. **i18n**：沿用 `GuiLang` 的 `<ns>.<path>` 规则 —— 机制名 `pvzce.mechanic.conveyor`，字段名 `pvzce.mechanic.conveyor.field.capacity`，缺失回退到 path。
