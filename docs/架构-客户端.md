## 6. 客户端

### 6.1 状态镜像

`ClientLevel` 是服务端状态的**只读镜像**：实体表、卡槽、场景（`SceneGrid<String>`）、队伍（按 team 分别存放的资源）、波次/日夜/目标速率/断线原因。`ClientLevel.init(...)` 与 `reset()` 共用 `clearTransientState()`，所以两者不会分叉。

日夜由共享的 `DayNightCycle` 计算，客户端不自己维护 `TimeOfDayS2C.night`。

### 6.2 GUI

- `Screen`：`init/render/tick/鼠标键盘` + **对话框栈** + **`FocusManager`（键盘焦点唯一属主）**。`onResize()` 会重建基础 widget 并把已打开的对话框按新尺寸放回（对话框不会因改窗口而消失）。
- 子类用 `modalDialog()` 取"当前最上层模态对话框"，不要自己倒序扫描 `widgets`。
- **模态输入分发是强制的**：`mouseClicked` / `mouseMoved` / `mouseScrolled` 在 `Screen` 里是 `final`，先发给模态对话框、没有再发给 widget，最后才调**界面自己的钩子** `onMouseClicked` / `onMouseMoved` / `onMouseScrolled`（逻辑 GUI 坐标）。界面要处理自己的点击区域就覆写钩子，**不要**覆写 `mouseClicked`（覆写会被 `final` 挡住，模态分发不可能被绕过）。少数必须在原始像素坐标下工作的调用（游戏内相机）用 `rawMouseX/Y` 换算。
- `addWidget` / `showDialog` 会自动把 `EditBox` 接到焦点管理器；`widgets` 里消费点击的控件拿走焦点，其它情况释放焦点。
- **触控只有两个手势**：单指点击与单指滑动。`client/input/PointerGesture` 把"滑动"变成滚轮 —— 而且
  **只接管按下点落在滚动区域里的那一次按下**（区域内点击留到松手，超过 `TAP_SLOP` = 8 GUI px 就只滚不点），
  区域之外保持"按下即发 + 每帧拖动"，所以棋盘的手势与鼠标完全一致。开关 `-Dpvzce.touch=false`。
- **手指怎么变成鼠标事件，三条平台三种做法**：Windows 由系统提升主指针；X11/**Xorg** 由 XInput2 为首个
  触点发核心指针事件；**Wayland 两条都没有**，于是 `client/input/wayland/WaylandTouch` 用 **FFM（Java 25）**
  在 GLFW 自己的连接上绑 `wl_touch`（registry → seat 能力位 → get_touch → listener，按 surface 过滤，
  GLFW 的默认事件队列会替我们派发），`client/input/TouchTranslator` 把它翻译成与鼠标完全相同的
  press/drag/release，只跟第一根手指、`cancel` 当松手。
- **窗口标题栏由游戏自己画**（`client/gui/WindowTitleBar`）：Wayland 上 GLFW 把装饰交给 libdecor，
  而 libdecor 的 GTK 插件在 JVM 里**永远拒载**（它要求 `getpid() == gettid()`，而 JDK 的 java 启动器
  故意不在进程首个线程上建 VM），GNOME 又不广播 `zxdg_decoration_manager_v1`，所以
  `glfwGetWindowFrameSize` 全 0、窗口没有标题栏与三大按键。判据写在启动行：`边框=[0, 0, 0, 0] 自绘标题栏=true`。
  这条 UI 只在"桌面没给画"时出现（全屏不画、X11/Windows 的 `frameInsets` 非 0 也不画），画在**帧的最上层**，
  不占 GUI 高度（游戏顶部本来就留白）；几何在 `WindowTitleBar.Layout`（纯算术，按键右对齐），
  手势在 `TitleBarGesture`（按下→抬起落在同一个键才算，空白处 400 ms 内两下 = 切换最大化），
  指针通路的最前面都先问它（`dragging()` 覆盖整段按下到抬起）。**不做拖拽移动窗口**：
  Wayland 客户端不能自己设位置，`xdg_toplevel.move` 需要 GLFW 私有的 toplevel 与输入 serial，
  而 `glfwGetWaylandWindow` 给回的指针实测**不是** `struct wl_proxy`，够不到 GLFW 的窗口结构
  （试过并回退，见 `踩坑清单.md` 119/125 条与 `todo.md`）。
  **它的 Y 只有一个原点**：键盘鼠标给的都是"距窗口顶部"，而 GUI 投影的原点在底部，所以进它之前
  只换算一次（`PvzceClient.guiMouseYTopDown()`，比例是 `窗口高 / gui高` 而不是 `guiScale`）；
  第一版两处各用一个原点，症状是"红十字压在按键上、按下却判不中"（`踩坑清单.md` 121/122）。
  栏高有**设备像素下限 44**（`ceil(44/scale)` 个 GUI 单位），可点带再宽限 20%
  （`activationHeight()`）——只按 GUI 比例算的 36 像素靶子，用户实测点不中（同 124 条）。
- **Linux 上默认走 X11/XWayland，这是配置项 `prefer_x11`（默认 `true`），不是删掉 Wayland**：原生 Wayland
  那条路完整保留（`pvzce.platform=wayland` 或把 `prefer_x11` 改回 `false` 就切回去，代码一行没删）。
  取舍写在明面上：原生 Wayland 是**唯一能触控**的后端（GLFW 的 Wayland 后端才有 `wl_touch`），但它
  **没有任何窗口装饰**——libdecor 的 GTK 插件在 JVM 里起不来（`踩坑清单.md` 118），GNOME 又不给服务端装饰；
  X11/XWayland 换来桌面自带的标题栏与拖动/缩放，代价是 Wayland 桌面上的触摸不再进游戏
  （XWayland 只转发指针）。判据只看启动行：`边框=[0, 0, 0, 0] 自绘标题栏=true` 是原生 Wayland，
  `边框=[0, 37, 0, 0] 自绘标题栏=false` 是 X11（37 是 GNOME 的标题栏高度）。
- **Wayland 上"先 show、再全屏"是硬性顺序**：GLFW 的 xdg_toplevel 只在 `glfwShowWindow` 里创建，在那之前
  请求全屏不报错、只是被丢掉（`PvzceWindow` 的构造顺序因此是 show → setFullscreen）。启动那一行
  `[启动] platform=… 窗口=… framebuffer=… contentScale=… guiScale=… 全屏=… 主显示器=… 边框=[…] 自绘标题栏=…`（`边框` 全 0 就是"桌面没画装饰"）是排查
  "窗口没出来 / 点不准"这类报告的第一手材料；需要查 GL 调用时 `-Dpvzce.traceGl=true`。拿不到（没有 libwayland / seat 没有触摸）只记一行日志，
  不影响键鼠。**Wayland 会话因此优先走原生 Wayland**（`PvzceWindow.preferWayland`），`-Dpvzce.platform=x11` 可强制。
- **"哪里能滚"是声明出来的**（`client/input/ScrollRegion`）：`Screen.scrollRegionAt` 按点击同样的顺序问
  （模态对话框 → widgets → 界面钩子 `onScrollRegionAt`），`Overlay.scrollRegionAt` 是覆盖层那一份；
  声明必须复用滚轮处理器已有的矩形。`AbstractSelectionList` 与 `Slider` 各自实现
  `scrollRegionAt` / `claimsDrag`。
- **键盘只有一张绑定表**（`client/input/KeyBindings`）：每一步操作（窗口、工具、聊天、节奏 lane…）→ GLFW
  键码，`PvzceClientConfig` 的 `[keys]` 表往返（缺项逐条回落）。**这个文件只记"玩家改过的"**：仍等于
  出厂默认的动作不写进去，所以以后改默认值能到达每一个没动过它的人（早期版本把整张表写进文件，
  于是节奏草坪的按键从 `Q W E R Y` 搬到 `S D F J K L` 之后，老配置仍然把旧键位钉在那里 —— 见
  `踩坑清单` 145）。读盘时另有一条升级规则：**存下来的值若等于这个动作历史上用过的某个默认值，
  就当作"没被选过"**（`SUPERSEDED_DEFAULTS` + `asShipped`），改用现在出厂的键；玩家自己挑的键照旧保留。分两类：**窗口的**（全屏 F11 / 诊断 F3 / 截图 F2 / 血条 F10）
  在 `PvzceClient.handleBoundAction` 里就地答完，浮层开着也照常；**关卡的**（聊天 T、命令 `/`、
  工具 1~4）转交 `InGameScreen.keyAction`，因为工具键要"光标下的那一格"。`bind` 会把键从原来那个
  动作手里**拿走并留空**，不是搬家 —— "两个动作一个键"只会让后一个永远不触发。
  - **工具键认工具，不认卡位**：`1` 永远是铲子，哪怕它在这关的卡槽里排第 12（牌堆比屏幕宽时它会被
    挤到 `1x` 按钮底下）。工具箱里没有这把工具就**安静吃掉**；另外三种拒绝（不在运行中/暂停/卡不可用/
    光标不在草坪）也全安静，所以有一行 `-Dpvzce.traceInput=true` 的追踪说清是哪一种。
- **两种覆盖层：控制台与聊天行**（`ConsoleOverlay` / `ChatOverlay`）：`T` 开底部一条聊天行、`/` 开面板式
  控制台（预填一个 `/`），两者都画 `ClientLevel.messages()` 那一份消息表。玩家打的字走
  `ChatC2S` → 服务端 `say()` → `ServerMessageS2C` 回来 —— 本地回显更省事，但"服务端没见过的话"
  不在任何人的日志里（联机时就是只有自己看得见的聊天）。
- **F2 截图在帧末读**：按键只置一个待办位，PNG 在 `render()` 之后由 `FramebufferCapture` 抓（冒烟钩子
  共用同一段代码）。按键那一刻读缓冲存下来的是**上一帧**。
- **F10 血条**：只给"不满血"的东西画，比例的分母来自 `EntitySpawnS2C.maxHealth`（协议 39 起）——
  客户端原先只有当前血量，缺的正是这个分母。开关状态进消息日志（`血量显示：开/关`），
  因为场上没有受伤目标时屏幕上不会有任何一处动。
- **准备阶段**（`pvzce:preparation`）：`ClientLevel.preparing()` 是服务端流下来的那个布尔，
  关卡 HUD 在棋盘中央画一个「开始」按钮（懒创建的真按钮控件）与两行提示（规则 + 可用阳光），
  按钮发 `StartWavesC2S` —— 阶段是不是还在跑由服务端回答，所以按两次或撞上自动倒计时都不会开两遍。
- **设置页**（`SettingsScreen`）多一行「快捷键」→ `KeybindScreen`：12 行，点一行进入"请按一个键"，
  被夺键的那一行当场显示为未绑定。
- `Clipping`：GUI 空间裁剪栈（`client.clipping().push/pop/pushPixels`），GUI→framebuffer 换算只有一份（`guiMouseX/Y` 的精确逆运算），支持嵌套求交；帧末 `reset()`。
- `SeedCardRenderer`：卡片绘制的**唯一**实现（游戏内卡槽与选卡界面共用），`CardKind` 决定底栏显示价格还是"收集"。**传送带上的卡不印价格**（`SlotInfo.NO_PRICE = -1`）：它不是"价格恰好为 0"，而是"这张卡是发给你的"，印个 0 会读成一次免费交易。
  - **卡面（chrome）是 `CardModel` 的一部分**：`background` 为空就是种子包；**铲子卡用 `SHOVEL_SLOT_BACKGROUND`（原版 `ShovelBank.png`）**，图标居中、底栏不印价格。
  - **卡槽条里每一张卡一样高**：`fitBackground` 只在"整张卡画的是别人的原图"时用（今天的奖励种子包），**工具卡不用它** —— `ShovelBank.png` 接近正方形，按自身比例居中画会把**整张卡**（连图标）缩到卡片高度的约四分之三，于是铲子/手套/锤子在同一排里比植物矮一截。工具卡的图要走卡片比例：植物卡是 100×140 的卡面 + 一张方形图标，工具照做即可（`textures/gui/cards/hammer.png` 就是这么渲染出来的，见 `tools/render_controller_icons.py` 的 `TOOL_ENTITIES`）。
- **拿起卡有声音，放下也有**：卡片条上按下（点击或拖拽都算）时，植物/工具卡放原版的 `sfx/ui/seedlift`，**铲子放 `sfx/effect/shovel`**；选卡界面与游戏内卡片条都走它。**把卡放回去是同一个手势倒过来，所以是同一个声音**（`playCardSound`）——再点一次已选中的卡、右键、点棋盘外都走 `cancelSelection`，一样有声。
- **右上角是一对 HUD 按钮**（`InGameScreen.init`）：**倍速在左、暂停在最右**，两者**等高**（`min(56, guiH/5)`）、
  倍速更窄（`min(64, guiW/10)`，因为它只写"1x"两个字）。`rightBound()` 给的是这对按钮里**最左那个**的左边再减 8——
  卡槽条与履带托盘用它避让，取错成"暂停按钮的左边"就会把倍速按钮压在条底下（换位置时踩过一次）。
- **暂停对话框**（`PauseDialog`）：按其它对话框的约定重做过——石框按 `frameScale(0.45)` 画薄（原生边框
  209 纹理像素，对这么小的面板来说就是全部；0.55 在这个高度下只够四行二十单位的"邮票"），标题用 `inlineTitle()`
  画在框内（吊牌在 400 宽的对话框上高约 90 单位，而 GUI 只有 240 高，会顶到屏幕外），按钮保持**石牌**样式
  （它们长在石框上，木牌反而像塞进来的另一个控件）。四行：继续游戏 / 设置 / 重新开始 / 保存并退出；
  行从**框内侧**往上排，行高按拿到的实际高度算（窗口小的时候 `create` 会把面板压扁），所以不会溢出。
  "设置"开的是**设置菜单**（`SettingsScreen`，即音量/视频那一页的入口），不是音量页本身；开着它去设置页是安全的：
  服务端已经收到暂停，回来时 `paused` 还是真，对话框照旧在。
- **新装第一次打开的是引导页，不是标题页**（`OnboardingScreen`）：就两问（语言、界面大小），一块居中的
  石框面板（与暂停框同一份九宫格美术，`NinePatch.drawDialogFrame`），方向键与鼠标等价，回车下一步、
  Esc 回上一步且不离开这一页。选语言**当场**把整页换成那种语言，选大小**当场**按那个比例重画 —— 预览
  就是这一页本身。`PvzceClient.openFirstScreen` 决定开哪一页：`config.onboarded()` 为假才开引导页，
  回答完立刻写盘（老玩家的档案里没有这个键 = 已经回答过，见 `PvzceClientConfig`）。
- **界面语言是一个设置**（`config.language`，默认 `zh_cn`）：`GuiLang.reload(resources, locale)` 在
  启动与切换时读它，`PvzceClient.setLanguage` 换完字符串再 `refreshGui()`（widget 的标签是构造时抓的，
  不重建就会留着旧语言）。可选语言是**扫包栈**得来的（`GuiLang.availableLocales`：`assets/<ns>/lang/*.json`，
  内置的排第一），每个语言文件都写着所有语言的母语名，所以那一行谁看都读得懂。
- **"自动" UI 大小 = 这个分辨率最合适的比例**（`PvzceClient.recommendedScale`：离 960×540 最近的一档，
  并列取更小的档 = 更大的界面；1080p→2x、1440p→3x、4K→4x、720p→1x）。`fitScale` 仍是 MC 的
  `calculateScale`（最多能放到几倍），手选上限与"窗口放得下"都由它回答。
- **设置类页面的背景是"打开时那一帧"的模糊**（`renderer/BlurredBackdrop` + `Screen.blurredBackdrop()`）：
  没有新增后处理通道——`openScreen` 在**新页面画之前**把当时的后备缓冲用 `glBlitFramebuffer` 缩到 1/6 存进一张 FBO 贴图，
  页面再把它放大铺满（双线性放大本身就是模糊），上面压一层暗色（`0.10,0.11,0.14,0.62`）保证字读得清。
  于是"在游戏里打开设置"看到的是**那一局画面**糊掉的样子，而不是一张和玩家所在位置无关的菜单图；
  缩放/窗口变化不会坏（贴图被拉伸），第一屏（底下什么都没有）拿到 `false` 就回落到 `renderBackground`。
  `SettingsScreen` / `VideoSettingsScreen` / `DifficultyScreen` / `ConfigScreen` 四个页面开了这个开关。
- **难度页（`DifficultyScreen`）**：四行按钮，每行都是"名字 + 四个倍率"，当前档打 `●`。四行**一样长**是有意的 —— `Button` 会把自己的标签缩放到刚好放得下，短一行就会被画成大字，一页四种字号读起来像四件不相干的东西。"普通 = 原版"那句是整列的注解，所以画在标题上方而不是塞进某一行（第一版画在标题下方，被第一个按钮的底板整个盖住了：控件是在界面自己的文字**之后**画的）。
  > **选卡页/关卡列表上的角标**（`LevelSelectScreen.drawDifficultyBadge`）只在非普通档时画：普通档在世界里什么都不改，一个永远在场的角标就是噪声。它画在「剧情」按钮**下面**，理由同上一条 —— 与那个按钮同一行会被它的底板盖住。
- **设置页只在"没有关卡"时才请求菜单曲**：音乐控制器是**四条独立轨道**（menu / background / battle / stinger），
  所以从关卡内打开设置时请求菜单曲不会顶掉关卡曲，而是**叠着播**（这就是"关卡内打开设置两首歌一起响"）。
  判据用 `ClientLevel.initialized()` 而**不是** `level() == null`——客户端那面关卡镜子是构造时就 new 出来的长命对象，
  永远不为 null（离开关卡时只是 `reset()` 成空）。菜单里打开设置照旧播 `crazy_dave`（`smokeScreen=settings` 验过）。
  想听/看当前在播什么：`-Dpvzce.traceMusic=true`。

- **关卡内的卡槽条有两种形态**（接口 `CardBar`，两个实现各自 `render`：`SeedCardBar.render` 与 `BeltCardBar.render`，由 `InGameScreen` 按关卡是否传送带选用）：普通关卡是**顶部左侧一排种子卡**（`SeedCardBar.updateLayout` 把行放在 `guiH - cardHeight - 8`，即窗口上缘下方 8 GUI 像素，紧跟阳光银行右侧：`CardBarLayout.cardsLeft(true)` = 边距 8 + 银行宽 78 + 间隙 8 = 94）；**传送带关卡是顶部的履带**——托盘由原版 `ConveyorBelt_backdrop.png` 九宫格成框（`NinePatch.drawNineSlice`，边框按 GUI 像素固定，不随托盘拉伸），原版 `ConveyorBelt.png` 的胎面**画在框内**（`BeltCardBar.BELT_FRAME_X/Y` 是边框厚度，也是胎面的内缩量）并持续向左滚动。**裁剪必须用胎面自己的矩形**（`beltX/beltY/beltWidth/beltHeight`）：平铺的相位不落在框边上，首尾两块会伸到胎面之外，裁到托盘就会把左右两条边框盖掉（上下两条因为胎面在内缩框里所以看不出来，这正是「上下有框、左右没有」的来源）；卡片**骑在带上**从右端滑入、向左走到队尾停住，前面的卡被用掉时后面的会跟着往前挪（位置按卡 id 记录在客户端，见 §4.9）。胎面与卡片用同一个速度常数，否则卡会像在冰上滑。卡按带上顺序排列（**不**走 `orderCardSlots` 的"资源→植物→工具"分组：队列的顺序本身就是信息），点击命中按**当前绘制位置**判定。托盘宽度按 `belt_capacity` 固定，窄窗口下缩小卡片以保证不钻到暂停按钮底下。**带子只发植物卡**：`BeltCardBar.split` 按 `kind` 把服务端"带子在前、留在身上的工具在后"那个分类重建出来，植物骑在带上，工具/资源卡（阳光是 HUD 银行、不算卡）**固定在托盘右侧、不随带子移动**，布局把两侧宽度一起算进可用空间、托盘左缘从阳光银行之后起算。工具跟着带子走会读成"带子正要发这把铲子"，托盘按容量算宽也会被它们挤爆。
  > 胎面纹理只在**去掉 1 像素边框后的中段**才是每 6 像素周期的，所以平铺取的是 `u ∈ [1/502, 499/502]` 这一段：整图平铺会把一条 2 像素的接缝每几秒滚过屏幕一次。
- **列表要"点一下就进去"时 → `AbstractSelectionList.setOnRowClick`**（标题页的玩家列表）。不要指望界面自己的 `onMouseClicked`：控件先吃掉点击，钩子根本不会被调用。
- **关卡内取消选卡**：再点一次已经选中的那张卡就放下它（右键与点击棋盘外同样取消），并放选中时那一声。
- **一次完整使用之后卡就回手**：`spendSelectedCard` 对所有卡（工具也算）都在发出请求后清掉 `selectedCard`。
  **约束：不要把"下一次点击要花掉的东西"留在一张已经冷却的卡上。** 手套是"拿起 / 放下"两击，很容易被做成
  "两次点击之间保持选中"，而它的冷却在拿起那一刻就开始了 —— 卡条对"选中但没就绪"的卡画灰、`cardUsable` 也会
  当场拒绝第二次点击（`sfx/ui/buzzer` + 抖动），表现成"手套卡住不动、像有无限冷却"，而植物还吊在手套上等 15 秒。
  服务端那半边的规则是 `finishingMove`：正在拿东西的手套忽略自己的冷却，一次搬运只花一次使用次数。
- **不能用的卡在点下去的那一刻就说"不"**：`InGameScreen` 用 `SlotInfo.available`（服务端把冷却、次数、价格三件事折成的同一个答案）当场判断：`refuseCard` 放 `sfx/ui/buzzer` 并让那张卡左右抖一下（`CardBar.Host.cardShake`，只有被拒的那张偏 6px，三条半周期后归零）。**不进入选中态**——被拒的卡不可以变成"下一次点击要花掉的东西"。
- **拖拽放卡**：在卡槽上按下就把卡拿起来（`draggingCard`），松手时若光标在棋盘内就直接种下/使用；松手在卡槽条上则保留选中，于是「点一下再点格子」的老手势一个字节没变 —— 两条路最后都走 `spendSelectedCard`。拖动时卡片图标跟着光标画，悬停格子的高亮仍然说明会落在哪。
- **弹丸也可以有动画**：投射物一直是"静态贴图 + `render_scale`"，`pvzce:fire_pea` 是第一个有动画文件的（`animations/projectile/fire_pea.json`，本体 + 火焰 + 火花，`idle`/`lit` 两个状态名）。**被火炬树桩点燃的豌豆不换 def，只换状态**：`pea.json` 的 `animations.lit` 指向那个文件，服务端在 `ProjectileEntity.torch()` 里 `setAnimation("lit")`，实体状态本来就会同步，协议没有动。没有这份绑定的弹丸照旧画自己的贴图。
- **木槌光标是一段动画**（`InGameScreen.renderDefaultToolCursor`）：关卡声明了 `default: true` 的工具时，光标画的是**那件工具自己的动画**，不是它的卡片贴图 —— 工具定义用 `animation_dir` 指向 `animations/tool/hammer.json`，`EntityArt.bindings` 也会查工具注册表，所以"哪件美术"和植物、僵尸走同一条回答。它经 `ArtTarget`（不是实体：木槌不在棋盘上，没有血、没有队伍、没有格子）挂到动画管理器上，画在一个 `beginOverlayWorldView` 开出来的、跟着指针走的方形小视口里：动画渲染器按世界单位工作，而这个投影正是"把一块世界矩形贴到一块 GUI 矩形上"的那个。**锚点在框的下沿**，因为转换出来的模型原点是它被拟合的那条地平线，锚在中心会让木槌高半格、脑袋被视口切掉。**点击时挥的那一下**（`swingDefaultToolCursor`，点击当帧就播，不等服务器回话）是 `attack` clip，播完由它自己的 `on_end: idle` 回到持握姿势；命中与否不影响这一下，服务端只补一声 bonk。没有这个工具的关卡一个像素都不画。
- **召唤出来的那把木槌是另一条路**（`InGameScreen.summonMallet` / `renderMalletSwings`）：空手点到花瓶或恐怖花瓶时，客户端在该格挂一个短命的 `ArtTarget`（同一个 `animations/tool/hammer.json`、同一个 `attack` clip），0.3 秒后连同它的 playback 一起丢掉（`stopAnimation()` —— 直接丢会把手柄留在管理器里），同时发 `SmashContainerC2S` 告诉服务端砸的是哪一格。**它画在粒子之上**：POW 是 0.83 秒的云，挥击只有 0.3 秒，画在下面等于没有。木槌不是工具、不是实体，也不在任何一边手里。
- **按住扫过即拾取**：在棋盘上按住左键拖动，光标扫过的阳光/金币直接收集（`onMouseDragged` → `resourceDropAt` → `CollectResourceC2S`，同一个掉落物只发一次）。一次点击只能捡一个掉落物，而草坪上常常同时躺着五颗阳光 —— 让玩家逐个瞄准是纯体力活。
- **种子包是草坪上的第二种"可点物件"**（`CardDropEntity`）：渲染走 `InGameScreen.drawCardDrop` —— 用 `SeedCardRenderer` 把**卡面本身**画在格子里（`CardPainter.icon(cardId)` 回答"这张卡长什么样"，与卡槽同一份答案；页脚不印价格，因为容器就是付款），闪不闪按实体的 `health`（= 服务器给的剩余 tick）。拾取判定是**格子大小的方框**（`cardDropAt`，与绘制读同一个 `EntityVisuals.CARD_DROP`），而且**只能点、不能扫**：扫过一地的包会顺手捡起一个，挡掉下一个（手里只能有一株）。点包 → `PickUpCardC2S`；手里有包时点草坪 → `PlantHeldCardC2S`（在卡槽选中之前判，因为手上那株才是下一次点击要种的东西），右键 → `ReleaseHeldCardC2S`；拿在手上的那株画在光标处（`renderCarriedPlant`，与手套搬植物同一段代码：来源只有"从卡槽拿的"与"从包里捡的"两种），种植预览（`renderPlacementPreview`）同样认它。`HeldCardS2C` 一到就把卡槽的选中清掉：手上只有一株植物。
- **拖动预览（种植幽灵）**：选中的是**植物**卡时，光标悬停的格子上画一个该植物 idle 动画的半透明副本（`InGameScreen.renderPlacementPreview`，alpha 0.5，`client.pushEntityAlpha` 压住动画路径里写死的 alpha 1）。它点击选中与拖拽两种手势都显示，图形走的是实体渲染的同一个 `drawEntityArt`，所以预览与种下去之后长得一模一样。**位置必须写格中心**：光标给的是格子下标，而实体坐标是格中心（服务端 `new PlantEntity(...)` 传的是 `grid + 0.5`），直接把下标塞进 `setCellX/Y` 会让幽灵比真正种下去的植物低半格、左半格。**它不判断能不能种**：地形与叠放只有服务端知道（`PlantPlacement` 的 Ctx 需要服务端实体），客户端只保留了它确实知道的那一条——关卡放置区的绿/红悬停高亮。
- **容器的悬停高亮**（`InGameScreen.renderContainerHover`）：光标停在一个花瓶/恐怖花瓶上、且**这一击真的会落在它身上**时，那一格画一层暖白（空手 = 砸开；选了植物卡且那是花瓶 = 塞卡；手里拿着种子包 = 不亮，因为那一击是种植）。判据与点击同一份，所以"会亮"和"点得动"不可能分家。
- **进关卡只有一条判断**：`skipsSeedScreen(info)`（关卡自己的 `seed_screen: false`、且没有增益页要问）决定"要不要那个卡屏"，三条入口——列表进入（`enterLevelFromMenu`）、存档框的重新开始、暂停菜单的重新开始（`restartCurrentLevel`）——**都调它**，跳过时一律走 `requestFreshRunDirectly`（开场对话因此在关卡内播）。第三条曾经漏了，症状是"从暂停菜单重开 4-5 会冒出选卡页"。
- **开场与大波是文本，不再是贴图**（`client/gui/components/BannerAnimation`）：三拍是「准备… 安放… 植物！」，
  最终波是「最后一波攻势」，**文案走 `assets/pvzce/lang`**（`pvzce.announce.*`，中英各一份），用 display 字面画成
  原版那种红字黑边。从美术里保留下来的只有**姿势**（位移/缩放逐帧抄自 `refer/anim/StartReadySetPlant.reanim` 与
  `refer/anim/FinalWave.reanim`，偏移按宽度归一化，所以画面尺寸变了动作比例不变）；**节拍是音效的**，因为原版动画与

  两次"咚"在 0.00 / 0.60 秒，正文 1.20–3.30 秒 —— 现在三个词落在两次咚上、`植物！`压住整段正文。
  最终波同理：`awooga.ogg` 有 **4.15 秒**、峰值在 2.20 秒，所以飞入被拉长到 1.10 秒到位、停到 3.5 秒
  （原来 1.9 秒就演完，音效还没响起来）。画在 **GUI 空间、窗口中央**（横幅是"游戏在对玩家说话"，不随棋盘缩放）。
  字号按"高度不超过绘制宽度的 0.36、宽度不超过 0.92"取小值——中文比它替换掉的英文更紧凑，
  照英文的高度排「最后一波攻势」会顶出窗口。黑边是**画出来的**（同一个词在四个方向各偏移一遍再叠正稿），
  shader 的描边在这里不够用：它的采样距离上限是两个设备像素，在这么大的字上就是一根发丝。

  「一大波僵尸即将来袭」（`renderWaveWarning`，同样从 lang 读，见 §6.2），与最终波的横幅不是同一句。
- **失败画面也是原版的**（`client/gui/components/DefeatScreen`）：黑幕淡到 0.5、`ZombiesWon_.png` 从中心放大到屏幕的 70%，逐帧抄自 `refer/anim/ZombiesWon.reanim`（24 fps，12 帧）。**它前面有两拍演出**（`InGameScreen.tickDefeat`）：镜头先朝房子平移 2.1 格（`PvzceCamera.panned`，**上限由 `maxPanX()` 给出**——背景图左边缘不能被推进画面里），停在最后那只僵尸啃房子的画面上约 1.2 秒（客户端把最靠左的地面僵尸按在 `eat`，并每隔 0.6s 补一声咬合音；关卡已经停止 tick，镜子里的它永远停在 `walk`，所以这是**唯一一处客户端改动画**的地方），然后才轮到失败画面。**平移期间点击不生效**（ESC 随时可以走），否则玩家随手一点就会跳过唯一说明"刚才发生了什么"的那一幕。

  > `grave_field` 在**建关时**撒的（`LevelServer.openingBoard`：构造一个用完就丢的关卡，读完格子就扔），
  > 文件里根本没有它们的坐标 —— 照文件画就会得到"预览一块干净草坪、进关卡处处是墓碑"。

- **不能选卡的关卡不进选卡页**：`SeedOptions.hasNothingToChoose` 为真时 `openSeedSelection` 仍然开这个屏（对话、平移、预览都在这儿），但它只是过场；**存档提示框的「重新开始」**则连过场都不走，直接 `RestartLevelC2S`——那一局玩家已经看过一次入场了。

- **按钮标签的字号是算出来的，不是每个调用点猜的**（`Button.fittedLabelScale`）：**可书写面**（见下）的
  `LABEL_SIZE_OF_FACE = 0.75` 是上限，取"行盒放得下高度"与"文字放得下宽度"的小值，再乘调用点给的可选倍率
  （`Button.scale` 现在**只是倍率**，1 = 填满），最后夹在 [0.5, 2.4] 之间。0.75 是调出来的：0.88 那种"填满面"的观感
  是字要把按钮撑破，低于 0.7 又显得按钮空；**这一个数就是"所有按钮标签一起小一点/大一点"的旋钮**。于是高按钮的字自动变大、窄按钮里的长标签（编辑器那种九个字的按钮）自动缩回去，
  `ButtonLabelScaleTest` 钉住"放得下、越大越大、夹得住"。
  - **可书写面是量着美术定的，不是控件本身**：石牌（`button_middle.png` 46px 高）顶部 8px 是高光、底部 8px 是阴影，
    面在 8..38 行之间——只有控件高度的 0.65；**宽度扣的是两端圆角（约 10/46 个高度），不是端帽宽度**：
    端帽合计 71/46 个高度，窄按钮上比按钮本身还宽（倍速按钮 44×48 就被算成"剩下 1 单位宽"，
    它的"1x"因此小得看不见）。木牌是一张整图拉伸，边框是 42 行里的 2+5 行、156 列里的 2+2 列。
    标签因此永远落在"面"里、给边框留出边距——填满控件那种做法（0.9）会顶到高光和阴影上，被退回过。
  - **垂直位置按墨迹居中**（`Button.labelBaseline`）：行盒是对称的、汉字不是（墨迹在基线上 0.76em、下 0.05em），
    按行盒居中会让每个标签都偏低——字号一小看不出来，字号一大就先从下沿顶出去。
  - **悬停时标签跟着面板一起沉**：`button_down_*` 就是同一块面板在贴图里下移 1 个原生像素（悬停即用这套图），
    所以标签也下移"控件高度 / 46"同样的比例。字号不跟着变——为了 4% 的高度差重新光栅一套字形不值得。
- **HUD 上的数字用站酷体**：阳光银行那个大数字（`InGameScreen.renderHud`）与每张种子卡印的价格
  （`SeedCardRenderer`）都走 `fonts().button()`——原版这两处本来就是同一个字体，而且在这个尺寸上
  站酷的笔画比思源的细横更站得住。
- **粗体是"膨胀"出来的，不是字体自带的**（`TextStyle.bold()` → `FontRenderer`）：stb_truetype 没有合成粗体，
  内置的站酷也没有粗体字重，所以渲染器借 shader 的描边分支、把**颜色设成字色**再画一遍——四个方向各外扩一个
  纹素、对称加粗，字宽（advance）不动，所以粗体不会挪版。**不要改成"平移一个像素再画一遍"那种假粗体**：
  在 4~5 像素宽的汉字笔画上，平移就是平移，看起来像两个字叠在一起没对齐（试过，被退回）。
  粗体那一遍**最后画**，正好压住自己描边的内圈，所以"深绿 + 粗体 + 浅描边"的标签最终是
  **1 像素浅色边 + 粗一档的字**，边不会跟着变粗、也不会重影。
- `GuiText` / `GuiStatusText`：短 id、数字格式化/解析（带范围夹紧）、存档状态文案。
- `GuiLayout`：只负责按钮行高适配（`fitHeight`/`gapFor`）。
- **钱包 / 卡槽 / 解锁（档案）到达客户端的通道**：`ProfileS2C` 只有一个发送者 ——
  `PvzceServer.sendLevelList`（另有几处 grant/购买后的回推）。所以**不打开关卡列表也能到的页面**
  （商店）必须自己问：`PvzceClient.requestProfile()` → `RequestProfileC2S(world)`，服务端按
  `menuWorld()` 用同一个 `profilePacket` 回答。`profileLoaded` 在换世界时清掉、由快照（或发送本身）
  置位，所以"问一次"是幂等的；`setCurrentWorld` 会 `profile.reset()`，那是"新世界还没加载完时不显示
  上一个世界的钱"。
- `layout/MenuPageCanvas`：**菜单页的画布**——商店页与数据包页都在这张 800x600 的坐标系里构图，
  再 contain 缩放到窗口（y 轴向下，与截图量出来的数字一致；`Canvas.x/y/scaled` 负责换算）。
  面板（`seed_chooser_background` 九宫格）、标题条、背景（`title_background` + 22% 暗色）与
  `widgetAt` 都在这里，**只有一份**。两条约定：**控件不进画布**（列表与按钮仍是 GUI 单位，标签才
  会跟着窗口字号走，所以要放进面板的控件用 `interiorX/Width/Bottom/Height` 或 `widgetAt` 换算）；
  **contain 拟合的下限只能是 0**（写过 0.55 的"可读性下限"，默认窗口需要 0.40，于是画布顶出屏幕
  45 单位、标题条与页脚按钮全被推出画面）。
  `Canvas.widgetAtInterior(...)` 是"钉在某个面板内角、按源像素内缩"的那一种放置（商店页的购买
  按钮用它）：内缩量从 `interiorX/interiorBottom` 数起，所以它与画出来的框不可能分家。
- **商店页是"选中 + 购买"两步**：行点击走 `AbstractSelectionList.setOnRowClick`（列表先吃点击
  是既定规则，界面自己的 `onMouseClicked` 在行上根本不会被调用——写在那里就是"点了没反应"），
  右侧 1/3 是详情栏、右下角是购买按钮（`ShopScreen.select` / `buySelected`）。列表自己的
  绿色选中高亮是关掉的，因为"哪一行被选中"与"详情栏显示什么"必须是同一个事实。
- `Screen.coverFit(...)`：cover 适配的唯一实现，返回 `CoverFit`，界面用它把"按背景图素坐标写死的面板矩形"映射成点击区域（背景怎么画、点击区就怎么算）。
- `ListEditorSupport`：关卡/音乐/卡池编辑器共用的列表编辑算法（刷新并保持选中、保留指定项、上移下移、删除后选中谁），**只有这一份**，五个编辑器（对话 / 音乐 / 波次 / 卡池页 / 卡池对话框）都调它。两条已经定过的语义：移动是**删了再插**（不是交换，否则列表被筛过时一项会跳好几行），选中认的是**项**而不是行号（按行号重置会在列表重排后高亮另一项）。`ListEditorSupportTest` 钉住这两条。
- `GuiLang`：`assets/<ns>/lang/<locale>.json` → 显示名。key 是 MC 的 `<namespace>.<path>`。编辑器、波次表、卡池页都走它，缺失的 key 回退到 path（不是 `namespace:path`）。
- `PaletteList`：带**图 + 名字**的列表行（`Kind` 决定图标族：实体 / 场景 / 资源 / 纯色块）。
- **一行图标是三种东西之一**（`PaletteList.Item.Icon`）：一张贴图、一具**活骨架**、或什么都没有（画自己的色块）。
  - 植物与僵尸**只能走骨架那条**：它们声明的那张 `texture` 其实是**部件目录**（`textures/entities/plant/attacker/pea_shooter` 是一堆 `anim_head*.png`），所以"优先用声明的贴图"对 77 个内置内容 id 必然落空——画出来是品红/黑的缺失贴图。判据是 `EntityArt.animationFile(id) != null`（`iconFor` 里唯一一处决定），绘制交给 `EntityPreview`。
  - `components/EntityPreview`：把一具活骨架画进一个小方框的**有界缓存**（最多 24 具，按访问顺序淘汰并 `release`）。它**在绘制路径上**启动播放而不是在 `tick()` 里（预览是第一帧才惰性建的，那一帧的 tick 已经过去了——图鉴当年就是这么让"每张僵尸卡都是空的"）。编辑器三个调色板各持一个，页面的 `onClosed` 里 `releasePreviews()`。
  - 卡面行（卡池页）不走这一条：它问 `CardPainter.icon(cardId)`，也就是卡槽条与地上种子包问的**同一个**答案（48 个卡槽里 44 个画的是一张与实体美术无关的卡面）。
  - `AnimationManager` 上那个"取控制器模型里最大部件贴图"的 `iconTexture` 随之删掉：它拼的是 `animations/<id.path()>.json`（内置内容全在 `animations/<animation_dir>/<leaf>.json`，根目录下零个文件），从上线那天起就是死代码。
  - 守门测试 `EditorIconTest`：每个卡槽的图标都指向真的存在的 PNG；每个植物/僵尸都以**骨架**形态到达调色板。
- 配置界面：`config/ConfigScreen` 用**一次 `layoutRows()`** 同时驱动"摆滑块"和"画标签"；滑块 `onChange` 只在值真变时触发，**落盘走 `onCommit`（拖拽结束）**。
- **悬停显名只有一份实现**（`client/gui/HoverTip`）：一块深色底板 + 一行字，画在光标旁、贴到窗口边时翻到另一侧。它是个**函数**不是控件（不进 `widgets`，因此永远吃不掉点击），三处共用——游戏内卡槽条（`InGameScreen.renderCardHover`）、选卡页的卡池与增益池、关卡内的增益图标。**卡槽悬停显名以前根本不存在**：名字一直在语言文件里，只是没人画。触发条件一律是"光标下的东西确实在、且已经画完"（面板还在滑入、关卡已结束、正在拖卡时不画），因为给一个点不动的东西标名字比不标更糟。
- **关卡增益的图标画在左下角**（`hud/BuffIconRow`）：24px 一枚、横排左起，底部起点在**钱袋银行上方**（`CardBarLayout.MARGIN + BANK_HEIGHT + 4`）。左下角是钱袋银行的地盘，但它只在金币变化后显示 2.6 秒——正好是自动拾取开着时最常出现的那 2.6 秒，所以增益行让开它而不是共用。图标读的是 `ClientLevel.activeBuffs()`（服务端解析后的集合），**不自己算**：哪些增益开着决定服务端做什么，客户端画自己推出来的东西就可能显示一条模拟并没有应用的规则。悬停出名字（`HoverTip`）。
  > **这一行以前只在进场时更新过一次。** 列表唯一的上线通道是 `LevelInitS2C` 里的 `LevelPayload.activeBuffs`，而变异里的"增益变动"会在关卡中途换掉它 —— 于是角落的图标一直显示开局那份，模拟却按另一份跑。现在这份列表跟着 `MutationStateS2C` 走（`ClientLevel.setMutations` 顺手写 `setActiveBuffs`），服务端在 `setActiveBuffs` 里发现真变了就 `MutationManager.buffsChanged()` 强制发一次；横幅也由 `Mutation.announcement` 报出**具体**获得/失去了哪些增益。
- **没拿到的增益在池子里是带锁的**：服务端把每一个增益都发下来，用 `SeedOptions.LOCKED_OPTION`（复用价格字段）标记"这个玩家还没获得"，客户端据此画与固定卡同一个挂锁、并且点它只响一声。看到的与能用的因此是两句话：`1-6` 一进去就能看见两个增益长什么样，但只有 1-9 / 2-9 通关之后才勾得上。世界自动启用名单里那条同样会被过滤掉（一个还没获得的东西不该被"自动帮我选上"）。
- **选卡页的两个 tab**（`ChooseSeedsScreen`）：顶部一排"种子卡槽 / 关卡增益"，放在木牌标题栏上（标题与计数占了左右，宽度不够时整排移到面板上方那条缝里；关卡没有增益页时**一枚 tab 都不画**，而不是画一个禁用的）。两页共用同一套排版、同一个绘制器、同一条"已选行在上、池子在下面"的结构，差别只有列表、标题与"清空"清哪一页（清空是**分页**的：清了卡不等于要丢增益）。`previewOnly`（过场）现在要求**两页都没得选**——固定卡填满卡槽但放开增益的关卡（1-1 那种形状加上 `pvzce:player_choice`）必须让玩家进得去，否则会自动开局把他的增益丢掉。增益页的初始选择来自 `PvzceClient.openSeedSelection`：续档时是**存档里的那份**（`PvzceClient.savedBuffs` 直接读磁盘上的 `level.dat`，与关卡对话同一层），否则是世界自动启用名单（`ClientProfile.autoBuffs`，由 `ProfileS2C` 下发）。

- **对话框的内容区没有扣除九宫格边框**：`Dialog` 摆按钮时只按内容矩形算，没减去 `NinePatch.DIALOG_TOP/BOTTOM`，
  所以大对话框的按钮会跨到边框上。`LevelSaveDialog` 仍受这条影响（曾经举的第二个例子 `MusicEditorDialog` 已不存在：
  编辑器各页现在住在 `EditorScreen` 里，不再是自己弹的对话框）。
- **种植反馈只画到"如果种下去长这样"**：悬停预览是植物 id 的 idle 动画幽灵 + 放置区绿/红，但"**能不能种**"仍然只有服务端知道，
  客户端画的不是"这里能种"。要补全得把 `PlantPlacement` 的 `Ctx` 从"传 `PlantDef` 对象"改成"传 id 自取注册表"，
  因为 `ClientEntity` 只拿得到 defId。

### 6.2.1 关卡选择页（`LevelSelectScreen`）
- **左上角有一个「剧情：开/关」开关**（`storyToggle`）：关掉后进入任何关卡都**不播开场对话**（`PvzceClient.levelDialogue` 直接返回空表，所以选卡页与关卡内两条路一起静默；提示框 `hints` 不受影响）。它是**客户端配置**（`config/pvzce-client.toml` 的 `story`，缺省 `true`），不进配置界面：理由是"这场对话我已经读过了"是一次性回答，而不是每局都要重新决定的画面选项。按钮沿用世界里那个"标签即状态"的做法（`剧情：开` ↔ `剧情：关`），点击即存盘。
- **关卡的分类就是它的 id 路径**：`levels/yard/adventure/1_1.json` 加载成
`pvzce:yard/adventure/1_1`，第一段是主题、第二段是类别、其余是关卡自己的名字。规则只有一份实现
`api/util/LevelGrouping`（纯函数），服务端分组、客户端过滤、编辑器换组都调它 —— 读取依据是
**id 而不是文件位置**，因为文件里的显式 `"id"` 优先于路径，两者可以不一致。

- 主题与类别是**数据驱动的注册表**：`level_theme` / `level_category`，目录是
  `data/<ns>/level_themes/`、`level_categories/`，文件是 `id` + `order`（+ 可选 `trophy`）
  （**没有 name**：显示名与植物/僵尸一样走 `GuiLang` 的 `<ns>.<path>` key）。类别只声明一次、
  可被任意主题使用；某主题下出现哪些类别，由**该主题下实际存在的关卡**推出，所以加一批关卡
  不需要额外声明页签，也不会出现"打开是空的分类页"。主题顺序 = `order`，未分类页永远最后。
- **`trophy: true` 的类别，通关一门就在列表行右侧得一枚金杯**（原版 `refer/im7/images/trophy.png` → `textures/gui/screen/level/minigame_trophy.png`，按原比例画，行里的关卡名与 id 给它让位）。它是**类别的性质**：说的是"这一类关卡通关算一枚奖章"，所以同一类别下所有关卡共用，新加一关不用声明。判据是 `LevelInfo.cleared`（**通关过至少一次**）而不是行上那个标签 —— 已通关的关再开一局中途退出时行上写的是"进行中"，奖杯不会因此消失（与 §4.3「通关优先于进行中」是同一条事实的另一半）。`LevelRowRenderer.showsTrophy` 是唯一判定处（未知类别回答 false，客户端缺包也能画列表）。
- id 不足两段（`demo_level`、`yard/one_off`）、或引用了未注册的主题/类别 → **未分类**页
  （`pvzce:uncategorized` 哨兵）。**未分类页是固定页**：客户端在拼页签表时永远补上它，所以左侧列永远有"未分类"按钮、也永远能在那里新建关卡。服务端只下发有内容的页，空页由客户端补齐。`PvzceServer.validateLevelGroups()` 在 `/reload` 时把
  "谁因为什么落到未分类"打进日志，否则症状（关卡不在我放的地方）指向不了任何东西。
- 页签表由服务端下发（`LevelTabsS2C`，与关卡列表一起发；`PROTOCOL_VERSION` 因此 = 3），
  客户端**只渲染被告知的内容**：自己从关卡列表里收集页签的实现在"服务端资源包与客户端不同"
  时会给出与关卡不一致的导航，也无法表达顺序。`LevelInfo` 带 `theme`/`category` 两个字段，
  `LevelPage` 负责"这一页有哪些关卡"（纯函数，见 `LevelPage` / `LevelSelectSelectionTest`）。
- 页面形态：**左侧主题列 + 顶部类别行 + 行列表**（一关一行，一屏 6~8 关）。右侧仍是 `ListPaging` 翻页（箭头 + 滚轮），页码指示器在列表下方。
- `LevelCreateDialog` 的主题/类别两行按钮**预选当前正在看的页**，id 预览实时显示
  `<命名空间>:<主题>/<类别>/<名字>`；**命名空间是独立的一个输入框**（默认 `pvzce`，自由文本 +
  标识符命名空间字符校验），数据包/模组不必再被塞进内置命名空间；**未分类页保留自由 id**
  （该桶的定义就是"id 里没有主题"），手打 `namespace:` 时也仍然自由。文件路径、id 的
  "创建后只读"规则都不变。
- 编辑器信息页可**换组**，保存时 `LevelMove` 一并完成：**换 id + 移关卡文件 + 搬该关存档目录
  与通关标记**（旧的 `sourceFile` 在新文件写好之后才删，失败则整体不动）。id 是存档目录名、
  通关标记与其它关卡引用的键，所以这是**唯一**允许改 id 的操作，且是显式的，不藏在改名里。
- **冒险模式 40 关的波次表都是原版那一局的复算**（`tools/original_levels.py` + `tools/write_adventure_levels.py`，见 `架构-服务端.md` §4.7.2）：草坪、卡槽与奖励仍按下面这张表，而"来多少僵尸"不再由关卡手写。草坪一行行放开、每关首通给下一关要用的卡：

### 6.2.1b 标题页：谁要玩游戏（`TitleScreen` / `PlayerPickerDialog`）

- **玩家列表就是世界列表**：一个世界目录就是一名玩家的存档（`saves/<名字>/`），所以原版的"你是谁"和本项目的"选世界"从来是同一个问题。
- **标题页上只有名字**：左上角一块木牌（`renderPlayerBoard`）写着当前玩家的名字，底下是「谁要玩游戏？」。整块牌子就是按钮，点击弹出 `PlayerPickerDialog`。牌子**不是控件** —— `Button` 只画一行居中的文字，而这是两行不同字号、都要落在牌子里面，所以牌子由界面自己画、点击由 `Screen.onMouseClicked`（界面自有点击区的规定位置，见 §6.2）处理。
- **`PlayerPickerDialog` 只负责切换**：列表＝世界列表，加名字输入框、全解锁开关与「新玩家 / 删除选中 / 切换到这个玩家」。选中一个名字**只高亮**，真正改阵营的是「切换到这个玩家」；它也**不会打开关卡列表** —— 那是菜单上「开始游戏」的事，一个点击同时"换人"和"出发"会让两件事变成同一个手势。标题页的木牌在对话框后面，切换后下一帧就显示新名字，这就是反馈。
- **谁在玩会记下来**：`PvzceClient.currentWorld` 在构造时从客户端配置（`config/pvzce-client.toml` 的 `last_world`）恢复，`setCurrentWorld` 每次换人写回一次（名字先按 `WorldPaths.sanitize` 归一，与存档目录同一条规则）。所以重开游戏时标题页写的就是上次玩的那名玩家，「开始游戏」一步进他的关卡列表而不再问一遍；只有那个目录**不存在**（新装的游戏，或玩家在对话框里把它删了）才改用选择器。名字本身仍然一键可换，木牌就在那里。
- **对话框的边框按 `frameScale` 缩着画**：九宫格石框在原图里约 209 像素边框，3 倍 UI 下框本身就吃掉小对话框的大半个身子，列表＋输入框＋四个按钮放不进剩下的地方。`Dialog.frameScale(0.55)` 是同一份雕花按比例变薄，切片形状不变；`Dialog.inlineTitle()` 则把标题从"挂在框上的木牌"换成框内一行字（木牌约 38 单位高，内容密的对话框没有地方留给它）。
- **点名字就是进关卡** 这条只属于**关卡列表**：那边列表多了一个 `onRowClick` 回调（`AbstractSelectionList.setOnRowClick`），因为控件会吃掉自己的点击 —— 界面自己的 `onMouseClicked` 钩子只在"没有控件接手"时才跑，所以"先选中、再让界面决定"这条路对列表根本不成立。
- 世界选择不再是一屏 `WorldSelectScreen`：它已删除，`PvzceClient.showWorldSelect()` 变成 `showTitle()` 的别名（离开关卡、协议不符、关卡列表的声明根都还叫这个名字，它们不该各自知道"玩家选择在哪一屏上"）。
- **`${user_name}`**：关卡对话的台词里可以写这个占位符，替换发生在 `DialogueOverlay.create` 建帧的时候（不是画的时候）—— 一行台词因此只有一个最终文本，打字机、换行与"点击继续"量的都是同一个串，晚到的改名不会让半截句子在玩家眼前改变长度。值是 `PvzceClient.currentWorld()`，也就是玩家在标题页选的名字。写错的花括号不会被吃掉，原样显示，作者一眼能看见。

### 6.2.2 开场对话（`DialogueOverlay`）

关卡可以有一段**开局对话**：数据是关卡 JSON 的 `dialogue` 块（每行 = 角色 / 立绘 / 台词 / 语音 /
站位 / 该行的动画）加一个 `dialogue_character` 注册表（显示名、立绘目录、大小、气泡贴图），所以**加一个新角色
不用改代码**。运行时的唯一实现是 `client/gui/components/DialogueOverlay`：立绘贴说话那一侧的屏幕
下沿，气泡用 `box_left`/`box_right` 单图九宫格画在对侧（尾巴落在左下/右下那 56×24 的角里，改贴图时
别把尾巴挪出角外），台词按气泡内宽逐字换行、**逐字打出**（打字机），左键推进、ESC 跳过整段。
播放有两处入口——走选卡页的关卡在选卡页里播（镜头横摇之前），直接进关卡的（传送带关、编辑器测试）在关卡内播并暂停整关——**两处都从 `PvzceClient.levelDialogue` 取台词**，所以关卡选择页的「剧情」开关（§6.2.1）在这两处同时生效：关掉后连 overlay 都不会建，不是"把字藏起来"。

- **入场与出场**：每一个角色的滑入滑出各有自己的时钟（`DialogueScript.Slide`）。整段对话的开场是**第一句台词把谁放上台、谁就从自己那一侧滑进来**（左角色从左、右角色从右，`center` 没有"自己那一侧"，于是**从下方升起**），整段的收尾是最后一句点完后台上所有人按同一方向滑走，**滑完才调 `onFinish`**——所以"人退场了，镜头才开始走/关卡才开始"。ESC 跳过整段**不补动画**（玩家刚说了"我不看了"，再让他等一段动画是唯一不能做的事）。中间换说话人**不动画**（`slots` 没变，人就在原地）；只有一句新台词**点名了一个还没上台的角色**才播滑入、**漏掉一个已经在台上的角色**才播滑出。`"exit": "none"` 让退场变成硬切（`DialogueScript.isExiting` 立刻为真）。
- **一个舞台上最多站三个人**：一句台词用 `slots` 说"这一句谁在场、各站在哪"（`[{"slot":"right","character":"pvzce:pea_chan"}]`，名字与站位，没有立绘信息——非说话人的立绘是上一句留下的）。站位有三档：`left` / `center` / `right`，`center` 是"站在另外两个人中间"（3-10 的缠从中间杀出来），画面居中、气泡横在窗口下半部，进出场和居中的说话人一样**从下方升降**。不写 `slots` 的句子**舞台原样不动**（谁都不进、谁都不出、也不换半边；只有整段的第一句、台上还空着时才按说话人的 `side` 把人放上去），所以**单角色对话（1-1~2-10 的全部）逐字不变**，而多角色场面里"这句没提谁"也永远不会把人挪走。两人同时在场时两边的框并排摆，宽度装不下就**成对缩小**（`DialogueMotion.portraitHeight`，地板 `MIN_PAIR_SCALE = 0.62`），说话人画在最上层。谁在台上、谁在滑、哪一行已经可达，全在 `client/gui/components/DialogueScript` 里（没有贴图也没有输入，`DialogueStageTest` 直接断言它）。
- **一句台词可以是一个问题**（`line.choices`，最多 5 条）：这一句点击**什么都不做**，屏幕上长出按钮（真实的 `Button`，松开才算、按下后滑开就是改主意，字色与石牌用默认样式）。按钮**不在气泡里**：它们是玩家的回答，站在**说话人不在的那半边**、窗口下方偏上的位置（窗口宽的 34%、底边 0.40H，一行放得下就一行、放不下就等宽分列），所以按下去永远不挡刚问话的那张脸，也不会贴到屏幕底部的 HUD 条上。
- **按下按钮后直接接角色的下一句**：写在这一句下面的那行是**玩家自己的话**（`speaker_name` + 没有 `character`），它只用来给问题一个落点——**对话从不画它**，因为按钮上刚写过同一句话。`DialogueScript.step` 因此会跳过两种行：还锁在未回答的问题后面的、以及玩家自己的（`isHidden`）。点中的哪条只决定"下面那行解锁"，之后立刻走到角色接的那一句并开始打字。`LevelValidator` 会点名"下面不是玩家回答行"、"玩家回答行之后没有角色接话"与空选项。
- **一行的身份有两种**：`character`（注册表里的角色，给立绘与默认显示名）或 `speaker_name`（只有名字，`${user_name}` 同样替换）——两者都没有的行会被校验器报出来（气泡上没人名）。
- **立绘的空白边距是要量的**（`DialogueCharacterDef.PortraitInsets`，角色文件的 `portrait_insets`）：立绘的贴图尺寸不等于人物占的地方，缠的图是整幅画满的、豌豆酱的人物只占中间 58%~85%，同一个绘制高度下两个人离窗口边完全不同。排版因此把**画面里的那个人**贴到自己那一侧的窗口边（左角色贴左、右角色贴右），气泡的锚点也从"立绘边缘的 80%"改成"可见边缘往脸的方向 62%"（`BUBBLE_PORTRAIT_ANCHOR_RATIO`）。表是离线量出来的（一行/一列有 5% 像素不透明才算"有画"），没有条目的表情按"没有边距"处理。
- 几何是三个纯函数（`DialogueMotion`：滑入滑出的偏移、抖动的阻尼正弦、缩放的插值、两人并排的高度），时长在它的常量里（滑入滑出 0.35s、抖动 0.35s、缩放 0.25s）。
- **每条台词可以带一个动画**（`line.animation`，缺省 `none`）：`{"type":"shake","amount":2}`（**抖一次**：阻尼正弦，幅度 = 窗口宽的 1.2% × `amount`，0 表示不抖）或 `{"type":"scale","scale":1.25}`（**改这条立绘的大小**：从上一句留下的尺寸平滑过渡到该倍率，下一句没写就回到 1）。缩放**以底边为基准**（人是长高了，不是飘起来了），代价是超过约 1.11 之后**头顶会被窗口裁掉**——`MAX_SCALE` 因此只有 1.6，这是"贴底立绘还能放大多少"的答案，不是一个凑整的数。抖动与缩放都作用在**整块立绘矩形**上，气泡锚在立绘边缘，所以两者一起走（气泡不会站在原地看人走开）。首句的动画与入场滑入同时开始，这是有意的：一句喊叫本来就该在人物进场的同时发生。
- **站位有三档**：`side` 取 `left` / `center` / `right`。`center` 把立绘摆在窗口正中（同一尺寸，占窗口高 90%），
  气泡**居中压在下半部**（底边仍是 70% 那条下巴线）——"旁边"在正中间没有意义，左右两种答案都会把气泡尾巴指向空草坪。
  编辑器「对话」页的位置按钮在左→中→右之间循环，写回文件的就是这三个词。
- **台词可以为空**：`text` 为空 = **没有台词的一拍**，只演立绘、一个气泡都不画（`Frame.silent()`，`bubbleBox` 返回
  `null`），点一下继续。原版用它做表情演出。
  `LevelValidator.validateDialogue` 因此不再把"没有台词"报成问题，只把拼错的 `side` 报出来。

- **它是一个 `Dialog`（modal）**，不是新机制：`Screen` 把鼠标 / 键盘 / 滚轮事件先给最上层模态对话框，
  所以"对话期间选卡与按钮点不动"是结构上成立的，不需要在每个宿主界面里各写一份输入闸门。
- **排版跟角色走，不跟屏幕走**：立绘占窗口高度的 90%（×角色 `scale`）、贴下沿，气泡按**台词自身**的宽度收窄
  （短句就是一个小气泡），底边固定在窗口高度 70% 处（说话人的下巴高度），行数多了就向上长；气泡里台词右下角
  有一行小字「点击继续」（`pvzce.dialogue.click_continue`）。气泡靠角色的那一侧锚在**立绘宽度的 80%** 处
  （`BUBBLE_PORTRAIT_ANCHOR_RATIO`）而不是贴图边缘：立绘是整幅带透明边距的图，锚在贴图边缘会在角色和气泡之间
  留出一大块空白。立绘在左时气泡在右，反之亦然；两者都在 `DialogueOverlay` 的常量里，要调只改那几个数。
  换行后如果最后一行只剩一个字，会把上一行最后一个字挪下来（`avoidOrphans`）——"…僵尸的世 / 界" 是对的换行，
  但不好看。台词字号上限 1.35（随窗口高度增长），气泡内边距也在同一组常量里。
- **打字机**：每秒 28 字（`TYPEWRITER_CHARS_PER_SECOND`），句末标点额外停 0.18s、句内标点 0.09s
  （`pauseAfter`），所以读起来像说话而不是电传打字机。揭示进度**由墙钟推导**（`lineStartNanos` +
  `revealedCharacters`），不是每帧累加，掉帧不会让台词变慢。**气泡按整句排版、只画已打出的前缀**
  （`typedPrefix`），所以打字过程中气泡不会忽大忽小；「点击继续」小字只在整句打完后才出现——打字途中
  那一下点击的语义是"补全整句"，写"继续"会骗人。
- **两个宿主**，取决于这一局怎么进的：走**选卡界面**的关卡在 `ChooseSeedsScreen` 里播——对话期间镜头
  停在最左（房子一侧），草坪与僵尸预览照常渲染，对话结束后才走既有的"横摇 → 木牌滑入 → 选卡 / 自动开始"时间线（`panStartNanos`，无对话时就是 `startNanos`）；**传送带关卡**这类没有选卡界面的直接进
  `InGameScreen`，对话在草坪上播，`entryNanos`（"准备… 安放… 种植！"横幅）推迟到对话结束，
  期间发 `PauseGameC2S(true)` 冻住关卡、结束时恢复。
- **触发条件是"新开一局"**，不是"第一次玩"：选卡界面只在没有存档时打开（`enterLevelFromMenu`），
  所以它自己就能判定；直接进关卡的那条路（传送带、编辑器测试、暂停菜单重开）由 `PvzceClient` 用
  `directDialogueLevelId` 把"这一局是新开的"带过关卡初始化的往返。继续一局存档不播，通关后再玩会再播。
- 客户端从**本地数据包**读对话（与 `usesConveyorBelt` / `lockedSlotsFor` 同一层），所以没有新包、
  没有 `PROTOCOL_VERSION` 变化。
- 校验：`LevelValidator.validateDialogue` 报未知角色 / 拼错的 `side` / 拼错的 `enter`·`exit` / 未知的
  `animation.type` / 非法立绘名 / 拼错的 `slots[].slot` / 一个站位两个人 / 同一个角色写两遍 /
  既没有 `character` 也没有 `speaker_name` / 问题的下面不是玩家回答行 / 玩家回答行之后没有台词 / 空选项（加载时随其它关卡问题一起打；
  这些值都像 `side` 一样解成 `UNKNOWN` 而不是让整个关卡解析失败，`UNKNOWN` 的表现就是缺省行为——
  拼错的站位被跳过、拼错的人名不会被画出来——所以拼错不会把对话变样，只会被报出来），
  `validateDialogueAssets` 在 `/reload` 时按 `PvzceResourceManager.hasTexture`
  报缺失的立绘与气泡贴图（`[PVZCE/对话]`）。立绘名必须是**文件名**：`Identifier` 的 path 允许 `/`，
  不过滤的话 `../别人的角色/smile` 会解析出本角色目录之外。
- **台词里的 `${user_name}` 会被换成玩家名**（标题页选的那个名字，见 §6.2.1b）：替换在 `DialogueOverlay.create` 建帧时做一次，所以一行台词只有一个最终文本，打字机、换行与"点击继续"量的都是同一个串。写错的花括号原样显示，作者一眼能看见。
- 编辑器有独立的**「对话」页**（列表 + 角色/立绘两个选择器 + 台词/语音/位置 + **动画** + **「同台：…」**，后者打开 `DialogueChoicesDialog`：左右两半的角色 id、气泡上的名字、最多 5 条选项），保存时只覆盖
  `dialogue.lines`，块内其它字段（`enter`/`exit`、以后的 `trigger` 之类）原样保留；台词框每帧提交进模型，所以
  换行、点别的台词或直接按保存都不会丢掉刚打的那句。「动画」是一个循环按钮（无 → 抖动 → 缩放）+ 一个数值框
  （抖动幅度 / 缩放倍率，选"无"时禁用）；**只有非"无"的行才写 `animation` 块**（"没有动画"就是字段不存在，
  给每条台词都写一遍 `{"type":"none"}` 是让作者每次都要读过去的噪音），页面上不认识的类型**整个对象原样写回**
  （与解锁页对无法编辑的条件类型同一条规矩）。`slots` 与 `choices` 在模型里是**原样保留的 JSON**：对话框是它们唯一的编辑入口，没打开过就一个字节都不改——保存不会悄悄删掉 `dialogue.timed` 之外任何它没有控件可编辑的东西。

### 6.2.3 关卡编辑器（`EditorScreen`）

一页一个主题，导航栏切换：**地形 / 植物 / 僵尸 / 规则 / 波次 / 卡池 / 音乐 / 信息**。前三个共用左侧内容面板 + 中间画布 + 右侧操作面板；其余页把中间与右侧合成一块面板。

- **画布走游戏自己的世界投影**（`beginOverlayWorldView` + `SceneTileRenderer.render` + `AnimationManager.render`），不是 GUI 空间的一堆 quad。所以预设植物/僵尸**播的是游戏内动画**，格子形状也和游戏内一致 —— 画布的落点来自同一份 `LevelStage.board(canvasW, canvasH, columns, rows)`（画布不读关卡的 `background`，所以它永远拿草坪几何；泳池关卡在编辑器里因此按 9×5 显示，见 §6.3），而 `cellAtCursor()` 是它的精确逆运算。
- 预览实体在 `syncCanvasEntities()` 里建 `ClientEntity` 并**手动 `attachAnimationManager`**：动画管理器平时由 `ClientLevel` 在 spawn 时注入，编辑器不走 spawn 包，不接就没有动画。`releaseCanvasAnimations()` 在每次重建与退出时释放 playback（与选卡预览同一个泄漏点）。
- **规则页对注册表生成**：遍历 `GAME_RULES`，布尔 → 开关按钮，数值 → 滑块 **+ 数值输入框**（滑块表达不了 0..12000 的 tick）。滑块范围来自 `RULE_RANGES`，与 `BuiltInRegistries.registerGameRules` 的注册值对应；只写被改过的规则，其余留空以继承默认值，列表上标"已改"。
- **波次页**：**表格 + 详情同屏**，占满整宽（`fullContentArea()`）。左表：一波一行（序号 / 类型 / 间隔 / 预警 / 僵尸组成 / 合计）；右栏：选中波次的类型 / 间隔 / 预警 / 数量，加「组成」与「可选僵尸」两个列表；底部：新增/删除/上移/下移/自动填充/末波倍率。**没有二级菜单**，波次数据与 JSON 在 `WaveEditorModel` 里。
- **音乐页**：同样是**时间线 + 详情同屏**、占满整宽。左：cue 列表（tick / 轨道 / 事件）；右：tick / 音量 / 淡入、轨道 / 循环 / 停止、事件选择（点选即应用，读 `SOUND_EVENTS` 里所有 `music/` 条目）。也没有二级菜单，数据在 `MusicEditorModel` 里。
- **底部动作栏只有「保存 / 测试 / 返回」**，编辑入口只从导航栏进。
- **卡池页**：**两列**——左边是本关卡的卡（顺序即游戏内卡槽顺序），右边是全部卡（按 kind 分「植物·资源·工具」三段，带分段标题）。按钮排在列表**下方的独立两行**里，不压列表；右列里本关已选的卡带一个右对齐的「已选」角标。
- **卡槽规则只有一条**：**关卡列出的卡就是固定的**（进入关卡必发、选卡界面不能取消），**总卡槽数减去关卡卡数就是玩家自选的空间**。没有 per-card 的 fixed 开关，也没有 `seed_selection` 这种第二份"哪些是可选"的声明 —— 位置即语义。`LevelDef.seedPlan(allCards)` 是这条规则的唯一实现：`lockedSlots` = 关卡的卡（按顺序、去重），`pickableSlots` = 全部卡减去已固定的，`maxSlots` = 总卡槽数。
- `max_seed_slots` 在 `LevelDef` 的规范构造器里**自动抬到不小于关卡卡数**：关卡列了 13 张却声明 6 个卡槽，只可能是数据写错，截断会静默丢掉作者自己的设计。**"玩家没得选"按提示处理、不按错误处理**（`LevelValidator.describeFixedDeck` 返回一句话）：第一关就是把牌组写死的，那是一种正当设计，报成缺陷会教作者去关掉校验。卡池引用未知卡由 `SlotResolver.reportUnknown` 报一次（同一个 id 只报一次，避免每关刷屏），`unlock.requires` 里的未知卡则走 `LevelValidator.validateUnlock`。
- 服务端 `SeedSelection.sanitize` 先放关卡的卡、再按提交顺序补玩家的选择直到总卡槽满；不认识的卡与重复卡丢弃。选卡界面对固定卡画挂锁角标、点击无效、"清空"只清玩家自己选的。客户端绕不过这些 —— 服务端会重新算一遍。
- 想给玩家留选择空间：关卡卡数 < 总卡槽数即可（编辑器卡池页顶部实时显示「总卡槽 / 关卡固定 / 玩家可选」三个数）。
- **信息页**：关卡名称、描述、初始阳光、**奖励**（首通解锁卡 / 重复通关金币 / 僵尸掉币概率 / 每次掉币数量）；关卡 ID **只读**（创建后不可改，存档、卡池、其它关卡都引用它）。奖励块**整块由编辑器写出**（它只有四个字段），手写的多条 `first_clear` 会在保存时被规范化成"至多一张卡 + 一条金币"。
- **保存**：`buildLevelJson(previous, ...)` 从**载入时的 JSON** 出发，只覆盖编辑器拥有的字段，所以 teams、`env_vars`、其它工具写的元数据、更新版本新增的字段都不会因为"编辑了一下"而消失。写入路径优先回写**载入时那个文件**（`sourceFile`），内置关卡才落到 `datapacks/user_levels/`。
- **新建流程**：`LevelSelectScreen` 的「新建关卡」→ `LevelCreateDialog`（主题 / 类别 / 名称 / id / 尺寸）→ 编辑器；id 与名称从此分离，主题/类别默认取**当前正在看的页**，id 预览实时拼成 `pvzce:<主题>/<类别>/<名字>`。列表下方的「编辑关卡」按钮把**选中的关卡**送进编辑器。
- **「测试」与「从列表打开」走同一条路**：测试按钮只保存，然后交给 `PvzceClient.testEditedLevel`：它等**服务端重载后的关卡列表**再打开选卡界面 —— 必须等，否则选卡界面描述的是保存前的那份定义。`/reload` 命令因此会主动补发一次关卡列表（`PvzceServer.refreshLevelList`），客户端不必猜重载要多久。
- **列表分页**：左右箭头与滚轮都是**翻页**，不是滚动。算法抽到 `client/gui/layout/ListPaging`（纯函数，可单测）：首页行号永远是页大小的倍数，末页夹到 `(pageCount-1)*pageSize`，页数**向上取整**（最后一页只装残余行，可能不满）。`ListPagingTest.everyRowIsReachableOnExactlyOnePage` 对全部"行数 × 页大小"组合断言**每一行恰好出现在一页上** —— 它同时挡住两类翻页 bug：页数向下取整会让尾部若干行**没有页**，按 `totalRows - pageSize` 夹取会让相邻两页**重复同一行**。不重复靠"末页也从页边界开始"，不靠砍掉末页。
- 底部动作栏是**四个**按钮：下一步 / 编辑关卡 / **图鉴** / 返回；右上角是**本世界的金币**（`drawCoinCounter`，`money_bag` 贴图，缺图回退金币贴图）。图鉴取代了原来的背包页，见 §6.2.5。
- 「返回」走 `LevelSelectScreen.goBack()`：栈里还有上一屏就 `closeScreen()`，否则 `showWorldSelect()`。通关后客户端是用 `showLevelList()` **整体替换**屏幕栈的，此时栈里只有这一屏，直接用 `closeScreen()`（它拒绝弹出最后一屏）会让按钮**完全失效**；ESC 也走同一条路。
- 列表里选中一张卡会**同时**点亮「下一步」和「编辑关卡」（`updateActionButtons`）。这个按钮还会按选中关卡改名（进行中 → 「继续游戏」，见 §4.3）。
- **选中的是关卡本身，不是格子**：`LevelSelectScreen` 记住选中关卡的 **id**，每次列表刷新（换世界、`/reload`、编辑器存档）后按 id 重新解析行号（`indexOfLevel`，纯函数），所以"高亮的卡"与"按钮作用到的关卡"必然是同一个。

**编辑器只覆盖自己拥有的字段**（`buildLevelJson` 从载入的 JSON 出发），所以它不认识的数据块**不会被保存动作删掉，
但也没有 UI 去编辑**：`conveyor` / `placement_zone`（小游戏关卡目前是手写数据）、`buffs` / `max_buff_slots`、
`endless_schedule`（无尽关卡根本不进编辑器）、`dialogue.timed`（对话页会把整个 `dialogue` 块按自己认识的字段重写，
所以**用编辑器保存一个带 `timed` 的包关卡会把定时台词丢掉**）与 `mechanics.schedule`（脚本变异只能手写 JSON）。
另外：`CanvasPage` 每帧用 `palette.selected()` **回读**选中项（列表有行点击回调 `setOnRowClick`，但没有"选中变了"的事件，所以只能回读）；画布只支持地形与预设实体，仍按草坪几何画泳池关卡（它不读 `background`），也不画关卡背景、不显示装备档位
（画布上的僵尸是满血预览实体，`armor` 取 `NO_ARMOR`，`EquipmentArt` 把它当成"没磨损"画完整的那一张）；
`rewards.first_clear` 手写多条时编辑器只认第一条 `unlock` 并把多余的规范化掉（判定在 `InfoPage.readRewardLists`，纯函数，
由 `InfoPageRewardsTest` 钉住）；关卡只写进 `datapacks/user_levels`，没有"另存为"。

### 6.3 渲染

- `RenderSystem`：极薄的 GL 门面（混合/深度、投影、纹理缓存绑定、时令光照 uniform、**世界空间点光源** `setPointLight`：上限 `ShaderProgram.MAX_POINT_LIGHTS`，着色器里按半径做 `smoothstep` 叠加）。
  **只有阳光是光源**（`PvzceClient.lightsTheBoard`，按**内容 id** `pvzce:sun` 判定；白天暖黄、夜里偏冷）。**实体 kind 是类别（plant/zombie/projectile/resource），永远不是内容 id**：`EntityKind.RESOURCE` 是 `"resource"`（kind 字符串走 `EntitySpawnS2C`，故 `PROTOCOL_VERSION` = 10），`EntityLightTest` 同时钉住「只有阳光亮」与「kind 不等于任何内容 id」。
- `SpriteRenderer`：`textured` / `texturedQuad` / `solid` / `shadow` / `projectedShadow`（投影阴影是真梯形，远边有纵向跨度）。
- `PvzceCamera`：把格子坐标映射到背景图上的草坪。**舞台几何是构造参数**（`LevelStage.Geometry`），`geometry()` / `liquidFrame()` 把它交还给渲染路径，`panned()` 也带着同一份几何走；`PvzceClient.camera()` 的缓存键因此是"窗口尺寸 + 棋盘尺寸 + 几何"，换一关（前院 ↔ 泳池）不会接着用旧格子。**`inBoard` 接收的是 GLFW 原始自上而下的鼠标 Y，内部会翻转**；与 `worldX/worldY`、`screenX/screenY` 同一坐标系语义。
- `EntityTextures`：内容 id → 纹理 id 的唯一换算（保留命名空间）。**转发给 `EntityArt.sprite`**，因为路径不再能从 id 推出来：内置美术按类目分层（`textures/entities/plant/attacker/pea_shooter/`），所以定义里用 `texture` 字段显式声明；没声明的（mod 的常规写法）仍然按 id 推。
- **缺失贴图只有一个样子**：`EntityArt.MISSING_TEXTURE`（`textures/mission.png`，2×2 品红/黑棋盘格，`TextureManager` 对它单独用 `GL_NEAREST`，否则放大后四个方块会被插值糊成一片紫色渐变）。`PvzceClient.drawTextureRegion` 与 `drawTextureQuad` 取不到贴图时画的就是它（`drawMissingTexture`），动画部件也走同一条路——它和"故意画成空白"的精灵不会混淆。`EntityArt.sprite(null)` 也回答它。
- `EntityArt`（`common/core`）：**"这个内容 id 用哪份美术"的唯一答案**，两个问题一次查表 —— 播哪个**动画文件**（`animationFile`，读定义里的 `animation_dir`，缺省回落到 id 路径）与没有动画时画哪张**兜底贴图**（`sprite`，资源注册表里的资源另外回落到它自己的 `icon`）。渲染器、编辑器图标、选卡图标与 `AnimationManager` 都从这里取。
- `EntityVisuals`：每类实体的视觉常量（脚→动画锚点抬升、贴图兜底尺寸/偏移、渲染层、排序桶）唯一来源。新增实体种类只改这一张表。
- **站在水里的实体跟着水面往下走**（`AnimationManager.liquidDrop`）：`anchorLift` 是"脚离格中心多远"，与地形无关，而泳池的水面被 `LevelStage.POOL` 的帧故意画低了 0.22~0.34 格 —— 所以荷叶、缠绕水草、种在荷叶上的植物、以及水行里的僵尸都曾经比它们该在的位置高三分之一格，荷叶看上去悬在池沿上。修法是在渲染锚点上叠 `frame.y(y) - y`（逐行不同，所以不能写成一个常数），并且**只在该格真的是液体时**才叠。它是纯渲染量：服务端坐标、种植判定与存档都还是那块普通格网。阴影与"冰冻僵尸脚下的冰"也读同一个函数，否则阴影会留在格网上而东西沉到水里。
- **蹦极僵尸的绳与靶是渲染伴侣，不是它的骨骼**（`client/renderer/BungeeRig`）：原版把绳（`BungeeCord.png`）与落点靶（`BungeeTarget.png`）画在僵尸之外，两张图在 `refer/im7/images` 里、不在它的 reanim 里。绳从手画到**视口顶**（`camera().worldTop()`，所以窗口多高都像吊在屏外），靶画在格的着地点（与阴影同一个 `anchorLift`）；两者都在实体之下。它的**下降**不在这两张图里：服务端在 drop/grab/hold/rise 四段写 `Entity.height`（掉落物同一条通道），客户端锚点已经会叠这个量，`AnimationManager` 的插值让它按帧走而不是 20Hz 跳。
- **精灵管线的边界就是 `Tesselator` 一处**：只有一种顶点格式（`VertexFormat.POSITION_COLOR_UV`，9 float），每帧的每次绘制都经过它，`draw()` 把 CPU 侧缓冲一次性上传并画掉，**不做批合并**（`RenderSystem` 也没有矩阵栈，`Matrix4f` 只有 `identity`/`ortho`；深度测试关闭，层级完全依赖提交顺序与 z 常量）。GPU 对象那一半已经做完了：`Tesselator` 只建一块 VAO/VBO 并复用，`draw()` 走 `glBufferSubData` 流式上传（见 `架构变更记录.md`「每个 quad 建销一对 GL 对象」）。**批合并要做对，有三条前提与约束，缺一条就会画错或白做**：
  - **图集是前提**。`Sprite` 的 u0/v0/u1/v1 今天恒为整图（`phase 1: whole image`），每个 texture id 一张贴图——实盘 1140 张 PNG / 170MB。逐 quad 批处理最多合并"相邻且同一张贴图"的那几次，没有图集就几乎没有收益；省 draw call 的收益全在图集那一半。
  - **批的键必须带上 uniform 状态**：`(纹理, 混合模式, 阴影模式, 文字效果)`。`ShaderProgram` 的每个 uniform 都是全局状态且在 pass 内被反复改——`SpriteRenderer` 逐 quad 切 `setShadowMode`、`FontRenderer` 逐**字形**切那组文字效果 uniform、`ControllerPlayback` 与 `ParticleEngine` 逐段切 `blendAdditive`/`blendNormal`、阳光逐帧用 `setPointLight` 上传。漏掉任何一项，阳光的辉光就会串到旁边那株植物上。
  - **flush 时必须按 z 稳定排序**（同 z 保提交顺序）。层级完全靠提交顺序，按纹理重排会直接改画面；稳定排序 + 只在"z 与纹理都相同"的连续段内合并，输出才与今天逐字节一致。
  另外 `Tesselator.begin()` 那条"build 了却没 draw 就抛异常"的不变式是为立即绘制写的，改批之后要挪到帧末 flush（`PvzceClient.render()` 是唯一收口处）。
  今天每个 quad 一次 `glBindVertexArray` + `glDrawArrays`，一帧上千次；实体动画的每个部件各画一次（`ControllerPlayback` 只把混合模式收成两趟：普通一趟、加法一趟）。
- **两种"看不见"是同一套渲染层判定**（`client/mechanic/FogClientMechanic` / `StormClientMechanic`）：
  雾遮住棋盘的一侧、雷雨遮住整块棋盘，两者都画在 `Z = 0.30` 的 `WorldOverlay` 上，并且**都让 `InGameScreen`
  的实体循环跳过站在黑暗里的实体**（`FogClientMechanic.hides(x,y)` 按列、`StormClientMechanic.hides()` 不看位置）。
  它们是"同一件事的两种形状"：雾是空间的斜坡，雷雨是时间的脉冲；两者都不碰任何规则、命中判定或生成。
  - **雾是按原版的格子铺云**：`textures/gui/screen/fog_cloud.png`（`tools/gen_fog_texture.py` 从
    `refer/im7/images/fog_.jpg` 烘出来，1680×190 = 8 帧 210×190）是**一整条连续云带切成的 8 片**，
    逐格按 `x*80-15, y*85-30`（原版 `Board::DrawFog` 的坐标，单位是背景图自己的像素）铺开；帧号由
    格子的 x 位置决定（`210n` 那一片），不是随机挑的——挑错帧相邻格就对不上、带子会出现接缝。
    每格再叠一个缓慢的明暗漂移（原版那两个正弦，周期 5.2s / 9.4s，逐格相位不同）。
    两处容易错、都踩过一次：贴图坐标要乘 `PvzceCamera.boardScale()`（1920×1080 下棋盘比背景图大
    1.8 倍，按世界格直接画会又小又偏），绘制要走**世界格**（`client.drawTextureShaded` 的参数是格，
    不是屏幕像素——原先自己乘 `unitX` 把整条雾带挪出了屏幕）。
  - **隐藏判据与画面同源**：`hides()` 用 `hidingColumn()`（云从格子左边 0.1875 格处开始，所以线落在
    雾的第一列里 0.1875 格处）+ 逐顶点 alpha 的路灯折叠。引擎其实一直支持逐顶点颜色
    （`VertexConsumer.color`），只是没有入口；现在 `PvzceClient.drawTextureShaded` 提供它，
    路灯花的圆洞因此是**平滑的**（每格 4×4 细分、逐角取 alpha），不再是格子马赛克。
    `FogData.alphaAt` 仍然是"哪里算暗"的唯一出处，但它不再被烘成贴图（`fog_alpha.png` 与
    `gen_fog_gradient.py` 因此删掉了）：云是画，`alphaAt` 是判据。
  - **雷雨是服务端的一台时钟**：每 tick 经 `MechanicSyncS2C` 发一次 `StormState.Wire`（**pulse +
    曝光**，12 字节），客户端只用这个数画黑暗与判隐藏 —— "该不该藏"和"画多黑"因此是同一个表达式。
    曝光在服务端由**形状表**算（`StormState.PATTERNS`：双击 / 连续闪烁 / 慢扫 / 单峰余辉，按 `pulse`
    轮换，整条形状铺在 `flash_ticks` 上），所以"闪电长什么样"只有一份实现，续档也接着同一条形状打。
  - **黑暗盖住整个可见舞台**，不是棋盘：用 `camera.worldLeft/Right/Bottom/Top`（可视矩形，单位是格）
    画一块覆盖视口的 quad，马路、房子、小推车带与天空一起变黑，只有 HUD 留在外面 ——
    原先只盖棋盘，看上去是一块夜色贴在画面上而不是天气。
  - **雨声是一条独立的 ambient 循环源**（`SoundEngine.playAmbient/stopAmbient`，与 `PvzceMusicController`
    的四条轨道分开、不参与交叉淡入）：进关卡时起（`PvzceClient.onLevelInit` → `StormClientMechanic.startWeather`）、
    离开时停（`clearLevelClientState`）。4-10 的 `music.cues` 是空列表，所以这一关只有雨声。
    素材本身是**可循环**的（`tools/gen_rain_loop.py`：尾巴等功率交叉淡入自己的头，再用整词变速拼成
    14.3 秒的床），所以循环点听不出来；`-Dpvzce.traceAmbient` 每次起停打一行（带缓冲帧数），
    用来区分"素材有缝"和"被反复重启"。
  - 诊断：`-Dpvzce.traceStorm` 每次"亮 ↔ 暗"翻一次打一行（含 pulse/tick/exposure/darkness）—— 这一族
    故障在屏幕上只表现为"一块黑的"，没有那行字就只能靠猜。
- `LevelStage` / `SceneTileRenderer`：背景舞台、场景瓦片。**几何按背景图分**：`LevelStage.Geometry` 是一个舞台自己的"草坪矩形 + 原生格子尺寸 + 液面帧"，`geometryFor(background)` 是"这张图用哪套几何"的唯一答案 —— `background3`/`background4` → `POOL`（草坪仍从 x=256 起、720 宽，高 510 而不是 500，格子 80×85：原版后院的六条车道，9×6 的棋盘正好铺满，棋盘底边落在图上的 y=590），其余（含没写背景与未知贴图）→ `YARD`（720×500、格子 80×100），`board(w, h, columns, rows, geometry)` 把棋盘等比缩放进选中的那块草坪（恰好一个轴填满，另一个轴留出背景的裸地）。`SceneTileRenderer.render` / `renderBoard` 因此多收一个 `LevelStage.LiquidFrame`（见 §6.3.1）。
- **按行分车型的小推车**（`client/mechanic/MowerClientMechanic`）：画哪些行、每行画什么，都来自 `ClientLevel` 里**解析后**的 `pvzce:mower` 机制块（`MowerData.rowsFor` / `kindFor`；没写 `mower` 的关卡由 `LevelMechanics.effective` 补上每行一辆）；车型是内容 id，美术按 `mechanic/<path>` 取（`pvzce:lawn_mower` → `mechanic/lawn_mower.json`，泳池两行 → `mechanic/pool_cleaner.json`）。位置与状态仍然只有 `MechanicSyncS2C` 里那两个数，所以车型不进包、不占 `PROTOCOL_VERSION`。
- **节奏关卡的四件事**（`client/RhythmPlay` + `InGameScreen.renderRhythmHighway`）：① **时钟**是 `ClientLevel.smoothLevelTicks()`（心跳的两个计数器之差 + 插值），因为谱面按关卡 tick 写、而心跳本身只有 250 ms 精度，单靠它判定的误差比 PERFECT 窗口还宽；② **起点是服务端的数**——`RhythmMechanic` 锚定谱面时经 `MechanicSyncS2C` 发一条 `Status(...)`（锚点在最前，后面跟着能量、战况、乘数与辣椒数），`RhythmClientMechanic` 收进 `ClientLevel.mechanicState`，客户端**不再自己猜**"准备阶段什么时候结束"（那条路差过一个完整的摆阵期：`ClientLevel.preparing()` 在第一包状态到达前默认 false，见 `踩坑清单` 150）；③ **判定**是"这一条 lane 里最近的、还没按过的、在窗口内的那个音符"，发的是音符本身的 tick 与偏差；窗口是**飞行行程的百分比**（5% / 10% / 15% = PERFECT / GOOD / FAIR），所以画面与判定是同一个数（`RhythmChartData.approachTicks`）；④ **漏掉也归客户端说**：窗口关闭还没按的音符自己计一次 MISS 并显示——服务端另外计自己那份分，两边是同一套算术。**时钟跳变不算漏**：`smoothLevelTicks` 允许被心跳校正，一帧跳超过 30 tick 就只把游标推过去（那条判据来自一次真实故障：胶片上 `MISS 127`，一帧里判漏了九千 tick 的音符）。

- **节奏 HUD 的两半，谁算谁的**：画面上"这局打得怎么样"（`PERFECT/GOOD/FAIR/MISS` 统计、连击与最高、
  连续 PERFECT、能量、倍率）全部读服务端的 `RhythmMechanic.Status`；`RhythmPlay` 自己那份计数只用来
  **当帧**回答按键 —— 判定字与那一列的闪光（帧是这一侧的）。这不是洁癖：服务端对同一次按键取
  "两个时钟里更好的那个"，所以两边**按设计**可能给出不同的判定，把两个来源并排画出来就是
  `PERFECT 0 · 连续 PERFECT ×1` 这种自相矛盾（胶片抓到的就是这一帧）。
- **按下了就亮，哪怕没命中**（`RhythmPlay.pressed/pressFlash/pressedGrade`）：按键在**判定之前**
  先记下"哪一列刚被碰过"，给一个 150 ms 的衰减值；命中时这次闪光换成判定色，空按留中性白。
  屏幕侧 `rhythmLaneColour` 三态（命中 = 判定色、空按 = 白、没人碰 = 暗琥珀），判定线与按键胶囊
  同色同闪，判定线还多一条更宽的辉光。理由：空按与"按键没生效"在画面上必须能分辨。
- **判定字是站酷体 + 三条曲线**（`InGameScreen.drawRhythmVerdict` + `RhythmPlay.verdict*`）：
  落点 2.1 倍、生命的前 14% 回落到 1 倍、全程二次曲线上浮 16 单位、最后 45% 淡出，并加
  `TextStyle.outline`（草坪上什么背景都可能有）。曲线在 `RhythmPlay` 里（`VERDICT_NANOS` 的邻居），
  所以 `RhythmPlayTest` 不需要渲染器就能钉住它们。
- **能量条是右侧的竖条**（`InGameScreen.renderEnergyBar`）：挂在窗口高度的 0.78 处往**下**长，
  而不是接在统计行下面 —— 接在下面会长到屏幕外（第一张胶片只拍到进度条后面的一截轨道）。
  轨道 18 单位宽、最高 200，`ENERGY_DOUBLE_AT`/`ENERGY_TRIPLE_AT` 画成两条刻度线并各带 `×2`/`×3`
  标签，填充色就是当前倍率（琥珀 / 冷蓝 / 热红），条顶写着点数。倍率大于 1 时条左边多一个
  `×N` 大字。
- **连续 PERFECT 的乘数写在判定字右边**（`drawRhythmVerdict`）：只有 PERFECT 有，**连续 ≥2 才写**，
  LEFT 对齐在字的右缘之外、跟着同一条弹入曲线缩放与上浮。理由：玩家的眼睛在判定线上，而"这是第 27 个"
  在打的那一刻比右侧那行统计更该被看到；锚点必须跟着字自己的放大走，否则最要紧的那一帧里徽标会滑进字里。
- **连击辣椒有横幅**（`InGameScreen.renderRhythmBanner`）：读 `rhythm.jalapenos()` 这个**累计数**，
  一变多就弹 `火爆辣椒！`（站酷、落点 2.6 倍、1.2 秒）。累计数而不是标志位：丢一包也只会漏一次
  播报，不会漏一个"刚才发生了什么"。
- **结束页的战报**（`client/gui/RhythmScoreText`，两个屏幕共用）：赢在结算页的羊皮纸上（`本局战报` +
  四项判定 + 连击/连续 PERFECT/辣椒 + 一行金币脚注），输在失败浮层上（把 `存活 N 波` 整行换掉——
  节奏关卡没有波，那一行在这一模式里本来就是错的）。数字全部来自 `GameStateS2C.RhythmScore`，
  也就是**关卡结束那一刻**服务端读的那一份，而不是 HUD 那条每 6 tick 一次的流（它在歌尾会差最后几个音符）。
  `RhythmScore.played` 是"这一关有没有谱面"的显式标志——没有谱面与"有谱面但一个音符都没判到"是两件事。
- **关卡列表的行绘制抽成了 `LevelRowRenderer`**：图标、名字、状态行、锁、奖杯、"内含 x 个关卡"
  在两张屏上必须长得一样（`LevelSelectScreen` 与 `LevelCollectionScreen`）。行里右侧的预留带
  （`reservedRight`）同时给奖杯、选中行的 id 文本和集合的"内含 x 个关卡"让位：奖杯在行的右中，
  id 在左上角那一侧，`内含` 在右下角。
- **集合点进去是一张新屏 `LevelCollectionScreen`**：它从客户端自己的关卡列表里按 id 取出集合那一行
  与它的每个成员（**同一份快照**，所以锁与存档不会画成两份），用同一个 `LevelRowRenderer` 画；
  `openScreen` 压栈，返回即回到原来那一页与原来的选中（见 `UI切换与导航架构.md`）。
  集合行本身在列表里不锁（盒子不是关卡），动作按钮变「进入」，双击同一行也进入。
- **判定线与按键都在草坪上**（`InGameScreen.renderRhythmHighway`）：每条**真有音符**的 lane 画一条竖导线、判定线上一个亮块、判定线下方一个按键胶囊，音符画成**它对应的那个键的字母**从草坪顶端沿列飞下来，命中/漏掉都从天上消失；字母取自**玩家当前的绑定表**（`KeyBindings.Action.forLane` → `keyName(code)`，改了绑定就显示改后的键，没绑就不画），命中时胶囊与判定块一起闪成 PERFECT 的黄，判定字画在判定线上方。行模式的 lane 仍然把胶囊画在该行左端（手写谱面用得到）。四个位置上的坑写在注释里：**键与线必须在棋盘里面**——底图是 cover 缩放，1920x1080 下草坪底边只在屏幕上方 36 px，提示条还压着那一段，"棋盘下面"没有地方（见 `踩坑清单` 150）；z 必须是 0.5 那一档（`drawSolid` 的第 5 个参数是 z 不是圆角，见 `踩坑清单` 137）；画在**拖拽种植预览之后**（那一格半透明的方格会把它冲淡）；并且是 `render()` 的最后一笔，**在提示条之后**——模式自己的下沿不能被教学挡住。
- **手瞄植物的瞄准态**（`InGameScreen.aimingPlantId` / `beginAiming` / `renderAimReticle`）：一个**纯客户端**的模式，和选卡一样没有服务端镜像（`PickCardC2S` 也是发过去就被忽略）。第一次点一株"能瞄"的植物进模式并画出 3×3 的准星（橙色十字，比种植高亮更宽一格：它说的是"这一炮盖九格"，不是"这里能种"），第二次点格子发 `FireAtC2S`。右键、点卡槽、点棋盘外都会退出这个模式 —— 它们都走 `cancelSelection()`，那是"把手上的东西放下"的唯一入口。**"能瞄"问的是植物定义里有没有 `pvzce:cob_cannon` 能力**，不是在客户端留一份 id 名单：那会是一份 mod 的炮永远进不来的副本。
- **成对传送门**（`client/mechanic/PortalClientMechanic`）：四只圈全部来自关卡自己的 `pvzce:portal` 块的 `pairs`，客户端**不重算任何东西** —— 谁通到谁、僵尸从哪个口出来都是服务端的事，这一层只回答"画在哪"。一对门的两端用同一组贴图的两段循环区分方向（`a` 端 `idle`、`b` 端 `pulse_reverse`），因为原版 `Portal_Circle.reanim` 里除了脉动方向没有别的东西能区分两端。画在 `Z = 0.05`：地形是 0、最低的实体层是 0.15，所以门在草坪之上、所有站着的东西之下 —— 门是草坪上的一个洞，站在里面的僵尸必须看得见。它和 `MowerClientMechanic` 一样属于"不是内容"的世界层：美术按 `mechanic/<path>` 取（`mechanic/portal.json`，由 `tools/reanim_to_pvzce_all.py` 从原版 reanim 转出），没有注册表条目、没有定义、不占 `PROTOCOL_VERSION`。
- **文字在运行时从 TTF 光栅化，没有烘焙图集**（`client/renderer/font/`）：调用点只认四个**角色**（`Fonts` 的 button / body / bodyMedium / serif），
  `FontRenderer` 一处决定每个角色用哪个字面、em 多大；`TtfFace`（stb_truetype + 自写 cmap 解析，所以格式 12 的扩展区汉字也读得到）按需把一个字
  光栅成 8 位覆盖率，`GlyphAtlas` 用货架装箱排进 2048² 页（**纯 CPU、无 GL、可单测**），`GlyphPage` 只管纹理与上传，`GlyphQuad` 是"这个字画在哪、
  取哪几个纹素"的纯几何。五条踩过的约定：
  - **`y` 是基线，不是行盒顶部**：旧位图渲染器把墨迹下沿放在 `y + (基线行 − 墨迹下沿行)`，那个和恰好让基线落在 `y` 上，
    而它的 240 多个调用点（按钮居中、玩家牌、底板、提示框…）全是按这个锚点写的——TTF 版一度改成"行盒顶部"，整屏文字因此统一偏低一个 ascent
    （实测按钮标签中心差 +51px；改回基线后 +14px，与旧图集的 +17.5px 同量级）。`ascent(scale)` 是"基线之上的高度"，供调用点自己居中。
  - **请求的字号就是 em 盒**，不是 stb 的 `ScaleForPixelHeight`：后者缩放的是 **hhea 行盒**（思源黑体 1160/-288 = 1.448em），
    于是同一个字号下思源比站酷小 1.448 倍，而排版用的 ascent/descent 来自 OS/2（正好 1.0em）。一个字号只有一个含义，两个面才可能混排。
  - **覆盖率既是 alpha 也是 RGB**（白字 + alpha = 覆盖率）：普通精灵路径按 `tex * vColor` 取色、按 `tex.a` 取不透明度，文字特效分支单独读覆盖率，
    四个通道同一个数，两条路才画出同一个形状。
  - **页缓冲是翻转的**：GL 把上传数据的第一行当 t=0（贴图底部），`TextureManager` 为 PNG 打开 `stbi_set_flip_vertically_on_load` 就是这个原因；
    字形图集按"图像第一行最后写"排，`GlyphPage.Slot` 的 v 才与全局约定一致（否则采到的是页的镜像位置，多数时候那里什么都没有）。
  - **一个字形纹素 = 一个设备像素**（字形就按要画的尺寸光栅），所以阴影/描边的 uv 偏移由设备像素除页宽得到，且**上限是图集 gutter**：
    读得更远就采到隔壁那一个字。
  标定：body em = 14 GUI 单位（= 被替换的烘焙图集——98px 字画进 18 单位行——的墨迹高度 13.2），display = body × 1.14（站酷的汉字在自己的 em 里
  画得比思源小，1.14 让两个角色**光学同高**而不是数字相同）；行高 = 1.0em，所以 `lineHeight(1)` 从旧图集的 18 变成 14。`FontRendererTest`
  钉住这两条标定，`GlyphAtlasTest` 钉住通道、行序与基线锚点三条（按 GL 真正读到的那些字节采样，不是按页缓冲的另一种读法）。
- **背景由关卡决定**（`LevelDef.background`，随 `LevelPayload` 下发）：原版每个舞台都画在同一张 1400x600 的画布上，但**格子不是同一套**（前院 9×5×80×100，后院 9×6×80×85），所以背景图不只回答"画哪张画"，还回答"这一个舞台用哪套几何"——`LevelStage.geometryFor(background)` 是唯一的查表点，`InGameScreen`（世界棋盘）、`ChooseSeedsScreen`（预览棋盘）与 `PvzceClient.camera()` 都问它，三处因此不可能对"这块草坪几行、格子多大"有不同看法。关卡没写就用 `LevelStage.BACKGROUND_TEXTURE`（其路径不在泳池名单里，所以落到 `YARD`）；写了但贴图不在（缺资源包）**也照画**，几何仍按它选中的那一套 —— 棋盘会露出缺贴图的棋盘格，而不是变成一张不属于这一关的院子。
  > **编辑器画布是唯一仍按 `LevelStage.YARD` 画的地方**：它不读关卡的 `background`（画布本来就不画背景），所以泳池关卡在编辑器里是 9×5 的草坪格、水面也按格画；游戏内与选卡预览用的是泳池几何。

**场景元素的三种"额外说法"**（`SceneElementArt`，全是可选的，不写就按 id 推路径、按 1 格画）：
- `texture` / `night_texture`：**原版给弹坑画了两版**（白天一版、夜里一版，是同一张图的左右两半），用哪版由关卡的日夜决定（`EntityTextures.forScene(id, night)`，与给草坪上色的同一个时钟）。某种变体缺失就回落白天那版——缺美术不该变成一个看不见的元素。
- `width` / `height`：贴图不等于一格时按这个尺寸**居中**画（原版弹坑是 90x61 像素，比 80x100 的格子宽、比它矮，塞进一格会被压扁）。
- `underlay`：**这个元素画在哪个元素上**。墓碑与弹坑的美术只有石头和洞口，底下是草坪——而一格只存一个元素，所以"底下那层"必须写出来。它写的是**元素 id 而不是贴图**：资源包换草坪时墓碑底下跟着换，关卡把草坪隐藏时（见下）墓碑底下也一起隐藏，否则一块隐藏了草坪的关卡会在每座墓碑下面露出四块绿方块。
- **隐藏的场景元素**（`LevelDef.hiddenSceneElements`，随 payload 下发，客户端解析成 `SceneVisibility`）：每项是元素 id 或 `#` 开头的标签，命中的格子**整个不画**，露出关卡的背景图。这是给"背景图里已经画好草坪"的关卡用的：地形仍然要画在文件里（它决定哪里能种），但再画一遍就等于盖了第二层草坪。草地外边那圈 `GRASS_VISUAL_MARGIN_CELLS` 也一起关掉（它是为了让瓦片不要硬边，而背景图自己会延续），否则隐藏草坪的关卡会被一圈绿框围住。编辑器里不隐藏（作者得看得见自己画了什么），所以"隐藏"只作用于游戏内与选卡预览。
- `SceneShifts`（`client/`）：**哪些格子的元素现在不在自己格子里**。两件事共用一套画法（元素往下挪、在格子下沿裁掉，露出的就是它美术的顶部那一截）：墓碑被 `grave_spawner` 中途种下时**从土里钻出来**（`#pvzce:rises_from_ground` 标签判定，0.35 秒；开局就画好的墓碑不算，全量重同步也不算）、以及被墓碑吞噬者吃掉的墓碑**从上往下沉**（下沉量就是那棵植物自己的高度，见 `架构-实体与能力.md`）。每帧 `sync()` 一次：进度是时钟，沉降是植物状态，`at(x,y)` 只查表。

#### 6.3.1 液体渲染（`client/renderer/liquid/`）

场景元素带 `liquid` 字段时不再走贴图，改由一个**独立的水面 pass** 绘制。它不是第二套精灵管线，而是"几何一次批量、图案全在 shader 里"的一条通道：

| 类 | 职责 |
|---|---|
| `LiquidDef`（`api/content`） | 渲染参数的**唯一载体**：色板、不透明度、深度尺度、泡沫、波形、焦散、高光、静态帧数。`data/<ns>/liquids/*.json` |
| `LiquidGeometry` | 纯函数几何：8 连通 BFS 求**离岸距离**（深度场），外加每格四边/四角的接壤掩码。可单测，不需要 GL |
| `LiquidBatch` | 每格两个三角形，一次 `glDrawArrays`；VAO/VBO 建一次复用 |
| `LiquidShader` | `#version 150 core` 独立 program + 自带 attrib 绑定（0..3） |
| `LiquidRipples` | 固定 16 槽环形缓冲，满了丢**最旧**（新溅的水花才是玩家在看的） |
| `LiquidTextures` | 场景元素 id → 液体定义的唯一解析点（带缓存，`/reload` 时清）；`renderWorld` / `renderGuiBoard` 多收一个 `LevelStage.LiquidFrame`，由它把舞台的液面帧缩进调用者自己的像素 |
| `LiquidRenderer` | uniform 上传、画质档 → 特征位、关闭 shader 时的烘焙帧降级 |

**水面画在哪由舞台声明，不由水格自己决定**（`LevelStage.LiquidFrame`）：帧是"世界格坐标下的原点 + 一个格的尺寸"，水格 `(x, y)` 画在 `origin + (x, y) * cell`。`LiquidFrame.CELL`（原点 0 / 格子 1×1）是普通情形——水格就是水面，今天只有泳池不是：`background3/4` 把水池内壁画在 x 253..961、y 295..433，而两条水行是 y 250..420，所以 `LevelStage.POOL` 的帧是 `(-0.0375, 0.2235294) / (0.9833333, 0.8117647)`（`LevelStageTest.poolWaterLandsOnTheBackdropsBasin` 钉住帧里的 2..4 行正好落在池沿上）。帧只做**平移与缩放**这一件几何事：`LiquidShader` / `LiquidRenderer` 的 uniform 与顶点格式一行未改，游戏内这一侧由 `InGameScreen` 把 `PvzceCamera.liquidFrame()` 交给 `SceneTileRenderer`，预览这一侧由 `ChooseSeedsScreen` 把**同一个世界格帧**交给 `SceneTileRenderer.renderBoard`——两者都传 world cells，缩放那一次只发生在 `LiquidTextures.renderGuiBoard` 里（它是唯一知道"这块棋盘画在多少 GUI 像素上"的地方）。不声明液面的舞台就是 `CELL`，与从前完全一致。
  > **约束：液面帧只许缩一次。** `scaledTo` 是仿射的、不幂等 —— 调用方缩一遍、`renderGuiBoard` 再缩一遍，
  > 水面批次就会落到 `origin≈(2540,893)`、格子 2265×2111（GUI 只有 640×360），整块水被画到屏幕外，
  > 池底只剩背景图那块空白池盆。判据是 `liquid pass:` 日志里的 origin/size：游戏内是
  > `(-0.0375,0.2235)/(0.98×0.81)`，缩过头时是 `(25xx,893)/(2265×2111)`。

**顶点属性**：在共享的 `POSITION(3)+COLOR(4)+UV(2)` 后**追加** `LIQUID(4)`（共 13 float），所以现有所有绘制路径一行未改。`aLiquid` 打包为：格坐标（+1 使符号可承载"该侧是否有岸"）、接壤掩码、角落掩码、深度（3 bit）。**注意坐标轴是反的**：north 标志在 x、掩码的 north 在 y，详见 `LiquidVertexFormat` 的注释。

**水面为什么会动，靠的是哪一层**（这一层是补上去的，别删）：程序化焦散是**加色光**，而泳池的底图很亮（G/B 大片 240~255），加色项没有地方可加 —— 实测逐像素随时间的变化中位数只有 **1.3/255**，等于不动。所以真正让水面动起来的是原版自己那张可平铺焦散图 `textures/scene/water_caustics.png`（`tools/gen_water_caustics.py` 从 `refer/im7/images/pool_caustic_effect.jpg` 转来，对比度拉伸到 0..255 再压到 0.75，因为它是**加**上去的）：它自带宽窄不一的暗巷道，所以是**调制**而不是单纯提亮，两轴以不同速度漂移（`uCausticScroll` 与它的 0.35 倍），相位与速度都在 `liquids/water.json` 的 `caustics` 块里。实测同一块水面 80 帧后的逐像素变化中位数 **6/255**（草地对照 0）。

**着色器次序**（顺序即正确性，改一处要想清楚）：
底图（按**世界格坐标**连续平铺，不是每格重开）→ 水色吸收（`opacity` 是"水占多少"而不是 alpha）→ 程序化焦散网 → **原版焦散贴图（漂移）** → 日光高光 → 菲涅尔 → 泡沫与临陆内缩 → 昼夜色调。
**水体不透明**，只有临陆边缘羽化；内部格之间不软化，否则会在湖心露出接缝。

**画质档**（`config/pvzce-client.toml` 的 `water_quality`，视频设置可切）只切特征位与采样量，**不切几何**，所以三档的水面形状完全一致。三档里的时间项：LOW 一项都不开（"低"就是"不动"），MEDIUM 有波形、高光与**焦散贴图**，HIGH 再加上程序化焦散与菲涅尔。`shaders_enabled=false` 时整条 pass 换成 `textures/scene/water_frames/water_*.png`（`tools/gen_water_frames.py` 生成，由 `static_frames` 决定帧数并循环）。关卡也能单方面把它关掉：`LevelDef.disable_shaders` 为真时 `LiquidRenderer.available()` 直接回答 false（关卡的话压过玩家设置），水面就只剩降级帧 —— 内置关卡里 19 关显式钉成 true（原版背景自带烘焙光影），**泳池与迷雾的关卡（3-1~3-10、4-1~4-10）显式写 false**，白天与夜里的草坪关卡显式写 true（4-5 是夜草坪，也写 true），因为这条水面 pass 本来就是 shader。

**涟漪**：服务端 `LevelServer.emitRipple*` 是唯一权威点（僵尸入水已接入），经 `EffectEventS2C` 的 `ripple`/`ripple_strength` 字段下发，客户端按液体 id 解析后入槽。**splash 的格坐标要过一遍舞台的液面帧**（`InGameScreen` 用 `PvzceCamera.liquidFrame()` 的 `x()/y()`）才入 `LiquidRipples`：涟漪与水面必须活在同一个坐标空间里，否则泳池里那圈水花会浮在水面之上（水面是按帧画的，比水行整体偏低）。涟漪是纯表现，走墙钟而不是 tick，所以暂停时水面照常流动。

**水面的深度是每格量化的**：深浅按 8 连通步数算、6 bit 里占 3 bit，所以 5 行关卡的深浅只有两三档、交界是矩形台阶；
要根治需在 `LiquidGeometry` 里把深度场双线性上采样成逐像素值。编辑器画布走的**就是**同一趟液体渲染
（`CanvasPage.renderBoard` → `SceneTileRenderer` → `LiquidTextures`，只是把投影换成 `beginOverlayWorldView`），
所以"编辑器里的水与游戏内不一致"已经不是问题。`tools/preview_water.py` 是 shader 的 CPU 镜像，靠人工同步常量
——已有测试保证 shader 可编译与 uniform 齐全，但**参数**仍需人工保持一致。
`shaders_enabled=false` 时水面只剩 `water_frames/*` 那几张预烘焙帧，里面只有水色与岸线泡沫：
看不到云纹，也看不到漂移的焦散图。泳池关卡显式写 `disable_shaders: false`，正常路径不受影响；
要把降级路径也补上，得让 `tools/gen_water_frames.py` 把底图与焦散烘进帧里。

### 6.4 动画

- `AnimationManager`：playback 表 + 文件缓存。`play()` 的幂等判据是**当前活动 clip**（循环 clip 在播则不动；已结束的一次性 clip 允许重开），不是 `requestedState`（所以判等用的是**解析后**的 clip 名：`death` 会解析成 `death` 或 `death2` 中的一个）。
- `AnimationVariants`（`client/animation`）：**"这个状态到底播哪个 clip"**。死亡是一族而不是一个 clip，随机只在该美术**真的有**的那几个里挑（报纸僵尸的文件没有 `death2`，以前有一半的死亡会解析到不存在的 clip、静默回落 `idle`，尸体就站着不动六秒）；挑的依据是**实体 id** 而不是掷骰，所以同一局的同一具尸体每次都是同一段，重放也对得上。`death_superlong` 不在池子里（那是重型身体的死法，由定义自己把 `death` 指过去），`death_water` 是family 成员（美术没有就按普通死亡沉下去）。缺 clip 回落 `idle` 时**会按 (文件, 状态) 报一次警告**——这个 bug 之所以藏了很久，就是因为回落是完全静默的。
- **墓碑里钻出来的僵尸**（`InGameScreen.renderRisingZombies`）：画在草坪**之后**，用一条从头顶扫到该格地平线的裁剪线露出来（不是把美术往上挪——两者在屏幕上一样，但裁剪不需要第二份位置）。所以身体是**从土里滑出来**的，而不是"埋在草下 1 秒、然后整个人瞬间站好"。`PvzceConstants.ZOMBIE_RISE_DEPTH_CELLS` 是两侧共用的那个深度：服务端用它推高度，客户端把它读回成"还有多少埋在下面"，两处各写一份就会切错高度。出土的**手臂**是这只僵尸自己的一帧表演（先钻出一只手、身体随后），不是粒子——粒子走墙钟，暂停的关卡里它会继续挥手。掉落的手臂粒子（半血断臂、小推车断臂）仍然走粒子，它们现在画的是整张精灵：`drawTextureQuad` 的 UV 单位是**像素**不是 0..1，之前转了角度的粒子都在采样一个 1 像素的方框，于是被拉成一条细线。
- `MovingTarget`（`client/api`）：`Animatable` 里"有地面速度"的那一半。走路/飞行这类 clip 的**作者速率由实测位移推**（`AnimationPlayback.measureLocomotion`），而位移只有实体才有，所以它是一个独立接口而不是 `Animatable` 上的一个方法——机制道具、UI 预览、掉落物都播 clip 但没有地面速度，给它们编一个位置只会让答案变成假的。位置读的是**绘制位置**（`drawnX/drawnY`），不是权威坐标：脚要踩的是屏幕上那条线。
- `AnimationPlayback`：共用的时间/过渡/事件/生命周期；两个后端 `FlipbookPlayback`（帧序列）与 `ControllerPlayback`（骨骼控制器）。
- `Timeline`：**唯一的时间线数学**（循环 wrap、非循环夹紧、帧查找、延迟默认值）。新增采样方式请走它。
- `AnimationResourceLoader`：clip 公共字段（`loop/on_end/next/transition`）与"animations 条目必须是对象"的校验都只有一份。
- **一个 clip 可以是一条"合成段"**（`tools/reanim_to_pvzce_all.py` 的 `range_frames`）：`range` 收一对数字是"从头放到尾"，收**一串数对**就是"一段接一段放"。这是把原版的**并行时间线**塞回一条 clip 的唯一办法 —— 三线射手的三个头各有一条开火轨道（源里是 29..41 / 70..82 / 111..123，中间隔着别的相位），照 29..123 整段放会得到三秒里两秒半没有头。
- **`phase_windows`：一个 clip 里按阶段各演各的骨骼。** 每条窗口写一个掩码轨道 + 一组骨骼名，语义是"这一段是这些骨骼的戏"，帧号是**clip 自己的**，而**骨骼本身全程都画**：轮到它就用自己的轨迹，其余时间借用 `idle` 第一帧的姿态。两半缺一不可 —— 只按窗口开合（原来叫 `visibility_windows`）会让三线射手的三颗头一颗一颗飞进来；只强制可见而不重新摆姿势，则三颗头会叠在同一个像素上（源文件里"没在演"的部件摆的是无意义的值）。
  > 骨骼名是去重后的（三个头是 `head` / `head_2` / `head_3`），所以**窗口里的正则必须锚定**：`head` 是 `head_2` 的前缀、`headleaf_1` 是 `headleaf_1_2` 的前缀，不锚定就会让两个头同时上场。而 `force_visible_bones` 是用 `fullmatch` 比的 —— 它一度写成裸的 `(head|mouth|blink|face)`，`fullmatch` 只认第一个头，于是**另外两个头与所有 headleaf 在 idle 里被写成 `visible: false`**，站着不动时是"一个头挂三根茎"。
- 缓存：文件存在但解析失败与文件不存在**分开记录**；`invalidate()` 在资源重载时清空两者（否则一个坏关键帧会永久禁用该动画）。

**动画这一层还差两件**：`AnimationHandle` 的返回值在调用点被丢弃（没有任何地方读它，也就没有"播完了"的回执）；
骨骼混合与 Spine 未接入 —— 今天的骨骼动画是逐部件贴图，没有骨骼空间插值，也没有第二条后端。

### 6.5 声音与粒子

- `SoundEngine`（OpenAL）：事件表来自 `assets/pvzce/sounds.json`；音高有统一夹紧范围。**音频源在重新绑定 buffer 之前一律先 `alSourceStop`**：源是 16 个一组的环形缓冲，6 秒的大波提示占用的那个源马上会被下一个音效重用，而 `AL_LOOPING` 是**源的属性、不是 buffer 的属性** —— 一个被要求循环过的源会把之后绑上来的任何 buffer 一直循环下去。`play()` 另有两道保护：同一事件 130ms 内的重复被折叠（齐射不会糊成电流声），以及**一个事件在自己的声音播完之前再次请求会被丢弃而不是叠加**（`nextSource` 返回 -1）—— 上游把同一个事件每帧发几百次时，玩家听到的仍然只是那一个声音，而不是环形缓冲绕圈循环。两道保护都不是"哪些音效只能播一次"的白名单（会公告自己的音效换过一次，白名单也得跟着换）。`-Dpvzce.traceSounds=true` 会按秒打印实际播放的事件计数，用于诊断这类问题。
- **音乐是整首解码的，所以要先解码再等 cue**：`SoundEngine.preload(event)` 在关卡加载时把该关音乐时间线里的事件解成 buffer（服务端在 `LevelInitS2C` **之前**发 `MusicEventS2C.preload`，与那三条 reset 同一条通道），于是 cue 到点时 `alSourcePlay` 是即时的——不预解码的话，一首三分钟的曲子要 **149 ms**（实测）才出声，而谱面时钟那一刻已经在跑，跟着音乐按最好也只能拿 FAIR（见 `踩坑清单` 147）。预解码是同步的，跑在加载画面里（那里卡一下不要钱）：换线程要处理 OpenAL 上下文归属，而且第一次播放仍会和解码抢时间。
- `PvzceMusicController`：菜单/关卡/静音轨与淡入淡出；`ensureMenu(track)` 在**同曲已播时不重启**（界面 `init()` 会在每次改窗口大小时重跑）。**"这个源还占着东西吗"要连暂停一起算**（`SoundEngine.musicSourceActive`：`PLAYING` 或 `PAUSED`，只有 `STOPPED` 才算结束）——暂停对话框会把所有音乐源 `alSourcePause`，而把"暂停"读成"放完了"会让一条 `loop: false` 的曲子被轨道遗忘、离开关卡时谁也停不掉它（见 `踩坑清单` 144）。`leaveLevel()` 因此还有一条硬保证：轨道状态说自己没在放时，它那**两个源**也直接停掉——离关必须静音，不依赖状态机相信什么。
- `PvzceMusicController.ensureMenu(event)` 的语义是**"同曲不重启，异曲要换"**：菜单之间的交接（奖励页 → 关卡列表 → 选卡页）因此真正换曲，而窗口缩放反复调 `init()` 依旧不会重头播。
- **音乐属于"一局"**：轨道名（`menu`/`background`/`battle`/`stinger`）以 `MusicEventS2C.TRACK_*` 为唯一定义（关卡数据与客户端控制器共用同一批字面量）。关卡时间线在波次处把背景轨换成战斗轨，而**只有"离开关卡"这条路会停乐**（`clearLevelClientState()` → `music.leaveLevel()`），重开与编辑器「测试」都不经过它。**每个新关卡实例**由服务端在 `LevelInitS2C` **之前**补发三条 `MusicEventS2C.reset(track)`（`PvzceServer.silenceClientLevelMusic()`）**外加这一关时间线里每个有事件的 cue 的一条 `MusicEventS2C.preload`**（`preloadClientLevelMusic`：客户端趁加载把这曲子解码好；不预解码的话，cue 到点时才开始整首解码——实测 149 ms、约九 tick 的偏差，见 `踩坑清单` 147）——顺序有意义：init 才是启动新轨道的那一步。**同一实例的 resync 不发重置**（它的音乐就是当前状态，`startLevel` 的"同曲不重启"也因此得以保留）。
- `ParticleEngine.tick(seconds)`：**按时间步进**（不是按帧），单帧步长上限 0.1s；寿命以 60tps 的 tick 授权、内部按秒积分。

#### 6.5.1 粒子（数据驱动）

粒子是**数据驱动**的：原版那 81 张粒子贴图与 112 个 emitter 脚本都能用上。

| 位置 | 职责 |
|---|---|
| `ParticleDef`（`api/content`） | 定义载体，**JSON 是扁平的而 record 是嵌套的**：`look`（贴图/帧序列/寿命/缩放/自旋/透明度曲线/颜色）与 `motion`（速度/角度/重力/阻力/落地），另加 `additive`、`count`、`count_spread`。`data/<ns>/particles/<类目>/*.json` |
| `PvzceParticles`（`common`） | 内置能力默认引用的效果 id。**与 `PvzceSounds` 同形**：不要在能力里散落字符串字面量（未知 id 只在客户端每秒报一次日志，症状"这个效果不见了"指向不了任何地方） |
| `ParticleEngine`（`client/particle`） | 世界空间贴图粒子：帧动画、旋转 quad、**加法混合**两趟批处理（普通粒子先画、发光粒子后画，整帧最多切两次混合状态） |
| `RenderSystem.blendAdditive/blendNormal` | 加法混合。原版的光晕就是加法画的，用普通 alpha 画出来是一块盖住底下东西的实心圆盘 |

- **未定义的效果不画东西**，只按 id 报一次日志，所以拼错不会伪装成一个真效果。
- **`scale` 是"画多高"，`aspect` 是"画多宽"**（引擎里 `halfHeight = size/2`、`halfWidth = size*aspect/2`；不写 `aspect` 就是正方形）。`scale` 来自原版的 `ParticleScale`，原版取值约等于"精灵像素 / 80"——星爆 8px → 0.1 ✓。**"画多大"对僵尸掉下来的零件另有一条规矩：按它在模型上的大小来**（`PvzceConstants` 不管这事，数字在各自的定义里）：僵尸美术被拟合进 0.95 格，所以零件比自己的像素尺寸小一圈，路灯 59×57px 在模型上是 0.44×0.425 格 —— `pvzce:zombie_traffic_cone` 就写 `scale: 0.425` + `aspect: 1.294`（宽 = 高 × 1.294 ⇒ 0.55×0.425），铁桶 `0.499` + `1.158`，手臂 `0.5` + `0.65`（26×50px 的原生大小，与出土那只手臂同一尺寸），头颅 `0.354` + `1.38`。**这一条以前是错的**：四边形一律画成正方形，26×50 的手臂被拉宽 1.4 倍，66×123 的铁纱门被压扁，路障还额外写着 1.5（比模型上的自己大 3.5 倍）。
- **曲线表**：`alpha_curve` / `scale_curve` 是 `[[时间, 值], ...]`，时间已归一化到 0..1。直线淡出由 `alpha_from`/`alpha_to` 两个端点表达，只有真正弯曲的（先胀后消的烟、脉冲的光）才带表 —— 这也是转换器 `tools/particles_to_pvzce.py` 的判断依据。
- **单位**：距离是世界格、时间是秒。转换器按 60fps、80 像素/格换算原版的「每帧像素」（330 px/frame 的抛射速度 → 247 格/秒），文件头记录了全部换算因子。
- **贴图来源有三处**：`refer/im7/particles`（粒子贴图）、`refer/anim`（emitter 引用的 reanim 部件，如僵尸帽子）、`refer/im7/images`（零散图，如泥土、水花）。转换器按名字归一化（忽略大小写与下划线）在三处查找，并把结果拷成小写文件名 —— `Identifier` 的 path 只允许小写，而原版文件名是驼峰。
- **精灵表切分**：原版用 `<ImageFrames>`/`<ImageRow>`/`<ImageCol>` 把一格里横排的多帧画在一张 PNG 上，本渲染器一帧一张贴图，所以转换器在生成时把它切开（8 帧 × 2 行的 `dirtsmall` 就是这样变成 `dirtsmall_1..8` 的）。
- **帧序列有两种含义，看有没有帧率**：`frames` + `frames_per_second > 0` 是**动画**（按时间走、`loop` 决定要不要绕回）；`frames` + **没有帧率**是**变体** —— 每颗粒子在出生时随机挑一帧、画到死。原版的碎片发射器就是后者（一个瓶子九块碎片，每颗粒子挑一块），照动画实现会变成 16 片在九张图之间每秒闪 60 次（`ParticleEngine.frameTexture` 的 `frozen` 那一支）。

### 6.2.4 图鉴（`AlmanacScreen`）

背包页（`InventoryScreen`）已经不在了：它只回答"我现在能带什么卡"，而玩家真正会问的是"这东西到底是什么"。图鉴把两个问题一起答了，版式照原版那一本（Suburban Almanac）来 —— **布局是从原版截图上一像素一像素量出来的**，不是照着自己的美术文件想出来的（第一版就是这么做的，做出来完全不是那个东西，见 `架构变更记录.md`）。

**一页的骨架**（原版三页共用的形状）

```
┌──────────────────────────────────────────────────────┐
│                  标题带（页名）                        │
├───────────────────────────────┬──────────────────────┤
│ 条目货架：本页每一条一张卡，    │ 详情卡：图窗、名字、   │
│ 选中的那张高亮；植物卡上印阳光  │ 卡片简介、风味引文、数值│
├───────────────────────────────┴──────────────────────┤
│  图鉴索引                                    关闭      │
└──────────────────────────────────────────────────────┘
```

- **索引页**：原版的封面页 —— 两块板（植物棕木、僵尸蓝灰石）各带一个"查看"按钮，标题带在上方，板里站着**本页第一件内容**（原版画的是向日葵与普通僵尸）。板是画出来的色块而不是把卡片框缩进去：324×484 的框塞进 363×240 只能缩到 49%，剩下四分之三空着。
- **植物页**：8 列 × 4 行，卡片 46×70、间距 (52,80)，与原版同尺寸；每张卡上印**阳光花费**（原版印的就是这个数）。僵尸页：5 列，卡片 76×87、间距 (82,80) —— 两种卡片形状不同是有意的，僵尸卡要宽才装得下走动的身形。
- **详情卡**：两种卡片框按**它自己的像素尺寸**画（植物 324×484、僵尸 324×497），图窗与文字窗的位置是从这两张 PNG 上量出来的常数。名字在文字窗顶部居中，往下依次是卡片简介、数值、风味引文，**用版式而不是剪刀**保证不越界（`drawWrapped` 收一个地板，越线的行直接不画）。
- **颜料顺序**（改错过，写在代码注释里）：不透明层（卡框 → 图窗底色）→ 文字 → 动画预览。卡框画出来的文字窗是不透明的，先画字就会被盖掉；而动画预览要切世界投影，只能最后画。
- 翻页/选择：点货架上任一张卡看它、滚轮与方向键换条目、Backspace 回索引；关闭/索引两个按钮用原版 `Almanac_{Close,Index}Button.png`。
- 整页 800×600 **contain** 缩放（不是 cover）：书自己的边框就在图里，cover 会把标题与底部按钮裁掉。

**内容与文案**

- 条目 = 注册表本身（`AlmanacEntries`）：加一种植物/僵尸/资源，货架自动多一张，没有第二份名单要维护。顺序是原版的图鉴号（植物读 `PlantDef.order`；僵尸是 `AlmanacEntries.ZOMBIE_ORDER` 这张代码表，3-5 的六只小僵尸排在原版名单之后）。
- 文字全部从语言文件读：`<类别>.<ns>.<id>.desc` 是卡片正面那一行、`.flavor` 是引文。**数值不在语言文件里**：阳光、冷却、血量、速度、咬伤、资源价值都从定义读，所以图鉴不会写出游戏不用的数。`GuiLangTest.everyAlmanacEntryHasItsCardLineAndBio` 保证每一件内容都两段齐全。
- **预览全部跑真动画**：货架上的每一张卡、详情卡的图窗、索引页两块板，都是 `ClientEntity` + `AnimationManager` + `beginOverlayWorldView`，与编辑器画布同一条路，世界视口取 `PREVIEW_CELLS`（0.85 格）—— 一格的话豌豆射手只有一个小点。
  - **预览按条目缓存**（`previews`，进页面时建、离开时释放），不是每帧重建：一页最多 32 条，每帧建一次就是一个播放泄漏。
  - **静态回落只对没有骨架的内容生效**（资源；模组的内容如果没写 `animation`）。僵尸的贴图是"一条肢体一张 PNG"，没有整身的静态图可画 —— 第一版拿"动画里最大的那块"当图标，画出来是一条腿，缺贴图时更是整片洋红。植物的种子包图标虽然可用，但塞进非正方形的框会被拉扁，所以也走骨架。
  - 每条内容的脚下是**草地**（`almanac_groundday`）：原版"每株植物的背景随它能用的场景不同，僵尸则统一是白天草坪"，本项目只有草坪这一种，按场景换是换一个 id 的事。
- **僵尸不设"未解锁"**：这一版没有"见过哪只僵尸"的记录，所以僵尸页全部可见；只有植物的锁来自 `SlotResolver.owns`（未解锁画的是同一张卡 + 挂锁，与原版"图鉴是奖品"的做法不同，是本项目的取舍）。
- 资源没有原版页（原版没有资源系统），复用植物页的骨架。

### 6.2.5 变异 HUD（`MutationHud`）

变异关卡（§4.10）的三件表现，都在 `client/gui/hud/MutationHud`：**中央横幅**（新变异出现时按名字 + 抽到的数字喊一句，两端淡入淡出，深色底板压在任意画面上都可读）、**右端常驻列表**（到达顺序，与挤出顺序一致；待机/被压制各自变暗并标出，底部一行是"下次变异 Ns"）、**暗色遮罩**（`MutationEffects.DARKNESS` 时铺一层半透明深蓝，画在 HUD 之下、棋盘之上 —— 背景与光照本来就是客户端按服务端时钟画的，这层是原版浓雾/夜晚的那点"霾"）。

- **数据只从 `MutationStateS2C` 来**，客户端不推：变异会走，所以面板不可能由关卡定义算出来。`InGameScreen.applyMutationState()` 按记录**身份**判断"是不是新的一条"，再做两件事：给 `MutationHud` 决定要不要拉横幅、以及（`cardBar()` 里）在 `cardBarKind` 变化时**丢掉旧卡槽条与手上的卡** —— 卡槽条被换掉后旧索引指向的卡已经不存在了。
- **名字与数字**：`label()` 拼"名字：主体 ×倍率"。名字读语言文件的 `mutation.<ns>.<名>`（`GuiLang`），服务端那份 `MutationText` 只用于横幅、且会带上抽到的数字；跨线的只有 id，所以两边各有一处文案，加新变异时语言文件要写（同内容 id 的处境）。
- **`MutationEffects` 是位集合**：多个变异可以要同一种特效，客户端问的是"有没有"（`anySet`），不是"哪一条要的"。

**运行时发放的工具**（打地鼠的锤子）走同一份包：`MutationStateS2C.tools` 是 `ToolGrant`（id / 是否默认点击 / 是否免费 / 冷却），`ToolClientMechanic.tools()` 把它拼在关卡声明的工具块**后面**，于是 `defaultTool` 与光标锤子（`InGameScreen.renderDefaultToolCursor`）都自然生效，变异被挤出时锤子跟着消失 —— 这也是那份列表**不进 `mechanicState` 缓存**的原因。
