# 验证与流程约定（按需，不是每轮全量）

> 这份文件是**验证强度与工作流程**的唯一出处。其它文档（`00` 的导航、`01`/`02`/`03` 的阶段验收、
> `关卡机制与拼装式编辑器-设计方案` 的推进方式、`当前项目架构.md` §9）只指向这里，不再各写一份。
> 冒烟钩子本身（`pvzce.smoke*` 的完整参数表、坑与典型组合）在 `冒烟与截图指南.md`；
> "会再犯的教训"按主题累积在 `踩坑清单.md`（与本文的分工：这里是**约定**，那里是**案例**）。

---

## 1. 一句话

**默认不跑全量、不拍截图。** 一轮改动验到什么程度由改动面决定，没有硬性分级，也没有
"每轮必须测试全绿 + 截图冒烟"的约定。判断留给人（或 agent），在交付说明里写清跑了什么即可。

| 改动面 | 跑什么 | 代价 |
|---|---|---|
| 纯函数 / 数据 / Codec / JSON / 工具类 | 相关测试类：`./gradlew :pvzce-game:test --tests "com.pvzce.<包>.*"` | 数秒 |
| 服务端逻辑 / 网络 / 存档 / 关卡加载 | `./gradlew :pvzce-game:test`（全量单测） | 约 20s |
| 界面 / 渲染 / 动画 / 输入 | 上面 + **一次**截图冒烟（见下） | 一次约 12s |
| 文档 / 注释 / 纯文字 | 不跑 | — |
| 发版 / 跨模块重构 | 全量 + 一份覆盖主要画面的冒烟清单 | — |

没有"必须"的一档：改一行常量不必跑全量，改一处界面也不必把每个屏幕都拍一遍。
**入口只用 Gradle 原生 `--tests`**（不额外包 task、不写脚本）。

### 截图冒烟的纪律（硬性数量）

- **一次改动最多 1 次冒烟启动。** 要看 6 个时刻就一次启动拍一整条胶片：
  `-Ppvzce.smoke="… pvzce.captureFrame=<第一帧> pvzce.captureEvery=<间隔>"` ——
  `captureEvery` 是既有开关（`SmokeDriver`），不要一帧一次 Gradle。
- **成品图最后只拍一次**：改动定稿后再拍要交付/写进文档的那张，中间过程图不要重复拍。
- **输出必须落在仓库内**（`.smoke/<主题>/`）：写到 `/tmp` 会被沙箱**静默**吞掉（无报错、无文件）。
- **`GRADLE_USER_HOME=$PWD/.gradle-user`**：`~/.gradle` 是只读的，不加就会在 wrapper 解压阶段失败。
- 迭代顺序：**先单测**（秒级）→ 画面/行为确认（快照或探针）→ **最后**才写测试与文档。

## 2. 开工前的确认门（硬性）

动手写代码前，先给出 **3~5 行**，等答复再开工：

1. **我读到的事实**：素材盘点的结果（见 §3）、涉及的文件/定义、现状到底是什么；
2. **打算怎么做**：要改哪些文件、改成什么、影响面；
3. **我不确定的地方**：取舍点、两种读法、需要用户决定的事。

要确认的是**隐含事实与取舍**（原版行为、数值、位置/朝向、动哪些东西），
**不是复述用户的指令** —— "把 A 改成 B"这种明确指令直接做，不用回头问"我真的改成 B 吗"。

为什么是硬性：**猜错一次的代价约等于改对一次的 2.5 倍**（先加、再删、文档与测试各写两遍）。
这一条来自两次真实代价：把"在岸上的动画不对"读成"位置不对"，加了一整套数据字段与客户端映射又被删掉；
把"爆炸时间太长"读成动画播放速度，真正超时的是服务端粒子。

## 3. 动手前的素材与实现盘点（一条命令级）

任何涉及"原版长什么样"的改动，先盘点，再设计：

- **美术/动画**：列出源文件的动画清单（reanim 的 `anim_*` mask 列表、目标 JSON 的 clip 列表）。
  一张 reanim 里的动画**远不止**转换器默认导出的那几段 —— `Zombie.reanim` 里有 `anim_swim`，
  `PoolCleaner.reanim` 有四段 mask，漏一段就是"僵尸在水面上走"这种只能靠肉眼发现的 bug。
- **现成素材**：先在 `refer/` 里找贴图/动画/音效（原版素材优先于任何外部资料）；
  要找"水面的样子"就先 `ls refer/im7/images | grep -i water`。
- **既有实现**：同一件事是不是已经有机制（`*Capability` / `level/mechanic` / `MowerData` 这类数据块），
  别新造一套平行概念。
- **引用面**：改了数据字段/行为，先 grep 出所有引用者（关卡、测试、文档、编辑器），
  免得改一半留下一处静默失效。

盘点的结果就是 §2 确认门里的"我读到的事实"。

## 4. "太长 / 太短 / 不对" 的排查顺序

1. **先把这条链上所有时钟/元素列全并写上数字**（引信、片段时长÷rate、`linger_ticks`、粒子寿命、
   音效长度；位置、姿势、朝向、层级……），再动手。
2. **只改最大的那一项。** 一次改一项，改完再量。
3. 抱怨里"位置"和"动画"要分开确认：它们通常能独立对错，一起改就会把做对的那半也推翻（见 §2 的例子）。

| 例 | 表面症状 | 真正的大头 |
|---|---|---|
| 樱桃炸弹 | "爆炸时间太长" | 动画 rate 只是其一；`pow` 粒子 0.833 s（前 2/3 全不透明）才是主因 |
| 水池小推车 | "动画也不对" | 位置本来是对的，错的是停靠时用了"水中"那半段 mask |

---

## 5. 朝向 / 相位 / 对齐：先探针，不推导

凡是"这张图和那个格子对不对得上"的问题，**放探针量，不要用代数推**：

- 探针 = 一张几条纯色带的临时贴图 / 四个角各采一次像素，**一次冒烟启动**就能读出映射关系；
- 探针产物放 `.smoke/`，不进仓库；结论（含推导出来的公式）写进代码注释与文档；
- 依据是真实案例：底图采样是**镜像**的（世界第 Y 行读九格贴图的第 `9-Y` 行），
  按公式推了两版都错，探针两分钟定案。

## 6. 用例的增删判据

- **加**：只有**修掉了一个真 bug** 才给它加回归用例。已有不变量覆盖的行为不重复加；
  "顺手补一个也更保险"不是理由。
- **删 / 合**：与别的用例重叠、只锁实现细节、或断言同义反复的用例可以直接合并或删除；
  删之前先给出清单（谁被谁覆盖），不要静默删。
- **不记数**：文档不再写"测试全绿（N 例）"。例数不是指标，也不作为验收条件：
  它只会让每一轮都倾向于"再加几个用例"而不是"改对"。
- **偶发失败必须当成缺陷处理**：要么改成确定性断言，要么删掉，不允许留着"单独跑必过"的用例 ——
  那会让"全绿"这个信号本身失效。

## 7. 界面为什么是"按需"而不是"每轮"

`@PvzceGametest` 注册式集成测试与离屏 FBO 图 diff **都还没建**（规划见 `03-第三阶段` §3.6.1），
所以界面目前**没有自动化验证**，只能截图人工核对。这正是"按需"的原因：

- 单测能断言的（控件树、屏幕栈、客户端发了哪个包）**用单测，不要拍图** ——
  `Screen.dispatchMouseClicked` + `Connection.createMemoryPair()` 就是为这条路留的口子。
- 只有"画面对不对"这一类问题才拍图，并且一次拍完要看的那些帧（§1 的截图纪律）。
- 拍图时**务必带 `-Ppvzce.gameDir=<临时目录>`**，否则会写进真正的游戏目录（见冒烟指南 §2.2）。

## 8. 文档维护与义务分级

**必须写**（改动落地后）：

- `架构变更记录.md`：现象 → 定论。**只记最终落地的做法**；被回退的尝试最多留一行
  （"曾试 X，已回退，原因 Y"），不给每个错误写长文。
- 测试（按 §6 的判据加）。
- `当前项目架构.md`：只有"当前能力/已知差距"真的变了才改（§9 的差距清单、目录约定等）。
- 踩过的坑：`踩坑清单.md`（按主题累积，一条 = 现象 → 判据/怎么避免 → 出处）。

**默认不写**：

- `docs/mod-guide/*`：**不跟着改动更新**，只在用户点名时改（它是给第三方 mod 作者的对外文档，
  内部实现与关卡内容的改动不欠它一笔）。
- 规划文档（`01`/`02`/`03`）：记路线，不随每次实现回写。

**其余三条老规矩不变**：

- **as-built 文档只写现状**：`当前项目架构.md` 与 `UI切换与导航架构.md` 描述"现在是什么样"，
  不写"以前是什么样"。历史放 `架构变更记录.md`。
- **一个事实只写一处**：能被别处指过去的内容不在两份文档里各维护一份。
- **改动没有传遍所有文档的义务**：只有该文档描述的行为真的变了才改它。

**写文档的时机**：画面或行为**确认通过之后**再写。不要为还没验证的改动先写变更记录 ——
回退时那份记录要重写第二遍，这是返工成本里最容易被忽略的一半。

## 9. 对用户有决定权的事实：不查资料

"原版到底是不是这样""这个数值该多少""关卡该给哪首曲子"这类问题，用户是最终决定权人：

- 按其判断改，并在 `架构变更记录.md` 里注明**这是用户定的取舍**（必要时写"与原版/W 不同"），
  免得下一轮被"按原版修正"改回去；
- 不为这种事实花检索预算；确实需要佐证时，只说一句"外部资料写的是 X"，不展开论证。

## 给测试开一个诊断开关

`gradle test` 会把 `-Ppvzce.smoke=名字=值` 的每一项转成测试 JVM 的系统属性（`pvzce-game/build.gradle` 的 `tasks.named('test')`），并且开着 `testLogging.showStandardStreams`，所以用 `Boolean.getBoolean("pvzce.xxx")` 保护的诊断输出可以直接这样看：

```bash
./gradlew :pvzce-game:test --tests '*AnimationLocomotionTest*' \
    -Ppvzce.smoke=pvzce.traceLocomotion=true
```

Gradle 的 `-D` 只到 daemon，进不了 fork 出来的测试进程——和 `run` 任务里的冒烟参数是同一件事。
