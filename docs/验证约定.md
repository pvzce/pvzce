# 验证与流程约定（按需，不是每轮全量）

> 这份文件是**验证强度与工作流程**的唯一出处。其它文档（`00` 的导航、`01`/`02`/`03` 的阶段验收、
> `关卡机制与拼装式编辑器-设计方案` 的推进方式、`当前项目架构.md` §9）只指向这里，不再各写一份。
> 冒烟钩子本身（`pvzce.smoke*` 的完整参数表、坑与典型组合）在 `冒烟与截图指南.md`；
> "会再犯的教训"按主题累积在 `踩坑清单.md`（与本文的分工：这里是**约定**，那里是**案例**）。

---

## 1. 一句话

**默认不跑全量、不拍截图。** 一轮改动验到什么程度由改动面决定，没有硬性分级，也没有
"每轮必须测试全绿 + 截图冒烟"的约定。判断留给人（或 agent），在交付说明里写清跑了什么即可。

| 改动面 | 跑什么 | 代价 |
|---|---|---|
| 纯函数 / 数据 / Codec / JSON / 工具类 | 相关测试类：`./gradlew :pvzce-game:test --tests "com.pvzce.<包>.*"` | 数秒 |
| 服务端逻辑 / 网络 / 存档 / 关卡加载 | `./gradlew :pvzce-game:test`（全量单测） | 约 20s |
| 界面 / 渲染 / 动画 / 输入 | 上面 + **一次**截图冒烟（见下） | 一次约 12s |
| 文档 / 注释 / 纯文字 | 不跑 | — |
| 发版 / 跨模块重构 | 全量 + 一份覆盖主要画面的冒烟清单 | — |

没有"必须"的一档：改一行常量不必跑全量，改一处界面也不必把每个屏幕都拍一遍。
**入口只用 Gradle 原生 `--tests`**（不额外包 task、不写脚本）。

**一个例外**：**新内容**（新数值、新界面/卡面、新美术）有硬性的证据要求，见 §10 ——
那里管的是"证据的种类"，不是"跑多少"。

### 截图冒烟的纪律（硬性数量）

- **一次改动最多 1 次冒烟启动。** 要看 6 个时刻就一次启动拍一整条胶片：
  `-Ppvzce.smoke="… pvzce.captureFrame=<第一帧> pvzce.captureEvery=<间隔>"` ——
  `captureEvery` 是既有开关（`SmokeDriver`），不要一帧一次 Gradle。
- **成品图最后只拍一次**：改动定稿后再拍要交付/写进文档的那张，中间过程图不要重复拍。
- **输出必须落在仓库内**（`.smoke/<主题>/`）：写到 `/tmp` 会被沙箱**静默**吞掉（无报错、无文件）。
- **`GRADLE_USER_HOME=$PWD/.gradle-user`**：`~/.gradle` 是只读的，不加就会在 wrapper 解压阶段失败。
- 迭代顺序：**先单测**（秒级）→ 画面/行为确认（快照或探针）→ **最后**才写测试与文档。

## 2. 开工前的确认门（硬性）

动手写代码前，先给出 **3~5 行**，等答复再开工：

1. **我读到的事实**：素材盘点的结果（见 §3）、涉及的文件/定义、现状到底是什么；
2. **打算怎么做**：要改哪些文件、改成什么、影响面；
3. **我不确定的地方**：取舍点、两种读法、需要用户决定的事。

要确认的是**隐含事实与取舍**（原版行为、数值、位置/朝向、动哪些东西），
**不是复述用户的指令** —— "把 A 改成 B"这种明确指令直接做，不用回头问"我真的改成 B 吗"。

为什么是硬性：**猜错一次的代价约等于改对一次的 2.5 倍**（先加、再删、文档与测试各写两遍）。
这一条来自两次真实代价：把"在岸上的动画不对"读成"位置不对"，加了一整套数据字段与客户端映射又被删掉；
把"爆炸时间太长"读成动画播放速度，真正超时的是服务端粒子。

## 3. 动手前的素材与实现盘点（一条命令级）

任何涉及"原版长什么样"的改动，先盘点，再设计：

- **美术/动画**：列出源文件的动画清单（reanim 的 `anim_*` mask 列表、目标 JSON 的 clip 列表）。
  一张 reanim 里的动画**远不止**转换器默认导出的那几段 —— `Zombie.reanim` 里有 `anim_swim`，
  `PoolCleaner.reanim` 有四段 mask，漏一段就是"僵尸在水面上走"这种只能靠肉眼发现的 bug。
- **现成素材**：先在 `refer/` 里找贴图/动画/音效（原版素材优先于任何外部资料）；
  要找"水面的样子"就先 `ls refer/im7/images | grep -i water`。
- **既有实现**：同一件事是不是已经有机制（`*Capability` / `level/mechanic` / `MowerData` 这类数据块），
  别新造一套平行概念。
- **引用面**：改了数据字段/行为，先 grep 出所有引用者（关卡、测试、文档、编辑器），
  免得改一半留下一处静默失效。

盘点的结果就是 §2 确认门里的"我读到的事实"。

## 4. "太长 / 太短 / 不对" 的排查顺序

1. **先把这条链上所有时钟/元素列全并写上数字**（引信、片段时长÷rate、`linger_ticks`、粒子寿命、
   音效长度；位置、姿势、朝向、层级……），再动手。
2. **只改最大的那一项。** 一次改一项，改完再量。
3. 抱怨里"位置"和"动画"要分开确认：它们通常能独立对错，一起改就会把做对的那半也推翻（见 §2 的例子）。

| 例 | 表面症状 | 真正的大头 |
|---|---|---|
| 樱桃炸弹 | "爆炸时间太长" | 动画 rate 只是其一；`pow` 粒子 0.833 s（前 2/3 全不透明）才是主因 |
| 水池小推车 | "动画也不对" | 位置本来是对的，错的是停靠时用了"水中"那半段 mask |

---

## 5. 朝向 / 相位 / 对齐：先探针，不推导

凡是"这张图和那个格子对不对得上"的问题，**放探针量，不要用代数推**：

- 探针 = 一张几条纯色带的临时贴图 / 四个角各采一次像素，**一次冒烟启动**就能读出映射关系；
- 探针产物放 `.smoke/`，不进仓库；结论（含推导出来的公式）写进代码注释与文档；
- 依据是真实案例：底图采样是**镜像**的（世界第 Y 行读九格贴图的第 `9-Y` 行），
  按公式推了两版都错，探针两分钟定案。

## 6. 用例的增删判据

- **加**：只有**修掉了一个真 bug** 才给它加回归用例。已有不变量覆盖的行为不重复加；
  "顺手补一个也更保险"不是理由。
- **删 / 合**：与别的用例重叠、只锁实现细节、或断言同义反复的用例可以直接合并或删除；
  删之前先给出清单（谁被谁覆盖），不要静默删。
- **不记数**：文档不再写"测试全绿（N 例）"。例数不是指标，也不作为验收条件：
  它只会让每一轮都倾向于"再加几个用例"而不是"改对"。
- **偶发失败必须当成缺陷处理**：要么改成确定性断言，要么删掉，不允许留着"单独跑必过"的用例 ——
  那会让"全绿"这个信号本身失效。

## 7. 界面为什么是"按需"而不是"每轮"

`@PvzceGametest` 注册式集成测试与离屏 FBO 图 diff **都还没建**（规划见 `03-第三阶段` §3.6.1），
所以界面目前**没有自动化验证**，只能截图人工核对。这正是"按需"的原因：

- 单测能断言的（控件树、屏幕栈、客户端发了哪个包）**用单测，不要拍图** ——
  `Screen.dispatchMouseClicked` + `Connection.createMemoryPair()` 就是为这条路留的口子。
- 只有"画面对不对"这一类问题才拍图，并且一次拍完要看的那些帧（§1 的截图纪律）。
- 拍图时**务必带 `-Ppvzce.gameDir=<临时目录>`**，否则会写进真正的游戏目录（见冒烟指南 §2.2）。

## 8. 文档维护与义务分级

**必须写**（改动落地后）：

- `架构变更记录.md`：现象 → 定论。**只记最终落地的做法**；被回退的尝试最多留一行
  （"曾试 X，已回退，原因 Y"），不给每个错误写长文。
- 测试（按 §6 的判据加）。
- `当前项目架构.md`：只有"当前能力/已知差距"真的变了才改（§9 的差距清单、目录约定等）。
- 踩过的坑：`踩坑清单.md`（按主题累积，一条 = 现象 → 判据/怎么避免 → 出处）。

**默认不写**：

- `docs/mod-guide/*`：**不跟着改动更新**，只在用户点名时改（它是给第三方 mod 作者的对外文档，
  内部实现与关卡内容的改动不欠它一笔）。
- 规划文档（`01`/`02`/`03`）：记路线，不随每次实现回写。

**其余三条老规矩不变**：

- **as-built 文档只写现状**：`当前项目架构.md` 与 `UI切换与导航架构.md` 描述"现在是什么样"，
  不写"以前是什么样"。历史放 `架构变更记录.md`。
- **一个事实只写一处**：能被别处指过去的内容不在两份文档里各维护一份。
- **改动没有传遍所有文档的义务**：只有该文档描述的行为真的变了才改它。

**写文档的时机**：画面或行为**确认通过之后**再写。不要为还没验证的改动先写变更记录 ——
回退时那份记录要重写第二遍，这是返工成本里最容易被忽略的一半。

## 9. 对用户有决定权的事实：不查资料

"原版到底是不是这样""这个数值该多少""关卡该给哪首曲子"这类问题，用户是最终决定权人：

- 按其判断改，并在 `架构变更记录.md` 里注明**这是用户定的取舍**（必要时写"与原版/W 不同"），
  免得下一轮被"按原版修正"改回去；
- 不为这种事实花检索预算；确实需要佐证时，只说一句"外部资料写的是 X"，不展开论证。

## 10. 新内容的"体验级"自验（数值 / 界面 / 美术三类硬性）

§1 的"按需"管的是**改动面**，这一节管的是**证据的种类**：一个改动可以测试全绿、冒烟也拍过，
却仍然不合格 —— 如果它没有回答"玩家会遇到什么"。

**机制级证据**（编译过、单测断言了某个机制、代码里挂上了）和**体验级证据**
（这个数在一局里是多少、这张卡玩家看不看得懂、这个美术动起来像不像）是两种东西，
不能互相顶替。漏掉的问题几乎都出在把前者当成了后者。

### 10.1 要主动防的三种倾向

1. **用机制的名字写断言。**"卡变了""按间隔来了一只""地面单位会掉血"都是真的，
   但玩家感受到的分别是"换来的卡能不能用""一局会被拿走多少""这东西是不是免费又全局"。
   机制断言通过就结案，是漏检的主要来源：**断言应该写在玩家那一侧的量上，机制只是手段**。
2. **数字自己拍。** 新内容的间隔、倍率、概率如果来自规划文档里一个人写的表，而做的时候一局都没跑过，
   那它不是"定好了"，是**没验过**。用户没给数的地方就等于**还没有答案**，
   要拿模拟结果或明确的取舍说明去补，而不是随便定一个数就往下做。
3. **把"和原版一致"做成"功能一致"。** 原版参照物不在仓库里时，容易用"能跑、挂得上、看一眼没崩"结案。
   参照物缺失要**明说**，把"这些参数是估的"写进 `todo.md`，不要把估的东西写成"已实现"。

### 10.2 三类硬性证据（缺一项 = 该批次未完成）

| 类别 | 必须产出 | 合格判据 |
|---|---|---|
| **数值 / 节奏** | 一段**模拟输出**：跑真 `LevelServer`，报一局的量（拿走了多少、给了多少、峰值多少、多久打完） | 间隔一律换算到**档位倍率之后**的秒数并写出来；**免费 / 永久 / 全局**的效果单独算一次量级，和玩家已有的手段比一比 |
| **界面 / 卡面** | **一张定点截图**（真实窗口尺寸下的那一屏，不是"某次冒烟里顺便有一张"） | 这张卡/这一行字回答了玩家的问题：能不能用、要多少钱、为什么不能用；不成立的选项必须有明确标记 |
| **美术 / 动画** | 一条**帧带**（`captureEvery`），至少覆盖 idle 加一个动作状态 | 头 / 手 / 影子在动起来的时候对得上；没有原版参照时，把"参数是估的"写进 `todo.md` |

其余类别（机制、存档、网络、数据校验）按 §1 的老规矩：相关测试类或全量单测，建议性。
这三类是**唯一**的硬性例外：它们没有自动化验证（§7），所以"没拍 / 没跑"就等于没有证据。

### 10.3 内容在上下文里成立吗（建议性，但优先）

一件新内容（一张卡、一种僵尸、一条变异、一个关卡机制）进入某个上下文之前，先问一次
**"它在这个上下文里成立吗"**，并把判据写成一句话：

- 这张卡能不能在这块棋盘上种下去（地形、水位、前置植物）？
- 这条变异有没有成本、有没有上限、会不会同时作用于全场？
- 这只僵尸出现在这一关时，玩家手里有没有对付它的东西？

答不上来的，要么改内容，要么在关卡 / 卡池那一层加一道过滤。两者都比"反正机制是通的"好。

## 11. 上线前 5 分钟快速验收（给用户的）

> 这一节是**玩家侧**的验收：新内容做完之后按顺序走一遍，专抓"机制通了但体验不对"的问题。
> 每行是"看什么 → 合格 → 不合格通常长什么样"，五分钟能走完。

| # | 看什么 | 合格 | 不合格的样子 |
|---|---|---|---|
| 1 | 标题页 | 按钮不多不少，没有红字报错挂着 | 按钮挤在一起 / 有报错行 |
| 2 | 进新关卡，先看卡槽 | 每张卡有价格，不能用的卡有明确标记 | 卡片空白、没价格、看不出为什么点不了 |
| 3 | 放两个植物、等一波 | 节奏有呼吸，提示自己会消失 | 一开局就被压死 / 提示一直挂在屏幕上 |
| 4 | 有传送带或新卡条时 | 工具卡在带子**外面**，新卡从右边滑进来 | 工具卡跟着带子跑 / 卡从中间冒出来 |
| 5 | 有新僵尸或新美术时 | 走动、攻击、死亡三个状态都对得上 | 头/手/影子错位，贴图糊成一团 |
| 6 | 有变异时 | 面板上每条都读得懂，抽到的变异看得见效果 | 名字看不懂 / 强到没得玩 / 弱到看不出 |
| 7 | 有商店或新页面时 | 价格、余额、买完的变化都看得见 | 数字不变、点了没反应 |
| 8 | 退出前 | 聊天/控制台没有刷屏报错 | 一直刷红字 |

任何一行不合格，按 §10 的类别回到对应的硬性证据上补：数值缺模拟、界面缺截图、美术缺帧带。

## 12. 一次内容批次怎么走（固定动作 + 可直接复制的模板）

§1 定**强度**（跑多少）、§10 定**证据种类**（拿什么证明），这一节定**顺序与模板**：
从"这一批要加什么"到"提交并写报告"的一整套动作，任何一批内容都照这个走。

### 12.1 固定动作（七步）

1. **盘点**（§3）：列出既有素材与既有实现 —— 动画清单、`refer/` 里有什么、有没有现成机制。
   没有参照物的东西，在这一步就说清楚"我要估"。
2. **改代码**：一次只改一件事。行为不对时按 §4 先把时钟/元素列全，再改最大的那一项。
3. **跑对应档位的单测**（§1 的表）。
4. **玩法类自己模拟玩**：起真 `LevelServer`（+ `Connection.createMemoryPair()` 当需要过网络），
   跑够 tick 再断言 —— **不是"编译过了"**。harness 在 `testutil/ServerHarness` / `ClientHarness`。
5. **按 §10 补体验级证据**：数值 → 一段模拟输出；界面/卡面 → 一张定点截图；
   美术/动画 → 一条帧带。一次改动最多 1 次冒烟启动（§1 的截图纪律）。
6. **写文档**（行为确认通过之后）：按 §8 的义务清单走 —— 哪些必写、哪些默认不写都在那里，
   这里不重复一份。
7. **提交**：`git add -A && git commit`，信息见 §12.3。

按类别的"做完了"口径（与 §10 的三条硬性证据互补）：

| 类别 | 做完了 = |
|---|---|
| 玩法 / 数值 | 在测试里模拟玩过；数值有一局的量（§10.2） |
| 动画 | 状态 ↔ clip 的配对按代码逐一核过；能截图的拍过帧带 |
| 界面 | 能用 `dispatchMouseClicked` + harness 断言的写单测；只有"画面对不对"才拍图，并且拍过 |
| 内容（植物/僵尸/关卡） | `BuiltInLevelsValidateTest` 一类的校验要过；新内容有"点名每一件"的用例 |

### 12.2 命令模板（复制即用）

> 冒烟钩子的**完整**清单在 `冒烟与截图指南.md` §4（那份表是唯一出处）；这里只是最常用的三条。

```bash
export GRADLE_USER_HOME=$PWD/.gradle-user      # ~/.gradle 只读，不加会在 wrapper 阶段失败
export GD=$PWD/.smoke/gd                        # 一次性的游戏目录

# 单测：一个包 / 一个类 / 全量
./gradlew :pvzce-game:test --tests "com.pvzce.common.level.mutation.*"
./gradlew :pvzce-game:test --tests 'com.pvzce.server.VaseTest'
./gradlew :pvzce-game:test

# 冒烟：路径必须落仓库内、必须绝对路径（写 /tmp 会被静默吞掉）
mkdir -p .smoke/<主题>
./gradlew :pvzce-game:run -Ppvzce.gameDir=$GD -Ppvzce.smoke="\
pvzce.smokeLevel=pvzce:yard/survival/endless_lawn_day \
pvzce.smokeFrames=400 pvzce.captureFrame=200 pvzce.captureEvery=2 \
pvzce.capturePath=$PWD/.smoke/<主题>/s.png"

# 只拍一屏（标题页 / 数据包页 / 商店页 …）
./gradlew :pvzce-game:run -Ppvzce.gameDir=$GD -Ppvzce.smoke="\
pvzce.smokeScreen=packs pvzce.smokeFrames=200 pvzce.captureFrame=180 \
pvzce.capturePath=$PWD/.smoke/<主题>/packs.png"

# 在关卡里执行命令（`+` 代表空格，`|` 分隔多条）
./gradlew :pvzce-game:run -Ppvzce.gameDir=$GD -Ppvzce.smoke="\
pvzce.smokeLevel=pvzce:yard/survival/mutation_normal \
pvzce.smokeCommands=/mutation+add+pvzce:flood_lawn \
pvzce.smokeFrames=900 pvzce.captureFrame=800 \

```

诊断开关（服务端拒绝的原因 / 缺贴图 / 卡顿 / 音轨打架）：
`-Dpvzce.traceMessages=true`、`-Dpvzce.traceTextures=true`、`-Dpvzce.traceFrames=true`、

### 12.3 提交信息模板

一行中文，说清"这一批做了什么"；**不要**写 `fix bug`、`update` 这类没有信息量的字样。
一批多件事时用一行标题 + 若干行正文（正文写"为什么"，不写 diff 已经说了的"改了什么"）：

```
修复变异卡槽覆盖顺序、传送带保留工具、无尽分类合并、提示框 15s 上限
世界 4：4-1 ~ 4-10（含迷雾与三条奖励）
20 条新变异（二）：场地与僵尸突袭组
```

### 12.4 一份收官报告的结构

报告是**这一轮任务的**交付物（放在 `docs/`，文件名带任务名），七段：

1. **一句话**：这一轮做了什么、用户报的问题与需求各自的状态。
2. **需求对照表**：每一条 —— 用户原话 → 落地在哪 → 怎么验的 → 现在的行为。
3. **新增内容表**：每项一行"是什么、在哪里、怎么验的"。
4. **break change 清单**：变了什么、为什么、旧存档会怎样（例如分类合并导致的关卡 id 变更）。
5. **顺手修掉的既有缺陷**：现象 → 根因（文件）→ 修法。
6. **没做完 / 明确不做的**：逐条写清，并**同步进 `todo.md`**。
7. **验证证据**：跑了哪些测试、哪几次冒烟、图在 `.smoke/<主题>/` 的哪里；
   最后附**给用户的 5 分钟验收清单**（§11）。

### 12.5 立项时的三条纪律

1. **需求确认门（§2）过了之后，不再回头问需求。** 遇到不确定的实现细节，按"哪个更自洽、
   更好扩展"自己选，并写进 `架构变更记录.md`；只有**真正与用户已定取舍冲突**的发现
   （例如"素材盘里没有这一套原版动画"）才值得回去说一句。
2. **不为没验证的东西写文档。** 回退时那份记录要重写第二遍 —— 这是返工里最容易被忽略的一半。
3. **不记用例数。**"全绿"只有在用例本身是确定性的时候才是信号（§6）。

## 给测试开一个诊断开关

`gradle test` 会把 `-Ppvzce.smoke=名字=值` 的每一项转成测试 JVM 的系统属性（`pvzce-game/build.gradle` 的 `tasks.named('test')`），并且开着 `testLogging.showStandardStreams`，所以用 `Boolean.getBoolean("pvzce.xxx")` 保护的诊断输出可以直接这样看：

```bash
./gradlew :pvzce-game:test --tests '*AnimationLocomotionTest*' \
    -Ppvzce.smoke=pvzce.traceLocomotion=true
```

Gradle 的 `-D` 只到 daemon，进不了 fork 出来的测试进程——和 `run` 任务里的冒烟参数是同一件事。
