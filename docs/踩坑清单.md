## 素材与动画（开工前必盘）

1. **一张 reanim 里的动画远不止转换器默认导出的那几段。**
   `Zombie.reanim` 里就有 `anim_swim`（250~291 帧：腿关、救生圈换 inwater 那张、水线尾迹），
   `PoolCleaner.reanim` 有四段 mask（`anim_land` / `anim_water` / `anim_suck` / `anim_landsuck`）。
   少导一段的后果只能靠肉眼发现（"僵尸在水面上走""清洁器漂在池沿上"）。
   → **动手前先列 `anim_*` 列表**（`tools/reanim_to_pvzce.py` 的 `load_reanim` + `visible_ranges` 就能列）。

2. **未知动画状态会静默回落 `idle`。** 能力发布 `swim` 而美术文件里没有该 clip，僵尸会站在水里不动，
   日志里只有一行 warn。→ 新增状态必须同时有对应 clip，并加测试钉住"状态 ↔ clip"配对。
   （`PoolAreaLevelsTest.everyFloatieHasItsSwimClipAndTheSwimClipIsTheWaterLook`）

3. **`animation` 借的是整份文件**（骨架、装备轨道、片段全跟过来），
   而 `EntityArt.animationFile()` 必须认它，否则解析到不存在的文件 → 缺失贴图。
   判定盒不变是免费的（`render_scale` 纯表现），但**血量一定写在定义里**：一份定义一套数值。

4. **原版长什么样，先翻 `refer/`，别先搜资料。** 贴图/动画/音效都在仓库里；
   同理，"这个数值/这关给哪首曲子"是用户的决定权，不花检索预算（见 `验证约定.md` §9）。

5. **别信"`refer/` 里没有这个东西"这句话 —— 自己去 `ls` 一遍。** 斗转星移的门一直躺在
   `refer/anim/Portal_Circle.reanim`（连 `Portal_Square.reanim` 一起），`todo.md` 却写着
   "refer 里没有原版传送门的现成素材"，照着它就得手画一对旋涡。文档里的素材存量是**会过期的断言**，
   而盘点的成本是一条 `ls`。→ 凡是要新美术，"先列 `refer/anim` 与 `refer/im*` 里的候选"这一步
   不能因为某处写过结论就跳过；结论错了就把那句话一起改掉。

## 渲染与坐标

5. **底图采样是镜像的。** shader 的 `v` 跟着行号走，行号从棋盘**底部**往上数，而 PNG 自上而下存 ——
   世界第 Y 行读到的是九格贴图的第 `9-Y` 行（水行 2..3 → 贴图 5/9..7/9）。
   纯平铺的图看不出方向，有上下之分的图会贴反（暗边落在两行水**中间**，成一道横贯水面的线）。
   → **放探针量，别推导**（`tools/gen_water_surface.py` 的注释里有完整推导；
   `LiquidDefinitionTest.theSurfaceArtIsPhasedOntoTheWaterRows` 钉住相位与朝向）。

6. **舞台几何与液面帧是按美术量出来的常数。** `LevelStage.POOL`、液面帧、`base_scale: 1/9`
   都挂在 `background3/4` 的具体像素上，换背景必须重量（`LevelStageTest` / `LiquidDefinitionTest` 钉住）。

7. **液体深浅是逐格量化的**（8 连通步数，6 bit 里 3 bit），所以水面有极淡的逐格台阶、交界是矩形；
   要根治得把深度场双线性上采样。已有约定，不是新 bug。

8. **关掉 shader 的降级路径画的是预烘焙帧**（`textures/scene/water_frames/*`），
   不含水面贴图与底图；泳池关卡 `disable_shaders: false`，走 shader 路径。

9. **`FontRenderer` 的 `scale` 是 GUI 尺度，不是像素、也不是原生单位。**
   `scale = 1` 就是"一行约 14 GUI 单位"，全项目的调用点都在 0.6~2.0。
   字号想按"原生单位"写（"这一行占 15 个单位"）就会绕一圈除法，而**绕的圈数等于页面的缩放因子**——
   图鉴为此错了两次，字比卡片大 3 倍，看着像投影没还原（旁边的美术是对的，所以更像）。
   → **坐标**才可以按原生单位写（`sx/sy/sw`），**字号**一律照抄别处的 scale。

10. **`beginOverlayWorldView` 顺手把精灵缩放也设了。** 它设视口 + 投影 + `spriteXScale`，
   而 `beginGuiView()` 才把三样都还原。用世界投影画完实体后**在同一个 try 里立刻切回 GUI**，
   否则**这一页后面画的文字**会按世界尺度出来（图鉴里约大 8 倍）。
   这不是"忘了恢复投影"那么显眼：美术正常、只有文字错。

11. **九宫格只适用于"边框工具"，不适用于"一张卡片的画"。**
   324×484 的卡片框拉到 660×150，木纹会被横向抹开成一道糊；
   判定很简单：**中间那段拉伸后还像不像原来那个东西**。
   卡片、面板这类"画出来的物件"要按自己的像素比例整体缩放，位置留给版面去让。

12. **JPG 素材要转 PNG 再进 `assets/`。** `TextureManager` 只找 `assets/<id>.png`
   （`resources.getResource(id + ".png")`），`refer/im7/images` 里的背景是 JPG。
   图鉴的 `Almanac_*Back.jpg` 就是这么转的。

---

13. **"照着素材做布局"之前先看原版长什么样。** 仓库里有全套 `Almanac_*` 图，不等于知道那一页怎么排：
    图鉴第一版把背景当底板、卡片框当详情卡，做成"一条一页 + 左右箭头"，与原版（一页列出全部条目
    + 右侧一张详情卡 + 底部两个按钮 + 索引页两块大板）完全不是一个东西。
    **素材只说明有哪些零件，不说明零件怎么摆** —— 摆法去看原版截图，量出数字再写代码。

14. **剪刀（scissor）活不过一次 `beginGuiView()`。** 图鉴的详情文字推了裁剪矩形，看着对，
    实际有一半印在了图窗上：卡框绘制结尾会调 `beginGuiView()`（世界投影与精灵缩放都要还原），
    而裁剪状态不跟着还原。**凡是"画完实体再画文字"的地方都会中这一枪。**
    要文字不越界就用**版式**（算好放得下几行，越线的不画），别用剪刀。

15. **懒建的实体要在"画它的地方"启动动画，不能只在 `tick()` 里。** 预览实体是**第一次画它的那一帧**
    才建的，而那一帧的 `screen.tick()` 已经跑过了 —— 结果实体有 manager、`playAnimation` 却从没被
    调到，`render()` 返回 false，画面上就是"每一张僵尸卡都是空的"。判据：`currentAnimation()` 为空。

16. **`getOrLoad` 抛异常，`hasTexture` 才是探测。** 僵尸的静态贴图路径其实是**一个目录**
    （`textures/entities/zombie/basic/basic_zombie/`），直接 `getOrLoad` 会抛
    `Failed to decode PNG … Image not of any known type`，**整条客户端主循环挂掉**。
    路径来自"id 推导"时必须先 `hasTexture`，并且真正的加载也要 try/catch —— `hasTexture` 说"有"
    不等于字节能解码（目录项、截断的包文件）。

17. **"一条肢体一张 PNG"的骨架内容没有整身的静态图。** 僵尸的贴图是拆开的
    （`entities/zombie/basic/basic_zombie/` 下每个部位一张），所以"拿动画里最大的那块当图标"
    画出来是一条腿；那块贴图不存在时更是整片洋红（缺贴图占位）。这类内容要显示只能**画骨架**
    （`ClientEntity` + `AnimationManager` + 一个世界视口）。反过来，**静态图塞进非正方形的框
    要按比例 fit**，否则豌豆射手会被压扁 —— 图鉴两样都踩过。

18. **不透明的美术层会盖掉先画的字。** 卡片框的"文字窗"是不透明的：先画字再画框，字就没了
    （图鉴的详情面板空了好几轮，就是这个）。颜料顺序是**不透明层 → 文字 → 切投影的动画**，
    三段的相对顺序各有理由，别随手调。

19. **界面元素的"位置"要问它和谁共享一条边。** 标题页左下角的托盘被摆过四次：按底边摆（被菜单按钮压住）、
    按玩家木牌的下沿摆（1080p 下木牌在**屏幕顶部**，托盘被摆到屏幕外，截图上完全看不见）、按按钮高度放大
    （又压回木牌上）。**判据**：先说清它属于哪条边/哪个带 —— 木牌与菜单列都锚在**底边**，所以托盘与菜单列
    共用一条带；再对每个要支持的窗口尺寸跑一遍"盒子的四条边都在窗口内、且不与邻居相交"，
    这类断言是纯函数（尺寸进、矩形出），不需要窗口。**出处**：`TitleScreen.trayForGui` 与
    `TitleScreenTrayTest`。

20. **固定画布的 contain 拟合没有"可读性下限"。** 给 `MenuPageCanvas` 写过 `MIN_SCALE = 0.55`
    当"太小就看不清"的保护，而默认窗口（GUI 427x240）需要 0.40 —— 下限赢了 fit，整张画布顶出屏幕
    上方 45 单位，**标题条与页脚按钮直接被画到画面外**，截图上看像"这页没有页头"。
    → contain 的下限只能是 0；要保证可读性就改版面，别夹缩放。

21. **版面尺寸别拿字体行高去算。** 托盘单元高度一度由 `fonts().body().lineHeight(scale)` 推出，
    而它是**设备像素**算完再除 GUI 缩放（scale 3 时是 14 而不是 5），单元一下变成 90 高、
    第二个格子被裁出托盘。→ 凡是要跟另一个常量对齐的尺寸就用常量；只有"必须容得下这行字"的地方
    才从字体量，并且要按 GUI 单位复核一遍。

22. **"画出来了"和"点得进去"是两条路，别用一条的证据结另一条的账。** 标题页左下角托盘的两块木牌
    画得好、悬停也亮，点下去却毫无反应 —— `TitleScreen.onMouseClicked` 在上一次改版面时被删掉了。
    三层验证全都没拦住：纯函数断言验的是几何、截图只看得见绘制、冒烟钩子 `pvzce.smokeTray` 自己调
    `dispatchMouseClicked` 绕过了界面自己的处理函数。**判据**：可点区域至少有一条断言走
    `界面.dispatchMouseClicked(...)` 再看屏幕换没换（悬停亮 ≠ 点击通）。
    **出处**：`MenuProfileFlowTest.clickingACornerCellOpensItsPage`；约定在 `验证约定.md` §7.1。

23. **删代码别用行号切片。** 上面那条回归的成因：用一段"按标记取两段再拼起来"的脚本删掉一个方法，
    把夹在两者之间的 `onMouseClicked` 一起切掉了 —— 它编译得过（`onMouseClicked` 在 `Screen` 里
    有默认空实现）、也没有任何测试覆盖。**判据**：改完立刻 `grep -c "你要保留的那个方法名"`，
    再跑一次相关测试；宁可多写几条精确锚点，也不要"从 A 到 B 全删"。

## 数据与内容

24. **"同一具身体、另一套数值"只能写多份定义。** 没有"按关卡改僵尸血量/大小"的开关：
   血量、护甲、断臂阈值、存档全读 `ZombieDef`。小僵尸（3-5）就是这么做的六个定义。
   （注：血量减半是本项目的难度取舍，原版是四分之一 —— 见 `架构变更记录.md`，别再"按原版修正"。）

25. **`LevelServer.markEnd` 把胜负都写成 `WON`**，谁赢了要读 `winner()`。
    出怪报表因此踩过：`gameState` 不是"玩家赢没赢"的答案（`WavePacingMetricsTest` 现在打印 winner 列）。

26. **小推车的停靠锚点在棋盘**左外侧半格**，两种车共用**（割草机停路沿、泳池清洁器停池沿）。
    想"把它挪到水里"之前先确认原版停在哪 —— 直觉错过一次，加了一整套 offset 字段又删掉。

26b. **内置关卡 JSON 是生成物：改关卡要改生成器，然后重新跑它。**
   1-1~4-10 四十关全部由 `tools/write_adventure_levels.py`（事实来自 `tools/original_levels.py`）写出，
   手改 `data/pvzce/levels/yard/adventure/*.json` 会在下一次重新生成时**静默消失**，而症状是
   "上一轮修好的东西又回来了"。
   → 判据：`python3 tools/write_adventure_levels.py --check` 干净 = 磁盘与生成器一致；
   它报 `stale: <路径>` 时，缺的是生成器那一处，不是文件那一处。

26d. **一个字段的语义由"写出它的那张表"决定，不由引擎当下的实现决定。**
   冒险关 40 张波次表的 `delay` 是按原版 `Board::PickZombieWaves` 复算的（从上一波**触发**那一拍
   起算），而 `WaveDirector` 当时是从上一波**放完**起算 —— 于是"表没问题、引擎也没崩"，只有手感是错的
   （波间多等一个出怪窗口），而 `docs/架构-服务端.md` 把引擎的行为写成了契约（"所有波次表都按这条
   契约写"），读起来像证据、其实是结论的倒影。
   → 判据：改一处**时间/计量**的语义前，先用探针量出"实际发生的时刻"，再跟**数据生成器**里的常数对齐
   （这里是 1800 / 2500+rand(600) / 4500）；两边对不上时，先怀疑引擎，不要先怀疑数据 —— 数据是
   从别处复算来的，引擎是这一轮写的。相关回归：`WaveDelayOriginTest`。

26c. **"这一关没得选"从来不只体现为一个字段。** 固定卡组关卡要同时说三件事，缺哪一件都会以
   "玩家看到的和关卡文件写的不一样"的形式露出来：
   ① `seed_screen: false`（默认 **true**，全项目只有 4-5 与 2-5 写着）—— 不写就照弹选卡页；
   ② `max_seed_slots` 钉成固定卡数 —— 不写时卡条**跟着背包走**，`SeedSelection.defaultFor`
   会用玩家自己的卡把空位填满，于是"我发四张卡"实际发的是"四张 + 你解锁的若干张"；
   ③ 资源卡要在 `slots` 里 —— `collectible_without_card: false` 的资源（阳光就是）没有卡就
   **一颗也捡不起来**（"没有对应资源卡，无法收集"），银行 HUD 也不画。2-5 三件都缺过。

26d. **"上一拍/上次在哪儿"这类记忆，一拍只能读一次。** `PortalMechanic` 原本是"外层遍历门对、
   内层遍历僵尸"，而 `state.lastX.put(id, x)` 在内层 —— 第一对门把僵尸**这一拍**的 x 写进去，
   第二对读回来当"上一拍"，`previous == x`，于是**第二对之后的每一对都永远看不到跨越**。
   现象是"两对门的关卡只有一对能用"，而代码看着完全正常、单对门的测试也全绿。
   **判据**：任何 `prev = map.put(key, now)` 形状的检测，先问"这段代码一拍跑几次"；
   要求"一拍一次"的读必须放在最外层循环里，写与读之间不能隔着另一个循环。
   回归：`PortalMechanicTest.theShippedLevelsSecondDoorSendsRowOneIntoRowFour`。

## 工具与流程

27. **Gradle 必须带 `GRADLE_USER_HOME=$PWD/.gradle-user`**：`~/.gradle` 只读，
    否则 wrapper 解压 `gradle-9.3.0-bin.zip.lck` 时以只读文件系统失败。

28. **截图路径要给绝对路径，而且只能落在仓库内**（`.smoke/<主题>/`）：写到 `/tmp` 会被沙箱
    **静默**吞掉（不报错、也没有文件，看起来像"冒烟没跑"）；而 `run` 任务的工作目录是
    **`pvzce-game/`**，不是仓库根（`冒烟与截图指南.md` §3 写的"相对仓库根"是错的），
    相对路径 `-Ppvzce.capturePath=.smoke/x.png` 会落到 `pvzce-game/.smoke/`。
    另外存储是**双缓冲**：`afterFrame` 在 `swapBuffers` 之后跑，`glReadPixels` 读到的是
    **刚呈现的那一帧**，所以 `captureFrame=N` 拍到的是第 N 帧，而同一帧里改的状态要到
    N+1 才看得见 —— 冒烟钩子因此在 `beforeFrame` 里翻页（见 `SmokeDriver.applyAlmanacShots`）。

29. **冒烟截图不会替你建目录。** `capturePath` 的父目录不存在时只打印一行
    `[SMOKE] failed to write screenshot <路径>`：**没有异常、没有非零退出码、`BUILD SUCCESSFUL` 照旧**，
    看起来就是"图没生成"或"冒烟没跑"。→ 先 `mkdir -p .smoke/<主题>`，跑完再核对那一行日志。
    （`冒烟与截图指南.md` §2.1b）

30. **一帧一次 Gradle 是纯浪费。** `pvzce.captureEvery` 早就在 `SmokeDriver` 里、也早就写在
    `冒烟与截图指南.md` §4.1（"拍一条帧带…给会动的东西用"），一次启动就能拍完整条胶片 ——
    本会话仍然 10 次启动、63 张图，多数是同一批帧重拍。→ 先读参数表再用。

31. **文档不要先写。** 变更记录/测试在"画面或行为确认通过"之后再写；
    否则回退时那份记录要重写第二遍 —— 返工成本里最容易被忽略的一半。

32. **不记用例数**（`验证约定.md` §6 的既有约定）。本会话违反过：往 `当前项目架构.md` 写过用例数，已删。

33. **`docs/mod-guide/*` 默认不跟着改动更新**，只在用户点名时改。

35. **把一个声音设成循环，先确认"这两段样本本来就该挨着"。** `rain.ogg` 是 rip 的 4.34 秒原样片段，
   直接交给 `AL_LOOPING` 就变成"每四秒接一次从来没打算相接的样本"，玩家的描述是"断片的感觉"。
   判据与做法：先量循环点的不连续度（末样本到首样本的落差 ÷ 文件内部的典型相邻落差），
   大于 1 就说明接缝比噪声本身还显眼；修法是**把素材做成可循环**（尾巴等功率交叉淡入自己的头，
   两段先对齐 RMS —— 线性淡化在噪声上会掉 3 dB，听起来是"呼吸"），不是在线路里加一层淡化。
   顺带：`-Dpvzce.traceAmbient` 每次起停打一行，用来先排除"引擎把循环反复重启"这一半。
   （工具 `tools/gen_rain_loop.py`；同类的还有"4.3 秒的纹理听一分钟就腻"——所以床是 14.3 秒。）

36. **协议一改，录像必须重录。** 机制负载的形状变了（`StormState` 加了曝光字段）就是 wire 变了：
   `PacketProtocolTest.theWireFormatIsUnchanged` 会红，而它的修法是**先跑
   `-Ppvzce.smoke=pvzce.printWire=true` 把新录像贴回去、再把 `PROTOCOL_VERSION` +1**，
   不是把断言删掉。顺序反了会得到一个"版本号变了但录像还是旧的"的红，看起来像自己改错了。

34. **探针产物不进仓库**：色带贴图、临时对照图放 `.smoke/`；
    要交付的成品图最后只拍一次（`验证约定.md` §1）。

35. **"这张脸到底有没有上台"要先证，再查它化没化妆。** 选卡预览的泳池一点水都没有，
    第一轮怀疑了贴图、着色器编译、混合模式、裁剪，全部排除干净却毫无进展。
    决定性的一步是**把 fragment 输出强制成品红**：屏幕上仍然一个品红像素都没有，
    于是范围立刻缩到"几何/光栅化"（片元根本没跑到），再打顶点快照就看到坐标是 2539/5116。
    **一个"画出来完全不对"的东西，先证明它有没有被画，再查它为什么长这样。**

36. **`scaledTo` 这类仿射换算不幂等，"谁负责缩"必须只有一个答案。**
    液面帧在 world cells，`LiquidTextures.renderGuiBoard` 负责缩进 GUI 像素；
    调用方又缩了一遍，于是水面批次跑到屏幕外（origin 2540 / 格子 2265，而 GUI 只有 640×360）。
    **两个地方都"顺手做一下"换算，结果不是更保险，是平方。**

37. **缺省值可能是别人的答案。** `ExplosiveCapability` 的缺省粒子是原版灰烬线那一闪，
    土豆地雷没写 `particles` 就安静地画了它 —— 而它恰好是樱桃炸弹三件套的中间那件。
    **凡是有"统一缺省"的字段，都要问一句"这个缺省对每一件内容都成立吗"**，
    并且让测试点名每一件应当有自己答案的内容，而不是只测前两个。

38. **"压制/优先级"这类规则，先问它管的是哪个资源。** `cardSourcePrecedence` 原本是
    "谁在发牌"，默认实现写成了"谁的数大谁压谁"，于是传送带的 10 把其余 17 条变异的 0
    全压住，且因为挤人时跳过发牌者而永久生效。**一条只覆盖一对用例的测试**
    （只测了"传送带压卡槽替换"）让这个 bug 从底下走过去 —— 这种全目录规则要**遍历**着测。

39. **同一份状态有两条上线通道时，问"中途变了走哪条"。** 关卡增益的上线通道只有进场那次
    `LevelInitS2C`，而中途会变的只有变异；于是角落的图标一直显示开局那份，模拟按另一份跑。
    **"客户端画的是服务端解析后的集合"这句话要问：那份集合什么时候更新？**

40. **"全绿"只有在用例本身确定性时才是个信号。** 这个仓库里有三条用例读真实掷骰的
    `LevelServer.random`（`GameplaySimulationTest.finishedLevelSaveDoesNotRestorePlants`、
    `MutationManagerTest.aReplacedBarComesBackAsTheReplacedBar`、
    `MutationManagerTest.theApocalypseDoesNotGoOffTwice`），在干净的工作树上也会偶发红
    （实测 6/2 与 12/3）。**跑完全量红了第一件事是分辨"我改坏的"还是"它本来就这样"** ——
    分辨的办法是 `git stash` 回到干净树、把同一类跑几遍，而不是先怀疑自己的改动。
    这三条按 `验证约定.md` §6 应该被改成确定性断言，尚未处理。

41. **"谁先谁后"这类规则，顺序要由调用方给，不能让实现自己猜。**
   `suppressedBy(other)` 一旦让实现自己去比较"谁优先级高"，就必然有人写出与顺序无关的判断，
   于是"先到的高优先级"会永久压住"后到的"——而 `evictOldest` 又不会驱逐持条者，被压的永远回不来。
   → 规则是"后到的赢"时，**由调用方只把排在后面的拿给实现看**（`isHeldBack(entry, index)`）。

42. **两个入口都在"顺手把状态恢复一下"，结果不是更保险，是平方。**
   `slot_replace` 改写卡槽，而 `rebuildCardBar()` 也会从玩家选的卡重建卡槽 ——
   两者相遇时改写被静默冲掉。判据：**凡是有"重建 X"的代码，就要问一句"谁在 X 上写过东西"**，
   并给那条写路径一个"重建之后再来一次"的钩子（`RewriteBarMutation.rewriteBar`）。

43. **夹具自己是一枚骰子，测试红了就分不清是谁的错。**
   "一波一只僵尸"的关卡每一行都敞开，僵尸五分之一概率落在没防守的那一行，于是**关卡是输的**，
   而那条用例测的是存档。→ 夹具里**凡是随机的都要钉住**（`WaveDef.Entry.rows`、`random().setSeed`），
   并在断言里带上诊断（把服务端拒绝的原话打出来），下一次失败不用猜。

44. **"淡出"写成"重设时钟"就是"再显示一遍"。**
   `hide()` 里 `shownNanos = now` 而 `alpha()` 从 `shownNanos` 量 —— 淡出变成了重新淡入。
   对 `PERSISTENT`（`Long.MAX_VALUE/4`）的那条 `if` 还恒真，于是"收起"实际是"寿命翻倍"。
   → **不变量要成对检查**：改了"截止时间"就不要动"起点"，两者只有一个能被改。

45. **"兜底"要放在所有路径都会经过的那一个点上。**
   落水这件事有四个生成点（波次、变异召唤、Boss、召唤伴舞），只修波次的行选择等于没修。
   → 找"这件事的唯一入口"（这里是 `LevelServer.spawnZombie`），把不变量放在那里；
   顺带问一句"这条路要不要缓存"——洪水变异会改地形，缓存的行划分是过期答案。

46. **"做了 A 之后如果没成，就做 B"要写成"做完之后看结果"，不要写成"如果条件是 A"。**
   `BuffShiftMutation` 的回退写成"如果方向是给且没有可给的，就改成拿"，
   覆盖了"列表满"却漏了"列表空"，于是百分之一的概率静默无操作。
   → 回退的判据是**结果没变化**，不是**前置条件不成立**。

47. **同一个技能换一种实现方式时，挂在它身上的测试要跟着换个问法。**
   倭瓜从"范围爆炸"变成"压扁一只"之后，`everyAshPlantStaysLongEnoughToDrawItsBlast`
   里那句"它必须带 explosive 能力"就成了错的断言。→ 改的是**断言的方式**（读它自己的
   `lingerTicks()`），不是把倭瓜从名单里删掉——那条不变量对它依然成立。

48. **"静止时看得见的东西，动作片段不能让它整段消失。"**
   水壶的 `attack` 把普通壶藏了 0.85 秒、换成金壶（禅境花园的升级件），而渲染器永远不会去选变体。
   → 动画文件里的"另一套同名变体"（`*_gold`、`*_damaged`…）**先问一句谁会去选它**；
   没人选就说明转换器读错了 mask。

49. **数值改动"看不出来"是缺陷，不是手感。**
   浇水快三分之一，在两头豌豆的间隔里读不出来，玩家的结论就是"没效果"。
   → 一个**为了被看见**而存在的机制，它的数值下限是"一次交互之内能观察到"。

50. **一条曲线写在两个地方时，必须有一条测试把两边对拍。**
   雾的浓度坡在 `FogData.alphaAt` 里（用来决定隐藏边界）和一张烘好的贴图里（用来画），
   因为引擎没有逐顶点色。两边一旦分叉，症状是"僵尸比看上去早一点/晚一点消失"——
   肉眼看不出来，但玩家能感觉到。→ 测试直接读 classpath 上的 PNG，逐像素对拍。
   **写完先故意把其中一边改掉，确认它会红。**

51. **"借来的图标"与"画错的图标"是一回事。**
   自动拾取借了资源目录那张阳光 —— 玩家看到的是"阳光"，不是"自动捡阳光"。
   → 一个机制**为了让玩家理解它**而存在时，它的图标必须是它自己的；
   程序化画一张也比借一张对。

52. **改生成物之前，先问一句它是谁生成的。**
   上一轮手工改对了 `threepeater.json` 的叶茎姿势，这一轮跑一次转换器缺陷就回来了。
   → **能改生成器就不要改生成物**；实在要手改，就把规则同时写回生成器，
   并在提交信息里说清楚"下次重新生成会怎样"。

53. **`putResource` 是设置，`addResource` 才是累加。**
   `Team` 上这两个名字只差四个字母，写错一次的结果是"退款把玩家的阳光银行换成了退款额"。
   → 凡是"返还/奖励"语义，问一句这个 API 是加还是设；测试要断言**总额的变化量**而不是**操作后的值**。

54. **"没有档案"不等于"什么都拥有"。**
   `ownsCard == null` 的约定是"每一张**卡**都可用"，那是关于卡池的话。
   把"这个玩家买过钉耙吗"也塞进同一个谓词，就给每个测试和植物 AI 白发了一把钉耙。
   → 一个新的所有权问题，配一个新的显式答案（`SeedContext.ownsRake`），别复用语义不同的旧谓词。

55. **`replace: false` 说的是运行时合并语义，不是"我这样写就不会覆盖"。**
   用脚本整份重写 `data/c/tags/plant/*.json` 时没先读原文件，把 `pvzce:tangle_kelp`
   从 `water_plant` 里挤掉了，测试当场红。
   → 改任何既有数据文件之前先读一遍（或 `git show`），**加值用追加而不是重写**。

56. **"声明了却没有调用方"的钩子是一个安静的坑。**
   `PlantCapability.onRemoved` 从存在那天起就没有被派发过 —— 直到路灯花需要它才发现。
   同类还有盘点报告里的 `MutationHooks.onLevelTick`。
   → 加钩子时顺手加一个"它会被调用"的测试；翻到旧钩子时先 grep 调用方。

57. **构造器里的 `Math.max(1, x)` 会把"没写"变成"写了 1"。**
   `DeathBlastCapability` 用 0 当"块里没写 `damage`"的哨兵，构造器却把它夹成 1，
   于是每个没写该字段的定义都成了 1 点伤害的炸弹。
   → 哨兵值不要在构造器里被 clamp；要 clamp 就在**用它的时候**分情况。

58. **弹丸的 `direction()` 正负是有方向的，僵尸的枪要反着开。**
   正向 `ProjectileRef` 朝草坪深处飞。写反的症状不是"打错人"，是"根本没开枪"——
   豌豆直接飞出屏幕了。→ 新写一条发射路径时，先问一句它该往哪边飞。

59. **一个"只有一方有枪"的引擎里，路由往往也只认一方。**
   `ProjectileEntity.findTarget` 问 `enemiesInRow`，答案永远是僵尸——因为在 ZomBotany 之前
   只有植物会开火。让僵尸也能开枪时，缺的不是伤害逻辑而是**另一半目标查找**。
   → 加"另一方也能做这件事"的内容时，先把引擎里"只有这一方能做"的假设逐条列出来。

60. **"投影型"的集合不能从外面往里塞。**
    传送带的卡槽条是它队列的投影（`BeltCardSource.rebuildBar`），任何绕过队列直接加进条里的卡，
    在下一张卡滑过来时就被抹掉 —— 花瓶砸出来的奖励卡会**凭空消失**。
    → 往一个集合里加东西之前先问"谁是它的主人"：加卡要问卡源（`CardSource.receiveCard`），
    而不是问条本身。

61. **两个必须同生同死的状态，就存成同一条记录。**
    花瓶"画着满的"（`pvzce:vase_full`）与"里面是哪张卡"分两处存，迟早会出现
    "画着满的、砸开是空的"。它们同属**场景**，所以内容表跟 `scene` 分区写进同一个存档。
    → 一个状态存哪里，由"谁必须与它同时正确"决定，而不是由"哪个类用起来方便"决定。

62. **两击式操作里的中间态，能不改世界就别改。**
    手套搬**花瓶**时如果在"拿起"那一刻就把原格清掉，超时/放弃就得完整还原，
    还要处理"原格在这十几秒里被别人种上了东西"。改成"拿起不动格子、放下才写"
    （植物那条路本来就是这么做的），放弃就只是忘掉一个引用。
    → 中间态优先做成**纯记录**；非改不可时，把"怎么撤"和"改"写在一起。

63. **用 id 当键去表示"这一次实例"，迟早被重复的同一种东西拆穿。**
    变异的行动集合原来是 `Set<Identifier>`。变异**可以重复抽到**（权重允许），同一条变异的两个
    条目 id 相同，于是"撤销不再行动的那些"这一步里，后到那份的 id 替先到那份回答了"我在行动"——
    被压制的那一份继续 tick，而存档恢复后又是对的，于是只在"存一次档"的测试里现形。
    → 一个集合装的是**这一次的实例**时，键必须是实例自己（身份），内容 id 只能拿来**查询**。

64. **加了内容，老测试会红，而且看起来像"我改坏了"。**
    变异目录 18 → 38 条之后，所有"掷骰子跑一局再看状态"的用例抽到的东西全变了：一条夹具
    被"送僵尸"的变异打赢了（`GameState=lost`，后面的断言全错位），一条传送带的归属被新加的
    卡槽变异换掉了。
    → 与掷骰有关的夹具**先定种子，再把"可能输"的机制关掉**（僵尸速度设 0、天空关掉、每 tick
    清场），而不是每次涨目录就去改断言。看现象先问"这是不是我加的内容改变了它抽到的东西"。

65. **"关卡自己的时钟"和"服务器的时钟"不是一回事。**
    客户端原先只有 `DebugInfoS2C.tickCount`（跨关卡连续计数），拿它当"关卡内时刻"用，
    第二关一开始所有 `at_tick` 就都"已经过去"了，定时台词会一口气全播完。
    → 任何"关卡内的第 N 个 tick"都必须来自关卡自己的计数器；数据里写 `at_tick` 的功能，
    先确认线上有没有这个数。

66. **机制级断言通过，不等于体验合格。**
    最容易被当成"验过了"的三句话是"卡变了""按间隔来了一只""地面单位会掉血"——
    它们都是真的，但玩家感受到的分别是"换来的卡能不能用""一局会被拿走多少""这东西是不是
    免费又全局"。用机制的名字写断言，就会在机制正确、体验崩坏的地方一路绿灯。
    → 断言尽量写在**玩家那一侧的量**上（一局损失/收益、能不能种、看不看得懂）；
    机制只是手段。判据见 `验证约定.md` §10。

67. **自己一个人拍的数值，等于没验过的数值。**
    新内容的间隔、倍率、概率如果只来自规划文档里一个人写的表，而做的时候一局都没跑过，
    那不是"设计好了"，是"还没验"。尤其两件事最容易漏算：
    **间隔要换算到档位倍率之后**（表里是基础值，跑起来是除以倍率的值），
    以及**免费 / 永久 / 全局的效果**（不占卡、不花资源、对全场同时生效的东西，
    等于一条常驻光环，量级要单独算一次）。
    → 新数值必须附一段真 `LevelServer` 的模拟输出；用户没给数的地方要拿模拟结果或明确的
    取舍说明去补，不要随便定一个数就往下做。

68. **新内容进新上下文之前，先问"它在这里成立吗"。**
    一张卡能不能在这块棋盘上种下去（地形、水位、前置植物）、一条变异有没有成本与上限、
    这只僵尸出现时玩家手里有没有对付它的东西 —— 这些都不是机制问题，机制全对也可能不成立。
    → 给新内容写一句"它在什么上下文里成立"的判据；答不上来就改内容，或者在关卡/卡池那一层
    加一道过滤（卡池过滤是既有做法，别绕开它自己抽一套）。

69. **合成出来的美术，"挂上了"不是判据。**
    没有原版参照物时，容易用"文件生成了、骨骼挂对了、每个状态都有 clip、看一眼没崩"结案，
    甚至看一眼就把"挂上了"写成"正确地长在头上"。
    → 合成美术要**动起来看**（`captureEvery` 拍帧带，至少 idle + 一个动作状态），
    并明确写下"这些参数是估的"（缩放、偏移、锚点）与它进了 `todo.md`；
    参照物缺失本身要写进交付说明，不能默认它不存在就不是问题。

70. **`git status --porcelain` 的中文路径默认是八进制转义。**
    `core.quotePath` 缺省为 true，`docs/架构变更记录.md` 会打成 `docs/\346\236\266...`。
    按前缀匹配改动路径的脚本（`tools/doc_check.py` 就是一例）会**一条也匹配不上却照常退出 0**——
    "脚本跑了"与"脚本看出东西了"是两件事。
    → 调用处统一 `git -c core.quotePath=false …`；判据是**输出里看得见中文文件名**。

71. **归文档分卷时，文件名会决定链接好不好看。**
    Markdown 链接目标里的空格与中文要百分号转义（`架构变更记录/%E6%8C%89%E5%B1%82-...md`），
    一屏 `%E6` 把索引的可读性吃光。
    → 归档文件名不带空格、` / ` 写成 `、`，正文标题里保留原样；**文件名叫什么不影响正文**。

72. **搬家式整理"看起来搬完了"不等于搬完了。**
    把一大段文档拆到几处（分册、待办、概览表）时，漏掉一句是**没有声音**的：
    读者不会发现少了一句他从没见过的约束，评审也看不出来。
    → 验收判据是**关键词回查**：把原文每个条目的关键名词/方法名逐个在新文档里搜一遍，
    缺哪个补哪个。这一轮 36 组关键词查出 1 处真丢失（`CanvasPage.palette.selected()` 的回读）。

## 变异、平衡与 HUD

73. **转换器的骨骼去重必须对"整具模型"唯一，不能按 base 名各数各的。**
    旧实现按"同一个 base"计数：`hand`/`hand_2` 与 `hand2` 两组各自从 1 数起，于是生出两根
    `hand_2`；`ControllerModel` 直接拒绝重复骨骼，日志只有一行 `Duplicate controller bone`，
    蹦极僵尸全身画成紫黑缺失格。→ 命名表一律拿**已发出的全部名字**去重，并补一条
    "遍历整个动画目录、逐个 parse"的测试（本轮的 `everyShippedAnimationParses`）。

74. **隐藏一根骨骼要改它的 `visible` 轨，不能整条轨道换掉。**
    把 `head` 的轨道写成 `{"visible": {"0.0": false}}` 会把它的 translation/rotation/scale
    一并删掉；作为子骨骼的 `plant_head` 失去父变换，直接掉到实体锚点（脚下）。
    → 用 `clip["bones"].setdefault(name, {})["visible"] = ...` 保留其余轨；合成美术必须拍帧带
    看它是否跟随父骨骼。

75. **"按高度适配"只适合立着的素材。**
    地刺（`Caltrop.reanim`）的绘制盒是 83×36 的扁平垫子，按高度适配把它放大 2.1 倍，画出来
    1.8 格宽、压住左右两格。→ 宽高比明显偏离 1 的实体要按两个轴 contain 适配，并加一条
    "最宽零件 ≤ 一格"的断言（`theSpikeweedIsAboutOneCellWide`）。

76. **实体的竖直位移用 `Entity.height`，动画片段只是姿势。**
    蹦极僵尸的"从天上降下来"在原版是对象位移；本引擎里 `height` 会进渲染锚点（掉落物就是
    这么落的），所以下降 = 服务端按阶段写 `height`、客户端插值。→ 需要"从天上下来"的东西
    先查 `Entity.height`，不要在 clip 里硬做位移。

77. **"死亡触发"的效果先问两件事：回调是同步还是延迟，以及怎么标记"这次死亡来自我自己"。**
    僵尸死亡在 `damage` 内**同步**回调，植物死亡在 tick 末的移除循环里；所以标记必须带 tick
    号（`PvzceEntity.markBlastDeath`），且幸存者要立刻清标记，否则"后来被豌豆打死"也不再触发。
    → 链条类效果（爆炸、溅射、连锁）必须有一条"被同类杀死不再触发"的测试。

78. **数值注释也要跟着数一遍。**
    荆棘草坪的注释写"15 秒走完、约 60% 血"，实际基础僵尸 0.23 格/秒、9.5 格要 41 秒，旧数值
    是 156%——一条"过强"的反馈就是这么来的。→ 平衡改动要把注释里的推导重新算一遍，或者只留
    结论删掉推导。

79. **HUD 里"谁属于这条栏"要显式分类，不能按位置猜。**
    传送带客户端原先只排除阳光卡，于是铲子/水壶跟着带子移动、托盘还按带子容量算宽度而溢出。
    → 服务端"带子在前、工具在后"的布局要由客户端按 `kind` 重建（`BeltCardBar.split`），并写
    一条不依赖客户端的纯函数测试。

80. **原版的算式有顺序，抄表要连顺序一起抄。**
    `PickZombieWaves` 是"先算旗帜波的 ×2.5 与它顺手放下的普通僵尸 + 旗帜，再乘关卡自己的倍率（迷你 boss ×3、
    小僵尸/保龄球 ×4）"。把倍率提到旗帜波之前，旗帜波的预算会差一倍多，而且**看起来只是"这关怪多"**。
    → 复算原版算法时逐行对着反编译源码抄，并在 `tools/original_levels.py` 的注释里写明每一步的顺序。

81. **0 波的关卡永远不会"波次出完"，胜负必须有人自己说。**
    `checkEnd` 判胜的条件里有 `waves.allWavesReleased()`，而它要求 `roundWaves > 0`——恐怖花瓶（4-5）因此
    既不会赢也不会自己结束。→ 机制型的胜负条件要显式调 `LevelServer.declareVictory()`；
    新写"没有波次的关卡"时先问这一句：赢了谁来说？

82. **同一件东西的两种归属要有两个 id。**
    玩家的花瓶是 `pvzce:vase`（里面那张卡属于玩家），关卡的花瓶是 `pvzce:pot_question`/`pot_leaf`
    （里面是卡还是僵尸属于关卡）。合成一个 id 会让"锤子砸下去该给卡还是该放僵尸""搬走它算不算偷关卡的牌"
    这类问题在实现里没有答案。→ 判断与内容各留一份（`ScaryPotterMechanic` / `LevelServer.vaseContents`），
    并且给它们各自的美术。

83. **依赖冰面的僵尸不能靠关卡文件写行。**
    雪橇小队只在冰上成立，而冰是雪橇车这一局跑出来的：开局时那一行没有冰，写在 `waves.rows` 里的行号
    是"开局的样子"。→ 这类"场地先于实体存在"的规则放在生成路径上（`LevelServer.spawnRowFor` 选行 +
    `WaveDirector.spawnQueued` 兜底），关卡文件只写它想表达的种类与数量。

84. **关卡文案会跟着数据一起过期，而且不会有人告诉你。**
    世界 3/4 的描述与提示里写着"气球""矿工""巨人"，在僵尸池改为原版之后这些字全都指向不存在的怪；
    `doc_check.py` 看不到 JSON 里的散文。→ 重做一关的内容后，**同一批**把它的名字/描述/提示一起过一遍，
    并让文案里的每句事实都能在生成器里找到对应字段（波数、发卡、首现僵尸、布景）。

85. **"放东西"的判定只问了一半，那个工具就变成了"覆盖"。**
    玩家的花瓶工具原先只问"这一格有没有植物"，于是它可以盖掉墓碑、盖掉恐怖花瓶：盖掉瓶子时，瓶子里的内容还留在机制自己的账上，草坪上却再没有可砸的瓶——关卡永远打不完，画面上是一堆空花瓶。
    → 任何"往格子里放东西"的入口都要问**这一格是不是裸地**（`pvzce:grass` / `ground` / 屋顶两式，且无植物），而不是"有没有我想到的那一种东西"；再加一条自愈：状态里还有、棋盘上已经没有的东西要能重新立起来或划掉。

86. **"写进服务端状态"不等于"客户端知道"。**
    冰车压过的格子服务端一直是冰（存档、`rowHasIce`、`canPlacePlant` 全对），客户端镜像里却还是草——
    `ZamboniCapability.leaveIce` 是唯一一处只 `setScene` 不 `sendSceneCell` 的地形改动。这类 bug 的
    **单测必然全绿**，因为断言写在服务端网格上。→ 凡是"客户端画的东西"，测试要断言**包**
    （`SceneSyncS2C` / `EntityUpdateS2C` …），而不只是状态；写完 mutator 顺手 grep 一下同一个方法
    的其它调用点是怎么配对的。

87. **源文件的 mask 是"谁在演"，不是"谁存在"。**
    三线豌豆的三段 `anim_shooting*` 各自只画一颗头，把 mask 当成可见性窗口，播出来就是"一颗头飞进来、
    吐一口、消失"。→ 从 reanim 转换时，"这一段之外"的部件要摆成**它在静止姿态里该有的样子**
    （idle 帧的姿态），而不是它在源文件里"没被演"的那个值（scale 1.0、原点附近的未设置姿态）。

88. **新表现的 z 序会和它自己的特效打架。**
    召唤出来的锤子一开始画在粒子下面：0.3 秒的挥击正好被 0.83 秒的 POW 完全盖住，玩家只看到爆炸。
    → 新加"动作"类表现时，先问一句"它和同一时刻的特效谁在上面"，并**在冒烟里看一眼**——
    这一条是胶片刻出来才发现的，单测与代码审读都不会说话。

89. **冒烟的画面会被三样东西遮住：控制台回显、开场横幅、提示条。**
    这一轮三次胶片都踩了：`smokeCommands` 的"已生成 …"回显盖住左半屏；"准备/安放/种植"开场横幅
    盖住第 2~3 行；关卡 `hints` 的提示条盖住最下面一行。→ 拍棋盘时：能写进 `initial_entities`
    就别用 `smokeCommands`；想看哪一行就把它放在第 1~2 行（横幅在中间、提示在底部）；验收关卡自带
    `"hints": []`。

90. **慢的东西拍不进短胶片：先算它的速度。**
    冰车是 0.15 格/秒，5 秒胶片里只走 0.75 格——想让冰道入镜，要么预置冰面、要么给它足够时间。
    → 拍"会动的过程"之前先把速度×帧数算一遍；算不出来就换个能把状态直接摆出来的入口
    （`/spawn`、关卡的 `scene`/`initial_entities`、`smokePlace`）。

91. **"恢复"和"筛选"是两个问题，别用同一个方法回答。**
    续档恢复卡槽走的是选卡请求的 `SeedSelection.sanitize`，它按 `max_seed_slots` 截断：4-5（2 格）里
    花瓶一路给玩家的植物卡，在每一次续档时被静默切掉，玩家看到的是"花瓶从来不掉卡"。
    → 写"读回来"的路径时先问**这份数据是谁的**：run 自己的状态（卡槽、场上实体）整份恢复，
    只有"这一关允许带什么进来"才过筛选；两者共用一条路时，注释写的意图和代码做的事会分家。

92. **实体的绘制锚点不是统一的"格子中心"。**
    植物的锚点是格的**底边**（`visualCellY()` 直接当底边用），于是照抄植物画法的种子包被画到了
    **上一格**；而它的判定盒还是按格心算的，两者差半格。→ 掉在格里的东西（卡片、掉落物）要在
    `EntityVisuals` 里把 `spriteOffsetY` 写成"半格"，让绘制与判定读同一个数；模板是植物的代码时，
    先确认它在格里的哪条边上。

93. **冒烟点击的 GUI 坐标 → 世界格，别用 raw 像素直接当世界换算。**
    这一轮连错两次行：`smokeClick` 收的是 GUI 坐标，1280×720 窗口下 GUI 缩放是 **2**（不是 3），
    而棋盘几何（`LevelStage.YARD` + `cover`）给出的是 raw 像素。可用的公式：
    `worldY = (guiY × 2 − 24) / 120`、`worldX = (guiX × 2 − 107.2) / 96`（4-5 这种 yard 舞台、9×5）。
    → 拿不准就先点一次、看日志里那句 `[msg]` 是哪一格内容的回执（瓶子掉卡/掉阳光的回执把行说得很清楚），
    再决定要不要重拍；坐标错了会烧掉整次启动。

94. **"清场"这类整片移除的操作，别在脑子里替用户留例外。**
    回合之间清草坪时我把地上的种子包留了下来（想的是"包是玩家已经拿到的东西"），用户一句
    "清场时你忘记清理场地上没种下的种子包了"退回来。→ 用户说的是"清理场地"就按字面清干净；
    真要留例外，先问一句，别在实现里悄悄做决定。

95. **数值（tick 数）和美术片长是绑在一根绳上的。**
    倭瓜的引信写 60 tick、原版起跳动画 1.25 秒，结果是跳到一半就切进落地姿势——玩家看到的是
    "原地压扁然后瞬移"。→ 凡是"一个动作持续多久"的数值，都要和它那个 clip 的 `animation_length`
    对一遍，并写成测试（`AnimationResourceLoaderTest` 里"落地姿势 ≥ linger"与"引信 ≥ 起跳片长"是同一族）。

96. **拿 1-1 当多行草坪的测试底板，"上面那一行"其实不存在。**
    1-1 只有 **一行**（原版第一关就是一条道），`LevelServer.spawnRowFor` 会把每一行都夹到第 0 行；
    于是 `ExplosiveBoundsTest` 里"隔一行的僵尸"和植物站在同一格，两只僵尸一起咬它——这个 bug 一直到
    倭瓜动作变长才暴露。→ 需要多行的用例把底板写成 `TestLevels.copy(1_1).width(9).height(5)`，
    别假设关卡有几行。

97. **粒子的 `frames` 是"动画"，不是"变体"。**
    原版的碎片发射器（一瓶九块）是每颗粒子随机挑一张画到底；照抄进本项目的粒子格式会变成 16 片在九张
    图之间每秒闪 60 次。→ 帧序列 + `frames_per_second: 0` 才是"变体"（出生时挑一张），要动画就写帧率。

98. **同一个决定有 N 个入口，就要在 N 个地方问同一句话 —— 或者只写一个函数。**
    "这个关卡要不要选卡页"在客户端有三条路（列表进入、存档框的重新开始、暂停菜单的重新开始），前两条各写了一遍
    `skipsSeedScreen(info)`，第三条漏了，于是 4-5 从暂停菜单重开时会冒出一个它自己声明"没有"的卡屏。用户的问法
    很准："是不是因为走了不同的路？" → 同一件事在多入口出现时，先找那条"只写一次"的路（这里是
    `requestFreshRunDirectly`），或者至少让每个入口都调同一个判断。

99. **原版动画的"位移"可能只有十分之一个格子，看起来像动的部分要在实体层做。**
    倭瓜的起跳动画（`anim_jumpup`）是在原地拉伸/压扁的：把它的骨骼位移换算到世界单位只有约 0.1 格，
    所以"照着动画播"看上去就是平移。→ 需要"真的飞起来"的动作，要用实体的 `height`（或位置）画出轨迹，
    动画只负责姿态；判据写成"峰值高度/滞空 tick"这类数字，而不是"看起来像跳"。

100. **给一个动作加"可被提前打断"的窗口，要顺手验证"不被打断"的那条路径在实战里真的会发生。**
    瓶子放出来的小丑改成"开箱 + 110 tick 前摇"之后，它在玩家防线中间被植物打死，于是**爆炸永远不会发生**——
    玩家报的是"缺少爆炸效果和那一声"，听起来像效果坏了。→ 新加的等待窗口，要问一句"这段时间里最可能发生什么"；
    玩家防线里的东西要按"它随时会被打掉"来设计。

101. **"这段等待/前摇没用"这种判断，先去 `refer/` 里确认原版有没有它，再推荐删掉。**
    小丑僵尸的 110 tick 开箱动画我先按"玩家会在窗口里把它打死"推荐删掉，用户退回："应该先留个 1~2s 的时候，
    让它播放音乐盒要爆炸的动画，动画播完才炸"——那本来就是原版自己的节拍（`pop_ticks` 就是 `PHASE_JACK_IN_THE_BOX_POPPING`）。
    → 玩家报的是**现象**（"没看到爆炸"），不等于要改**设计**；"原版这里有没有这一段"是事实，属于该花的检索预算
    （`验证约定.md` §9 只把"数值/给哪张卡"这类决定权留给用户）。

## 输入与坐标（改鼠标/键盘/触控前先读）

102. **点击是"按下即发"，而且全仓库没有位移阈值。** `PvzceWindow.mouseButtonCallback` 只把 `GLFW_PRESS`
    入队，`pollInput` 一拿到就 `dispatchMouseClicked`；所以任何"把拖动合成成别的事件"的做法都会在起点
    多按一次 —— 商店那一按就是买、玩家选择器那一按就是换人。**判据**：在 `pollInput` 里改输入之前，
    先想清楚"这一下按下要不要延后"。触控的滑动就是这么做的（`PointerGesture`），而且**只在声明了
    `ScrollRegion` 的区域里延后**，区域外保持原样。

103. **同一次 `glfwPollEvents()` 里的按下 + 松开，轮询状态直接是"已松开"。**
    `glfwGetMouseButton` 反映的是最后一条消息，所以 `leftMouseWasDown` 那条松手分支根本不会跑；
    靠"按下延后、松手补发"的写法会把这种快速点击**静默吞掉**。**判据**：延后点击的入口要带
    "现在还按着吗"（`PointerGesture.press(..., stillDown)`），已经松开就当场补发。

104. **滚轮的下游消费者读的是光标位置，不是调用方给的位置。** `SeedCardBar.scroll` 先 `contains()`
    判定，控制台还要分"日志还是补全"；而 `dispatchMouseScrolled` 是从 `window.cursorX/Y` 取坐标的。
    合成滚轮（手势、冒烟、脚本）必须**把坐标一起传下去**（`PvzceClient.dispatchGuiScrolled`），
    否则事件会落在指针恰巧停着的地方。

105. **滚动方向不是全局事实。** `AbstractSelectionList` 的行自下而上排（index 0 在底行），
    选卡页卡池与关卡网格自上而下排；一个全局符号必然让其中一个"反着走"。**判据**：方向写在
    区域声明里（`ScrollRegion.Swipe`），别在手势层统一。

106. **冒烟的 `smokeDragTo` / `deliverRawDrag` 绕过事件循环**（直接调 `dispatchMouseDragged`），
    所以它验不了"事件循环里的新逻辑"。要验手势就得加一条走同三次调用（press/dragged/released）的钩子
    （`pvzce.smokeSwipe`），否则截图只证明了旧路径没坏。

107. **截图比"第 N 帧"晚一帧。** `capture` 读的是上一帧已经画完的缓冲，所以"第 60 帧的动作"出现在
    `..._90.png` 里（拍帧带时按这个错位读图，否则会误判成"没生效"）。

108. **Linux 上"手指=鼠标"不是自动的：三条栈三种行为。** Windows 由系统把主指针提升成鼠标消息；
    X11/**Xorg** 由 XInput2 为首个触点发**核心** ButtonPress/Motion（GLFW 的 X11 后端只选核心事件，
    所以收得到）；**Wayland 什么都不做** —— GLFW 3.4 的 Wayland 后端源码里一处 touch 处理都没有。
    → 写"触控在某个平台自动可用"之前，先确认是哪条栈；Wayland 会话下必须自接 `wl_touch`
    （`client/input/wayland/WaylandTouch`）。判据：`GLFW platform` 那一行 + `触控：…` 那一行。

109. **Wayland 下没有 attach buffer 的 surface 是不可见的。** 只 `glfwCreateWindow` 不画东西时，
    屏幕上什么都没有、Dock 里却有个图标，看起来像"窗口没建出来"（探针踩到）。→ 探针/工具窗口也要
    建 GL 上下文并逐帧 `glfwSwapBuffers`。

110. **`GLFW_ANY_PLATFORM` 在 Wayland 会话上选的就是 Wayland**（本机实测 393219），
    所以"想验 X11"必须显式 `glfwInitHint(GLFW_PLATFORM, GLFW_PLATFORM_X11)` 或 `-Dpvzce.platform=x11`，
    否则你以为在测 X11，其实一直在测 Wayland。

111. **FFM 调 libwayland 有三个必踩的坑**（都真踩过）：
    ① `wl_proxy_marshal_array_flags` 的**参数数组不能传 NULL** —— 每条请求签名里都有 `new_id`，
    libwayland 会解引用它，传 NULL 直接 SIGSEGV；
    ② **listener 数组必须活到连接结束**：libwayland 只存指针，放在方法内的 confined arena 里会在返回时
    被释放，回调于是**静默不触发**（没有异常、没有崩溃，只是永远收不到事件）；
    ③ **要两次 roundtrip**：第一次派发 global 的过程中我们才 queue `bind`，而 roundtrip 一到 `done`
    就返回，bind 还躺在客户端缓冲区里没 flush —— 第二次才把 `capabilities` 收回来。
    → 判据：`seat capabilities = 7` 那行（`touch=true`）不出现，就是这三条之一。

112. **`--enable-native-access=ALL-UNNAMED` 不是可选项。** 自 JDK 24 起 FFM 的每个入口都是
    restricted method：不带这个参数会**每个调用点打一条警告**，未来的 JDK 会直接拒绝。
    构建里已给 `run`/`test` 带上，外部启动脚本同样要带。

113. **Wayland 上"窗口还没 show"时请求全屏会被静默丢弃。** GLFW 在 Wayland 下把 xdg_surface/toplevel 的创建
    放在 `glfwShowWindow` 里（`_glfwCreateWindowWayland` 只在 `window->monitor || visible` 时建），而
    `acquireMonitor` 的全屏请求是 `xdg_toplevel_set_fullscreen` + `if (toplevel)`。所以顺序必须是
    **先 show、再 setWindowMonitor**；反过来做不报错，只留下一个"游戏以为在全屏、合成器不知道"的状态，
    表现就是窗口压根不出现（X11 无此问题：窗口一创建就存在）。

114. **构造 GL 程序时先 bind 再设 uniform。** `glUniform*` 作用于"当前程序"：在构造函数里设初始 uniform
    而没 `glUseProgram(self)`，轻则 `GL_INVALID_OPERATION`（KHR_debug 会点名
    `glUniform(program not linked)`），重则**静默改掉上一个已绑定程序的 uniform**。
    → 定位这类"只有一个 0x502、不知道是谁干的"错误：`-Dpvzce.traceGl=true`（debug context + KHR_debug 同步输出）。

115. **一个数字两种坐标空间：`wl_touch`/`wl_pointer` 给 surface 像素，`Screen` 要 GUI 逻辑像素。**
    指针位置（`PvzceWindow.setPointerPosition` / 光标回调）用前者；滚动区判定与 `dispatchMouseClicked` 用后者。
    混用的症状极具误导性：**悬停完全正确、点击全部落空**（按钮照常亮——`Button.render` 的"按下"就是
    `active && hovered`——但点在 UI 没听说过的地方）。`guiScale = 1` 时两者相等，所以只有缩放 UI 才暴露。
    → 换算只允许有一个入口（`PvzceClient.touchSink`）。

116. **合成输入的钩子必须走真实设备经过的同一个边界。** `deliverGuiTouch` 收 GUI 坐标、直接喂翻译器，
    绕过了"native 像素 → GUI"那次换算，于是冒烟全绿而真机上"按钮点不动"——
    **绿的是一条真实路径上不存在的路径**。判据：钩子只许调用与设备相同的入口（这里是 `touchSink`），
    不许绕过它去调下游。

117. **FFM 的 upcall 里抛异常不是"被吞掉"，而是直接终止 VM。** 探针实测：回调里抛
    `IllegalStateException` → 打印堆栈 + `Unrecoverable uncaught exception encountered. The VM will now exit`。
    所以"点了没反应但也没崩"**不可能是** Native→Java 回调里动作抛异常造成的，别往那个方向查。

118. **JVM 的 `main` 不是进程的首个线程，所以 `gettid() != getpid()` 恒成立。** JDK 的 java 启动器
    **故意**在新 pthread 上建 VM（[JDK-6316197](https://bugs.openjdk.org/browse/JDK-6316197)），
    于是任何"你是不是主线程"的 C 检查都会失败。libdecor 的 GTK 插件开场就是
    `if (getpid() != gettid()) return NULL;`，**一声不响**地拒载——外面只看到
    `Failed to load plugin 'libdecor-gtk.so': failed to init`，看起来像系统没装 libdecor（装了的）。
    实测：JVM 里 `getpid=42 / gettid=44`，同一台机器的 python3 是 `2/2`；
    而且**没有任何 JVM 参数能改**（`-Xss` 之类无关）。
    → 判据：看到这条报错先别装包，先想"这个 loader 是不是要求主线程"。

119. **Wayland 上窗口装饰只有两条路，JVM 里两条都断。** 一条是 libdecor（第 118 条），
    另一条是服务端装饰——而 GNOME 的 Mutter **不广播** `zxdg_decoration_manager_v1`
    （本机 registry 实测没有这个 global，`zxdg_*` 只有 exporter/importer），所以
    `GLFW_WAYLAND_DISABLE_LIBDECOR` 换不来任何东西；GLFW 自带的那套灰色兜底装饰只在合成器回
    `CLIENT_SIDE` 时才建，那条分支走不到。**判据**：`glfwGetWindowFrameSize` 返回全 0
    就是"桌面没给你画边框"，此时要么自绘（`client/gui/WindowTitleBar`），要么接受无边框。
    顺带：`glfwSetWindowPos` 在 Wayland 上直接报错 "The platform does not support setting the
    window position"，所以**拖标题栏移动窗口**没有 GLFW 层的实现；`xdg_toplevel.move` 需要 GLFW 私有的
    `xdg_toplevel` 与输入 serial，从私有 struct 按偏移猜指针是拿 SIGSEGV 赌，不做。

120. **`pvzce.smokeClick` 只发"按下"，不发"抬起"。** 它的松手本来靠帧循环发现"这个键已经不在按下状态"，
    而合成点击不会让 GLFW 的按键状态变化，于是**一切"松手才生效"的控件在冒烟里都像死的**
    （真机上是好的）。这正是第 116 条那个陷阱的另一副面孔：绿的是一条设备不会走的路。
    → 需要"按下再抬起"就跑 `pvzce.smokeRelease=<帧数>`（与 `smokeDragTo` 互斥，后者自己会松手）；
    判定某个按键是否真的被按下，用 `titleBar.activate()` 那行 `标题栏：按下 X` 日志，别只看截图。

121. **"距顶部"和"距底部"是两种 Y，混用一次就够毁掉一个控件。** GLFW 的光标回调报的是
    **距窗口顶部**的像素，GUI 投影的原点在**底部**，`guiMouseY` 负责翻转。标题栏第一版按 GUI 的 Y
    判定、按距顶部画，症状在日志里看着不可能：**红十字（按距顶部画）正压在按键上，按下（按 GUI 判）
    却说没命中**。判据：任何新控件先在纸上写清"我这几个数字是哪个原点"，并且**只在一个边界处换算一次**——
    一个指针两个原点，就是两个答案。

122. **物理像素 ↔ GUI 单位的比例是 `窗口高 / gui高`，不是 `guiScale`。** 两者只在窗口与 framebuffer
    等大（`contentScale = 1` 且合成器没改过窗口）时相等。本机实测：`guiScale = 2`、窗口 1408 而
    gui 高 704（比例恰好 2，所以这个 bug 一直藏着），另一次窗口被合成器改成 1920x1080 / gui 高 540
    （比例 1.78）。拿 `guiScale` 当比例去换算指针，栏的命中区会**落到窗口另一头**。

123. **Wayland 合成器可以完全忽略 `glfwSetCursorPos`。** 探针实测：`warpCursor(2532, 1390)` 之后
    回调报的仍是原处，`glfwGetCursorPos` 甚至返回 `0,0`；而 `smokeHover` 那套
    "把指针钉在某点"的钩子**看着生效**只是因为它同时记录了位置。要合成"按住某处"，
    必须**每帧重新记录**（`PvzceWindow.setPointerPosition`），并把钩子的坐标写成与控件同一个原点。
    这也是 `smokeHold` 的 `y` 用"距顶部"而不是别的钩子那套"左下原点"的原因。

124. **点击目标要有物理下限，不能只按 GUI 比例算。** 标题栏第一版是 `gui高/240`（1440p 缩放屏上
    36 设备像素），而**可点区域就等于画出来的那一块**——用户三次点击落在距顶 12.7 / 14.5 / 19.0 像素处，
    全在"看着是栏、判定不认"的缝里。Windows 标题栏 46 设备像素、GNOME 47。判据：给指针目标写一条
    **以设备像素为单位的下限**（用 `ceil`，`round` 会差半像素），并且可点区域**比画出来的略宽一点**。

125. **GLFW 的 Wayland 窗口结构，从 Java 这边够不到。** 想给自绘标题栏补"拖动移动窗口"，唯一正规做法是
    `xdg_toplevel.move(seat, serial)`（`xdg-shell.xml` 里 opcode 5），而它要 GLFW 私有的 `xdg_toplevel`。
    实测这条路**走不通**：`glfwGetWaylandWindow`（= `GLFW.glfwGetWaylandWindow`）返回的那个指针
    **本身就不是一个 `struct wl_proxy`**（按 proxy 布局读，+40 是 `0x100000000`、+48 是个堆地址，
    都不是 interface/id；用 `wl_proxy_get_class` 的等价校验也认不出来），所以"把它当 `_GLFWwindow`
    再按偏移找 toplevel"从一开始就找错了对象。顺带：libwayland 的 `wl_proxy_get_class` 会
    **直接解引用** `proxy->object.interface->name`，拿垃圾指针去问必 SIGSEGV——要扫内存必须先用
    `/proc/self/maps` 把候选框在可读区间内（并且排除 rwx 映射，否则代码字节也会被当成接口名）。
    → 判据：`xdg_toplevel.move` 在这套栈里做不到；GNOME 下用 Super+拖动 / Alt+F7，或者等上游给
    GLFW 加 `glfwSetWindowPos` 的 Wayland 实现。

126. **"原生 Wayland 与系统标题栏，目前只能要一个"。** 这不是偏好问题：Wayland 的装饰只有 libdecor
    一条路（第 118 条）而它在 JVM 里起不来，服务端装饰 GNOME 不给（第 119 条），拖动又够不到
    GLFW 的 toplevel（第 125 条）。于是本轮把 Linux 的默认后端切回 **X11/XWayland**（配置
    `prefer_x11`，默认 true），换来桌面自带的标题栏与拖动，代价是 Wayland 桌面上的**触控失效**
    （XWayland 不转发触摸）。判据：启动行 `边框=[0, 37, 0, 0] 自绘标题栏=false` = X11；
    `边框=[0, 0, 0, 0] 自绘标题栏=true` = 原生 Wayland。切回原生 Wayland：
    `-Dpvzce.platform=wayland`（或 `prefer_x11 = false`）。

127. **`captureEvery` 不会自己拍第一张，它挂在 `captureFrame` 上。** 只写
    `captureEvery=30 capturePath=.../s.png` 而**不写 `captureFrame`** 时，后者是默认的 `-1`，
    帧带从 -1 起算就一直不触发 —— 冒烟跑得干干净净、日志里一行错都没有、**目录是空的**。
    （指南把 `captureEvery` 记成"从 `captureFrame` 起每 n 帧"，我是按"从第 0 帧起"读的。）
    → 判据：截图跑完先 `ls` 输出目录；空的就补 `captureFrame=<要开始拍的那一帧>`
    （同一个 `captureFrame` 也会拍下那单独的一张，是想要的）。

128. **导出器的 `hidden` 骨头连 `force_visible` 都拦。** `bone.hidden`（`damage_states`、
    `extra_bones` 产生的骨头）原来在可见性计算的**最后**无条件写成 `false`，注释写的是
    "没有任何 force_visible 能复活它"。这对僵尸装备是对的，但对**片段级**的
    `force_visible` 就错了 —— 那个字段的意思正是"这一段画这个骨头"（雪橇的板子只在
    `walk` 里画）。现在的优先级是：配置级 `force_visible_bones` 不能复活 hidden 骨头，
    片段级 `force_visible` 可以，`force_hidden_bones` 仍然最后说话。
    → 判据：改导出器的可见性顺序之前，先问"这条规则是给谁说的"——给**客户端状态**说的
    （伤害档位）不该被美术覆盖，给**这一个片段**说的应该能覆盖。

129. **"按美术的曲线走"要先确定"美术的哪根骨头是实体"。** 撑杆僵尸的落地位置对不上，
    我先把 `body_1`（躯干）当实体位置，算出来差 0.4 格；换成两只脚的中点又差 0.5 格；
    两边的**跨度本身**就不一样（1.06 ~ 1.13 格，因为四肢还在绕髋关节摆动）。定论是
    **躯干**：玩家读"僵尸在哪儿"读的是身体，四肢是相对的；跨度按躯干归一化，
    `DEFAULT_JUMP_DISTANCE` 就取那个数（1.0908 格）。另外表要按**片段时间**采样
    （43 帧铺满 210 拍，多数采样点落在两个关键帧之间），按源帧号取会在半程差出 0.03。
    → 判据：一条"服务端曲线 = 美术曲线"的表，必须有一例把它与**导出的片段**对起来
    （`PoleVaultTest.theArtAndTheSimulationAgreeOnWhereTheZombieIs`），否则重导出会让它悄悄失效。

130. **`refer/` 是只读的，所以"要从 refer 拿的新素材"得留在仓库内。** 雪橇那张板子在这套素材里
    **根本不存在**（`Zombie_bobsled.reanim` 只有骑手，`refer/` 全库没有 sled），而导出器按
    "`refer/anim/<名字>.png`"找零件图。做法是：生成器把图画进
    `assets/.../entities/.../<bone>.png`（真正被打包的那一份），**再复制一份**到
    `refer/anim/Zombie_bobsled_sled.png` 供导出器读；`tools/gen_bobsled_sled.py` 是这张图的
    唯一出处，改图要重跑它 + 重导出。判据：只有 `assets/` 那一份会在游戏里显示，
    `refer/` 那份只是导出器的输入。

131. **"服务端在跑什么"与"文件里写了什么"是两张表，下发的那张是前者。**
   玩家买来的钉耙只存在于 `LevelServer.mechanics()`（构造时由 `withPlayerMechanics` 合进去的
   解析结果），而 `payloadFor` 发的是 `LevelMechanics.payloads(def)` —— **关卡文件声明的**那张。
   客户端 `ClientMechanics.worldOverlays` 遍历下发来的 `mechanicIds()`，于是 overlay 从来没被创建：
   僵尸在草坪上被钉死，画面上什么都没有，服务端与客户端都不报错。它躲了很久，因为
   **没有任何内置关卡声明过 `pvzce:rake`** —— 这条路的唯一用户是"买过钉耙的玩家"。
   → 判据：一个机制如果可能来自"关卡之外"（玩家、变异、关卡创建时掷的骰子），
   那它就不能只靠 `def` 拼下发内容。加这类机制时先问一句"客户端是怎么知道它存在的"，
   并在测试里断言**`LevelInitS2C` 的机制表里有它**，而不是断言服务端装了它。

132. **"这个内容声明的贴图"对骨架内容来说是一个目录，不是一个文件。**
   植物与僵尸的 `texture` 字段指向的是**部件目录**（`textures/entities/plant/attacker/pea_shooter/`
   里是一堆 `anim_head1.png`、`peashooter_backleaf.png`…），而 `EntityArt.sprite(id)` 会把它当成
   一个 PNG 路径交出去。于是编辑器三个调色板（植物 41 行、僵尸 36 行、卡池 44 行）全部画成
   品红/黑的缺失贴图，而且**没有任何一处报错** —— `TextureManager` 找不到文件就回落到那一格。
   → 判据：一个内容 id 只能有两种"图"——`EntityArt.animationFile(id) != null` 的走**骨架预览**
   （`EntityPreview`），否则才走单张贴图。加任何"列表/卡片/图标"的绘制前先问一句
   "这个 id 的美术是一张图还是一具骨架"；这也是为什么 `AnimationManager.iconTexture`
   （取控制器模型里最大的部件贴图）从来没能救它——它拼的 `animations/<id.path()>.json`
   在内置内容里**一个文件都不存在**，根目录下零个 JSON。

133. **一个"一次只报一件"的结构，会在它不再只发一件的那天开始静默丢东西。**
   `LevelRewardS2C` 原本是三个单值字段（一个解锁 / 一个增益 / 一个物品），`RewardSettlement`
   也只记住每一类的**第一件**。一次通关同时发两张卡时，第二张照发进档案，**页面上一个字都没有**。
   → 判据：凡是"服务端一次可能发多份"的东西，形状就得是列表（`grants`），"第一件"是**从列表
   推出来的视图**（`headline()`）而不是存储形状。同一轮里 `WaveDirector` 的强制首只僵尸行
   也是这条：能装多件的容器不要用单数字段建模。

134. **"相机空间"与"指针空间"是两个上下相反的 Y，而棋盘是垂直居中的 —— 所以错半个棋盘时，
   中间那一行看起来是对的。** `PvzceCamera.screenY()` 与 `worldY()`/`inBoard()` 同边（自下而上的
   棋盘像素），指针却是自上而下报告的；`smokeHoverCell` 漏了那次翻转，于是 `=4,2` 把光标钉在第 3 行。
   **判据**：棋盘上"看起来对"不是判据（第 2 行恰好是两种读法的同一个格，`踩坑清单` 121 的同族）；
   判据是**让代码自己说**——`-Dpvzce.traceInput=true` 打出 `cell=x,y`，一眼就是 4,3。
   凡是要"把某个东西指到某格/某点"的代码（悬停、工具、探针、编辑器预览）都该有这一行。

135. **带帧号的冒烟钩子，"帧号"必须自己判。** `smokeType` 少了 `clientTick != frame` 这一半，
   于是它在**第一帧**就把整串字打完了 —— 打进加载页，一个文本框都没有。现象是"打字这条链坏了"
   （逐字符注入、文本框焦点、浮层路由全都被怀疑了一遍），真因是它早了 170 帧。
   **判据**：形参里有 `clientTick` 不等于它被用了；`Done.add(frame)` 只保证"只发一次"，不保证
   "发在那一帧"，两句话得一起写（`if (clientTick != frame || !done.add(frame)) continue;`）。
   同一族还有"帧号从哪算起"：带 `smokeLevel` 的一跑从**关卡**算、纯菜单的一跑从**进程**算，

141. **"客户端能自己算出来的就不发"这条省下的那个包，可能是一个整局都玩不对的起点。** 节奏草坪的
   谱面起点原本由客户端自己锚（"准备阶段结束那一帧"），因为服务端也是那一刻起的。但
   `ClientLevel.preparing()` 在第一包状态到达之前**默认 false**：客户端在关卡 tick 0 就锚了，
   服务端锚在玩家按"开始"的 tick 118（存档里的 `RhythmStart`）。差 118 tick 远大于判定窗口
   （12 tick），于是**每一个 `RhythmHitC2S` 都被拒**——玩家看到的是"我明明按在拍子上"，
   而两个 HUD 各说各话（客户端 combo 5、存档 0 命中 20 漏）。→ **判据**：凡是"两边各自推出同一个
   时刻/编号"的设计，先问一句客户端的那份输入**是否已经到达**；镜像里有默认值的字段（false / 0）
   与"服务端真的处于这个状态"在屏幕上没有区别。现在这条数走 `MechanicSyncS2C`
   （`RhythmMechanic.Start` + `RhythmClientMechanic`），读档后再发一次。
   **同一个教训的另一半**：客户端拿这条插值时钟去数漏音符时，一帧跳 9000 tick 的心跳校正被当成了
   九千个音符漏掉（`MISS 127`）——插值出来的钟只能用来**判断现在**，不能用来**清算过去**，
   跳变超过一帧就只推游标不计数（`RhythmPlay.MAX_SWEEP_JUMP_TICKS`）。

142. **静帧看不出方向：一个会动的东西"往哪动"必须由断言钉住，不能靠看截图。** 节奏草坪的音符按
   `progress`（0 = 刚出现、1 = 该按了）插值到世界坐标，而这一版的算术写成了
   `judgeY + progress * (topY - judgeY)`——**从判定线往上飞**，与它自己那行注释（"0 在顶端、
   1 在判定线"）正好相反。棋盘上世界 y 是**向上增长**的（`board.y()` 是草坪的屏幕下沿、行 0 画在
   最下面），所以"往下"是一次减法，写成加法也照样是一串在动的胶囊：我按 `captureEvery=100`
   拍的胶片里音符确实在动，方向却是用户先看出来的。→ **判据**：任何"随时间从 A 到 B"的位置
   插值，(1) 把它放在**持有那个参数**的地方（现在是 `RhythmPlay.Flight.worldY`，`progress` 的
   隔壁），(2) 用**逐点比较**的用例钉住单调方向（`RhythmPlayTest.aNoteComesDownToTheJudgementLine`
   比较每一个 tick 与上一个的高低），(3) 需要从画面确认时把胶片拍密
   （`captureEvery=30`，半个飞行行程内至少两张），稀疏的帧带只能证明"有东西在动"。

143. **胶片不仅要证明"那一下点到了"，还要证明"那一眼看得见"——而同一帧里的两个钩子是同一个时钟。**
   `smokeClick`（点卡片）与 `smokeClickCell`（点格子）都从 `smokeClickFrame + k * smokeClickPeriod`
   起算，所以"选中卡片"和"把卡片放到格子上"会落在**同一帧**：卡片在被画出来之前就已经被消耗、
   `selectedCard` 归 -1，于是"拖卡时高亮整列"这个新画面在一整条胶片里**一帧都没有**（像素比对：
   目标列的草地纹丝不动）。→ **判据**：要拍一个"持卡/hover 状态"，就让最后一次 `smokeClick`
   **没有**配对的 `smokeClickCell`（`smokeClickRepeat=2` 而 cell 列表只写一个），它之后的那段
   帧带才是那个状态；另外**别把新画面放在被 hover 的那一格上量**（植物和幽灵会污染像素），
   挑一列空的、并在没被 hover 的那一行采样。

144. **"暂停"不是"结束"：拿 `AL_PLAYING` 当"这一发还在不在"的判据，会把暂停中的曲子从轨道手里弄丢。**
   音乐控制器用"源还在不在播"判断一条 `loop: false` 的 cue 是不是放完了（`finishOneShotIfDone`），
   而暂停对话框会把**每一个**音乐源 `alSourcePause` —— 暂停中的源报 `AL_PAUSED`，于是轨道当场
   **遗忘**它（`currentSource = -1`，源却还握着整首歌）。此后 `leaveLevel()` 的 `stopCue` 得到
   "已经没有源了"，什么都不停；玩家点「保存并退出」时对话框 `close()` 又触发 `setPaused(false)`
   把那个 `AL_PAUSED` 的源 `alSourcePlay` 唤醒——歌从此没有任何人管得住，一直放到进程结束。
   现象是"退出关卡音乐不停"，而**只有 `loop: false` 的曲子会中招**：全游戏只有节奏草坪那首歌是这样
   （1-1 的 grasswalk 是循环轨，所以用普通关卡怎么试都是好的）。→ **判据**：问一个媒体对象
   "还在不在"时先问清"暂停算不算"；`PLAYING`/`PAUSED` 是"占着"，`STOPPED` 才是"结束"。
   另外"离开关卡＝静音"这种硬要求不要只依赖状态机——`silenceForTheRoad` 在轨道自称没在放时
   仍把那条轨的两个源直接停掉。诊断入口：`-Dpvzce.traceMusic=true`（这一次就是它把
   `(already silent)` 与 `(stopping over 0.5s)` 的差别摆出来的）。

145. **把默认值写进配置文件，等于把"当年的默认"钉在玩家身上。** 键位表是"每个动作一行"整个写进
   `config/pvzce-client.toml` 的，于是玩家从没碰过的动作也在文件里带着**当时的出厂键**；等默认值改了
   （节奏草坪的列键 `Q W E R Y` → `A S D J K` → `S D F J K L`），老配置一读就把旧键位原样装回去——
   **代码没错、文件也没错，只是文件比默认值老**，而玩家看到的是"你根本没改"。→ **判据**：凡是"默认值 +
   用户覆盖"两份合一的配置文件，只写**与默认不同的项**（改动才能到达没动过它的人）；已经有老格式在野外时，
   读盘再加一条升级规则——**值等于该键历史上用过的默认值就当作没被选过**（`KeyBindings.SUPERSEDED_DEFAULTS`
   / `asShipped`），并把这条历史显式写在代码里（它是唯一能分辨"旧默认"与"玩家选择"的信息）。
   验证方式是拿一份真·老配置跑一遍：`.smoke/rhythm8/`（配置里 `rhythm_col_0 = 81` 即 Q）里草坪底部
   显示的是 `S D F J K L`。

146. **跳过某个能力的门，会把它已经许诺出去的活一起跳掉。** 节奏草坪的停火是 `PlantEntity.tick` 里的一句
   `continue`（`holdsFire` 为真就不 tick 那个能力），而"一次攻击"并不总是一瞬间：双发的第 2 发、机枪的后 3 发
   是**后续 tick 上才出生**的（`ShooterCapability.firePendingShots` 按 tick 递减待发队列），大嘴花咬完还要
   **嚼 1800 tick 才消失**。于是这一关里双发每次只出第一发——与单发完全没区别（3 轮完美 60 伤害，而数据写着
   120），大嘴花咬一口就永远停在"嚼"、永远不离开那一格。→ **判据**：任何"停掉某个行为"的开关，先问一句
   "这个行为有没有已经答应出去、**要在以后几拍才交付**的部分"；有的话就配一条只推进欠账的通道
   （这里是 `hasPendingWork`/`tickPending`，与 `tick` 分开，且明确不许在里面做新决定）。
   用例：`RhythmTest.anOrderedVolleyKeepsItsBurst`（三档各两发＝120 伤害）与
   `anOrderedBiteStillFinishesItsChew`（嚼完必须消失）——两条在修之前都是红的。

147. **"谱面卡不到点上"未必是谱面的错：先量谱面 vs 音频，再量播放 vs 时钟。** 用户报"铺面经常卡不到点上"、
   要求重新生成谱面。逐颗量过之后：173 颗音符对**实测 onset**（spectral flux 峰值）中位偏差 **5.8 ms**、
   99% 在 30 ms 内、前后半段无漂移（+1.9 / −3.7 ms）、95% 落在强度 ≥8 的格上——**谱面没问题**。
   真正的原因在播放这一侧：音乐是**在要放它的那一刻整首同步解码**的（`stb_vorbis_decode_memory` +
   `alBufferData`，189 秒的 ogg = 33 MB PCM，全在渲染线程上），实测 `music/ancient_egypt_ultimate_battle`
   **149 ms**（`grasswalk` 120 ms、`crazy_dave` 76 ms）。歌因此比它的 cue 晚**约九 tick**才响，而谱面按同一
   tick 判定——PERFECT 窗口 ±4 tick、GOOD ±8，所以**跟着音乐按最好只能 FAIR**。
   → **判据**：(1) "对不上拍"这类报告先分成"谱面 vs 音频"与"播放 vs 时钟"两段，各自量出数字再动手；
   (2) 整首解码的资源**不能等到要播它时才解**——服务端在 `LevelInitS2C` 之前发一条 `preload`
   （`MusicEventS2C.preload` + `SoundEngine.preload`），解码落在加载画面里，cue 到点即出声。
   诊断入口：`[sound] decoded <file> in <ms>`（`-Dpvzce.traceMusic` / `traceSounds` 下打印）。

148. **GUI 坐标的 y 是向上的，矩形参数里的 y 是它的<下>边缘——"接在下面"要减高度。** 能量条第一版

149. **按"每行一个键"收集行时，键与另一行的身份撞车就会静默丢行。** 关卡列表把行收进

150. **按机制 id 分发的那条同步通道，一个机制只能有一种载荷。** `MechanicSyncS2C` 由

   否则伤害照算、画面与声音全无。

   合并成一块（这里：有战报时金币降级成一行脚注），要么显式按对方的结束位置续排。截图里看到
   文字互相压字，八成不是字太大而是两个锚点各画各的。

154. **同一张图里"背景图像素"与"世界格"是两套坐标，混一次就整条带子消失。** 原版 `Board::DrawFog` 的
   `x*80-15, y*85-30` 是**背景图自己的像素**；本项目里棋盘每格在 1920×1080 下是 144px
   （`PvzceCamera.boardScale()` = 1.8），而且世界格与屏幕像素之间还隔着棋盘原点与相机投影。
   这一轮两处各错一次：先按世界格直接画（雾画得又小又偏），改成自己乘 `unitX/unitY` 画"屏幕像素"
   （整条带被推到屏幕外，画面里一滴雾都没有——日志里 `drawn=42` 一切正常）。
   → **判据**：往世界层画东西只有两种合法写法——要么参数就是**世界格**（`client.drawTextureShaded` /
   `drawSolid` 这类），要么用 `camera.screenX/screenY` 换算；**不要**自己乘格子的像素大小。
   素材尺寸是"参考图像素"时，先乘 `boardScale()` 换回世界格再交给绘制。判断"画了但看不见"的岔路：
   临时把它画成洋红实心——还看不见就是坐标/层的问题，看得见就是贴图 alpha 的问题。
