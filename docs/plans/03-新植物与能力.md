## 2. 需要的新能力（6 个）

### 2.1 `pvzce:spike` — 地刺

- 文件：`common/capability/plant/SpikeCapability.java`。
- 行为：每 `interval`（默认 30 tick）对**站在自己格子里且 `layer() == GROUND`** 的僵尸
  造成 `damage`（默认 20）点 `pvzce:impact`（不吃护甲、不触发灼烧）。
- **僵尸不咬它**：这是本能力唯一的系统性改动。
  `ZombieEntity.walkOrEat`（`server/entity/ZombieEntity.java:324`）现在读
  `level.plantAt(...)`。新增 `LevelServer.biteTargetAt(column, row)`：在 `plantAt` 的基础上
  跳过带 `#c:walk_over` 标签的植物；`walkOrEat` 改读它，**工具（铲子/水壶/手套）仍读 `plantAt`**。
- 被车压毁：`ZamboniCapability`（批次 5）与 `HammerCapability`（巨人）走"直接 `plant.remove()`"，
  所以这条是免费的；但要给 `SpikeCapability` 加 `crushable()` 语义的注释说明。

### 2.2 `pvzce:torchwood` — 火炬树桩

- 文件：`common/capability/plant/TorchwoodCapability.java`。
- 需要一个**弹丸穿过的钩子**。现在弹丸与植物的交互只有"命中/被挡住"两种，
  所以新增：`PlantCapability.onProjectilePass(PlantEntity self, ProjectileEntity p, LevelAccess level)`
  （默认返回 `false` = 不处理）。`ProjectileEntity` 每 tick 检查自己格子里有没有植物，
  逐个问一遍；返回 `true` 表示这一发已经被改造（不再问后面的植物）。
- 火炬树桩的实现：把弹丸的 `damage` 翻倍、`damageType` 换成 `pvzce:fire`（灼烧）、
  在弹丸上叠一个火焰附属粒子。同一发**只烧一次**（用一个 `torched` 标记，避免一排火炬叠 8 倍）。
- 火豌豆美术：项目里已有 `refer/anim/FirePea.reanim` + 贴图，
  `data/pvzce/projectiles/` 下要加 `fire_pea`（如果还没有——先查一遍，
  `PvzceIds.PEASHOOTER_PEA` 已存在、`MendelMutation` 提到 `FIRE_PEA`，很可能已经有了）。

### 2.3 `pvzce:reveal` — 路灯花

- 文件：`common/capability/plant/RevealCapability.java`。
- 只是往迷雾系统登记的"可见源"：`FogMechanic` 维护一个
  `List<RevealSource(cellX, cellY, radius)>`，渲染时用它把雾的 alpha 挖洞。
- 所以本能力**依赖批次 2**；批次 2 先留好这个接口（`FogMechanic.addRevealSource`），
  本批次只填实现。

### 2.4 `pvzce:blow_away` — 三叶草

- 文件：`common/capability/plant/BlowAwayCapability.java`。
- 行为：种下后 `fuse_ticks`（默认 60）播放一次吹风，把**所有 `layer() == AIR` 的僵尸**
  走 `ZombieEntity.blowAway(direction)`（新方法：把它们移出屏幕外并 `remove()`，
  与气球僵尸被打爆的既有路径一致——先查 `BalloonCapability` 是怎么处理"被打爆"的，复用那一条）。
- 同时吹掉场上的雾（对迷雾系统发一次"短暂揭开"）；自己用一次就 `remove()`。

### 2.5 `pvzce:shell` — 南瓜头

- 文件：`common/capability/plant/ShellCapability.java`。
- 关键点是**它和里面的植物共占一格**，靠的是既有的 `PlacementDef`：
  `layer = LAYER_GROUND + 1`、`count = 1`、`group = "shell"`（新组名），
  并且 `#c:carrier` 语义要反过来——它**罩住**同格已有的植物。
  §3 说明这套怎么落地。
- 行为：僵尸咬的时候先咬壳（`biteTargetAt` 返回壳），壳破了才咬里面那株。
  → 所以 `LevelServer.plantAt` / 新的 `biteTargetAt` 要**从外向内**排：
  `plantsBottomFirst` 的**最后**一个仍是"最外面的那一层"，现在就是这个语义，无需改动。

### 2.6 `pvzce:magnet` — 磁力菇

- 文件：`common/capability/plant/MagnetCapability.java`。
- 行为：每 `interval`（默认 300 tick）扫描半径 `range`（默认 4.5 格）内
  **带护甲**的僵尸，把最靠近自己的一个的护甲**整条移除**
  （`ArmorCapability` 需要一个新的 `strip(level)` 入口，而不是靠打光耐久）。
- 被吸走的护甲落到磁力菇旁边变成一个小掉落物？**不做**——原版是直接消失，
  做掉落物要多一套实体，收益低。

## 3. 放置系统的两处扩展

`api/content/PlacementDef.java` 的文档已经预告了南瓜头（"a plant-on-plant-cover (pumpkin)"），
所以这次是把预留的用法**接上**，不是新造概念：

1. **南瓜头**：`"placement": {"layer": 2, "count": 1, "group": "shell"}`；
   同格允许"一株普通植物 + 一个壳"。需要在 `PlantPlacement` 里确认
   `group` 互斥的判定是"同组才互斥"，那么壳的组名与 `plantable` 不同就自然共存。
   **先写一条纯函数测试**把矩阵跑一遍（`PlantPlacementTest` 已有这个形状）。
2. **地刺**：`"placement": {"layer": 1, "count": 0, "group": "under_plant"}` ——
   `count = 0` 表示它不占层（僵尸照样能被种在上面的植物挡住），
   `group = under_plant` 是既有的"可以和普通植物共存"的组（土豆地雷用的就是它）。
   如果 `count = 0` 在 `PlantPlacement` 里没有正确语义，就改用地雷那套（`layer 1 + under_plant`）。
3. **海蘑菇**：`"placement": {"requires_water": true}` 走既有的地形标签
   （`#c:water`，见 `data/c/tags/scene_element/water.json`）——检查 `PlantPlacement`
   有没有现成的 `requires_*` 标签机制，有就加一个标签文件，没有就加一条 placement 字段。

## 4. 每株植物要写的六处

照现有植物的形状（以 `chomper.json` 为模板）：

1. `data/pvzce/plants/<id>.json` —— 定义（cost / health / capabilities / sounds /
   `animation_dir` / `texture` / `render_scale` / `order`）。
2. `data/pvzce/slots/<id>.json` —— 卡槽定义（费用与冷却的卡面副本）。
3. `assets/pvzce/animations/plant/<族>/<id>.json` —— 由 `tools/reanim_to_pvzce.py` 转出。
4. `assets/pvzce/textures/entities/plant/<族>/<id>/` —— 由 `tools/group_entity_assets.py` 归位。
5. `assets/pvzce/textures/gui/cards/<id>.png` —— 卡面图标（从 reanim 里最大的那块烘一张，
   或用 `tools/render_controller_icons.py`）。
6. `assets/pvzce/lang/{zh_cn,en_us}.json` —— `plant.pvzce.<id>` / `.desc` 两个键；
   `data/pvzce/tags/plant/*.json` 按需补标签（`#c:walk_over` / `#c:tall` / `#c:water_only`）。

`order` 字段决定图鉴排序（原版图鉴号），9 株的号要按原版插进去。

## 5. 顺带要做的两件基础设施

### 5.1 运行时给卡槽加一张卡（花瓶要用）

现在卡槽只在开局建一次（`LevelDef.SeedPlan` / `LevelMechanics.cardSource`），
运行期没有任何"往条里加一张卡"的入口。花瓶要求"砸开后掉出那张植物卡，捡起来能种"。

→ 新增 `LevelServer.addCardToBar(Identifier cardId)`：
- 从 `SlotResolver.resolve(cardId)` 拿到 `ResolvedCard`，造一个 `Slot`（冷却 0）；
- 追加到 `plantPlayer.slots()` 末尾，然后 `send(new SlotSyncS2C(toSlotInfo(slot)))`
  （包与客户端 `ClientLevel.upsertSlot` 都已存在）；
- 卡槽上限**不受 `max_seed_slots` 限制**（花瓶是额外的），但同一张卡重复加入时**叠在同一槽**
  （`Slot` 加一个 `usesLeft` 累加）——不对，`Slot` 的 `usesLeft` 是消耗品计数，
  这里要的是"多一张可种的卡"，所以**同 id 直接叠加 `usesLeft`** 是最省事且语义正确的做法。
- 存档：卡槽本来就走 `Slots` 分区，所以续档自动带上，不需要新分区。

这一条同时被花瓶（批次 7）与后续可能的"变异发卡"复用，所以放在植物批次里先做。

### 5.2 纵向飞行的弹丸（杨桃要用）

`ProjectileRef.direction()` 只有 ±1 的横向（`api/content/ProjectileRef.java:83`）。
杨桃的上下两发需要纵向。做法：

- `ProjectileRef` 加 `vertical` 布尔（或把 `row_offset` 复用成"纵向目标行"）；
- `ProjectileEntity` 的移动从"只改 X"改成"按 `(dx, dy)` 走"，`dy` 默认 0；
- 命中判定从"同一行"改成"同一格"（对纵向弹丸而言）；
- 目标搜索（`ProjectileRef.atTarget`，`:117`）按方向选。

**代价可控**：现在所有弹丸的 `dy` 都是 0，所以既有内容的行为逐字节不变。
