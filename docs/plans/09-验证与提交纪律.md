## 2. 命令模板

```bash
export GRADLE_USER_HOME=$PWD/.gradle-user
export GD=$PWD/.smoke/gd          # 一次性的游戏目录

# 纯单测
./gradlew :pvzce-game:test

# 单个包
./gradlew :pvzce-game:test --tests "com.pvzce.common.level.mutation.*"

# 冒烟（路径必须落仓库内、必须绝对路径）
mkdir -p .smoke/<主题>
./gradlew :pvzce-game:run -Ppvzce.gameDir=$GD -Ppvzce.smoke="\
pvzce.smokeLevel=pvzce:yard/survival/endless_lawn_day \
pvzce.captureFrame=200 pvzce.captureEvery=2 pvzce.smokeFrames=400 \
pvzce.capturePath=/media/crystalneko/enkoo/java/pvzce/.smoke/<主题>/s.png"
```

诊断开关（`冒烟与截图指南.md` §4.7）：`-Dpvzce.traceMessages=true`（看服务端拒绝的原因）、
`-Dpvzce.traceTextures=true`（缺贴图）、`-Dpvzce.traceFrames=true`（卡顿）、
`-Dpvzce.traceMusic=true`（两条音轨打架）。

**要进锁着的关卡**：先跑一次 `pvzce.smokeScreen=levels` 并用**同一个 `-Ppvzce.gameDir`**
人工勾"全解锁"建一次世界，之后那个目录下所有关卡都能直接开
（`冒烟与截图指南.md` §2.1）。

## 3. 每个大任务的固定动作清单

1. 改代码（一次只改一件事；"太长/太短/不对"按 `验证约定.md` §4 先把时钟/元素列全再改最大的那一项）。
2. 跑对应档位的单测。
3. 需要时跑一次冒烟，图看一遍。
4. **玩法类自己模拟玩**：起真 `LevelServer` + `Connection.createMemoryPair()`，
   跑够 tick，断言结果（harness 见 `testutil/ServerHarness` / `ClientHarness`）。
5. 写文档（在"行为确认通过之后"）：
   - `../架构变更记录.md`：现象 → 定论，一行到一段；被回退的尝试最多留一行。
   - `../todo.md`：做完的条目删掉；新发现的缺口加进去。
   - `../当前项目架构.md`：只有能力/已知差距真的变了才改。
   - `../踩坑清单.md`：新教训按主题加一条（≤5 行，"下次该怎么做"）。
   - `../架构-服务端.md` / `../架构-客户端.md` / `../架构-实体与能力.md`：
     对应那一层的行为真的变了才改。
   - **`../mod-guide/*` 默认不改**（只有用户点名才改）。
6. `git add -A && git commit`。

## 5. 全部做完之后的报告怎么写

报告落在 `../总结报告-变异与内容扩展.md`（新文件），结构：

1. **一句话**：这一轮做了什么、用户报的 9 类缺陷与全部新需求的状态。
2. **缺陷表**：每一条 —— 用户原话 → 根因（文件:行）→ 修法 → 怎么验的 → 现在的行为。
3. **新内容表**：20 条变异 / 9 株植物 / 6 种僵尸 / 15 个关卡 / 4 条无尽 / 2 个新关卡类型 /
   1 个商店 / 1 个资源包页，每项一行"是什么、在哪里、怎么验的"。
4. **break change 清单**：关卡 id 变更（无尽分类合并）等，逐条写"变了什么、为什么、
   旧存档会怎样"。
5. **没做完 / 明确不做的**：逐条写清楚，并**同步进 `../todo.md`**。
6. **验证证据**：跑了哪些测试、哪几次冒烟、图在哪（`.smoke/<主题>/`）。
7. **下一步建议**：留给世界 5 的 8 株植物、`.zip` 形式的包、世界级数据包目录等。

## 6. 立项时就该记住的三条

1. **不要问需求**。需求已经在 `00-问答记录.md` 里定完了；动工后遇到不确定的实现细节，
   按"哪个更自洽、更好扩展"自己选，并写进 `架构变更记录.md`。
   只有**真正与用户决定冲突**的发现才值得回头说一句（例如"素材盘里没有 ZomBotany 的
   原版动画，我合成了"）。
2. **不要为没验证的东西写文档**。回退时那份记录要重写第二遍。
3. **不要记用例数**。"全绿"只有在用例本身确定性时才是信号——所以缺陷 10
   那三条偶发用例必须先修掉。
