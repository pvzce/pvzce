# 决策记录：为什么长这样

> 这里记**取舍**——用户拍板的事、以及实施时自行拍板的小事。它是"这些规则为什么长这样"的最终依据：
> 与"按原版应该……"冲突时以这里为准（`验证约定.md` §9：对用户有决定权的事实不查资料）。
> 代码里凡是写了"用户答复 / 用户要求"的注释，指的都是这张表。
>
> 与别处的分工：
> - `00-架构总览与开发路线.md` §0.2 是**规划期**已确认的技术决策（D1~D15，约束全部文档）；
> - 本文件是**落地期**的取舍（实施中途问的、当场定的）；
> - "现象 → 定论"的历史在 `架构变更记录.md`，本文件只留**结论与理由**，不写排查过程。
> - 某一份设计文档内部的决策（例如编辑器那六条）留在该文档自己的 §0，本文件 §4 只做索引。

## 2. 自行拍板的小事（用户未表态，日后可改）

| 事项 | 我的决定 | 理由 |
|---|---|---|
| ~~3-6~4-10 每关发哪株植物~~ | ~~让 9 株新植物均匀落在世界 3/4~~ → **已被 Q16 取代**：发卡链回到原版（3-10 海蘑菇、4-1 路灯花、4-2 仙人掌、4-3 三叶草、4-5 分裂豌豆、4-6 杨桃、4-7 南瓜、4-8 磁力菇、4-10 卷心菜投手），原版「什么都不发」的八关仍由本项目的工具/增益填 | 均匀分布正是当年把世界 4 的奖励整体错位一格的原因 |
| 迷雾渐变的几何 | 右起黑幕，按列做线性 alpha（`FogData.alphaAt`） | 与用户选的"越靠右越黑"一致 |
| 商店商品的显示顺序 | 卡槽 → 阳光铲 I → 钉耙（便宜的在前） | 与关卡列表"由弱到强"一致 |
| 变异名字的第二份表 | 删掉客户端那份，改读语言文件 | 还掉 `todo.md` 的这笔债 |
| 教程关的剧本 | 先演"卡槽替换 / 阳光速率 / 坚果保龄球 / 传送带"四种类型，`random: false` | 四种类型各一个例子 |
| 关卡脚本变异与定时台词的时钟 | 都用**关卡自己的** tick | 全局 tick 跨关卡连续，会让第二关的台词一口气播完 |
| 变更记录的分卷粒度 | 主文件留"按层定论索引 + 最近 3 轮"，更早的每轮一份归档 | 主文件仍能顺序读最近的历史，更早的按标题可检索 |
| 统计块只统计四项 | 主源码/测试/资源的文件与行数 + 内容条目数 | 再多就会变成需要维护的表，而它本来是为了**不用**手维护 |

## 3. 被否决 / 明确不做的（免得下一轮重提）

| 事项 | 结论 | 出处 |
|---|---|---|
| 卡槽轮换把 0 阳光或种不下的植物送进卡槽 | **保持现状**（这是变异"就是乱"的设计，不是缺陷） | 用户在变异轮答复 |
| 让 UI 页面自动注册（把 `PAGES` 换成注解扫描） | 不做，注册式已够 | 编辑器设计方案 §8 |
| 关卡 JSON 支持 `$ref` / include | 不做，只做内存 codec 拼装 | 编辑器设计方案 §0 决策 4 |
