# 架构变更记录

> 记历史：**现象 → 定论**。现状看 `当前项目架构.md`，取舍看 `决策记录.md`，教训看 `踩坑清单.md`。
> 写法：只记**最终落地的做法**；被回退的尝试最多留一行（"曾试 X，已回退，原因 Y"），
> 不给每个错误写长文。写之前先确认行为通过 —— 回退时这份记录要重写第二遍。

> **结构**：§1 是**定论索引**（一条一行，链到归档全文），§2 是**最近 3 轮全文**。
> 更早的每一轮在 `架构变更记录/` 目录里按 `YYYY-MM-<轮名>.md` 分卷（冻结不改）。
> 归档只搬家不改写：分卷前的每一节都在，找一条旧定论用 §1 的索引，或直接在该目录里搜索。
> 分卷规则：主文件留最近 3 轮，其余每轮一份；一条定论只在一个归档文件里，主文件不重复正文。
> 文件名不带空格（`/` 写成 `、`），这样链接可以直接写中文路径。

## 2. 最近 3 轮（全文）

# 第一株不由原版素材转换来的植物：冰爆菇（冰层累积 → 冻结 → 击碎）与小游戏「冰库」

> 用户提的需求：往项目里加**第一株原创植物**（"我给你 AI 生图工具"），并"做一个对应的小游戏关卡
> 来使用这个植物"。这一轮记两件事：**这条新链路长什么样**，以及**我在其中犯的两个错**——
> 两个都是设计错误而不是笔误，而且第一个会让单测通过、实机永远不触发。

## 现象与根因

- **49 株植物全是 `refer/anim/*.reanim` 转换来的**，没有"自己画的植物"这条链路的任何先例。
  卡面、部件贴图、动画 JSON、图标四样东西平时都由 `tools/reanim_to_pvzce_all.py` 与
  `tools/gen_*.py` 从原版零件派生；一株没有原版零件的植物，这四样都得从零产。
- **原版没有"冰层累积"这类机制**：`ZombieStatus` 只有 `SLOW` 与 `IMMOBILIZED`，`damage_types/`
  八个类型里没有"对冻结目标加成"的读法，`StatusOnHitCapability` 每次命中都是**覆盖**同一状态
  （`instance.ticks = Math.max(...)`），所以"打三下冻住"用现成能力组合不出来。

## 定论

**1. 美术链路：`tools/gen_iceboom_shroom.py` 一份脚本从源图产四样，源图留在 `tools/art/`。**
源图是文生图按"冰蓝色蘑菇"这一通用形象生成的（不是照原版任何一株的造型），随 GPL-3.0 入库；
脚本把它按**品红底 flood fill** 抠出来、按"脖子"切成 `head`/`body` 两层、降到棋盘的
100px/格比例、再写出控制器动画 JSON 与卡面。**分层是必须的，不是好看**：不切两半就只能整株平移，
待机呼吸与开火后坐都做不出来。

**2. 补颈：被帽子挡住的那一段茎必须画回去。** 帽子的像素是**盖在**茎上的，所以那一片像素在源图里
只有帽子。头部一抬起来，缺口就露出草坪——第一次做出来正是"帽子上移 3px，中间空一条"。
现在的做法是把分割线以下的茎按行在两缘之间**用茎自己的颜色填回去**（`paint_neck`），并且
**这些像素从 head 层拿走**（两边都留 = 抬头时茎上横着一条冰晶，这是第二个版本的症状）。

**3. "第几发冻住"必须记在僵尸身上，不能记在弹丸身上。** 第一版把计数放在
`ShatterCapability`（弹丸能力）的实例里，**单测直接调 `cap.onHit` 三次是通过的**，
但实机里弹丸命中即销毁，每个弹丸的计数永远是 1——三发冻结在真实游戏里**永远不可能发生**。
现在计数落在 `ZombieEntity.addBuildup(key, by)`（`Identifier` 键 + 计数，进存档，与
`statuses` 并列但**没有时钟**）：它按"这一株的冷"这个键累计，所以寒冰射手的减速不会推进它，
读档也不会把已经付过钱的三发忘掉。

**4. `replacesDirectHit` 是一条承诺：回答了它就必须自己把伤害打出去。** 第二版让弹丸能力
接管命中（3 倍碎冰必须是一个数、不能是"命中伤害 + 奖励"），却只在碎冰那一支里调了 `damage()`——
于是**平时那一发什么都不做**：三段冻结、僵尸却一直是满血，画面看起来完全正常。现在三条分支
（普通命中 / 冻住的那一发 / 碎冰）各自结算伤害，普通命中走 `target.damage(def, damage, level)`
（和真弹丸同一条路，含护甲与火把）。

**5. 冻结是 `IMMOBILIZED`，碎冰是新的伤害类型 `pvzce:shatter`。** 冰冻状态复用寒冰菇那一个
（客户端画冰块的唯一判据），碎冰另立类型只是因为**护甲规则不同**：`ignores_front_armor: true`
——冻住之后举在身前的铁门挡不住这一下，这是"先冻再打"值得做的理由。数值抄在
`data/pvzce/projectiles/iceboom_bolt.json`：三发冻住、3.25 秒冻结（寒冰菇的数）、每发 20、
碎冰 ×3。

**6. 新植物在实机里的可验性：小游戏「冰库」**（`data/pvzce/levels/yard/minigame/ice_storage.json`）。
传送带只发冰爆菇与坚果、12 波（普通/路障/铁桶/橄榄球），白天草坪、僵尸速度 ×0.9，
所以"哪一只先冻住、先打谁"是这一关唯一的决策。**卡是关卡固定的**（`slots` 为空 + 传送带），
所以不需要先解锁它——新植物默认不在任何世界的背包里（`PlayerProfile` 只送豌豆射手），
要发给玩家得走关卡 `rewards` 的 unlock（这一轮没做，见 `todo.md`）。

**7. 顺带修掉一个冒烟钩子的静默 bug**：`smokeAlmanacEntry` 从来没生效过。冒烟驱动建完
`AlmanacScreen` 就调 `show(page)` + `selectEntry(n)`，而这一屏的目录是**第一帧懒建**的，
`init()` 会重开页面并把选中项重置到第 0 条——于是"翻到第 48 条"拍回来永远是第 1 条。
修法是建完屏先 `initIfNeeded()` 再导航（`SmokeDriver`）。

## 验到了什么

- `ShatterShroomTest`（5 例）：三发冻住（按**命中次数**数，不按 tick 猜）、
  冻结后那一发是 60 而前三发各 20（按**命中序列的形状**断言，不钉死整张表——弹道飞行时间
  会让某一发早/晚一 tick）、温僵尸那一发就是 20、堆积计数进僵尸自己的存档、
  注册与卡面齐全。
- `.smoke/iceboom/card/almanac.png`：图鉴第 48 条，卡面、阳光 175、冷却 5 秒、
  `.desc` 与 `.flavor` 两行都在（这一屏也顺带证明了原创卡面被正确渲染）。
- `.smoke/iceboom/shatter2/`：一次启动的帧带（`captureEvery=12`，92 张）。僵尸在第 564~600 帧
  被冻成冰块（脚下白霜 + 全身冰色），612~636 帧是**碎冰爆发**（冰晶像素量从 ~150 跳到 1939），
  右下角能看见冰爆菇本体与卡槽里的卡。
- `python3 tools/classify_assets.py --check`：365 个素材全部有归属；原创从 70 涨到 75
  （源图 4 张在 `tools/art/`，不在 `assets/` 统计范围内）。

## 用户报"只显示影子"：手写模型 JSON 的三个坑

> 用户上手第一眼就报了：**植物种下后只有影子**。这一节记根因，因为三处都在
> `tools/gen_iceboom_shroom.py` 产出的那一份手写 JSON 里，而且**每一处都不会让任何检查变红**。

### 现象与根因

- 现象：棋盘上该有植物的格子**什么都没有**，影子在；图鉴预览里也只有一个空框。
- 第一步排查（错的方向）：先怀疑贴图与动画文件。两者都是好的——
  `AnimationResourceLoader.parse` 能把那份 JSON 解析成 `ControllerFile`，两张 PNG 都有几千个不透明像素。
- 真凶在日志里：`Missing texture reference: pvzce:textures/entities/plant/attacker/iceboom_shroom`。
  这句是**扁平贴图回退**报的（内容定义里的 `texture` 指的是一个目录），而回退是被
  `AnimationManager.render(entity) == false` 触发的。给两边各加一行临时探针后立刻看到：
  `poses={body=…visible=false, head=…visible=false}`——**立绘每帧都在画，只是两根骨骼都被判定不可见**。

三处原因（第二、三处是修第一处时暴露出来的）：

1. **`"visible": {"0": 1}` 里写的是数字。** 加载器用 Gson 的 `getAsBoolean()` 读这一路，
   数字会**抛异常**，而那条关键帧在循环里被就地丢掉——于是"可见性轨"变成空轨，空轨采样回退到
   骨骼自己的 rest pose。转换出来的 83 份动画里这一路写的是 `true`/`false`。
2. **部件 `offset` 与骨骼 `translation` 是相加的。** 手写脚本把"画布中心"同时写进了两处，
   于是整块画布被抬高了**一个画布高度**——帽子和身体分成两半。
3. **头部那块画布是裁到脖子的**，所以它的 offset 不能再取"画布中心"：裁掉的 39 行让它整体上移了，
   得用「身体墨迹上沿」减去「头部墨迹下沿」这一个减法补回去。这一处我前后写错三次
   （符号、基准点、还有一次用了会把上沿挪两行的 alpha 阈值）。

### 结论

**1. 手写动画的几何要**从贴图里量**，不要从公式里推。** `gen_iceboom_shroom.py` 现在读两层 PNG 的
alpha 行号，用「身体上沿 − 头部下沿」求头部的静止位移，并把结果写进两个 clip 的每一帧。

**2. 手写动画的每一处细节都要有一条会红的用例。** 新增 `ModelPartsJoinUpTest`（`client` 包）：
它读**真文件**、用量出来的墨迹而不是部件四边形，断言四条——脚在原点、整株约一格高、
**帽子的裁线与茎的顶是同一条线**（静止时差 0，呼吸全程差 < 0.06 格）、每根骨骼在 `idle` 里可见、
`shoot` 会在结束时交回 `idle`。上面三个坑里，前两个被它直接钉死，第三个是它**逼出来的**
（我为了让它过，才不得不承认"公式"算错了）。

**3. 转换来的模型为什么没踩到 1 和 3。** 它们由 `reanim_to_pvzce_all.py` 统一产出：可见性写成布尔、
offset 由 pivot 推导、`size` 取动画文件的包围盒。**手写模型绕开了这三条约定**——这就是这一轮的教训，
也是为什么这一株的 JSON 值得一份专门的用例。

### 用户接着报"这个动画真的好敷衍"，然后是"头和身体有点分离"、"外层突然下移"

三份反馈，三个不同的病：

**（一）敷衍**：原版是两根骨骼 + 等间隔正弦，读起来是"参数在动"。对照转换来的植物
（豌豆射手 idle 是 **9 根骨骼 × 25 帧**、各不同相位幅度、还有眨眼）重做：`idle` 帽子领
0.014 格、顶端停一拍再落，茎按同一拍跟 80%，两者各自 squash/stretch，关键帧不等间隔；
`shoot` 拆成**预备 / 爆发 / 过冲 / 余韵**四拍（0.06 拉回 → 0.10 前冲，子弹在这一拍出膛 →
0.22 过冲 → 0.55 归位），另加一根 `flash` 骨骼，用冰弹自己的图放大，放在
`PlantShots.MUZZLE_OFFSET_X`（0.3 格）与植物地平线上——即子弹**真正出现的位置**。
关键帧密度现在与转换来的植物同量级（每骨骼 10~11 帧）。

**（二）头和身体分离**：根因是**帽子的墨迹裁在脖子上，而身体的冠就是同一条线**，
所以两块画布的相对位移就是玩家眼里的缝。第一版让帽子独自上下（相对位移最大 0.034 格 = 3.4px），
第二版改成"身体晚 0.06 秒跟"——**延迟本身就是缝**（顶端 0.027 格）；第三版才定成
**同一拍、80% 的距离**，缝降到 0.4px（连开火全程也是 0.4px）。中途还撞出第三个来源：
**part 是绕骨骼 pivot 缩放的**，帽子在 0.95、身体在 1.05 时，两块画布会沿它们本该共享的那条线
被拉向相反方向 —— 光对齐 translation 不够，**身体必须用帽子的 squash 曲线乘以一个小于 1 的系数**。
`theCapNeverLeavesTheStalk` 现在**对三个 clip 各采样 41 帧**，断言这条缝永远 < 0.02 格；
只看静止帧的断言在这三版里都通过过。

**（三）外层突然下移**：那是眨眼。第一版把整只眼睛层**下移 0.03 格**（这个缩放等级下就是 3px）
伪装闭眼——瞳孔是没了，但整张脸看上去是被"整块推下去"了。改成 **y 向压扁**（`scale` 是双轴，
压到 0.10 再弹回），三层骨骼没有一处再平移超过 0.004 格。闭眼本来就是"被压扁的眼睛"。

**（四）冻住的那一下闪全屏**：用户报"很晃眼"。根因是我给"冻住一只僵尸"这一下接了
`ICE_SPARKLE`（`pvzce:ice_trap`）——而它的定义是**一张白色像素放大 1600 倍、50% 不透明度**，
那是原版"整片草坪被冻住"的全屏白闪，寒冰菇用正合适，一株每次冻一只的植物用就是闪玩家的眼。
`ShatterCapability` 改成局部的 `SNOW_PEA_SPLAT`（四片雪花，0.2 格）。`ICE_SPARKLE` 的注释里写清
"这不是逐个僵尸的效果，用之前先读定义"，`PvzceParticles` 是唯一出处；寒冰菇那条路
（它自己的 `particles` 字段里点名 `ice_trap`）一点没动。`ShatterShroomTest` 加一条守门：
冻住时必须发 `snow_puff`、且**不得**出现 `ice_trap`。

**顺带**：`follow()` 必须按**位移**缩放（`rest + (y − rest) × k`）而不是按绝对值缩放——
绝对值缩放会让两条轨在各段过渡里的**斜率**不同，端点对上、中间对不上，
开火中段因此一度又是 3.7px 的洞。

# GPL 法律声明进游戏、git 历史摘掉原版素材

> 接着上一轮的素材分层做两件收尾：**合规**（GPL-3.0 §5(d) 要求的法律声明）与**仓库体积**
> （重写历史摘掉素材）。素材判决本身见上一节与 `素材对照表.md`，这里只记这两件。

## 现象与根因

- **游戏里只有版本号，没有法律声明**。`PvzceGame.main` 打 `"{} {} starting in {}"`、
  `DebugOverlay` 显示版本——版权行、无担保声明、许可去哪取，三样都没有。GPL-3.0 §5(d) 把
  "Appropriate Legal Notices" 定为有交互界面作品的义务，并且明说图形界面该用 about box。
- **历史里躺着素材，`.git` 283 MB**。上一轮只把 1719 个文件移出**工作区**，`git log` 仍能取出
  它们；另有早期删掉的 `assets/pvzce/font/ui.png`（18 MB × 两份历史版本）从没被清过。

## 定论

**1. 声明文本一处定义、两处显示。** 新增 `PvzceLicense`（`com.pvzce.common`）：`COPYRIGHT`
（`Copyright (C) 2026 crystalneko`）、`STARTUP_NOTICE`（一行）、`ABOUT_TEXT`（"关于"页的全文）。
出口是 `PvzceGame.main` 的一行日志与设置里的**"关于"页**（`AboutScreen`）。启动日志刻意只给
一行：每次启动刷十几行法律文本会被当噪声跳过，比不写更糟；展开的正文在 about box 里。

**2. 版权行没写进 `LICENSE`。** 那是 FSF 的许可原文，一个字节都不该改（末节 "How to Apply
These Terms" 是给使用者抄的模板，填进正文会让许可文件的版本不可辨认）。它落在根 `README.md`
的"许可"一节，代码侧的单一出处是 `PvzceLicense.COPYRIGHT`。

**3. 历史用 `git filter-repo` 全路径清除，不再要那些文件。** 摘掉 `assets/pvzce/animations/`、
`assets/pvzce/sounds/` 与 `font/ui.png` 三条路径的**全部**历史。之所以是全路径而不是"只摘已删的"：
HEAD 里 `assets/pvzce/` 留下的都是自产与二次创作素材（它们在更早的提交里也一直存在），
按路径整棵清除不会误删现在还要的文件。`assets/java/icon.png` **不能删**——`ModInfo` 专门认
id 为 `java` 的内置 mod，那是它的图标。

**4. 新增 `smokeScreen=about` 页键。** 这一页在游戏里要点"设置 → 关于"两次，而它的内容
（法律声明）只有截图才能核对排版：文本长度是合规性的一部分，被截断成省略号就白写了。

## 更正：角色立绘是原创，不是二次创作

**现象**：所有者指出四组角色立绘（`textures/gui/dialogue/`，70 张 / 107 MB）"只是参考了豌豆/蘑菇
的通用形象，并没有直接利用 PvZ 的资源"。我在上一轮把它们归成"二次创作"，理由是"画的是原版的
角色"——**这个理由是错的**：它把"题材像"当成了"衍生"。

**定论**：分类口径定为「**有没有照原版的具体造型**」，不是「题材像不像」。通用植物/真菌形象本身
不是版权客体，正如"画一只蘑菇"不构成对任何蘑菇题材作品的侵权。立绘归**原创**，随 GPL-3.0；
真正属于衍生的只剩复刻原版界面与美术版式的那 23 MB（卡面、图鉴、HUD、标题 logo、关卡缩略图、
场景地面、粒子）。

**落地**：`tools/classify_assets.py` 新增第五类 `ORIGINAL`（原创），`DERIV` 从 332 个 / 130 MB
缩到 262 个 / 23 MB；`docs/素材对照表.md`、`THIRD-PARTY.md` §1/§4、`docs/当前项目架构.md` §2.2
与 `docs/决策记录.md` 同步更正。**这个判断错在方法上**：我按"文件在哪个目录、题材像什么"推断
归属，而正确的做法是问作者——已记进 `踩坑清单.md`。

# 素材的版权分层：原版素材移出工作区，自产与二次创作留下

> 用户给的指令：「要把这个项目上传到 github，可能涉及到许可证问题」。结论来自一轮独立调研
> （`docs/报告/PvZ开源项目的许可证与版权素材处理调研.md`，12 个同类仓库实测 + EA 官方政策原文），
> 用户随后拍板两件事：**排除范围只取「原版素材」**，**zombotany 的动画一并排除**。

## 现象与根因

- **仓库里没有任何版权分层**。`assets/pvzce/` 一棵树下混着三种来源：从 `refer/` 转换/搬运的原版
  素材（PopCap/EA 版权）、按原版形象重画或改色的二次创作、以及完全自产的素材（程序生成的水面、
  原创角色立绘、OFL 字体）。**77 MB 原版素材被 git 跟踪着**，其中 `sounds/music/` 就是原版原声。
- **文件名判不出归属**，三个反直觉实例都验过：`giant_nut/body.png` 与 `wall_nut/body.png` 的
  sha256 完全相同（原版坚果复用）；`explosive_nut/` 是原版坚果改色（字节不同但形体一致）；
  `tools/gen_scary_pots.py` 这个名字像自产脚本，读的却是 `refer/im7/images/Scary_Pot.png`。
  所以只能按**文件谱系**判：谁生成了它。
- **"别的改版都带素材也没事"是幸存者偏差**。同类 12 个仓库实测下来，带素材的确实是多数
  （`GeeeekExplorer/PVZ` 367★、GPL-3.0、README 11KB 零声明），但同一个作者 `wszqkzqk` 从
  `pypvz`（1808 张素材、无 LICENSE）转向 `PvZ-Portable`（零素材 + LGPL-3.0 + 四段声明）。
- **EA 有明文政策，不是沉默**。官方内容政策写着 `we don't allow game revivals, fan games, or
  community-run servers for them` 与 `obtain assets through "data mining"`——对"重制 + 拆包素材"
  是逐条命中。2024-05 那次叫停用的是**私下警告**（开发者原话 "It is not a cease and desist or a
  DMCA. It was a warning"），所以 GitHub 上查不到任何 DMCA 记录，这**不等于**没人被找过。

## 定论

**1. 判决按文件谱系，不按文件名。** 三类证据：`tools/reanim_to_pvzce_all.py` 的 83 条实体配置
（原版 reanim 转换的唯一入口）、`tools/gen_*.py` / `tools/make_*.py` 的输出路径、sha256 去重
（707 个文件是同一张图被多处复用，这是原版"零件图集"的指纹）。判决表落在
`tools/classify_assets.py`，四类：`PvZ` / `DERIV` / `OWN` / `THIRD`，`--check` 在有未归类素材时
退出码 1。生成的对照表是 `docs/素材对照表.md`。

**2. 只移 `PvZ` 一类，共 1719 个文件 / 65 MB。** 其余由用户拍板**留在仓库**——这是取舍不是
法律结论，边界写在 `THIRD-PARTY.md` §4。**注：这一轮把四组角色立绘判成了"二次创作"，下一轮
经所有者纠正改为"原创"**（立绘只参考通用植物/真菌形象，未照原版具体造型），口径定为
"有没有照原版的具体造型"而非"题材像不像"。
`THIRD` 的 4 份 OFL 字体必须留（分发义务）。zombotany 的 4 个动画虽是 `make_zombotany_assets.py`
拼合、含创作成分，但零件是原版的，用户选择与 `PvZ` 同类处理。

**3. 素材留在本机，用 gitignore 而不是删除。** 归宿是仓库根的 `local-assets/`
（`tools/exclude_pvz_assets.py` 搬运，`--dry-run` 预览、`--rm` 搬回、`--copy` 保留原件），
并生成 `pack.mcmeta`。`git` 侧表现为 1719 条 `D`，工作区里文件仍在。

**4. 本地构建靠一个 classpath 根接回去，不靠"两套资源"。** `pvzce-game/build.gradle` 的
`pvzce-game/build.gradle` 里新增一个 Copy 任务，把 `local-assets/assets/` 拷进 `build/localAssets/assets/`，
再把这个目录**加到 `test` 与 `run` 的 classpath 最前面**。三个坑都踩过并修掉：
写 `build/resources/main/assets` 会被 Gradle 9 判成"两个任务写同一位置"而报错；
资源根必须让 `assets/` 在顶层（少一层 `TextureManager` 就按 `assets/<id>.png` 找不到东西）；
`destinationDir` 指向的是 `.../localAssets/assets`，classpath 要的是它的父目录。

**5. 许可证侧同时落地。** 仓库补 `LICENSE`（GPL-3.0，取自 GitHub licenses API 的官方文本）、
`THIRD-PARTY.md`（Fabric Loader fork 的 Apache-2.0 边界 + 字体 + 素材）、`pvzce-loader/README.md`
（Apache-2.0 的归属声明要跟着代码走，不能只写在根目录）、`font/OFL-zhanku.txt`（站酷快乐体原本
没有随附许可原文，而 `font/OFL.txt` 只覆盖三份 Noto）、根 `README.md`。
fork 的比对结论：**上游 139 + 20 个文件逐字节一致**，只新增了 `com/pvzce/launcher/` 与一个
`META-INF/services` 文件、两个 `Messages*.properties` 各追加 2 行——所以 Apache-2.0 §4(b) 的
"标注改动"几乎不触发，§4(d) 的 NOTICE 义务因上游无 `NOTICE` 文件而不适用。

## 验到了什么

- `./gradlew :pvzce-game:test :pvzce-api:test` **全绿**（1350 例）。中途 41 例红过，全是素材找不到
  ——即 classpath 接法错了，修好即恢复，非用例本身的问题。
- `python3 tools/classify_assets.py --check` → 2078 个文件全部有归属，0 未归类。
- git 侧核对：`git status` 报 1719 条 `D`，与分类的 `PvZ` 计数**逐条吻合**；残留 359 个文件
  = `DERIV` 332 + `OWN` 21 + `THIRD` 6。
- **没有跑冒烟**：这轮没改任何渲染/玩法代码，验证强度按 `验证约定.md` §1 取单测即可。
  素材在构建期资源里确实回来了（`build/localAssets` 下 182 个 OGG、91 个动画 JSON），
  这是"本地还能跑"的直接证据，但画面本身未截图确认。
