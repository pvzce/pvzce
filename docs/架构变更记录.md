# 架构变更记录

> 记历史：**现象 → 定论**。现状看 `当前项目架构.md`，取舍看 `决策记录.md`，教训看 `踩坑清单.md`。
> 写法：只记**最终落地的做法**；被回退的尝试最多留一行（"曾试 X，已回退，原因 Y"），
> 不给每个错误写长文。写之前先确认行为通过 —— 回退时这份记录要重写第二遍。

> **结构**：§1 是**定论索引**（一条一行，链到归档全文），§2 是**最近 3 轮全文**。
> 更早的每一轮在 `架构变更记录/` 目录里按 `YYYY-MM-<轮名>.md` 分卷（冻结不改）。
> 归档只搬家不改写：分卷前的每一节都在，找一条旧定论用 §1 的索引，或直接在该目录里搜索。
> 分卷规则：主文件留最近 3 轮，其余每轮一份；一条定论只在一个归档文件里，主文件不重复正文。
> 文件名不带空格（`/` 写成 `、`），这样链接可以直接写中文路径。

# 十三条美术/玩法缺陷：逐条定位到"哪一层说错了"

> 用户一次报上来十三条。它们的共同点是**每一条都能追到一个说错了的地方**，而不是十三处
> 画得不好——所以这一轮的做法是先把每一条定位到"数值/机制/素材里的哪一处是错的"，再改那一处。

## 现象与根因（按报告顺序）

1. **撑杆/海豚的落地位置与实际位置不符** —— `VaultCapability` 用自己发明的
   `AIRBORNE_FROM/TO` 缓动把位移摊在窗口上，而美术画的是另一条曲线（脚从帧 13 抬起到帧 36 落下）。
   两条曲线在落地时差**半格**。另外僵尸自己的 `height` 一直是 0，所以美术收起的腿被画在
   地面线以下。
2. **商店点击无效** —— `ShopScreen` 把购买写在 `onMouseClicked` 里，而
   `AbstractSelectionList.mouseClicked` 会吃掉点击并只调它自己的回调。行点击因此完全没反应。
3. **倭瓜会被啃掉 / 只压一只** —— `SquashCapability` 是单目标，且没有 `walk_over` 标签。
   用户拍板"可啃，但是激活时无敌"，于是改成 `invulnerable()` 在 `look/fuse/linger` 三态为真。
4. **三线射手头不跟着动 / 三发分开** —— 导出器把每根骨头都挂在 root 上，而动画里三个头的位置
   是"静态"的：原版靠 `anim_head1/2/3` 控制轨移动它们，转换器看不到没有图的轨。另
   `plants/threepeater.json` 三个 entry 的 `initial_delay` 是 0/30/60。
5. **坚果被啃后外观不变** —— `Wallnut_cracked1/2.png`、`Tallnut_cracked1/2.png` 不被任何轨
   引用，转换器不会发现它们；引擎那时也**没有**"按血量换植物贴图"这条路。
6. **传送带关卡没有铲子** —— 六个传送带的 `slots` 全是 `[]`，而 `BeltCardSource.rebuildBar`
   会把玩家的非植物卡留在带子右侧。校验器却禁止"传送带 + 任何 slots"。
7. **火爆辣椒用樱桃炸弹的特效** —— `ExplosiveCapability` 的默认粒子是 `EXPLOSION_POW`；
   原版那趟火是 `refer/anim/fire.reanim`，没转过。
8. **冰车该被地刺扎毁 / 要有破损 / 爆炸动画错** —— `ZamboniCapability` 无差别压碎格里所有植物；
   `Zombie_zamboni_1_damage1/2.png` 与 `ZamboniExplosion{,2}.xml` 的五个发射器都没接。
9. **高坚果体积不对** —— `tall_nut` 与 `wall_nut` 共用 `PLANT_BOX`，146px 的身体被塞进 0.76 格。
10. **雪橇没被显示** —— `Zombie_bobsled.reanim` 里只有骑手，`refer/` 全库没有那块板子。
11. **工具花瓶用了花盆贴图** —— `tools/vase.json` 写着 `gui/cards/flower_pot`，
    `make_vase_tool_anim.py` 就是照花盆控制器生成的。
12. **花瓶大小错误** —— `scene/vase.png` 是项目自画占位，比例不是原版那只。
13. **阳光铲贴图错误** —— `gui/buff/sun_shovel.png` 是一张 1254² 的写实插画，风格与游戏无关。

## 定论

1. **跳跃僵尸按美术自己的曲线走**：`VaultCapability` 的 `VAULT_TRAVEL_KEYS` / `VAULT_LIFT_KEYS`
   由新工具 `tools/vault_curve.py` 从**转换后**的 `jump` 片段里读出来（躯干管水平、最低的脚管
   抬升），`DEFAULT_JUMP_DISTANCE` 改成实测的 1.0908 格，`advanceVault` 同时写 `cellX` 与
   `height`。pogo 没有水平位移，继续用缓动。`PoleVaultTest` 新增一例把两张表钉在片段上。
2. **商店是"选中 + 购买按钮"**：行点击走 `setOnRowClick`（列表先吃点击是既定规则），右侧
   1/3 是详情栏，购买按钮钉在面板内右下角（`MenuPageCanvas.Canvas.widgetAtInterior`）。
3. **倭瓜激活即无敌，落地压整格**：`land()` 按落地格筛 `enemiesInRow` 逐个 `crush`。
4. **导出器支持真实的父子骨**（`EntityConfig.bone_parents`）：子骨的键被改写成宿主空间，
   模型里声明 `parent`。三线射手三个头分别挂 `stem_1/2/3`；`initial_delay` 全改 0。
5. **植物按血量换图**：新 `client/renderer/PlantDamageArt`（`BoneArt` 的第二种实现，与
   `EquipmentArt` 并列），认模型里 `cracked_N` 这一族，按原版的三等分选；两个坚果的
   `damage_states` 在导出器里声明。`AnimationManager` 现在按 kind 分派两种 override。
6. **传送带的工具/资源跟着带子**：五个传送带关卡的 `slots` 加 `pvzce:shovel`；
   `ConveyorMechanic.validate` 从"不许有任何 slots"改成"不许有**植物**卡"。
7. **辣椒是整行火**：新粒子 `pvzce:jalapeno_fire`（`tools/gen_jalapeno_fire.py` 从
   `fire.reanim` 的 12 帧切出），`ExplosiveCapability` 对 `Trigger.ROW` 逐格发一条。
8. **冰车被地刺扎毁 + 破损 + 原版爆炸**：`ZamboniCapability.tickMovement` 见到
   `#c:walk_over` 的植物就同归于尽；`damage_states` 接上两张破损图（经 `equipment` 的
   健康驱动族）；死亡发 `PvzceParticles.ZAMBONI_WRECK` 五件套。
9. **高坚果按自己的比例**：`target_box` 换成按绘制框换算的 (0.623743, 1.093202)。
10. **雪橇是同一模型里的新骨头**：导出器新增 `EntityConfig.extra_bones`（宿主键 + 自己的
    贴图 + 模型空间的 y 偏移），板子只在 `walk` 片段 `force_visible`；美术是新画的
    （`tools/gen_bobsled_sled.py`），因为原版那张**不在 refer 里**。
11. **花瓶贴图来自原版**：`tools/gen_vase_art.py` 从 `refer/im7/images/Scary_Pot.png` 切出
    空瓶与绿瓶，写场景贴图、卡面与**单骨头**的工具控制器；`make_vase_tool_anim.py` 删除。
12. 同上——`scene/vase*.png` 不再是占位图，比例与原版一致。
13. **阳光铲是原版铲子 + 原版太阳**：`tools/gen_sun_shovel_icon.py` 合成 128² 图标，
    `BuiltInBuffs.SUN_SHOVEL` 的图标从 `auto_collect` 换成 `sun_shovel`。

## 判据

- `./gradlew :pvzce-game:test` 全绿；新增 `PlantDamageArtTest`、`PoleVaultTest` 的曲线一例、
  `BungeeAndZamboniTest.aSpikeweedWrecksTheZamboni`，改写
  `CombatSystemsTest.theThreepeaterOpensAllThreeHeadsAtOnce`。
- 商店页冒烟（`.smoke/fix/s_190.png`）：左列表 + 右详情栏 + 右下"购买"按钮都画在面板里。
- 五处测试里"传送带关卡不列任何卡"的断言改成 `TestLevels.plantSlots`（工具/资源不算）。

# 节奏草坪二改：底部五键、飞入判定线、植物只在按键时开火、僵尸潮

> 用户一次报了五条：按键放在左边不直觉（"放到下面，按列来算"）、PERFECT 只给一个阳光
> （"应该生成一个阳光实体（25 阳光），会被自动收集"）、玩家不知道什么时候按/在哪里按
> （"模拟音游那种，把按键飞过来，误差 5% 以内算 Perfect，没按也显示 MISS"）、
> 这一关的植物不该主动攻击（"按下的那一列的植物攻击三次/两次/一次/不攻击"）、
> 僵尸数量与频率都要很高（"每一行可能都会同时出僵尸，移速 2 倍以上"）。
> 五条里四条是同一个根：**这一关从来没有过"玩家在对什么下手"的画面**——判定窗口是写死的
> tick 数、音符不飞、植物的输出与按键无关、播放起来与普通关卡没有区别。

### 现象与根因

- **按键提示在草坪左边缘**（`RHYTHM_KEY_ROW_X`），因为四档都是**行**模式（5 行 = 5 键 D F G H J）。
  行的形状读起来是"这一行从左到右整条"，而玩家的手在键盘上、眼睛在草坪上——"什么时候按、
  按哪里"没有一个共同的锚点。
- **PERFECT 只是 `team.addResource(SUN, 1)`**：一个既不在场上、也不在草坪上的数字，
  与"产阳光"的观感（`spawnProducedResource`）无关。
- **判定窗口与画面无关**：`perfect_ticks: 4` / `good_ticks: 9` 是作者手写的两个 tick 数，
  客户端既没有音符轨道也没有判定线，玩家只能靠听歌猜。
- **这一关的植物照常自动开火**：四档卡池是"阳光 / 豌豆射手 / 坚果 / 铲子"，输出其实来自
  豌豆射手自己的 90 tick 时钟，命中的音符只是额外沿整列结算一次 `damageColumn`——
  也就是说，**不按键也能打**，按键只是加了一层看不见的伤害。
- **僵尸表是 3 波 10~24 只、移速 1×**，而这一关的胜负是"活到歌尾"（185 秒），
  后 100 秒场上没有新东西。

### 定论

- **六列六键，判定线在棋盘底行**：四档全部改成 `col` 0~5（`S D F J K L`，第七~九列仍然能种、
  仍然挡僵尸，只是没有键）。`RhythmPlay` 新增 `inFlight()`（哪些音符在飞），
  `InGameScreen.renderRhythmHighway` 一条竖导线 + 判定线 + 按键胶囊 + **沿列飞下来的按键音符**
  （音符画的就是它对应的那个键的字母），命中/漏掉都从天上消失。
- **判定窗口是飞行行程的百分比，不是手写的 tick 数**：谱面新增 `approach_ticks`（默认 80），
  三档窗口 = 5% / 10% / 15% → 4 / 8 / 12 tick。一个数同时决定"音符飞多久"和"多准算 Perfect"，
  所以画面与判定不可能对不上——**`perfect_ticks` / `good_ticks` 两个字段删掉**（一个事实一个出处）。
- **三档判定 + MISS**：`RhythmChartData.Grade`（PERFECT / GOOD / FAIR / MISS）与
  `volleys(grade)`；FAIR 进 `RhythmMechanic.Score`、进存档（`RhythmFair`）、进 HUD 计数。
  没按下去的音符在窗口关闭时由**客户端自己数成 MISS 并显示在判定线上方**（服务端照旧自己数）。
- **PERFECT 掉阳光实体**：从那一列里随机一株植物 `spawnProducedResource(SUN, 25)`——
  一颗真阳光，0.25 秒后被自动拾取（关卡固定带 `pvzce:auto_collect`，玩家自己那份增益照旧）。
  那一列没有植物就不掉：阳光是从植物身上出来的。
- **植物平时不开火，按键才是武器**：`RhythmChartData.plants_hold_fire`（默认 true，生成器显式写出）
  → `LevelServer.plantsHoldFire()` → `PlantEntity.tick` 跳过 `PlantCapability.holdsFire()` 为真的能力。
  命中的音符让**那一列（或那一行）的每一株植物各打 N 次它自己的攻击**
  （`PlantEntity.queueStrikes`，每次间隔 4 tick，避免三发叠在同一格）：射手发一轮、投手抛一轮、
  近战咬一口、喷菇吐一口、地刺扎一下；坚果与向日葵没有攻击手段，就是"不攻击"。
  `attack_damage` 换成 `attack_volleys`（默认 3；GOOD = 2、FAIR = 1 由它推导），
  编辑器那一栏的语义跟着改成"PERFECT 攻击次数"（同一个输入框）。
- **僵尸潮**：规则 `zombie_speed_multiplier` 2.0/2.2/2.4/2.6 与 `zombie_spawn_speed_multiplier`
  1.4/1.6/1.8/2.0（后者同时除以波间 `delay` 与波内 `spawn_interval`），波次表按档重写成
  6/8/9/10 波、**每条 entry 都点名全部五行**（"每一行都可能同时出僵尸"就是这一条）、
  总量 39/59/79/104 只（原来的 3~5 倍），表长按 10000 tick 写（约一首歌，谱面与僵尸同时结束）。
  卡池补成六张（加寒冰豌豆、双发）——输出全在按键上，卡池就是上限。
- **谱面的起点是服务端的事实**（冒烟抓到的第二条，见下）：`RhythmMechanic.Start` 走
  `MechanicSyncS2C` 下发（与准备阶段的旗标同一条通道），`RhythmClientMechanic` 收进
  `ClientLevel.mechanicState`，`RhythmPlay` 读它当锚点。客户端不再自己猜"准备阶段什么时候结束"。

### 冒烟（与用户）抓到的三个真问题

- **判定线与按键全在屏幕外**：第一版按"棋盘的下面"放（世界 y = -0.08 / -0.42）。
  1400x600 的底图是 **cover** 缩放的，1920x1080 下草坪自己的底边只在屏幕上方 **36 px**
  （约五分之一格），提示条还压在那一段里——胶片上判定线与五个胶囊一个都看不见。
  现在的判据是"格内可画"：判定线与胶囊都放进棋盘底行（`RHYTHM_JUDGE_Y = 0.68` /
  `RHYTHM_KEY_COL_Y = 0.36`），并且画在提示条之后（`renderRhythmHighway` 现在是 `render()`
  的最后一笔）。这与行模式的胶囊早就在棋盘里面是同一个理由（`踩坑清单` 138）。
- **音符是从下往上飞的**（用户看胶片后报的，不是冒烟抓到的）：`Flight.progress` 的注释写着
  "0 在顶端、1 在判定线"，而渲染那一行写成了 `judgeY + progress * (topY - judgeY)`——插值与它自己的
  契约反了，于是音符从按键上冒出来往天上飞。棋盘上世界 y **向上增长**（行 0 画在最下面），所以
  "往下"是一次减法；现在这条算术与 `progress` 放在一起（`RhythmPlay.Flight.worldY`），
  并且用**逐点比较**的用例钉住方向（`RhythmPlayTest.aNoteComesDownToTheJudgementLine`）。
  教训进 `踩坑清单` 142：静帧里的胶囊两个方向长得一样，稀疏帧带只能证明"有东西在动"。
- **客户端自报 combo 5、服务端存档 0 命中 20 漏**：客户端在自己以为"准备阶段结束"的那一帧锚定谱面，
  而 `ClientLevel.preparing()` 在第一包状态到达之前**默认 false** → 客户端锚在关卡 tick 0，
  服务端锚在玩家按"开始"的 tick 118。差 118 tick 远大于窗口（12），于是**每一个按键包都被拒**，
  玩家看到的是"我明明按上了"。定论就是上面那条：起点走机制同步下发，
  并且顺带修掉客户端漏数把**心跳校正**当成 miss（第一版胶片上的 `MISS 127` = 九千 tick 的音符
  在一帧里被判漏；现在时钟一帧跳超过 30 tick 就只把游标推过去、不计漏也不断连击）。

### 判据

- 新 `RhythmPlayTest`（客户端逻辑，纯数据无渲染）：漏音符在窗口关闭时计一次；三档判定；
  空按什么都不发生；音符在飞行区间内才在空中、按下即消失；**时钟跳跃不计漏**；
  **服务端锚点没到之前什么都不发生**（不画、不判、不漏）；**音符从上往下飞**
  （刚出现时在棋盘上方、该按时落在判定线上，且飞行中每一 tick 都比上一 tick 更低）。
- `RhythmTest` 扩写：三档窗口与 `volleys` 的推导（3/2/1/0）；按键让**那一列/那一行**的植物出手
  （同列有豌豆、别列没有，僵尸只在自己那一行挨打）；PERFECT 掉的是**实体**（`25`、进不了银行、
  空列不掉）、GOOD 不掉；同一片草坪在 `plants_hold_fire=false` 时照常开火；
  `plantsHoldFire()` 的关卡答案；hold-fire 却零次攻击是数据错误；四档都 ≥2 倍移速与 >1 的节奏。
- `RhythmChartsTest`：四档都是前六列且 `plants_hold_fire` 为真、`approach_ticks = 80` 且不再写窗口、
  移速逐档递增且 ≥2、出怪节奏 >1、每条 entry 五行、总量与波数递增。
- `WavePacingMetricsTest` 的报表：四档在场上峰值 9~13 只、空场占比 0~8%，关卡仍按歌尾正常结束。
- `ColumnPlantingTest`（新）：一次点击种满整列且只扣一张卡的钱；点到已占用的格子照样把其余四格种上、
  被占的那格不动；整列无处可种时不扣钱且给出提示；规则关掉时仍然"一次一格"；这条规则确实进了
  关卡载荷（客户端才画得出整列预览）。`KeyBindingsTest` 增补 `S D F J K L`、以及"行键与第
  七~九列都不绑"。
- 冒烟（`.smoke/rhythm5/`，拍种植这一条）：进关卡时**可用阳光 500**；点一次豌豆卡（底部那排按键胶囊）
  后阳光掉到 **400**、**整列五株**同时出现——一次点击、一张卡的钱、一整列；再点一次

# 节奏草坪重做（能量条、连击辣椒、站酷判定）与关卡集合（tags、新分类）

> 用户一次报了五件事：判定字要站酷体 + 打击动效、按下键就要点亮判定区、连续 PERFECT 的乘数与
> 30/50/80/100 的火爆辣椒、能量条及其两档子弹倍率，以及"关卡集合"——把 1-x/2-x/3-x/4-x、
> 变异、节奏草坪各收进一个盒子，盒子在列表里长得和普通关卡一样、右下角写"内含 x 个关卡"。
> 前者是节奏草坪这一关"太简陋"的补完，后者是列表结构第一次有了第三层。

## 现象与根因

- **判定字用的是思源黑体**。`InGameScreen` 画判定字走的是 `fonts().body()`，而项目里"站酷快乐体"
  （`fonts().button()`，`assets/pvzce/font/zhanku.ttf`）一直是按钮/标题/HUD 数字的角色——模式里
  最需要"有反应"的那四个词，恰好是全项目唯一一处没用它的地方。而"打击感"当时完全不存在：
  400ms 里字的大小、位置、透明度一动不动。
- **判定区只在命中之后才亮**。`playRhythmLane` 先判定、`press()` 返回 `null` 就直接 return，
  于是"空按"在画面上与"按键没生效"完全一样——而这两件事把玩家送去两个不同的地方。
- **能量与连击没有**。节奏模式只有"命中数 + 连击数"两个计数器，没有任何会随时间变化的资源，
  也没有"打得久就有回报"的东西：30 个 PERFECT 和 30 个 FAIR 在画面上只有一行数字的差别。
- **列表只有两层**。分类由 id 路径前两段决定（`LevelGrouping`），页 = 主题 × 分类，没有第三层，
  也没有"一个关卡属于某个组"的表达方式：40 关冒险平铺在一页、变异四档和五条无尽混在生存页。
- **一个只有测试能看见的坑**：服务端把列表行收集进一个"按排序键索引的 Map"，而集合的排序键
  **就是它第一个成员的 id**——盒子那一行被成员那一行覆盖，而成员又是页面要过滤掉的，于是整个盒子
  从列表里消失，两侧单独的断言却全绿（`ServerMenuFlowTest` 那条回归测试是为此补的）。

## 定论

- **判定字走 `fonts().button()`（站酷），动效是三条纯曲线**：`RhythmPlay` 上新增
  `verdictProgress/verdictScale/verdictAlpha/verdictRise`——落点 2.1 倍、`VERDICT_POP_SHARE`(14%)
  内回落到 1 倍、全程上浮 16 单位（二次曲线，前段快）、最后 45% 淡出；`TextStyle.outline` 描边
  （草坪 + 僵尸 + 火焰上都要读得清）。曲线在 `RhythmPlay` 而不是在屏幕里，因为那里已经放着
  `VERDICT_NANOS`，而 `RhythmPlayTest` 不需要渲染器就能钉住它们。
- **按下即亮，命中与否分色**：`RhythmPlay.pressed()` 在判定**之前**记下"哪一列刚被碰过"，
  `pressFlash()` 给一个 150ms 的衰减值，`pressedGrade()` 是命中时的判定（空按为 `null`）。
  屏幕侧 `rhythmLaneColour` 三态：命中取判定色（金/蓝/灰红）、空按中性白、没人碰是原来的暗琥珀；
  判定线与按键胶囊同一颜色、同一闪，并多一条更宽的辉光。
- **能量条与连续 PERFECT 并进 `pvzce:rhythm`**（当成模式规则，不新造机制块）：数值全部进
  `PvzceConstants`（`ENERGY_PERFECT/GOOD/FAIR/MISS`、`ENERGY_DRAIN_PER_SECOND`、`ENERGY_MAX=6000`、
  `ENERGY_DOUBLE_AT=3000`、`ENERGY_TRIPLE_AT=5000`、`PERFECT_STREAK_MILESTONES={30,50,80,100}`、
  `PERFECT_STREAK_STEP=20`）。能量按 tick 小数累积（5/秒 = 1/12 点每 tick，整数会在两种取整里
  选一个错的）；建造阶段不涨不减（`PreparationMechanic.isPreparing` 之前就 return），暂停同样停。
- **乘数是"子弹数"而不是"攻击次数"**：`LevelAccess.projectileCountMultiplier(plant)` 是新的
  等级侧问法（`sporeRangeMultiplier` 的邻居），`LevelServer` 覆写为读 `RhythmMechanic`。落点是
  射手 `ShooterCapability.fire` 的三处 `shot.count()`（一个收窄点同时覆盖自己的时钟与谱面指令
  两条路）、投手 `ThrowerCapability.lob`（它没有 burst 字段，借射手的 6 tick 间隔，并补了一个
  `PendingLob` 队列让 hold-fire 关卡不吞掉余下的抛射）、玉米加农炮的 `launchAimedProjectile`。
  僵尸的豌豆走 `spawnZombieProjectile`，不乘。叠加关系按用户拍板：PERFECT 的 3 次齐射 × ≥5000 的
  3 发 = 9 发。
- **辣椒是"整行爆炸"，不是植物实体**：把 `ExplosiveCapability` 的 ROW 分支抽成
  `public static fireRow(level, row, damage, damageType, meltsIce, sound, team)`（行伤害 + 融冰 +
  每格一道 `JALAPENO_FIRE`），`detonate` 与 `RhythmMechanic.release` 共用一处几何；伤害/伤害类型/
  是否融冰/音效全部**从辣椒的植物定义读**（`PvzceIds.JALAPENO` + `PlantDef.capability`），
  于是数据包改了辣椒，奖励跟着改。`PvzceSounds.PLANT_JALAPENO` 新常量，给"没有植物可读"的调用方。
- **奖励在 `tick` 里发，不在 `judge` 里发**：`LevelServer.emitEffect` 在 `bridge == null` 时是空操作，
  而按键包是在 `level.tick` **之前**处理的——所以 `judge` 只把 `pendingJalapenos` 加一，
  `tick` 里 `release()` 才真的点火。一行胶片证实了这条：不这么做，五道火龙既没画面也没声音。
- **同步只有一条载荷**：`MechanicSyncS2C` 按机制 id 分发，所以 `RhythmMechanic.Start` 扩成
  `Status(tick, energy, perfect, good, fair, missed, combo, bestCombo, streak, multiplier, jalapenos)`，
  锚定时发一次、之后每 `STATUS_INTERVAL_TICKS`(6) 一次；两个读取点（`RhythmClientMechanic`、
  `InGameScreen.rhythmStatus`）同步改。
- **HUD 的"战况"全部来自服务端，本地镜像只留判定**：这是胶片抓到的第二个矛盾——同一帧里
  客户端把一次按键判成 GOOD、服务端按"取两边时钟里更好的那个"判成 PERFECT，于是
  `PERFECT 0 · 连续 PERFECT ×1`。定论：tally/combo/最高/连续/能量/倍率都读 `Status`，
  `RhythmPlay` 自己的计数器只负责**当帧的判定字与闪光**（帧是这一侧的）。顺带修掉了
  "续档后客户端计数从 0 重来"的老毛病。
- **关卡集合是 level 注册表上的 tag**（用户拍板"直接用 tags"）：
  `data/pvzce/tags/levels/collections/<名字>.json` → `#pvzce:collections/<名字>`，
  `PvzceTags.COLLECTION_PREFIX` 是"什么算集合"的唯一约定（别的 level tag 不会变成盒子）。
  成员顺序 = tag 文件里的顺序（`RegistryTagView.orderedIds`，`TagSet` 内部本来就是 LinkedHashSet，
  只有视图那层用 `Set.copyOf` 把顺序丢了）——变异因此可以是 easy/normal/hard/hell/tutorial 而不是
  字典序。**集合的页、图标、排序键都取自它的第一个成员**（`LevelCollections.Collection`）：
  没有第二处要同步的元数据，也自然得到白天草坪→夜晚草坪→白天泳池→夜晚泳池。
- **`LevelListS2C.LevelInfo` 多两个字段**：`collection`（这一行**是**一个盒子）与 `collectionId`
  （这一行**在**哪个盒子里）。成员行照旧下发——集合页要画它们的锁、存档与奖杯——只是
  `LevelPage.rowsFor` 把有 `collectionId` 的行滤掉，于是页面上一个关卡只出现一次。
  协议 `PROTOCOL_VERSION` 45 → 46，golden hex 重录（样本里补了一行集合，两个新字段才被钉住）。
- **客户端**：新增 `LevelRowRenderer`（两屏共用的行绘制，`showsTrophy`/`iconTexture` 从
  `LevelSelectScreen` 搬进去——判定只有一处）、新增 `LevelCollectionScreen`（`openScreen` 压栈，
  返回即回到原页与原选中）、`LevelSelectScreen` 的集合行显示"内含 x 个关卡"（右下角，与奖杯/
  id 文本共用一个 `reservedRight` 预留带）与"已通关 y/z"（状态行），动作按钮在集合上变"进入"，
  双击同一行也进入。集合名走 `level_collection.<ns>.<去掉 collections/ 的路径>` 语言键。
- **节奏草坪独立成分类**：`data/pvzce/level_categories/rhythm.json`（order 4，排在生存无尽后），
  四张谱面从 `yard/minigame/` 移到 `yard/rhythm/`，id 由 `pvzce:yard/minigame/rhythm_*` 变成
  `pvzce:yard/rhythm/rhythm_*`（**接受存档作废**，同 endless→survival 的先例，用户拍板）；
  编辑器节奏页的默认分类跟着改成 `rhythm`。
