# 架构变更记录

> 本文件只记历史（现象与定论）；现状看 `当前项目架构.md`。原载段落已从该文档移除。

# 3. 框架层

## 日志有两套设施：58 处 `System.out/err` 对 7 个 slf4j logger
> 清理轮发现（现状见 §3 总览与 `代码规范.md` §5）

- **现象**：项目早就引入了 slf4j + logback，但只有 7 个文件在用，且 logger 名有两种拼法（`"PVZCE/Network"` 与 `"pvzce-client-mechanics"`）；其余 58 处诊断直接 `System.out/err.println`。后果有三类：`printStackTrace()` 让 5 处异常只剩一行裸堆栈、没有级别也没有出口；每放一张卡打一行 `[PVZCE] Planted …`、每 10 秒一行 `tick check`、每次构造关卡把校验问题全量重打一遍（重开关卡也算），而真正重要的失败（存档损坏、通关标记读失败）反而是一行没有任何级别的 `System.err`；测日志里 246 行 `[PVZCE]` 噪声把失败信息淹掉。
- **定论**：主源码只剩 `PvzceClient` 里 6 处 `[SMOKE]` 走 stdout —— 那是冒烟钩子与脚本之间的协议输出，刻意不加时间戳、不进日志设施。其余全部走 slf4j，logger 名统一为 `"PVZCE/<模块>"`（23 个），高频行降为 `debug`，`printStackTrace` 归零。由 `-Dpvzce.trace*` 开关保护的诊断刻意停在 `info`：logback 默认级别是 INFO，降到 `debug` 会让那些开关静默失效。

## 协议里有一个既没有发送方也没有处理方的包
> 清理轮发现（现状见 §3.5 网络）

- **现象**：`MovePlantC2S(slotIndex, gridX, gridY)` 有自己的 record、占着 C2S id 16、还被 `PacketProtocolTest` 当成样包，但全仓库没有一个发送点、也没有一个处理分支 —— 手套搬植物走的是 `UseToolC2S` → `LevelServer.applyToolEffect` 那条工具路径，这个包是工具效果重构之前的遗留。
- **定论**：删除该类，id 16 **退役但不复用**（`PvzcePackets` 里留一行注释说明它曾是什么），这样旧客户端不会落到另一个包上；`PacketProtocolTest` 的样包同步移除。

## 存档里的 `DataVersion` 写了三处，没有一处读
> 清理轮发现（现状见 §3.4 NBT 与存档）

- **现象**：`PvzceConstants.SAVE_DATA_VERSION` 被写进 `profile.dat`、`level.dat` 与 `level_status/<key>.dat`，而全仓库没有一处 `getInt("DataVersion")`，也没有迁移链 —— 字段只是让存档看起来有版本管理。
- **定论**：删掉常量与三处写入。项目未发布、没有需要迁移的存档；真要发版时再连同迁移链一起设计，而不是先摆一个没人读的字段。

## 内置包根把命名空间拼了两遍，标签还有三段式路径
> 原载 §3.3 资源包 / 数据包

- **现象**：内置包曾写成 `data/pvzce/pvzce/plants/` —— 加载器要求命名空间后必须有一个字面量 `pvzce` 段，于是把自己的命名空间拼了两遍；标签另有一套 `data/<ns>/tags/pvzce/<注册表>/<名>.json` 的三段式兼容路径。
- **定论**：包根就是命名空间（与 MC 一致），数据包目录是 `data/<ns>/<注册表目录>/<相对路径>.json`；三段式标签路径已随包根扁平化一并删除。

## 存档目录键 `ns + "__" + path` 撞车
> 原载 §3.4 NBT 与存档

- **现象**：旧的 `key = ns + "__" + path.replace('/','_')` 让 `pvzce:a/b` 与 `pvzce:a_b` 共用同一个存档目录与通关标记 —— 后保存的关卡静默覆盖前一个。启动时还为此保留过一次「旧键 → 新键」扫描（`LevelKey.legacyMigration` / `PvzceServer.migrateLegacySaveKeys`）。
- **定论**：`LevelKey` = `十六进制(命名空间) + "__" + 转义(path)`（`%`→`%25`、`/`→`%2F`），两半各自单射，不同关卡 id 永远不共目录（`LevelKeyTest.distinctIdsNeverShareAKey`）；项目未发布、不存在用旧键写出的存档，那次扫描已删除。

## 金币钱包卡在 `COIN_CAP` = 9990
> 原载 §3.4 NBT 与存档

- **现象**：`PlayerProfile.Coins` 曾经卡在 9990（`COIN_CAP`），一局一局攒下去的金币会被静默吃掉。
- **定论**：只保留"32 位字段不溢出"这一条边界（`COIN_LIMIT`），四个币种资源的 `max_stack` 与它同值。

# 4. 服务端

## `/summon resource` 与关卡初始实体一律生成 25 个，不管是什么资源
> 清理轮发现（现状见 §4.5 背包、金币与关卡奖励）

- **现象**：天降阳光读规则 `pvzce:sun_value`（默认 25），而另外两条生成资源的路径把 `25` 写死在代码里：`/summon resource <id>` 与关卡的 `initial_entities`。于是 `sun_value` 改成 100 之后，天上掉的是 100、召唤出来的是 25；更要紧的是**资源种类被完全忽略** —— `/summon resource pvzce:diamond` 生成的是价值 25 的钻石堆、`pvzce:coin_silver` 也是 25，而这两种资源的 `default_value` 分别是 1000 与 10。
- **定论**：一条资源的一单位值多少，由**资源自己的 `default_value`** 回答（`spawnEntity` 与 `/summon` 都改成读它），`ResourceDef` 的 codec 默认值也改成引用 `PvzceConstants.SUN_VALUE` 而不是字面量 25。规则 `sun_value` 从此只管"天上掉的阳光值多少"这一件事。

## 关卡的 `slots` 曾经也接受植物 id 当槽位 id
> 清理轮发现（现状见 §4.4 玩家、卡槽与资源）

- **现象**：`SlotResolver.resolve` 在槽位定义查不到时，会退一步把同一个 id 当成植物 id 再查一次，并凭空造出一张卡。内置的 29 种植物每一种都有自己的 `slots/*.json`，所以这条回退在出厂数据上从来没有被走到过；它唯一的作用是让"忘了给内容写槽位定义"表现成"这张卡能用"，而不是一个能被 `LevelValidator` 报出来的问题。
- **定论**：删除回退 —— 关卡 `slots` 里写的就是**槽位 id**，查不到即记录一次并跳过（`SlotResolver.resolve` 仍是"这张卡是什么"的唯一答案）。模组加植物时要在 `slots/` 里放一条定义。

## 「下一步」与进入判定：选完卡才弹存档框
> 原载 §4.3 进入/重开关卡的协议语义

- **现象**：曾经的实现把关卡列表的「下一步」一律送进关卡准备 → 选卡，进行中的关卡也会先出现选卡界面，而玩家提交卡组后服务端走的却是"加载存档 + 提示框"（`StartLevelC2S(restart=false)` 命中存档），表现为**选卡结束后才弹出重开/继续提示框**；把"有没有存档"折进 `status` 之后，"已通关 + 有一局放弃的重玩"（两者同时成立）被压成一个值，进入判定看不到存档，同一个症状又复发过一次。
- **定论**：`hasRunningSave()` 为真时根本不进这两屏；`LevelInfo.runningSave` 是**独立字段**，`status` 只负责列表行上显示什么；列表右侧按钮改名为「继续游戏」。

## 重开路径：`StartLevelC2S(restart=false)` 被当成 resync、选卡界面 push 在旧关卡上
> 原载 §4.3 进入/重开关卡的协议语义

- **现象**：曾经的实现把 `StartLevelC2S(restart=false)` 也当成"resync 当前实例"处理：服务端已经换成新关卡，客户端却收到一个描述**仍在运行的旧实例**的 `LevelInitS2C`，玩家选的卡组被静默丢弃，表现为"没有真正重新开始、旧关卡也没关掉"。另一处旧实现把选卡界面 `push` 在仍在运行的关卡之上，按 ESC 会退回旧关卡的暂停菜单。
- **定论**：选卡只发生在一局开始之前，`restart=false` 命中在跑的关卡时必定重开并应用这套卡组；「重新开始」改为先 `LeaveLevelC2S` 真正关闭当前关卡（服务端先存档再 shutdown）再用 `setScreenReplacing` 换屏，`openCurrentLevelSeedSelection` 已删除。

## 背包、卡池与奖励三件事以前都不存在
> 原载 §4.5 背包、金币与关卡奖励

- **现象**：**玩家没有身份**（`Team` 的资源与 `Slot` 的卡组都随关卡生灭），**卡池不看玩家**（关卡列什么就能用什么），**通关没有奖励**。
- **定论**：现在分别由 `PlayerProfile`（`saves/<world>/profile.dat`）、`SeedOptions.cardPool(def, owns)`、关卡 `rewards` 块 + `PvzceServer.awardProfile` 承担。

## `max_seed_slots` 未声明被当成字面量 6，旧关卡又全变成固定卡组
> 原载 §4.5 背包、金币与关卡奖励 / §6.2.3 关卡编辑器（`EditorScreen`）

- **现象**：`max_seed_slots` 没写时以前被当成字面量 6，升级过的背包（`PlayerProfile.seedSlots`，上限 12）会被这个"默认值"悄悄压回去；而所有旧关卡都是"整份卡池 + 默认 6"，在"关卡列出的卡就是固定"这条规则下全部变成固定卡组。
- **定论**：未声明是 `LevelDef.UNSET_MAX_SEED_SLOTS`（-1），`LevelDef.effectiveMaxSeedSlots(profileSlots)` 是唯一来源（写了用关卡的，没写用背包的）；`max_seed_slots` 在规范构造器里自动抬到不小于关卡卡数，新关卡靠"关卡卡数 < 总卡槽数"留出自选空间。

## `hasNothingToChoose` 用"已选卡数"当判据
> 原载 §4.5 背包、金币与关卡奖励

- **现象**：早先的写法用 `maxSeedSlots - selectedOrder.size()`，于是"记住的卡组正好填满卡槽"（1-2 第二次进入）被读成"没得选"而自动开局，玩家再也不能换卡，页面上表现为"开了又自动关"。
- **定论**：判据是**总卡槽数 − 关卡固定卡数**，抽在纯函数 `SeedOptions.hasNothingToChoose(pool, maxSlots, lockedIds)`，选卡屏与存档提示框共用。

## 动画掉落物的 `render_scale` 此前只作用在宽度上
> 原载 §4.5 背包、金币与关卡奖励 / §4.7.1 资源掉落：三种落地方式

- **现象**：倍率只作用在**宽度**上——阳光按 0.95 格宽缩放、高度却按动画自带的 0.37 格，屏幕上是 1.7:1 的椭圆；`AnimationManager.xScaleFor` 里那段"再乘一次 `spriteXScale`"是同一件事的第二份补偿。症状是「金币只被压扁、大小没变」。
- **定论（第一次）**：声称改成"两个轴同倍率，三枚硬币的动画模型按 `0.8 × render_scale` 写成 0.4×0.4 格的正方形"，`CoinVisualLayoutTest.aCoinsArtIsAuthoredAtTheSizeRenderScaleDrawsIt` 钉住。
- **后来的更正**：那次**没有真正落地**——代码里仍然是"宽度拟合到 0.8、高度取自动画文件"，所以模型尺寸只能手改成拟合结果的那个数（硬币被手工从 0.42 覆写成 0.2），而**重跑一次转换器就会静默回退**，这正是后来那个坑的来源。那一版测试也只断言 `model.size` 等于 `0.8 × render_scale`，从未验证真正画出来的尺寸，于是"通过测试"与"画得对"是两件事。彻底的修法见下面的 §动画系统的八个缺陷。

## 资源音效两处错配：产阳光用了拾取音、捡币用了阳光音
> 原载 §4.5 背包、金币与关卡奖励

- **现象**：`ProducerCapability` 曾回落到 `sfx/ui/points`——那是**捡**阳光的声音，一朵花每 18 秒自己响一次"有人把它捡走了"；捡币放的也是阳光那声，保龄球连击一次掉一串币时听起来像在下阳光。
- **定论**：产阳光无声，拾取声由 `ResourceDef.pickup_sound` 在玩家真去点时放（缺省 `sfx/ui/collect`，硬币 `sfx/ui/coin`、钻石 `sfx/ui/diamond`），金盏花保留自己的出币声。

## 奖励等待期写的是"点击领取奖励"
> 原载 §4.5 背包、金币与关卡奖励

- **现象**：奖励落在草坪上等待领取时，此前靠草坪上那句文字说明。
- **定论**：改成头顶一枚上下滑动的金色箭头——原版 `refer/im7/particles/DownArrow.png` → `textures/gui/hud/down_arrow.png`（32px ÷ 原版 80px/格 = 0.4 格宽），照抄 `AwardPickupArrow.xml` 第二个 emitter 的 `IMAGE_DOWNARROW` + `Position` 曲线，不写字也不用翻译。

## 收集动画被 `hasSunBank()` 整体挡住
> 原载 §4.5 背包、金币与关卡奖励

- **现象**：飞向银行的动画被一句 `if (animations.isEmpty() || !hasSunBank()) return;` 整体挡住——传送带关卡（1-5）没有阳光卡、也就没有阳光银行，于是**金币被收集后直接消失**，根本看不到飞进钱袋。
- **定论**：按每条动画自己的 `bankTarget` 判断：金币只要求左下钱袋（它本来就是「有变化才显示 2.6s」的回执），阳光才要求左上阳光银行。

## 奖励页曾是"第二个领钱的地方"
> 原载 §4.5 背包、金币与关卡奖励

- **现象**：奖励页原先在没有解锁卡时画一个钱袋、要玩家点它才撒币——而那笔钱服务端在发这个包之前就已经记进钱包了。同一笔钱被发两次（一次在草坪、一次在这一页），而草坪上那次反而看不见。
- **定论**：钱袋留在草坪上炸开、金币飞进玩家一路看着的那个 bank，这一页只报账，并按 `FADE_IN_NANOS` 淡入。

## 奖励的钱袋把小推车的钱又发了一遍
> 见 §4.5 背包、金币与关卡奖励

- **现象**：`LevelRewardS2C.bonusCoins` 是一笔**已经含小推车折价**的总额，而客户端一边让每辆幸存的小推车在自己位置上变成一枚金币，一边又把整笔 `bonusCoins` 从钱袋里炸出来；HUD 的金币收款条还把两个数**相加**。一局结束时同一笔钱在动画里出现两次，收款条比钱包实际到账的多出小推车那一份。
- **定论**：`InGameScreen.rewardOnlyCoins()`（`bonusCoins - mowerCoins`）是钱袋/奖励物负责的那一份，两个 `claimed*Coins` 相加正好等于 `bonusCoins`；发 `resource` 奖励（一颗钻石）时同一份钱由那**一个资源**飞进钱袋，而不是拆成十枚银币。

## `first_clear` 的解锁与首通标记混在一起判
> 原载 §4.5 背包、金币与关卡奖励

- **现象**：首通标记只说明"这一关以前打通过"，不说明"这份奖励发出去过"：1-4 的手套就是反例——关卡在玩家通关之后才加上这条奖励，此后每次通关都走 repeat 分支，奖励页永远显示钱袋。
- **定论**：`first_clear` 里的 unlock 条目**幂等**：已拥有即空操作、缺失就补发，与 `level_status` 的首通判定分开。

## 阳光、金币、能量豆原先都从空中 2.2 格落下
> 原载 §4.7.1 资源掉落：三种落地方式

- **现象**：三种掉落原先**都**从空中 2.2 格处落下（同一个 `ResourceDropEntity`，同一个 `START_HEIGHT`），于是僵尸掉的金币从天上飘下来，向日葵产的阳光出现在花上方两格；下落时长 150 tick 时太阳还没被看到就已经落地了。
- **定论**：由 `ResourceDef.drop_motion` 决定（`fall` / `rise` / `landed`）：天上掉的阳光 `fall`，向日葵产的那一朵经 `LevelAccess.spawnProducedResource` 要求 `rise`（上浮 0.5 格再落回原点），金币一律 `landed`；下落时长 300 tick。

## 出怪间隔曾是全局常量
> 原载 §4.7.2 波次节奏：每波自己的出怪间隔

- **现象**：`spawn_interval` 之前是 `WaveDef.SPAWN_INTERVAL_TICKS` 一个全局常量（15 tick → 改 60 tick → 仍然太快），所以「把前期的节奏放慢」会连带把最终波也放慢。
- **定论**：`spawn_interval` 写在**每一波**上、缺省 300 tick（简单关第一波 8 秒一只、最后一波 6 秒一只；困难关最后一波 2.5 秒一只），两件事因此能分开调。

## 大波预警：提示不灭、音效在"到达"时才响
> 原载 §4.7.3 大波提示的生命周期

- **现象**：`nextWaveDelayTicks` 在最后一波释放后是 `-1`（"没有下一波"的哨兵值），判据 `remaining > 0` 没写，负数让区间检查恒真，提示从最后一波起一直亮着；关卡在提示亮着时结束（获胜或落败）时 `markEnd` 停止 tick，提示永远留在屏幕上。另一处：`hugewave` 在**波次到达**时才响，那时红字已经淡出，玩家先读到"一大波正在接近"，六秒后才听见同一句话。
- **定论**：`markEnd` 一并清掉提示与进度、判据写明 `remaining > 0`（两条都有回归用例）；`hugewave` 由 `updateWaveWarning` 在预警窗口**开启的那一 tick**发出（`announceWaveWarning` 按波次索引去重），与红字同一拍淡入。

## 续档后 siren / hugewave 重播（听起来像"无限循环"）
> 原载 §4.7.3 大波提示的生命周期

- **现象**：`announcedWaves` 不是存档字段，续一局停在最后一波的存档时 `restore()` 还没填满它，`triggerWave` 看到空的已宣告集合，会把 siren 与 hugewave 再放一遍；6.5 秒的 `sfx/ambient/hugewave` 正好压在最后一波进场的窗口上，听起来就是"最后一波的音效在循环"。当时的排查记录：`awooga`/`hugewave` 在服务端整局只各发一次（有整局计数的用例），`SoundEngine.play` 也确认 `AL_LOOPING=false`、音源状态正常。
- **定论**：`restore()` 按 `NextWaveIndex` 把 `announcedWaves` 重新填满（索引之前的波次都已经进场过、也就都已经宣告过），客户端另有 90 秒内同实例只播一次的保险。

## 关卡此前没有任何门槛
> 原载 §4.8 关卡解锁条件

- **现象**：服务端把关卡注册表整个发给客户端，每一行都可点，所谓"进度"就是玩家自己挑的顺序。
- **定论**：关卡可以声明 `unlock`（`level` / `card` / `coins` 条件，可选 `cost` 买断与 `hidden`），规则实现是纯函数 `LevelUnlocks.evaluate`，服务端求值、客户端接收 `UnlockInfo` 结论，入口门槛在 `createLevel` 重新求值一次。

## 传送带 / 放置区 / 小推车原先都不是关卡数据
> 原载 §4.9 小游戏关卡（传送带 / 放置区 / 保龄球）

- **现象**：1-5「坚果保龄球」是第一种结构与普通关不同的关卡，在此之前"带子出卡、只能种在某几列、哪些行有推车"三件事都不存在。
- **定论**：三件事都由关卡 `mechanics` 列表描述（`conveyor` / `placement_zone` / `mower`），两个默认（没有 card source 得 `deck`、没有 `mower` 得每行一辆）只在 `LevelMechanics.effective` 里加。

## 保龄球曾经"撞到就反向"
> 原载 §4.9 小游戏关卡（传送带 / 放置区 / 保龄球）

- **现象**：曾经的实现是"撞到就反向"，于是坚果命中第一只僵尸后就一路朝房子滚回去，一颗只能打一只——而保龄球的核心恰恰是**斜向弹开继续前进**、在密集的僵尸群里连撞。
- **定论**：撞到僵尸改为被撞进相邻车道（`ricochet`）、**永远向前**；左右边界是出口、上下边界是墙，方向反转与"上下反弹"是两件事。

## 1-5 的波次从 228 只减到 116 只
> 原载 §4.9 小游戏关卡（传送带 / 放置区 / 保龄球）

- **现象**：原版 n-5 的僵尸密度配上传送带是 5 秒一张卡，228 只对本项目的刷怪节奏太挤（`(数量-1) × 出怪间隔` 已经顶到波间隔）。
- **定论**：改成"1.5 倍频率、一半数量、1.5 倍移速"：11 波 116 只、出怪间隔 30~60 tick、波间隔 600 tick、移速 ×1.5、传送带 150 tick 一张。

## 小推车 `idle` clip 的轮子一直在转
> 原载 §4.9 小游戏关卡（传送带 / 放置区 / 保龄球）

- **现象**：原 reanim 的轮子轨道在 `anim_normal` 的**每一帧**都在转，把整段导成一个循环 clip，得到的是"停在路边轮子却一直在转"的车。
- **定论**：转换器的 `range: [0, 0]` 把 `idle` 冻在第 0 帧（停放姿势），`drive` 才是滚动的那个；`MowerClientMechanic` 按 `STATE_READY`/`STATE_ROLLING` 选 clip，没有为它加新语法。

## 土豆地雷炸了但僵尸无伤
> 原载 §4.9 小游戏关卡（传送带 / 放置区 / 保龄球）

- **现象**：触发用 `trigger_range`（0.6）、伤害用 `radius`（0.55），僵尸每 tick 走 0.003 格，所以**进入触发圈的那一 tick 距离约 0.599，正好在爆炸范围之外**——每一次引爆都必然落空。
- **定论**：`ExplosiveCapability.detonate` 加了不变量"爆炸半径至少覆盖触发范围"（`max(radius, trigger_range)`，近战雷再与 `MIN_RADIUS` 取大），`potato_mine` 的 `trigger_range` 改成 0.5（僵尸真正踩进格子才炸），数据与代码都改。

## 樱桃炸弹的爆炸动画一个包都没发出去
> 原载 §5.2.1 / §8 约定 31b

- **现象**：`ExplosiveCapability.detonate()` 在同一 tick 里既 `setAnimation(explode)` 又 `plant.remove()`，而实体状态每 3 tick 才发一次 —— 于是 `explode` 这个状态**通常根本没有进过包**，客户端收到的唯一消息是 despawn，樱桃炸弹看起来是凭空消失的（0.47 秒的 clip 白做了）。同一段代码在引信期间按 `trigger == PROXIMITY` 才发 `grow`，**timed** 也走 `GROW`，而樱桃炸弹的动画文件里只有 `idle` 与 `explode`（原版 `CherryBomb.reanim` 就这两条 track），客户端每次收到 `grow` 都在静默回退到 `idle`。
- **定论**：爆炸后植物留在场上 `LINGER_TICKS`（30 tick）自己 `remove()`，并在引爆那一 tick 调 `LevelServer.requestEntitySync()` 让状态当拍发出；引信期间 timed 请求 `idle`、proximity 才请求 `grow`/`armed`。`CombatSystemsTest.anExplosionPublishesItsClipBeforeThePlantLeaves` 与 `AnimationResourceLoaderTest.everyAshPlantDefinesTheClipsItsCapabilityAsksFor` 各钉一半。

## 灰烬类被僵尸一口啃掉
> 原载 §5.2.1 / §8 约定 32c

- **现象**：樱桃炸弹 100 血、僵尸一口 100，所以它在引信烧完之前就被咬没了；土豆雷 300 血也只是三口。原版灰烬类在整个存活期间都啃不动，僵尸咬它只是白咬。
- **定论**："咬不动"与"铲不掉"拆成两个判据：新增 `PlantCapability.invulnerable`（`PlantEntity.damageFrom` 遇真即丢弃这次伤害，僵尸的啃咬、巨人的锤子都走这条路），`occupiesCell` 继续只管"还算不算这一格的植物"（铲子、手套）。引爆之后 `invulnerable` 变假、`occupiesCell` 也变假 —— 那时它已经不存在了。

## 爆炸闪光只有一个很小的贴图（不会膨胀）
> 原载 §4.7.1 资源掉落 / §5.2.1

- **现象**：原版 `Pow.xml` 的 `ParticleScale` 是 `.2 .5,7` —— 一个范围加一个曲线类型，而转换器把三个数字按 (value, time) 关键帧配对，读成"全程 0.2"：`scale_curve` 根本没有生成，引擎把爆炸画在**起始尺寸**上，所以看起来只有一个小贴图。引擎一直有 `scale_curve` 这条路。
- **定论**：`tools/particles_to_pvzce.py` 新增 `growth_curve()`：无歧义的 `[a b]` 与开头的 `a b` 读成一条从 a 到 b 的直线，带时间或曲线类型的（`,7`、`,60 0`、`EaseIn`）保持常数（猜错会得到"长到 60%"这种明显错的表）。`pvzce:pow` 因为原版写着 `,7`，由**手写**的 `scale_curve` 定案；`ParticleDefinitionTest.theExplosionFlashGrowsOverItsLife` 钉住它。

## 两波僵尸"一起出"：`delay` 从触发时刻起算
> 原载 §4.7.2 波次节奏

- **现象**：`triggerWave` 立刻把下一波的倒计时设为它的 `delay`，而这一波的出怪队列才刚开始放人 —— 于是 `spawn_interval` 600（10 秒）的前三波，玩家看到的是两波队列交替放怪、间隔 4~6 秒。1-2 与 1-3 因此比数据写出来的难。
- **定论**：`tickWaves` 在 `pendingWaveSpawns` 还有货时冻结 `waveIntervalTicks`，`delay` 从"上一波放完"那一 tick 起算（第一波例外）。1-2 / 1-3 的前三波 `spawn_interval` 改成 600，`delay` 不动；`WaveSystemTest` 的 `theNextWaveWaitsForThePreviousOneToFinishReleasing` 与 `theOpeningWavesOfTheFirstLevelsAreTenSecondsApart` 各钉一半。顺带发现那三个计时用例把出怪间隔写进了 `WaveDef` 的 `warning_ticks` 参数（4 参构造器），一直跑在 300 的缺省值上 —— 已改成按行为断言。

## 开局两波「不到 10 秒就冒第二只」：间隔是关卡说了算，不是玩家说了算
> 原载 §4.7.2 波次节奏 / §8 约定 46

- **现象**：出怪节奏只有一个旋钮（每波的 `spawn_interval`），于是 1-6~1-10 的第一波把三只僵尸写在 420 tick（7 秒）一只上：玩家第一株豌豆还没打完第一只，第二只已经在路上了。把间隔调大是"替玩家猜速度"，换个玩家（或换个关卡）就又不对：间隔惩罚的是**打得快**的人，放过的是打得慢的人。
- **定论**：开局两波（`WaveDef.EARLY_WAVE_COUNT`，且必须是 `small` 波）改由**玩家的击杀**推进 —— 上一只一死就出下一只，`WaveDef.DEFAULT_EARLY_HOLD_TICKS`（1200 tick / 20 秒）还没死就照出；**波间**也门控：上一波没清完时扣住下一波的**到达**（延迟照常跑），同样 20 秒封顶。三态字段 `hold_until_dead`（缺省 = 上面的规则 / 0 = 关掉 / 正数 = 换封顶值）与两个门的存档一起落地。数据侧的 `spawn_interval` 一个字没改：它仍然是"这一波打算多快"，只是开局两波不再由它决定。

## 波间门控第一版把倒计时冻住了：清完场还要空等一整个 delay
> 原载 §4.7.2 波次节奏 / §8 约定 46

- **现象**：波间门控的第一版选择"冻结倒计时"（怕大波横幅在等清场时熄灭、大波随后静悄悄地来），代价是玩家把场上清干净之后，下一波的 `delay` 才从零开始跑——`到大波的时候，即使僵尸已经杀完了，也不会继续前往大波，而是要在没有僵尸的情况下等待一会`。
- **定论**：改成**延迟照常跑、只扣住到达**：`tickWaves` 的倒计时不再被门控冻结，`waveIntervalTicks >= nextWaveDelayTicks` 之后才问门（`openingWaveStillOnTheField`），门关着就最多扣 20 秒。横幅的问题用另一种方法解决：被扣住时 `waveArrivalHeld` 让 `updateWaveWarning` 继续认为这一波在预警中，所以大波不会在横幅熄灭之后才来。`WaveSystemTest` 的三条用例分别钉住"清得早按原节奏"（`clearingTheOpeningEarlyDoesNotDelayTheNextWave`）、"清得晚就等清完"（`theSecondWaveWaitsForTheOpeningToBeCleared`）与"清不完 20 秒后放行"（`theSecondWaveIsReleasedWhenTheOpeningNeverEnds`）。

## 夜间关卡的选卡页与开场对话是白天
> 原载 §6.2.1 关卡选择页

- **现象**：2-1（固定夜晚）在**正式开始之前**——选卡页、以及选卡页里播的开场对话——草坪与背景都是大白天，按下「开始游戏」进关卡才突然变黑。同一关的两个画面，两个时间。
- **根因**：昼夜明暗只有一条数据来源：`LevelInitS2C` 里的 `day_length`/`night_length`，而选卡页发生在关卡存在之前，拿不到这个包，于是只能按"没有时钟 = 白天"画。
- **定论**：把关卡内那套光照算式抽成纯函数 `TimeOfDayLighting.compute(dayTicks, dayLength, nightLength, w, h)`（关卡内与选卡页共用，避免两份数值各自漂移），选卡页改从**本地关卡定义**读那两条规则、以 tick 0 计算（客户端本来就解析同一份数据包，与 `usesConveyorBelt`/`lockedSeedsFor` 同一层，不需要新协议字段）。顺带把定向光从世界格换算进选卡页自己的像素坐标，月亮才会落在它画的那块草坪上；UI（木牌、卡槽、对话）在中性着色器下画，不跟着变暗。

## 墓碑一直是一张「GRV」占位图
> 原载 §6.2.1 关卡选择页 / §4.9 小游戏关卡

- **现象**：`textures/scene/grave.png` 是灰底写着「GRV」的 64×64 占位图，`grave_2.png` 也一样。它从没被任何**通过**的关卡用到（只有 `combat_test` 摆了墓碑），所以直到 2-1 需要四座墓碑时，草坪上才会出现四个灰方块。
- **定论**：用原版素材补上：`refer/im7/images/Tombstones.jpg`（十字墓园图集）配同名 alpha 掩膜 `Tombstones_.png` 切出四款墓碑，各自按一格草地的比例贴到草地贴图上，成为四个共享 `GRAVE` 表面的场景元素（`grave`/`grave_cross`/`grave_slab`/`grave_wide`，全在 `#c:unplantable` 里）。美术是一次性整理的，没有进 `tools/`。

## 伤害类型：三条并列的入口合成一条
> 原载 §5.2.1

- **现象**：`damageBody`（爆炸/推车，无视护甲）、`damageImpact`（保龄球/巨人拳，先护甲）、`damage(ProjectileDef,…)`（子弹，按层路由）是三条并列的入口，"吃不吃护甲"由**调用点调了哪个方法**决定；内容作者看不到也改不了，`RULE_PLANT_DAMAGE_MULTIPLIER` 还在三处各乘了一遍。
- **定论**：注册的 `pvzce:damage_type`（`data/<ns>/damage_types/*.json`，字段只有 `ignores_armor`），`ZombieEntity.damage(amount, type, level)` 是唯一入口，倍率在那里乘一次；`explosive`/`splash` 各自声明 `damage_type`，小推车与锤子工具落在 `pvzce:mower` 上。子弹直击保留 `onProjectileHit` 的层路由（那是"这一发从哪来"，不是"这是什么伤害"）。

# 5. 实体与能力系统

## 装备只有一个贴图、挨打掉的是橄榄球头盔
> 原载 §5.2 能力（Capability）

- **现象**：路障、铁桶、铁门、报纸与旗帜僵尸的"装备"以前只有**一个贴图**（`anim_normal` 里那份完好的帽子）；`ArmorCapability` 每次吸收伤害都发 `zombie_helmet`，于是路障僵尸每挨一发豌豆就掉一顶橄榄球头盔，自己的路障永远不掉。
- **定论**：装备数据写在僵尸定义上（`equipment`：`art` 骨骼族 + 可选 `piece` 护甲 + `drop_particle`），破损档位由 `damage_states` 烘进模型，画哪一张由 `EquipmentArt`（`BoneArt` 钩子）决定，掉落粒子只在真的打碎那一发发。

## 平射绕过帽子，路障一辈子不掉耐久
> 原载 §5.2 能力（Capability）

- **现象**：`ArmorCapability.onProjectileHit` 只把**平射**弹路由到 `front` 槽位，而路障/铁桶在本项目里是 `top`（帽子）——于是豌豆从帽子旁边穿过去直接打身体，路障**一辈子不掉耐久**，僵尸死的那一刻帽子才"凭空消失"。
- **定论**：平射先找 `front`（盾牌/铁门），**没有盾牌就落到 `top` 上**（帽子挡平射，正如它挡抛射），抛射仍然只碰 `top`；路障僵尸的有效血量因此是 570、铁桶是 1300，与原版一致。

## 抛掷物粒子被按错误的单位与符号读入
> 原载 §5.2 能力（Capability）

- **现象**：`tools/particles_to_pvzce.py` 把原版的 `LaunchSpeed` 当"像素/帧"读，路障僵尸的帽子和僵尸手臂得到 0.04 格/秒的速度与 **50 转/秒**的自旋——看起来就是"啪"地消失；`ParticleMotion.gravity` 是"**向下**的加速度大小"（引擎里 `vy -= gravity * dt`），转换器却把它写成负数，等上一步把数值变成真实值之后**每一件抛掷物都往天上飞**（"僵尸头颅直接飞上天"）。
- **定论**：原版用 `GroundConstraint` 标出的那一族（头、手臂、路障、铁桶、旗帜）改用像素/秒、度/秒（`PROP_SPEED_DIVISOR`）：帽子 2.5 格/秒、手臂 0.5 格/秒、自旋约 1 圈/秒，落回**它自己那一行**（手臂 0.19 格、路障 0.64 格、旗帜 0.97 格、被碾的头 11.2 格）；其余 122 条仍按每帧读数，见 §9 已知缺口。

## 粒子的落地行为：地面写死、头颅滑出屏幕
> 原载 §5.2 能力（Capability）

- **现象**：`ParticleEngine` 原先把 `bounce` 的地面写成世界坐标 `-0.42`——只有第 0 行是对的，第 1 行以上扔出去的东西会一路掉出草坪下沿；引擎落地时只把 `vy` 归零、`vx` 一个字节不动，于是 `pvzce:zombie_head`（速度 4.125 格/秒、角度 167.5°）落地后继续向左滑到自己 3 秒的寿命结束，一路滑出屏幕左边。
- **定论**：地面改成**出生点下方 0.42 格**；新增 `ParticleMotion.ground_friction`（落地时 `vx *= friction`，缺省 **1** = 保留"一直滑"的行为），头颅那一条调成速度 2.3、角度 125°、摩擦 0.25，原地掉落、原地淡出。

## 死亡动画从来没有播过
> 原载 §5.2 能力（Capability）

- **现象**：死亡 clip 是 3.25 秒（巨人 4.9 秒）且 `on_end: hold`，原来的实现在同一 tick 就 `remove()` 并发 despawn，**整段死亡动画从来没有播过**，僵尸是凭空消失的。
- **定论**：僵尸死亡时 `setAnimation(DEATH)` 并在世界上留 6 秒（`ZombieEntity.CORPSE_TICKS`）；尸体期间不走路、不啃、不被打、不计入 `aliveZombieCount`，`corpseTicks` 进 `saveState`。

## 最后一杀的状态包发不出去
> 原载 §5.2 能力（Capability）

- **现象**：实体状态本来每 3 tick 发一次，而死亡之后同一 tick 里 `checkEnd` 就可能结束关卡、此后再不 tick，包就永远发不出去——玩家会看到一个活生生的僵尸站在已经结束的棋盘上。
- **定论**：`LevelServer.entitySyncPending` 让最后一杀的那次同步是强制的。

## `on_end: hold` 的一次性 clip 被"重播"
> 原载 §5.2 能力（Capability）

- **现象**：`AnimationManager.isAlreadyPlaying` 原先把"已结束"当成"可以重开"，而服务端每隔几 tick 就重发实体状态——死亡动画在尸体存在的 6 秒里被从头播了 2~3 遍（尸体刚倒下又站起来）。
- **定论**：只要请求的状态还是**当前活动 clip**、且它是 `HOLD` 收尾，就认为"这个状态正在播"；只有交给别的 clip（`on_end: idle` / `next`）之后再请求才会重新开始，`shoot`、`explode` 这类反复触发的动作照旧。

## 胡子 track 与"连帽子一起量身高"
> 原载 §5.2 能力（Capability）

- **现象**：原版只在"胡子彩蛋"里画的那条 `Zombie_mustache` track 会被转换出来；路障/铁桶/铁门/报纸的装备骨骼此前没被排除在量尺寸的包围盒之外，于是路障僵尸**连帽子一起**被压到 0.95 格，身体比普通僵尸小 15%（模型 0.565 宽 vs 0.625），看起来"小一圈"。
- **定论**：`ZOMBIE_*_EXCLUDE` 排除 `MUSTACHE`；`EntityConfig.measure_exclude_regex` 把装备骨骼排除在包围盒之外（骨骼照旧导出、照旧绘制），四种僵尸的身体盒与普通僵尸逐字段一致（83.9×127.5px）。

## 受击动画只设了一个 tick
> 原载 §5.2 能力（Capability）

- **现象**：原本 `damageBody` 只把 `animation` 设成 `hit` 就结束了，而 `walkOrEat` 在同一 tick 结束前必然把它改回 `walk`——客户端**通常根本收不到**（实体同步每 3 tick 一次），偶尔收到了也是把一个一秒多的 clip 播一个 tick 再混回去，这正是"僵尸挨打时动画不流畅"的来源。
- **定论**：受击是持续 8 tick 的状态（`ZombieEntity.HIT_HOLD_TICKS`），期间 `walkOrEat` 保持 `hit`，让 clip 自己的 transition 做淡入淡出；`hitTicks` 进存档。

## 放置判定与种植顺序相关
> 原载 §5.5 放置与叠放（标签驱动）

- **现象**：旧实现里"雷种不进花盆""豌豆不会长在雷上"这两件事结果是相反的。
- **定论**：`PlantPlacement.canPlace` 只看比自己层低的东西（`layerIndex(other) < layerIndex(self)`）：豌豆和土豆雷都在 layer 1，谁也够不着谁，结果与种植顺序无关。

## `SceneElementDef.accepts` 是放置规则的第二份副本
> 原载 §5.5 放置与叠放（标签驱动）/ §8 约定 15

- **现象**：`SceneElementDef` 曾存"能种什么"的 `accepts` 字段，是同一套放置规则的第二份手写副本，会与标签驱动的判定分叉。
- **定论**：能不能种只有 `PlantPlacement.canPlace` 一份（纯函数，只读 `#c:` 标签与 `PlacementDef`），`accepts` 已删除。

## 咖啡豆曾是"立即强化"，而不是"叫醒蘑菇"
> 原载 §5.2 能力（Capability）/ §6.2.1 关卡选择页

- **现象**：`boost_below`（咖啡豆）调的是每个能力的 `boost()`：放在向日葵上立刻产一颗阳光、放在射手上立刻射一发。原版咖啡豆只做一件事——叫醒白天睡觉的蘑菇；在这个语义下"加强"是免费的收益，而且**蘑菇根本不会睡**（`pvzce:nocturnal` 还不存在）。
- **定论**：能力改名 `pvzce:wake_below`，只调 `PlantEntity.wake()`：真的叫醒一个（`NocturnalCapability` 的 `Awake` 标志，进存档）时播 `wake_sound`，对醒着的植物什么都不发生（豆子照样消耗）。`PlantCapability.boost()` 随之删除——能量豆的大招是另一套设计（`02` 文档 §2.2.5），不该挂在同一个钩子上。

# 6. 客户端

## 客户端自己维护 `TimeOfDayS2C.night`
> 原载 §6.1 状态镜像

- **现象**：日夜此前由客户端自己维护（`TimeOfDayS2C.night`），与服务端是两份。
- **定论**：日夜由 `common/level/DayNightCycle` 计算，服务端与客户端共用同一份。

## 睡着的植物每帧都在冒 Zzz，而且两张计时表从不回收
> 清理轮发现（现状见 §5.2 能力 · 睡觉会冒 Zzz）

- **现象**：`InGameScreen.tickSleepZzz` 把"下一次该冒泡的时刻"记成了**当前**时刻（`zzzNextNanos.put(id, now)`），于是那条 `now < due` 的判据只挡住了 `(id % 4) * ZZZ_STAGGER_NANOS`（150ms 一档），真正的呼吸间隔常量 `ZZZ_INTERVAL_NANOS`（620ms）从头到尾没有参与运算 —— 一株睡着的蘑菇大约每 0.15~0.45 秒吐一个 z，比原版快 1.4~4 倍，而那个常量自己是一段死代码。同两处计时表（`zzzNextNanos` / `zzzStep`）以实体 id 为键，却从不清理，关卡跑得越久表越大。
- **定论**：首次呼吸仍按 id 错开，此后每 `ZZZ_INTERVAL_NANOS` 一次（相位不收敛）；被打断很久（暂停、重载）时重新对表，而不是连发补上；每帧末按"这一帧真正睡着的植物"裁剪两张表。`Zzz` 是纯客户端表现，服务端一行未改。

## 模态输入分发靠"子类记得先调 `super`"
> 原载 §6.2 GUI

- **现象**：此前这是"子类记得先调 `super`"的约定，而 `LevelSelectScreen` 先判定了占满窗口的卡牌网格，于是"新建关卡"对话框的按钮全部点不动。
- **定论**：`mouseClicked` / `mouseMoved` / `mouseScrolled` 在 `Screen` 里是 `final`，先给模态对话框、再给 widget、最后才调界面自己的钩子（`onMouseClicked` 等），结构上不可能再绕过。

## 铲子卡被种子包盖住
> 原载 §6.2 GUI

- **现象**：原来 `CardPainter` 先画了铲子槽、`SeedCardRenderer` 又把种子包盖在上面，于是唯一一张不该像种子包的卡长得和种子包一模一样。
- **定论**：卡面是 `CardModel` 的一部分，铲子卡用 `SHOVEL_SLOT_BACKGROUND`（原版 `ShovelBank.png`）并 `fitBackground = true`，图标居中、底栏不印价格。

## 卡槽条与"放下卡"路径没有声音
> 原载 §6.2 GUI

- **现象**：选卡界面一直有拿起卡的声音，游戏内卡片条以前是哑的；再点一次已选中的卡、右键、点棋盘外这些"放下"路径也一声不响，看起来像那次点击没生效。
- **定论**：拿起与放下都走 `playCardSound`（植物/工具 `sfx/ui/seedlift`、铲子 `sfx/effect/shovel`），取消路径统一进 `cancelSelection`。

## 点不动的卡没有任何反馈
> 原载 §6.2 GUI

- **现象**：冷却中 / 阳光不够 / 次数用尽的卡以前什么也不做——服务端会在两步之后拒绝种植，而玩家那时已经挑好了格子、正等着有东西长出来。
- **定论**：`InGameScreen` 用 `SlotInfo.available` 当场判断，`refuseCard` 放 `sfx/ui/buzzer` 并让那张卡左右抖一下（`CardBar.Host.cardShake`，偏 6px、三条半周期），被拒的卡不进入选中态。

## 卡片充能条的分母写死成 300，而且涂的是"已经过去"的那一份
> 见 §4.4 玩家、卡槽与资源 / §6.2 GUI

- **现象**：卡条把"还剩多少冷却"除以写死的 `300`，再把**已经过去**的那一份从卡片底边向上涂暗。于是只有冷却恰好是 300 tick 的卡画对过：樱桃炸弹（1800）、火爆辣椒（3000）的充能条只在最后 300 tick 里动一下，其余时间整条是空的；而每张卡在冷却期间都是**越等越暗**，等到能用了才"啪"地亮回来——读起来像在放电而不是充电。关卡一旦缩放冷却（`seed_cooldown_multiplier`），所有卡从被消耗的那一刻起就显示成"已经充了一部分"。
- **定论**：分母改为随包下发的 `SlotInfo.cooldownTotal`（服务端 `LevelServer.effectiveCooldownTicks` 算出的、这一关实际收的那一段），`SlotInfo.cooldownRatio()` 是唯一的比值；涂的是**还没回来的那一份**、从顶边往下量，卡从底部长回来。

## 失败画面曾是一句 UI 字体的"失败！"
> 原载 §6.2 GUI

- **现象**：失败时原来只画一句 UI 字体的"失败！"。
- **定论**：改为原版 `ZombiesWon_.png` 的 `DefeatScreen`（逐帧抄 `refer/anim/ZombiesWon.reanim`，24 fps、12 帧），前面另有两拍演出（镜头朝房子平移 2.1 格、停在最后那只僵尸啃房子的画面约 1.2 秒）。

## 选卡屏的归位位置差半个 `panMax`
> 原载 §6.2 GUI

- **现象**：归位位置曾经是 `stage.x() + panMax`，而游戏内 `PvzceCamera` 显示的是 cover 之后**居中截取的中间一段**（图左边缘在 `stage.x()`）——两者差半个 `panMax`，交接那一刻画面会横向跳四分之一屏。
- **定论**：`panOffset = panProgress * panMax`：home 与游戏内对齐，路的终点仍是背景图右边缘贴住屏幕右边。

## 编辑器与列表：三份拷贝、短 id、旧测试图
> 原载 §6.2 GUI

- **现象**：关卡/音乐/卡池编辑器各有一份列表编辑算法，三份拷贝此前已经分叉（一处用交换、一处用摘除插入），同一按钮在两个编辑器里行为不同；物品列表画的是 `GuiText.shortId(id)`；编辑器植物/僵尸页的图标取 `textures/entities/<id>.png`——那是控制器美术之前的旧测试图，画出来和游戏里完全不是一个东西。
- **定论**：算法抽成 `ListEditorSupport`；`PaletteList` 是带贴图 + 名字的列表行，图标优先 `AnimationManager.iconTexture(id)`（控制器模型里最大的部件贴图或 flipbook 第一帧），取不到才回退平铺 PNG。

## 语言文件从第一阶段起就没有代码读它
> 原载 §6.2 GUI

- **现象**：`assets/<ns>/lang/<locale>.json` 从第一阶段就在仓库里，但**没有任何代码读它**，所以列表里显示的是英文 id。
- **定论**：`GuiLang` 是唯一入口（key 是 MC 的 `<namespace>.<path>`），编辑器、波次表、卡池页都走它，缺失的 key 回退到 path。

## 未分类页曾被从关卡推导而消失
> 原载 §6.2.1 关卡选择页（`LevelSelectScreen`）

- **现象**：从关卡里推导"未分类"这一页，会让它在"当前没有未分类关卡"时消失。
- **定论**：未分类页是**固定页**（`pvzce:uncategorized` 哨兵），客户端拼页签表时永远补上它；服务端只下发有内容的页，空页由客户端补齐。

## 关卡列表：4×4 卡片网格、选中只存下标
> 原载 §6.2.1 关卡选择页（`LevelSelectScreen`）/ §6.2.3 关卡编辑器（`EditorScreen`）

- **现象**：页面原来是 4×4 大卡片网格（一屏 4 关）；选中的关卡旧实现只存下标，刷新后同一个下标可能指向另一关，于是"高亮的卡"和"按钮作用到的关卡"不一致；列表里选中一张卡此前也只点亮「下一步」，「编辑关卡」永远是灰的。
- **定论**：现在是左侧主题列 + 顶部类别行 + 行列表（一屏 6~8 关）；`LevelSelectScreen` 记住关卡 **id**，每次刷新后按 id 重新解析行号（纯函数 `indexOfLevel`）；`updateActionButtons` 同时点亮两个按钮，并按选中关卡改名（进行中 → 「继续游戏」）。

## 旧关卡 `level_1` 已删除、旧存档不迁移
> 原载 §6.2.1 关卡选择页（`LevelSelectScreen`）

- **现象**：id 从 `pvzce:level_1` 变成 `pvzce:yard/adventure/level_1`，存档目录名（当时的 `levelKey` = `ns + "__" + path.replace('/','_')`）随之变化，旧目录留在磁盘上不再被读取；原来的 `level_1`（9×5、整份卡池、巨人）已删除。
- **定论**：这是"分类改了、进度从头开始"的既定取舍，不是丢失；`LevelKey` 后来改成十六进制转义的单射键，旧键同样不做迁移（见 §3.4）。

## 空台词行会画出一个空气泡
> 原载 §6.2.2 开场对话（`DialogueOverlay`）

- **现象**：`text` 为空的行（原版用它做表情演出）以前会画出一个空气泡 + 「点击继续」，看起来像漏翻了一句。
- **定论**：空台词 = 没有台词的一拍（`Frame.silent()`，`bubbleBox` 返回 `null`），只演立绘、点一下继续；`LevelValidator.validateDialogue` 不再把"没有台词"报成问题。

## 编辑器画布用静止贴图、格子被拉伸
> 原载 §6.2.3 关卡编辑器（`EditorScreen`）

- **现象**：旧实现的预设精灵是静止贴图，且格子被拉伸到填满画布。
- **定论**：画布走游戏自己的世界投影（`beginOverlayWorldView` + `SceneTileRenderer.render` + `AnimationManager.render`），落点来自同一份 `LevelStage.board(canvasW, canvasH, columns, rows)`，`cellAtCursor()` 是它的精确逆运算。

## 波次/音乐编辑：独立屏与对话框、动作栏重复入口
> 原载 §6.2.3 关卡编辑器（`EditorScreen`）

- **现象**：波次界面原本在独立的整屏 `WaveEditorScreen` 里、音乐在 `MusicEditorDialog` 里，真正的编辑藏在二级菜单；底部动作栏还挂着「编辑波次」和「音乐」两个入口，与导航栏同名页重复，一个目标两个入口。
- **定论**：两页都改成"列表/时间线 + 详情同屏"、占满整宽、没有二级菜单（只剩 `WaveEditorModel` / `MusicEditorModel`），动作栏只剩「保存 / 测试 / 返回」。

## 编辑器入口：写死 `openEditor("custom_level")`、测试直接开局
> 原载 §6.2.3 关卡编辑器（`EditorScreen`）

- **现象**：列表下方的「编辑关卡」此前入口写死 `openEditor("custom_level")`，每点一次都在编辑同一关，存成别的名字那份永远打不开；测试按钮原先直接发 `RequestLevelC2S`（＝让服务端开局），跳过了选卡界面，同一个关卡从列表打开却要选卡。
- **定论**：「编辑关卡」送**选中的关卡**进编辑器；测试按钮只保存，再交给 `PvzceClient.testEditedLevel` 等**服务端重载后的关卡列表**（`/reload` 后由 `PvzceServer.refreshLevelList` 补发）再打开选卡界面。

## 翻页的两种边界 bug
> 原载 §6.2.3 关卡编辑器（`EditorScreen`）

- **现象**：页数向下取整会让尾部若干行**没有页**（18 关 4 列 4 行可见时是 5 行，页数 floor(5/4)=1，指示器写"1/1"、两个箭头全灰、第 5 行永远看不到）；按 `totalRows - pageSize` 夹取会让相邻两页**重复同一行**（13 关 4 列 2 行可见时页曾是 0-1、2-3、3-4）。
- **定论**：算法抽到纯函数 `ListPaging`：首页行号永远是页大小的倍数、末页夹到 `(pageCount-1)*pageSize`、页数**向上取整**，`ListPagingTest.everyRowIsReachableOnExactlyOnePage` 对全部"行数 × 页大小"组合断言每一行恰好出现在一页上。

## `kind().equals("sun")` 让每一种掉落物都发光
> 原载 §6.3 渲染 / §8 约定 27

- **现象**：光源判定原本写的是 `kind().equals("sun")`，而 `EntityKind.RESOURCE` 的值**就是** `"sun"` —— 于是**每一种掉落物**（金币、钻石、能量豆）都被当作太阳，落地就在草坪上投一圈黄光。
- **定论**：判定一律比**内容 id**（`defIdString()` / `PvzceIds`）；`EntityKind.RESOURCE` 改为 `"resource"`（kind 字符串走 `EntitySpawnS2C`，故 `PROTOCOL_VERSION` = 10），`EntityLightTest` 钉住"只有阳光亮"与"kind 不等于任何内容 id"。

## 缺失贴图曾是一块白方块
> 原载 §6.3 渲染

- **现象**：取不到贴图时以前画的是一块**白方块**，和"故意画成空白"的精灵分不出来；而这类引用确实存在过（`textures/resource/generic`、`textures/resource/coin`、没有 `texture` 字段的内容）。
- **定论**：`EntityArt.MISSING_TEXTURE`（`textures/mission.png`，2×2 品红/黑棋盘格，`TextureManager` 对它单独用 `GL_NEAREST`）是缺失贴图唯一的样子，`PvzceClient.drawTextureRegion` / `drawTextureQuad` 与 `EntityArt.sprite(null)` 都回答它。

## 一次性音效变成"无限循环"的物理来源
> 原载 §6.5 声音与粒子

- **现象**：`AL_LOOPING` 是**源的属性、不是 buffer 的属性**——一个被要求循环过的源会把之后绑上来的任何 buffer 一直循环下去；大波提示占用的源马上会被下一个音效重用，于是一次性音效听起来变成了无限循环。
- **定论**：音频源在重新绑定 buffer 之前一律先 `alSourceStop`；`play()` 另有两道保护（同一事件 130ms 内去重、一个事件在自己的声音播完之前再次请求会被丢弃），都不是白名单。

## `ensureMenu` 的"空闲才播"与重开时的音乐重叠
> 原载 §6.5 声音与粒子

- **现象**：`PvzceMusicController.ensureMenu` 曾被写成"菜单轨空闲才播"，于是奖励页的 `zen_garden`（菜单轨）一直压着关卡列表——关卡列表请求 `choose_your_seeds` 时发现轨道忙，什么都不做；另一处只有"离开关卡"这条路会停乐（`clearLevelClientState()` → `music.leaveLevel()`），从存档提示框重开、编辑器「测试」不经过 leave，上一局的战斗轨会继续循环、压在新一局的轨道下面（表现为音乐重叠）。
- **定论**：`ensureMenu` 的语义是"同曲不重启、异曲要换"；每个新关卡实例由服务端在 `LevelInitS2C` **之前**补发三条 `MusicEventS2C.reset(track)`（`PvzceServer.silenceClientLevelMusic()`），同一实例的 resync 不发重置。

## `aNewLevelInstanceResetsTheClientsMusicAndAResyncDoesNot` 大约四次里红一次
> 原载 §关联用例（`ServerMenuFlowTest`）

- **现象**：这条用例在 resync 段偶发失败（`resyncing the running level must not touch its music`）。**与改动无关**：在未改动的 HEAD 上单跑 12 次复现 3 次。真正的原因是**测量窗口开早了**——新实例的开场音乐 cue 由 `processMusicCues` 在它的**第一 tick** 发出，而 `LevelInitS2C` 是在 `createLevel` 里同步发的，所以 cue 落在 init **之后**；用例一看到 init 就发 `ContinueLevelC2S`，这个 cue 有时就落进了 resync 的统计窗口，被当成"resync 动了音乐"。
- **定论**：等新实例真的 tick 过（`level().tickCount() > 1`）再取基线：那一 tick 之后，开场 cue 已经在窗口之外。修完连跑 10 次该类 + 3 次全量全绿。

## 粒子曾是效果名上的一个 `switch`
> 原载 §6.5.1 粒子（数据驱动）

- **现象**：粒子曾经是 `ParticleEngine` 里对效果名的一个 `switch`，只能画**纯色方块**——原版那 81 张粒子贴图与 112 个 emitter 脚本一张也用不上；内置效果 id 还是散落在能力里的字符串字面量，未知 id 只在客户端每秒报一次日志，症状（"这个效果不见了"）指向不了任何地方。
- **定论**：粒子由 `ParticleDef` 数据驱动（`data/<ns>/particles/<类目>/*.json`），内置 id 集中到 `PvzceParticles`（与 `PvzceSounds` 同形）。

## 金币光晕因没有加法混合被砍掉
> 原载 §6.5.1 粒子（数据驱动）/ §4.5 背包、金币与关卡奖励

- **现象**：原版的光晕用加法混合画，当时本渲染器没有加法模式，用普通 alpha 画出来是一块盖住底下东西的实心圆盘，金币光晕因此被整个砍掉——生成硬币美术时也排除了 `COINGLOW` 与 `DIAMOND_SHINE`。
- **定论（第一次）**：`RenderSystem.blendAdditive` / `blendNormal` 补上加法混合（普通粒子先画、发光粒子后画，整帧最多切两次混合状态）；硬币美术仍排除这两个 emitter。
- **后来的更正**：控制器部件现在也能声明 `"blend": "add"`（见下），阳光的两圈光晕就是这样画的。硬币的光晕**仍然不进模型**，但原因不同了：不是"画不出来"，而是它比币面宽（80px vs 43px），而一个控制器模型的所有骨骼共用一个缩放倍率，把它留在模型里会让币面被作者成目标尺寸的 54%。它该由粒子层负责。

## 未定义的效果会画一个红方块
> 原载 §6.5.1 粒子（数据驱动）/ §8 约定 22

- **现象**：曾经会给每个未知的效果名画一个红方块，让拼错看起来像个真效果。
- **定论**：未定义的效果**不画东西**，只按 id 报一次日志。

## 关卡列表按字符串排序，`1_10` 跑到 `1_2` 前面
> 原载 §6.2.1 关卡选择页 / §8 约定 45

- **现象**：列表与页签都按 `Identifier.toString()` 排序，而 id 是给人编号的文本：加进第 10 关（`1_10`）之后，它排在 `1_1` 与 `1_2` 之间 —— 关卡越全，列表越不像一条关卡链。
- **定论**：`LevelGrouping.compareIds` 做自然序比较（数字段按数值、其余按字符），服务端下发列表（`PvzceServer.sendLevelList`）与页签推导（`LevelTabs.build`）共用它；**不重命名任何已有 id**（id 是存档目录名与其它关卡的引用键）。

## 手套卡住不动，像有无限冷却
> 原载 §6.2 关卡内取消选卡

- **现象**：手套是"拿起 / 放下"两击，客户端为了让它能收第二击，把卡**跨点击保持选中**；而冷却在拿起那一刻就开始了。于是第二次点击落在同一张卡上时，`cardUsable` 看到的是"选中但没就绪"，直接按拒绝处理（buzzer + 抖动），植物吊在手套上等 15 秒超时 —— 玩家看到的是**手套用一次就永远冷却**，而卡片条上那张卡也确实一直是灰的。
- **定论**：`spendSelectedCard` 对所有卡（工具也算）**发出请求后立刻清掉选中**：一次完整使用之后卡就回手。服务端那半边的规则不动（`finishingMove` 让正在搬运的手套忽略自己的冷却，一次搬运只花一次使用次数）。

## 阵营是客户端替关卡决定"僵尸方不可选"
> 原载 §4.3 进入/重开关卡的协议语义

- **现象**：`LevelSetupScreen` 把僵尸方写死成"未解锁"（当时确实没有僵尸方卡组），于是"这一关只有植物方"是**构建的事实**而不是**关卡的数据**；同时"要不要问阵营"这一问在关卡列表、编辑器测试、冒烟钩子里各写了一遍，只有列表那一份问了。
- **定论**：`LevelDef.playable_teams` 声明可玩阵营（缺省＝全部），服务端按它下发每条 `TeamInfo.playable`；`enterLevelFromMenu` 是唯一的入口决策，"只有一个可玩队伍就跳过 `LevelSetupScreen`"也只在那一处判断。

## 爆炸范围写成半径，于是"3×3"要靠猜一个数
> 原载 §4.9 爆炸范围

- **现象**：`pvzce:explosive` 与 `damageArea` 一直只认**径向**距离，可是原版的灰烬线是按**格**说的：樱桃炸弹打的是"它那一格加上周围八格"，土豆雷只打"自己那一格"。当时的等效数是 `radius 1.5` 与 `radius 0.55` 这类**推出来的半径**（相邻格中心距 1.0，所以单格要 ≥0.5、3×3 要 ≥1.0 而 1.5 更宽），既没有说明它到底覆盖哪几格，也让"土豆雷自炸一格"要靠 `trigger_range` 0.5 与半径 0.55 之间的空隙勉强成立。
- **定论**：`radius` + `square` 直接读成**格数**（判据 `|Δ| ≤ radius + 0.5`）——土豆雷 0.5 = 自己那一格，樱桃炸弹 1.0 = 3×3，毁灭菇 3.0 = 7×7；火爆辣椒另走 `trigger: "row"` + `LevelAccess.damageRow`，因为"整行"是形状而不是距离：一个足够大的方格会连带打穿旁边的行，而"刚好 9 列宽"的半径在更宽的草坪上会短一截。

## 锤子是写死的 100000 点、走小推车的伤害类型
> 原载 §4.9 关卡自带的工具

- **现象**：`HAMMER_TOOL_DAMAGE = 100_000`，伤害类型写死 `pvzce:mower`（无视护甲）。于是木槌在草坪上等于一辆小推车：普通僵尸、路障、铁桶全都一下死，"路障要两下、铁桶要三下"这条原版规则在数据里根本表达不出来，换一把工具也无处声明它打多重。
- **定论**：`ToolDef.damage` / `damage_type`（缺省 200 点 / `pvzce:impact`），锤子自己在 `tools/hammer.json` 里写这两个数。200 是普通僵尸的血量，`impact` 让护甲照常吸收，于是普通 1 下 / 路障 2 下 / 铁桶 3 下由既有的 `ArmorCapability.absorb` 自动成立。

## 攻击不看阵营，所以"变成自己人"无从表达
> 原载 §5.2.2 阵营与魅惑

- **现象**：`zombiesInRow(row)` 返回这一行所有僵尸，射手、投手、近战、爆炸、子弹命中测试全都直接用它；伤害也从不过问来源与目标的阵营。于是"把一只僵尸变成我方"这件事在引擎里没有落点：要么在每一处攻击代码里加一句"这个僵尸是魅惑的吗"，要么让它变成一只仍然挨打的我方僵尸。
- **定论**：**"谁是敌人" = 不是同一支队伍**。`LevelServer.isEnemyOf` 是唯一判据，`LevelAccess.enemiesInRow(row, team)` 是攻击方的唯一读法（`damageArea` / `damageRow` 的 `sourceTeam` 同源），`zombiesInRow` 只留给"这一行有几只僵尸"。魅惑因此只剩一件事要做：`setTeam`；代价是胜负判定必须改数 `hostileZombieCount()`，否则关卡会在最后一只敌意僵尸死后仍然无法结束。

## 穿透子弹在每个重叠 tick 都造成一次伤害
> 原载 §5.2 子弹能力 / §5.2.1 伤害类型

- **现象**：`pierce` 只回答了"命中后不要消失"，没有回答"同一只僵尸还算不算目标"。子弹每 tick 都在僵尸的命中半径内，于是**每一 tick 都是一次新命中**：一发 20 点的大喷菇喷雾十个 tick 打死 200 血的僵尸，玩家看到的是"大喷菇秒杀一切"。这是引擎里的洞（原来没有任何穿透子弹，所以没人踩到），不是大喷菇的数值问题。
- **定论**：`ProjectileEntity` 记住这发子弹打过哪些僵尸（`hitIds`），`findTarget` 跳过它们。用集合而不是"上一只"，因为两只僵尸可以在同一格里。
- **顺带**：大喷菇的伤害类型从 `pvzce:ash` 换成新的 `pvzce:spray` —— 无视护甲（穿纱门）与 `burns`（烧成焦尸）是两件事，共用一个类型会让喷雾也留下焦尸。

## 大喷菇是一团气，却被做成了会飞的子弹
> 原载 §5.2 植物能力（`pvzce:cone`）

- **现象**：上面那条把"每 tick 重复命中"修好之后，剩下的问题还在：大喷菇的喷雾是一颗 `linear speed 2.4` + `pvzce:pierce` 的**真实弹体**，带着自己的精灵飞满 4 格。于是它必须借 `pierce` 加 `hitIds` 那套记账来**模拟**范围伤害，屏幕上的读法也从"贴着邻居呼气"变成"远程狙击手"——一团气不该有飞行时间。原版的大喷菇是一瞬间覆盖身前一整片的锥形，是**近战形状**，不是射程更短的射手。
- **定论**：新增 `pvzce:cone`（`ConeAttackCapability`）——**一个形状，结算一次**，与 `explosive(row)`、`freeze_all` 同族：同一 tick 取本行敌人、留下正前方 `range` 格内的、每只打一次，没有弹体也没有逐发记账。`fume_shroom.json` 改用它（`interval` 90 / `damage` 20 / `range` 4.0 / `damage_type` `pvzce:spray`，原版"前方 4 格"）。`pierce` 与 `hitIds` 留着（仍是合法能力、仍由同一个用例钉着），只是**内置内容已经没有穿透子弹**。
- **画面不能只 emit 一次**（`cloud_particle` / `cloud_count`）：粒子引擎把一条定义里的**每一颗粒子都放在 effect 生成的那一个点上**，只有 `motion` 会把它挪走 —— 所以一次 emit 就是植物脸上的一团，而不是一条气。原版没有这个问题：它的 `FumeCloud` 就是那颗**会飞的投射物精灵**，气之所以显得"铺开"是因为图在飞；伤害改成瞬发之后没有东西可飞了，于是把形状**画**出来：`cloud_count` 个发射点沿锥形均匀铺开，各自带 `pvzce:fume_cloud` 自己的前向漂移。
- **间距必须小于一团云的宽度**：间距是 `range / cloud_count`，而一团云约 0.7 格宽。4 格配 3 个 = 1.33 格间距 → 屏幕上是一串**断续的独立团**（用户直接反馈的就是这个）；6 个（`DEFAULT_CLOUD_COUNT`）约 0.67 格间距 → 叠成一条连续的带。**要加长光锥就得加数量，不是拉间距。**
- **同一条里抓到的第一个错**：`cloud_particle` 用 `optionalFieldOf("cloud_particle")` 读，JSON 不写这个字段时拿到的是 `Optional.empty()`，而空的意思按设计是"不画"。于是**凡是没有把这个字段写全的植物都一个粒子都不画** —— 默认值形同虚设。构造器现在把"缺省"规范化成 `DEFAULT_CLOUD_PARTICLE`，只有显式 `cloud_count: 0` 才是"只要伤害不要画面"。
- **同一条里抓到的第二个错**：**"在前面"必须按格子判断**。植物中心 1.5、枪口在 1.8，而走到植物身上那只僵尸的中心是 1.99 —— 比枪口更靠右、也在 4 格之内，所以只比 `cellX > muzzleX` 会让蘑菇对着**正在啃它的那只**喷气。判据改成 `zombie.gridX() > plant.gridX()` 再看射程。原版的喷雾从不打自己那格，`NightAreaTwoLevelsTest.theCloudReachesFourCellsForwardsAndNoFurther` 用三只僵尸（锥内 / 四格之外 / 踩在植物身上）钉住。
- **顺带**：`PvzceIds` 补上 `DAMAGE_SPRAY`（`spray` 是唯一一个没有常量的内置伤害类型，此前各处只能写字面量）；`LevelValidator.validateDamageTypes` 原来只查 `explosive` 与 `splash`，现在把 `freeze_all` 与 `cone` 一并查，并且各自报告**它自己真正的兜底类型**（原来一律写"回退到 `pvzce:projectile`"，对灰烬/splash/喷雾都是错的）。

## 手套的冷却从"拿起"挪到"放下"
> 原载 §6.2 卡槽条

- **现象**：上一轮为了让第二次点击能被接受，把"完整使用一次后取消选择"套到了所有卡上，同时手套的冷却仍在**拿起**那一刻开始。于是选中手套、拿起植物之后，卡进入冷却、条子把它画灰、`cardUsable` 拒绝再选它 —— 玩家拿起了植物却放不下去，手套"几乎无法使用"。
- **定论**：手套的冷却在**放下**（或搬运超时）时才计，因为那时这一次使用才算结束；客户端把手套当作"冷却中也可以点"的卡（`InGameScreen.gloveCard`），服务端仍然拒绝"手里没拿东西且在冷却"的点击。

# 8. 约定（避免重新长出重复实现）

## 约定清单的由来：每条都曾是已分叉的重复实现
> 原载 §8 约定（避免重新长出重复实现）

- **现象**：以下每一条都对应一处**曾经存在两份以上实现并已经分叉**的地方——例如 `easeInOut` 除 `MathUtil` 外还有一份 `ChooseSeedsScreen` 的私有副本。
- **定论**：改相关逻辑时顺着那条唯一实现改，不要新开一份。

## 分层表只是文档里的一张表，没有一个断言
> 与上一条同一轮

- **现象**：`api` / `common` / `server` / `client` 在同一个 source set 里，分层全靠包约定；"哪些反向引用是有意的"写在文档里，但**没有任何东西能检查它**。一次清理就能让表格里的"例外：2 类"变成 3 类而没人发现 —— 编译器不会说话，评审也看不见 6.2 万行里多出来的一个 import。
- **定论**：写成 `LayerDependencyTest`（5 个用例）+ 共用的 `testutil/SourceTree`。零容忍的三条：`server`/`common`/`api` 不 import `client`；`client` 不 import `server`（共用逻辑属于 `common`，否则"服务端权威"会变成一个程序两个名字）。有例外的一条：`common → server` 只许从 `common/capability/**` 与 `common/level/mechanic/**` 出发。**第三类例外是这轮新查出来的**：`api.content`/`api.entity` → `common`（21 处）与 `server`（7 处）—— 定义包里带着行为预设表（`PlantBehaviorPresets` 等），它们必须指名能力实现；`api.entity.LevelAccess` 的返回类型是 `PlantEntity`/`Team`。它与第一类互为反向，真要拆干净得把能力接口搬进 `pvzce-api` 模块，属于独立重构；在那之前按**文件名白名单**钉住，不会再默默多一处。守卫本身用一次注入验证过会红（给 `MathUtil` 加一行 `import com.pvzce.server.Team;` → `commonReachesTheServerOnlyThroughCapabilitiesAndMechanics` 失败）。

## 一个包可以同时有 id、有样包、没有任何调用点
> 与上一条同一轮

- **现象**：`MovePlantC2S` 是**人工通读整个协议**才发现的（它占了 id 16、被 `PacketProtocolTest` 当样包，但全仓库没有一个 `new MovePlantC2S` 也没有一个处理分支）。一个问题要靠在 42 个包里逐个 grep 才能发现，说明缺的不是一次清理，而是一条断言：包的类、协议表里的行、两端的调用点，这三样东西之间**没有任何联系**，编译器不会替它们对齐。
- **定论**：`PacketWiringTest`（`com.pvzce.arch`）。以 `common/network/packet/` 下的类文件为准（不是那张私有表）：每个 `*C2S`/`*S2C` 必须①在 `PvzcePackets` 里有一行（且两张清单的数量必须相等，所以"加了类没加行"与"删了类没删行"都会红），②两端的**主源码**都要出现它的名字 —— C2S 由客户端构造、服务端处理，S2C 由服务端**或 `common` 里的机制**（机制自己发同步包）构造、客户端处理。只查主源码是关键：`PacketProtocolTest` 里那个样包列表曾经让"没有调用点"看起来像有。附带一条：`*C2S`/`*S2C` 之外的文件只允许是 `LevelPayload`/`SeedOption`/`SlotInfo` 三个载荷 record。同样用注入验证过（删掉 `PickCardC2S` 那个空处理分支 → `everyPacketIsSentAndHandled` 报 "no server code names it (no handler)"）。

# 动画系统的八个缺陷（一次性修复）

> 现象与定论都源自 2026-09 的一次完整排查：把 `tools/reanim_to_pvzce*.py` → `animations/**/*.json` → `client/animation/` → `ControllerPlayback`/`SpriteRenderer`/`Tesselator` → `ClientLevel`/主循环这条链整条读了一遍，并对生成好的资源做了统计验证。

## 每帧 alpha 被解析后丢掉
- **现象**：阳光是"一个核心 + 两圈半透明光晕"，画出来是"又亮又没有实体"的白色一团；金币的 `shading`、樱桃/毁灭菇的渐显、僵王的眼/口发光全都不对。
- **定论**：解析器的字段表里有 `a`（`reanim_to_pvzce.py`），但继承用的状态字典里**没有** `a`，`elif key in state` 于是把它静默丢掉，`FrameState` 也没有这个字段；运行时更是写死 alpha=1。补上 `FrameState.a` → JSON `alpha` 通道 → `BonePose.alpha` → `ControllerPlayback` 的绘制调用，并且**只在该骨骼透明度真的变化时才写通道**（否则 2688 条骨骼轨道每条都多一份"全是 1"的常量表）。

## 控制器没有加法混合，光晕只能靠砍
- **现象**：见上一条。alpha 修好之后，光晕用普通 alpha 画仍然是一块盖住核心的实心圆盘。
- **定论**：`ControllerModel.Part` 加可选 `blend`（`normal`/`add`），生成器的 `EntityConfig.additive_images` 按贴图名正则标记，`ControllerPlayback` 用**两趟**（先 ordinary 后 additive）画完，混合状态每实体最多切两次。阳光的 `Sun2`/`Sun3` 已标上。

## 逐 clip 播放速率缺失
- **现象**：僵尸死得慢悠悠（3.25 s 而原版约 1.6 s）、啃咬比原版慢一半以上；铁桶/路障走路滑步。
- **定论**：数据格式加 `rate`（静态倍率）与 `reference_speed`（作者假设的地面速度，格/秒）。僵尸死亡 2.5×（39 帧压到 1.3 s，仍在 6 s 尸体留场之内）、啃咬 1.5×（原版 1 s 咬 3 口而 `anim_eat` 40 帧两口）、行走 `reference_speed` 0.23（运行时按实测位移推速率，静止时回 1×）。测量读数用**绘制位置**，因为它才是脚踩着的那条线。

## 循环长度算错一帧
- **现象**：走路每圈在原地僵 83 ms、僵王死亡僵 250 ms；反过来，气球僵尸的飘浮每次循环倒退着闪一下。
- **定论**：原来一律按 `帧数 / fps`，而采样是在关键帧之间插值的——duration 越过最后一个关键帧就是一段静止。现在由生成器按**接缝**判定：末帧能接回首帧（接缝跳变量 ≈ 普通帧间步长）→ `帧数 − 1`；接不回 → 整段。源数据里故意以停住收尾的段用 `trim_end` 显式去掉（土豆雷的 `anim_armed`）。**不能用"首末帧是否相等"判定**：豌豆射手 idle 的首末帧只差 0.1px（普通步长 0.47px）却是个完美闭环。

## 掉落物的自动拟合自相矛盾
- **现象**：金币被画成 0.8×0.2 格的横条（宽高比 4:1），阳光是 1.43:1 的椭圆。
- **定论**：删掉"宽度拟合 + 高度取自动画文件"这套规则与那个 3× 上限。掉落物与植物/僵尸同规则：**画多大就是模型里写多大，再乘 `render_scale`（两轴同倍率）**。转换器把掉落物的 reanim 缩放到 `EntityVisuals.AUTHORED_DROP_CELLS`（0.34 格，与运行时共用一个常量），比本体宽的光晕不进模型。`model.size` 也改成按**运行时同一套 affine 在模型空间算出**（原来用的是"每帧旋转角包围盒"的并集，比真正画的矩形大：金币是 80×80px 而币面是 43×40）。

## 实体锚点踩在 20 Hz 阶梯上
- **现象**：僵尸的影子在平滑滑动，身体每 50 ms 跳一格；下落的阳光一格一格往下跳。
- **定论**：`AnimationManager.anchor` 读的是包里的权威坐标，而实体每 3 tick 才同步一次、客户端画 60~260 帧。改用 `visualCellX/Y/Height`（已有补间），与影子、贴图兜底路径同源。权威值仍然只用于命中测试、相机换算与断言。

## 只活一个 tick 的动画状态发不出去
- **现象**：射手开火时常常**完全不放动画**（子弹飞出去、植物僵着）。
- **定论**：实体状态每 3 tick 发一次，而 `ShooterCapability` 在冷却结束那一 tick 先把状态设成 `IDLE`、下一 tick 才设 `SHOOT`——那个 `IDLE` 三次里漏掉两次，客户端就没有"离开 shoot"这一步，一次性 clip 播完 HOLD 住之后再请求同一个状态被 `isAlreadyPlaying` 当成"还在播"。`Entity.setAnimation` 现在会置脏标记，`LevelServer.syncSlots` 见到就当场同步。

## 每个 quad 建销一对 GL 对象
- **现象**：帧时间被对象创建/销毁吃满，动画按帧采样，于是掉帧直接表现为动作变粗。
- **定论**：`BufferBuilder.build()` 每个 quad 都在 `glGenVertexArrays` + `glGenBuffers`，`MeshData.close()` 再删掉——一块草坪加一波僵尸每帧上千次。`Tesselator` 改成一块持久 VAO/VBO：CPU 侧照旧构建，上传用 `glBufferData(size, GL_STREAM_DRAW)` 孤儿化后 `glBufferSubData` 只传数据，属性指针只在创建时设一次。148 处调用点零改动，并加了一条"build 了却没 draw"的检查。顺带缓存了 `client.camera()`（渲染路径一帧问 15 次，每次都新建两个 `Matrix4f`），并把实体绘制顺序改成**按行**优先（原来只按种类，前排僵尸会被后排植物压住）。

## "未知 JSON 键"这条通用检查做不成，原因是编解码器不对称

## `存档目录键` 的客户端抄本已经分叉
- **现象**：`LevelKey`（服务端）与 `LevelMove.saveKeyAfterMove`（客户端）各有一份键推导，本意是"编辑器换组不必往返服务器"。两份对世界名的净化处理不同（客户端把非法字符换成 `新世界`，服务端换成 `___`），于是同一个世界在两边指向不同目录。
- **定论**：规则上移到 `common/util/LevelKey`（`of` / `hex` / `escapePath` / `levelDir` / `statusFile`），两边都调它，抄本删除；世界名净化统一到 `WorldPaths`。测试分两层：`LevelKeyTest` 钉规则本身（含"不同 id 永不共目录"），`LevelMoveTest` 钉换组后文件真的落在了那个键下。

# 体验修正（上次世界 / 阳光颜色 / 2-5 / 木槌）
> 一次五件事的体验轮。现状见 `架构-客户端.md` §6.2.1b（标题页）与 §6.2（木槌光标）、`架构-服务端.md` §4.7.1（掉落与亮度）与 §4.9（墓碑）。

## 每次重开都要重新选择世界
- **现象**：`PvzceClient.currentWorld` 是写死的 `"world"`，只有标题页的玩家选择器会改它，且不落盘。于是每个新进程都从"未选择"开始：默认世界目录不存在就弹选择器，玩家每开一次游戏都要重新点一遍自己是谁。
- **定论**：谁在玩是**这个游戏目录的事实**，不是这个进程的状态。配置 `config/pvzce-client.toml` 增加 `last_world`（客户端构造时读、`setCurrentWorld` 变化时写，名字先过 `WorldPaths.sanitize`，与存档目录同一条规则）。标题页因此一进来就写着上次那名玩家，「开始游戏」直接进他的关卡列表；只有目录真的不存在（新装的游戏、或玩家删掉了它）才回落到选择器。

## 阳光亮到发白，层次全糊在一起
- **现象**：阳光的动画是三层叠加（36px 核心 + 77px、117px 两圈加法混合的光晕），而所有掉落物共用一刀切的灰乘色 `EntityVisuals.DROP_TINT = 0.5`。核心是饱和黄，两圈光晕的贴图本身偏白（B 通道高到 180），加在一起就是"往黄里加白"——太阳变成一个没有形状的白团，而且换任何一种掉落物都只能用同一个数。
- **定论**：拆成两件各管一半的事。**颜色归资源**：`ResourceDef.tint`（缺省 `DropTint.DEFAULT` 的 0.5 灰，行为与从前一致），阳光声明暖黄 `[0.58, 0.50, 0.15]`，金币继续是灰 —— `EntityVisuals.dropTint(defId)` 是唯一的查表处，两张渲染路径（动画与贴图兜底）都走它。**强度归光晕**：转换器新增 `EntityConfig.additive_alpha_scale`，sun 那份配置写 `0.7`，把叠加层的 alpha 按比例写进 `animations/resource/sun.json` 的关键帧 —— 加法混合越叠越亮，三层满 alpha 必然糊掉，压到七成既留形状又不盖核心。截图对照：白天是黄色球 + 暖光晕，夜里也仍是暖黄而不是白点。

## 2-5 是三条独立的问题：收不了阳光、僵尸从马路上来、墓碑数量恒定
- **现象**：2-5 的体验有三处不对。其一，收集阳光要同时满足"本关解锁该资源"与"卡槽里有阳光卡"，而这一关的三个槽位是墓碑破坏者 / 土豆雷 / 樱桃炸弹 —— 击杀掉出来的阳光**一颗也捡不起来**，连左上角的阳光数字都不显示（`hasSunBank()` 也按卡槽判）。其二，`grave_spawner` 与 `waves` 同时在出怪：波次表里的 132 只僵尸照常从马路走进来，"僵尸只从墓碑出来"这条设计根本没生效，而墓碑每 10 秒才冒一只。其三，波次与墓碑数量无关，砸掉的墓碑只是被补回同一个数。
- **定论**：三处分别处理。**阳光卡进卡槽**：`slots` 加 `pvzce:sun`（`max_seed_slots` 随之 4），阳光卡是 HUD 而不是卡片（`SeedCardBar.orderCardSlots` 一直跳过它），所以卡条外观不变、左上角出现阳光银行、阳光可以直接点。**僵尸全部来自墓碑**：波次表保留但清空 `entries`（`waves.allWavesReleased()` 要求 waves 非空，删掉波次表这一关就永远赢不了 —— 波次在这里负责进度条、节奏与收尾判定），墓碑的 `interval` 从 600 降到 90（1.5 秒一只）。**墓碑随波次增长**：`GraveSpawnerData.graves_per_wave`（每来一波目标座数 +1，2-5 写 1：9 座起步、第六波 15 座），`standingTarget(已到达波数)` 是唯一算这个数的地方。**顺带修掉一个会让这一关打不完的问题**：墓碑在最后一波之后停止冒怪（`LevelServer.wavesReleased()`），否则场上永远有僵尸、胜利判定永远不成立；那一波由 `graves_spawn_night` 把每座墓碑一次性开一遍，正好当高潮（这条规则 2-5 一直开着，旧文档写它关掉了）。

## 僵尸掉的阳光从天上落下来
- **现象**：`dropZombieSun` 走资源自己的 `drop_motion: fall`，于是"僵尸死后掉三颗阳光"表现成"死亡格子的上方 2.2 格凭空出现一颗阳光，用五秒慢慢飘下来"——掉落物看起来像关卡天气，而不是这一击杀的产物。
- **定论**：击杀掉落改用 `landed`，并按 `zombie_sun_drop_count`（新规则，缺省 3）掉**多颗**：落在死亡格或它相邻的格里（散开一格是为了三颗不叠成一个像素，且落在草坪范围内）。概率从 0.08 降到 0.03 —— 概率是**按颗数读的**，3% 掉三颗与 9% 掉一颗收入相近，但前者是更少、更值钱的瞬间。

## 木槌没有挥击动作，边缘反倒常驻一圈光
- **现象**：2-5 的鼠标是木槌，但它画的是**卡片贴图**（一张静态 PNG），点击时唯一的反馈是服务端在命中点炸开的 25 颗星形粒子 —— 那个位置就在光标脚下，看起来像木槌周围多了一圈光圈而不是一次打击。另外客户端还在地上画一个半径等于 `ToolDef.range` 的半透明黄色圆盘当准星，常驻显示、同样像光圈。
- **定论**：把两圈"光"去掉、把动作补上。**射程圆盘删除**（`InGameScreen.drawAimDisc` / `renderDefaultToolHover` / `ClientMechanics.defaultToolRange` 一并消失）：打得中打不中由点击时挥的那一下回答，而不是在地上画一个圈。**命中星形粒子删除**（服务端只留那声 bonk）：打击的画面是木槌自己。**木槌改成动画**：`Hammer.reanim` 的 `anim_whack_zombie` 段本来就是"举起 → 砸下 → 收回举起"，于是转换器把它切成两个 clip —— `idle`（最后一帧，持握姿势）与 `attack`（整段一次性播放，`on_end: idle`）；工具定义因此要能声明美术，`ToolDef` 增加 `AnimationBindings`（`tools/hammer.json` 写 `"animation_dir": "tool"`），`EntityArt.bindings` 也查工具注册表。客户端把光标画在 `beginOverlayWorldView` 开的方形小视口里（`ArtTarget` 而不是实体：木槌不在棋盘上，没有血、没有队伍、没有格子），**锚点在框的下沿**——转换出来的模型原点是它被拟合的地平线，锚在中心会高半格、脑袋被视口切掉。点击当帧播 `attack`、不等服务器回话（空挥也挥），播完由 clip 自己的 `on_end` 回到持握姿势。


# 动画与场景表现（一轮修复）

## 报纸僵尸死后站着不动：一半的死亡请求落在一个不存在的 clip 上
- **现象**：`ZombieEntity` 随机从 `death` / `death2` 里挑一个发出去，而"这具美术有没有 `death2`"是按 `animations` 映射猜的 —— 两者都没显式映射时 `resolve` 返回同样的 `Optional.empty()`，于是被判成"有两段死亡"。报纸僵尸、小鬼、气球、撑杆、矿工的**每一半死亡**因此发的是 `death2`，客户端找不到这个 clip 就静默回落 `idle`，尸体用站姿停满 6 秒（`death_water` 溺水同理）。这个回落是完全静默的，所以线上只看到"站着的尸体"，日志里什么都没有。
- **定论**：**挑变体这件事移到客户端**（`AnimationVariants`）：服务端只发 `death` 这一个状态，客户端在文件**真的有**的死亡 clip 里按**实体 id** 挑一个（不是掷骰：id 由服务端按关卡顺序发，同一局的同一具尸体每次都是同一段，重放也对得上）。`death_superlong` 不进池子（重型身体的死法由定义自己把 `death` 指过去），`death_water` 是家族成员（美术没有就按普通死亡沉下去）。`AnimationManager` 的判等改用**解析后**的 clip 名（否则每帧都会重启一次尸体），缺失 clip 回落 `idle` 时按 (文件, 状态) 报一次警告 —— 这类 bug 之所以能藏住，就是因为回落没有声音。

## 出土的僵尸"瞬间出现"：它被画在草坪之前，于是被草皮整格盖住
- **现象**：升起的僵尸靠负高度往下挪、且在**场景之前**绘制（`renderRisingZombies`），想法是"让草坪盖住还埋着的部分"。但草皮是不透明的整格贴图、又在这之后提交，深度测试还是关的 —— 结果是**整只僵尸**被自己那格草皮盖住：爬的 1 秒里什么都看不见，高度归零那一帧"啪"地站好。同一处的 `zombie_rise` 粒子是 20~40 只乱飞的 `zombiearm`，看起来就是半血断臂。
- **定论**：**画在草坪之后，用裁剪线露出**：每只升起的僵尸按它那一格的**地平线**（格子下沿）裁掉地下部分，裁剪线随进度从头顶扫到地平线；起始深度改成"整个人都埋住"（`PvzceConstants.ZOMBIE_RISE_DEPTH_CELLS`，两侧共用的那个数），并且 `beginRise()` 立刻写高度，spawn 包里带的就已经是"埋着"的状态（否则镜像会先用 3 个 tick 把站姿滑到埋姿）。裁剪线只在 **climb** 上走，身体比手臂晚 0.3 秒开始 —— 顺序就是原版的：先一只手，再整个人。**手臂不再是粒子**：它按这条上升时钟画（`zombie_rise` 粒子与它的定义一并删除），因为粒子走墙钟，暂停的关卡里它会继续挥手。

## 转了角度的粒子被采样成一个像素
- **现象**：`PvzceClient.drawTextureQuad` 的 UV 单位是**像素**（动画 JSON 的写法），而 `ParticleEngine` 的旋转分支传的是 0..1 —— 于是每颗粒子都在采样 1 像素的方框再把它拉满整个四边形，所有**会旋转**的抛掷物（断臂、小推车甩出去的头、碎片）都变成一条纯色细线。不旋转的粒子走另一条路径，所以一直没被发现。
- **定论**：旋转分支按贴图自己的像素尺寸传 UV（尺寸从 `TextureManager` 取，取不到就 1x1 让下面的兜底去报缺贴图）。

## 墓碑瞬间出现、墓碑吞噬者原地啃
- **现象**：`grave_spawner` 每 1.5 秒种一座墓碑，`placeGrave` 直接写格子、客户端下一帧就画出来；墓碑吞噬者啃的 4 秒里墓碑一动不动，植物也站在原地。
- **定论**：两者都是"元素不在自己格子里"这同一幅画（往下挪、在格子下沿裁掉），所以共用 `SceneShifts`：**墓碑钻出**由客户端的时钟驱动（0.35 秒），只有"这局中途被改成的格子"才动画（开局就画好的墓碑与全量重同步都不算 —— 判定在 `ClientLevel`，只有它分得清），服务端只补一撮泥土；**被啃的墓碑往下沉**，下沉量是那棵植物**自己的高度**（`GraveBusterCapability.SINK_DEPTH_CELLS`）：进度只有一份，随实体同步走，存档恢复之后接着啃也对，植物半路被吃掉时格子立刻变回完整的墓碑（每帧重算，不存状态）。

## 弹坑：贴图是占位图，而且没有任何东西会造出弹坑
- **现象**：`textures/scene/crater.png` 是一张 64x64 的 "CRT" 占位图（`crater_2.png` 同样是占位、且无人引用），而且全仓库没有一处创建弹坑 —— 只有恢复计时器在读它。毁灭菇炸完什么都不留。
- **定论**：换成原版美术（`crater.png` 是 180x61 的**左右两版**，白天与夜里各一张，`crater_fading.png` 是"正在填回去"的同一对）并按 90x61 像素的原始尺寸居中画（比一格宽、比一格矮，塞进一格会被压扁）；`ExplosiveCapability.leaves_crater`（毁灭菇开着）让爆炸把覆盖到的裸地变成弹坑，footprint 与 `damageArea` 同一套算法；**恢复的淡出是地形而不是客户端特效**：`tickScene` 在 `crater_recovery` 的最后一秒把格子换成 `pvzce:crater_fading`，到点变回草坪 —— 能种什么由地形决定，所以客户端只画它被告知的那一格。
- **顺带**：场景元素多了可选的美术块（`SceneElementArt`：贴图、夜间变体、尺寸、**underlay**）。`underlay` 写的是**元素 id**：墓碑与弹坑的美术只有石头和洞口，底下那层草坪必须写出来，而且必须是元素 —— 资源包换草坪时它跟着换，关卡隐藏草坪时它跟着隐藏。

## 关卡背景与"隐藏的场景元素"
- **现象**：背景是写死的 `LevelStage.BACKGROUND_TEXTURE`（只在棋盘与选卡页各画一次），关卡无法指定；而一格只画它自己的元素，所以一个"背景图里已经画好草坪"的关卡没法让程序别在它上面再盖一层草坪。
- **定论**：`LevelDef` 多两个字段，随 `LevelPayload` 下发（`PROTOCOL_VERSION` 18→19，`PacketProtocolTest` 的字节转储同步更新）。`background` 是**贴图 id**：原版每个舞台都是同一张 1400x600、棋盘位置也一样，所以换背景就是换一张图，`LevelStage` 的几何一个数都不动；原版七张可用背景一并导入（JPG 转 PNG）。`hidden_scene_elements` 每项是元素 id 或 `#` 开头的标签，命中的格子**整个不画**（露出背景图），由客户端的 `SceneVisibility` 判定；草地外边那圈 margin 也一起关掉，否则隐藏草坪的关卡会被一圈绿框围住。编辑器新开一页「外观」（`LookPage`，用 `FormLayout` 的列布局）放这两个字段 —— 没放进 `InfoPage`，因为那一页在 720p 下本来就排不下（它的最后几行已经落在面板外）。
- **墓碑美术的去草坪**：四种墓碑原本把草坪**烤进**了贴图（草 + 石头），隐藏草坪的关卡里就会在每座墓碑下露出四块绿方块。贴图改成只留石头与它脚下的土堆，草坪交给 `underlay`。

## 僵尸掉下来的零件按"它在僵尸身上的大小"画（并给粒子加了 `aspect`）
- **现象**：粒子的四边形一律是正方形，所以 26×50 的手臂被拉宽 1.4 倍、66×123 的铁纱门被压扁成方块；路障更离谱 —— `zombie_traffic_cone` 的 `scale` 是 **1.5**，画出来比戴在僵尸头上时大 3.5 倍（玩家截图里那个占满两格的橙色路障）。同一张头颅贴图在不同定义里还有 0.4 与 0.8 两个尺寸，小推车甩出去的头因此是普通死亡头颅的两倍。
- **定论**：`ParticleLook` 增加 `aspect`（宽度 = `scale × aspect`，不写＝正方形），旋转分支的四个角也按各自的半宽半高算。僵尸零件的尺寸一律改成**它在模型上的大小**（模型被拟合进 0.95 格，所以比像素尺寸小一圈）：路障 `0.425`/`1.294`、铁桶 `0.499`/`1.158`、手臂 `0.5`/`0.65`、头颅 `0.354`/`1.38`（三种头的定义统一到这个数）、铁纱门 `0.75`/`0.671`、旗帜 `0.499`/`1.158`。出土那只手臂也跟着改成同一个尺寸（同一个精灵不该有两个大小）。顺带修掉 `zombie_head_light` 的 `scale: -0.8` —— 负尺寸被引擎夹到 0.01，这个定义从来画不出东西。

## 1-1~2-5 用自己的背景图，草坪不再画第二遍
- **现象**：背景一直是写死的 `background1unsodded`（未铺草的院子），草坪靠每格贴图铺出来 —— 于是背景图里那片院子与贴出来的草坪叠在一起，草地网格的接缝看得见，而且 1-10/2-x 是夜关却用白天的院子配夜色调。
- **定论**：这 15 关写 `background`（1-1~1-9 用 `background1` 白天铺草版，1-10 与 2-x 用 `background2` 夜晚版）＋ `hidden_scene_elements: ["pvzce:grass"]`（地形照旧写在 `scene` 里，它决定哪里能种；只是不再画）。草坪外那圈 margin 一并关掉。**1-10 是一个特例**：它的 `day_length` 是 3600（先亮一分钟再入夜），而背景只能是一张图，所以它的白天那一分钟会看到夜空与月亮 —— 想改就把它换成 `background1`（或把白天缩掉）。

## 打僵尸像在下太阳、啃植物冒紫雾、阳光的光圈不在阳光身上
- **现象**：三处特效都用错了定义。**被攻击**时服务端发的是 `pvzce:starburst`（25 颗金色加法混合的星星，本来是星果与结算页用的），于是每一发豌豆命中都像下了一场太阳；**啃植物**时发的是 `pvzce:chomp`（`puff_splat`：小喷菇那 8 团孢子），任何僵尸咬任何植物都在草坪上留一团紫雾；**收集阳光**时 `pickup_effect` 打在 `drop.cellY()` 上 —— 而掉落物的高度在 `height()` 里（下落中的太阳最高 2.2 格、向日葵刚吐出来的在 0.5 格），所以光圈落在草地上，运气不好离太阳两格远。
- **定论**：**命中特效按发射物的定义走**（`ProjectileDef.impact_particle`，豌豆/雪豆/玉米/西瓜/黄油/卷心菜/大喷菇/小喷菇各一个 `*_splat`，用的就是那发子弹自己的精灵；原版为每种子弹各画了一张 splat，那批图不在本仓库里）。撞在**护甲**上时同样放这发子弹的 splat（`ArmorCapability` 现在把 projectile 的 `impact_particle` 传进 `absorb`），只有"不是子弹的重击"（保龄球）才留 `HIT_SPARK`。**啃植物只剩声音**：那一口本来就没有粒子，紫色那团是小喷菇的。**收集光圈打在掉落物自己的位置上**（`cellY + height`），太阳在半空就亮在半空。
- **顺带**：`pvzce:strburst_2` 与 `pvzce:starburst_1` 这两个 id 被 `PvzceParticles.PEA_SPLAT_BITS` / `KERNEL_SPLAT` 借用成"豌豆/玉米的碎屑"，而它们其实是结算页的光线贴图 —— 常量还在，但命中路径不再经过它们。

## 2-5：最后一波不是每座墓碑都出僵尸
- **现象**：最后一波会开**当时站着**的每一座墓碑（`LevelServer.riseGraveZombies`，只在最后一波宣告的那一 tick 跑一次），而 `grave_spawner` 在它**之后**还在补墓碑（每来一波目标 +1，每 tick 最多补 2 座）—— 补出来的那些是"永远开不了的墓碑"，玩家看上去就是"最后一波只有少数墓碑出了僵尸"。测试 `everyStandingGraveOpensOnWhackAZombiesLastWave` 复现了：场上 10 座、只开了 9 座。
- **定论**：**最后一波释放之后不再补墓碑**（`GraveSpawnerMechanic.tick` 一开头就问 `level.wavesReleased()`）。之前那条"墓碑继续回来，结束的只是僵尸的涓流"是有意的，但它与"最后一波高潮是满场开墓"直接冲突：一座开不了的墓碑和开过的一模一样，玩家只会读成"这一座没出僵尸"。现在草坪上不会再长出没开过的墓碑，而那 +1 座（本来属于最后一波的目标增长）也就不再出现 —— 用一座墓碑换"每一座都开了"是划算的。

## 2-5 的节奏：走得更快、出土更快、阳光多掉一点
- **现象**：2-5 的僵尸走 2.2 倍速，但"打地鼠"的密度下还是慢；出土固定 1 秒（`ZombieEntity.RISE_TICKS` 是编译期常量）；僵尸掉阳光 3%。
- **定论**：`zombie_speed_multiplier` 2.2 → **2.6**，`zombie_sun_drop_chance` 0.03 → **0.05**；出土速度新开一条规则 **`pvzce:zombie_rise_ticks`**（缺省 60，2-5 写 **40**）—— 它是节奏而不是常量：一座一座开的关卡要看得见那口气，满场同时开的关卡只想快点结束。规则值由 `LevelServer.raiseZombieFromGrave` 读出来传给 `ZombieEntity.beginRise(ticks)`，客户端不用改：它读的是高度换算出来的"还埋着多少"，与时长无关。

## 最后一波：墓碑跟着旗子一起开；墓碑边缘的绿边；1-1~1-3 的背景；影子造成的悬空感
- **墓碑开得太晚**：最后一波的旗子在 `warning_ticks`（2-5 是 180 tick）之前就出现，而 `riseGraveZombies` 挂在**到达**那一 tick，于是玩家看完旗子还要等三秒。现在开墓挂在**警告**（`announceWaveWarning`，旗子亮起的那一 tick），到达那 tick 只留 awOoga；没有警告窗口的最后一波仍在到达时开（两者同一 tick）。
- **墓碑边缘的绿边**：上一步按颜色抠掉烤进去的草坪时留下了原草坪的抗锯齿边（约 1–2 像素的绿圈）。再腐蚀 2 像素（画布是源美术的 2.6 倍，所以远不到一个游戏像素），绿色像素从 1300~1850 降到 100~270（剩下的都是土堆上本来就有的草簇）。
- **1-1/1-2/1-3 的背景**：这三关的棋盘不是满草坪 —— 1-1 是 9x1、1-2/1-3 是 9x3，只有那一条草皮，其余是没铺草的院子。所以它们的背景只能是 `background1unsodded` 并且**不隐藏**草坪（草皮正是这三关自己画出来的）；1-4 起才是满草坪，用 `background1` 并隐藏。
- **悬空感**：影子画在 `drawY - 0.46`，而精灵的脚在 `anchorLift`（0.36）处 —— 接触点比脚低 0.1 格，在原版那张有明暗和割草纹的草坪上就成"浮在另一块灰色东西上面"。影子改用与动画路径同一个 `anchorLift` 作为接触点（并把植物影子的 alpha 从 0.34 提到 0.4）。

## 尺寸与"一个尸体一颗头"
- **植物 85%**：29 个植物定义写上 `render_scale: 0.85`（它是"这件内容自己多大"，两轴同倍，锚点在脚下，所以只是美术变小、脚不动）。
- **小推车 120%**：`MowerClientMechanic` 的 `MOWER_RENDER_SCALE = 1.2`（reanim 被拟合进 1.0x0.62 格，按原尺寸画在旁边那只即将被碾的僵尸旁边像玩具）。
- **小推车 / 烧死的僵尸各掉两颗头**：小推车的 `mow()` 自己发了"被碾的头 + 被碾的手臂"，而死亡路径又照常发一颗普通头（半血断臂再补一条手臂）；灰烬击杀则是尸体换成焦尸模型（本来就没有头），却又掉一颗头。现在**掉什么由这一击的伤害类型说了算**：`pvzce:mower` 写 `dismembers: true`（新的 `DamageTypeDef` 字段），死亡时改发"被碾的头 + 被碾的手臂"，并且半血断臂与普通头都跳过；`burns` 的击杀则什么都不掉（焦尸自带头的样子）。一件事实一个出处：`mow()` 里那两行删掉了。

## 手套：拿在手上的植物跟着鼠标（A 方案）
- **现象**：`carriedPlantId` 只有服务端知道，所以拿起植物后玩家手上什么都没有 —— 手套看起来像"点了没反应"；而冷却的记账方式又取决于两次点击能否配上对，一旦中间被打断，卡面就停在说不清的状态（玩家报的"一直显示冷却"）。
- **定论**：新增 `CarrySyncS2C(plantId)`（空 = 没拿着；协议 21），服务端在**拿起 / 放下 / 忘记**三处各发一次，客户端存进 `ClientLevel.carriedPlant()`，`InGameScreen.renderCarriedPlant()` 把它画在**光标**上（不是悬停的格子上：手里那株还不属于任何一格，格子是它*将要*去的地方）。三条打断路径全部走 `clearCarry()`：超时、拿着的植物被吃掉、去点别的卡或别的工具（`useToolInternal` 开头的 `abandonCarry()`）；`clearCarry()` 顺手给手套起冷却，于是"拿着不放"也会正常结算，卡面不会再停在一个说不清的状态。
- 冷却语义保持不变并写死为一句：**拿起**算一次使用、**放下**不算、**被打断不算**（打断时由 `clearCarry` 结这一次）。

## 手套（补）：手上画的是缺失贴图，且必须再点一次手套才能放下
- **缺失贴图**：幽灵图原本走 `EntityTextures.forEntity(defId, PLANT)`，而植物的美术是动画、定义里没有单张精灵，于是查到的是缺失贴图格。改成用**卡槽自己的图标查找**（`CardPainter.icon(slot)`）—— 就是玩家刚刚点的那张卡的图；拿不到卡号时（存档在搬运中途被恢复）按"哪个卡槽的内容是这株植物"反查，走的是同一个 `SlotResolver`。
- **必须再点一次手套**：`spendSelectedCard` 在点击后会 `selectedCard = -1`（一条注释解释了原因：工具卡点一次就归位），于是第二次点击时"没有选中任何卡"，客户端根本不发 `UseToolC2S`。现在客户端记住**这次搬运是从哪个卡槽开始的**（`carrySlot`，拿起时记、搬运结束或不再携带时清），只要手上还拿着东西，点草地就发那个槽的 `UseToolC2S` —— 放下是同一动作的后半段，与当前选中什么无关；服务端照旧重新校验那是不是手套。

## 手套（再补）：为什么"记住卡槽"没生效，以及改成自动重新选中
- **上一版的错**：`carrySlot` 是在渲染路径里"`carriedPlant` 为空就清掉"的，而渲染路径每帧都跑 —— 包括**拿起点击之后、服务端还没回 `CarrySyncS2C` 的那一帧**：刚记下的卡槽立刻被自己抹掉了，所以第二次点击依然什么都不发，玩家只能重新点一次手套。
- **定论**：改成只在**看到状态变化**时动（`syncCarry()` 比较上一帧的服务端状态）。拿起时**自动重新选中手套卡**（玩家手上拿着东西，亮着的卡就是它的可见反馈，而点草地走的就是和第一次点击完全相同的那条路）；搬运结束时连同选中一起放下。

## 手套（三补）：放下后不取消选中，以及"用满 3 次后无限冷却"
- **放下后手套还亮着**：放下那一步走的是 `carrySlot` 分支，它 `return` 之前没有清 `selectedCard`，于是卡面一直亮着，下一次点击又会去拿脚下的植物。现在放下时同时取消选中；`syncCarry()` 看到搬运结束（不管是放下、被吃还是超时）也会把选中一起放下。
- **用几次之后永久冷却**：`pvzce:glove` 的工具定义里写着 **`uses: 3`** —— 手套是"一关只能搬三次"的限量道具，用完 `hasUsesLeft()` 为假，`ready()` 永远为假，卡面就一直灰着，看起来正是"无限冷却"（空卡和卡住的样子一模一样）。改成 **`uses: -1`（不限次数）**：原版的手套/铲子只有冷却、没有次数。测试 `GloveMoveTest` 里那条"拿起扣一次使用"的断言随之改成"拿起不扣次数"，并直接盯住定义值，免得这个数字再被人写回去。

## 背包与选卡：按原版的登记顺序排，而不是字母序
- **现象**：两个页面都从 `SeedOptions.allCards()` 拿卡，而那里是 `SLOT_TYPES.keySet().stream().sorted()` —— 于是背包里排在最前的是 Wall-nut、豌豆射手排第三，"每个人都有的第一张卡"永远不在第一个。
- **定论**：植物定义新增 **`order`**（缺省 1000），值就是**原版图鉴的编号**（豌豆射手 1、向日葵 2、樱桃炸弹 3……冬西瓜 45；`bowling_nut` 是迷你游戏道具，不给编号，排在最后）；`allCards()` 改成按 `(order, id)` 排，非植物卡按**注册顺序**排在植物之后的一个区段里。顺序只有一个出处：两个页面都直接吃这个列表，改这里两边一起变。
- **测试**：`SeedOptionsOrderTest` 盯住"前五张就是原版最先给的五张"、晚期植物的相对位置，以及"没有编号的植物排在最后"。

# 夜晚后半段（2-6 ~ 2-10）

## 夜关的墓碑一直是手写坐标，而原版是开局随机撒的
- **现象**：2-1 / 2-4 的墓碑写在 `scene` 里，一处一格（`"pvzce:grave": ["6,0"]`）。这与原版是两件事：原版每一关开局把墓碑**随机撒在远离房子的那半场**，同一关每次重开位置都不同，所以"要绕开哪几格"是每局都要重读的信息；手写坐标把这件事变成了一张固定的图。补丁式地"多写几种布局"也不行 —— 关卡文件里没有"七座，随便哪"这种写法。
- **定论**：新增关卡机制 **`pvzce:grave_field`**（`count` / `min_x` / `max_x` / `region` / `designs`），在 `onLevelCreated`（关卡构造完成、棋盘已经铺好之后）把墓碑撒下去。随机的来源是**关卡自己的 `random`**（与掉阳光、分线同一个源），所以撒出来的草坪与其它随机一致；它没有运行状态、也不写存档 —— **棋盘本身就是状态**（`saveScene` 写全部格子，恢复时整块覆盖），续档不会重撒、也不会与旧墓碑叠加。
- **撒的实现只有一处**：`GraveScatter`（`common/level/mechanic/`），`grave_spawner` 补墓碑也走它。实现是**洗牌区域内的格子后逐个 `placeGrave`**，而不是"掷一个点、撞上已有墓碑就放弃"：2-10 是 13 座墓碑落在 5×5 的半场里（25 格），掷点重试实测只撒得出 **8** 座，而"撞上就放弃"在持续补墓碑的路径上是有意的（下一 tick 会重数）。
- 2-1 / 2-4 改成用它（**墓碑的格子还给草坪** —— 手写墓碑时那几格是 `scene` 里的墓碑、不是草坪，改完 `9×5` 才是完整的草坪），2-6~2-10 从一开始就用它。
- **同一条事实的另一半没变**：墓碑是障碍物，最后一波由 `pvzce:graves_spawn_night` 一次性开墓；"会补、持续冒怪"仍然是 `grave_spawner` 的事，两个机制可以同时出现（2-5 就是）。

## 夜晚的植物谱系缺两块：胆小菇与寒冰菇
- **现象**：原版 Night 区的奖励链是 2-6 胆小菇 / 2-7 寒冰菇 / 2-8 毁灭菇，而本项目 2-6 与 2-7 没有东西可发；`refer/anim` 里两个植物的 reanim 一直都在，行为却无处安放 —— "僵尸靠近就缩起来不射"与"全屏冻住"都不是已有能力能表达的。
- **定论**：两个植物 + **两个新行为**，都按"能组合就不特判"的形状加：
  - **胆小菇**（`pvzce:scaredy_shroom`，25 阳光 / 7.5 秒冷却 / 300 血 / 整行射程）不是第二种射手：`ShooterCapability` 多一个 `hide_within`（格，缺省 0 = 从不躲），僵尸进到一格以内就发布 `hide` 并**完全停止射击**（连冷却都不走）。"它会打谁"与"它怕谁"共用同一个 `canBeHitByGround` 判据，所以被魅惑的僵尸与天上的气球都不吓它。模型里的 `hide`（低头，一次性）与 `hide_loop`（保持）由 clip 自己的 `on_end` 串起来，服务端只知道"现在躲着"。
  - **寒冰菇**（`pvzce:ice_shroom`，75 阳光 / 50 秒冷却 / 100 血）的能力是 **`pvzce:freeze_all`**：同一 tick 给**每一行**的每只僵尸上 `IMMOBILIZED` 3.25 秒、20 点 `pvzce:splash` 伤害、16 秒 50% 寒冷，然后植物消失（它的美术里没有"爆炸"这一姿态）。形状是"行"而不是半径 —— 一个够覆盖 9 列的半径在更宽的草坪上会短一截，而"全场"本来就不是一个距离。
  - **"冻不住谁"是标签**：`#pvzce:freeze_immune`（内置气球僵尸、矿工僵尸）里的僵尸照吃伤害与寒冷，只是不被冻住。原版对它们的区别正是这两件事分开，而"哪些僵尸冻不住"是关于内容的一句话，不该由寒冰菇的代码记住。

## 寒冷只减速了腿，没有减速嘴
- **现象**：`ZombieStatus.SLOW` 只有一处读法 —— `ZombieEntity.moveSpeed` 乘 `magnitude`。啃咬间隔是 `def.biteIntervalTicks()`，与状态无关，所以被寒冰射手打中的僵尸走得慢了，却仍然按原速啃植物。原版的"寒冷"是一个状态同时减半移动与啃咬。
- **定论**：啃咬间隔改为 `ZombieEntity.biteIntervalTicks()`（`def` 的数 ÷ `magnitude`），两处 `biteCooldown = ...` 都走它。没有第二个计时器 —— "多久咬一口"本来就只有这一个倒计时。

## 夜晚新僵尸：橄榄球、跳舞与伴舞
- **现象**：Night 区在原版里引入五种僵尸，本项目此前只有读报（2-1）与纱门（2-3），2-6 起的橄榄球、舞王与伴舞都没有；没有它们，2-6~2-10 只能拿更晚世界的僵尸顶替（巨人、气球、矿工），与原版对不上。
- **定论**：三个定义 + 一个能力（美术全部来自原版自己的 reanim，走 `tools/reanim_to_pvzce_all.py`）：
  - **橄榄球僵尸**（`football_zombie`）：200 身体 + **1400 面罩**（`position: top`，与铁桶同一条"平射先撞没有盾的帽子"规则）、**0.43 格/秒**（原版约普通僵尸的 1.88 倍）。面罩三档磨损来自 `Zombie_football_helmet{,2,3}.png` —— 与前两个一样是"未被任何 track 引用的破损贴图"，所以走 `damage_states`；它的 `zombie_football_upperbody2/3`（球衣的另外两个破损档）被 **track 过滤掉**：本项目的僵尸不画身体破损，断臂与掉头另有其道。
  - **跳舞僵尸**（`dancing_zombie`，500 血）+ **召唤能力 `pvzce:summon_dancers`**：以 0.67 格/秒**月亮步**进场（`moonwalk` clip），走到 `summon_at_x` 停下、举手 48 tick，然后按原版的十字队形招出 4 名伴舞（同排前一格 / 同排后一格 / 上一排 / 下一排），此后每 120 tick 检查一次队形、缺人就补。**"哪个位置缺人"是每 tick 按位置重新数出来的**，不是记住自己生成过哪些实体：实体 id 不写进存档，记住的那份名单读档后会指向不存在的实体，舞王会再招一整队。伴舞生成在**舞王当前的队伍**上，所以被魅惑的舞王招出来的伴舞天然帮植物打。
  - **伴舞僵尸**（`backup_dancer`）：200 血、0.18 格/秒（队形的节奏），没有装备、没有特殊行为。
  - **`refer/anim` 里有四个跳舞文件，画的是同一个角色的不同版本**（`Zombie_Jackson` = 2009 年的 MJ 造型、`Zombie_disco` = 后来替换的 afro 造型、`Zombie_dancer` = 第三种服装、`Zombie_backup` = 伴舞）。原版画在草坪上的是 `Zombie_disco`（它也是唯一带 `anim_moonwalk` 的那个），所以舞王取它；`Zombie_dancer`/`Zombie_Jackson` 不使用。

## 传送带没有"这张卡一共发几张"
- **现象**：`LevelBelt.BeltCard` 只有 `id` + `weight`，而原版 2-10 的墓碑破坏者是 **Max Count 13**（草坪上正好 13 个墓碑，第 14 张没有用处）—— 关卡文件里没有地方写这件事，传送带也没有记账的地方。
- **定论**：`BeltCard` 多一个可选 `max_count`（缺省 = 不限），计数由**传送带自己**持有（`ConveyorBelt.dealt`，**发出就算**：用掉没用掉都算，因为这说的是"发过几张"而不是"场上还有几张"）。发满的卡退出池子、其余权重重新归一；一个卡都发不出来时传送带停摆而不是空转。计数与队列一起进 `level.dat`，续档不会补发第 14 张。`LevelValidator` 报 `max_count: 0`（写出来却永远发不到的卡）。2-10 是唯一用到它的关卡。

## 一声"便条"值多少：2-9 与原版同形
- **现象**：原版 2-9 的首通奖励不是植物，是僵尸们送来的一张便条（便条之后才是 2-10 的传送带关）。本项目没有"便条"这种东西。
- **定论**：照 1-9 的先例 —— **不写 `rewards` 块**，走 `LevelRewards.DEFAULT`（首通无额外奖励、重复 100 金币、掉银币 25%），关卡描述里提一句"打完这一关，僵尸们会送来一张便条"。不新增物品，也不新增界面。

# 体验修正（选卡 / 锤子 / 孢子 / 魅惑 / 缩头 / 续档音乐 / 冰锥）

## 选卡页记得上一局的卡，而"我上次选了什么"不是关卡的一部分
- **现象**：`PvzceClient` 按 `世界|关卡` 记住玩家上次的选卡（`config/pvzce-seed-selections.json`），下次打开这一关的选卡页就把它填回去；没有记录时退一步"卡池的前 N 张"。于是"我想换一套打法"要先一张一张把上一局的卡取消掉，"第一次进这一关"也是别人（上一次的自己）替玩家选的。
- **定论**：**选卡页一律从空开始**，只保留关卡自己钉死的卡（那是关卡的设计，不是玩家的选择）。删掉整套记忆：字段、文件读写、`seedSelectionOrDefault` 与它的四个调用点（列表进入、存档提示框重开、暂停菜单重开、重启同一关）。同时把"正在进行的这一局的卡"与"下一局要选的卡"分开：前者由存档恢复（`SeedSelection.plan` 的 `loadSave` 分支），后者永远是空的。

## 木槌：30 秒冷却、50 阳光 → 20 秒、免费
- **现象**：`tools/hammer.json` 写的是 `use_cost.resources.pvzce:sun = 50` + `cooldown = 1800`（卡片自己的 `slots/hammer.json` 也是 1800）。2-5 那一关把它覆盖成"无冷却、不花阳光"，于是同一把锤子在两处的手感差得很远。
- **定论**：`use_cost` 清空、`cooldown` 与卡槽的冷却都改成 **1200 tick（20 秒）**；2-5 的关卡覆盖照旧（那一关的鼠标就是锤子，本来就不该有价格与冷却）。测试随之改成盯住新数字。

## 小喷菇的孢子是灰白色的，落地还炸出一团紫色的"啃咬云"
- **现象**：孢子贴图用的是原版 `Puff.reanim` 那套灰白烟雾的一帧，而命中特效指向 `pvzce:puff_splat` —— 那是**啃咬**（`PvzceParticles.CHOMP`）用的八个紫色大孢子团，于是每一发落地看起来都像被咬了一口。
- **定论**：两处都换成"孢子本来的样子"：孢子改用原版孢子粒子的紫色贴图（`refer/im7/particles/PuffShroom_puff1.png`，54×53 画布），命中特效新建 `pvzce:spore_splat`（三颗小孢子、0.2 秒淡出、轻微外扩）。`pvzce:puff_splat` 留给大嘴花与啃咬，两个效果不再共用一份定义。

## 被魅惑的僵尸继续朝房子走
- **现象**：`isCharmed()` 分支只改了"不吃植物、改咬僵尸"，移动方向仍然是 `cellX() - speed`，索敌也仍然只看左边。于是被魅惑的僵尸背对着自己要走的方向倒着走，走到房子前站着不动（`checkReachedLeft` 对它不上报，它就一直留在最左边）。
- **定论**：方向收敛成一处 —— `ZombieEntity.walkDirection()`（`-1` 朝房子 / `+1` 被魅惑）。移动、索敌（`enemyZombieInFront` 用同一个方向乘 delta）、离场判定（`checkReachedEdge`：往回走的从右缘离场并移除）都读它。**客户端把整只立绘水平镜像**：`AnimationPlayback.flipX`，控制器后端翻转每个 quad 的 x（逐角保留自己的 UV，绕序反过来无所谓——面剔除本来就是关的），帧序列后端交换 u0/u1，平面贴图兜底路径换 `drawTextureRegion` 的 u 区间。不镜像的话它会倒着走完整条车道。

## 大喷菇的喷雾无视一切护甲，于是橄榄球僵尸和普通僵尸一样脆
- **现象**：喷雾的伤害类型 `pvzce:spray` 写着 `ignores_armor: true`，`ArmorCapability` 根本不被征询 —— 铁桶、路障、橄榄球面罩全都不吃伤害。原版的喷雾是**穿门不穿帽**：纱门/报纸挡不住气体，帽子照样吸收。
- **定论**：`DamageTypeDef` 多一个 **`ignores_front_armor`**（缺省 false），`spray` 改成 `ignores_armor: false, ignores_front_armor: true`；`ArmorCapability` 在两条命中路径上都读它（`onProjectileHit` 直接按它选槽位，另加一个带类型的 `onImpact` 重载）。于是喷雾穿过 `front` 的那一件，落回 `top` 的那一件上。

## 用过一次铲子之后，点植物就铲掉
- **现象**：`InGameScreen.spendSelectedCard` 对**每一个**工具都记下 `carrySlot`（那是手套"拿着植物等第二下点击"用的），而清除它的 `syncCarry` 只在**携带的植物发生变化**时才动 —— 铲子从不携带植物，"空 → 空"不算变化，于是这个槽位永远留着。此后板子上任何一次点击都走"放下手里那株"的分支，把 `carrySlot` 里的铲子再发一次：没有选卡、卡面也不亮，但植物照样被铲掉。重进关卡时界面重建，`carrySlot` 归零，所以它"自己好了"。
- **定论**：只有会拿起植物的工具才留下"这一手还没完"（`carrySlotFor` = 手套才记，铲子/锤子立刻归 -1，测试钉住这条）；同时 `syncCarry` 改成**每帧**都按服务端的携带状态对齐（不再只对变化作出反应），槽位丢了也能从携带的植物 id 反查回来（`cardGranting`），所以丢槽位不会退化成"必须再点一次手套"。

## 手套抬起植物之后放不下：左下角说"不是工具卡"
- **现象**：手套的第一下把植物拿起来，第二下点草坪却放不下，服务端回一句"不是工具卡。"，植物一直拿在手上（只能等超时）。根因是**第二下用的卡不对**：`InGameScreen` 原本把"这次搬运是从哪个卡槽开始的"记在 `carrySlot` 里，而那一版为了修"点过一次铲子之后点植物就铲掉"把清除逻辑改成了"每帧按携带状态对齐"，于是抬起的下一帧（服务端还没回 `CarrySyncS2C`）槽位就被清掉了；等到携带状态真的到达，回填用的却是 `cardGranting(carried)` —— 那个查的是**携带的那株植物自己的卡**（一张植物卡），于是第二下把植物卡发上了工具路径，服务端自然回答"不是工具卡"。
- **定论**：**这一手归哪张卡不需要记**：两次点击都发给手套自己的卡槽，而它在卡栏里查（`gloveSlotIn` / `gloveInBar`，一场最多一张手套）。判定"现在手上有没有植物"用服务端的 `ClientLevel.carriedPlant()`（本来就画着那只跟随光标的幽灵），于是没有本地状态可以过期：没拿着植物时点击走普通路径，拿着时点击就是把植物放下。`carrySlot` 字段、`carrySlotFor` 与它们的分支一并删除，测试改成盯住"放下发给手套、不发给植物卡"这条查找规则。

## 毁灭菇的弹坑是整个爆炸范围，而不是它脚下那一格
- **现象**：`ExplosiveCapability` 把弹坑的覆盖范围直接用了 `blastRadius`（毁灭菇 = 3.0 → 7×7 格），于是炸过之后半个草坪都变成不能种的弹坑，恢复期长达 `crater_recovery`。
- **定论**：弹坑是**植物自己那一格**（`CRATER_RADIUS = 0.5`，与土豆雷"半径 0.5 = 自己这格"同一个读法），与爆炸范围解耦 —— 原版的毁灭菇留下的就是一个下沉的格子（那也是"把它种在哪"这个决定真正的代价）。测试逐格断言：除它自己那一格外，整块草坪都不是弹坑。

## 胆小菇只有半个向日葵高，缩起头之后就再也不动了
- **现象**：两件事。其一，它被拟合进"小蘑菇"的 0.38 格框，而它的 reanim 比小喷菇高近一倍（71.3px vs 38px），照原版比例它该有 0.726 格。其二，`hide` clip 写的是 `"on_end": "hide_loop"`，而 `AnimationClip.OnEnd.parse` 只认 `idle` / `next`，**其它值一律当 hold** —— 于是低头那一下播完就停在最后一帧，看起来就是"缩进去以后没有动画了"。同一条静默回退还压着墓碑破坏者（`on_end: chew`，落地之后不嚼）与阳光菇（`grow → idle_big`）。
- **定论**：`AnimationResourceLoader` 现在把 `on_end` 里的**clip 名字**解析成 `NEXT` + 该名字（`idle`/`next`/`hold` 三个关键字照旧），名字在这个文件里不存在时才退回 hold **并打一行日志**（诊断"这个动画停住了"原先指向不了任何地方）。加载器测试用真实文件钉住 `scaredy_shroom.hide → hide_loop` 与 `grave_buster.idle → chew`，以及"名字写错 → hold"。胆小菇的框改成按原版比例算出来的 `SCAREDY_SHROOM_BOX`（0.530 × 0.726），寒冰菇从同一个"小蘑菇"框放回 `PLANT_BOX`（0.83 × 0.76）。

## 续档之后音乐变成 grasswalk
- **现象**：音乐是一串**事件**（`LevelDef.music.cues` 按 tick 发 `MusicEventS2C`），服务端的游标 `NextMusicCueIndex` 随存档保存，但"现在在放哪一首"没有任何地方记着。续一局打到一半的关卡时，游标已经越过了 0 tick 的那条 cue，客户端只按"进入关卡"播了默认曲（grasswalk），夜晚的 `moongrains` 再也不会来。
- **定论**：`LevelServer` 记下**当前曲目**（`currentMusicCue`：每发一条 cue 更新，`stop` 或无事件的 cue 清空），`restore` 时按保存的游标把 cue 表重放到该位置（而不是把曲目本身写进存档 —— 那会是关卡音乐块的第二份副本），`sendFullState` 在 init 之后把它作为一条 `MusicEventS2C` 重发。重发同曲在客户端是幂等的，所以顺带覆盖了"第二个玩家加入"与"同一局 resync"（`ServerMenuFlowTest` 断言 resync 不停任何轨道、只说当前曲目）。

## 舞王的召唤没有动画，而且补人补得太快
- **现象**：`SummonDancersCapability` 靠 `walkState()` 返回 `armraise`，但召唤期间它自己 `tickMovement` 返回 true —— **走路循环整个不跑**，而那是 `walkState` 唯一的调用方。于是举手这一拍被选中了却从没发布出去。补人的间隔还是 120 tick（2 秒），一队伴舞刚被清掉就又站满了，玩家永远清不完。
- **定论**：召唤期间由能力自己每 tick 发布 `ARM_RAISE`（与蓄力地雷每 tick 发布 `armed` 同一个做法），间隔默认与数据都改成 **1200 tick（20 秒）**：清掉一队之后有二十秒的窗口，这才是"他带来的是一次压力"而不是"打不完"。

## 寒冰菇只冻 3.25 秒，冻住的僵尸还在原地走路
- **现象**：`freeze_ticks` 是 195（3.25 秒）；`IMMOBILIZED` 只让服务端停止移动，客户端既不知道有这回事（`EntityUpdateS2C` 只有 `chilled`，那只是"变慢"），也没有任何画面 —— 被冻住的僵尸原地走完走路循环，看起来像卡住了。
- **定论**：冻结改成 **6 秒**，并把 `frozen` 作为一个新的状态位发出去（`EntityUpdateS2C.frozen`，协议 21 → 22；`ZombieEntity.frozen()` = `IMMOBILIZED` 且还活着）。客户端据此做两件事：在僵尸脚下画原版 `icetrap` 那张冰锥图（`textures/entities/status/frozen_spikes`，0.675 × 0.375 格，z 在影子与僵尸之间），并**按住这条 clip 的时钟**（`AnimationPlayback.setPaused`：暂停时把时间锚在当前帧，解冻时把锚整体后移，动画从那一帧接着放）。测试断言更新包里的 `frozen` 与被冻/被豁免的两类僵尸。

# 传送带关卡也走选卡页（仅预览），2-10 换收尾主题曲

## 传送带关卡直接进关，于是它们的僵尸预览没有地方显示
- **现象**：1-5 / 1-10 / 2-10 的卡组由关卡自己发，所以客户端在 `enterLevelFromMenu` 里对它们直接 `requestFreshRunDirectly`（"选卡页会让玩家挑一套马上被丢掉的卡"）。代价是**这一屏也是唯一显示"这一关会来哪些僵尸"的地方**：关卡列表只有一行名字，于是这三个关卡的僵尸阵容在整个界面上看不到。
- **定论**：卡组没得选的关卡照样走选卡页，只是那一页是**仅预览过场** —— `ChooseSeedsScreen` 多一个输入 `dealsItsOwnCards`（客户端按机制问 `PvzceClient.dealsItsOwnCards`，与编辑器页签、服务端卡组用的是同一个答案），它和"固定卡填满卡槽"一起决定 `previewOnly`：画面板与卡池都不画、点击落在草坪上、播完开场对话后 2.1 秒自动开局（与 1-1 完全同一条路径）。四条入口（关卡列表、暂停菜单重开、存档提示框重开、编辑器测试）里那三段"传送带直接进"的特例随之删除，`openSeedSelectionForRestart` 只剩"取不到关卡信息"这一个回落。顺带删掉客户端那个随之失去调用点的 `hasNothingToChoose(LevelInfo)`（`SeedOptions.hasNothingToChoose` 仍是唯一判据）。
- 关卡的过场因此多了三样它本来就有、只是看不到的东西：草坪（按关卡自己的昼夜渲染）、开场对话、僵尸预览 —— 见 `UI切换与导航架构.md` §4。

## 2-10 的音乐是普通夜曲，不是收尾关的主题
- **现象**：2-10 是夜晚的最后一关、也是第三个传送带关卡，但音乐沿用了全夜通用的 `music/moongrains`；同类的 1-10（Day 区收尾的传送带关）用的是 `music/ultimate_battle`。
- **定论**：2-10 换成 `music/ultimate_battle`，与 1-10 同一首（收尾关就是这两个）。`tools/write_night_levels.py` 里也加了 `music` 参数（缺省仍是 `moongrains`），免得下次重生成时又漂回夜曲。

## 阳光掉落是一枚硬币：间隔随机到没有形状
> 本次重做（现状见 `架构-服务端.md` §4.7 经济）

- **现象**：天上掉的阳光是**每 tick 独立掷一次**（`rules.sun_spawn_chance`，1-1~1-9 写 0.0017）。平均值对得上"约十秒一颗"，但分布是几何分布：**一局 75 秒的 1-1 里可能只掉两颗，也可能掉十颗**，中间还能夹一次 30 秒的干旱与一次一秒三颗的爆发。原因是这份实现没有"上一颗什么时候掉的"这个状态 —— 掷骰子没有记忆，"平均十秒"只保证长期平均。
- **定论**：改成**区间计时器**。新规则 `pvzce:sun_spawn_interval_min` / `_max`（默认 480 / 720 = 8~12 秒）与 `sun_spawn_initial_ticks`（默认 300 = 首颗 5 秒，开局是唯一允许天空准时的时刻）；`SunDropClock` 在每次掉落时抽下一个间隔（含两端），倒计时**进关卡存档**，读档不会白送一颗。**`min = max = 0` 就是开关**（取代 `sun_spawn_chance: 0`），`sun_spawn_chance` 规则与其 13 处关卡引用一并删除。迁移时把 0.0017 换成**均值相同的区间**（1-1~1-4 用 420~660、长关卡 540~840、其余 480~720），所以这次改的是"间隔的形状"，不是收入。`SunDropClockTest` 钉住三件事：每次间隔都落在区间内、零区间一颗不掉、倒计时随存档往返。

## 出怪节奏只有一张固定表：清场之后只能干等
> 本次重做（现状见 `架构-服务端.md` §4.7.2）

- **现象**：波次表能写"第几秒来第几波、一波里每几秒出一只"，但**没法表达三件关卡真正需要的事**。其一，玩家把场上清空之后仍要等完作者写给"更慢的玩家"的倒计时 —— 快的人白等、慢的人刚好；其二，一波僵尸只能按写死的间隔涓流，打死一只不会让下一只来得更快，于是"剩六只却每五秒一只"；其三，一波的组成必须逐个写出，而"这一波值多少威胁"是另一回事（普通 1 分、铁桶 3 分、巨人 12 分）。
- **定论**：新增关卡机制 **`pvzce:wave_pacing`**（数据 `WavePacingData`，注册在 `LevelMechanics`，与 deck / mower 一样**有隐式默认**：不声明也拿到引擎默认节奏）。四种模式：`fixed`（现状）、`stockpile`（场上本波僵尸少于 `max_alive` 时按差额缩短间隔，到上限就停手）、`survival_ratio`（本波放完后，死亡达到 `kill_ratio` 就让下一波倒计时每 tick 多跑一拍）、`budget`（用点数在 `pool` 里随机组合，`entries` 作为兜底）。按**波次编号（从 1 开始）**的覆盖表选择"哪一波用哪个机制"，与波次页显示的编号一致。
- **清场奖励是默认行为**：`clear_reward_factor`（默认 3）在**场上无僵尸且上一波放完**时加速倒计时，但**前段不加速**（`clear_reward_grace_ticks`，默认 10 秒）—— 奖励是"少等一会儿"，不是"下一波立刻贴脸"。第一版把整段倒计时按 3 倍跑，结果 1-2 变成三波连发；缓冲窗口就是那次教训的产物。
- **每波倒计时的目标是冻结的**：目标在倒计时开始的那一 tick 定下（`nextWaveTargetTicks`），之后不再变。目标若在倒计时途中变小，而计数器被夹在目标上，这一波就**永远到不了终点** —— 这是"只出一波就不动了"的成因，也是本次唯一一个把整关跑成死循环的 bug。
- **`due` 判定要求倒计时真的跑过**：上一波还在放怪时计数器被冻结在 0，而 0 会被"到期"读成"等待结束"，于是后续每一波都在前一波被触发的下一 tick 瞬发。判定加上 `waveIntervalTicks > 0` 之后，放怪窗口与倒计时不再互相冒充。
- **等待的起算统一为"等待 + 1 拍"**：计数器在装填的下一拍才减、减到 0 时出怪，于是 **300 的间隔＝301 拍、1200 的死亡门＝1201 拍**。这条边界是所有波次表 `delay` 的隐含契约（`WaveSystemTest` 一直按它断言），重做期间它被破坏过两次，症状都是"整体早一拍"。
- **每波自己算存量**：`waveOwner / aliveByWave / killsByWave / arcByWave / releasedWaves` 记"这一波的僵尸还有几只站着、死了几只"，因为关卡的 `aliveZombieCount()` 回答的是"整片草坪"。读档时按**最新波优先**重新认领场上的僵尸（实体 id 不跨进程），代价是一波在读档后可能多补一次存量。
- **死亡门会收紧**：`early_kill_delay_factor`（默认 0.75，下限 1 秒）让"打死一只才出下一只"的 20 秒上限每超时一次缩短四分之一 —— 打不死第一只的玩家会依次遇到 20 / 15 / 11 / 8 秒，而不是卡在第一只上。
- **工作量证明**：`WavePacingMetricsTest` 对 23 张表跑三档击杀速度，输出总时长 / 最长空场 / 空场占比 / 并发峰值（`-Ppvzce.smoke=pvzce.pacingReport=true` 打表），默认只断言"最慢档也能通关"。**12 张关卡按它的数据重调了两轮**（只动 `delay` 与 `spawn_interval`）：1-7 从 17222 拍到 10292、1-8 从 19172 到 11402、1-9 从 24932 到 14462、2-4 从 25022 到 16742，最长空场从 13~14 秒降到 7~10 秒。传送带关（1-5 / 1-10 / 2-10）与墓碑关 2-5 保持原节奏 —— 前者的压力来自卡的发牌速度，后者的波次只是进度条。

## 出怪速度没有旋钮：想调快只能重写整张波次表
- **现象**：关卡能调"僵尸走多快"（`zombie_speed_multiplier`）和"卡片冷却多长"（`seed_cooldown_multiplier`），但**僵尸多快出现**只能一个一个改 `waves[].delay` 与 `waves[].spawn_interval`。两张收尾的传送带关（1-10 / 2-10）因此没法只调节奏：它们的压力来自"卡按固定节奏发、僵尸来得更快"，而这半边没有一处能写。
- **定论**：新规则 **`pvzce:zombie_spawn_speed_multiplier`**（缺省 1，范围 0.1~20）。它是**速率**倍率（越大越快，与 `zombie_speed_multiplier` 同一读法）：`WaveDirector` 在取波间隔（`effectiveWaveDelay`）与取波内出怪间隔（`effectiveSpawnInterval`）时都除以它 —— 两处一个读法，不存在"只快了一半"的写法。不缩放的东西也写明：`warning_ticks`（横幅的提前量是给玩家看的）与 `spawn_interval` 的 15 tick 下限（"一波不是一次性倒出来"这条缩放后仍然成立）。规则经 `WaveDirector.Host.zombieSpawnSpeedMultiplier()` 读，与波次需要的其它东西同一个接口。
- **1-10 / 2-10 写成 `2.0`**：同一张波次表按两倍速播，而传送带的发牌速度（4 秒一张）不变。
- **顺带修掉一个构造顺序问题**：`WaveDirector` 在 `LevelServer` 构造里比 `this.rules` 先赋值，而它构造时就会算第一波的延迟（现在要读这条规则）—— 规则赋值挪到 `WaveDirector` 之前，否则是构造期的空指针。`ZombieSpawnSpeedTest` 钉住"2 倍速就是整条时间线砍半"（第一只的 tick 正好一半，第四只在 2 tick 误差内一半）与两个关卡的数据。

# 关卡增益：玩家在选卡页决定的一局规则

## 关卡只有"机制"，没有"玩家自己选的规则"
- **现象**：`mechanics` 是关卡说了算的东西（传送带、放置区、小推车），卡槽是玩家说了算的东西；两者之间没有第三种。于是"这一局自动捡阳光""这一局蘑菇射得更远"这类**玩家想开的开关**无处安放：写成 mechanic 就变成关卡强制的，写成 game rule 就只能改数据文件。
- **定论**：新增 **`LevelBuff`**（`api/content/LevelBuff` + 代码注册的 `PvzceRegistries.LEVEL_BUFFS` + `common/buff/BuiltInBuffs`），与 mechanic 同一套注册/查询形状但不是同一件事：关卡有权**钉死**某些增益（`"buffs": ["pvzce:auto_collect"]`，哪怕玩家背包里没有这个增益，与 `slots` 的固定卡同一条逻辑）或写哨兵 `pvzce:player_choice` **放开**给玩家选，还能用 `max_buff_slots` 声明本关能带几个（不写＝跟随背包新增的 `PlayerProfile.buffSlots`，默认 5）。没有写 `buffs` 的关卡**连增益页都不会出现**，所以 23 个内置关卡里已有数据的形状一个字节都没变。收选规则收在 `LevelBuffSelection`（纯函数），与 `SeedSelection` 一一对应：锁定项先放且永不筛掉、自选按提交顺序填到上限为止、上限先判后加、续档时存档里的 `Buffs` 优先（`null`＝那份存档早于增益系统，这才回落到世界偏好）。

## 射程这类"两半是同一个数"的效果，缩放点只有一个
- **现象**：`ProjectileRef.range` 同时决定"植物认为值不值得开火"（`ShooterCapability.hasTarget`）与"子弹什么时候消失"（`ProjectileEntity.maxRange`）。在任何一半上做增益都会得到"能射到但打不中"或"能打中但不射"。
- **定论**：**远距蘑菇**（`pvzce:mushroom_range`，×1.5）在 `LevelServer.spawnProjectile`/`spawnArcProjectile` 里缩放一次 —— 子弹是照着这份 ref 造出来的，而植物的判定读的是同一份 ref，两半不可能分叉。判定"谁是蘑菇"用**两个能力**（`pvzce:nocturnal` + `ShooterCapability`）而不是植物 id 列表：小喷菇与胆小菇吃得到，大喷菇的喷雾是 `ConeAttackCapability`（不是有射程的弹道）因此吃不到，阳光菇/魅惑菇/寒冰菇/毁灭菇没有射击能力也吃不到，而以后新加的蘑菇自动吃得到。`range` 为 0（整块草坪）的射击**不受乘数影响**——"整块草坪乘任何数还是整块草坪"。倍率每发射一次重读，所以中途改增益下一次射击就生效。

## 自动拾取一生成就收，会让掉落物根本没出现过
- **现象**：`LevelServer.tick` 里掉落物的生成包与 `ResourceCollectS2C` 若在同一批发出去，客户端只会看到"结算 +25 阳光"，草坪上什么都没出现过——向日葵刚产的那朵阳光会像凭空消失。
- **定论**：**自动拾取**（`pvzce:auto_collect`）用一张 `autoCollectTimers`（按实体 id）让每枚掉落物先躺 **15 tick** 再收，掉落在客户端眼里是"落地 → 被捡走"。它**不绕过关卡的收集规则**（`collectible`、本关是否解锁该资源、卡槽里有没有那张卡照旧判），只是被拒时**不出声**：每秒一条"没有对应资源卡，无法收集"会盖住它本来要帮的那块草坪。手动点击那条路一个字没变（包括聊天栏那行 `+25 阳光`）；自动那条路只发声音、闪光与飞向银行的动画，因为这些才是"你的阳光到了"的反馈。

## 一局带进去的增益，下一次要能自动帮我选上
- **现象**：玩家在选卡页勾了自动拾取，下一关的选卡页又是空白的——每一关都要重新勾一次不是选择，是手续。
- **定论**：`PlayerProfile.autoBuffs`，**每世界一份**（设计阶段定下：想要自动拾取的人是想在所有关卡都自动拾取）。它写的是"这一局实际生效的增益"（`PvzceServer.createLevel` 里 `rememberAutoBuffs`），所以"我上次带进去的"与"下次帮我预选的"永远是同一份，空列表是合法值（＝以后别帮我选）；**续档时不写**——那一局的选择是上一次会话做的，不是现在的表态。它随 `ProfileS2C` 下发（协议 22 → 23），并且**开局那一刻就补发一次**：不然客户端要等下一次关卡列表刷新才知道这个变化，而下一个选卡页很可能在那之前就打开了。命令入口 `/profile buffs [id...]` 与 `/profile buffslots <n>`。

## 卡牌悬停显名根本不存在
- **现象**：把鼠标放在种子卡上什么都不显示。名字一直在 `assets/pvzce/lang/zh_cn.json` 里（`pvzce.puff_shroom`），但没有任何一处画它；关卡增益的图标同样需要一个说法。
- **定论**：`client/gui/HoverTip` —— 深色底板 + 一行字、贴边翻面，是个**函数**而不是控件（不进 `widgets`，因此永远吃不掉点击）。三处共用：游戏内卡槽条、选卡页的卡池与增益池、关卡内的增益图标。触发条件一律是"光标下的东西确实在、且已经画完"（面板还在滑入、关卡已结束、正在拖卡时不画）。名字经 `SlotResolver` 解析到**内容** id 再查 `GuiLang`，所以"槽 id 与它给的植物不同名"的卡显示的是它实际给你的那个东西。

## 固定卡填满卡槽的关卡，加了增益页就必须让玩家进去
- **现象**：`previewOnly`（不画面板、2.1 秒后自动开局的过场）原来的判据是"卡片没得选"，而"没得选"在增益出现之后变成了两页的事：一个钉死整套卡组、却写了 `pvzce:player_choice` 的关卡会自动开局，玩家**永远没机会选增益**。
- **定论**：`previewOnly = 自己发卡 || (两页都没得选 && 没有已选增益 && 没有锁定增益)`。选卡页顶部随之多一排两个 tab（种子卡槽 / 关卡增益），两页共用同一套排版与绘制代码；"清空"**分页**执行（清了卡不等于要丢增益）。关卡内的增益图标画在**左下角、钱袋银行上方**：左下角本来是钱袋的地盘，但那块只在金币变化后显示 2.6 秒——正好是自动拾取开着时最常出现的那 2.6 秒，所以让开它而不是共用。

## `y` 的语义：旧渲染器锚在**基线**上，TTF 版锚在行盒顶部
- **现象**：字体本身画对了之后，整屏文字仍然统一偏低约一个 ascent —— 按钮标签垂在按钮下沿、玩家牌上的两行几乎叠在一起。
  实测（1280×720，同一批截图）：按钮内容中心与标签中心之差，旧位图渲染器是 **+17.5px**，TTF 版是 **+51px**。
- **定论**：旧渲染器把墨迹下沿放在 `y + (baselineRow - inkBottomRow)`，而 `baselineRow` 就是"基线所在的行"，
  所以那个和恰好把**基线**放在 `y` 上（对坐在基线上的字与带下伸的字都精确成立）。TTF 版把 `y` 解释成"行盒顶部"，
  于是每个调用点都向下平移了一个 ascent。fb8a7ee 只把 `client.font()` 机械替换成 `client.fonts().<role>()`，
  **一行 y 公式都没改**，所以 240 多个调用点（`Button` 的居中、`TitleScreen` 玩家牌、`HintBox`、`HoverTip`、
  `AwardScreen` 的底板…）仍然全是按基线锚点写的。修法是把锚点改回基线（`drawGlyph` 直接把 `y` 当基线），
  并把 `Fonts`/`FontRenderer` 的坐标说明、`ascent()`（现在是"基线之上的高度"，供调用点自己居中用）一并改对；
  修完实测按钮标签中心差 **+14px**，与旧版的 +17.5px 同量级（剩下的差是两种字面墨迹比例不同，不是锚点）。
  `GlyphAtlasTest.glyphInkSitsOnTheAnchorRatherThanUnderIt` 钉住"墨迹在锚点之上"。

## 顺带修掉：`buffs` 的 JSON 形状与 codec 不匹配
- **现象**：`LevelBuffPlan` 一开始写成"带自己 codec 的 record"，于是 `"buffs"` 被读成**对象**，而关卡文件里写的是数组（`"buffs": ["pvzce:auto_collect"]`），19 个关卡全部 `Not a JSON object` 加载失败。这是写测试时立刻暴露的：端到端用例跑真实数据包，而纯函数用例用的是 Java 构造器，两边一个红一个绿。
- **定论**：两个字段**扁平地**解在 `LevelTail` 上（`LevelBuffPlan.mapCodec()` 经 `RecordCodecBuilder.of` 接进去），与 `slots` / `max_seed_slots` 的形状一致，作者的写法与记录的字段一对一。**这也是为什么要有一个跑真实数据包的端到端用例**：只测纯函数的话，"Java 里能构造"与"文件里能读出来"是两件事。

## 关卡增益应当是打出来的，不是一开始就有的

- **现象**：`LEVEL_BUFFS` 一注册，两个内置增益对任何放开增益的关卡都立刻可选——玩家在第 1-6 关就能勾"自动拾取"，而原版里这类能力是**通关给的**。更具体地说：1-9 与 2-9 原本是"不给植物、只给一袋钱"的两关，它们的奖励位空着。
- **定论**：增益做成**第三个袋子**（`PlayerProfile.unlockedBuffs`，自己的 NBT 键 `UnlockedBuffs`，与卡、关卡购买并列）：没被某一关发过的增益**列在池子里但带锁**（`SeedOptions.LOCKED_OPTION` 复用价格字段；客户端画挂锁、点它只响一声），`LevelBuffSelection.sanitize` **不收**它 —— 服务端这一侧才是门，池子上的标记只是把门画出来。**1-9 首通发 `pvzce:mushroom_range`（远距蘑菇），2-9 首通发 `pvzce:auto_collect`（自动拾取）**，于是"蘑菇射得更远"出现在夜关之前、"自动拾取"出现在 2-10 那条传送带之前，而 2-5 / 2-10 那种关卡自己钉死的增益照旧不需要玩家拥有（关卡的"我这一关就是这样"优先于背包，与固定卡同一条逻辑）。奖励类型是 `{"type":"buff","id":...}`，与 `unlock` 同样**幂等**、**任何一次通关都补发**，所以早就通关过的老世界也拿得到；那两关的 `repeat`/掉币继续是引擎默认值，显式写出来只是因为 `rewards` 块现在存在了。
- **顺带改掉一个命名**：`PlayerProfile.owns` → `ownsCard`。第三个袋子一进来，"owns 什么"就不再自明，而一个叫 `owns` 的方法读起来像"这个玩家拥有它吗"，实际只回答卡——增益问的是 `ownsBuff`。同一个改动也让奖励结算里 `profile.ownsCard` 与 `profile.ownsBuff` 并排出现时不必靠注释区分。
- **奖励页与草坪上那一件东西**随之多一档：解锁的增益排在资源物品之前、卡之后（`LevelRewardS2C.unlockedBuff`，**协议 23 → 24**）。它画的是**种子包的框 + 增益自己的图标**，因为这一页说的是"你拿到了新东西"，钱袋会说出相反的话；结算页的文字换成 `pvzce.award.new_buff` 与一句"选卡时可以带上它"。
- **操作入口**：`/profile buff <id>` 发一个增益（冒烟与测试用，等价于通关 1-9 / 2-9 的那一步）。

## 远距蘑菇"没有生效"：缩放做了，判定没做

- **现象**：把 `pvzce:mushroom_range` 打开，小喷菇的孢子确实飞得更远（`ProjectileRef.scaledRange` 正确、`LevelServer.sporeRangeMultiplier` 返回 1.5、所有单测都绿），但**在游戏里看不出任何区别**。实测两次运行完全一样：首次开火时僵尸距离 2.9925 格、孢子最远飞到 2.27 格。
- **定论**：`ProjectileRef.range` 是**一件事的两个半边**——植物"值不值得开火"（`ShooterCapability.hasTarget` 里的 `shot.covers(muzzleX, z.cellX())`）与子弹"什么时候消失"（`ProjectileEntity.maxRange`）。原实现只在 `LevelServer.spawnProjectile` 里缩放（子弹那一半），判定那一半读的仍是定义里原始的 `range`，所以植物始终等到 3 格以内才开火，而它现在能打到 4.5 格这件事从来没有机会发生。修法是把这条规则收进**一处**：`PlantShots.scaled(ref, plant, level)`（倍率来自新的 `LevelAccess.sporeRangeMultiplier(plant)`，`LevelServer` 实现它），射击能力拿它瞄准、`spawnProjectile` 拿它造子弹——同一个调用，两半不可能再分叉。
- **为什么原来的测试看不出来**：测"孢子飞了多远"永远测不出这个 bug——僵尸会自己走进射程，无 buff 的那次也会开火，两次测量于是**完全一致**。新用例 `MushroomRangeBuffTest` 测的是**首次开火那一刻僵尸在多远**（2.99 格 vs 4.19 格），这才是 `covers` 决定的那件事。它跑在真正的夜关 2-1 上：白天的蘑菇在睡觉，一枪不开——那也会被读成"增益没生效"。
- **顺带**：探针关卡一开始连 `teams` 都写成空的（`LevelServer` 不会补默认队伍，僵尸根本进不了实体流），所以最早两次测量是"没有任何敌人"的假象；写这种"直接驱动 LevelServer"的用例时，队伍、昼夜、波次三样都得是关卡自己的。
- **另一个顺带**：`BackpackAndCoinsTest` 里"召唤的僵尸必须到达客户端"是一个既有的偶发失败——`awaitPacket(EntitySpawnS2C.class)` 返回的是**最后一个**同类型包，而天上掉的阳光也是 `EntitySpawnS2C`，阳光恰好落进窗口时断言就在跟一枚阳光比对。改成等"kind 是 zombie 的那一个"。

# 表现修正（孢子 / 双发 / 弹速 / 缩头 / 动画速率 / 两套爆炸）

> 玩家报告的一批"看着不对"，一轮修完。共同点是：数据里其实都有，只是**没有一处**把它们连起来——
> 或者连起来了但被另一条规则挡住。每个缺陷的判据都落在一个可断言的地方（下表最后一行）。

## 孢子云太大、而缩到 1/4 之后又断成了点线

- **现象**：大喷菇喷出的孢子（`pvzce:fume_cloud`）每颗 0.5 格，铺满整条锥形，比原版那团雾厚一倍不止；
  改成 1/4（0.125 格）之后又变成**虚线**：锥形的 8 个停靠点是按 0.5 格的贴图定的（0.5 格间距，注释里
  写明了"贴图必须比间距宽"），12.5px 的孢子按 25px 的间距排下来就是一条点线。
- **定论**：两个数一起改，且**都写进注释的算术里**：`fume_cloud.scale` 0.5 → 0.125，
  `ConeAttackCapability.DEFAULT_CLOUD_COUNT` 8 → **32**（间距 0.125 格 = 贴图宽度，实测才连成一条雾带）。
  16 个停靠点先试过，截图里仍是断续的点——一次挥发的粒子横向只铺开约 0.2 格，够不到下一站。
  32 站 × 每站 28±8 颗 ≈ 900 颗，贴着 `ParticleEngine.MAX_PARTICLES`（1024）的上限。
  这件事只能靠截图判定：粒子数、间距、生命期三者算得出来，**看起来连不连**算不出来。

## 双发射手看起来和豌豆射手一模一样

- **现象**：`repeater` 的 `count: 2` 从数据到代码都是对的，两颗豌豆确实都生成了——但它们在**同一 tick、
  同一个出生点**生成，速度相同、方向相同，于是永远重合：屏幕上只有一颗豌豆，同一 tick 里打同一个僵尸，
  两份伤害读起来是一份。"双发射手"因此和豌豆射手在画面上没有任何区别。
- **定论**：`ProjectileRef` 新增 **`burst_delay`**（一轮齐射里颗与颗之间隔多少 tick，缺省 0 = 全部同 tick）。
  `ShooterCapability` 为此带一张 `pendingShots` 队列：第 1 颗在开火那一 tick 出膛，其余按 `i * burst_delay`
  排在后面；队列每 tick 先走（`tick` 开头就 `firePendingShots`），所以植物中途缩头或进入冷却都不会吞掉
  已经打出去的子弹。`repeater` 与 `gatling_pea` 都写 12 tick（0.2 秒，按 4 格/秒算是 0.8 格间距）。
  队列**不进存档**：一轮齐射 0.6 秒，存档正好落在里面最多丢一轮的尾巴，而为此让存档认识"一个指向内容定义的队列"不划算。
  用例：`CombatSystemsTest.aBurstVolleyLeavesOnePeaAtATime`（开火 tick 天上只有 1 颗；齐射出完时 2/4 颗彼此相距 > 0.5 格）。

## 直线弹的速度慢了一半

- **现象**：`pea` / `snow_pea` / `puff` 都是 2.0 格/秒，`cactus_spike` / `fume` 2.4。原版豌豆约 4.2 格/秒
  （80px 一格、约 3.3px/帧），所以画面上子弹是"飘"过去的。
- **定论**：直线弹**各自 ×2**：pea/snow_pea/puff → 4.0，cactus_spike/fume → 4.8。抛物线弹（投手）不动——
  它们的 `arc` 速度与重力是一对，翻倍会把弹道压平，那是另一件事。

## 胆小菇缩头之后不会哭

- **现象**：`ScaredyShroom.reanim` 把缩头画成两条 clip（`anim_scared` 把头低下去 + `anim_scaredidle` 保持并流泪），
  美术文件用 `on_end: hide_loop` 说这件事，服务端只发布一个 `hide` 状态。客户端每帧请求 `hide`，
  而 `AnimationManager.isAlreadyPlaying` 把"活动 clip 已经不是这个状态解析出来的那个"读成"这个状态已经结束"——
  于是缩头一播完就被从头重开，**哭泣的循环一次也没上过屏**。
- **定论**：`AnimationPlayback.chained`——由 `on_end: <clip>` 交接来的 clip **仍算同一个状态在播**
  （`isAlreadyPlaying` 见到它就返回 true），重发同一个状态不会把它推回去重播。
  另一条规则一个字没动：`on_end: idle` 的交接**不是**链条（那是"动作结束、回到待机"），
  所以 `shoot`、`explode` 这类要反复触发的动作照旧能重播。
  用例：`AnimationManagerIntegrationTest.aDuckedScaredyShroomHandsOverToItsCryAndStaysThere`
  （等待交接 → 复查 clip 名 / 重发 `hide` 不回到 `hide` / `shoot` 播完仍能重开）。

## 攻击动画比原版慢一半

- **现象**：射击动作的速度从来没人给过，于是按 reanim 自己的 12fps 播：豌豆射手一次出手 2.08 秒、
  大喷菇一次呼气 2.5 秒——比 1.5 秒的射击间隔还长，植物永远在"上一发的收势"里，整条车道像慢放。
- **定论**：`tools/reanim_to_pvzce_all.py` 新增 **`SHOOT_ANIMATION_RATE = 2.0`**，写进 14 种植物 15 条
  `shoot` / `shoot_high` clip（豌豆/寒冰/双发/机枪/三线/裂荚、大喷菇/小喷菇/胆小菇、仙人掌、卷心菜/玉米/西瓜/冬西瓜），
  然后按 `--entity` 逐个重生成。生成器是这些动画文件的唯一出处（重生成与 shipped 文件逐字节一致），所以改的是配置而不是 JSON。

## 樱桃炸弹的动画与爆炸对不上

- **现象**：`CherryBomb.reanim` 是 30fps，转换器把 `anim_idle` 裁成真正在动的 12 帧 = 0.4 秒，
  而引信是 60 tick（1 秒）：炸弹在鼓到第 2.5 遍中间爆掉，读起来像"动画播错了"。
- **定论**：`CHERRY_BOMB_ANIMATION_RATE = 0.4`——0.4 秒 ÷ 0.4 = **1.0 秒正好一发引信**，
  一次鼓起配一次爆炸。`explode` 用同一个倍率（同一条 27 帧轨道、同一个动作的后半），
  配合下面那条 `linger_ticks` 正好播完。

## 爆炸特效：樱桃只有一个小贴图，毁灭菇发的是别人的闪光

- **现象**：两处都缺"组成"这个概念。樱桃炸弹的爆炸只有一颗 `pvzce:pow`（0.2 → 0.5 格，约 40px），
  对着 3x3 的爆炸范围小得可笑；而 `pvzce:powie`（原版的橙色爆炸云）转换出来是 `scale: 0`，
  渲染器直接跳过——**它从转换出来那天起就没画出来过**。毁灭菇发的是同一个 `pvzce:pow`，
  而原版那朵"菌柄 + 七块菌盖 + DOOM 字 + 全屏白闪"的组合早就转好了放在 `data/pvzce/particles/explosion/` 里，
  一行代码都没引用过（`PvzceParticles.DOOM` 是个没人用的常量）。另外 `LINGER_TICKS` 写死 30 tick
  并注释成"比所有 explode clip 都长"，而毁灭菇的 explode 有 **2.75 秒**（火爆辣椒 1.08 秒、倭瓜 0.67 秒也一样）——
  爆炸动画只播了个开头，植物就消失了。
- **定论**：三块拼图。
  1. **出生偏移**：`ParticleDef.ParticleMotion` 新增 `offset_x` / `offset_y`（相对效果触发点的出生位置，单位格），
     `ParticleEngine` 在实例化时应用，`bounce` 的地面线也跟着改成相对**出生点**。原版用 `EmitterOffset`/`SystemPosition`
     摆一朵云，转换器把那两个字段丢掉了——于是"九块美术摆成一朵蘑菇"这件事在数据里无处表达。
  2. **组成是一个列表**：`pvzce:explosive` 新增 **`particles`**（按发射顺序排的粒子 id，缺省 `["pvzce:pow"]`）
     与 **`linger_ticks`**（爆后留在场上的 tick 数，缺省 30）。`detonate` 把列表逐条发在植物自己那一格，
     声音只挂在第一条上（每次 emit 携带整个效果事件，逐条挂会把一次爆炸响九遍）。
  3. **数据**：`pow` 的终点从 0.5 格提到 2.5 格（贴图 136x123，按 3x3 的爆炸范围定）、新增 `pow_flash`
     （0.16 秒的局部亮闪，additive）、修好 `powie`（scale 0 → 0.9 并按外扩方向发散、淡出）；
     `powie` 还顺手把僵尸王锤子的那朵云一起修好了（`HammerCapability` 发的就是它——以前那一下也是什么都不显示）；
     毁灭菇的九块按原版像素尺寸重写（`scale` 是画出来几格高，`aspect = 宽/高 × 1.25` 才是屏幕上的形状，
     `offset` 照抄原版的 `SystemPosition` ÷ 80/100）——整朵云约 3.4 格宽 × 2.8 格高，全屏白闪改成会淡出
     （原转换结果是 `alpha_to: 1.0`，一屏不透明的白）。`cherry_bomb` / `doom_shroom` 的 `linger_ticks`
     分别 70 / 165（= 各自 explode clip 在屏幕上的时长），顺带把 `jalapeno`（65）、`squash`（40）被截断的爆炸动画也补上。
  用例：`AnimationResourceLoaderTest.everyAshPlantStaysLongEnoughToDrawItsBlast`（停留时长 ≥ clip 时长 ÷ rate，
  两边都从文件里读）、`theBlastsNameParticlesThatExistAndArePlaced`（会炸的植物必须点名自己的组成、每个 id 都能解析、
  菌盖至少 5 块带出生偏移）、`ParticleEngineTest`（偏移真的落在引擎里）。

## 顺带：`write_plant_content.py --dry-run` 会写盘

- **现象**：这个脚本的 `--dry-run` 分支写文件**之后**才判断，所以"预演"把 14 个植物 JSON 的
  `render_scale` / `order` 与 5 个投射物 JSON 的 `impact_particle` 抹掉了——那些字段是生成之后手工补的，
  脚本的表里没有。文件改动与 HEAD 的差异当场暴露了这件事。
- **定论**：`write_json` / `update_lang` 收一个 `dry_run` 参数，预演只打印不落盘；文件头的文档写清
  "**这是生成器，不是同步器**"：跑它等于"按表重建这几个定义"，手工加过的字段会被丢掉，先用 `--dry-run` 看差异。

# 字体：TTF 动态渲染的七个缺陷（一轮修复）

> 现象与定论源自 2026-09 的一次完整排查：把 `assets/pvzce/font/*.ttf` → `TtfFace` → `GlyphAtlas`/`GlyphPage` → `ShaderProgram` → `FontRenderer` → 调用点
> 这条链整条读了一遍，并把"按 GL 真正会读到的那些字节采样"写成了用例。当时的界面是**所有文字都画成实心色块**（`zz_final.png` 那种盖住整条按钮的长条），
> 前六个缺陷叠在一起，其中任何一个单独修都不会让文字出现；**第七个是跑起来看图才发现的**——字形画对之后整屏文字仍然统一偏低一个 ascent，
> 单测与离线预览都看不见（它们都只验证"这个字画在哪一行"，没验证"调用点给的那条线是什么"）。

## 覆盖率写进了错误的通道（"实心色块"的直接原因）
- **现象**：文字一律是不透明的实心方块/长条，按钮标签就是一条盖住整条按钮的色带；而 dump 出来的图集完全正常——笔画清楚、方向也对。
- **定论**：图集把覆盖率写进 RGB、alpha 一律 `0xFF`，普通精灵路径却取 `tex.a * vColor.a` 当不透明度，于是每个字形 quad 都是全不透明；
  同一份代码里文字特效分支读的又是 `tex.r`，两条路对"覆盖率在哪个通道"给出的答案不一致。统一成**白字 + alpha = 覆盖率**（与它替换的
  `ui.png` 同一约定，也是旧位图管线验证过的形状），特效分支改读 `tex.a`。

## 页缓冲自上而下写，UV 却按"已翻转"的约定算
- **现象**：同一个图集里，有的字完全不显示，有的位置上渗出别的字的笔画。
- **定论**：`copyInk` 把 stb 的第一行（墨迹**顶**行）写进缓冲第 `y` 行，而 `glTexSubImage2D` 把上传数据的第一行放在 `t=0`（贴图**底**部），
  于是整页在纹理空间里是倒的；`Slot` 按 `TextureManager` 的 PNG 约定（`stbi_set_flip_vertically_on_load`，`v1 = 1 - y/SIZE` 是顶边）算 UV，
  采到的是镜像位置——靠页顶的字形映到页底（空白 → 不显示），页中间的字形映到别的格子（→ 串字）。现在整页按"图像行 R 写到缓冲行
  `SIZE-1-R`"落盘：写入、清格子、上传切片、两种 dump 全走同一个 `dataRow`。

## 一个字号有两个含义：stb 的行盒 vs 排版的 em
- **现象**：同样字号下两个角色大小不一致（常量注释里"站酷 em 76 的墨迹只有 15 单位、思源却有 21.7"就是它），基线也跟着偏。
- **定论**：`stbtt_ScaleForPixelHeight` 缩放的其实是 **hhea 行盒**（思源黑体 1160/-288 = 1.448em），而 `ascent`/`descent` 来自 OS/2（正好 1.0em），
  光栅与排版差 1.448 倍而且每个面还不一样。改成 `pixelSize / unitsPerEm`：请求的字号就是 em 盒，度量与轮廓终于说的是同一件事。

## 字形 quad 的底边取了反号
- **现象**：带下伸的字（逗号、`g`、`y`）整字被抬高约两倍下伸量——图集里看不出来，一行中文标点就能看出来。
- **定论**：`visualBottom` 是"相对基线的、**向上为正**的有符号偏移"（坐在基线上的字为 0，下伸为负，`TtfFaceTest` 一直这么钉着），
  绘制处写的却是 `baseline - visualBottom`。改成 `baseline + visualBottom`，并把 `Glyph`/`GlyphRef` 里那句不自洽的 "positive down" 改成与实现一致的表述。

## em 常数比旧图集大五倍
- **现象**：即使上面四条都修好，文字仍会撑满并溢出所有面板。
- **定论**：旧图集是 98px 字画进 18 单位行（em ≈ 13.8 GUI 单位，中字墨迹 13.2），TTF 版写的却是 body 72 / display 90。改成 **body 14**、
  **display = body × 1.14**（站酷的汉字在自己的 em 里画得更小，这个比值让两个角色**光学同高**）、serif 同 body。行高随之成为 1.0em，
  `lineHeight(1)` 由 18 变 14 —— 这是这一轮**唯一**有意改变的观感，标定推导与旧值对照写在常量注释里。

## 文字特效的偏移单位与采样距离
- **现象**：`TextStyle` 的阴影/描边（调用点目前还没有人用）即使触发也等于没画：偏移按设备像素传给 shader，shader 当 uv 用，
  采样点落到页的另一头（多半是空白），于是只剩干净的字。
- **定论**：偏移在 `FontRenderer` 里换算成 uv（一个字形纹素 = 一个设备像素，因为字形就按要画的尺寸光栅），并把幅度**截到图集 gutter**：
  读得更远就会采到隔壁那个字形、把它的笔画当描边画出来。`uTextOffset`、`setTextEffects` 与 `TextStyle.outline` 的注释同步改成"uv / 上限是 gutter"。

## 顺带
- `GlyphAtlas` 从 `GlyphPage` 拆出来（装箱、清格子、覆盖率缓冲都不碰 GL），于是"上传的到底是哪些字节、字形朝哪边"可以被
  `GlyphAtlasTest` 直接钉住（它按 GL 的放置规则读**待上传的切片**，不是按页缓冲的另一种读法）；`GlyphQuad` 从绘制循环里拆出来，
  于是"这个字落在基线的哪个位置"也不需要 GL 就能断言。无 GL 用例从 6 个（`TtfFaceTest`）扩到 19 个（3 个文件）。
- `TtfFace.of` 的缓存键统一成不带扩展名的文件名：游戏问 `zhanku`、测试问 `zhanku.ttf`，同一个字面在同一个进程里只能
  `stbtt_InitFont` 一次（这既是缓存存在的理由，也是它必须按名字归一的原因）。`FontRenderer` 里没人调用的 `GL30_TEXTURE_BINDING_2D()` 删除。

# 界面配色与字体：按钮绿字、提示条橙字、HUD 数字用站酷体

> 一轮按原版观感做的调整（不是缺陷修复，记在这里是因为它定下了"哪种东西用什么字/什么颜色"）。

- **两种按钮两种字色**（`components/Button`）：石头灰的 `Style.DEFAULT`（标题页、设置、关卡存档对话框、编辑器各页）
  标签改成**深绿 #1C6B26**，棕色木牌的 `Style.SEED_CHOOSER`（关卡列表页签与底部那排、选卡页）**保持白色**——
  绿字压在棕木上两种颜色会一起糊。禁用态照旧只降 alpha（1 → 0.6），不换色，所以"按不动"与"什么样"是两件事。
- **颜色是照着"实测对比度"定的，不是照着色卡定的**：那些按钮的底板内部是深板岩色（RGB 74,76,109，
  相对亮度 0.078）。第一版深绿 #1C6B26 的渲染实测只有 **1.26:1**，屏幕上就是"深色压深色"，被退回"太暗"；
  中途还试过"深绿 + 粗体 + 浅色描边"来补对比，同样被退：**汉字笔画只有 4~5 像素宽，一圈 2 像素的浅边会把
  字里的空当糊掉**，看着像两个字叠在一起。最终定成 `Button.LABEL_STYLE = TextStyle.bold()` +
  **#4CAF50（实测 2.97:1）**，无描边。要再调只动 `LABEL_R/G/B`：上到 #6BC74A（3.89:1）、
  下到 #43A047（2.50:1）都在可用区间，候选色阶见 `.smoke/analyze/green_candidates_big.png`。

## 按钮标签的字号交给按钮自己算（顺带修掉"字总是偏低"）
- **现象**：同一行按钮里，设置页那种高按钮的字显得很小（标签只占按钮高度的一半），而调用点写的是各自的常数
  （标题页与设置页都写 `scale(1.1F)`，暂停对话框写 `min(1.05, buttonHeight/42)`——同一个问题在三处各猜了一遍）。
  把字号调大之后又发现：字一放大就从**下沿**顶穿按钮，上沿却还空着一大截。
- **定论**：三条规则。
  1. **字号 = 放得下可书写面**：`Button.fittedLabelScale` 取"行盒 ≤ 面高"与"文字宽 ≤ 面宽"的小值 × 调用点倍率，
     再夹在 [0.5, 2.4]；面本身只给标签 `LABEL_SIZE_OF_FACE = 0.75`（0.88 那种填满面的观感是"字要把按钮撑破"，
     低于 0.7 又显得空——这一个数就是整体缩放旋钮）。**"面"是量着美术定的**：石牌（46px 高）面在 8..38 行之间 =
     控件高度的 0.65，两侧 36+35 像素的端帽按高度缩放；木牌是一张整图，边框是 42 行里的 2+5 行。
     第一版按"控件高度的 0.9"填满，直接顶到高光/阴影上（用户截图里"暂停"顶穿边框就是这个），退回。
  2. **垂直位置按墨迹居中**（`Button.labelBaseline`）：汉字墨迹在基线上 0.76em、下 0.05em，行盒却是对称的，
     按行盒居中会让标签整体偏低约 0.14em——字号一大就先从下沿顶出去。
  3. **悬停时标签跟着面板沉**：`button_down_*` 不是"另一块面板"，而是同一块在贴图里下移 1 个原生像素；
     面板沉、文字不沉，就成了"面板从字底下移开"。标签因此下移 `高度 / 46`（字号不动，为 4% 的高度差重光栅不值得）。
     这条没法在本机截图验证（`smokeHover` 需要窗口焦点，平台会忽略指针挪动——见 `冒烟与截图指南.md` §4.5），
     改成 `ButtonLabelScaleTest.theLabelCentresOnTheInkAndSinksWithAPressedPlate` 钉住。
- **粗体第一版做错了，记下来免得再犯**：`FontRenderer` 一开始把同一个 quad **平移一个设备像素再画一遍**
  （右下），这是常见的假粗体做法。在 320×180 的观感下看着还行，但按钮标签是 4~5 像素宽的汉字笔画，
  平移的结果是"两个字叠在一起没对齐"——而且那一遍把**描边也一起平移了**，浅色环变成左边 2px、右下 3px，
  重影更明显。改成**对称膨胀**：借 shader 的描边分支、颜色设成字色，四个方向各外扩一个纹素，最后一遍画，
  压住自己描边的内圈 → 最终是"1 像素浅色边 + 粗一档的字"，advance 不变（粗体不改排版）。
  对比图：`zoom_ghost.png`（旧：平移版，重影 + 环粗细不均）对 `zoom_bold2.png`（新：对称膨胀 + 单圈细边）。
- **提示条的文字是橙黄**（`hud/HintBox`，`TEXT_R/G/B` 由米白改成 **#FFA626**）：原版屏幕下方那句提示就是这个暖色，
  底色（深灰半透 + 一像素亮边）不动。它和"又一条白色标签"的区别，正是"游戏在跟玩家说话"与"界面在报字段"的区别。
- **阳光显示用站酷体**：阳光银行的大数字（`InGameScreen.renderHud`）与每张种子卡印的价格（`SeedCardRenderer`）
  从 `fonts().body()`（思源黑体）改成 `fonts().button()`（站酷快乐体）。两处本来就是原版同一个字体的两处出现，
  而且卡片脚注那个尺寸上站酷的笔画更站得住（代价是同一个 scale 下比思源宽约 14%，两处都验过放得下）。
  截图证据：`small_title.png` / `small_settings.png` / `small_levels.png`（最终：绿色粗体、无描边、字号随按钮
  但只占可书写面的 0.78，边框留边）、`final_btn_zoom.png` 与 `final_pause_zoom.png`（放大看边距）、
  `green_candidates_big.png`（色阶候选）、
  `bold_before_after.png`（假粗体重影 vs 对称膨胀）、`bold_levels.png`（木牌仍是白色无描边，与 `color_levels.png` 逐字节相同）、
  `color_board.png`（站酷数字 + 橙字提示条）、`zoom_bank.png` / `zoom_price4.png`（两处站酷数字）。

# HUD 右上角的一对按钮、以及暂停对话框的重做

- **倍速挪到暂停左边、暂停占最右**（`InGameScreen.init`）：两者**等高**（`min(56, guiH/5)`），倍速更窄
  （`min(64, guiW/10)`）。顺带一个坑：`rightBound()`（卡槽条与履带托盘用来避让的右边界）原本取的是**暂停按钮**的左边界，
  暂停挪到最右之后它就跑到倍速按钮右边去了——条会从倍速底下穿过去。现在取这一对里最左的那个减 8。
- **暂停对话框太空、和框子也不搭**（`PauseDialog`）：原来的面板 440×400，在 240 GUI 高的窗口里被夹到 216 高却仍按固定值排版，
  三行按钮挤在下方、吊牌标题被顶到屏幕外，而且用的是**石按钮**——对话框是"石板框 + 木牌"，石按钮看起来像属于底下那块框。
  现在按其它对话框的两条约定改：`frameScale(0.55)` 把石框画薄、`inlineTitle()` 把标题画进框内，按钮换成木牌并加到四行
  （继续游戏 / 设置 / 重新开始 / 保存并退出），行从**框内侧**往上排、行高按实际高度算。开着的暂停面板里点"设置"
  是安全的：服务端已经暂停，关掉设置页回来时 `paused` 仍为真，对话框照旧在。

# 设置页的模糊背景、暂停菜单、倍速按钮

- **"设置"打开的是音量页**（`PauseDialog`）：那一行写"设置"，却直接调 `client.buildSettingsConfig()`（`ConfigScreen`，音量滑块页）。
  改成 `new SettingsScreen(client)`——想调音量的人再走一步就到了。
- **暂停菜单的按钮风格**：先按"其它对话框都用木牌"改成了木牌，被退（"应该用灰色按钮"）——这些按钮长在**石框**上，
  木牌像塞进来的另一个控件。已改回石牌，并把石框从 0.55 画到 0.45：240 高的窗口里面板被夹到 216，
  0.55 只够四行二十单位的"邮票"，0.45 才给到按钮该有的行高。
- **窄按钮上的字被算没了**：可书写面的宽度原本扣的是九宫格端帽宽度（`(36+35)/46` 个高度）——端帽合计比窄按钮本身还宽，
  倍速按钮（44×48）于是只剩 1 单位宽的面，"1x"小到看不见。扣的应该是**两端圆角**（约 `10/46` 个高度），
  端帽中段是平的、居中的标签本来就会跨过去。
- **设置页在花哨背景上看不清** → 加了 `BlurredBackdrop`：`openScreen` 时把当前后备缓冲 blit 到 1/6 的 FBO 贴图，
  页面放大铺满（放大即模糊）再压一层暗色。没有新增后处理通道，也没有重画底下那一屏。
  验证：`blur_from_title.png`（标题页之上打开设置 → 背景是模糊的标题页）；
  游戏内打开设置走的是同一条路，只是背景换成那一局的画面。

## 关卡内打开设置会同时响两首歌
- **现象**：从暂停菜单进设置，菜单曲和关卡曲一起播。
- **成因**：`SettingsScreen.init()` 抄了标题页那句 `client.music().ensureMenu("pvzce:music/crazy_dave")`，
  而音乐控制器是**四条独立轨道**（menu / background / battle / stinger）：菜单请求不会顶掉关卡曲，只会加一条。
  这个页过去只从菜单进得去，所以没人碰到；暂停菜单加了"设置"那一行之后就成了必然。
- **定论**：只在**没有关卡**时请求（`!client.level().initialized()`）。判据不能用 `level() == null`——
  客户端那面关卡镜子是构造时就 new 的长命对象，永远不为 null。顺带补了 `-Dpvzce.traceMusic`：
  每次切轨打一行并列出四条轨道各自在播什么，"两首歌一起响"没有任何其它可见症状。

## 关卡提示语从贴图改成字体渲染
- **现象/诉求**：开场的「准备… 安放… 植物！」与最终波的「FINAL WAVE」是原版的 PNG（英文烘焙进图里）：
  任何语言都改不了、任何资源包也换不掉，而游戏里其它每一句话都是文本。
- **定论**：`BannerAnimation` 改成**文本**——文案走 `assets/pvzce/lang`（`pvzce.announce.ready/set/plant/final_wave`，
  中英都在），用 display 字面画成原版那种红字黑边（黑边是同一个词四方向偏移叠出来的；shader 描边的采样距离上限
  两个设备像素，在这么大的字上等于没有）。**从美术里保留下来的是时间轴**：逐帧姿势仍抄自
  `StartReadySetPlant.reanim` / `FinalWave.reanim`，偏移按宽度归一化，所以动作、节奏、落点全都没变。
  字号取"高度 ≤ 绘制宽度 × 0.36"与"宽度 ≤ 0.92"的小值：中文比英文紧凑，照英文的高度排会顶出窗口。
  那四张 `textures/gui/hud/announce/*.png` 从此没人引用（保留在资源里当参照）。
- **跟着音效重排了节拍**（第一版照 reanim 自己的 0.5 秒一词跑，被退"太快、没契合音效、停留太短"）：
  量了两段音频——`readysetplant.ogg` 5.26 秒（两次"咚"在 0.00/0.60 秒，正文 1.20–3.30 秒）、
  `awooga.ogg` 4.15 秒（峰值 2.20 秒）——三个词因此落在两次咚上、`植物！`压住整段正文（总长 3.25 秒），
  最终波的飞入拉长到 1.10 秒到位、停到 3.5 秒。**"停留"是这次真正的修法**：原来每个词只活 0.5 秒，
  现在前两拍各占满一个 0.6 秒的拍子、最后一拍在屏幕上待 2 秒。
- **两句大波文案**：横幅是「最后一波攻势」（final），提示行是「一大波僵尸即将来袭」（huge）。
  那一行原来是**写死**在 `renderWaveWarning` 里的 `"一大波僵尸正在接近！"`，既改不了、又与横幅重复，
  现在走 `pvzce.announce.huge_wave`。
