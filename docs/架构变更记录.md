# 架构变更记录

> 记历史：**现象 → 定论**。现状看 `当前项目架构.md`，取舍看 `决策记录.md`，教训看 `踩坑清单.md`。
> 写法：只记**最终落地的做法**；被回退的尝试最多留一行（"曾试 X，已回退，原因 Y"），
> 不给每个错误写长文。写之前先确认行为通过 —— 回退时这份记录要重写第二遍。

> **结构**：§1 是**定论索引**（一条一行，链到归档全文），§2 是**最近 3 轮全文**。
> 更早的每一轮在 `架构变更记录/` 目录里按 `YYYY-MM-<轮名>.md` 分卷（冻结不改）。
> 归档只搬家不改写：分卷前的每一节都在，找一条旧定论用 §1 的索引，或直接在该目录里搜索。
> 分卷规则：主文件留最近 3 轮，其余每轮一份；一条定论只在一个归档文件里，主文件不重复正文。
> 文件名不带空格（`/` 写成 `、`），这样链接可以直接写中文路径。

# 迷雾重做：按原版的格子云铺，逐顶点 alpha 的路灯

> 用户一句话：「4-x 关卡的迷雾渲染完全错误，很糟糕，应该按照原版的迷雾来渲染。`refer/im7` 里面有能用的
> fog 贴图。」四个取舍事先问过并得到确认：雾按原版是实的（盖住的草坪几乎看不见）、覆盖范围伸出棋盘、
> 贴图用 `fog_.jpg` 的 8 帧云朵、每格的缓慢流动照原版做。

## 现象与根因

- **原版画的是云，我们画的是一块黑幕**。`FogClientMechanic` 把云图**拉满整条雾带高度**垫在下面，
  再用 16 级**黑 quad** 按 alpha 叠在上面，深处再补一块纯黑矩形。且绘制走的是 `FogData.alphaAt`
  的斜坡：`start=6, end=9` 时第 6 列只有 0.31、到第 7.8 列才到 0.75（隐藏阈值），所以整片实际上
  是"边缘一条硬竖线的黑块"，云被完全盖住。玩家自己种在那几列的植物也被这块黑盖掉。
- **真正的原因是没有照原版的模型画**。原版 `Board::DrawFog` 是**逐格铺云**：每格画一张
  `IMAGE_FOG` 的帧，位置 `x*80-15, y*85-30`，每格一个 alpha（起始列 200/255，其余 255），
  再叠一个逐格缓慢变化的颜色。云是实心的，所以"看不见"是云本身给的，不是黑幕给的。
- **"引擎没有逐顶点颜色"这条注释是错的**。`VertexConsumer.color` 一直存在，只是 `SpriteRenderer`
  与 `PvzceClient` 的每个入口都只收一个色——所以路灯花的圆洞只能靠 8 分格的小 quad 拼，边界是马赛克。
- **贴图本身也被烘错了**：`tools/gen_fog_texture.py` 读的是 `fog.jpg`（一条近乎均匀的灰带，不是云），
  还按"铺满整条带"的思路在上下做了羽化——那是为旧画法服务的。
- **两个坐标空间被混为一谈**。原版的 `x*80-15` 是**背景图自己的像素**，而这个项目里棋盘在
  1920×1080 下每格是 144px（`PvzceCamera.boardScale()` = 1.8）；而且世界格与屏幕像素之间还有
  棋盘原点与相机投影。第一次修完，雾在屏幕上整个不见了——两处各错一次。

## 定论

- **云是一条带子，不是八朵云**：`fog_.jpg` 是**一整条连续云带切成 8 片**（1680×190 = 8×210×190，
  水平周期 420/840、内容上下留 10px 重叠）。所以帧号由格子的 x 位置决定
  （`frameFor = cellX*80/210 mod 8`），不是随机挑的——原版 `mGridCelLook = Rand(20)` 能成立是因为
  它那 8 帧是八朵可互换的云。挑错帧相邻格就对不上、整条带出现接缝。
- **烘焙曲线只有一个目的：让这张图当 alpha 用**（`tools/gen_fog_texture.py`）：灰阶去掉 JPEG 的
  黑底振铃、提为 alpha，颜色染成**夜色蓝灰** `(0.58,0.63,0.75)`（三份候选烘出来实机比对后选的——
  源图是白云，白云压在夜池上是一堵白墙）。`ALPHA_LIFT=0.25` 是因为单帧有大量空隙，按 80px 步长
  合成后一条带只有 0.76 均值、十分位 0.17，像一层纱；抬四分之一后同一测量是 0.92 / 0.71。
- **绘制照原版**：逐格 `x*80-15, y*85-30`（背景图像素）× `camera.boardScale()`，**世界格**交给
  `client.drawTextureShaded`（不是自己乘 `unitX` 画屏幕像素——那样整条带会离开屏幕）。每格一个
  alpha（= 关卡的 `max_alpha`）与一个明暗漂移（原版两个正弦：周期 5.2s / 9.4s，逐格相位
  `6π/9`、`6π/7`，下限 0.55）。行数比棋盘多一行、列多一列，与 `x < MAX_GRID_SIZE_X` 同一读法。
- **隐藏判据仍是 `FogData.alphaAt` 的唯一读数**：`hidingColumn()` = 关卡自己 span 里
  **0.1875 格**处（格子左边 0.1875 是云开始的地方，也就是原版"第一个有雾的格子就藏"）。
  曾试过"从云的合成 alpha 反推边界"，已回退：云的 alpha 是个阶跃（半个格子内就吃满），
  从它推出来的线会让 `start_column` 失去意义；那条推理留在 `hidingColumn` 的注释里。
- **路灯是逐顶点 alpha**：新增 `PvzceClient.drawTextureShaded` / `SpriteRenderer.texturedQuad`
  的逐角 alpha 重载，路灯覆盖到的格子按 **4×4 细分**、逐角取 `FogMechanic.alphaAt`。一个半径 2.5 的
  灯因此有约二十级 alpha 跨过自己的边——从"十边形"变成圆。
- **死掉的东西删掉**：`fog_alpha.png` 与 `tools/gen_fog_gradient.py`（渐变不再被任何绘制读），
  对应的对拍测试换成"云图在 classpath 上、且是有空隙的云而不是一块黑"。
- **`fog.jpg` 没被用上**：它是那条近乎均匀的灰带（1%/99% 分位 151/221），当底雾可以、当云不行，
  所以留作参考不动。

## 验到了什么

- 冒烟（`.smoke/fog-original/`，两次启动）：`tint_b.png` 是 4-1（雾从第 6 列），
  `deep49.png` 是 4-9（雾从第 4 列，能看到整片絮状云与逐格的明暗差），
  `lamp.png` 是两株路灯花在雾里抠出的**平滑圆洞**（这一张同时验了逐顶点 alpha 那条新路）。
- 三份 tint 候选先渲染成剪贴图比对再定色；`tints.png` 留在同一目录。
- `FogClientMechanicTest`（新，7 例）：4-1 上"clear → 雾第一列 → 深处"的隐藏行为与
  `hidingColumn` 的两侧各差 0.01；路灯把自己的格子照亮但不影响它照不到的地方；没有雾的关卡
  什么都不藏也不画；`max_alpha=0` 时 overlay 与隐藏一起消失；树格偏移/尺寸与 1.8 倍缩放；
  云图确实是 8×210×190。
- `FogMechanicTest`：云图在 classpath 上、且明暗两面都存在（防止烘成一块黑）；
  `FogWorldLevelsTest` / `StormClientMechanicTest` / `OriginalAdventureLevelsTest` 全绿——
  隐藏规则变了，关卡表那几条断言仍然成立（4-1 第 6 列起被藏，与 `start_column` 一致）。

# 节奏草坪重做（能量条、连击辣椒、站酷判定）与关卡集合（tags、新分类）

> 用户一次报了五件事：判定字要站酷体 + 打击动效、按下键就要点亮判定区、连续 PERFECT 的乘数与
> 30/50/80/100 的火爆辣椒、能量条及其两档子弹倍率，以及"关卡集合"——把 1-x/2-x/3-x/4-x、
> 变异、节奏草坪各收进一个盒子，盒子在列表里长得和普通关卡一样、右下角写"内含 x 个关卡"。
> 前者是节奏草坪这一关"太简陋"的补完，后者是列表结构第一次有了第三层。

## 现象与根因

- **判定字用的是思源黑体**。`InGameScreen` 画判定字走的是 `fonts().body()`，而项目里"站酷快乐体"
  （`fonts().button()`，`assets/pvzce/font/zhanku.ttf`）一直是按钮/标题/HUD 数字的角色——模式里
  最需要"有反应"的那四个词，恰好是全项目唯一一处没用它的地方。而"打击感"当时完全不存在：
  400ms 里字的大小、位置、透明度一动不动。
- **判定区只在命中之后才亮**。`playRhythmLane` 先判定、`press()` 返回 `null` 就直接 return，
  于是"空按"在画面上与"按键没生效"完全一样——而这两件事把玩家送去两个不同的地方。
- **能量与连击没有**。节奏模式只有"命中数 + 连击数"两个计数器，没有任何会随时间变化的资源，
  也没有"打得久就有回报"的东西：30 个 PERFECT 和 30 个 FAIR 在画面上只有一行数字的差别。
- **列表只有两层**。分类由 id 路径前两段决定（`LevelGrouping`），页 = 主题 × 分类，没有第三层，
  也没有"一个关卡属于某个组"的表达方式：40 关冒险平铺在一页、变异四档和五条无尽混在生存页。
- **一个只有测试能看见的坑**：服务端把列表行收集进一个"按排序键索引的 Map"，而集合的排序键
  **就是它第一个成员的 id**——盒子那一行被成员那一行覆盖，而成员又是页面要过滤掉的，于是整个盒子
  从列表里消失，两侧单独的断言却全绿（`ServerMenuFlowTest` 那条回归测试是为此补的）。

## 定论

- **判定字走 `fonts().button()`（站酷），动效是三条纯曲线**：`RhythmPlay` 上新增
  `verdictProgress/verdictScale/verdictAlpha/verdictRise`——落点 2.1 倍、`VERDICT_POP_SHARE`(14%)
  内回落到 1 倍、全程上浮 16 单位（二次曲线，前段快）、最后 45% 淡出；`TextStyle.outline` 描边
  （草坪 + 僵尸 + 火焰上都要读得清）。曲线在 `RhythmPlay` 而不是在屏幕里，因为那里已经放着
  `VERDICT_NANOS`，而 `RhythmPlayTest` 不需要渲染器就能钉住它们。
- **按下即亮，命中与否分色**：`RhythmPlay.pressed()` 在判定**之前**记下"哪一列刚被碰过"，
  `pressFlash()` 给一个 150ms 的衰减值，`pressedGrade()` 是命中时的判定（空按为 `null`）。
  屏幕侧 `rhythmLaneColour` 三态：命中取判定色（金/蓝/灰红）、空按中性白、没人碰是原来的暗琥珀；
  判定线与按键胶囊同一颜色、同一闪，并多一条更宽的辉光。
- **能量条与连续 PERFECT 并进 `pvzce:rhythm`**（当成模式规则，不新造机制块）：数值全部进
  `PvzceConstants`（`ENERGY_PERFECT/GOOD/FAIR/MISS`、`ENERGY_DRAIN_PER_SECOND`、`ENERGY_MAX=6000`、
  `ENERGY_DOUBLE_AT=3000`、`ENERGY_TRIPLE_AT=5000`、`PERFECT_STREAK_MILESTONES={30,50,80,100}`、
  `PERFECT_STREAK_STEP=20`）。能量按 tick 小数累积（5/秒 = 1/12 点每 tick，整数会在两种取整里
  选一个错的）；建造阶段不涨不减（`PreparationMechanic.isPreparing` 之前就 return），暂停同样停。
- **乘数是"子弹数"而不是"攻击次数"**：`LevelAccess.projectileCountMultiplier(plant)` 是新的
  等级侧问法（`sporeRangeMultiplier` 的邻居），`LevelServer` 覆写为读 `RhythmMechanic`。落点是
  射手 `ShooterCapability.fire` 的三处 `shot.count()`（一个收窄点同时覆盖自己的时钟与谱面指令
  两条路）、投手 `ThrowerCapability.lob`（它没有 burst 字段，借射手的 6 tick 间隔，并补了一个
  `PendingLob` 队列让 hold-fire 关卡不吞掉余下的抛射）、玉米加农炮的 `launchAimedProjectile`。
  僵尸的豌豆走 `spawnZombieProjectile`，不乘。叠加关系按用户拍板：PERFECT 的 3 次齐射 × ≥5000 的
  3 发 = 9 发。
- **辣椒是"整行爆炸"，不是植物实体**：把 `ExplosiveCapability` 的 ROW 分支抽成
  `public static fireRow(level, row, damage, damageType, meltsIce, sound, team)`（行伤害 + 融冰 +
  每格一道 `JALAPENO_FIRE`），`detonate` 与 `RhythmMechanic.release` 共用一处几何；伤害/伤害类型/
  是否融冰/音效全部**从辣椒的植物定义读**（`PvzceIds.JALAPENO` + `PlantDef.capability`），
  于是数据包改了辣椒，奖励跟着改。`PvzceSounds.PLANT_JALAPENO` 新常量，给"没有植物可读"的调用方。
- **奖励在 `tick` 里发，不在 `judge` 里发**：`LevelServer.emitEffect` 在 `bridge == null` 时是空操作，
  而按键包是在 `level.tick` **之前**处理的——所以 `judge` 只把 `pendingJalapenos` 加一，
  `tick` 里 `release()` 才真的点火。一行胶片证实了这条：不这么做，五道火龙既没画面也没声音。
- **同步只有一条载荷**：`MechanicSyncS2C` 按机制 id 分发，所以 `RhythmMechanic.Start` 扩成
  `Status(tick, energy, perfect, good, fair, missed, combo, bestCombo, streak, multiplier, jalapenos)`，
  锚定时发一次、之后每 `STATUS_INTERVAL_TICKS`(6) 一次；两个读取点（`RhythmClientMechanic`、
  `InGameScreen.rhythmStatus`）同步改。
- **HUD 的"战况"全部来自服务端，本地镜像只留判定**：这是胶片抓到的第二个矛盾——同一帧里
  客户端把一次按键判成 GOOD、服务端按"取两边时钟里更好的那个"判成 PERFECT，于是
  `PERFECT 0 · 连续 PERFECT ×1`。定论：tally/combo/最高/连续/能量/倍率都读 `Status`，
  `RhythmPlay` 自己的计数器只负责**当帧的判定字与闪光**（帧是这一侧的）。顺带修掉了
  "续档后客户端计数从 0 重来"的老毛病。
- **关卡集合是 level 注册表上的 tag**（用户拍板"直接用 tags"）：
  `data/pvzce/tags/levels/collections/<名字>.json` → `#pvzce:collections/<名字>`，
  `PvzceTags.COLLECTION_PREFIX` 是"什么算集合"的唯一约定（别的 level tag 不会变成盒子）。
  成员顺序 = tag 文件里的顺序（`RegistryTagView.orderedIds`，`TagSet` 内部本来就是 LinkedHashSet，
  只有视图那层用 `Set.copyOf` 把顺序丢了）——变异因此可以是 easy/normal/hard/hell/tutorial 而不是
  字典序。**集合的页、图标、排序键都取自它的第一个成员**（`LevelCollections.Collection`）：
  没有第二处要同步的元数据，也自然得到白天草坪→夜晚草坪→白天泳池→夜晚泳池。
- **`LevelListS2C.LevelInfo` 多两个字段**：`collection`（这一行**是**一个盒子）与 `collectionId`
  （这一行**在**哪个盒子里）。成员行照旧下发——集合页要画它们的锁、存档与奖杯——只是
  `LevelPage.rowsFor` 把有 `collectionId` 的行滤掉，于是页面上一个关卡只出现一次。
  协议 `PROTOCOL_VERSION` 45 → 46，golden hex 重录（样本里补了一行集合，两个新字段才被钉住）。
- **客户端**：新增 `LevelRowRenderer`（两屏共用的行绘制，`showsTrophy`/`iconTexture` 从
  `LevelSelectScreen` 搬进去——判定只有一处）、新增 `LevelCollectionScreen`（`openScreen` 压栈，
  返回即回到原页与原选中）、`LevelSelectScreen` 的集合行显示"内含 x 个关卡"（右下角，与奖杯/
  id 文本共用一个 `reservedRight` 预留带）与"已通关 y/z"（状态行），动作按钮在集合上变"进入"，
  双击同一行也进入。集合名走 `level_collection.<ns>.<去掉 collections/ 的路径>` 语言键。
- **节奏草坪独立成分类**：`data/pvzce/level_categories/rhythm.json`（order 4，排在生存无尽后），
  四张谱面从 `yard/minigame/` 移到 `yard/rhythm/`，id 由 `pvzce:yard/minigame/rhythm_*` 变成
  `pvzce:yard/rhythm/rhythm_*`（**接受存档作废**，同 endless→survival 的先例，用户拍板）；
  编辑器节奏页的默认分类跟着改成 `rhythm`。

## 验到了什么

- `RhythmTest` 扩写（全部走真实路径：一张 40~120 个音符的长谱面逐拍打满）：三档各付多少
  （测在按键前后、中间不 tick，所以数字就是判定本身的）、每秒正好 -5、空条上的 miss 不会把条

# 节奏草坪的僵尸改成自动计算：没有波表、只有一段曲线

> 用户两条：能量两档 3000/5000 "太容易达到"，改成 **6000/12000**；以及"这几关不要有波数了，
> 无限出僵尸，过关条件必须是完成铺面，关卡只需要设置一个难度系数，后面出什么、出多少完全由
> 自动计算得出"。第一条是调参，第二条是把这一关的**出怪**从"写一张表"换成"算一条曲线"。

## 现象与根因

- **能量条的上限比第二档还低**：上一轮把上限定在 6000，而这一轮要把第二档抬到 12000——那样
  ×3 是个永远拿不到的数。上限必须高于最高那一档（改成 15000，第二档再加四分之一）。
- **四张谱面各写了一张六波的波次表**（`RhythmCharts.WAVES`，每档 6 波、总量递增、每波五行全点名），
  而这一关的时钟是歌：表在歌之前发完就只剩站着，歌放完却没发完就是白送。上一轮的生成器为了
  "表刚好铺满歌"把 delay 手写成一万 tick 左右——**那是一张一次性算好的表，改一个 BPM 就全错**。
- **"无限出僵尸"这件事已经有现成机制**：`pvzce:endless` 的数据表（`EndlessScheduleDef`：僵尸池
  按"轮"解锁）+ 纯生成器（`EndlessWaves`）+ 导演（`WaveDirector` 通过 `Host.waveAt(round, index)`
  一次要一波）。缺的不是机制，是**"轮"在节奏关卡里该是什么意思**。
- **导演的回合滚动是要玩家选卡的**：`rounds=true` 的关卡每轮结束走 `tickRoundClear`，弹"选卡进
  下一轮"并等玩家（超时才自动继续）。节奏关卡不能要这个——歌中间没有选卡这回事。
- **右下角那条波次条是 `totalWaves()` 画的**：只要它不为 0，屏幕上就有"第 N 波 / 共 M 波"。
- 顺带发现 `EndlessMechanic.previewWaves`（"生成波的关卡该拿第一轮当预览"）**没有任何调用方**，
  于是无尽关卡与节奏关卡的选卡页一直是空的僵尸预览。

## 定论

- **`RhythmChartData` 多一个 `difficulty`，默认 0 = 关**。0 表示"照旧用关卡自己的波表"（手写谱面与
  所有既有测试都不受影响），正数才打开模式自己的僵尸时钟。它同时是**关卡关于出怪说的唯一一句话**：
  **池子、解锁顺序、数量、间隔、血量成长全部自动算**。四档的系数是用户给的 **0.6 / 1.0 / 1.5 / 2.2**
  （`RhythmCharts.TIER_DIFFICULTY`）；上一轮那三张速度/间隔规则保留，它们说的是"僵尸走多快"，
  不是"来的是什么"。
- **"轮"= 歌里的位置**（`RhythmWaves.roundFor`）：`1 + 谱面进度 × 调度表的 count_ramp_rounds × 系数`。
  于是系数 1 表示"整首歌刚好把调度表走一遍"（最后一小节到池子顶部），2.2 表示"走两遍还多、收尾时
  每条曲线都进了封顶段"。谱面时钟只往前走，所以轮数单调——**池子只会越来越强，不会回头**。
  生成器一行没改：`EndlessWaves.wave(schedule, 轮, index, 水陆行, random)` 原样复用，
  连"水行只放会水的"这条行安全也是白拿的。
- **共享调度表 `EndlessSchedules.rhythmLawn()`**（id `pvzce:rhythm_lawn`）：普通僵尸开场，逐段解锁
  路障 / 旗帜 / 撑杆 / 铁桶 / 读报 / 橄榄 / 门板；**没有巨人**（键盘回答不了的墙）、**没有矿工与气球**
  （判定线盖不到的层）、没有水生（节奏草坪是草坪）。间隔取 360→120、波间空档 420→180
  （比无尽那两条紧：一首歌三分钟，不是一晚上）。
- **没有波表，也没有波数**：`waves: []`；`LevelServer` 里"生成波"的关卡现在有两种（无尽 / 节奏），
  共用 `waveAt` / `wavesInRound` 两条分支。`Host.showsWaveCount()` 是新增的那一问：节奏关卡答 false，
  于是 `WaveProgressS2C.totalWaves` 与 `LevelServer.totalWaves()` 都是 0，**右下角那条进度条整条不画**。
  **大波横幅保留**（用户要求）：预警走的是 `warningActive` 而不是总数，所以"一大波僵尸正在接近"
  照旧；而 `WaveWarningFinal` 需要 `WaveType.FINAL`，生成器只发 HUGE/SMALL，所以**永远不会误报
  "最后一波"**。
- **回合滚动是静默的**：`tickRoundClear` 对节奏关卡直接 `beginNextRound(bridge, false)` ——
  不弹选卡框，也不发"第 N 轮开始"那行消息。一轮 12 波（`RhythmWaves.WAVES_PER_ROUND`）纯属记账：
  歌长到超出它才会发生，玩家看不到任何痕迹。
- **赢法就是歌放完**（原来就是这样，现在成了唯一一条）：`end_beat` 到点 → `sweepLawn` +
  `declareVictory`；波次导演在"波是生成的"关卡上从不自行判胜（`endless` 位）。因此校验加了两条：
  **带系数的谱面必须写 `end_beat`**（否则是一局只能输的关卡），**也不能再写波表**（两个答案，一个会输）。
- **预览补上了**：`payloadFor` 里新的 `previewZombies` 先读关卡自己的表，读不到就问生成器要
  "开场那一波"——`EndlessMechanic.previewWaves` 那个死方法终于有了调用方，无尽的选卡页也一并有了
  僵尸预览。
- **能量**：`ENERGY_DOUBLE_AT` 3000→**6000**、`ENERGY_TRIPLE_AT` 5000→**12000**、
  `ENERGY_MAX` 6000→**15000**（上限必须高于最高那一档，否则那一档是个够不着的数）。
- **编辑器**多一栏"出怪难度系数"：只填一个（普通档的），四档按 `TIER_DIFFICULTY` 的比例摊开——
  "一个系数"这句话在编辑器里也成立。
