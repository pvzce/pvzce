# 架构变更记录

> 记历史：**现象 → 定论**。现状看 `当前项目架构.md`，取舍看 `决策记录.md`，教训看 `踩坑清单.md`。
> 写法：只记**最终落地的做法**；被回退的尝试最多留一行（"曾试 X，已回退，原因 Y"），
> 不给每个错误写长文。写之前先确认行为通过 —— 回退时这份记录要重写第二遍。

> **结构**：§1 是**定论索引**（一条一行，链到归档全文），§2 是**最近 3 轮全文**。
> 更早的每一轮在 `架构变更记录/` 目录里按 `YYYY-MM-<轮名>.md` 分卷（冻结不改）。
> 归档只搬家不改写：分卷前的每一节都在，找一条旧定论用 §1 的索引，或直接在该目录里搜索。
> 分卷规则：主文件留最近 3 轮，其余每轮一份；一条定论只在一个归档文件里，主文件不重复正文。
> 文件名不带空格（`/` 写成 `、`），这样链接可以直接写中文路径。

## W1 · 钉耙不是工具，而是一把原版的钉耙

> 这一轮是十项长线功能的第一个工作流（W1），改动最小、依赖最少、能立刻验。
> 用户报的是"钉耙不应该作为工具"，但顺着它查下去发现**四个**独立的错，每一个都能追到
> "某一层说错了"。

### 现象与根因

1. **钉耙是一张点了没反应的死卡** —— `data/pvzce/tools/rake.json` 与 `slots/rake.json` 把它注册成
   工具卡，效果 id 写的是 `pvzce:rake_placed`，而 `LevelServer.applyToolEffect` 的 `switch` 里
   **没有这一条**（落到 `default -> false`）。买了钉耙的玩家因此多出一张永远点不动的卡：
   服务端不扣费、不进冷却、也不回一句话，客户端只会重发一次 `SlotSyncS2C`。
2. **它同时在棋盘上存在（另一半是对的）** —— `RakeMechanic` 早就是完整的：开局在一条随机车道铺一把、
   第一只走到它那格的地面僵尸死、用过即消失、进存档。两半靠 `PvzceIds.RAKE` 一个字符串连着，
   于是"钉耙"这件事在代码里有两个身份。
3. **伤害写的是 `100_000`** —— 注释还写着"读小推车的数"，于是巨人僵尸也一钉死，与"钉耙是一条车道
   一次性的先手"这个定位矛盾。
4. **买来的钉耙客户端根本画不出来** —— 这是最隐蔽的一条：`LevelServer.payloadFor(def, seeds)` 发的是
   `LevelMechanics.payloads(def)`，也就是**关卡文件声明的**机制表；而玩家那把钉耙只存在于
   `LevelServer.mechanics()`（构造时由 `withPlayerMechanics` 加进去的解析结果）。客户端
   `ClientMechanics.worldOverlays` 遍历的是 `level.mechanicIds()`（= 下发的那张表），所以 overlay
   从来没有被创建过 —— **僵尸死得无声无息，草坪上一根草都没动**。没有关卡声明过 `pvzce:rake`，
   所以这条路一次都没被走过。

### 定论

- **钉耙不是卡**：删掉 `tools/rake.json` 与 `slots/rake.json`。`SlotResolver.resolve(pvzce:rake)`
  从此为空，选卡池再也不可能把它端出来。`ShopItems.Item.Kind.TOOL` 改名 `UNLOCK`（它本来就只是
  `profile.unlock(id)`），并新增 `STANDALONE_UNLOCKS` = "买了但不是一张卡的解锁"，只放钉耙。
  `ShopTest.theRakeIsNotACard` 把这个"不存在"钉成断言 —— 这是最容易被数据长回来的东西。
- **它站在从右数第 2 列**：`RakeMechanic.COLUMNS_FROM_RIGHT = 2`，9 列草坪即第 7 列，
  触发线就是那一格的中心。**位置只有一处**：客户端画的是服务端发来的 `x`，服务端算的是
  `columnX(level)`。它不再是"小推车锚点"的别名 —— 那个共用常量已经解开。
- **它值 1800 点**：普通/路障/铁桶/橄榄球都死（`pvzce:mower` 伤害类型 = 无视护甲 + 会分尸，
  与原版"踩上去头会掉"一致），巨人 3000 血扛得住。一条数值窗口，不是特例。
- **它只在草地上**：`Rig.place` 把候选车道里是水的那些剔掉 —— "哪几行是水"是棋盘的事实，
  `RakeData.rowsFor` 是文件的事实，两者不在一个地方回答。
- **它替玩家决定第一只僵尸走哪条道**：`WaveDirector.Host.forcedOpeningLane(zombieId)`（默认 -1）
  由 `LevelServer` 用"钉耙还在就报它的行"回答，导演只问**本关第一只**。这一条是"原版保证"
  的直接翻译：一把第一只僵尸永远走不到的钉耙，是一次什么都没做的购买。强制是**建议而不是覆盖** ——
  僵尸走不了那条道（走路的被塞进泳池）时照旧按普通规则发牌，所以 `rowFor` 的"按能不能走筛一遍"
  被提成 `usableLanes`，两条路共用。
- **"这里没有钉耙"要说出来**：以前 `rows: []` 让 `place` 直接 return，一个包都不发；现在仍然发一次
  `State(x, row = -1, spent)`，因为客户端无论如何都有一个 overlay，而"没有"与"没说"不该长得一样。
- **发出去的是解析后的机制表**：`LevelMechanics.payloads(List<TypedMechanic>)` 是新的一半，
  `LevelServer.sendFullState` 用它发**自己正在跑的那张表**。`payloadFor(def, seeds)` 保留给关卡列表 ——
  那张表是预览，钉耙的行是关卡创建时掷的，预告没有意义。**"服务端在跑什么"与"文件里写了什么"
  从这一刻起在下发路径上第一次分开**：以后再加"玩家带来的机制"（紫卡、节奏关）不会重犯这个错。
- **沙盒世界也有钉耙**：`PlayerProfile.ownsRake()` = `unlockAll || unlocked.contains(RAKE)`。
  以前直接问 `unlocked()` 集合，于是"全部解锁"的沙盒世界是唯一一个永远见不到钉耙的世界。
- **三个关卡明确说不要**：1-5（保龄球）、2-5（打地鼠）、4-5（恐怖花瓶）各写一条
  `{"type":"pvzce:rake","rows":[]}`。这三关里"免费杀一只"都不是这一关的意思，而
  "关卡声明了就由关卡说了算"这条三态语义正好用来表达它。
- **冒烟多一个钩子**：`pvzce.smokeSetup=<命令>`，在**开局请求之前**发控制台命令。
  `smokeCommands` 要等关卡起来才发，而"这个世界拥有什么"是关卡创建时读一次的，
  所以拍"有钉耙的棋盘"以前根本拍不到。发送顺序有保证：命令走服务端命令队列（每帧开头清空），
  开局请求走包连接（同一帧稍后清空），不会倒过来。

### 验到了什么

- `RakeTest`（13 例）：位置、1800 打不死巨人、水里不铺、第一只僵尸走钉耙那行、
  用过就不再指挥出怪、存档往返、`level init` 里真的有 `pvzce:rake`、没买的玩家没有、
  沙盒有、三个关卡声明 `rows: []` 时没有。
- 一次冒烟胶片（`.smoke/rake/s_*.png`，160 帧 / 每 15 帧一张，`smokeSetup=profile+unlockall`）：
  第 25 帧钉耙躺在第 7 列、第 40 帧第一只僵尸正好走到它脚下、第 55 帧僵尸中钉（powie + 头飞出去，
  原版的分尸表现）而钉耙消失、第 100 帧第二只僵尸踏着同一条道走进来。

## W2 · 编辑器图标、数据包文件夹、结算页的物品简介

### 现象与根因

1. **编辑器三个调色板全是品红/黑格子**：植物 41 行、僵尸 36 行、卡池 44 行。两处叠加——
   `PaletteList` 先问 `AnimationManager.iconTexture(id)`，而它拼的是 `animations/<id.path()>.json`
   （内置内容全在 `animations/<animation_dir>/<leaf>.json`，根目录下**零个** JSON），于是永远落空；
   兜底的 `EntityArt.sprite(id)` 给出的是**部件目录**（`textures/entities/plant/attacker/pea_shooter`
   是一堆零件 PNG），`TextureManager` 找不到文件就画缺失贴图那一格。两处都不报错。
2. `AnimationManager.iconTexture` 是**从上线那天起的死代码**（唯一的调用者就是调色板），
   而 `docs/架构-客户端.md` 一直写着它有效——文档与代码各说各话。
3. 数据包页只有"启用/停用"和"重新加载"，**没有打开文件夹**：想手改一个包得自己去猜
   `<gameDir>/datapacks/`。全仓库唯一的系统集成是模组列表里的 `Desktop.browse(URL)`。
4. 结算页的羊皮纸写的是 `金币 +{0}` / `金币总数：{0}`，与"这一页讲的是带走了什么"相反；
   而且 `LevelRewardS2C` 是**三个单值字段**（一个解锁 / 一个增益 / 一个物品），
   一次通关发两张卡时第二张照发不显示。

### 定论

- **一行图标是三种东西之一**：`PaletteList.Item.Icon` 是 `Texture` | `Rig` | 空（画色块）。
  判据只有一处——`EntityArt.animationFile(id) != null` 就是骨架，交给新的
  `components/EntityPreview`（把活骨架画进小方框的**有界**缓存，最多 24 具，在**绘制路径**上
  启播而不是等 `tick()`：预览是第一帧才建的，那一帧的 tick 已经过去了，图鉴当年就是这么让
  "每张僵尸卡都是空的"）。编辑器三页各持一个池，`onClosed` 里 `releasePreviews()`。
- **卡面行不走这条路**：卡池页改问 `CardPainter.icon(cardId)`——卡槽条与地上的种子包问的同一个答案。
  48 个卡槽里 44 个画的是一张与实体美术无关的卡面，问实体链必然问错人。
- **`AnimationManager.iconTexture` 删掉**（死代码），`docs/架构-客户端.md` 里那段"优先取动画资源"
  的说明重写成了上面这条。
- **守门测试 `EditorIconTest`**：每个卡槽的图标都指向真的存在的 PNG；每个植物/僵尸都以**骨架**
  形态到达调色板；并且断言植物声明的那张"贴图"确实不是一个文件。这三条正是当年该拦住它的东西。
- **数据包页多一个"打开文件夹"**：`client/gui/OSFolder` 是"把路径交给桌面"的唯一实现
  （先试 `Desktop.open`，失败退到 `xdg-open` / `open` / `explorer`；headless 与精简 Linux 上 AWT 会直接抛，
  所以两条路都要）。内置包没有目录、按钮说一句而不是打开别处；启动失败在页面上报一行。
- **奖励包从三个单值字段改成一张 `grants` 列表**（`CARD` / `BUFF` / `ITEM`，顺序即页面绘制顺序）：
  `headline()` 取表头 = "这一局最大的新闻"，相框与草地上掉的东西都用它；`hasUnlock()` /
  `unlockedCard()` / `unlockedBuff()` / `hasRewardItem()` 这些旧问题全部**由表头回答**，
  所以 `InGameScreen` 与掉落表现一行没改。协议 36 → 37。
- **结算页的正文变成"你拿到了什么"**：每样东西一行名字 + 它自己的 `.desc`（图鉴里那句话，不另写一份），
  金币降成页脚一行。放不下时按"**名字优先于句子**"贪心填，剩下的写成"还有 N 件"而不是截断。
  两个锚点：正文从美术的 `NOTE_TOP` 往下排，金币行锚在 `NOTE_BOTTOM` 与「继续」按钮上沿的**较高者**
  （按钮是这一页唯一必须按得到的东西，而 4:3 底图被 16:9 窗口上下裁过）。`Screen.CoverFit` 为此补了
  两个逆映射（`textureX` / `textureY`），免得调用点自己再写一遍 cover-fit 公式。
- **增益有了自己的 `.desc`**（5 条，中英各一份）：结算页要"简介"，而增益此前只有名字。
- **冒烟多一个钩子**：`pvzce.smokeEditorPages=<帧>:<页>,…`，一次启动拍多个编辑器页
  （与 `smokeAlmanacShots` 同一形状）。`pvzce.smokeScreen=award` 的合成奖励也换成"一卡 + 一增益 + 一物品"，
  否则新页面的列表、简介与金币降级一条都拍不到。

### 验到了什么

- `EditorIconTest`（3 例）全绿；全量 1177 例只有 `DocStatsTest`（统计块，按规矩由测试写回）。
- 一次 1080p+gui_scale=2（参考环境）的胶片：
  - `.smoke/w2/s_70.png` / `s_120.png` / `s_170.png`：植物调色板、僵尸调色板、卡池页画的全是**真美术**
    （僵尸那一页出现一个没有语言键的 id 回退，是 `.smoke/gd` 里遗留的测试数据包带来的自定义僵尸，不是缺陷）。
  - `.smoke/w2/s_270.png`：数据包页三个按钮——始终启用 / **打开文件夹** / 重新加载。
  - `.smoke/w2/f_120.png`：结算页一次发三件——「获得新植物！」+ 向日葵 + 它的一句简介 + 自动拾取 +
    「还有 1 件」+ 降级后的金币行。
  - `.smoke/w2/f_220.png`：纯金币那一支，三行全部落在羊皮纸里。

## W3 · 四档全局难度

### 现象与根因

**项目里根本没有"难度"这个概念。** 30 条 `GameRules` 是每关一份、由关卡文件写的；`MutationDifficulty`
那四档只管变异关卡自己。于是"简单/普通/困难/地狱"要从零建，而它要动的那四样东西（僵尸血量、
移速、出怪间隔、阳光产出）**全都是按关卡生效的规则**，其中有两条（血量、植物攻速）只在
生成/种植那一刻读一次。

### 定论

- **难度是"折进规则里的因子"，不是第 31 条规则**：`common/level/Difficulty` 是个四档 enum（带 codec），
  四个参数乘进 `zombie_health_multiplier` / `zombie_speed_multiplier` /
  `zombie_spawn_speed_multiplier` / `sun_rate_multiplier`。**模拟里没有任何一处需要知道难度存在** ——
  僵尸问的还是"我这行这条规则是多少"。出怪间隔在表里读作"间隔乘多少"，落进规则时取倒数：
  那句"间隔 ×1.15"因此不必写成一个 0.87 的魔数。
- **普通档 = 原版，且这是构造上的事实**：四个因子全是 1，`ruleFactors()` 直接返回**空表**，
  所以"应用普通档"是零次乘法而不是四次乘一。没有档案的调用者（测试、植物 AI、编辑器预览、
  `openingBoard`）拿到的一律是 `NORMAL`，它们的数字与加难度之前逐位相同。
- **它随世界存**：`profile.dat` 的 `Difficulty`（缺键读作普通——一条写在这之前的存档不能因为
  加了个字段就变难）。服务端权威，因为决定游戏难度的东西不能由客户端说了算；客户端只拿到一个
  **名字**，用来画角标与勾选。
- **切换是即时的，运行中的关卡一起改**：`LevelServer.setDifficulty` 先把旧档的因子**除出去**再乘新的，
  所以"关卡自己写的那个数"不会被吃掉；已经放出来的僵尸保持生成时读到的值（血量与移速本来就是
  生成时读一次），下一只才用新档 —— 这是唯一不会让血条在玩家眼皮底下跳的读法。
- **存档要把它除回去**：`level.dat` 的 `Rules` 块写的是**关卡自己的数**，读档时 `applyDifficulty()`
  再折一遍。少了这一步，续档就是难度的平方（变异因子当年踩过同一个坑，所以这里直接复用了它
  在同一段代码里的位置与理由）。
- **`/difficulty [档]` 与 `SetDifficultyC2S` 是同一个门**：设置页与截图脚本都走它，所以
  "现在是哪一档"有一个不依赖 HUD 的答案。协议 37 → 38。
- **页面**：`SettingsScreen` 多一行"难度"（四行表从 3 行变 4 行，行高由 `GuiLayout.fitHeight` 重算），
  新 `DifficultyScreen` 四行按钮。**四行一样长**是有意的：`Button` 把自己的标签缩放到刚好放得下，
  短一行就会被画成大字，一页四种字号读起来像四件不相干的东西 —— 所以普通档也写出四个 ×1，
  "普通 = 原版"改画在标题上方（第一版画在下方，被第一个按钮的底板整个盖住了：控件在界面自己的
  文字**之后**画）。关卡列表的角标同理画在「剧情」按钮下面而不是同一行。

### 验到了什么

- `DifficultyTest`（12 例）：四档单调性、普通档零乘法、间隔的倒数是自己的逆、因子**乘**在关卡自己的
  数上（1-5 的 1.5 × 1.25）、切档不丢关卡自己的数、切换后新生成的僵尸吃到新血量而场上的不吃、
  档案往返、缺键与坏名字都回落到普通、**存档里是关卡自己的数**（续档不平方）、无档案的关卡玩原版。
- 一次 1080p+gui_scale=2 的胶片 `.smoke/w3/d_120.png`（难度页四行 + `●` 在切到的那一档 + 标题上方的注解）
  与 `badge.png`（关卡列表左上角"难度：地狱"），设置页的四行表同一张里拍过。

## W4 · 键位设置、聊天行、截图与血条

### 现象与根因

**每一个绑定都是 `pollInput` 里的一句 `key == GLFW_KEY_*`**：玩家改不了，加一条要手改那一处，而且
"窗口的事"（全屏、诊断面板）与"关卡的事"（用哪张卡、打字）混在同一个循环里，顺序靠注释维持。
**没有聊天行**：`T` 打开的是一个空控制台 —— 于是"聊天"与"命令"是同一条东西、同一个面板、同一个键，
`/` 没有绑定。**没有截图键**（要看画面只能跑冒烟），**没有血条**：客户端只镜像当前血量，
"占最大值的比例"这个数它根本没有。

### 定论

- **一张表**：`client/input/KeyBindings`（12 个 `Action` → GLFW 键码），`PvzceClientConfig` 的 `[keys]`
  表往返（`KeyBindings.from` **逐条**回落：旧档案缺一项只丢那一项）。键的名字归这张表自己
  （`glfwGetKeyName` 要 scancode，而设置页要为一个没人按的键画名字）。
- **一键只属于一个动作**：`bind` 把键从原来那个动作手里**拿走并留空**，而不是给它搬家 ——
  "两个动作一个键"不是玩家能表达的设置，后者只会永远不触发。
- **动作分两类，各走各的门**：窗口的（F11 全屏 / F3 面板 / F2 截图 / F10 血条）在
  `handleBoundAction` 里就地答完，所以控制台开着时它们照常生效；关卡的（T 聊天、`/` 命令、
  1~4 工具）交给 `InGameScreen.keyAction` —— 工具键要光标下的格子，聊天行是关卡自己的浮层。
- **工具键认工具，不认卡位**：`1` 永远是铲子，不管它在这关的卡槽里排第几。验收就选在这一点上：
  `combat_test` 的铲子是第 **12** 张卡（14 槽的牌堆，屏幕只画得下 11 张，它被挤在 `1x` 按钮底下），
  按 `1` 照样把它挖在光标那一格上。工具箱里没有这把工具时**安静吃掉**：键是工具的、工具不在这儿，
  去摇一张不在屏幕上的卡没有意义。另外三种拒绝（不在运行中 / 暂停 / 卡不可用 / 光标不在草坪）
  各有各的出口，`-Dpvzce.traceInput=true` 会把是哪一种打出来 —— 它们**全都安静**，
  "按了没反应"否则无法与"键根本没到"区分。
- **聊天行走服务端**：`ChatC2S` → `PvzceServer.say()` → `ServerMessageS2C` 落回 `ClientLevel` 已有的
  那份消息表，浮层画的就是它。本地回显更简单，但"服务端没见过的话"不在任何人的日志里。
  这一步顺手修掉一个哑巴：`LevelServer.sendMessage` 要等一次 tick 装上的桥，而命令是在两次 tick
  **之间**跑的，于是"发出去了、也丢了" —— 改走 `send`（回落到关卡自己的出站口，和其它包同一条）。
- **截图在帧末读**：F2 只置一个待办位，PNG 在 `render()` 之后抓，与冒烟钩子共用 `FramebufferCapture`。
  在按键那一刻读缓冲，存下来的是**上一帧**。
- **血条要的是比例，所以新字段是 `EntitySpawnS2C.maxHealth`**（协议 38 → 39，冒烟的 golden dump
  跟着重生成）。HUD 只给"不满血"的东西画条，开关状态与消息日志同一处说一声（`血量显示：开/关`）——
  场上没有受伤的东西时，屏幕上不会因为按了 F10 而动任何一处。
- **`T` 与控制台从此不是同一条路**：`T` 开聊天行（底部一条，画的是关卡消息表），`/` 开控制台（面板，
  且预填一个 `/`）。两个键、两种面板、两套历史。
- **新页面**：`SettingsScreen` 多一行「快捷键」→ `KeybindScreen`（12 行，点一行进入"按一个键"，
  被夺键的那一行同时显示为未绑定）。

  于是"点击得到、按键找不到"。三处都修在各自的层上，验收是同一张图：
  `.smoke/w4/belt3/bar.png`（铲子卡就画在托盘右边）与 `s_120` → `s_300`（`1` 把向日葵挖掉）。

## W5 · 首次运行引导页：语言 + 界面大小

### 现象与根因

**"第一印象"这件事在代码里根本不存在。** 新装第一次打开就是标题页：界面全是硬编码中文（`GuiLang`
早就有一套键与 762 个中文词条，但读它的只有较新的几页），**没有任何地方能选语言**；而"自动"UI 大小
走的是 MC 的 `calculateScale` 上限（1080p 上算出来是 **4x**，界面只有 480×270，是每页布局所依据的
960×540 的一半）。两件都只有一个机会说：第一次打开的时候。

### 定论

- **就两问**：语言、界面大小。两者都是"玩家这台机器"的事（他读哪种字、屏幕多大），都必须在使用任何
  界面之前定下来，而且都**事后找不到** —— 读不懂当前语言的玩家，正是找不到设置页的那个人。
- **答案由页面自己演示**：选语言 → 这一页每个字立刻换成那种语言；选大小 → 整个界面立刻按那个比例重画
  （`setLanguage` / `setGuiScaleSetting` 都是即时生效的）。做一个"预览面板"就等于在另一个比例下再画一份
  界面，而"我能不能看清"最诚实的预览就是正在读的这一页。
- **它是"一页"，不是"一串控件"**：一块居中的石框面板（`NinePatch.drawDialogFrame` —— 与暂停框、确认框
  **同一份**九宫格美术，为此把那份贴图 id 与切片尺寸从 `Dialog` 挪进了 `NinePatch`），面板上面是游戏
  logo、里面从上到下是标题/说明/选项/步骤点/按钮。第一版把行钉在顶部、按钮钉在底部，在 1x（1280×720
  GUI）下标题压在 logo 上、中间空一大块 —— "在任何 GUI 高度下都读起来是一页"这件事只能靠整块面板居中。
- **键盘与鼠标等价**：方向键在当前这一步的选项里走并**当场应用**（与点击同一效果），回车 = 下一步/开始
  游戏，Esc = 回上一步且**永远不离开这一页**（新装时它下面没有页面可去，一页能被跳过的引导页等于自我跳过）。
- **语言是"发现"出来的**：`GuiLang.availableLocales` 扫包栈里的 `assets/<ns>/lang/*.json`，内置的
  `zh_cn` 排第一，其余排序。资源包多带一个语言文件，引导页与设置页就多一行。**每个语言文件写全所有
  语言的母语名**（`pvzce.lang.<locale>`），因为读这一行的人正是读不懂当前语言的人。缺名回落成 locale 码，
  不回落成空白。
- **"自动"改成"这个分辨率想要的那个比例"**：`recommendedScale` 取离 540 GUI 单位最近的一档（1080p → 2x
  = 960×540，1440p → 3x，4K → 4x，720p → 1x），并列时取**更小**的档（界面更大）—— 每页都是按 320×240
  的下限写的，超过目标那一侧才是会挤会叠的方向。`fitScale`（MC 的算法）仍是"最多能放到几倍"，手选
  的上限与它一致。
- **引导页只出现一次，判据在"文件在不在"**：`config.onboarded` 缺键 = **已经玩过的老玩家**（文件是旧
  版本写的，而那个版本没有这一页），缺**文件** = 新装。把两者弄反，就是给每个老玩家弹一次语言选择。
  回答完立刻落盘，不等退出。
- **视频设置页当场跟着本地化**，并顺手删掉一处会被翻译打断的逻辑：那一页原来用 `label.startsWith("全屏")`
  把按钮标签反查回它代表的设置，翻成英文就静默失效；行标签现在是每次重建时按设置重新算的（原来那套
  `setLabel` 刷新本来也刷在新的按钮实例上，等于没刷）。语言行就放在"UI 大小"旁边：界面的两件事。

### 验到了什么

- `OnboardingTest`（4 例）：语言表以内置语言打头且不重复、每种语言都用母语名互相称呼（`en_us` 视图里
  `简体中文` 仍读作"简体中文"）、推荐比例就是 1080p→2/1440p→3/4K→4/720p→1（且不超过能放下的上限、
  随屏幕变大不倒退）。
- `PvzceClientConfigTest` 加了两条：语言往返（空值回落到内置）、**只有全新档案才算首次运行**
  （文件在而键不在 = 老玩家）。
- 一次**全新游戏目录**（`.smoke/w5/fresh`，没有 config）的 1080p 侧 1280×720 冒烟，用 `smokeKeys`
  把两页走完：`f_60` 是中文那一步（`● 简体中文` + 面板 + logo）、`f_120` 按 ↓ 之后**整页变英文**、
  `f_180` 是大小那一步（`● Auto（recommended）1280×720 → 1280×720`，下面 1x/2x/3x 各自写明会得到
  多少 GUI 单位）、`f_360` 是回答完之后**英文的标题页**；跑完 `config/pvzce-client.toml` 里是
  `language = "en_us"` / `gui_scale = 1` / `onboarded = true`。

## W6 · 紫卡：种在别的植物身上的升级植物

### 现象与根因

**"升级植物"在这个项目里不是一个概念。** `gatling_pea` 与 `winter_melon` 早就注册好了（美术、行为、图鉴条目
都在），但它们和豌豆射手一样，是一张**往空地上种**的普通卡 —— 而原版那八张是 Crazy Dave 卖的**紫包**：
种在被升级的那株植物**身上**，并把那株吃掉。另外六株（双子向日葵 / 忧郁蘑菇 / 香蒲 / 地刺王 / 玉米加农炮 /
吸金磁）连定义都没有。**卡面也没有第二种颜色**：所有卡都画在同一张绿包上。

### 定论

- **升级是植物自己的一个字段**（`PlantDef.upgrade = {base, adjacent}`），不是标签：八张各认一株**不同的**底植物，
  标签表达不了"必须是这一株"。放在植物上而不是卡上，是因为放置规则、服务端结算与卡面颜色读的都是同一处。
- **放置规则在 `PlantPlacement.canPlace` 最前面短路**：升级卡只认"这一格里站着它的底植物"，其余一概不问 ——
  底植物当初就是按那些规则种下的，再问一遍会把唯一有用的场景（香蒲种在睡莲上，而睡莲让那一格水面可种）拒掉。
  两条附加条件：底植物是**载体**（睡莲/花盆）时它必须是这一格最上面那株（原版"莲叶上已经有植物就不能升级"，
  理由是升级要占据载体的位置，否则莲叶上那株会悬在水面上）；`adjacent` 要求同行相邻格再站 N 株底植物
  （只有玉米加农炮要 1，即原版的 2×1 玉米投手 —— 左邻优先，所以"消费哪一株"是确定的而不是"列表里先撞上哪个"）。
- **底植物是被"吃掉"的**：`LevelServer.consumeUpgradeBases` 在升级出现**之前**安静地移除它 —— 没有土坑、
  没有退款、没有死亡特效。原版那里不是一株植物死了、另一株来了，而是同一株变成了升级版。
- **紫包由调色板旋转生成**（`tools/gen_upgrade_packet.py`）：原版的紫包就是同一张画换了套配色，而仓库里只有绿的那张。
  逐像素把色相从绿转到淡紫、**保留明度与饱和度** —— 画的时候乘一层紫色会把高光压成灰的，读起来像"绿包盖了层滤镜"
  而不是"同一个包的另一种颜色"。卡面颜色由 `CardPainter.packetFor` 一处决定，两条卡槽、选卡页、结算页读的都是它；
  它同时接受卡的两种拼法（卡槽自己的 id 与它指向的内容 id），因为卡槽可以叫别的名字。
- **商店按原版金币价**（[$3000…$20000](https://plantsvszombies.wiki.gg/wiki/Upgrade_plants)）：机枪 5000、
  双子 5000、忧郁 7500、地刺王 7500、香蒲 10000、冰西瓜 10000（玉米加农炮 20000、吸金磁 3000 见下）。
  买下即入背包，"已拥有"由档案里那个 id 回答，选卡页从此给出这张紫卡。
- **香蒲的"打全场"是射击者的一条新字段**（`ProjectileRef.target_row`）：`hasTarget` 与出手都走同一个
  "最近的、够得着的僵尸"搜索，所以"决定开火"和"从哪一行出去"不可能各答一套。**忧郁蘑菇的"四周一圈"是
  `SpikeCapability` 多了一个 `rows`**：地刺的"就这一格"与它的"上下各一行"于是是同一个循环换个数字，
  而美术那一侧它的开火片段叫 `attack` 而不是 `shoot` —— 那条能力发布的状态是 ATTACK，片段名对不上时
  动画管理器会静默回落到 idle（**这是这一轮里唯一一处"看着对、其实没动"的缺陷，由转换美术的那一半发现**）。

### 验到了什么

- `UpgradePlantTest`（7 例）：只认自己的底植物（豌豆射手不算）、空地不能种、载体上有植物时不能升级、
  2×1 的玉米加农炮规则（相邻才算、隔一列不算、左边也行）、**种下去之后底植物没了而升级在、只扣一次阳光**、
  放错时的拒绝会说话、以及八张升级的 `base` 都指向真实植物且都有卡。
- 一次 1080p+gui_scale=2 的冒烟（`.smoke/w6/shots/u_190.png`）：卡槽里六张紫包与它们的底植物卡两两相邻
  （机枪/双子/忧郁/地刺王/香蒲/冰西瓜，价格分别是 250/150/150/125/225/200 阳光），草坪上是 `/spawn` 出来的
  双发射手与机枪射手、向日葵与双子向日葵 —— 卡面颜色、卡上价格与两株新美术一起被拍到。
  冒烟用的关卡是 `.smoke/gd-1080/datapacks/w6_smoke` 里的固定牌堆（仓库里的关卡还没有一张发这些卡）。

## W7 · 准备阶段：先摆阵，再放僵尸

### 现象与根因

原版的"谁笑到最后"开门先给一笔阳光、空草坪上随便摆，摆完按开始才出怪 —— 这个项目里没有这回事：
关卡一开始 `waves` 就按自己的时钟走，"先摆好"只能靠玩家手快。要把它做成一个**机制**（而不是给某个
小游戏写一段特例），因为它是**两个**工作流共用的：谁笑到最后（W8）与节奏草坪（W10，谱面要留一拍让玩家读）。

### 定论

- **它是一个关卡机制**（`pvzce:preparation` + `PreparationData`）：`manual`（玩家按开始）/ `ticks`
  （自动倒计时）二选一，`refund`（这段时间里铲掉植物**全额退款**，默认开）。机制系统本来就是这个用途，
  关卡文件写一行就有这一阶段，`LevelServer` 不需要认识哪个小游戏。
- **阶段里只停两样东西：出怪与天上的阳光**，其余全是普通规则（同样的卡、同样的价格、同样的放置判定）。
  「只能花初始阳光」这条规则因此是**构造上的事实**而不是一句检查：天上不掉，钱包就只有关卡给的那笔。
  阳光时钟也**不 tick**（`maybeSpawnSun` 内部走时钟），所以阶段结束后的第一颗阳光是完整一个间隔之后，
  而不是"结束那一帧就掉一颗"。
- **阶段是服务端状态，进存档**：中途退出再进来必须还在准备阶段 —— 反过来（读成"波次已经开跑"）会把第一波
  砸在一个还没摆完的阵上，而这种错只在你退出过一次之后才出现。存档里缺这个键 = 老存档 = 波次本来就在跑。
- **开始由服务端说了算**：`StartWavesC2S`（协议 39 → 40，无字段）由玩家那个按钮发出，服务端问一句
  "现在还在准备吗"，所以按两次、或者按下的那一刻正好撞上自动倒计时，都不会把波次开两遍。
  客户端那半（`PreparationClientMechanic`）只把 `preparing` 一个布尔镜像到 `ClientLevel` ——
  按钮画在关卡 HUD 里（与波次条、卡槽同一层），而不是机制自己画一套 HUD。
- **按钮是懒创建的**：这个状态是**流**下来的，到得比 `InGameScreen.init()` 晚，所以它不在 `init()` 里
  建（那时还不知道有没有这一阶段），而是在第一次看到阶段的那一帧建出来、加进 `widgets`、阶段结束就隐藏；
  `init()` 每次重建时把它置空（`clearWidgets()` 已经把旧控件扔了，字段还留着就是一个没人画的按钮）。
  这样做换来的是**游戏自己的按钮美术**（悬停、点击音都跟着），比手画一个矩形好看，
  也避免"画出来的矩形"和"可点区域"各算一遍。

### 验到了什么

- `PreparationTest`（6 例）：阶段里**没有阳光也没有僵尸**（手动阶段等多久都算数）、开始之后天上开始掉、
  **阳光时钟在阶段里不走**（十倍的间隔之后开始，也不是那一帧就掉）、自动阶段在自己那一刻开始（299 帧还在准备、
  301 帧已经开跑）、**铲掉植物全额退款**（钱退回它自己定义里那个数）、以及状态真的流给了客户端（开始前后各一条
  `MechanicSyncS2C`）。
- 一次 1080p+gui_scale=2 的胶片（`.smoke/w7/shots/p_180.png` → `p_420.png`）：准备阶段那一帧是居中"开始"按钮
  +「准备阶段：只能用初始阳光，摆好再开始」+「可用阳光: 500」，草坪上没有僵尸、天上没有阳光；

# 十三条美术/玩法缺陷：逐条定位到"哪一层说错了"

> 用户一次报上来十三条。它们的共同点是**每一条都能追到一个说错了的地方**，而不是十三处
> 画得不好——所以这一轮的做法是先把每一条定位到"数值/机制/素材里的哪一处是错的"，再改那一处。

## 现象与根因（按报告顺序）

1. **撑杆/海豚的落地位置与实际位置不符** —— `VaultCapability` 用自己发明的
   `AIRBORNE_FROM/TO` 缓动把位移摊在窗口上，而美术画的是另一条曲线（脚从帧 13 抬起到帧 36 落下）。
   两条曲线在落地时差**半格**。另外僵尸自己的 `height` 一直是 0，所以美术收起的腿被画在
   地面线以下。
2. **商店点击无效** —— `ShopScreen` 把购买写在 `onMouseClicked` 里，而
   `AbstractSelectionList.mouseClicked` 会吃掉点击并只调它自己的回调。行点击因此完全没反应。
3. **倭瓜会被啃掉 / 只压一只** —— `SquashCapability` 是单目标，且没有 `walk_over` 标签。
   用户拍板"可啃，但是激活时无敌"，于是改成 `invulnerable()` 在 `look/fuse/linger` 三态为真。
4. **三线射手头不跟着动 / 三发分开** —— 导出器把每根骨头都挂在 root 上，而动画里三个头的位置
   是"静态"的：原版靠 `anim_head1/2/3` 控制轨移动它们，转换器看不到没有图的轨。另
   `plants/threepeater.json` 三个 entry 的 `initial_delay` 是 0/30/60。
5. **坚果被啃后外观不变** —— `Wallnut_cracked1/2.png`、`Tallnut_cracked1/2.png` 不被任何轨
   引用，转换器不会发现它们；引擎那时也**没有**"按血量换植物贴图"这条路。
6. **传送带关卡没有铲子** —— 六个传送带的 `slots` 全是 `[]`，而 `BeltCardSource.rebuildBar`
   会把玩家的非植物卡留在带子右侧。校验器却禁止"传送带 + 任何 slots"。
7. **火爆辣椒用樱桃炸弹的特效** —— `ExplosiveCapability` 的默认粒子是 `EXPLOSION_POW`；
   原版那趟火是 `refer/anim/fire.reanim`，没转过。
8. **冰车该被地刺扎毁 / 要有破损 / 爆炸动画错** —— `ZamboniCapability` 无差别压碎格里所有植物；
   `Zombie_zamboni_1_damage1/2.png` 与 `ZamboniExplosion{,2}.xml` 的五个发射器都没接。
9. **高坚果体积不对** —— `tall_nut` 与 `wall_nut` 共用 `PLANT_BOX`，146px 的身体被塞进 0.76 格。
10. **雪橇没被显示** —— `Zombie_bobsled.reanim` 里只有骑手，`refer/` 全库没有那块板子。
11. **工具花瓶用了花盆贴图** —— `tools/vase.json` 写着 `gui/cards/flower_pot`，
    `make_vase_tool_anim.py` 就是照花盆控制器生成的。
12. **花瓶大小错误** —— `scene/vase.png` 是项目自画占位，比例不是原版那只。
13. **阳光铲贴图错误** —— `gui/buff/sun_shovel.png` 是一张 1254² 的写实插画，风格与游戏无关。

## 定论

1. **跳跃僵尸按美术自己的曲线走**：`VaultCapability` 的 `VAULT_TRAVEL_KEYS` / `VAULT_LIFT_KEYS`
   由新工具 `tools/vault_curve.py` 从**转换后**的 `jump` 片段里读出来（躯干管水平、最低的脚管
   抬升），`DEFAULT_JUMP_DISTANCE` 改成实测的 1.0908 格，`advanceVault` 同时写 `cellX` 与
   `height`。pogo 没有水平位移，继续用缓动。`PoleVaultTest` 新增一例把两张表钉在片段上。
2. **商店是"选中 + 购买按钮"**：行点击走 `setOnRowClick`（列表先吃点击是既定规则），右侧
   1/3 是详情栏，购买按钮钉在面板内右下角（`MenuPageCanvas.Canvas.widgetAtInterior`）。
3. **倭瓜激活即无敌，落地压整格**：`land()` 按落地格筛 `enemiesInRow` 逐个 `crush`。
4. **导出器支持真实的父子骨**（`EntityConfig.bone_parents`）：子骨的键被改写成宿主空间，
   模型里声明 `parent`。三线射手三个头分别挂 `stem_1/2/3`；`initial_delay` 全改 0。
5. **植物按血量换图**：新 `client/renderer/PlantDamageArt`（`BoneArt` 的第二种实现，与
   `EquipmentArt` 并列），认模型里 `cracked_N` 这一族，按原版的三等分选；两个坚果的
   `damage_states` 在导出器里声明。`AnimationManager` 现在按 kind 分派两种 override。
6. **传送带的工具/资源跟着带子**：五个传送带关卡的 `slots` 加 `pvzce:shovel`；
   `ConveyorMechanic.validate` 从"不许有任何 slots"改成"不许有**植物**卡"。
7. **辣椒是整行火**：新粒子 `pvzce:jalapeno_fire`（`tools/gen_jalapeno_fire.py` 从
   `fire.reanim` 的 12 帧切出），`ExplosiveCapability` 对 `Trigger.ROW` 逐格发一条。
8. **冰车被地刺扎毁 + 破损 + 原版爆炸**：`ZamboniCapability.tickMovement` 见到
   `#c:walk_over` 的植物就同归于尽；`damage_states` 接上两张破损图（经 `equipment` 的
   健康驱动族）；死亡发 `PvzceParticles.ZAMBONI_WRECK` 五件套。
9. **高坚果按自己的比例**：`target_box` 换成按绘制框换算的 (0.623743, 1.093202)。
10. **雪橇是同一模型里的新骨头**：导出器新增 `EntityConfig.extra_bones`（宿主键 + 自己的
    贴图 + 模型空间的 y 偏移），板子只在 `walk` 片段 `force_visible`；美术是新画的
    （`tools/gen_bobsled_sled.py`），因为原版那张**不在 refer 里**。
11. **花瓶贴图来自原版**：`tools/gen_vase_art.py` 从 `refer/im7/images/Scary_Pot.png` 切出
    空瓶与绿瓶，写场景贴图、卡面与**单骨头**的工具控制器；`make_vase_tool_anim.py` 删除。
12. 同上——`scene/vase*.png` 不再是占位图，比例与原版一致。
13. **阳光铲是原版铲子 + 原版太阳**：`tools/gen_sun_shovel_icon.py` 合成 128² 图标，
    `BuiltInBuffs.SUN_SHOVEL` 的图标从 `auto_collect` 换成 `sun_shovel`。

  `BungeeAndZamboniTest.aSpikeweedWrecksTheZamboni`，改写
  `CombatSystemsTest.theThreepeaterOpensAllThreeHeadsAtOnce`。
