# 架构变更记录

> 记历史：**现象 → 定论**。现状看 `当前项目架构.md`，取舍看 `决策记录.md`，教训看 `踩坑清单.md`。
> 写法：只记**最终落地的做法**；被回退的尝试最多留一行（"曾试 X，已回退，原因 Y"），
> 不给每个错误写长文。写之前先确认行为通过 —— 回退时这份记录要重写第二遍。

> **结构**：§1 是**定论索引**（一条一行，链到归档全文），§2 是**最近 3 轮全文**。
> 更早的每一轮在 `架构变更记录/` 目录里按 `YYYY-MM-<轮名>.md` 分卷（冻结不改）。
> 归档只搬家不改写：分卷前的每一节都在，找一条旧定论用 §1 的索引，或直接在该目录里搜索。
> 分卷规则：主文件留最近 3 轮，其余每轮一份；一条定论只在一个归档文件里，主文件不重复正文。
> 文件名不带空格（`/` 写成 `、`），这样链接可以直接写中文路径。

## 2. 最近 3 轮（全文）

# 对战 AI 分两层：指挥官（大语言模型）+ Jev（战术），双方自动收集，植物方补上铲子

> 用户："添加一个大语言模型作为指挥官模型，每隔 30~60 秒查看一次场上状况，并将接下来大体的决策
> 方向写入 Jev 的提示词，让 Jev 可以更好的决策。同时，双方都启用自动收集，以及，你忘记给植物方
> 带铲子了。"

## 现象

- Jev 是一只**决策**模型，不是战略模型：它每三秒在"买得起什么"里挑一个，看不见"我方经济还没
  起来""这条车道正在被针对"这类句子。
- 对战关里只有 **AI 那一方**会自动捡阳光（`JevBrain` 自己的六 tick 扫掠），玩家那一方要自己点：
  一场人机对战变成了比谁点得快。而 AI 当植物方时它的阳光是凭空被捡起来的，两边规则并不一样。
- 植物方的卡条里**没有铲子**：种错了没法挖。僵尸方本来就不需要工具，所以这条只影响植物侧，
  而植物侧正是最需要反悔的一方（种错列、挡住自己的射手）。

## 定论

**1. 两个层级，两种节奏，两条独立通道。** `AiSettings`（原 `JevSettings`，这次一次迁移成名：
它描述的就是"一个 AI 端点"）有两个具名工厂：`jev()`（战术，`pvzce.jev.*`）与 `commander()`
（指挥官，`pvzce.commander.*`）。两者各有自己的 URL / 模型 / key、自己的 HTTP 客户端与工作线程：

| | Jev（战术） | 指挥官（战略） |
|---|---|---|
| 协议 | 决策端点：`{model, state, questions}` → 带概率的类型化答案 | OpenAI 兼容 chat completions：`{model, messages}` → 文本 |
| 节奏 | 每 3 秒（`decision_ticks`） | 每 30 秒（`COMMANDER_INTERVAL_TICKS`） |
| 输出 | 一张卡 + 一个格子 | 两句话的方向 |
| 通道 | `JevClient`（12 秒超时） | `CommanderClient`（45 秒超时，**独立线程**） |

分开的理由是**慢的一方不能占住快的一方的槽位**：思考模型一次要几秒到几十秒，而战术决策每三秒
就要一次；两个客户端各自"一发在途"。

**2. 指挥官看的是简报，不是转储。** `JevBrain.commanderSnapshot` 写中文散文：我方是哪一方、胜负
条件与进度、当前阳光、**手牌与价格**（买不起的标负号）、**每行有什么**（我方植物带格子、对方僵尸
带 x 与剩余血量），以及**它上一次自己写的计划**。最后一条是刻意的：看不到自己上次命令的战略模型
会不断重复它，看得到才会延续或解释改变。回来后存成 `directive`，进 Jev 请求的
`state.commander_plan`，并在 `action` 的判据里附一句"优先按它执行，但眼前局面与它冲突时按局面办"
——**服从一条过期的命令把车道送掉，比忽略它更糟**。

**3. 关掉推理是"能用"的前提。** 实测 `deepseek-flash` 是推理模型：不关思考时，同一句"接下来一分钟
干什么"回了 **1500~4000 token 的 `reasoning_content` 而 `content` 是空的**（`finish_reason:
length`，每次都把预算想光）；加上 `{"thinking":{"type":"disabled"}}` 后 **24 token、两句话、
`finish_reason: stop`**。这个字段不是每家都认，所以先带着它，遇到 400/422 就**去掉重试一次**并
记住不再带（一次额外往返，之后没有）。

**4. 双方自动收集：一个事实、一个循环、一扇门。** `LevelServer` 新增事实
`setBothSidesCollect`（对战模式在 `onLevelCreated` 打开），`tickAutoCollect` 是唯一决定"谁自动捡"
的地方：有自动拾取增益 → 捡玩家自己的；开了双方 → 捡两边各自的。**同一个循环、同一个 15 tick
延迟、同一扇门**（`collectResourceFor`），所以"自动捡到的阳光"与"点到的阳光"永远等值。
`JevBrain` 那套六 tick 扫掠删掉了：一个事实一个出处。
> 这里踩过一个坑：计时器表原本由增益路径在"没有增益时"清空，而新的使用者和它共用这张表——
> 每 tick 都被清空，计时器永远长不大。见 `踩坑清单.md` 188。

**5. 植物方补上铲子，而铲子不进 AI 的手。** 三个对战关的 `plant_cards` 末尾加 `pvzce:shovel`
（kind 是 `tool`，`max_seed_slots` 随之抬到 8/10/10）。AI 的手牌只看 `Slot.Kind.PLANT`（僵尸侧看
`ZOMBIE`），所以铲子**只出现在玩家那一侧**——AI 会铲自己的植物反而奇怪。
`VersusSideChoiceTest` 现在钉住"植物方的卡条里有铲子"。

**6. 那句话只给 F3 看。** 玩家的 HUD 不该收到对手的意图；开发者要回答"它为什么这么打"。于是它作为
`VersusMechanic.State.commanderPlan/commanderBusy` 下发（**它自己会变，所以它自己进下发判据**），
由 `DebugOverlay` 画在**右下角、对战面板上方**（那个角是比赛数据的，诊断盖住要对照的数字比画高
一点更糟）。冒烟多了两个钩子：`pvzce.smokeDebug=true`（冒烟按不了 F3）与
`pvzce.smokeScreen=ai_settings`。

**7. 设置页变成两块。** 战术与指挥官各自的"服务商 / 接口地址+模型 / key"，指挥官那行提示说明它每
30 秒做什么、去哪看。两块都在 `AiSettingsScreen`，一次 `save()` 一起写进
`config/pvzce-client.toml` 并一起发给服务端（`AiSettingsC2S` 六个字段，`PROTOCOL_VERSION` 51→52）。

**8.（用户报的问题）指挥官会点一张这场没有的卡。** 现象：明明僵尸卡组里没有铁桶，指挥官却写
"等攒够 75 立刻放一个铁桶僵尸"。查下来**简报里本来就有**场景与手牌（`当前阳光`、`手里的卡` 带
价格、每行内容），缺的是三处：
1. **没有说这份列表是完整的**。模型被要求"说一张具体的卡"，它在列表里看到 75 阳光的那张，
   就顺手写了原版里最出名的同名角色——实测旧提示词 **5 次里 1 次**发生（而且那次把
   `conehead_zombie` 的价格 75 当成铁桶的价格，说明它是在"翻译"而不是在抄）。
2. **卡名只有 id**，模型有空间把它换成自己认识的词。
3. **回来之后没人核对**，于是这句话进了 Jev 的提示词，也进了 F3 面板。

落地的做法：
- 简报把名单写成**闭集**（"你能用的僵尸只有这些（完整列表…）"+"列表之外的任何卡都不可用，
  不要提到它们"），并补上**收入节奏**（"阳光收入：每 5.0 秒 35"）——没有它，模型没法说
  "攒一手再买好的"。
- 要求**结构化回答**：第一行只写名单里的一个卡 id（或 `hold`），后面才是理由。
- **代码核对第一行**：解析出卡 id（容忍 `pvzce:` 前缀、反引号、`：`/`,`/空格等分隔符），不在
  手牌里就**整条拒绝**并 WARN 记录（含被拒原文与手牌内容）——理由是它后面的推理是针对一张不存在
  的卡推出来的，把推理转给 Jev 等于递过去一个建立在虚构上的计划。合法时卡 id 单独作为
  `state.commander_card` 交给 Jev，让它不必从中文句子里找卡名。
- 复测：同一段简报连打 5 次，**首行合法 5/5**（旧提示词 1/5 会点到名单外的卡）。

**9.（用户报的两个问题）AI 无视卡片冷却；僵尸方看到了只能由植物方捡的资源。**

**9.1 冷却：AI 以前根本不走卡片条。** 玩家的每一次落子都要过一条卡：`slot.ready()`（在冷却里
就不行）、扣阳光、扣一次使用次数、`startCooldown(effectiveCooldownTicks(slot))`。AI 走的是另一条
路——直接按内容 id 解析、只扣阳光——所以它**没有任何冷却**：阳光够就能连着下。这在植物侧最明显
（豌豆射手 5 秒、向日葵 5 秒、高坚果 30 秒；僵尸卡只有 1 秒，所以僵尸侧的差别几乎看不出来，这也
是当初没被发现的原因）。

做法是**给对手一条真的卡条**：`LevelServer.opponentPlayer`（`PvzcePlayer`，牌来自对战块的
`cardsFor(对方)`），与玩家的卡条并列创建、并列每 tick 走冷却（不发给客户端——客户端要知道的是
对手"做了什么"，不是它手上每张牌剩几秒）。收费这件事收成**一个方法** `chargeCard(owner, slot)`
（ready → 阳光 → 次数 → 冷却），玩家的僵尸落子与 AI 的两种落子都走它；落子被棋盘拒绝时用
`restoreCard(slot)` 把阳光、次数与冷却一起还回去（否则一次被占用的格子会让这张牌白等一整个冷却）。
两份提示词里也各多了一个事实：Jev 的 `your_cards[].ready` / `cooldown_seconds`，指挥官的简报写
"冷却中 N 秒"——不然模型会一直点它刚打出去的那张牌，然后被判据拒掉。

**9.2 只属于对手的资源实体不再画。** 对战关里植物方的阳光照常落地，玩家当僵尸方时那些阳光
**点不到**，画出来就是在骗人（它是全场唯一长得像"该去点它"的东西）。现在按**它所属的队伍**过滤：
`PickupVisibility.isVisible(controlledTeam, entityKind, dropTeam)`——只对资源掉落生效，队伍不同就
不画；玩家没有控制任何队伍（编辑器、旁观）时什么都不藏。这条规则独立成一个类，因为它的全部内容
就是三个字符串，而真正要测的那一种情形（玩家当僵尸方）需要一局僵尸视角的对局才看得见。

## 验证与边界

- **冷却**：`theOpponentCannotPlayTheSameCardTwiceInsideItsCooldown`——给植物 AI 一笔花不完的
  阳光，唯一能限制它的就是冷却：120 tick 内只许有一株豌豆（改回旧路径立刻红：`expected: <1>
  but was: <2>`）。这个用例顺带抓出植物策略的另一个毛病：选定一条车道后，那格被占就整回放弃，
  于是它种下一株之后**站着不动**；现在每条规则按优先级依次试车道。

  "对方植物方阳光 50 / 6000"、草坪上只有植物**没有一朵阳光**。
- 冒烟新增两个钩子：`pvzce.smokeTeam=zombie`（按关键字选边；它需要等关卡列表到达，所以会主动
  请求一次列表并最多等 240 tick）与 `pvzce.smokeDebug=true`。
- **简报原文**（`VersusModeTest.theCommanderBriefingNamesTheDeckAndNothingElse` 会打印它，并按

# 共鸣苔接入铃兰网络：强度随当前铃兰数量变化

> 用户要求铃兰的增速关联当前网络，并新增一株承载其它植物、让上层植物分享网络加成的原创植物。
> 确认后采用“共鸣苔”陆地底座，攻击与阳光生产一起加速，强度只计算真正的铃兰。

## 现象 → 定论

**1. 加速有网络规模，底座不能堆出强度。** 共鸣速度为 `1.5 + 0.25 × (铃兰数量 - 1)`，
上限三倍；一株 1.5 倍、三株两倍、七株封顶。只计同队、存活、醒着并占据格子的铃兰，
接入或移除铃兰立即改变之后的冷却进度；共鸣苔只传导，空铺大量底座不会变成免费增速。
普通关卡仍以三轮接力触发六秒爆发，温室行直接激活网络；自身爆发与行借来的倍率取较大者。
`plant_rate` 是行激活的倍率上限，并受全局三倍上限约束，不再表示固定倍率。

**2. 共鸣苔把底座与上层植物接到同一线路。** `pvzce:echo_conduit` 标记可传导的底座，
`EchoNetwork` 按格子做正交 BFS，同格铃兰和苔的传播距离为零，相邻格为一步。
铃兰仍每轮各发一枚声波，苔不发弹丸；源铃兰可以沿苔接到远处铃兰，环形网络不反复触发。
同队上层植物通过严格位于其下的共鸣苔接入；断线、底座死亡、来源消失或睡眠都会撤掉加成。
叠种判定沿用 `PlantPlacement` 与 carrier / plantable / requires_ground 标签：陆地和屋顶可用，
水面、同格花盆和睡莲不可叠放。承载层看定义的放置层，不能拿所有植物相同的实体绘制层来比较。

**3. 上层的攻击与生产获得真实进度。** 普通植物的 `actionRate` 合并网络倍率、关卡规则与浇水，
射手、投手、近战咀嚼、锥形喷吐、地刺、玉米加农炮装填和生产能力各消费自己的时钟。
加速改变攻击或生产间隔，不追加同帧子弹，不改变原伤害、阳光面值、卡槽冷却、爆炸引信或成长时长。
连接只提供共鸣时的加速，没有铃兰时保持普通速度；植物原本没有攻击/生产能力就没有可加快的动作。

**4. 一份服务端状态说明实际加成。** `EchoNetworkS2C` 携带实体、当前网络、铃兰数量、蓄能和倍率，
变化时下发，断开显式清零；全量进场在实体之后发送，暂停加入与续档也能读到实际状态。
客户端绘制金线、灯、圆环和“铃兰数量 / 速度倍率”，上层另有“接入 ×倍率”短标记。
客户端不重建加速规则；网络 id 仅是当前运行中成员的代表 id，恢复存档后重新建立。
新增包使用新 id，协议升至 48，并更新线格式快照。全量同步不吞掉其它客户端待收的差量状态。

**5. 通用时钟只累积当前 tick。** `RateClock` 改为累积本 tick 的倍率并保留小数余量；
连线、断线或倍率变化不会回算历史进度、突然补发或停止计时。参与周期动作的能力保存余量，
旧存档缺键时从零余量读取。恢复前后逐 tick 比较实际攻击、产阳光和铃兰接力时刻一致。

**6. 新植物从原创高清源图构建。** 使用内置 GPT Image 生成透明原画，源图与原始提示词保存在
`tools/art/resonance_moss.png` / `tools/art/resonance_moss.prompt.txt`。
`tools/build_resonance_moss.py` 输出 512×247 棋盘贴图、512×512 卡面及原生 idle / linked / charged 片段；
像素采样与 0.96 格模型宽度分开。导出边界忽略 alpha 不高于 8/255 的零散像素，保留主体透明度。
新图、卡面与原生动画均分类为原创，没有读取或复制原版角色造型。

**7. 新卡有正常获取路径。** 回声温室固定卡组增加共鸣苔，容量随之为八张；仍是 325 初始阳光，
相邻两株铃兰预置与原波表不变。共鸣苔成本 75 阳光、300 生命、五秒卡槽冷却；
首通和重玩都能解锁它，已通关旧版本的玩家可以重玩领取，再带进普通关卡。

# 回声铃兰蓄能速射：普通关卡自带共鸣，连接与爆发看得见

> 用户指出铃兰离开温室后特点变弱，并要求共鸣改为加快攻速。确认后选择“接力蓄能、短时爆发”；
> 继续制作时再次指出玩家几乎感知不到特性，因此补齐种植预览、常驻状态提示与明显的整组圆环。

## 现象 → 定论

**1. 普通关卡也有可积累的共鸣。** 相邻铃兰每发起一轮有限接力蓄一格，三轮后整组进入共鸣，
最后一声之后持续六秒、冷却进度以两倍速度推进。单株不靠独唱蓄能；爆发期间不继续累积下一轮。
每轮每株仍只发一枚原伤害声波，没有另加伤害更低的额外齐射。连接新成员不跳过旧成员冷却，
蓄能按组内最低值合并；接入已共鸣的组可继承其原期限，不能延长期限。

**2. 温室借攻速，不再借子弹。** `ResonanceMechanic` 每 tick 给与共鸣行相交的连通组授予
当前 tick 的攻速倍率；离行、断开或机制移除即停止借来的加速，自身蓄出的共鸣仍按原期限继续。
两种倍率取较大者，不相乘。机制编辑器以 `plant_rate` 替代旧的额外齐射间隔与伤害字段；
行移动、僵尸加速、状态同步与存档时钟保留。

**3. 冷却只消费当下速度。** 每株保存剩余工作量与接力尾声期限，每 tick 只推进一次；共鸣在
冷却中途开始或结束也只影响之后的进度。存档包含小数冷却、蓄能、自身共鸣期限与待发声波；
旧存档的 `readyAt` 与已安排声波仍可读取，未安排的新额外齐射不再产生。

**4. 能力要在棋盘上讲清楚。** `EchoLilyLinks` 是植物自己的渲染伴侣，所有关卡都可显示金线；
拿着卡移到邻格时先预览连接。由服务端射击状态触发连线光点，蓄能三格灯在 GUI 层画，
不会被叶片盖住；每个连通组显示一份“接力蓄能 / 共鸣速射”提示，独株提示相邻种植可接力。
攻击状态带蓄能片段别名，开火时不会把灯清成零。共鸣期间圆环常亮并缓慢呼吸，待机动作更快；
顶行提示遇到卡栏时侧移。圆环纹理读取粒子定义，不另造内容 id 到纹理的映射。

## 验证与边界

  冷却中途加入、移除共鸣机制不会突然补发；普通共鸣续档后逐 tick 比较后续射击时刻与音调一致。
  根株与响应株开火期间下发的状态均保留蓄能。
- 实际内置关卡、普通难度、真实阳光成本与卡槽冷却，固定种子 17 / 20261001 / 81 均胜利，
  战斗时间分别 192.9 / 168.6 / 160.1 秒，全部 35 只敌人参与；总花费均 1450 阳光，
