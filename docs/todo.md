## 玩法与内容

### 指挥官只看时间，不看事件

现状：指挥官的节奏是固定的 30 秒（`COMMANDER_INTERVAL_TICKS`），掉一条车道、丢一辆小推车、
对手经济翻倍这类**局面剧变**要等到下一个整点才会进它的简报。
影响：最需要战略重估的那半分钟恰好是它看不见的；玩家会觉得"它反应慢"。
怎么做：给 `JevBrain` 加一个"值得立刻重估"的事件判据（掉车道 / 丢车 / 对比分变化超过阈值），
命中就清零 `commanderCountdown`（一次剧变最多触发一次，避免抖动时连发）。
卡在：这是给指挥官加逻辑，而不是修 bug；先看真人玩下来是不是真觉得慢。

### 指挥官的方向只给 F3，玩家看不到

现状：按用户要求，那句话只在 F3 调试浮层里画。正常玩的时候玩家看不到对手在打什么主意。
影响：这一层是"给 AI 更好决策"用的，玩家侧的信息面没有变化——如果之后想让玩家也能看到
（比如做成"对手意图"面板），需要改的是显示位置而不是数据（`State.commanderPlan` 已经在传）。
卡在：**要用户拍板**要不要给玩家看。


### 关卡准备页的两块面板是空的

`LevelSetupScreen` 的两侧面板只画了 `plant_or_zombie.png` 的底板，**没有草坪预览**——对战关
从列表点进去时，玩家看到的是两张大空框，只有底下的"植物方/僵尸方"文字说明哪边是哪边。
影响：这是选边的唯一一屏，也是最该说清"这一局长什么样"的地方（原版这一屏画的是那一关的
草坪与僵尸）。
怎么做：面板里画一次关卡场景的缩略（`LevelPayload.sceneCells` 已经有了），僵尸一侧可以顺带
画 `previewZombies`。
卡在：这一屏在本轮之前**没有任何关卡进得去**（没有双可玩阵营的关卡），所以它一直是未完成品；
要做先问一句"这一屏要不要重新设计"，而不是临时补两块草坪。


### 出怪频率被"压力预算"卡住：想要更密的节奏就得给僵尸卡降价

现状：僵尸方 420 阳光/分钟 + "每三次买一张好牌"的固定配比，实测 6.5~7.7 秒一只、同时在场 3~5 只。
**到达间隔的上限由压力预算决定**（实测约 2400 生命/分钟是五列草坪能接住的上限）：单位越便宜、
同样压力下到达越密；单位越贵越硬、到达越稀。想要"又快又硬"，唯一的杠杆是**给僵尸卡降价**——
加一个对战的 `zombie_cost_percent`（例如 50%：普通僵尸 25、路障 37、铁桶 50），
压力不变而到达间隔减半。
怎么做：加这个字段后，**同一份"生效价格"要同时喂三处**——AI 的 affordability 与卡面描述、
玩家的 `placeZombie` 收费、以及卡条上画出来的价格（`toSlotInfo` 现在画的是卡自己的价，
而 `plant_sun_cost_multiplier` 已经在收费侧生效，这两处本来就不一致，顺手一起修）。
卡在：**要用户拍板**——这是给对战模式加一个新旋钮，不是修 bug；本轮先把取舍的数字摆出来。

### 对战关的平衡只有仿真证据，没有真人试玩

三关的时长（14:32 / 17:30 / 20:19）来自 `VersusModeTest.theShippedLevelsRunToAnEnd` 的无头仿真，
植物方由**测试里写死的脚本**驱动（先补受威胁车道的射手、再铺六株向日葵），僵尸方是内置策略。
影响：这条曲线是"一个像样的玩家能赢"的证据，不是"人玩起来什么手感"的证据；僵尸方什么时候
真的能破防（人类植物方失误、或 Jev 打得比内置策略更好）没有数据。
怎么做：找人打几局，把每局的收满时间与破防时间记下来；要调就动 `duel_*.json` 里的
`zombie_income_sun` / `zombie_income_ticks` / `plant_initial_sun` 三个数，不动机制。
卡在：需要真人试玩。

### Jev 的卡面描述是数据推出来的，没有语义

`JevBrain.describe` 给模型的每张卡描述是"id、阵营、价格、血量（僵尸还有速度）"，**没有**
"这是经济植物 / 这是群体伤害 / 这是溅射"这类语义。影响：Jev 只能从 id 与血量猜用途，
`sunflower` / `cherry_bomb` 这类名字好猜，原创内容（回声铃兰、共鸣苔）就不好猜。
怎么做：给 `VersusData` 加一个 `card_hints`（id → 一句话）让关卡作者写，或者在 `PlantDef` /
`ZombieDef` 上加一条"角色"字段。卡在：还没有证据说 Jev 因为这条打得很差——先看试玩。

### 对战模式的存档只记住了阵营

`LevelServer.save` 写了 `HumanTeam`，续档时服务端先读它再构造关卡（这是对的），但**没有**
记录"上一局 Jev 打到哪一步"——`JevBrain` 的决策倒计时与最近一手不进存档，续档后从零开始。
影响：续档后对手会立刻重新决策一次，观感上是"它忘了刚才在干什么"；机制状态（收集数、收入
时钟）是存了的，所以不影响胜负与平衡。
怎么做：把 `JevBrain` 的倒计时与最近一手写进 `VersusMechanic` 的存档块（它是关卡级的）。
卡在：这一条是"想起来才做"的小事，没有玩家报告。

### Jev 的 HTTPS 只在无头与单机上验过

真调一次（`JevLiveTest`）是单机、直连、一次请求的路径。影响：慢网、代理、需要重试的渠道
没有验证；`JevClient` 有意**不重试**（下一次决策更便宜也更新鲜），所以"偶尔少一次决策"
是设计而不是故障。怎么做：要支持代理就加一个 `-Dpvzce.jev.proxy`，要走公司网关就改 URL。
卡在：没有用户报告的网络环境问题。


### 回声温室的高难度节奏还没有单独校准

普通难度已经用实际关卡、阳光成本与卡槽冷却在固定种子下跑到胜利；困难与地狱仍沿用通用难度倍率，
没有各自的整局预算与通关证据。影响：普通难度的可玩结论不能推到更高档位。
怎么做：复用 `EchoConservatoryTest` 的付费种植仿真切换难度，记录实际出怪间隔、阳光收支与峰值，再调整关卡波表。
卡在：本轮确认的是普通难度的原创玩法，更高档位的目标压力尚未定。

### 回声铃兰的原创动画节拍是估的

没有原版动画参照，待机 2.4 秒、开火 0.48 秒、共鸣 0.65 秒及倾斜、压缩幅度是自行估计的。
攻速与反馈修复已用连续帧确认蓄能灯、状态标签与共鸣圆环可见；基础动作节拍仍是估计值，尚无玩家对新爆发节奏的试玩校准。
影响：技术上接好不代表节拍已经最合适。怎么做：用本轮帧带和实际试玩确认“蓄力—出声—回落”的读感，
需要调节时改 `tools/build_echo_lily.sh` 的关键帧与对应能力的归位时刻。卡在：缺少玩家对本轮最终版本的试玩反馈。

### 共鸣苔的原创动画节拍尚需玩家试玩校准

透明源图和三种原生状态已在连续帧中确认，待机 2.4 秒、接入 1.5 秒、共鸣 0.9 秒及压缩幅度是自行估计。
影响：底座的动感是否与上层植物合拍仍需试玩判断。怎么做：用共鸣网络帧带与实际布阵确认呼吸强弱，
需要调整时改 `tools/build_resonance_moss.py` 的关键帧。卡在：没有原版参照，尚未收到玩家对新底座的试玩反馈。

### 一整首歌的通关没有端到端跑过

`pvzce.smokeAutoPlay` 让"按谱面打"可以自动化了（连击、辣椒、战报都拍到了，见 `.smoke/rhythm-song2/`），
但**一整首歌（189 秒 ≈ 11k tick）跑到结算**仍然没有在冒烟里跑通过：无头运行里服务端要与渲染抢 CPU，
关卡时钟只跑到约 22 tps，一首歌因此要九分钟墙钟。影响：`end_beat` 判胜这条路有单测
（`RhythmTest.theEndOfTheSongWinsASpawningLevel`），冒烟里也拍到了"12 拍的短谱面放完 → 判胜 → 领奖励 →
结算页"（`.smoke/rhythm-report9/`，用的是一张冒烟专用的短谱面关卡），但**真实四档 + 真实出怪 + 打满全场**
这一组同时成立没有证据。
怎么做：给冒烟加一条"把谱面时钟快进"的钩子（例如让机制认一个 `-D` 的倍率，或直接把 `startTick` 往前挪），
在短墙钟里走到歌尾；或者在 CI 里给无头运行留足时间（九分钟一关，跑不起四档）。
卡在：**要用户拍板**——这是验证工具链的投入（快进钩子会让"歌与谱面同一 tick"这条性质在冒烟里失真），
不是玩法。

### 迷雾的浓淡与覆盖范围还没有和原版逐帧比对过

这一轮把雾重做成原版的模型（逐格铺云 + 逐格 alpha + 缓慢流动，见 `架构变更记录.md`），实机画面在
`.smoke/fog-original/` 里（4-1 的 `tint_b.png`、4-9 的 `deep49.png`、路灯的 `lamp.png`）。但**没有**
拿原版 4-1 的截图逐块对过亮度：现在的配方是"从 `fog_.jpg` 提 alpha、染夜色蓝灰 `(0.58,0.63,0.75)`、
抬 25% 底、逐格亮度 0.55..1.0"，其中底色与抬升量是**用三份候选实机比对眼选的**，不是量出来的。
影响：雾的"浓"与"冷"可能整体偏亮或偏暗，而这类偏差只有在同一块草坪上和原版并排看才发现。
怎么做：找一张原版 4-x 的实机截图，取"被雾盖住的草地/水面"与"雾里最亮处"两块的平均色，与
`tools/gen_fog_texture.py` 的 `TINT` / `ALPHA_LIFT` 对一遍；差得多就调这两个常数（只动烘焙，不动绘制）。
卡在：手上没有原版 4-x 的实机截图（`refer/` 里只有拆包素材，没有成品画面）。

## 关卡集合不能嵌套，也不能跨页

集合是 level 注册表上的一个 tag（`#pvzce:collections/*`），页、图标、排序键都取自它的第一个成员：
成员分属两个分类时，盒子只出现在第一个成员的那一页上，另一页的成员**也只能从盒子里进**（页面会把
它们滤掉）。嵌套（一个集合里放一个集合）现在既表达不了也会被 `LevelPage.membersOf` 当成"列表里没有
这个 id"直接跳过。影响：数据包作者做"资料片 → 章节 → 关卡"三层时只能平铺成两页。
怎么做：真要嵌套的话，`CollectionInfo.members` 得能引用另一个集合 id，`membersOf` 递归展开，
页面过滤改成"被任何集合直接或间接收走"。卡在哪：**没有真实需求**——用户这一轮要的六组都是一层，
加了就是替一个不存在的用法写代码。

### 集合盒子不显示自己的锁定状态

`LevelCollections.Collection` 只看成员，盒子本身永远是可进入的（成员各自带锁，进去能看到"需要通关
1-1"）。影响：像"夜晚草坪"这种整章锁着的盒子，在列表上看起来和已开放的一模一样，玩家点进去才发现
十个格子全灰。怎么做：`LevelInfo.ofCollection` 里按成员算一个"全部锁着/部分解锁"的汇总，行渲染
把全锁的盒子画暗一档（`LevelRowRenderer` 里已有 `locked` 的绘制分支，盒子只是没有来源）。
卡在哪：**要用户拍板**——上一轮的选项里"全锁时集合框变暗"没有被选中。


### 清完场之后没有原版那套"本波血量消耗"加速

原版 `Board::UpdateZombieSpawning` 里有一条本项目没有的机制：倒计时跑过 400 拍之后，只要
`TotalZombiesHealthInWave(当前波)` 掉到 `mZombieHealthToNextWave`（本波血量的 50%~65%，开局随机）以下，
就把倒计时**直接压到 200 拍**（约 3.3 秒）—— 所以原版里"你把这一波打残了，下一波马上就来"。
本项目只有 `early_advance` + `survival_ratio` 模式做了一半（只有写了 `wave_pacing` 的波次才生效，
40 关冒险模式一个都没写），清场奖励也只是把剩余倒计时加快 3 倍、还要先付 10 秒宽限。
影响：这一轮修好 `delay` 起算点之后，普通关卡（2500~3100 tick 的 `delay`）玩家把场上清干净仍要等
约 10~17 秒；原版同场景是 3.3 秒。长 `delay` 的关卡（旗帜波后的 4500）差距更明显。
怎么做：`WaveDirector` 里给每波记一个"起始总血量"（`spawnZombie` 已经知道每只的血量与 `healthScale`，
在 `PendingWaveSpawn` 上记首只出生时的场上总量即可），每拍比对存活总量，掉到阈值以下就把
`nextWaveTargetTicks` 压到 200；阈值与是否启用应当是关卡数据（`WavePacingData` 加两个字段，
默认沿用原版的 0.5~0.65 与 200），因为它会改所有已发布关卡的手感。
卡在哪：这是**新增机制**，会动到已发布关卡的整体节奏，需要先决定"默认开还是默认关"。


### 金币没有消费去处

钱包、掉币、通关结算、结算页都做了，商店页也做了，但**只有三件商品**（钉耙 / 卡槽 +1 / 阳光铲 I）；
Crazy Dave 的商店全套与图鉴式商品栏都没做。金币目前主要是进度展示，这是有意的阶段性取舍。
增益槽（`PlayerProfile.buffSlots`）与卡槽一样留了升级入口（`addBuffSlots`），同样没有商店去卖。

### 商店页的购买失败只有面板顶上那行 2 秒提示

选中与购买按钮已经有了（列表选中 + 右侧详情栏 + 右下"购买"），但**失败反馈**仍然只有面板顶上
一行 2 秒的提示：金币不足、已拥有、服务端拒绝（例如价格在客户端与服务端之间变了）都走它。
真要做得像样得让那件商品自己说话（行上标红 + 抖动，与卡槽条的 `refuseCard` 同一套语言），
那需要把 `InGameScreen` 的 `cardShake` 抽成共用件 —— 现在它在游戏内那一屏里。

### 标题页托盘的图标没有常驻文字

左下角那两块木牌**只有图标**（金币 / 种子包），名字在悬停提示里。这不是设计选择：托盘的两格加留白
必须放得进**窗口左缘到菜单列左缘**之间，而菜单列居中且 280 宽 —— 默认窗口下只剩 65 GUI 宽，
"图标 + 两个汉字"的格子要约 100。托盘现在会按可用宽度缩，所以格子只会更窄。
要常驻文字就得先给这一角腾地方：把菜单按钮的宽度从 `min(280, guiW-24)` 收窄是唯一不需要挪位置的办法
（`TitleScreen.menuGap` 已经把这个宽度算在一处）。

### 我是僵尸的失败画面仍是"房子被吃掉"

`InGameScreen` 的失败序列只有一套（`isDefeat()` → 房屋被啃的表演），而解谜关里玩家是僵尸方：
他输的意思是"僵尸没吃到脑子"，屏幕上却在演自家的房子被吃。影响只在这一段表演，
结算与胜负都是对的（`gameStatus` 才是玩家的胜负，见 `架构变更记录.md` 的 W9）。
做法：给这一套表演一个"从哪一边看"的开关，或者给僵尸方写一段自己的失败表演。

### 冰爆菇的三个数是我拍的，没有一局真玩过

`hits_to_freeze 3` / `shatter_multiplier 3` / `freeze_ticks 195`（`data/pvzce/projectiles/iceboom_bolt.json`
与 `plants/iceboom_shroom.json` 的 175 阳光、20 伤害、90 拍间隔）。原版**没有**"冰层累积"这套机制，
所以这三个数没有参照物，是按"一次冻结周期约 4.5 秒、碎冰那一发值三发"定的。
影响：可能过强（冻 3.25 秒本身就很硬）或过弱（20 DPS 低于双发的 26.7）。
怎么做：真玩一局「冰库」或一局无尽，把"冻了几只、碎了几只、哪一波开始顶不住"记下来再调。
卡在：**要用户拍板**——手感是玩家的判断，不是测试里能断言的量；数值出口只有那两份 JSON，改数不用改代码。

### 冰爆菇冻住的那一下，玩家看不出是谁冻的

被冻住的僵尸沿用寒冰菇那一套表现（`EntityUpdateS2C.frozen` → 脚下冰锥 + 全身冰色），
所以"冰爆菇第三发冻住这一只"和"寒冰菇炸了全场"在屏幕上是同一幅画。
影响：只有观感，机制与数值都不受影响。做法：给冻结分一档来源（协议加一个字段，
或让客户端在"冰层计数到顶"的那一刻放一枚一次性粒子），或者给冰弹做"命中时冰层加厚"
（前两发薄霜、第三发厚冰）。卡在：加协议字段要涨 `PROTOCOL_VERSION`，而这一条只买观感——先记着。

### 世界 5 的八株植物还没发出去

`卷心菜投手 / 花盆 / 保龄球 / 机枪射手 / 玉米投手 / 万寿菊 / 西瓜投手 / 冰西瓜`：定义与美术都在
（连图鉴条目都有），只是**没有任何关卡发它们**。世界 5 预计 10 关，正好够八株植物加两关的增益/工具。

### 图鉴不显示"这一关给这张卡"

未解锁的植物在图鉴里只有一句「未解锁」，玩家看不到"通关 1-9 就能拿到它"。
`LevelRewards` 只记"谁发"、不记"发给谁"，所以显示这一行要反查全部关卡定义（`BuiltInRegistries.LEVELS` 的 `rewards`），
或者在 `PlayerProfile` 旁边存一份反向表。与「没获得的增益没有说明」是同一件事的两半，真要做得一起做。

### 图鉴不显示原版那两行档位（"类型 / 强壮度"）

原版卡片背面有 `类型：攻击 - 远程`、`强壮度：中等` 这类档位，本项目没有对应字段：`PlantDef` 没有类型分类，
僵尸只有真实血量而没有"低/中/高"的档位。现在图鉴列的是**本项目自己的数**（植物的阳光/冷却/血量、僵尸的血量/速度/咬伤、
资源的价值）。要补原版那两行就得给内容加字段并逐条填五十多个值 —— 那是一次内容活，不是显示层的活。

### 图鉴里的僵尸没有"未解锁"

原版的图鉴是**奖品**：僵尸见过才进图鉴，没见过的格子里是一句 "not encountered yet"。这一版全列（26 只全在）。
要做成原版那样，需要一个跨关卡、跨世界的见过记录（`PlayerProfile` 旁边加一个 `SeenZombies` 集合，
`ZombieEntity` 第一次生成时登记），并且要决定它在沙盒世界里怎么表现。

### 没获得的增益靠挂锁表达，没有"为什么锁着"的说明

池子里未获得的增益画的是与固定卡同一个挂锁（`ChooseSeedsScreen.drawLockBadge`），点它只响一声。
玩家看不到"通关 1-9 就能拿到它"。最省事的是把它接到已有的提示框上（`client/gui/hud/HintBox` + `LevelHints` 的
`on_card_refused` 那条路），文案里点名是哪一关发的 —— 但 `LevelRewards` 只记"谁发"、不记"发给谁"，
所以要反查全部关卡定义，或者干脆在 `PlayerProfile` 旁边存一份"这个东西是哪一关给的"。

### 泳池的"潜水"只有美术那一层

`pvzce:submerge` 让潜水僵尸在水下时 `canBeHitByGround()` 为假、并播 `swim` 片段（那份片段的 mask 只画水面上的头与呼吸管），
但**没有"水面盖住身体"的那一趟渲染** —— 引擎的层级是"场景 → 实体"，水永远画在僵尸后面，
所以一只在水里的僵尸看上去是站在水面上而不是浸在水里。要做得像原版，需要在实体之后再画一趟只覆盖水格的半透明水面
（并且只盖到水线以下的部分），那是一件独立的渲染活。

### 潜水僵尸的"出水"是一个片段没用上

`Zombie_snorkle.reanim` 的 `anim_uptoeat`（浮出水面再开咬）没有对应的服务端状态钩子 —— 僵尸一开始啃植物就是 `eat`，
所以浮出的那几帧跳过了。要接上得给 `ZombieCapability` 一个"进食状态"钩子（现在只有 `walkState`）。

### 弹坑只有草坪那一版

原版还有屋顶（`crater_roof_left/center`）与水面（`crater_water_day/night`）的弹坑美术，都在 `refer/im7/images` 里，
但 `LevelServer.isBareGround` 只把草坪与裸地变成弹坑 —— 屋顶与水面需要各自的贴图与尺寸，是一件内容活。

### 杨桃只打了四个方向里的两个

`ProjectileRef` 只有横向的 `direction()`，弹丸的移动与命中判定都按"同一行"写。杨桃在原版是**五个方向**：
前、后、上、下、自身格。现在它打前和后。做法（四步）见 `架构-扩展点与约定.md` §8.44b：
加纵向标记 → 移动改成按 `(dx, dy)` → 命中改成"同一格" → 目标搜索按方向选；既有弹丸的 `dy` 全是 0，
要用既有测试证明行为不变。

## 关卡与编辑器

### 海豚骑士的跳跃按撑杆僵尸的 210 拍走

两个僵尸共用 `VaultCapability`，位移与抬升读的是撑杆僵尸 `jump`（43 帧）的表，而海豚骑士自己的
`anim_dolphinjump` 只有 16 帧 = **115 拍**。于是它落地之后还要在空中飘一拍才被服务端放下来。
修法有两步，都在数据与常量上：`jump_ticks` 已经可以从内容里读（`vault` 的字段），给
`dolphin_rider_zombie.json` 写上 `"jump_ticks": 115` 就够；曲线仍按归一化进度采样，所以拖长
只是把动作放慢，不会错位。卡在：改了要重新拍一次海豚关卡确认它不再"落地后滑一下"。

### 雪橇小队的四只间距与雪橇长度是两个数

`BobsledCapability.DEFAULT_SPACING` 是 0.625 格（原版 `(position + 1) * 50 px`），板子画的是
1.875 格长；两者现在对得上，但它们由**两处**分别决定（能力常量与 `tools/gen_bobsled_sled.py`
的 `WIDTH`）。要让"四个人正好坐在板子上"成为一个可算的事实，得让其中一处读另一处 —— 最省事的
是给板子定一个"一格多少像素"的常量，把两者都从它推出来。

### 地刺扎毁冰车是"同归于尽"，原版另有数值

`ZamboniCapability` 现在见到 `#c:walk_over` 的植物就让两者一起没：地刺被压碎、冰车直接
`damage(health())` 秒掉。这是"扎毁"的字面读法，也是一个地刺换一台机器。原版的这一对是**数值**：
地刺按自己的间隔给冰车固定伤害（车毁不是一击），并且只有地刺/地刺王有这个能力。
要照着原版做得把"植物能伤到车辆"变成一条数据（植物侧的 `vehicle_damage`，或者一个
`#c:spike` 标签 + 车侧的减免），而不是在这里写死一个 `health()`。

### 一波里雪橇小队算 1 只

`aliveByWave` 按波次条目计一，而雪橇小队一条目会多出三只随从，所以用 `max_alive` 的 `stockpile` 波会多放一点。`budget_cost: 4` 只覆盖按点数计价的 `budget` 波。
要精确就得让 `WaveDirector` 按"这一波实际生成了几具身体"记账。

### 玩偶匣的三片小云没被画出来

原版 `jack_explode_jack_small_clouds` 转换后每个粒子的 scale 都被读成 0（`ParticleScale .5,60 0` 那个已知的"两个数"坑，`powie` 当年也是这么丢的），渲染器一律跳过。
要它出现得手写一份粒子定义；今天爆炸用 `jack_explode_big_cloud` + `jack_explode_sproing` + `sfx/effect/explosion` 表现。

### 爆炸没有震屏

本项目没有镜头抖动这一套（要新加包字段或客户端规则）。玩偶匣在原版会 `ShakeBoard(4, -6)`，这里只有粒子与音效。


### 冰面融化只认"火系爆炸"，且不区分冰的种类

`ExplosiveCapability.melts_ice` 是内容开关（樱桃炸弹 / 火爆辣椒写着），**不是**"所有爆炸都会融冰"：
土豆雷与玩偶匣也是爆炸但不是火，这一点是刻意的。没做的是另外两件原版有、这里没有的：
**被冻住的僵尸/植物**（寒冰菇那套 `FROZEN`）不会因为爆炸而解冻，**冰面融化也没有任何表现**
（到点直接变草，原版也没有过渡美术，但一声"化开"的音效也没有）。

### 冰面的融化时钟不进存档

`LevelServer.iceTimers` 与 `craterTimers` 一样不写进 `level.dat`：读档回来，剩下的冰从零开始数三十秒。
对单机是"宽容一次"，对"续档接续一局正在收尾的冰面"是不一致。要修就照 `Scene` 分区旁边加一列
"每格还剩多少 tick"，弹坑也该一起。

### 屋顶世界（世界 5）还没做

原版 5-1 ~ 5-10 的棋盘（斜坡 + 花盆）、关卡与两株植物还没做；屋顶的僵尸（扶梯 / 投篮车）也还没有，
所以 `tools/original_levels.py` 里那两行（`ZOMBIE_LADDER` / `ZOMBIE_CATAPULT`）现在谁也发不出来。
4-10 发的卷心菜投手按原版就是世界 5 的第一株，世界 5 因此从花盆（5-1 发）接着往下排。

### 4-5 的进度条上没有"还剩几只花瓶"

恐怖花瓶这一关没有波次，而进度条画的是"波数"，所以 `InGameScreen.renderWaveBar` 直接 `return`——
玩家看不到还剩几个瓶子。原版的这一关连波次条都不画，但**本轮没查清原版到底给不给反馈**，
所以先不加：要做得先决定画在哪（波次条的位置 / 关卡名旁边），再决定口径（剩余瓶子数还是回合数）。

### 花瓶只剩"整片撒在右半边"，没有按列指定

`pvzce:scary_potter` 只写"从第几列起"和总数，`pvzce:grave_field` 只写总数 + 左边界，
而原版是按列写的（`AddGraveStones(6, 1)` 与 `ScaryPotterDontPlaceInCol(5)`）。
9 列棋盘上两者的分布看起来一样，宽棋盘或想让墓碑/花瓶避开某一列时要加字段。

### 玩偶匣的引信不掷骰子

`pvzce:jack_in_the_box` 支持 `fuse_roll_cells`（原版 `Rand(300)`），但内置定义写的是固定的 6.5 格——
"什么时候炸"要能被关卡作者与玩家一起推算，也才能被测试钉住。要让同一波每局不同就填那个字段。

### 雪橇小队的四只共用一个雪橇血量

原版是四只各自 270 点身体 + 雪橇 300 点"头盔"，这里是"领队带 300 点雪橇 + 三只随从"，
随从被单独打死不影响雪橇。原版的另一种读法（任意一只被打都算雪橇受伤）没做。


### 编辑器不认识 `buffs`

关卡编辑器的信息页/卡池页都没有"这一关的增益"这一项：

- **不会丢数据**：`InfoPage.buildLevelJson` 从载入的 JSON 出发，只覆盖自己拥有的字段，
  所以手写的 `"buffs"` / `"max_buff_slots"` **会被原样写回去**；
- **但也没有 UI 去编辑它们** —— 今天配增益只能手写关卡 JSON，或者用 `LevelBuffPlan.mapCodec()` 认的两个字段写在文件里。

最小的形状是在卡池页（`CardsPage`）下面加一行"关卡的增益"：一个多选列表（列出 `BuiltInRegistries.LEVEL_BUFFS` 的全部 id
+ 一个 `pvzce:player_choice` 复选项）加一个 `max_buff_slots` 数字框。`MechanicPages` 那种"按注册表生成一页"的做法可以直接抄。

### 编辑器不认识 `conveyor` 与 `placement_zone`

同上一条：手写的这两块不会被保存动作删掉，但也没有 UI 去编辑它们——小游戏关卡目前是手写数据。

### 编辑器不认识 `dialogue.timed` 与 `mechanics.schedule`

对话页会把整个 `dialogue` 块按自己认识的字段重写，所以**用编辑器保存一个带 `timed` 的包关卡会把定时台词丢掉**
（`slots` / `choices` / `speaker_name` 已经有编辑入口——「同台：…」对话框——不再属于这一条）；
`MutationMechanic.editorFields()` 仍然是空的，脚本变异只能手写 JSON。要补的话：对话页加"定时台词"一栏
（一个 `at_tick` + 一行台词的列表），变异机制加一个只读提示 + "在 JSON 里编辑"的说明就够 —— 一个可视化的脚本编辑器不值得做。

### 编辑器不认识 `endless_schedule`，无尽关卡也不进编辑器

`pvzce:endless_schedule` 是数据注册表，编辑器不认识它，也没有"轮"这个概念的 UI。而
`pvzce:yard/survival/` 下的九关（泳池无尽、四条草坪无尽、四个变异难度档、变异教程）由代码构造
（`server/level/EndlessLevels` 与 `common/level/mutation/MutationLevels`），编辑器对它们只能编辑文件里有的东西
—— 而它们根本没有文件。想改这几关就得改代码；反过来，变异目录（38 条）也只能是代码，这是有意的取舍。
> 出道题的曲线**是**数据：`pvzce:endless_schedule`（`data/<ns>/endless_schedules/*.json`）决定一轮多长、
> 哪些僵尸第几轮解锁、节奏怎么收紧，内置两份（`pool_endless` / `mutation_endless`）。
> 所以"难度太陡"是一行 JSON，不是一次改代码。

### 编辑器只编辑一个首通解锁

`rewards.first_clear` 手写多条时，编辑器只认第一条 `unlock` 并在保存时把**多余的 unlock** 规范化掉（会打一行日志）。
它没有 UI 的条目（今天的 `resource`）会**原样读写回去**，不会被保存动作删掉 —— 判定在 `InfoPage.readRewardLists`
（纯函数，`InfoPageRewardsTest` 钉住）。

### 编辑器画布不画关卡背景、仍按草坪几何画泳池关卡

关卡可以指定 `background`，游戏与选卡预览都按它画，但画布仍然是"地形画在一块空底上"——作者选完背景图看不见它，
也看不见 `hidden_scene_elements` 的效果（画布故意不隐藏，否则作者看不见自己画了什么）。而且画布不读关卡的 `background`，
所以泳池关卡在编辑器里按 9×5 的草坪格几何显示、水面也按格画。要补齐得让画布按 `LevelStage.cover` 的那套投影
把 1400x600 的舞台画进它自己的小视口。

### 编辑器画布不显示装备档位

画布上的僵尸是满血预览实体，`armor` 取 `NO_ARMOR`，`EquipmentArt` 把它当成"没磨损"画完整的那一张。
想在编辑器里摆"破了的路障"需要一个新的预览状态。

### 选卡页的棋盘预览在僵尸种类多时文字会挤在一起

`.smoke/w3b/seed.png`（3-6 的选卡页）里，右侧棋盘预览上的僵尸名**纵向重叠**，糊成一片。3-6 有 11 种不同的僵尸，
是第一批把这个问题暴露出来的关卡。`ChooseSeedsScreen.drawPreview` 逐只按 `cellY` 算标签位置，字号是
`clamp(previewH / count / 90, 0.45, 0.62)` —— 最小值 0.45 在种类多时会赢，而**一个名字可能折成两行**
（`ducky_tube_buckethead_zombie`），于是行距不够。要看的是"名字长到换行时怎么办"：要么预先算行数、
要么把列表截断并加一个"…"、要么把名字缩短到只留最后一段。**没有查清之前不要猜着改。**

### 奖励页上的增益卡用的是种子包的框

1-9 / 2-9 首通时，草坪上落下的与结算页相框里放的是**增益自己的图标 + 种子包的框**（`SeedCardRenderer` 的
`CardKind.BUFF` 只决定"不印价格"）。这不是占位，只是取舍：项目里没有第二套"奖励卡"边框，而且这一页说的是
"你拿到了新东西"，与种子包同一个语义。要给增益做一套自己的卡片边框的话，`SeedCardRenderer` 已经有 `chrome(...)`
（铲子卡就是那么换的），加一个 `BUFF_CARD_BACKGROUND` 即可。

### 奖项页的羊皮纸容不下多条正文

`AwardScreen` 的相框与羊皮纸是照 4:3 底图坐标写死的，宽屏下 `coverFit` 会把顶部木牌裁掉。
正文（`grants` 逐条的"名字 + `.desc`"）现在**锚在按钮上沿与 `NOTE_BOTTOM` 的较高者**，所以不会再压住
「继续」、纯金币那一支也稳定落在羊皮纸里；但一次发三件以上时，多出来的条目会落到羊皮纸下那块木板上——
只是**排版**上的妥协，不是丢信息（数不进正文的写成"还有 N 件"）。真要做正，得让相框/羊皮纸跟着窗口而不是
跟着底图坐标走，那是一次独立的布局活。与提示框、白光无关。

### 鼓点分析是一首一份的代码常量

`RhythmCharts.SONGS` 现在两首（终极之战、小游戏），每首的强度表都是 `tools/rhythm_onsets.py` 量出来
再**手贴回代码**的 Java 字面量。加第三首歌的代价因此是：跑一次脚本、贴一次常量、`-Ppvzce.smoke=
pvzce.writeRhythmLevels=true` 重写四张关卡、再把新四关加进一个集合 tag。生成器本身已经支持"没有分析
就退回匀速拍点谱"，所以这不是失败，只是"选一首歌就能生成一张跟着它的谱面"还没做到。
怎么做（最小的形状）：把表从代码常量挪成 `data/pvzce/rhythm/<event>.json` 那样的资源（一首歌一个文件），
生成器按事件 id 查；分析仍然离线跑（游戏不做音频分析，这是这一模式的前提）。
卡在：一份 profile 是一次手工产物，需要一个"谁来跑、什么时候跑"的答案——现在它是仓库里的一条常量，
跟着代码一起评审。

### `strike` 尚未覆盖所有攻击能力

节奏关卡"按键才开火"这条规则靠 `PlantCapability.holdsFire()` / `strike()` 两个钩子，
射手 / 投手 / 近战 / 锥形喷吐 / 地刺已经支持，回声铃兰也实现了停火和点名接力；
现有卡池与手写谱面会遇到的那族均有对应钩子。
**玉米加农炮、倭瓜、爆炸类仍然按自己的时钟行动**（它们不在四档的卡池里），所以一张把它们
塞进去的谱面会让这几株植物"自己打"。补齐的路很短（每个能力一次 `strike` 转发），
但需要先决定"瞄准型植物被点名时瞄哪里"：玉米炮要一个格子，倭瓜要一个落点。

### 判定窗口没有作者旋钮

三档窗口固定是飞行行程的 5% / 10% / 15%（`RhythmChartData` 的三个常量）。这一轮刻意如此——
"音符在判定线上就是 PERFECT"是这一关的全部可读性，一个能单独调窗口的字段会让画面重新变得不可信。
真要一个更松的模式，办法是把 `approach_ticks` 调长（窗口按比例跟着变长，音符飞得更慢），
或者加一个"整档难度"的乘数；两者都还没做。

### 四档的僵尸潮没有真人试过

波次表是照"移速 2.0~2.6 倍、出怪节奏 1.4~2.0 倍、6~10 波、每条 entry 五行、总量 39~104 只"
写出来的，`WavePacingMetricsTest` 只证明它们能结束（峰值 9~13 只同时在场上）。四档能不能守住、
专家档是不是**只能靠小推车**，得真人打一盘才知道；要调的旋钮全在 `RhythmCharts.TIERS`
（每档两个倍数 + 波次表）与关卡的 `initial_sun` / 卡池上。

### 客户端的 MISS 计数只是自己那份

屏幕上的 `MISS n` 是客户端按同一套算术自己数的（`RhythmPlay.sweepMisses`），服务端那份进存档、
**没有包发回客户端**。两边时钟差得离谱时（例如被校正而客户端没跟着）两边会不一致：
玩家看到的漏数与结算的对不上。要做的话是加一条"分数同步"包（服务端自己的 Score 定时下发），
代价是 HUD 从"零延迟的本地副本"变成"一个包之前的服务端数"。

### 声卡自身的播放延迟仍未量过（解码那一半已经修了）

歌与谱面同 tick 起，**整首解码的 149 ms 已经消掉**（预解码，见 `踩坑清单` 147），剩下的只有
"包 → 帧 → `alSourcePlay`"（约 1 tick）与**声卡自身的缓冲**（几十毫秒量级，随设备/后端变）。
以 PERFECT 窗口 4 tick（67 ms）衡量，后面这段还没被量过、也没有补偿。要量的话：用 OpenAL Soft 的
wave 后端（`ALSOFT_CONF` 指一份 `[wave] file=…` 的配置）把实际输出录成 wav，再与源文件做互相关，
差就是"引擎侧总延迟"；要补偿就把它做成玩家可调的偏移（同时作用于画面与服务端起点，否则两边判定会分叉），
或者用 `ALC_SOFT_device_clock` / `ALC_DEVICE_LATENCY_SOFT` 在运行时读。

## 数值与美术

### 骨架实体的静态阴影探测误报缺图

回声温室冒烟中，普通与铁桶僵尸的 `texture` 指向部件目录，`PvzceClient.drawEntityShadow`
仍用 `getOrLoad` 尝试整身贴图并输出缺图警告；骨架角色正常显示，阴影回落到椭圆。
影响：日志把正常的“没有整身静态图”写成缺失资源。怎么做：先用 `hasTexture` 探测再选投影或椭圆，
沿用 `踩坑清单.md` 的纹理探测约定。卡在：本轮只验证原创植物与关卡，没有扩展到既有阴影渲染修复。

高清化冒烟里冰爆菇也命中同一路径：骨架正文可正常显示，静态阴影仍尝试读取纹理目录。

### 冰冻事件的 ice_trap 粒子路径仍有缺图警告

高清化胶片出现 `pvzce:textures/particles/plant/ice_trap` 加载警告（`ParticleEngine.renderOne`）。
数据定义的 `look.texture` 实际是 `whitepixel`；需要单独核对粒子纹理选择与资源回退路径，不能把
名称回退误当成真实贴图。此次只完成原创植物资源密度提升，没有更改通用粒子解析。

### 粒子单位只覆盖"抛掷物"那一族
`tools/particles_to_pvzce.py` 的 `PROP_SPEED_DIVISOR` 只作用于原版用 `GroundConstraint` 标出的抛掷物
（头/手臂/帽子/旗帜等 20 条定义）。剩下 122 条仍按"像素/帧"换算，所以它们的速度比原版小 60 倍、自旋大 60 倍
——碎片类本该四散飞开，现在是原地淡出；同样的单位问题还让自旋读成 15000 度/秒、`ParticleScale .5,60 0` 被读成尺寸 0。
结构与修法见 `架构-实体与能力.md` §5.2 的注：把判据从 `thrown` 放宽到"没有 Friction 的弹道发射器"可一次修好，
但要单独过一遍截图。

### 关掉 shader 的水面仍是不含原版贴图的静态帧

`pvzce:water` 的水面贴图是原版 `pool_base.jpg`（`tools/gen_water_surface.py` 做成九格一张的 tile），
但 `renderFallback` 走的是 `textures/scene/water_frames/*` 那几张预烘焙帧，里面只有水色与岸线泡沫
——低画质开关或没有 shader 的环境下看不到云纹**也看不到那张漂移的焦散图**。泳池关卡 `disable_shaders: false`，
正常路径不受影响；要把降级路径也补上，得让 `tools/gen_water_frames.py` 把底图与焦散烘进帧里。

### 小推车只有两种车型

`MowerData.kinds` 是"哪一行放哪种车"（内容 id，客户端按 `mechanic/<path>` 取动画），泳池两行因此跑
`pvzce:pool_cleaner`；屋顶的 `RoofCleaner`（`refer/anim/RoofCleaner.reanim`）还没转，也没有屋顶关卡去用它。

### 焦尸美术的细分

`Zombie_charred_*`（巨人 / 矿工 / 小鬼各有自己的焦尸）还没转，今天所有僵尸都用同一具通用焦尸。

### 其余场景的蘑菇

夜晚的八种蘑菇到 2-10 为止已经集齐（小喷菇 / 阳光菇 / 大喷菇 / 魅惑菇 / 胆小菇 / 寒冰菇 / 毁灭菇 + 咖啡豆），
缺的是**其余场景的蘑菇**：忧郁菇、磁力菇、海蘑菇（它们属于泳池/浓雾/屋顶）。

## 系统与工具

### 联机（TCP 未接线）

TCP 骨架（`TcpPacketTransport`）在清理轮删除：它已修好语义但从未接线，与其留一个没人构造的实现，
不如等真做联机时按当时的需求写。缺的是握手、`server.properties`、玩家身份/Team 占位、断线重连与 delta 重放。
协议层不受影响：`PacketTransport` 是接口，换一个实现即可。

### 注册表同步与客户端资源同步

客户端目前依赖本地资源/数据包自行解析注册表（`PvzceClient.run` 里另建了一个 `PvzceResourceManager`）；
联机时应改为服务端按注册表下发定义。`PvzceDataLoader.RegistryData` 预留了"哪个注册表需要同步"的位置，
但目前只有目录名与 codec 两个字段。
> **语言键已规范化，界面串没有**：内容键是 `<注册表>.<命名空间>.<路径>`，界面串仍是手写的 `pvzce.*` /
> `gui.pvzce.*` 两套前缀。合成一套要动 200 个键与 38 个文件，是纯重命名，见 `架构-框架层.md` §3.1b。

### 注册式集成测试与渲染冒烟未建

`@PvzceGametest` 注册式集成测试与渲染冒烟（离屏 FBO + 图 diff）**未建**，所以界面没有自动化验证 ——
这批工具是第三阶段的规划（见 `03-第三阶段-精修完善.md` §3.6.1）。现状是 JUnit 单测/集成测试。
服务端/客户端流程可以直接起真的 `PvzceServer`/`PvzceClient` + `Connection.createMemoryPair()` 来测：
`testutil/ServerHarness` 与 `testutil/ClientHarness` 是这两个 harness 的唯一实现。

### 逐字号的字形缓存没有淘汰，只有"整页重来"

`FontFace` 的字形缓存以 `(码点, 设备像素尺寸)` 为键，页面满了（4 页）就 `recycle()` 全部丢掉重光栅。
一屏文字装不满一页，所以现状够用；但"同一个面以很多不同字号画很多不同的字"（编辑器里缩放预览、mod 自己传 scale）
会让缓存反复重建。要做的话是 LRU + 页内空洞回收，而不是加页数 —— 加页数只是把问题推后，显存却是实打实的。

### 变异的数值区间只有档位倍率，没有逐条调参

18 条变异里只有 6 条（`RateMutation` 那五条 + 危机/打地鼠/墓碑的间隔）真的用了难度档的倍率，其余是
"有/没有"或"一次性"的效果。如果以后要给单条变异配权重或强度曲线，`Mutation.weight()` 已经在接口上
（今天都是默认值 10），改法是给它加一个"档位 → 权重"的重载，而不是在 `MutationRegistry.roll` 里写按档位的特判表。

### 变异关卡没有专门的战报

四个变异关卡与普通关共用选卡页与结算页：失败时结算页显示"存活 N 波 · 击杀 M · 用时 T"（`GameStateS2C` 的三个字段）。
但没有"本局经历了哪些变异"的战报 —— 而这份数据现在是现成的：变异的 id 与抽到的数字已经在 `level.dat` 的
`Mutations` 块里，缺的只是把它读出来画一页。

### 增益选择没有"每关一份"的记忆

自动启用名单是**每世界一份**（`PlayerProfile.autoBuffs`），这是设计阶段定的：玩家勾一次"自动拾取"，
是想在所有关卡都自动拾取。如果以后想要"某些关卡自动开、某些关卡自动关"，那要改成按关卡存
（`saves/<world>/buff_prefs.dat` 之类），`LevelBuffSelection.planForRun` 是唯一的入口。

### 增益只在关卡开始前可选

`StartLevelC2S` 是唯一带增益的包，也就是"一局开始了就不能再改"。这是有意的（增益是选卡的一部分），
但如果以后要加"关卡中途开关增益"（调试命令、mod 覆盖、奖励解锁），需要一个新的包与一处
`LevelServer.activeBuffs` 的写入口 —— 现在那个字段只在构造与 `restore` 时被写，
`sporeRangeMultiplier` 每发射一次都重读，所以"中途改了立刻生效"这半边已经成立。

### 渲染批合并与图集

现状、成因与"要做对必须满足哪三条"见 `架构-客户端.md` §6.3。省 draw call 的收益几乎全在图集那一半，
而图集是一次独立的资源活（今天每个 texture id 一张贴图，实盘 1140 张 PNG / 170MB）。

### 骨骼混合与 Spine 后端未接入

今天的骨骼动画是逐部件贴图，没有骨骼空间插值，也没有第二条后端；`AnimationHandle` 的返回值在调用点被丢弃
（没有任何地方读它，也就没有"播完了"的回执）。

### 包只认目录，不认 `.zip`，也不校验 `pack.mcmeta`

数据包页（`PackScreen` / `PackSelection`）扫的是 `resourcepacks/` 与 `datapacks/` 下的**顶层目录**。
三件明确不做，做了才有必要改这一页：`.zip` / `.jar` 形式的包；`pack.mcmeta` 的依赖解析与 `pack_format` 校验
（现在只读它的 `description`）；**世界级**数据包目录（`saves/<world>/datapacks`）—— 今天只有 `gameDir/datapacks`。

### 容器碎片是自己切的九块，不是原版那九张

`tools/gen_pot_chunks.py` 把项目自己的瓶子贴图按包围盒切成 3×3，因为原版的碎片贴图不在 `refer/` 里
（`refer/im7/particles/VaseShatter.xml` 只有发射器参数，`IMAGE_VASE_CHUNKS` 没有对应 PNG，粒子转换器的
dry-run 一直列着这条跳过）。哪天那份贴图补进 `refer/`，把三个 `*_shatter` 粒子换成原版九张即可，
参数不用动 —— 它们本来就取自那份 XML。

### 种子包没有拾取/落地的声音与光效

种子包（`CardDropEntity`）现在只有卡面本身与一句服务端消息：落地没有音效、捡起来没有闪光、种下去用的是
植物自己的种植音。原版这几下都有反馈。要补的话走现成的 `emitEffect` + `PvzceSounds`，不必开新通道。

### 回合之间清场没有逐株植物的消失表现

`ScaryPotterMechanic` 进入下一回合时调 `LevelServer.clearPlants()`，玩家的植物是**整片瞬间消失**的，
只有一句播报。要做得像样：逐株播一个枯萎/被拔掉的表现（或一小段错开的延迟），并给一声提示音。

### 花瓶里的卡不会因为"这一关发不了这张卡"而换成别的

`vase_field` 的 `card` 写的是**卡 id**，校验只问"这个 id 能不能解析成一张卡"，不问"这一关的卡池里有没有它"。
今天四只花瓶里的卡都是玩家自己也可能选的普通植物，但这意味着一个关卡作者可以在一关里塞进一张该关根本不给选的卡
—— 玩家拿到它之后能不能种下去取决于 `canPlacePlant`，多半能种。要不要收紧（例如"必须在 `SeedOptions` 的池子里"）
是个设计问题：花瓶本来就有"关卡白送一张你没有的卡"的用法，所以先留着。

### 触控只做了"单指点击 + 滑动"

Wayland（自接 `wl_touch`）、Windows 与 X11/Xorg 都能用手指玩了，但手势只有两个。没做的：
**多指**（双指滚动/捏合；`wl_touch` 的 listener 只按 v5 事件集绑，第二根手指的 id 已经被忽略）、
**右键**（触控上没有右键：取消选卡还能靠"再点一次已选卡"，但把草坪上捡起来的种子包放回去只有右键一条路）、
**悬停提示**（`HoverTip` 有几处是唯一的显名途径，触控要靠长按，而长按又要和小推车按住 500 ms 放车、
Windows"长按=右键"排先后）、**屏内键盘**（控制台/编辑器/玩家名在触控设备上需要外接键盘：
GLFW 不会告诉系统"输入框获得焦点"）。
影响：触控设备目前可以正常玩主线，但上面的场景要么做不到、要么要用鼠标键盘补。
### Wayland 上不能拖动标题栏移动窗口

标题栏（`client/gui/WindowTitleBar`）的三大按键与双击最大化都能用，但**按住空白处拖动窗口**没有实现：
Wayland 客户端不允许自己设位置（`glfwSetWindowPos` 直接返回 "The platform does not support setting
the window position"），唯一正规做法是 `xdg_toplevel.move(seat, serial)`，而它需要 GLFW 私有的
`xdg_toplevel` 与一个输入 serial——GLFW 两个都不对外暴露（libdecor 那条路因为 GTK 插件在 JVM 里拒载
也走不通，见 `踩坑清单.md` 第 118/119 条）。
影响：窗口位置只能由合成器决定；GNOME 下仍可用 Super+拖动 或 Alt+F7 移动，所以不是死路。
怎么做：等 GLFW 把 `glfwSetWindowPos` 在 Wayland 上实现（上游 issue），或我们自己接一版
`xdg_toplevel`/`xdg_toplevel_drag_manager_v1`（本机 registry 有后者）——无论哪条都要先有不靠猜偏移量
拿到 toplevel 的办法。
**已经试过并失败**（`踩坑清单.md` 第 125 条）：`glfwGetWaylandWindow` 给回的指针不是 `struct wl_proxy`，
所以"当成 `_GLFWwindow` 再按偏移找 `xdg_toplevel`"找错了对象；要再试得换一条拿到 toplevel 的路
（上游 API / 自己建 surface 与 toplevel），不是再猜偏移量。

### HiDPI 缩放屏上点击会整体偏移

仓库里没有一处 `glfwGetContentScale` / `glfwGetWindowSize`：`guiMouseX` 拿 **framebuffer 宽度**去除
GLFW 报的**窗口坐标**，两者只在 contentScale = 1 时相等（本机实测 = 1，所以一直没暴露）。
影响：显示器一旦是 150%/200% 缩放（`monitors.xml` 里就有 scale=2 的配置），每次点击（鼠标或手指）都会
按 1/scale 偏移，表现就是"完全点不准"——而触摸设备几乎都是缩放屏。
怎么做：把换算收在 `PvzceWindow` 一处：光标统一以 framebuffer 像素对外（乘 `framebuffer/window`），
`warpCursor` / `setPointerPosition` 反向换算；冒烟钩子里"只记录不移动"的行为保持不变。

### loader fork 在 JDK 25 下会打 `ZipError` 过时警告

`SimpleClassPath` / `GameTransformer` / `FileSystemUtil` 都 `catch ZipError`，JDK 25 报
`[removal] java.util.zip 中的 ZipError 已过时, 且标记为待删除`。现在只是警告。
影响：将来某个 JDK 真删掉它时这三处会编译失败（loader 不在常规改动范围内，届时要分清是 fork 的问题
还是我们碰了什么）。
### 卡条上的 `<` `>` 是画出来的字符，点它等于选中第一张卡

`SeedCardBar.render` 把两个箭头当文字画在可视区**里面**，而 `slotAt` 的判定覆盖整个可视区，
所以点箭头会选中它下面那张卡（滚动只有滚轮）。触控这轮给卡条加了滑动，够得到了，但误点还在。
影响：鼠标用户点箭头得到的是"选中第一张卡"，不是"向左滚一格"。
怎么做：把两段箭头各自做成一个可点的小控件（或从 `slotAt` 的判定里让出去），最小形状是
`SeedCardBar` 加两个"点这里滚一格"的矩形 + 渲染时不再画在卡片命中区里。

### 界面文案有一半还是硬编码中文

语言设置（`config.language`）与语言表（`assets/pvzce/lang/*.json`，中文 777 键）都有了，引导页与
**视频设置页**会跟着切，但更早写的页面仍是硬编码中文字面量：标题页的"谁要玩游戏？"、难度页的副标题、
音量设置、商店、图鉴、编辑器…（`GuiLang.raw(key, 默认值)` 是现成的写法，缺的只是逐页替换）。
影响：把界面切成 English 之后，一半页面是英文、一半还是中文 —— 比全中文更像坏了。
怎么做：一页一轮，页内**所有**字面量走 `GuiLang.raw` 并往两个语言文件里补键；顺手清掉任何
"用标签文字反查设置"的写法（`VideoSettingsScreen` 那处已经这么改过，见 `架构变更记录.md` 的 W5）。

### `.git` 仍然偏大：36 MB 字体与历史里的自产大图

历史重写摘掉了原版素材与 `font/ui.png`，`.git` 从 283 MB 降到 177 MB。剩下的体积主要来自
**入库的 36 MB 字体**（四份 TTF，最大的 Noto Serif SC 14 MB）与 107 MB 原创立绘，它们都是
要保留的内容，属于正常代价。
影响：clone 要下 177 MB。若日后觉得太慢，可把字体与立绘移到 Git LFS（`.gitattributes` 目前
不存在，还没有任何 LFS 追踪）。
卡在：不是问题，只是取舍——现在没做，因为 LFS 会让"直接 clone 就能跑"多一个前置条件。

### 角色立绘的 PNG 没有优化，107 MB 里有不少水分

`textures/gui/dialogue/` 70 张，107 MB，平均 **1.5 MB/张**（中位 1430 KB、最大 2.83 MB），
主体是 63 张 1024×1536。这个量级对插画来说偏大——PNG 是无损格式，这类图通常能靠
量化调色板（256 色，`pngquant` 那一档）压到原体积的 1/3~1/2 而肉眼难辨；它们又是要打进
fat jar 的资源。
影响：仓库与 jar 都白背约 50~70 MB；clone 与下载都慢。若日后改 Git LFS，这也是要先做的事。
怎么做：跑一次量化，逐张**人工比对**再替换（肤色渐变与大面积平涂最容易出色带）；顺带统一
尺寸（现在除 63 张 1024×1536 外还有 7 张杂尺寸）。
卡在：不是缺陷，是取舍——量化有画质风险，而这是作者自己的美术，要不要压、压多狠该由作者定。
